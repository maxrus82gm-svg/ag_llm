## Web Alarm Ultra — диагностика и безопасное исправление WorkspaceBusyError

**Исполнитель:** Codex 007  
**Координатор и независимый verifier:** ChatGPT  
**Приоритет:** HIGH  
**Направление:** Ultra Chat / Shared Workspace Storage / Stage 3 TEST  
**Связанный FOLLOWUP:** `FOLLOWUP-WUA-S3-WS-WRITER-BUSY-001`

### 1. Исходная ситуация

Stage 3 TEST реализован; пользователь подтвердил отправку сообщений и сохранность истории после F5.

Независимая Windows CI выявила нестабильный сбой существующего теста:

`test_ultra_chat_storage.ConcurrencyTests.test_two_processes_write_raw_create_and_rename_without_losing_anything`

В полном прогоне один из двух процессов завершился с `context_storage.WorkspaceBusyError`. Пять отдельных повторов теста прошли успешно.

Доказательства:
- FAIL: https://github.com/maxrus82gm-svg/ag_llm/actions/runs/42040238153
- Повторы 5/5 PASS: https://github.com/maxrus82gm-svg/ag_llm/actions/runs/42059663160
- Review: `reports/CHATGPT-WEB23-CODEX-S3-TURN-REVIEW-20261105/review.md`
- Источник предыдущей задачи: `H-CODEX-000013`

**Причина ошибки не установлена.** Одиночный PASS не закрывает дефект, а единичный timeout не доказывает потерю данных.

### 2. Цель

Установить причину нестабильной блокировки Workspace при конкурентных операциях, устранить подтверждённый дефект, если он имеется, и доказать сохранность записей при нагрузке.

Результат должен различать:
1. Настоящую ошибку синхронизации.
2. Допустимый ограниченный отказ `workspace_busy` при занятом Workspace.
3. Проблему тестового окружения или самого теста.

Не исправлять симптом без анализа.

### 3. Область работ

**Основные файлы:**
- `context_storage.py`
- `test_ultra_chat_storage.py`

**Читать по необходимости:**
- текущие контракты №36, №36.1, №36.2;
- актуальные правила №18;
- адресные материалы предыдущей задачи и FOLLOWUP;

**Записывать:**

- собственные отчёты и доказательства в `reports/CODEX-WUA-S3-WS-WRITER-BUSY-REPAIR-001/`;
- собственную карточку только через штатный механизм `finish` после завершения отчётного пакета.

Изменения `run_store.py`, API, UI, CI workflow, shared docs и других файлов — только после отдельного согласования расширения scope.

### 4. Порядок исполнения

**Этап A — диагностика.**

1. Изучить `_workspace_writer_lock`, `_existing_workspace_writer`, Windows byte-range locking, reentrant-состояние и освобождение lock.
2. Разобрать исходный FAIL и условия Windows CI.
3. На одноразовых TEMP Workspace выполнить ограниченную серию многопроцессных проверок, включая сценарий из исходного теста.
4. Зафиксировать длительность ожидания, время удержания lock, успешные/неуспешные операции, длительные блокировки и нагрузки; без записи в реальные пользовательские Workspace.
5. Разделить доказанные причины, гипотезы и невоспроизведённые сценарии.

**Этап B — исправление по результату.**

Если дефект подтверждён, реализовать минимальный безопасный ремонт.

Запрещено:
- убирать обязательную блокировку;
- допускать двух одновременных писателей;
- отключать проверку Workspace ID;
- ослаблять no-follow / junction / path safety;
- подавлять исключения без доказательства сохранности;
- автоматически повторять неидемпотентную запись;
- просто увеличивать `WRITER_LOCK_TIMEOUT_SECONDS` без обоснования.

Если корректный timeout вызван длительным конкурентным удержанием lock, оформить это как диагностированный ограниченный отказ и предложить адресную меру. Нельзя выдавать такой случай за исправленный дефект.

**Этап C — регрессия.**

Проверить:
- исходный двухпроцессный сценарий;
- множество последовательных и параллельных RAW-записей;
- сохранность количества, ID, содержимого и порядка фиксации RAW;
- отсутствие повторов, потерь, частичных публикаций и неожиданных staging-файлов;
- конкурентное создание и переименование чатов;
- освобождение блокировки при исключении и завершении процесса;
- корректное ограниченное ожидание и ошибку `workspace_busy`, если блокировка действительно занята;
- сохранность существующих отказов на unsafe path / junction / foreign identity;
- соответствующие соседние Run Store и Stage 3 TEST-проверки, без изменения их реализации.

Для нового конкурентного теста нужен проверяемый oracle, а не только отсутствие исключений. При изменениях тестов сохранить исходный FAIL и объяснить, почему новые проверки выявляют прежнюю проблему.

Запустить адресные тесты, затем доступную применимую регрессию. Для Windows обязательно предоставить точные команды, число прогонов, PASS/FAIL/SKIP, версии Python и исходные логи. Недоступные испытания обозначить `NOT RUN`.

**BLOCKED / FAIL**, если:
- причина осталась неизвестной;
