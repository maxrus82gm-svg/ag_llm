## 1. Цель

Подготовить следующий инженерный слой Web Alarm Ultra к первому настоящему диалогу с GigaChat.

H32 уже реализовала и прошла независимую проверку:

`Ordinary Chat → final bytes → S2/S3a → SENT → один fake send → durable terminal → Turn/RAW/usage/reopen`.

Теперь нужно подключить к этой архитектуре **производственный по форме транспорт GigaChat**, чтобы его поведение можно было полноценно проверять через OFFLINE HTTP fixtures.

Целевой результат H33:

- настоящий формат GigaChat HTTP-запроса формируется существующим Ordinary Chat core;
- финальные байты после budget admission передаются в транспорт без повторной сериализации;
- HTTP/OAuth границы изолированы и подменяются тестовым механизмом без сети;
- ответ, ошибки, тайм-ауты и usage проходят существующий жизненный цикл Turn;
- невозможно осуществить реальную отправку через настройки браузера, TEST launcher, env-флаг или прямой недоверенный вызов;
- сохранены все необходимые блокировки до отдельного разрешения на REAL.

**H33 не является разрешением на выполнение реального GigaChat API-запроса.** Она подготавливает механизм и доказательства, необходимые для последующей независимой приёмки.

## 4. P1 — Безопасный GigaChat transport adapter

Реализовать минимальный транспортный слой, переиспользующий имеющиеся функции и HTTP-поведение.

### 4.1. Контракт отправки

Транспорт принимает только уже подготовленную сервером попытку.

Необходимо обеспечить:

- неизменяемые финальные UTF-8 bytes от существующего serializer;
- согласованность model ID, endpoint identity, wire hash и policy revision;
- доверенное построение endpoint и заголовков вне пользовательского тела запроса;
- точное тело HTTP как `content=wire` либо эквивалент без повторного JSON encoding;
- отсутствие `json=payload` после сохранения и проверки wire hash;
- явный timeout и разбор статуса/JSON;
- совместимость с результатами существующего Ordinary Chat core.

**Физическая отправка допускается только при наличии действительного серверного разрешения**, доказанного непосредственно перед транспортной границей.

Нельзя принимать из HTTP body, UI или конфигурационного файла поддельный admission receipt, произвольный transport, endpoint URL или разрешение на REAL.

### 4.2. OAuth и секреты

Переиспользовать существующий `gigachat_transport.get_access_token()` по назначению, но в H33 не вызывать настоящий OAuth endpoint.

Для OFFLINE-тестов нужна строго контролируемая fake token-provider boundary.

Не допускаются:

- реальные credentials в fixtures, логах, GitHub или отчётах;
- вывод Authorization, access token, секретных частей тела запроса;
- замена существующей OAuth-системы новой;
- реальный OAuth-запрос ради проверки подготовки транспорта.

Соблюдать U5: технические журналы не должны раскрывать секреты; исходный незамаскированный дубль не создавать без отдельного утверждённого механизма хранения.

### 4.3. Явный fail-closed REAL gate

После H33 текущий Web Alarm должен по-прежнему честно сообщать, что REAL недоступен.

Нельзя:

- менять текущий `real_available: false` на `true`;
- включать REAL обычным env-флагом, аргументом запуска или настройкой UI;
- использовать синтетическую H32-политику как разрешённую реальную;
- подключать неподтверждённую модель или endpoint без проверенной политики лимитов;
- обходить S3a через отдельную transport-функцию.

Разрешено создать внутренний код транспорта и OFFLINE-инъекцию, однако **никакой путь из штатного пользовательского Web Chat не должен допускать реальный сетевой запрос** до следующего согласованного этапа.

Если независимое включение реального транспорта невозможно без изменений обязательного B2-контракта, сохранить fail-closed и описать точный blocker. Не ослаблять контракт ради зелёных тестов.

## 5. P1 — Интеграция с Turn, S2/S3a и обработкой ответа

Интегрировать транспорт в уже проверенный механизм H32 без переписывания Turn Service.

Обязательный порядок:

1. Существующий сервер формирует и сохраняет Ordinary Turn snapshot.
2. Core создаёт окончательный HTTP payload и wire bytes.
3. Проверяются модель, контекст, endpoint, политика, пользовательская идентичность и допустимость попытки.
4. S2 разрешает попытку в соответствующем явно определённом scope.
5. S3a выполняет durable reserve и подтверждённый `mark_sent`.
6. Транспорт получает **ровно те же bytes**.
7. Response/error классифицируется действующим Ordinary core.
8. Terminal фиксируется устойчиво и проверяется до публикации результата.
9. Turn/RAW/usage/reopen используют существующее хранилище.

Для H33 реальные условия пунктов 4–6 воспроизводятся только в разрешённом синтетическом OFFLINE-сценарии. Отдельная реальная policy и подтверждённые model caps остаются необходимыми перед LIVE.

Проверить и не допустить:

- повторной отправки после `SENT`;
- повторного OAuth/HTTP из-за автоматического retry;
- превращения timeout в доказанный `NOT_STARTED`;
- потери неизвестного расхода при `UNKNOWN`;
- публикации успешного assistant RAW без подтверждённого durable terminal;
- двойного учёта input/output/reasoning;
- изменения сохранённых предпочтений другого чата;
- восстановления старого ledger через обнуление.

Использовать `extract_usage()`. Отсутствующие provider-поля отображать как `UNKNOWN`, не подменять нулями. Если reasoning включён в output, не суммировать его второй раз.

## 7. P2 — OFFLINE HTTP и adversarial tests

Все тесты H33 выполняются без реальной сети и реальных credentials.

Использовать существующий H27/H32 isolation guard, синтетические Workspace и разрешённый HTTP mock/fixture transport. Реальный сетевой вызов должен блокироваться до выхода из процесса.

Нужно проверить минимум следующие группы:

**A. Положительный сценарий**

- Подготовка GigaChat-совместимого тела.
- Exact-byte identity на HTTP-boundary.
- Один успешный fake HTTP response.
- Сохранение Turn/RAW/usage.
- Reopen/F5-совместимость серверных данных.
- Несколько независимых чатов и Workspace.

**B. Отказ перед отправкой**

- S2 DENY.
- Нет или повреждён ledger.
- Несовместимый старый engine fingerprint.
- Неверный endpoint/model/policy revision.
- Подмена финальных bytes или хеша.
- Недействительный/повторный admission receipt.
- Неизвестный provider cap.
- Попытка включить REAL из UI/config/env.

Во всех этих сценариях ожидается **0 физических HTTP-вызовов**.

**C. Неопределённые исходы**

- Timeout после допуска.
- Transport error после возможной отправки.
- Crash-window после durable `SENT`.
- Отмена непосредственно до/после admission.
- Ошибка терминальной записи.
- Повтор idempotency key.
- Два конкурирующих отправителя.

Неизвестный расход должен оставаться консервативным. Запрещена скрытая повторная отправка.

**D. Безопасность и совместимость**

- Никакого настоящего OAuth/DNS/external HTTP.
- Секреты не попадают в журнал.
- TEST launcher H31 F-01 продолжает отказывать неподтверждённым сценариям.
- STANDARD и Tkinter не повреждены.
- H29 per-chat settings/usage сохранены.
- Предыдущая H32 synthetic one-send регрессия проходит.
- S1/S2/S3a и релевантные quality/isolation tests выполняются штатными runner-ами.
- Отсутствующий исторический pinned RAW честно обозначается NOT RUN, не заменяется придуманными данными.

Добавить хотя бы два осмысленных негативных контроля, демонстрирующих, что отключение pre-send проверки или замена отправляемых bytes после admission действительно обнаруживается тестами.

В отчёте различать positive PASS, ожидаемый RED и неожиданный FAIL.

## 11. Критерии готовности H33

**H33 готова к независимой приёмке**, если одновременно:

- транспорт GigaChat имеет проверяемый производственный формат запроса;
- exact bytes до budget admission и в HTTP send совпадают;
- весь путь тестируется OFFLINE без внешнего доступа;
- S2/S3a и Turn lifecycle переиспользованы и не ослаблены;
- отсутствуют неконтролируемые повторные отправки;
- тайм-ауты, отмена, ошибки и UNKNOWN обрабатываются консервативно;
- история и usage не повреждаются;
- негативные контроли обнаруживают намеренное ослабление защиты;
- H31/H32 и относящиеся предыдущие регрессии сохранены;
- реальные provider limits и недостающие B2 gates честно перечислены;
- нынешний UI и сервер не могут запустить REAL через конфигурационный обход;
