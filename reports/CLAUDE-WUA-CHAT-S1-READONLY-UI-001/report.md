## 4. Безопасное чтение: как выполнено каждое требование

| Требование БЛОКА 1 | Как выполнено | Проверено |
|---|---|---|
| `Host`, `Origin`, `Sec-Fetch-Site`, метод, параметры | Общий помощник с folder picker. Только GET; разрешены лишь `before` и `limit`, по одному разу; ID проверяются регулярными выражениями до любого обращения к диску | HTTP O1–O3, T1, D3; мутанты H03, H04, H05 |
| Чат принадлежит Workspace | Каждая карточка: имя папки = `chat_id`, `workspace_id` = идентичность папки | R: список, D2; мутант C11 |
| ID совпадают с именами каталогов и RAW-файлов | Имя файла = `message_id`, `chat_id`, `workspace_id`; дубликаты отсекаются | R: история; мутанты C04, C05 |
| Traversal, symlink, junction, reparse | ID без разделителей; звенья `.ultra` не могут быть reparse point; файл открывается без следования (`FILE_FLAG_OPEN_REPARSE_POINT`); проверка по дескриптору — обычный файл с одной ссылкой | R: junction на `.ultra`, `chats`, папку чата и `messages`; жёсткая ссылка; мутанты C02, C03 |
| **Подмена пути между проверкой и чтением** | Корень Workspace фиксируется его итоговым путём один раз за чтение. После открытия итоговый путь файла (`GetFinalPathNameByHandleW` по дескриптору) обязан совпасть с ожидаемым. Каталоги проверяются так же, со следованием. Данные читаются из уже проверенного дескриптора | R: подмена `messages` на junction **после** проверки каталога и **между перечнем и открытием**, с поддельными файлами той же идентичности; мутант C01 |
| Лимиты фактически прочитанных файлов и байтов | Перечень останавливается на 2 000 записях. Сумма размеров по `stat` до чтения ≤ 64 МиБ. Файл > 4 МиБ не читается. Каждое чтение `read(limit + 1)` по бюджету, который уменьшается фактически прочитанными байтами | R: лимиты, «файл больше своего stat», «рост после перечня»; мутанты C06–C10 |
| Размер ответа | Страница до 200 сообщений и ~8 МиБ содержимого, режется только между сообщениями; слишком большое сообщение — заглушка с размером | D6; мутант H09 |
| Повреждённый JSON и дубликаты | Счётчики причин, остальные сообщения видны; повреждённый диалог не скрывает другие | R, D2, D5; мутант C12 |
| Нет записи даже при ошибках | Чтение не вызывает `ensure_*`. Снимок имён, размеров, времени (по `os.lstat`) и SHA-256 до и после всех GET, включая ошибки, совпадает | R только чтение, D7, D1 (в папке без `.ultra` она не создаётся); мутант C13 |
| Нет утечек путей, данных, токена | Исключения ядра — только коды; ответы без путей; токен только в ответе возможности | D1, D2, D5, D8, D9; мутант H08 |
| Безопасный вывод | Только `textContent`, `innerHTML` нет | U3, E9; мутант U03 |
| Работа без folder picker | Возможность чтения не связана с `enable_folder_picker` | C1–C3; мутант H01 |
| `--disable-ultra-chat` | Возможность `disabled`, история 403; операторская панель, EVM, folder picker работают | C3, C5, U7 |
| `disabled` / `non_loopback` / `invalid token` раздельно | Разные коды и тексты | C3, C4, T1, U6, U7 |

Локальная возможность **не** защищает от других программ того же компьютера, которые обращаются к loopback-порту с правильным `Host`: они могут получить токен (контракт этапа 0, §7.1.1). Собственная аутентификация пользователя ОС не создавалась.

## 5. Что увидит пользователь и как открыть тестовый экран

**Открыть на синтетических данных** (настоящие Workspace и хранилище Web Alarm не затрагиваются):

```text
.venv\Scripts\python.exe reports\CLAUDE-WUA-CHAT-S1-READONLY-UI-001\tools\demo_ultra_chat.py --port 8790
```

Затем открыть в браузере `http://127.0.0.1:8790/`. Ctrl+C останавливает сервер и удаляет временную папку. С ключом `--disable-ultra-chat` видно состояние отката.

Что видно на экране:

1. **Верхняя панель.** Три раздела: «Ultra Chat» (выбран), «Операторская панель», «EVM · Подключения Ultra».
2. **Слева.** Четыре демонстрационных Workspace с состоянием: «История Ultra найдена», «В папке нет истории Ultra». Ниже — диалоги выбранного Workspace: повреждённый показан неактивным пунктом «Диалог повреждён», junction — «Ссылка вместо диалога — не читается».
3. **Справа.** Самый новый диалог открывается сразу на последних сообщениях. «Показать ранее» подгружает страницы по 50 сообщений, не сбивая место чтения.
4. **Метки.** Старая ошибка Tk — красный блок «Ошибка выполнения (старая запись), не ответ модели». Ещё есть «Ответ не сохранён» и «Прервано · исход неизвестен». Текст `<b>…</b><script>…</script>` выводится буквально.
5. **Состояния.** «Показана не вся история: …», «История слишком большая для просмотра. История не показана и не обрезана», «В этом диалоге нет сообщений», «История недоступна: …».
6. **Значок модели EVM.** «Модель: …» или «Модель не выбрана — откройте EVM».
7. **Поле ввода и «Отправить».** Неактивны, с пояснением, что отправка появится на следующем этапе.
8. **Прямые ссылки.** `…/#operator` открывает операторскую панель, `…/#evm` — EVM. Выбранная ранее TASK восстанавливается в операторской панели, как раньше.

## 7. MANUAL ENGINEERING REVIEW (TEST-ENG-01)

**Просмотренные ветви и порядок операций:**

- `_StorageAnchor` → `_verify_directory` (lstat, затем итоговый путь со следованием) → `_scan_directory` (ограниченный перечень) → `_read_file_bounded` (открытие без следования → `fstat` → число ссылок → итоговый путь → размер → `read(limit + 1)`). Поведение при `missing`, `unreadable`, `too_large`, `unsafe_storage_link`, `damaged`.
- Адаптер: проверка маршрута до токена; привязка по реестру; индекс Run Store читается так же, как в `run_store`: каноничный или новейшее поколение по ревизии; при отсутствии индекса классификация честно уходит в `legacy` или `run_index_unavailable`.
- Сервер: выделенная проверка происхождения даёт folder picker прежние коды и тексты. Его 16 тестов — PASS; инвентаризация изменений доказана байтами (§6.6).
- Страница: эпохи против поздних ответов; один повтор после `ultra_chat_token_invalid`; токен только в переменной сценария; блок двойного нажатия; прокрутка.

**Найдено и исправлено самим исполнителем до сдачи:**

1. **Проверка каталога без следования была ложной защитой.** Каталог, открытый с `FILE_FLAG_OPEN_REPARSE_POINT`, даёт итоговый путь самого junction, равный ожидаемому, и подмена после `lstat` не видна. Исправлено: каталоги проверяются со следованием, подмена ведёт в чужую цель. До запуска тестов.
2. **Мобильная раскладка.** Общее правило операторской панели `aside{max-height:330px}` действовало на панель чата, и при ширине ≤ 850 px содержимое наезжало на историю. Найдено при визуальной самопроверке, исправлено (`max-height:none`). После п. 5 панель — `<nav>`, и общее правило `aside` на неё не действует вовсе.
3. **Диалог открывался на ранних сообщениях страницы, а не на последних.** Исправлено; подгрузка ранних сохраняет место; добавлен тест U5.
4. **Заголовок недоступной истории был «Диалог».** Теперь название берётся из списка; тест U4.
5. **Регрессия, найденная первым полным прогоном** (`evidence/first_full_all.json`: 1024 = 1021 PASS / 2 SKIP / 1 ERROR).
   - Существующий `test_web_alarm_ui_ux` закрепляет, что на странице ровно три области `aside`/`main` операторской панели. Боковая панель чата была ещё одним `<aside>`.
   - Классификация TEST-FLAKY: PRODUCT DEFECT в моей разметке, не флейк.
   - Исправлено в `ui.py`: панель чата — `<nav aria-label="Workspace и диалоги Ultra">`. Тест не менялся.
   - После исправления: модуль и соседние UI/server/folder picker — 36/36, затем полный набор заново (§6).

**Гипотезы, проверенные и отвергнутые:**

- «Чтение меняет время каталогов» — нет. Это устаревшая копия отметок NTFS в родительском каталоге, которую видит `DirEntry.stat`. Первый FAIL сохранён (§6.5), оракул переведён на `os.lstat`.
- «Чтение с FILE_SHARE_DELETE не мешает писателю» — неверно ещё на этапе 0 (P12). Поэтому читатель держит дескриптор минимально. Под одновременным писателем Tk отказов записи не наблюдалось (§6.4); это наблюдение, а не гарантия.

**Рассмотренные альтернативы:**

- Отдельный модуль ядра вместо добавления в `context_storage.py` отвергнут: правила формата RAW остаются у одного владельца, существующие функции не тронуты.
- Хранить выбранный диалог в `localStorage` не стал: операторские тесты сверяют своё хранилище, а память выбора не нужна для первого результата.

**Пограничные случаи:** временные файлы писателя; файл, исчезнувший между перечнем и открытием; запись без `schema_version` (старая) и с более новой версией; пустой и отсутствующий `messages`; курсор на исключённое сообщение (404); регистрация с нестандартным ID; повреждённый индекс Run Store.

## 9. Риски и предложения на следующий этап

1. **Каждая страница перечитывает всю историю чата** (до 2 000 файлов / 64 МиБ), потому что порядок задаётся `created_at` внутри файлов. Для реальных чатов (десятки сообщений) это незаметно. Для настоящего постраничного чтения на этапе 2 нужен упорядоченный индекс сообщений чата (контракт этапа 0, §7.3).
2. **Параллельные запросы не ограничены.** `ThreadingHTTPServer` с токеном позволяет одной локальной программе запускать много чтений по 64 МиБ. Это вне модели угроз (локальные программы); при необходимости — ограничение одновременных чтений.
3. **Медленная сетевая папка в реестре** задержит список Workspace: для каждой читается `workspace.json`. Можно вынести статус в ленивую загрузку.
4. **Повреждённая запись в реестре Web Alarm** даёт 404 `unknown_workspace`: реестр не различает «нет» и «повреждено». Список при этом показывает `registry_unavailable`.
5. **Ответ форматируется с отступами** (`_send_json`, `indent=2`). Предел 8 МиБ относится к содержимому сообщений; итоговое тело чуть больше.
6. **Путь Tk не изменён** и по-прежнему уязвим к P1–P6 этапа 0. Тесты это закрепляют характеризацией (старые функции ведут себя по-прежнему). Исправление пути Tk — этап 2.
7. **Две независимые настройки модели** (Tk `ui_state.json` и EVM) остаются, как отмечено на этапе 0.
