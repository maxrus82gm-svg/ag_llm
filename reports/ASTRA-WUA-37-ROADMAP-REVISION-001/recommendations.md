# Рекомендации по синхронизации документации

TASK: `ASTRA-WUA-37-ROADMAP-REVISION-001`. Дата: 2026-10-26. Автор: Астра / Codex.  
Статус: **ПРЕДЛОЖЕНИЯ ДЛЯ НЕЗАВИСИМОЙ ПРОВЕРКИ; НЕ ВНЕСЕНЫ И НЕ УТВЕРЖДЕНЫ**.

В этой задаче изменяется только №37. Ниже перечислены адресные изменения другим владельцам. Их исходные байты зафиксированы в `evidence/baseline.json`; положения прочитаны локально. Публикацию и актуальный HEAD независимо проверяет координатор после пользовательской передачи. Номера строк служат ориентиром для исходной базы; устойчивый адрес — имя раздела.

## 1. Что согласовать в первую очередь

1. Принять программу-кандидат №37 или вернуть конкретные замечания. Её этапы 0–7 не являются новыми TASK ID.
2. Отдельно решить вопрос Ordinary Chat в RT-002: политика простого диалога включена в исторически отложенный V-13. Предлагается выделить только эту часть в текущий приоритет, сохранив остальные P2-направления отложенными.
3. На этом основании синхронизировать №20 §5а и №24, не менять принятые условия безопасности. Затем закрепить контракты данных и проверки в №03/11/36.2/36.3.
4. Обновлять карточки, реестры и текущие статусы только по факту независимой приёмки и пользовательского решения. Техническая готовность этой редакции ещё не означает принятие нового маршрута.

## 2. Адресные рекомендации

### R01. №24 — приоритеты и границы совместной работы

**Раздел:** `24_План реализации Web Alarm Workspace.md`, «Direction and sequencing / 2026-10-14 — approved priorities, no rescope» (исходная строка 33); «Статус документа»; «Канонический маршрут после RT-001 / PLAN APPROVAL EP-RT001-001».

**Существующее положение:** после завершения WA4-R предполагается независимый анализ интеграции Ultra; бюджетные сервисы могут развиваться параллельно. Ниже сохранены исторические snapshots WA4-R и утверждённый recovery route.

**Предлагаемое изменение:** добавить датированное уточнение текущего приоритета: «№37 описывает поэтапный Ultra Chat с единым ядром. Изолированная offline-разработка допускается по отдельным назначениям после принятия нужной базы и разделения файлов с LLM15/WA4-R. Условия WA4-R, WARN/GATEWAY REQUIRED/STRICT и файлового исполнения сохраняются; ни Chat, ни EVM не закрывают их». Привести текущую краткую карту в соответствие только после утверждения №37. Историческую запись 14.10 оставить с адресом нового решения.

**Причина:** снять устаревшее универсальное ожидание полного WA4-R для любой работы с Chat и одновременно не разрешить конкурирующие изменения общего сервера/UI.

**Утверждение:** требуется пользовательское принятие новой последовательности и редакторское назначение владельцу №24; новая приёмка WA4-R этим не даётся. Существующую единственную Wiki-связь №24 → аналитика Астры сохранить, дополнительных связей к аналитике не добавлять.

### R02. №20 §5а — расширение B2 для Ordinary Chat

**Раздел:** «RT-002/B2 — ЕДИНСТВЕННЫЙ текущий маршрут реализации Ultra», таблица predecessors, строки S1/S2/S3a/S3b/S5/S9, D/V-13; абзацы о единственном активном Codex implementation TASK и минимальной последовательности.

**Существующее положение:** S2 принят как чистая политика с ограничением независимого исполнения; production-защита ещё отсутствует. S3b охватывает все физические отправки. Ordinary Chat не имеет самостоятельного подтверждённого маршрута/роли. S6b требует принятия S13a и S6a; V-13 отложен.

**Предлагаемое изменение:** добавить отдельную датированную таблицу дополнения «Ordinary Chat: маршрут → владелец → политика → резерв → физическая попытка → usage → проверки». В ней:
- S1 — инвентаризация обычного чата и всех путей его вызова из Tk/web.
- S2 — явная роль/маршрут и область лимитов; не использовать фиктивный executor или mcp_chat.
- S3a — общий устойчивый журнал резервов, повторов, UNKNOWN и восстановления.
- S3b — включить новый путь в полный охват до HTTP, без частной приёмки нового пути за весь S3b.
- S5/S9 — неизменяемая политика принятого Turn и полный учёт по attempt ID, с сохранением существующих predecessors.
- D/V-13 — только после отдельного решения выделить политику простого диалога из отложенного перечня.

**Причина:** общий импорт политики не гарантирует ограничение расходов. Новый UI не должен создать обход принятого B2 или независимый журнал.

**Утверждение:** отдельное утверждение дополнения B2 обязательно; числовые defaults, UNKNOWN/missing profile, бюджеты и пределы попыток — явные пользовательские решения. **S13a + S6a → S6b сохраняется без сокращений**. Этап 6 №37 не переименовывается в S6. Ограничение на одну Codex implementation TASK не снимается общим разрешением архитектурной параллельности.

### R03. №21 — отдельная хронология нового маршрута и метрик

**Раздел:** вводное правило «Старые записи не переписываются задним числом; correction добавляется новой записью»; датированные записи 14.10 по S1 и S2.

**Существующее положение:** записи различают доказательства исполнителя и независимый source review; S1/S2 не прошли новый независимый executable-прогон на тех SHA. Исторические метрики R-031 относятся к агентскому runtime.

**Предлагаемое изменение:** после каждого фактического решения/этапа добавлять новую запись с точными источниками, статусом проверки и открытыми ограничениями. Для Chat учитывать Turn, RUN/attempt, модель, ревизию политики, фактические отправки/отказы, provider-reported/cached/processed input/UNKNOWN; отдельно отмечать offline=0 физических вызовов и разрешённый live. Сопоставления расходов проводить на одинаковых сценариях, данных и политике. Не объявлять диагностические delta-файлы экономией контекста провайдера.

**Причина:** не смешивать старые измерения, аналитическое принятие и будущую работающую защиту.

**Утверждение:** для записи факта достаточно предусмотренного closeout владельцем после доказательства; изменение политики и критериев метрик требует решения вместе с R02. Сами факты прошлого не пересогласуются и не удаляются.

### R04. №03 — модель Chat / Turn / RUN / TASK

**Раздел:** «CURRENT — TASK BLOCK / RUN STORE IDENTITY» (133), §13 «Identity сообщений», §15 «Когда сохраняется RAW», §18 «Multi-turn Chat storage и Executor Task-Scoped Context», §39 «Persistence после restart», §46 «Per-Chat Model Assignment».

**Существующее положение:** описана цепочка Chat → Task Block → RUN и постоянный message_id; user RAW сохраняется до API, assistant RAW — после успешного завершения. Это ещё не контракт устойчивого Turn. В исходниках старого Tk встречается сохранение диагностического результата ошибки как assistant RAW.

**Предлагаемое изменение:** добавить отдельно помеченную целевую модель Ordinary Chat: Turn хранит принятие/состояние/повторы и ссылки на RAW; RUN/attempt — исполнение и диагностику; Web Alarm TASK — разрешённые агентские действия; технический task_block не равен обязательной TASK. Уточнить формат исходов legacy-записей и отделить отображение истории от разрешённого контекста. Описать стабильные message_id, локальное повторное завершение, ключ повтора, порядок фиксации, UNKNOWN после неясной отправки, защиту общего индекса Workspace и совместимость обоих UI. Привязку модели фиксировать для принятого Turn.

**Причина:** существующая схема не определяет восстановление незавершённого запроса и может ошибочно потребовать TASK на каждую реплику.

**Утверждение:** сначала согласовать контракт этапа 0; публикация как **целевая** архитектура допустима после решения, как **реализованная** — только после принятия соответствующих этапов. Не переписывать старые RAW ради соответствия новому тексту.

### R05. №11 — назначение модели и единый сервис запроса

**Раздел:** «CURRENT IMPLEMENTATION STATUS», §3 «MODEL REGISTRY», §8 «Модель по умолчанию и модель конкретного Chat», §9.1–9.4 о политиках контекста, §13 «Provider Adapter», §23 «Не создавать отдельные интеграции для каждой функции».

**Существующее положение:** начальная глобальная MAIN CHAT MODEL допускается; per-Chat assignment — следующий этап. Реестр общий, контекст и права различаются по ролям.

**Предлагаемое изменение:** текущую EVM описывать как выбор предпочтения из общего реестра, без утверждения готовой доступности API. Целевой Ordinary Chat фиксирует модель и разрешённый контекст на принятие Turn; последующая глобальная смена не меняет уже ожидающий запрос. Уточнить, что существующий gigachat_transport предоставляет OAuth/URL/usage, а общий сервис обычной переписки ещё требуется выделить; обе оболочки пользуются одной реализацией. Planner OFF не является реализацией обычного безопасного чата.

**Причина:** предотвратить расхождение модели, истории и учёта между UI.

**Утверждение:** контракт вместе с этапом 0/4; фактический статус изменять только после реализации и проверки. Новых моделей, credentials store и внешних вызовов эта правка не назначает.

### R06. №23 — полномочия Web Alarm при появлении чата

**Раздел:** «Future integration direction / 2026-10-14 — USER APPROVED STRATEGY, NOT GO» (49).

**Существующее положение:** один владелец TASK/state/mutation/recovery/evidence и адаптеры Ultra; runtime Tkinter нельзя импортировать без проверки; WA4-R gates сохранены.

**Предлагаемое изменение:** дополнить разграничением: сервер обычного чата владеет своим Turn/историей, но не получает второй набор полномочий на управляемые файлы; агентские tools подключаются только через соответствующие разрешённые механизмы Web Alarm. Проверка HTTP-клиента для истории, изменения модели и send устанавливается явно, защита одного folder picker не наследуется другими маршрутами.

**Причина:** уточнить границу приватных диалогов и управляемых операций, не требуя полного агентского TASK на каждое сообщение.

**Утверждение:** архитектурное уточнение после принятия №37; любые новые permissions, API или rollout — отдельная инженерная задача и проверка безопасности.

### R07. №18 — понятный язык технических планов

**Раздел:** «DOC-TASK-READABLE-01 — Понятные пользователю названия задач и жёлтая метка» (141) и «DOC-CHANGE-01 — Проверка влияния документационной правки и порядок записи» (266).

**Существующее положение:** первое правило регулирует понятность названий задач; второе — влияние и сохранение истории. Отдельного общего требования объяснять каждый инженерный этап на естественном русском в этих разделах нет.

**Предлагаемый текст:** «Технические планы объясняют на естественном инженерном русском языке цель этапа, действия, используемую основу, результат, проверку, зависимости и границы. Английские имена сохраняются для точных программных сущностей, API, идентификаторов и устойчивых терминов. Новые сущности получают короткое объяснение. Существенная смена плана сопровождается сравнением прежнего и нового решения, причиной и статусом утверждения».

**Причина:** распространить полезный формат №37 на будущие планы без требования переписывать исторические доказательства или точные технические названия.

**Утверждение:** только владелец №18 после отдельного решения пользователя. Рекомендуется самостоятельный подраздел о языке инженерных документов со ссылкой из DOC-TASK-READABLE; если вводится новая нормативная обязанность, оформить новый Rule-ID/contract либо изменение версии по DOC-VERSION, а не менять смысл прежнего @1 незаметно. В этой задаче новый общий Rule-ID не присвоен.

### R08. №36.2 и №36.3 — будущие профили проверок

**Разделы:** №36.2 — «Матрица инвариантов: 13 независимых групп» (116), «Ведение каталога и совместимость» (200), «Предложения на следующие задачи (НЕ реализовано)» (206); №36.3 — «Файловая область Ultra (параллельная работа)» и §1 «Какие свойства обязаны сохраняться». Для Chat предложен новый подраздел матрицы, без изменения результатов прежних Windows/HTTP/UI-проверок.

**Существующее положение:** Web Alarm и Ultra имеют разные профили и границы файлов; новые runtime-контракты нельзя принять только по source review. Тесты Ultra находятся в корне; общий каталог/CI не переезжает сам собой.

**Предлагаемое изменение:** добавить адресную матрицу этапов №37: безопасное чтение/принадлежность/суммарные лимиты/RAW filename и duplicate IDs; общий писатель и межпроцессные сбои; повтор Turn; UNKNOWN/отмена/поздний ответ; смена модели в очереди; offline-сетевой запрет; B2 до физической отправки. Разделить локальные проверки, независимый Windows/visual результат и отдельно разрешённый live. Для каждого сценария определить наблюдаемый oracle; покрытие одного маршрута не выдавать за весь B2.

**Причина:** проверки будущих задач должны попадать в накопительную базу, а не оставаться только обещаниями roadmap.

**Утверждение:** координатор уточняет фактический подраздел профиля по актуальной редакции при выдаче implementation TASK. Изменение тестов/runner/CI — отдельный write-scope; это предложение не даёт разрешения на код. Реальную Windows-приёмку EVM необходимо закрыть отдельно.

### R09. Blueprint LLM — порядок интеграции

**Раздел:** §6 «Как не создать двойную работу при переходе в веб», особенно п.3 «Завершить текущий этап Web Alarm, затем организовать одну сквозную интеграцию».

**Существующее положение:** единое ядро и постепенный перенос сохранены, но краткое описание порядка может восприниматься как обязательное ожидание всего WA4-R.

**Предлагаемое изменение:** после утверждения №37 уточнить: подготовка контрактов блока идёт с этапов 0/4; обычный Chat разрабатывается разрешёнными изолированными шагами; файлы и права WA4-R согласуются; визуальный Blueprint — последующее направление. WUA-3 остаётся историческим обозначением First Blueprint Node. Принцип одного исполнения без дублирования OAuth/контекстов/защит сохранить.

**Причина:** убрать противоречие очередности, сохранив авторскую цель Blueprint.

**Утверждение:** отдельное согласование изменения авторского Blueprint; не переносить в него новую программу автоматически. Тактический журнал Blueprint получает только датированную запись решения, если владелец сочтёт нужным.

**Причина:** сохранить подлинность принятого исследования и убрать двусмысленность исполнения.

### R11. Текущие статусы и карточки после приёмки

**Разделы:** №34 — верхний «HANDOFF / WEB_14 — 2026-10-26 / Astra rev2 bounded PASS, user decision next»; №08 — «FREEZE INDEX / USER DIRECTION 2026-10-25»; персональная карточка Codex — БЛОКИ 1–4; №06 — новая датированная запись независимого результата, без исправления прежних verdict.

**Существующее положение:** аналитика принята, маршрут ещё кандидат; EVM/WA4-R/B2 и frozen MCP имеют свои ограничения. В карточке новая БЛОК 1 активна, хотя старый текущий handoff №34 говорит об ожидании новой задачи.

**Предлагаемое действие:** координатор после публикации и независимой проверки фиксирует эту TASK, точный SHA редакции №37, verdict и пользовательское решение. Затем по действующему DOC-TASK-CLOSEOUT-OWNER / DOC-TASK-HANDOFF-USER выполняет архивирование и закрытие карточки; следующую задачу выдаёт пользователю, не записывает автоматически. В №08 достаточно актуального указателя на принятый №37, если маршрут утверждён. MCP остаётся FROZEN; его старый independent acceptance не закрывается этим отчётом.

**Причина:** отличать фактическое завершение документационной работы от implementation GO и не оставлять конфликтующие оперативные статусы.

**Утверждение:** только координатор в разрешённом closeout после публикации/проверки; USER PLAN APPROVAL фиксируется только после реального решения пользователя. Точные секции иных реестров (№05/001 и т.п.) определяет их владелец при закрытии, правок в них от исполнителя нет.
