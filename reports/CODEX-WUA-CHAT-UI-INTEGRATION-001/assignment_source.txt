
**TASK ID:** `CODEX-WUA-CHAT-UI-INTEGRATION-001`

**Название:** Подключение существующей Ultra к веб-интерфейсу Web Alarm Ultra — проверка и доводка пользовательского сценария.

**Исполнитель:** Codex 007  
**Координатор и независимый проверяющий:** ChatGPT WEB21  
**Проект:** `ag_llm / Web Alarm Ultra`  
**Приоритет:** HIGH  
**Основание:** прямое решение пользователя продолжать разработку интерфейса силами Codex.

## 1. Цель

Уважаемый Codex!

Продолжаем утверждённую пользователем программу №37, не изменяя её архитектуру и последовательность этапов.

Наша задача — обеспечить понятную и проверяемую работу существующего веб-интерфейса Ultra Chat с данными старой Ultra (Tkinter).

Не создавать новое ядро, второе хранилище, отдельный реестр Workspace или ещё один механизм подключения моделей.

**Ожидаемый пользовательский результат:**

Пользователь запускает Web Alarm Ultra, подключает уже существующий Workspace через предусмотренный системой механизм, видит сохранённые чаты и историю, может создавать и переименовывать диалоги в рамках уже реализованных операций.

При этом данные остаются общими для старой Ultra и веб-интерфейса.

## 2. Что необходимо сделать

### 2.1. Проверить существующую реализацию

Изучить фактическую связку:

- `Start_WebAlarm.bat`
    
- `web_alarm/launcher.py`
    
- `web_alarm/ui.py`
    
- `web_alarm/ultra_chat.py`
    
- `web_alarm/server.py`
    
- `web_alarm/workspace_registry.py`
    
- `context_storage.py`
    

Определить, какие функции уже работают, какие только представлены в интерфейсе и какие остаются неподключёнными.

Не реализовывать повторно существующие функции.

### 2.2. Проверить подключение Workspace

На изолированном синтетическом Workspace выполнить сценарий:

1. Создать тестовые данные через существующее ядро Ultra.
    
2. Зарегистрировать Workspace предусмотренным Web Alarm способом.
    
3. Открыть Ultra Chat.
    
4. Выбрать Workspace и существующий диалог.
    
5. Прочитать сохранённую историю.
    
6. Создать и переименовать тестовый диалог через веб-интерфейс.
    
7. Убедиться, что изменения доступны через общее хранилище.
    
8. Повторить открытие после перезапуска.
    

Если возможно безопасно проверить фактическое чтение этих данных старой Tkinter-оболочкой — сделать это отдельно. Если нет — указать `NOT RUN`.

Никаких тестов на настоящих пользовательских диалогах.

### 2.3. Довести пользовательский интерфейс

Если существующие элементы интерфейса недостаточны, разрешается адресно исправить:

- понятный переход к существующей регистрации Workspace;
    
- объяснение, как открыть историю старой Ultra;
    
- различие между пустым, недоступным и частично прочитанным Workspace;
    
- отображение ошибок без раскрытия локальных путей и секретов;
    
- обновление списка диалогов и истории;
    
- сохранение понятного состояния выбранного Workspace и Chat;
    
- доступность элементов при изменении размеров окна.
    

Не создавать новый API регистрации или отдельный мастер переноса данных, если существующих возможностей достаточно.

### 2.4. Проверить ограничения

Кнопка отправки сообщений должна оставаться недоступной до отдельного разрешённого этапа.

Выбор модели в EVM не должен изображать успешное подключение к API или работающий inference.

Не изменять действующую вкладку Blueprint LLM и её контракты №43.

## 3. Технические границы

**Разрешённый кодовый scope:**

- `web_alarm/ui.py` — адресные изменения интерфейса;
    
- `test_web_alarm_ultra_chat_ui.js` — проверки поведения;
    
- `test_web_alarm_ui.py`, `test_web_alarm_ui_ux.py` — только необходимые UI-проверки;
    
- `reports/CODEX-WUA-CHAT-UI-INTEGRATION-001/` — отчёт и доказательства.
    

Другие файлы допускаются только для чтения и тестирования в разрешённой изолированной среде.

Изменения серверного хранения, `run_store.py`, `context_storage.py`, `web_alarm/server.py`, Blueprint, OAuth и провайдерных адаптеров не разрешены.

Если обнаружена проблема общего ядра — описать её с воспроизводимыми доказательствами и предложить отдельную задачу.

## 5. Обязательные проверки

Проверить штатные и отрицательные сценарии:

- Workspace зарегистрирован, отсутствует, недоступен или повреждён;
    
- список чатов пуст либо содержит несколько диалогов;
    
- частичная история не отображается как пустая;
    
- переключение Workspace не показывает данные предыдущего;
    
- повторное создание не производит неожиданные дубли;
    
- переименование сохраняется после повторного открытия;
    
- небезопасный текст RAW не исполняется как HTML;
    
- ошибки доступа, недоступный сервер и восстановление после перезапуска отображаются корректно;
    
- существующие EVM и Blueprint остаются работоспособными.
    

Тестирование выполнять на синтетических данных, без платных API и реальных LLM-запросов.

Перед запуском тестов проверить их побочные эффекты. После испытаний `Start_WebAlarm.bat` должен остаться в STANDARD. Если возврат не подтверждён — `RESTORE_BLOCKED`.

Проверки через реальную Windows GUI фиксировать отдельно от автоматических тестов. Невыполненное обозначать `NOT RUN`.

Код публикует пользователь. Независимую приёмку выполняет ChatGPT.
