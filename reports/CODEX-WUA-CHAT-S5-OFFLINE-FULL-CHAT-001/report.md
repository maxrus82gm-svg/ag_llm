## Общий путь

Web и TEST-панель существующего `UltraApp` используют один `OfflineUltraChatService`. Он подключает уже существующие WorkspaceRegistry, TurnService, S4A и S4B fixture transport. Turn остаётся владельцем попытки, восстановления, RAW и Run Store. Сервис оболочек хранит только ссылки на активные экземпляры TurnService, чтобы запросы состояния и отмены находили того же владельца во время отправки.

Сервер принимает TEST-профиль только с явной инъекцией временного реестра и loopback bind. Создание Workspace принимает название, а путь выделяется сервером внутри временного корня. Маршруты чата используют действующие отдельные read/write capability, Host/Origin и проверки размера. Настоящий STANDARD проверен на отказ Stage 5 отправки. Tk TEST открывается до загрузки обычного UI state и агентского интерфейса.

Каждый новый Turn получает явный model ID из зарегистрированных моделей. В контекст входит маркер выбранного чата и до одной последней подтверждённой пары user/assistant в пределах лимита. Пара читается только из выбранного Workspace/Chat и сверяется с исходом Turn. S4B фиксирует снимок и request_ref при приёме. Явный повтор исходного ключа использует сохранённую привязку, даже когда выбранная модель или история уже изменились. Перед отображением assistant RAW проверяется подтверждённый результат в Run Store.

Отправка, отмена, смена чата и проверка статуса доступны в обеих оболочках. После отмены активной попытки поздний ответ сохраняет доступный usage и оставляет UNKNOWN. Повтор ключа после нового Python процесса вернул исходный результат при запрещённом вызове fake. Для прерванного ACCEPTING без user RAW после перезапуска может потребоваться повторный ввод исходного текста. Восстановление использует тот же ключ.

## Запуск TEST для проверки

Из корня репозитория используется существующий запускатель и адресный профиль из пакета.

```powershell
.\Start_WebAlarm.bat --config "reports\CODEX-WUA-CHAT-S5-OFFLINE-FULL-CHAT-001\launch_stage5.json"
```

Профиль открывает Tkinter и печатает локальный URL для Web. Обе оболочки используют один временный корень этой сессии. Fake в профиле задерживает ответ на 1,5 с для ручной проверки отмены. После штатного выхода временные данные удаляются. Восстановление проверено отдельно на том же временном корне при смене экземпляра сервера, Tk окна и Python процесса. Штатный конфиг имеет active=standard, исходный BAT совпал с baseline.

Итоговые HTTP, Tk и JS проверки привязаны к финальным SHA.

Первый браузерный прогон не открыл модальный prompt, затем встроенная форма прошла фактическую проверку. Финальный TEST-маршрут завершает оборванное соединение, а повтор получает сохранённый результат.

Guard зафиксировал девять ожидаемых блокировок connect, DNS и credential value в трёх наборах. Проверены также veto на OAuth и HTTPX. Реальных provider/OAuth вызовов 0. Внешние данные не участвовали в запуске. SHA-256 595 файлов пользовательского хранилища и 10 файлов редактора сверены с baseline.

## OPEN и сдача

Чистая Windows установка по §2.4, новая независимая CI, полный Ultra suite и отдельная проверка визуальной доступности на всех размерах экранов имеют статус **NOT RUN**. Исторический `WorkspaceBusyError` остаётся UNKNOWN / OPEN. Воспроизведённый здесь WinError 10053 относится к доставке HTTP-ответа TEST. Следующий шаг — один коммит пользователя по allowlist в manifest и независимая приёмка WEB24. Реальные API, OAuth, Colibri и B2 находятся вне этого результата.

Штатный finish и readback сохраняются в `evidence/finish.stdout.txt`, `task_record.json` и `finish_receipt.json`.
