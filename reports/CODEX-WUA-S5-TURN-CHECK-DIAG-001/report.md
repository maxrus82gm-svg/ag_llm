## Итог и пределы

Механизм проверки читает состояние уже отправленного запроса. В Stage5 при
сохранённом ключе используется GET by-key, иначе GET latest текущего чата;
он не отправляет новый запрос модели. Успешный запрос проверяется и после
завершения, и после F5. В нашем прежнем браузерном прогоне одна отправка
`S5_TURN_DIAG_01` дала одну пару user/assistant и серверный SUCCEEDED.

Подтверждены два дефекта отображения: слабая обратная связь проверки и
ложная метка прерывания у активного запроса. Исчезновение после отмены/F5
пока известно только из сообщения пользователя. Сохранность или удаление
RAW этого отменённого запроса не установлены. Полный PASS продукта не выдан.

## Полторы секунды и назначение кнопки

`review_fixture.py:46–48` специально делает `asyncio.sleep(1.5)` перед ответом
fake transport. Это окно наблюдения TEST, а не обязательный срок нажатия.
`checkTurn` обновляет историю во время исполнения, поэтому ошибочная метка
прерывания становится заметна именно при раннем нажатии. После завершения
POST также обновляет историю, и следующий GET обычно возвращает те же факты.

Проверка нужна для восстановления ясности после потери связи/подтверждения.
Она не проверяет смысл текста, не останавливает выполнение и не оценивает
качество ответа. Размещение постоянной кнопки, условного уведомления между
сообщениями или действия только при задержке остаётся UX-решением F1.

## Отмена/F5, RAW и контекст: разные вопросы

Точный пользовательский эпизод: после отмены сообщение имело неопределённый
исход, после F5 исчезло из интерфейса. Не известны его Turn ID, ключ, момент
отмены, выбранный после F5 Chat, RAW и HTTP-представления. Этот эпизод сохранён
как USER_REPORTED / UNREPRODUCED, а не как доказанная потеря данных.

Код commit user RAW вызывается при приёме, до исполнения. Cancel после старта
пишет UNKNOWN и событие отмены; поздний ответ может не стать assistant RAW.
Чтение истории идёт через `read_chat_history_bounded`, затем классификацию и
пагинацию. Classifier не удаляет user на основании UNKNOWN: D2 возвращает
его с outcome no_answer. При этом чистая проверка D2 не доказывает сохранность
файла на диске и не исключает сбой на другом участке пути.

Контекст следующего Stage5-запроса строится отдельно из истории. Селектор
ищет последнюю подтверждённую SUCCEEDED-пару offline_chat_fixture, проверяет
идентичность user/assistant и bound размер (до 1024 UTF-8 байт сериализованного
текста каждого сообщения). Unanswered user сам по себе туда не включается;
при отсутствии пары получается только system. Текущий новый user передаётся
как новый запрос, это не означает повторную отправку отменённого старого user.

Следовательно возможны одновременно: user RAW сохранён, виден в истории,
не входит в будущий контекст. Это штатное ограничение текущей Stage5-проекции,
а не объяснение исчезновения из UI. Гипотезы для F3: смена выбранного Chat
после reload (UI по умолчанию выбирает newest), ошибка/исключения чтения,
пагинация или несогласованная история, реальный дефект хранения. Ни одна из
них не подтверждена для отменённого сообщения пользователя.
