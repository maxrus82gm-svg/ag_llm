## 1. Цель

Развить уже работающий Ultra Chat до безопасного принятия пользовательского сообщения.

После выполнения должно существовать понятное серверное состояние Turn, которое:

- сохраняет идентичность пользовательского запроса;
    
- фиксирует сообщение в общем RAW-хранилище;
    
- защищает от дублирования при повторной отправке;
    
- связывает запрос с выбранной моделью, разрешённым контекстом, политикой и попыткой исполнения;
    
- допускает безопасную работу с имитатором;

## 4. Реализация

### 4.1. Канонический Turn

Реализовать устойчивую сущность Turn на основе общего Workspace/Chat storage.

Обязательные сведения:

- `turn_id`;
    
- `workspace_id`, `chat_id`;
    
- `idempotency_key`;
    
- `user_message_id`;
    
- идентичность запроса или его проверяемый fingerprint;
    
- зафиксированные ссылки на модель, подключение, роль, контекст и политику;
    
- состояние Turn;
    
- идентичность попытки и связь с RUN там, где безопасный существующий контракт это допускает;
    
- ссылка на ответный RAW и сведения об ошибке/неопределённости, если применимо.
    

Конкретную версионированную схему определить после изучения действующего кода. Не вводить лишние сущности и вторую машину состояний.

### 4.2. Приём и повтор запроса

Ключ повтора создаётся клиентом и сохраняется для восстановления неопределённого HTTP-ответа.

Обязательно:

1. Один ключ с одинаковым содержимым возвращает тот же Turn.
    
2. Один ключ с другим содержимым отклоняется как конфликт.
    
3. Два одинаковых текста с разными ключами создают два намеренных Turn.
    
4. Повтор после перезапуска не создаёт новый пользовательский RAW.
    
5. HTTP-успех допускается только после необходимой устойчивой фиксации.
    
6. Если ответ HTTP потерян, клиент сначала выясняет состояние исходного Turn, а не создаёт новый запрос.
    

Переиспользовать `context_storage.commit_raw_message()` с заранее определённым `message_id`. Не возвращаться к `append_raw_message()` с новым UUID при повторе того же Turn.

### 4.3. Состояния и восстановление

Описать и реализовать достаточный минимальный lifecycle: принятие, ожидание/подготовка, попытка, результат, отказ, отмена и `UNKNOWN`.

Состояния и переходы должны иметь проверяемые правила.

После сбоя система должна определять, какие факты уже устойчиво сохранены, а какие неизвестны.

Особенно важно:

- не превращать неизвестный результат в `SUCCESS`;
    
- не считать отмену доказательством отсутствия отправки;
    
- не запускать повторную потенциально платную попытку автоматически;
    
- не создавать второй assistant RAW при повторном событии результата;
    
- поздний ответ не должен незаметно изменить уже отменённый или завершённый Turn.

Учесть открытые:

Если для полноценной записи RUN необходим ремонт существующего `run_store.py` или небезопасный путь `.ultra/audit`, **не обходить проблему собственным хранилищем**. Сохранить воспроизводимое доказательство, корректно ограничить готовность этой части и запросить отдельную адресную задачу.

### 4.5. HTTP

Добавить минимальные серверные операции принятия Turn и чтения его состояния через существующую Ultra Chat authority.

Обязательно:

- проверка Workspace и Chat ownership;
    
- защита Origin, метода, Content-Type, размера и формы запроса;
    
- отдельное право записи, не выводимое из токена чтения;
    
- безопасные коды ошибок без путей и секретов;
    
- недопустимость доступа к чужому Workspace/Turn;

Сервер не должен запускать внешнюю модель из этого маршрута.
