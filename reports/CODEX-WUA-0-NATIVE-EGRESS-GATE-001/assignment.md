## 1. Главная цель

Уважаемый агент 007 (Codex), предлагаю продолжить исследование безопасного подключения обычного ChatGPT к Web Alarm через MCP.

Предыдущая задача AM07 успешно подтвердила работоспособность синтетического HTTP CONNECT → SOCKS5 адаптера: 36/36 PASS. Однако это не доказало сетевую безопасность настоящего `tunnel-client`.

Теперь необходимо разработать и доказательно обосновать **Native Egress Gate**, который исключит любой прямой выход в интернет из процессов нашей MCP-интеграции в обход разрешённого V2Ray.

Целевая архитектура:

`ChatGPT → Secure MCP Tunnel → tunnel-client → HTTP CONNECT → SOCKS5 → V2Ray/sing-box → разрешённый удалённый маршрут`

Если существующий sing-box уже имеет пригодный HTTP/mixed inbound, допускается предложить вариант без промежуточного адаптера.

**Никаких прямых Windows outbound connections, DNS leaks, transparent fallback или альтернативных маршрутов для MCP-цепочки.**

Это требование относится ко всем процессам, составляющим MCP-цепочку, включая их дочерние процессы. Оно не является разрешением изменять сетевую политику всей Windows или отключать сеть других приложений.

## 3. Абсолютная сетевая граница

1. Запуск настоящего `tunnel-client` с любой потенциальной внешней сетью.
    
2. Запуск Cloudflared или иных дочерних сетевых процессов.
    
3. Реальные подключения к OpenAI, Cloudflare, MCP hosted endpoints и сторонним серверам.
    
4. Любые прямые исходящие соединения к внешним IP или DNS вне разрешённого V2Ray.
    
5. Проверка безопасности путём намеренного реального обхода прокси.
    
6. Изменение рабочего V2Ray, sing-box, firewall, Windows DNS, TUN, системного proxy, VPN или маршрутов.
    
7. Загрузка пакетов, исходников и зависимостей через Git, GitHub, curl, wget, pip, npm, go mod или аналогичные механизмы без отдельного разрешения пользователя и подтверждённого защищённого маршрута.
    
8. Использование реальных токенов, секретов, API keys или tunnel credentials.
    

**Если гарантия отсутствия прямого соединения не установлена, любые настоящие native-тесты имеют статус BLOCKED.**

Python audit hooks, proxy environment variables, `NO_PROXY`, localhost-bind и отсутствие наблюдаемых ошибок не считаются достаточной OS-level изоляцией.

## 4. Gate A — источник и точный граф сетевых соединений

В пределах локально доступных verified-исходников исследовать:

- Control-plane и secret transport.
    
- MCP Streamable HTTP и STDIO.
    
- OAuth discovery / token exchange.
    
- Harpoon.
    
- Proxy health checks.
    
- DNS resolution.
    
- Redirects, retries, reconnect и fallback.
    
- Global/component/binding proxy overrides.
    
- Environment proxy settings.
    
- Cloudflared и остальные дочерние процессы.
    

Для каждого сетевого пути установить:

**Инициатор → целевой endpoint → используемый транспорт → источник proxy policy → возможный обход → механизм запрета.**

Подтверждения разделять на `SOURCE VERIFIED`, `STATIC HYPOTHESIS`, `NOT VERIFIED`, `BLOCKED`.

Если официальный исходный архив локально недоступен, не скачивать его самостоятельно. Выполнить разрешённую часть и оформить точный `SOURCE PACK BLOCKED` с перечнем требуемых файлов.

## 5. Gate B — исследование изоляции Windows

Разработать инженерное решение, которое ограничивает именно MCP-клиент, адаптер и их дочерние процессы.

Рассмотреть:

- Отдельную disposable Windows VM без внешнего сетевого адаптера, NAT, шлюза и DNS для первых native offline tests.
    
- Изоляцию на уровне Windows Filtering Platform или другого реально принудительного OS-level механизма.
    
- Ограничение исходящих соединений каждого процесса и всего дочернего дерева.
    
- Независимое подтверждение того, что новые дочерние процессы не наследуют неограниченный интернет-доступ.
    
- Запрет UDP, внешнего DNS, IPv6 direct и альтернативных интерфейсов в тестовом окружении.
    
- Отказ всей MCP-цепочки, если защищённый маршрут недоступен.
    
- Автоматическую остановку теста при нарушении границы.
    
- Точный rollback для возможной будущей установки изоляции.
    

**На данном этапе только исследование, проектирование и допустимые read-only проверки.**

Не создавать новую VM, не включать Hyper-V, не устанавливать драйверы и не менять firewall или другие системные политики без отдельного USER GO.

Если подходящая изолированная среда уже существует, её наличие само по себе не разрешает запуск EXE: сначала подготовить доказательство изоляции и запросить отдельное разрешение.

## 6. Gate C — HTTP/SOCKS5 и V2Ray

На основании AM07 сравнить:

**Вариант A:** существующий HTTP/mixed inbound sing-box.

**Вариант B:** отдельный локальный HTTP CONNECT → SOCKS5 адаптер.

Сравнить безопасность, совместимость с native-клиентом, обслуживание, возможные обходные пути и последствия отказа.

Проверить, насколько возможно без реальных сетевых запросов:

- Кто владеет портами `10808` и `10814`.
    
- Есть ли read-only подтверждение фактически загруженной конфигурации.
    
- Можно ли установить HTTP/mixed protocol без предположений по GUI.
    
- Есть ли подтверждение выбора remote outbound.
    
- Какие DNS и DIRECT правила могут влиять на MCP.
    

Не подключаться к живым listeners и не проводить сетевые пробы без отдельного разрешения.

**Важное:** даже исправный HTTP→SOCKS5 адаптер не доказывает, что sing-box отправляет трафик через защищённый remote outbound.

## 7. Gate D — безопасные offline-тесты

Разрешено создавать дополнительные синтетические loopback fixtures и тестировать изолированные вспомогательные компоненты без реальных endpoints.

Проверки должны охватывать:

- Отсутствие защищённого прокси.
    
- Ошибку разрешения или недоступность endpoint.
    
- SOCKS5 refusal, timeout и disconnect.
    
- Попытку переключиться на direct connection.
    
- Неправильные proxy environment variables.
    
- Обход через `NO_PROXY`.
    
- Непредвиденное создание дочернего процесса.
    
- Попытку использовать неразрешённый порт/адрес.
    
- Корректное завершение, очистку сокетов и отсутствие утечек ресурсов.
    

У каждого теста должен быть проверяемый oracle, различающий **«соединение заблокировано»** и **«соединение вообще не пытались открыть»**.

Любые специально моделируемые обходы допустимы только в собственном loopback-стенде без внешней сети.

Настоящий native Go client **не запускать** в рамках этой задачи, если предварительно не получено отдельное разрешение после независимой проверки изоляции.
