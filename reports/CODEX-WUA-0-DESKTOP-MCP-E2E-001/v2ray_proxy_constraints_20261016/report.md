## Принятое ограничение пользователя

Доступ к OpenAI Platform Tunnels пользователь ещё не проверял; подтверждённого
tunnel_id нет. Действующий туннель не создавать. Конфигурацию, сеть, V2Ray и другие
подключения не менять. Все будущие внешние соединения tunnel-client должны проходить
через V2Ray; прямой интернет запрещён. При недоступности прокси обходного выхода
быть не должно. Следующий этап согласуется отдельно после проверки Tunnels.
API-ключи в чат не передаются.

Эти условия заменяют прежнюю инструкцию «получить реквизиты и запустить launcher».
Наличие tunnel_id само по себе больше не открывает gate запуска.

## Что проверено без соединений с туннельным сервисом

1. В штатной справке проверенного tunnel-client v0.0.16 есть `--http-proxy` — общий
   явный HTTP-прокси для control-plane, MCP HTTP и Harpoon. Есть также отдельные
   `--control-plane.http-proxy`, `--mcp.http-proxy`, `--harpoon.http-proxy`.
   Значение может быть URL или ссылкой `env:VAR`.
2. Встроенный образец `sample_mcp_enterprise_proxy` задаёт верхнеуровневый
   `http_proxy: "env:HTTPS_PROXY"`. Этот образец только прочитан; в рабочий профиль
   не импортировался. [Официальная документация OpenAI](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)
   подтверждает поддержку исходящих прокси, но не даёт доказательства фактического
   маршрута этого компьютера или отсутствия fallback в проверяемой ситуации.
3. В текущем окружении Codex отсутствуют HTTP_PROXY, HTTPS_PROXY, ALL_PROXY и NO_PROXY
   в обоих регистрах. Это снимок одного процесса; системный/TUN-режим из него не
   определяется. Значения секретов не собирались.
4. Read-only снимок процессов обнаружил v2rayN.exe и sing-box.exe. У sing-box есть
   listeners `127.0.0.1:10808` и `127.0.0.1:10813`. Соединения с ними не выполнялись.
   Их протоколы и маршруты outbound не установлены: номер порта и владелец процесса
   не доказывают HTTP CONNECT/SOCKS или передачу OpenAI через нужный outbound.
5. Прежний подготовленный launcher наследовал окружение, но не закреплял явный
   прокси и не проверял его отказ. Поэтому прежняя подготовка не удовлетворяет
   новому обязательному условию. Предыдущий успешный localhost bridge-тест проверял
   четыре MCP-вызова, а не V2Ray или интернет-маршрут.

Штатные команды справки не запускают daemon. Реальный tunnel-client run, doctor
с сетевой проверкой, proxy probes, DNS-запросы к целевому сервису и fault injection
в этом этапе не выполнялись. V2Ray config, subscriptions, ключи и удалённые серверы
не выгружались. Действующие процессы не останавливались.

## Защита подготовленного запуска

В собственный неактивированный `secure_tunnel_preparation/start_tunnel.py` добавлен
безусловный отказ для `--start` до чтения ключа и до запуска дочернего процесса:
`HOSTED_TUNNEL_ON_HOLD_BY_USER`. Обходного флага нет. Это изменение вспомогательного
артефакта TASK, не config.toml, не WUA plugin и не сетевой конфигурации.

Проверка реального launcher с `--start` завершилась кодом 1 и ожидаемым отказом,
без запроса credentials или создания tunnel-client процесса. Старый launcher и
документы сохранены в `before/` как исторические evidence, не как инструкция запуска.
Рабочий YAML-шаблон оставлен побайтно неизменным; пока он не является утверждённым
профилем V2Ray-only.

## Предлагаемый маршрут — пока не применён

Будущая цепочка: **tunnel-client → подтверждённый loopback HTTP-прокси V2Ray →
подтверждённый proxy outbound V2Ray → OpenAI**. WUA остаётся прежним STDIO-сервером;
его локальный fixture и health-интерфейсы не являются прямым выходом в интернет.

В отдельном согласованном этапе можно явно закрепить общий прокси через штатный
`--http-proxy env:WUA_V2RAY_PROXY` в окружении только нового процесса. Значение должно
содержать реально подтверждённый адрес существующего inbound, без угадывания порта.
Это описание будущего параметра: переменная, YAML и действующая конфигурация сейчас
не менялись. Нельзя полагаться только на системный прокси, название V2RayN, текущий
внешний IP или наследование HTTPS_PROXY.

Нужно проверить приоритет всех per-component overrides, отсутствие bypass через
NO_PROXY, обработку redirects/retries и всех дополнительных исходящих компонентов.
Cloudflared, Harpoon callouts и произвольные HTTP MCP endpoints не нужны данному WUA
и не должны вводить отдельный интернет-маршрут. Поддержка SOCKS/разрешения DNS для
SOCKS этим исследованием не подтверждена; HTTP-прокси нельзя подменять непроверенным
SOCKS-портом. Если подходящего inbound нет, изменение V2Ray требует нового согласования.

План отказной проверки должен охватить отсутствие адреса прокси, отказ подключения,
timeout и потерю соединения после первоначального успеха. Остановка действующего
V2Ray или изменение его настроек для теста сейчас запрещены. Сначала возможен
отдельно согласованный loopback-стенд: тестовый origin и тестовый прокси, где можно
зарегистрировать нежелательную прямую попытку без интернет-выхода. Он подтвердит
только поведение транспорта в этих условиях, не реальную маршрутизацию V2Ray.

Реальная V2Ray-проверка затем требует отдельного согласованного плана, который не
затрагивает работающие подключения. Сам по себе TCP listener или отказ doctor
не является доказательством fail-closed. Однократный снимок соединений тоже
недостаточен для исключения кратких обходных попыток: нужен журнал/захват на весь
интервал startup, discovery, polling, RPC, retries и отказа.

Если нужна принудительная гарантия запрета прямого egress на уровне ОС, одних
прикладных proxy flags недостаточно для такой гарантии. Отдельное ограничение
процесса потребовало бы согласования; firewall, права и маршруты сейчас не меняются.
При недоказанном fail-closed живой запуск остаётся закрыт.
