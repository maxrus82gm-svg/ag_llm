# Регламент ведения задач и документации

Редакция 04.11.2026: прямое поручение пользователя — короткие индексы вместо полных историй, постоянные номера, автоматическое сохранение при сдаче. Главный пользователь этого регламента — веб-планировщик ChatGPT. Исполнители и пользователь используют тот же скрипт сдачи.

## Прочитать сначала: что куда записывать

1. **Поручение до начала работы имеет TASK ID.** Например, `CODEX-WUA-CHAT-S3-TURN-RECOVERY-001`. Исполнитель не придумывает другой ID для той же задачи.
2. **При сохранении скрипт выдаёт HISTORY ID.** Например, `H-CODEX-000001`. Это постоянный номер истории. Повторная сдача той же TASK использует тот же номер; пропуски номеров после ошибок допустимы. Номера не переиспользуются и вручную не назначаются.
3. **Полное поручение хранится в папке задачи**, обычно `reports/<TASK-ID>/handoff_task.md`; результат — `report.md`, доказательства — manifest/evidence. `task_record.json` связывает оба ID, название, дату, статусы, пути и SHA-256. Это адресная запись, а не независимый PASS.
4. **№001 Codex/Claude/Ultra Desktop содержит только последние десять строк**, по одной на задачу: дата, HISTORY ID, TASK ID, понятное название, статус, путь к записи. Полную постановку и отчёт туда не вставлять. Выпадение из десяти строк не удаляет запись из папки задачи.
5. **№05 содержит короткий общий индекс и все FOLLOWUP/риски.** Ссылаться на тот же HISTORY ID и TASK ID. Открытый вопрос нельзя удалить потому, что задача старая или вышла из десятки.
6. **Веб-проверяющий обновляет результат проверки в существующей записи**, затем короткие индексы, событие №06 и текущую картину №34. Вторую историю с новым номером для той же задачи не создавать.

Понятное название обязательно: «Безопасное восстановление диалога после сбоя», а не одно «S3» или «исправления». Название не заменяет строгие ID. Принятые AMENDMENT, отрицательные результаты и ограничения остаются в полных источниках.

## Кто и когда запускает сохранение

| Ситуация | Кто действует | Что сделать |
| --- | --- | --- |
| Задача ещё выполняется | Исполнитель | Сохранять рабочие результаты; не освобождать БЛОК 1 и не объявлять независимую приёмку |
| Итоговый пакет готов, включая PARTIAL/FAIL/BLOCKED | Codex, Claude, Ultra Desktop либо пользователь | Выполнить `finish --apply` для точного TASK ID из БЛОКА 1; отдельно передать все chat-only AMENDMENT |
| Пользователь нажимает завершение в программе | Пользователь через окно | Окно запускает то же ядро `finish`; правила, номера и проверки одинаковы с CLI |
| Веб-планировщик получил опубликованную сдачу | Независимый ChatGPT-проверяющий | Взять HISTORY ID и путь из БЛОКА 1.1/протокола; открыть одну запись; проверить источники; записать ограниченный verdict |
| Веб имеет файлы, но не может выполнять Python | Веб-планировщик | Использовать готовые ID и пути. Для отсутствующего сохранения передать точную команду локальному исполнителю: `SCRIPT EXECUTION REQUIRED`; не имитировать запуск и не переносить слот вручную |
| Прямое поручение в чате без отдельной TASK в БЛОКЕ 1 | Исполнитель по этому поручению | Сохранить исходное поручение и отчёт; использовать `task_history.py register`. Чужую/прежнюю задачу в карточке не завершать |

Запуск `finish` означает сдачу автором. Он НЕ означает независимый PASS, публикацию, merge, разрешение нового этапа или назначения следующей задачи. БЛОК 1.1 содержит дословную последнюю постановку и служебную строку с HISTORY ID; БЛОКИ 2–4 скрипт не переписывает.

## Команды: один порядок для программы и агента

Из корня проекта; реальные значения вместо примеров. Ключи `--repo` и `--max-tokens` у `task_history.py` стоят ДО команды.

```powershell
python -B -X utf8 tools/task_slot_rotate.py finish --card "Документация/000_Задачи Codex.md" --task-id TASK-ID --no-chat-amendment --headless --apply
python -B -X utf8 tools/task_history.py list --agent codex --last 10
python -B -X utf8 tools/task_history.py read --id H-CODEX-000001
python -B -X utf8 tools/task_history.py --max-tokens 4000 read --id H-CODEX-000001 --part assignment --start-line 1 --lines 40
```

При поправках заменить `--no-chat-amendment` на `--chat-amendment <файл>` для каждой отдельной поправки. Для Claude изменить имя карточки; для Ultra Desktop — его карточку. Если БЛОК 1 не содержит корректного TASK ID, остановиться: номер истории не заменяет отсутствующее назначение.

`read` без `--part` показывает только адресную запись. Возможные части взять из её `sources`: `assignment`, `report`, `review` либо `legacy`. Сначала открыть запись, затем одну нужную часть. Большой текст читать явным диапазоном; инструмент показывает выданные строки и общий размер, не скрывает усечение.

После независимой проверки координатор использует:

```powershell
python -B -X utf8 tools/task_history.py review --id H-CODEX-000001 --verdict PARTIAL --scope "проверены исходники; Windows NOT RUN" --evidence "reports/REVIEW-TASK/report.md" --apply
python -B -X utf8 tools/task_history.py render --apply
python -B -X utf8 tools/task_history.py validate
```

`review` — инструмент записи решения, он не выполняет независимую проверку за человека/модель. `render` обновляет только отмеченные таблицы №001 и №05; он не назначает TASK, не меняет FOLLOWUP и не пишет №06/34 за координатора. Эти действия отдельно завершить и проверить.

Для прямого поручения без слота:

```powershell
python -B -X utf8 tools/task_history.py register --id TASK-ID --agent codex --title "Понятное название" --date 2026-11-04 --assignment "reports/TASK-ID/assignment.md" --report "reports/TASK-ID/report.md" --apply
```

## Порядок веб-планировщика: от постановки до закрытия

1. Прочитать общий `000_Задачи для агента.md`, текущие №34/40, очередь FOLLOWUP №05. Выбрать конкретную работу; старый NEXT не является назначением.
2. Подготовить пользователю три блока: полное поручение с TASK ID; короткую команду запуска; понятное объяснение результата. Пользователь назначает TASK в БЛОК 1. Изменения работающей задачи — отдельные AMENDMENT с тем же TASK ID.
3. После сдачи взять из БЛОКА 1.1 или JSON-протокола `history_id` и `record`. Для старой карточки без HISTORY ID искать по точному TASK ID: `task_history.py read --id <TASK-ID>`. Если записи нет — организовать сохранение; новый H-номер руками не выдавать.
4. Открыть `reports/<TASK-ID>/task_record.json`. Проверить совпадение ID, назначения, AMENDMENT, путей, SHA-256, опубликованной версии и области своей проверки. Утверждение автора и independent verdict различать.
5. Прочитать нужные исходники/доказательства адресно, выполнить разрешённые независимые проверки. Сохранить свой report с PASS/PARTIAL/REVISE/FAIL/BLOCKED, точным scope, counts и NOT RUN. Самопроверка исполнителя не становится независимой.
6. В существующей записи добавить review и адрес доказательств через `review`, затем `render`. Если веб редактирует через файловый API без Python, он может обновить существующую запись и строки таблиц с уже выданным номером, сохранив предыдущую версию метаданных; новый номер и перенос слота всё равно выполняет скрипт. `validate` поручить доступной среде. При недоступном источнике не заявлять проверку.
7. Все невыполненные пункты оставить/добавить в FOLLOWUP №05 с owner, gate, действием, критерием закрытия, статусом и successor TASK ID. Назначенный successor не равен VERIFIED_CLOSED. Принятие остаточного риска требует явного решения пользователя.
8. В №06 записать короткое событие с обоими ID, verdict и адресом review; в №34 — только текущий итог, OPEN и NEXT. №40/профили менять лишь при влиянии на координацию/архитектуру. Повторная доставка отчёта не создаёт вторую задачу и вторую запись истории.
9. Проверить чтение по ID и согласованность индексов; опубликовать только в пределах своих прав. Пользователь принимает GPT → main и синхронизирует Windows. Уже освобождённый БЛОК 1 и содержимое БЛОКА 1.1 повторно не трогать.

## Ограничения чтения и размера

- На входе не загружать №001/06, папки reports и старые архивы целиком. Обычно достаточно списка последних 5–10 названий; подробности — одна запись по ID.
- `list --last 10` выводит десять кратких строк, не десять полных задач. Полные задачи нужны только по цели текущего поручения. Пользователь может указать другую выборку.
- Читатель по умолчанию ограничивает весь ответ 8 000 единицами бюджета, явно допускает до 20 000. При установленном `tiktoken` используется `o200k_base`; без него — более строгая верхняя граница по числу UTF-8-байтов. Это не счёт биллинга модели. Превышение/ошибка даёт отказ с пустым stdout, без печати всего архива.
- Бюджет нескольких вызовов учитывать суммарно: начальный ориентир — 12 000 токенов на знакомство, дальнейшее чтение только под конкретное действие. Скрипт технически ограничивает один вывод, не все инструменты и не весь чат. Повторно тот же раздел с тем же SHA не читать без причины.
- Не раскрывать все `requires` на старте. Прочитать условия реально выполняемого действия; необходимые правила безопасности и зависимости для него получить перед этим действием. Правила закрытия/публикации не являются обязательным контекстом простого просмотра списка.
- №001 — максимум десять строк, без полных постановок. №05 — краткий индекс и открытые вопросы. №34 — текущая картина, цель 15–25 тысяч символов; абсолютный предел 50 тысяч. №08 — краткий вход, предел 16 тысяч символов. История не добавляется обратно при каждом closeout.

## Сохранность и ошибки

Старые полные №001 и прежний №05 сохранены неизменными снимками в `reports/CODEX-TASK-HISTORY-ID-001/preservation/`. Старые записи не объявлены заново проверенными; новые короткие строки содержат адрес исходного исторического фрагмента. Выпадение из рабочего списка не означает потерю архива.

Скрипт сохраняет прежнюю постановку, новый snapshot и адресную запись ДО освобождения активного слота; проверяет хеши и повторное чтение. При ошибке сохранения не освобождает БЛОК 1. Снимки могут остаться после отказа — это сохранённые данные, а не доказательство успешной ротации. Если номер занял параллельный процесс, повторить `finish`: уже зарегистрированный ID будет переиспользован. Файлы индексов являются восстанавливаемыми представлениями; после сбоя `render` повторяется, источники задач не удаляются.

Нельзя перезаписать отличающийся snapshot, вручную очистить слот, придумать историю, удалить OPEN ради десяти строк или выдавать LOCAL за PUBLISHED. При несовпадении источника/SHA — остановить зависимое действие и восстановить согласованность адресно.

## Полномочия и безопасность сохраняются

Пользователь назначает и расширяет задачи. Локальные Codex/Claude не получают Git/GitHub-права, включая чтение, без отдельного адресного разрешения. Веб-планировщик проверяет реальные инструменты и свои права; наличие API не разрешает публикацию автоматически. Чужие активные задания, live storage, права ОС, backup/rollback и изоляцию не изменять побочно.

Собственное инженерное исправление независимо принимает другой verifier. Scratch-проверки допустимы в разрешённом scope; production/paid/live/merge/rollout и новый этап требуют своих разрешений. Один Start_WebAlarm.bat, STANDARD/TEST и обязательный возврат сохраняются. B2, WA4-R, EVM/Windows/portability и freeze Desktop MCP не сняты миграцией документации. INDEPENDENT_PLAN сохраняет изоляцию: не раскрывать №34/40, чужие планы/архивы до разрешённого перехода.
