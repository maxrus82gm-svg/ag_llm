# Шаблоны задач, отчётов и архитектурных решений

Этот документ содержит копируемые шаблоны для единообразия документации.

---

## ШАБЛОН TASK

**TASK XX — НАЗВАНИЕ**

**ИСПОЛНИТЕЛЬ / MODEL**
Конкретная LLM/агент, для которой выписана эта карточка. TASK ID и карточка принадлежат именно этому исполнителю; при смене исполнителя делается явный reroute, а не молчаливое наследование чужой карточки.

**PERSONAL TASK ROUTE**
Указать персональный task-файл исполнителя и, если используется, его собственный report/history-контур. Общий `000_Задачи для агента.md` хранит проектный NEXT и ссылку, но не заменяет персональную постановку.

Для устойчивого персонального task-контура рекомендуется трёхблочный handoff:
- БЛОК 1 — входной слот текущей утверждённой постановки;
- после фактического завершения исполнитель сначала копирует полную постановку в БЛОК 2, затем записывает factual result в БЛОК 3 и только после доказанной сохранности БЛОКОВ 2–3 очищает БЛОК 1 до `ОЖИДАНИЕ НОВОЙ ЗАДАЧИ`;
- БЛОК 2 — полная копия последней выполненной постановки;
- БЛОК 3 — краткий factual result исполнителя: изменённые файлы, реализованное, проверки, границы scope, report path, findings/proposals и статус.
До независимой проверки результат исполнителя маркируется `RESULT READY / AWAITING INDEPENDENT VERIFICATION`. Permanent history и канонический `DONE / VERIFIED` фиксирует независимый verifier после PASS.

**ЦЕЛЬ**
Краткое описание того, что должно быть достигнуто.

**РАБОЧИЕ ФАЙЛЫ**
Список файлов, которые будут изменены или созданы.

**ТЕКУЩЕЕ СОСТОЯНИЕ**
Что уже есть, что нужно изменить.

**ТРЕБОВАНИЯ**
- Функциональные требования
- Нефункциональные требования
- Критерии приёмки

**НЕ ДЕЛАТЬ**
Явные ограничения и то, что выходит за рамки задачи.

**КРИТЕРИИ ПРИЁМКИ**
Чек-лист того, что должно быть сделано и проверено.

**ПРОВЕРКА ПОСЛЕ ИЗМЕНЕНИЯ**
Как проверить, что задача выполнена корректно. Перечисленные проверки — обязательный минимум, не полный потолок анализа.

**INDEPENDENT AGENT / ADVERSARIAL PASS**
Перед `RESULT READY` исполнитель обязан самостоятельно попытаться сломать собственное решение релевантными edge cases и соседними инвариантами. Scope ограничивает самовольные изменения, а не исследование. Найденное внутри scope исправить и покрыть regression test; реальную проблему вне scope не скрывать и не чинить самовольно — вынести в отчёт как `FINDING / PROPOSAL / BLOCKER` с evidence, impact и рекомендуемым next action. Подробное правило — `18_Регламент сопровождения документации.md`.

**ФОРМАТ ОТЧЁТА**
Ссылка на шаблон REPORT.

### DOCUMENTATION BLOCK для значимой технической TASK

Готовится одновременно с технической постановкой; исполняется после фактического результата. Канонический routing и критерии выбора документов — в `08_Старт.md`. Documentation-only TASK не требует рекурсивного блока.

```text
DOCUMENTATION BLOCK
TASK TOPIC: <подсистема>
PROFILE DOCUMENTS: <владельцы темы по реестру 08>
CHECK 01: YES / NO + причина
OTHER AFFECTED DOCUMENTS: <только реально затронутые>
AFTER TECHNICAL RESULT: code / diff / tests / live evidence → обновить подтверждённый статус; убрать ложный CURRENT STATUS; проверить ссылки; не переписывать историю 06
REGISTRY IMPACT: YES / NO
```

**ПРАВИЛО ОШИБОК:**
Не повторять одинаковый неудачный вызов более 2–3 раз. При повторяющейся ошибке остановиться и дать диагностику.

## ШАБЛОН REPORT

**TASK:** ID и название задачи
**ИСПОЛНИТЕЛЬ / MODEL:** конкретная LLM/агент, выполнившая TASK
**REPORT ROUTE:** собственный report/history-контур этого исполнителя; не записывать отчёт одной модели как отчёт другой
**STATUS:** RESULT READY / AWAITING INDEPENDENT VERIFICATION / В РАБОТЕ / ЗАБЛОКИРОВАНО

Для внешнего исполнителя `ГОТОВО` не равно каноническому `DONE / VERIFIED`: до независимой проверки использовать `RESULT READY / AWAITING INDEPENDENT VERIFICATION`.

**ИЗМЕНЁННЫЕ ФАЙЛЫ:**
- файл1
- файл2

**РЕАЛИЗОВАНО:**
Что конкретно сделано.

**ПРОВЕРЕНО:**
Как проверено, что работает.

**НЕ РЕАЛИЗОВАНО:**
Что осталось за рамками этой задачи.

**ОШИБКИ / РИСКИ:**
Проблемы, с которыми столкнулись, и потенциальные риски.

**ADVERSARIAL REVIEW / FINDINGS / PROPOSALS:**
Что исполнитель дополнительно попытался сломать сверх обязательного чек-листа; какие неперечисленные edge cases проверил; что нашёл. Для находки вне scope: reproduction/evidence, предполагаемый root cause, impact, почему сам не менял этот участок и конкретное предложение verifier/координатору. Если дополнительных находок нет — явно написать, какой adversarial pass был выполнен.

**СЛЕДУЮЩИЙ ШАГ:**
Что делать дальше. Предложение исполнителя не считается автоматически утверждённым NEXT.

**ФОРМА ВЫДАЧИ В CHAT:** итог исполнителя в Chat — один копируемый блок кода (метка `text`) по полям этого шаблона, без рассуждений и хода работы; промежуточные сообщения — вне блока. Блок самодостаточен: его копируют verifier / другому агенту без правок. Для ChatGPT Remote полный отчёт и continuity сохраняются по Remote-протоколу; для локальных Claude/Codex отдельный task-report-файл создаётся только при явной необходимости независимой проверки или по требованию TASK, а оперативные журналы на каждый шаг не создаются (см. `18_Регламент сопровождения документации.md`).

## ПРИМЕР ИСПОЛЬЗОВАНИЯ

### Пример TASK

**TASK 06.1 — Модель данных чатов и хранение на диске**

**ЦЕЛЬ**
Реализовать persistent storage для истории чатов.

**РАБОЧИЕ ФАЙЛЫ**
- Документация/03_Чаты, проекты и контекст.md (уточнение модели)
- (далее будут добавлены файлы кода)

**ТЕКУЩЕЕ СОСТОЯНИЕ**
Чаты не сохраняются между сессиями. История теряется.

**ТРЕБОВАНИЯ**
- Каждый чат имеет уникальную директорию
- История сохраняется на диск
- Метаданные в JSON
- API для CRUD

**НЕ ДЕЛАТЬ**
Не реализовывать сжатие контекста (это TASK 06.5).

**КРИТЕРИИ ПРИЁМКИ**
- [ ] Структура chat_XXX/ создана
- [ ] История сохраняется
- [ ] Чаты видны после перезапуска

**ПРОВЕРКА ПОСЛЕ ИЗМЕНЕНИЯ**
Запустить UI, создать чат, перезапустить, проверить наличие.

## РЕКОМЕНДАЦИИ

1. Используйте эти шаблоны для всех новых TASK и отчётов.
2. Копируйте целиком и заполняйте только нужные разделы.
3. Сохраняйте структуру для удобства навигации.
4. В STATUS используйте только: ГОТОВО, В РАБОТЕ, ЗАПЛАНИРОВАНО, ЗАБЛОКИРОВАНО.
5. При описании ошибок следуйте правилу: не более 2–3 повторов.
