## 9. ChatGPT Desktop ↔ Web Alarm Ultra: локальный MCP и вызов по событию (2026-10-16)

**Решение пользователя / приоритет исследования:** после завершения действующего WEB_08 по ранее утверждённым gates первым предметно разобрать, как подключить **обычный ChatGPT Desktop на Windows к локальному Web Alarm / будущей Web Alarm Ultra через свой ограниченный MCP-мост**, по аналогии с инструментальным доступом Desktop Commander. Это **архитектурное направление и feasibility-кандидат для WUA-0**, а не запуск реализации или переназначение активных задач. Старая Tkinter Ultra остаётся источником проверенных решений; целевой сервер — Web Alarm Ultra. Сохранить план будущей Ultra Tab и профилей GigaChat/Codex, уточнив последовательность исследований по отдельному GO.

**Два независимых механизма одного возможного контура:**

1. **Инструментальный доступ:** ChatGPT Desktop → разрешённый локальный MCP plugin/tool → узкий Web Alarm Ultra adapter → server-owned READ/STATUS/REPORT/context/evidence → ChatGPT. Первое испытание — read-only `ping` и чтение синтетического контекста из обычного Desktop Chat на компьютере пользователя. Никакой обязательной публикации исходников в GitHub и отдельного OpenAI model API для этого направления. Доступность в конкретной Windows/Plus-конфигурации, permissions, маршрут транспорта, продолжение после внешнего сообщения — **UNVERIFIED**. Не путать с отдельным направлением Ultra → GPT как вызываемый model provider (там иной контракт и обычно отдельный API).
2. **Инициирование обращения в чат:** эксперимент **AG LLM → Codex → существующий чат «Сервер WEB_08»** 2026-10-16 завершился **SUCCESS (BOUNDED)**: по поручению пользователя в чат действительно поступило сообщение агента, ChatGPT ответил; следующее сообщение инициировало адресное обновление `34_TACTICAL_CONTEXT.md` через подключённый GitHub (запись отражена в №34). Следовательно, уже продемонстрирована **возможность агента отправить сообщение в существующий чат и вызвать обработку поручения**, а не только пассивное хранение отчёта. Рассматривать Codex как **возможный канал доставки вызова Planner/Reviewer** после завершения задачи Web Alarm. Цель будущего сценария: Web Alarm хранит TASK/результат, Codex отправляет короткий `TASK ID + event`, ChatGPT при доступном MCP читает локальный контекст и возвращает решение; Web Alarm применяет его по своим gates. GitHub/общая папка/локальное хранилище могут служить транспортом данных, но не должны быть обязательны для самого сигнала.

**Границы подтверждения:** пока доказан **один ограниченный message/documentation smoke**, НЕ доказаны автоматический триггер именно из Web Alarm при task completion, точная оснастка/транспорт Codex, достоверная идентичность отправителя, получение Codex ответа, стабильный unattended двусторонний цикл, гарантированное «пробуждение» закрытого/спящего чата или доступность MCP после такого обращения. Нельзя приписывать OpenAI конкретное назначение интеграции или гарантировать сохранность этого механизма в будущих версиях. Канал Codex — **replaceable optional relay**, не единая точка отказа; при недоступности события сохраняются сервером до ручного или иного разрешённого возобновления.

**Будущий минимальный план проверки (не TASK / NO IMPLEMENTATION GO):** подтвердить создание/доступность локального MCP-плагина в обычном ChatGPT Desktop Chat; безопасно вызвать `ping` и `read_context` с проверкой источника; отдельно повторить доставку Codex-сообщения с `request_id/TASK ID`, затем проверить чтение локального статуса после обращения и независимый readback ответа. Предусмотреть проверку отправителя/полномочий, идемпотентность, ограниченные попытки/таймауты, аудит, ручные/автоматические gates и STOP. **Web Alarm остаётся единственным owner TASK, approvals и mutations**; само сообщение не разрешает write/execute/Git. Никаких изменений production, сети, тарифов или пользовательских прав без нового явного GO. Документ №34 содержит тактический статус и доказательства начального smoke.
