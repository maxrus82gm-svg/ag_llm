# 🟨 Задача: компактный интерфейс EVM, раскрытие карточек, избранное и пользовательская сортировка

**ARCH CLASS:** Web Alarm UI + server-side preferences; PRIMARY `36.2`, SECONDARY `36.3`.

**Базовая опубликованная версия:** `main@55cc4477a324460bf0db0b83b88cf93c8ad523d3` (коммит №455). Перед началом проверить актуальный HEAD.

**Источник полномочий:** отдельное прямое поручение пользователя по результатам визуального осмотра предыдущей EVM. Оно не закрывает `CLAUDE-WUA-EVM-MODEL-CARD-UI-001` и не заменяет незавершённую Stage1 `CLAUDE-WUA-CHAT-S1-READONLY-UI-001`.

## 1. Цель

Переработать EVM из полноширинной сетки больших карточек в компактный, удобный при большом количестве моделей каталог с интерактивным раскрытием карточек.

Сохранить существующие данные, API-статусы, назначенные роли, настройки и диагностику.

**Основной принцип:** одна универсальная реализация карточки и её раскрытого представления. Новые элементы добавляются централизованно, а не копируются вручную для каждой модели.

## 2. Предстартовая проверка

До изменений:

1. Проверить текущий GitHub HEAD и опубликованный пакет предыдущей EVM.
    
2. Подтвердить штатный STANDARD launcher, его фактическую цель и root. Пользователь визуально подтвердил обычный запуск, но исполнитель обязан соблюдать `DOC-WUA-LAUNCH-01`.
    
3. Адресно прочитать действующие правила №18, текущие №34, №40, программу №37, необходимые части №11, №19, №23, №36, №36.1, №36.2/36.3.
    
4. Проверить пересечение с незавершённой Stage1 и возможными работами направления Б. Особенно `web_alarm/ui.py` и `web_alarm/server.py`.
    
5. Если изменения текущих общих файлов несовместимы с незавершёнными работами, остановить конфликтующий участок и запросить решение. Не перезаписывать чужую работу.
    

Исполнителю запрещено самостоятельно изменять Git/GitHub, БЛОКИ 1–4, архив №001 и общие документы.

## 3. Компоновка EVM

На широком экране организовать четыре вертикальные области слева направо:

- **Избранное** — более узкий столбец.
    
- **API** — карточки моделей API.
    
- **MCP / Агенты** — реальные доступные подключения этого типа.
    
- **Локальные** — реальные локальные LLM, если их источник подключён.
    

Карточки внутри каждого столбца располагаются сверху вниз.

MCP-подключение не объявлять нейросетевой моделью без доказанного источника. Для отсутствующих MCP и локальных подключений показывать честное пустое состояние. Не генерировать фиктивные записи.

На небольших экранах столбцы адаптируются в последовательные разделы или переключаемые вкладки. Общая горизонтальная прокрутка страницы не должна становиться обязательной.

## 4. Компактная карточка

По умолчанию показывать небольшую карточку с:

- названием;
    
- типом подключения/провайдером;
    
- существующим индикатором API, если он применим;
    
- количеством параметров, если оно известно;
    
- звёздочкой добавления в избранное;
    
- доступным способом раскрытия.
    

Не размещать в свёрнутой карточке полную таблицу ролей, большой текст описания и все кнопки управления.

### Раскрытие

При наведении курсора полная карточка должна быстро и плавно появляться поверх списка, не раздвигая окружающие карточки.

При перемещении мыши между карточками предыдущая закрывается, следующая раскрывается. Не должно быть мерцания, случайного закрытия при перемещении курсора на кнопки или скачков страницы.

Ориентир: быстрая реакция в пределах примерно 100–200 мс, короткая ненавязчивая анимация. Учесть `prefers-reduced-motion`.

Полное представление содержит существующие роли, подсказки, описание до 500 символов, статус API, «Настройки» и «Проверить чат».

Поскольку наведение отсутствует на сенсорных устройствах, обязательно предусмотреть раскрытие нажатием. Для клавиатуры — `Enter`/`Space`, закрытие `Escape` и сохранение доступности всех кнопок. Раскрытая карточка не должна выходить за пределы экрана и обрезаться контейнером.

## 5. Перестановка карточек

Реализовать ручное изменение порядка карточек внутри каждого вертикального столбца.

Основной способ — drag-and-drop. Дополнительно предусмотреть доступное управление порядком без перетаскивания, например команды «Выше» и «Ниже».

Требования:

- порядок сохраняется после обновления страницы и перезапуска;
    
- порядок отдельных разделов независим;
    
- перетаскивание не запускает кнопки внутри карточки;
    
- сохранение порядка не меняет `model_registry`, назначения ролей, API-настройки и реальные подключения;
    
- появление новых моделей не удаляет прежние пользовательские предпочтения и не создаёт дубликаты;
    
- предусмотреть защиту от конкурентного сохранения и повреждённых настроек.
    

Использовать стабильные идентификаторы записей с указанием типа подключения. Не создавать отдельную копию реестра моделей.

## 6. Избранное

Реализовать звёздочку добавления/удаления из избранного.

В избранном показывать компактное представление существующей записи. Это ссылка на исходную модель или подключение, а не новая самостоятельная модель.

Избранное можно сортировать вручную. Изменение API-статуса, описания и других сведений в исходном объекте должно отражаться и в избранном.

Избранное и пользовательский порядок должны храниться отдельно от секретов, истории чатов и системных назначений моделей.

## 7. Редактирование описания

Пользователь сообщил, что не смог отредактировать поле «Сильные стороны модели».

В текущих исходниках редактирование предусмотрено: «Настройки → Модель → Сильные стороны модели», поле `evmSetDescription` и сохранение через `saveSettings()`.

Не предполагать заранее, что сохранение сломано.

Необходимо:

1. На изолированных данных проверить открытие нужной вкладки, ввод, сохранение, повторное открытие и перезапуск.
    
2. Если найден фактический дефект — исправить и добавить регрессионный тест.
    
3. Если механизм работает — улучшить обнаруживаемость: из полной карточки должна быть понятная команда «Редактировать описание», открывающая нужную вкладку.
    
4. Сохранить ограничение 500 символов, обработку ошибок и защиту `base_revision`.
    
5. Не разрешать изменение описания через новую скрытую систему хранения.
    

## 8. Выбор модели Ultra Chat

Убрать большой самостоятельный блок «Модель для Ultra Web Chat» из верхней части EVM.

Естественное место выбора — непосредственно в Ultra Chat, рядом с полем ввода.

Сначала проверить контракт Stage1. Если допустимо безопасно переместить существующий контроль выбора с использованием прежнего `/ultra/connections/selection`, выполнить перенос **только пользовательского предпочтения модели**, без добавления отправки сообщений, Turn, RAW-записи или расширения authority чата.

Если это нарушает действующий read-only scope Stage1, не удалять единственный работоспособный способ выбора. Остановить этот пункт как `BLOCKED`, указать минимальный необходимый handoff для следующего этапа. Самостоятельно не открывать Stage2.

Освободившееся место в EVM пока оставить под компактную информационную панель/будущий справочник, без сетевого мониторинга и фиктивных новостей.

## 9. Что не делать в этой задаче

- Не реализовывать новостного агента, автоматический поиск новых LLM и сетевое обновление справочника.
    
- Не подключать живой GigaChat API, ключи, OAuth или платные проверки.
    
- Не активировать отключённые кнопки управления ключами.
    
- Не изменять Tk Ultra, WA4-R, B2, MCP/V2Ray/WFP и пользовательские рабочие данные.
    
- Не закрывать Stage1, прежнюю EVM или их открытые проверки самостоятельно.
