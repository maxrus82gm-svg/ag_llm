# Блюпринт LLM — первый редактор в Web Alarm Ultra

Дата завершения: 3 ноября 2026. Основание: прямое поручение пользователя приступить к реализации в веб-интерфейсе. Статус: реализован редактор схем и демонстрационный предпросмотр; реальное выполнение LLM не подключено. Результаты ниже — проверки автора, а не независимая приёмка.

## Что доступно

- Новая вкладка «Блюпринт LLM» в существующем Web Alarm; прямая ссылка с `#blueprint`.
- Полотно с перемещением блоков и поля, масштабированием и показом всей схемы.
- Один тип `llm`, независимые экземпляры и копии. Роль выбирается на карточке либо вводится произвольно в настройках; модель, инструкция и контекст принадлежат экземпляру.
- Выбор исполнителя из существующего каталога `UltraConnections`, основанного на `model_registry`. Выбор в блоке не меняет глобальное назначение модели Ultra Chat.
- Типы пинов: текст, контекст, JSON, артефакт и событие. Можно добавлять и удалять пины. Связи создаются кликами или перетаскиванием.
- Серверная проверка типов, направлений, обязательных входов, числа источников, ссылок на блоки и отсутствия циклов.
- Сохранение, загрузка и копирование схем; защита от перезаписи конкурирующей версии. При конфликте можно сохранить отдельную копию или явно загрузить серверную версию.
- «Диалог с процессом» показывает демонстрационное прохождение вопроса по связям. В ответах и трассе явно указано, что это имитация без вызова модели.

## Как открыть

Если сервер уже запущен, перезапустить его обычным способом, затем открыть `Start_WebAlarm.bat` и выбрать «Блюпринт LLM». Одного обновления страницы недостаточно для загрузки изменённого Python-кода работающим процессом.

Нажать «Создать схему из двух блоков» или добавить первый LLM-блок. Настроить каждый экземпляр справа, соединить однотипные пины, указать итоговый блок и сохранить схему. Для демонстрации передачи данных ввести вопрос в нижнее поле и нажать «Предпросмотр».

Схемы хранятся в `<storage_root>/ultra/blueprints/<blueprint_id>.json`. Этот каталог создаётся при первом сохранении. Несохранённые правки хранятся в памяти страницы; при закрытии страницы с правками браузер предупреждает об их потере. В `localStorage` сохраняется только ID последней выбранной схемы. Демонстрационные сообщения не сохраняются в Ultra Chat.

## Граница с существующим ядром

Блок содержит ссылку `executor_ref`, а не адрес сервера или секрет. Каталог принадлежит Ultra. В текущем каталоге доступны зарегистрированные GigaChat-модели; поддержка других исполнителей требует их регистрации и адаптера в общем ядре. Выбор зарегистрированной модели не означает, что реальный вызов проверен.

Добавлены только маршруты проектирования:

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/ui/blueprints/capability` | Локальный доступ к редактору |
| GET | `/ultra/blueprints/catalog` | Общий каталог исполнителей, роли, типы, лимиты |
| GET | `/ultra/blueprints` | Список сохранённых схем |
| GET / PUT | `/ultra/blueprints/<id>` | Загрузка / сохранение с `expected_revision` |
| POST | `/ultra/blueprints/validate` | Проверка структуры |
| POST | `/ultra/blueprints/preview` | Чистая имитация передачи данных |

Использованы существующая проверка локального Origin/Host и `InterProcessLock`. У редактора собственный короткоживущий capability-токен. Запись выполняется атомарной заменой файла с проверкой ревизии; повреждённые файлы не перезаписываются. Статические ссылки и junction в каталогах определения отклоняются. Это не новая граница защиты от привилегированного процесса на том же компьютере.

Предпросмотр не вызывает провайдеры, не читает файлы по `context_refs`, не выдаёт разрешений, не создаёт Chat/Turn/RUN и не подтверждает PASS. Контекст передаётся в примере только по явно соединённому пину. Артефакты и события пока служат типизированными образцами данных; ветвления по событиям здесь не выполняются.

Для ограниченного MVP заданы технические пределы: 128 блоков, 512 связей, 64 пина на блок, до 200 сохранённых схем и 512 КиБ на запись. Граф пока ациклический. Это ограничение объёма обработки, а не набор специальных типов LLM-блоков.

## Следующий этап: реальный вызов через Ultra

1. В общем каталоге нормализовать ссылку на конкретное подключение и модель, вид runtime и поддерживаемые возможности. Inference API, агентский runtime и MCP-инструмент остаются разными контрактами. Секреты и адреса разрешаются сервером.
2. На запуск фиксировать неизменяемый снимок определения и его ревизии: `blueprint_id`, `revision`, `node_id`, `executor_ref`, роль, инструкцию, параметры, связанные входы и ссылки на контекст. Смена роли в редакторе применяется к следующему запуску; выполняющийся снимок не меняется.
3. Подключить блок к общему сервису вызова Ultra. Разрешение контекста, capability-проверки, права на инструменты, лимиты, отмена и повторные попытки принадлежат этому сервису. Отдельный исполнитель графов с копией старого ядра здесь не создавался.
4. Связать серверные события и результаты с существующим хранилищем RUN/историей. Разделить факт ответа LLM, проверку формата результата и серверное подтверждение успеха. Выход `error` должен возникать из серверного события, а не из произвольного заявления модели.
5. После сквозного реального вызова добавить управление ветвями, ограниченные циклы, объединение результатов и составные блоки. Для каждого определить правила запуска, ожидания входов и завершения.

Контракт текущего сохранённого определения имеет `schema_version: 1`. При появлении семантики исполнения потребуется явная миграция либо новая версия, особенно для управляющих пинов и структурированного контекста. Этот раздел — план продолжения; перечисленные возможности ещё не реализованы.

## Проверки и материалы

- 48 Python-проверок: новый контракт, сохранение и конкурирующие записи, повреждённое хранилище, HTTP-доступ, существующие сервер, UI и каталог подключений. См. `python-checks.txt`.
- 140 существующих JavaScript-проверок Ultra Chat, EVM и операторской панели: без ошибок. См. `ui-regression.txt`.
- Синтаксис нового JavaScript проверен `node --check`.
- В браузере на отдельном временном хранилище: две разные модели; произвольная роль; независимая копия и её дополнительный пин; отказ несовместимой связи; соединение кликами и перетаскиванием; перемещение блока; сохранение и восстановление после перезагрузки; демонстрационный ответ; обычное и узкое окно. Ошибок в консоли при этом не обнаружено.
- Снимки: `editor.jpg`, `preview.jpg`. На них только синтетический пример. `source-sha256.json` фиксирует сданные файлы. Изменения в существующих файлах: `server.py.diff`, `ui.py.diff`; исходные копии в `before/`.

Изменения находятся в `web_alarm/blueprints.py`, `web_alarm/blueprint_ui.py`, `web_alarm/blueprint_assets/`, `web_alarm/server.py`, `web_alarm/ui.py`, `test_web_alarm_blueprints.py`. Новые внешние зависимости не добавлялись. Для переносимой поставки нужно включать каталог `blueprint_assets` вместе с Python-модулями.

Рабочие данные пользователя, стандартный режим запуска, журнал проекта и назначения агентов не изменялись. Git-операции и публикация не выполнялись. Для отката следует отменить только относящиеся к этой задаче изменения; полная замена файлов копиями из `before/` может затереть последующие чужие правки.
