# MANUAL ENGINEERING REVIEW — TEST-ENG-01

Reviewed the changed server, EVM, Ordinary bridge and Turn paths after the targeted runs.

- Authority: EVM check POST requires local Origin plus the existing in-memory Ultra Chat write token. The checker requires an active non-synthetic session, the approved personal Workspace, model contract and catalog ID, then calls the existing Ordinary Turn once. Browser JSON cannot choose URL, key, Workspace or test text. TEST's default checker remains closed.
- Accounting/replay: the Turn still owns admission, reserve/SENT, RAW and usage. EVM status is secondary; duplicate Turn ID does not refresh confirmation. UNKNOWN/FAILED cannot become green. A status write error is surfaced as `evm_status_sync=UNAVAILABLE` while the committed Turn remains readable.
- Settings: profile ID/version/timeout are bound to a new Turn. A later EVM edit cannot rewrite accepted admission. Timeout is in the provider's existing deadline. Freshness changes only status age; diagnostic limit changes only rendered text. Description/parameter count do not enter inference.
- Negative checks: foreign personal Workspace, synthetic/closed session, absent write token, invalid profile timeout, changed settings version and duplicate Turn were checked offline. Pinned window and F5 UI regressions ran in JS. No personal Workspace, Tkinter settings or STANDARD/TEST launcher was touched.
- Operational grant: removed cumulative 12-send/liability ceilings only for `user_turn_mode=True`, which requires `max_oauth=None`, `max_inference=None`, `max_liability_tokens=None` and exactly one catalog GET. Legacy finite H38 grants retain their original validation. Every inference still needs the existing `_TurnAdmission`, durable reserve/SENT and exact wire validation; no loop or retry was added. The active grant expires after 24 hours and a new connect action is required. Per-attempt liability remains bounded by request bytes plus the selected output preference (maximum 24,096 token units in the web route). This is an admission bound, not a price or provider maximum. TLS, one-account serialisation, catalog membership, version family checks and UNKNOWN behavior remain enforced.
- Full answer path: raised the technical HTTP response ceiling to 512 KiB and the corresponding Turn/RAW/history read bounds. A 27,000-byte Cyrillic answer was stored and read back with `max_tokens=20000`; a response over the ceiling failed with `response_limit_exceeded` and one physical MockTransport POST. Thirteen synthetic Turns passed and a duplicate idempotency key did not resend. A first discovered Pro version was pinned; a different subsequent version was rejected as success. Invalid operational approval and oversized per-attempt liability were denied before I/O.
- A → B → replay A: the old dedup checked only `last_success_turn_id` or `last_failure_turn_id`, so a later opposite outcome could be overwritten by an old replay. The EVM checks store now retains every accounted chat Turn ID independently of its 50-event display history. The existing interprocess lock makes the dedup check and status write one atomic store update. A full store refuses growth beyond 2 MiB before writing, returning `evm_status_sync=UNAVAILABLE` instead of dropping old IDs or inventing a new indicator. Both success→failure→old success and failure→success→old failure were tested with unchanged raw store bytes and reload/F5 readback. An old ID still refuses after 55 newer events.
- EVM control: the new header controls call the existing personal registration and `/ultra/chat/live/start` or `/stop` with the Ultra Chat write capability. The capability read is from the existing local endpoint; TEST and protocol fixtures do not enable the controls. The connect confirmation precedes any personal-store creation or provider control call. A failed/uncertain connect is read back and never retried automatically. Disconnect closes the grant and keeps chat history. No second manager, registry, OAuth, transport or model sender was added.

**Static guard review:** S1's endpoint host literals in EVM are immutable provider metadata; the EVM checker never dereferences its `api_url` for sending. The only physical provider sender remains `RealGigaChatTransport.send_bytes`; OAuth/catalog remain in H38 `ProviderSession`. The current launcher only calls local loopback startup/status and gates optional LIVE behind interactive consent. Exact AST/references and policy gate hashes were updated in `rt002_multimodel_reconciliation.json` after inspection, then S1 69/69 and S2 73/73 passed with zero isolation violations.

**Risks / OPEN:** EVM status and Turn are separate durable stores, so a status-write failure needs repair/reconciliation; the response reports this but no automatic replay is attempted. The EVM button creates a visible diagnostic chat before sending; a pre-send refusal can leave an empty diagnostic chat. A long saved answer can exceed the existing next-request wire/context bound and block follow-up before POST. The separate provider output caps and account balance remain UNKNOWN; 20,000 is a disclosed operator preference ceiling, not a claim about provider capacity. Historical Pro failure cannot be conclusively reconstructed without original provider response. Full Windows CI, physical UI and independent acceptance remain OPEN; author tests are not release PASS.
