# REUSE CHECK / integration map

`model_registry.py` owns the six GigaChat IDs. `ultra_connections.py` owns saved chat role selection and registration. `model_cards.py` already owns EVM profiles, settings versions and durable API status; it has no transport. `ordinary_provider.py` and `ordinary_chat_bridge.py` already carry one authorised provider session into the shared Turn, RAW and ledger. `gigachat_runtime.py` remains the only REAL sender. No manager, registry, transport, OAuth route or new Chat Core was added.

Before this change, EVM timeout/profile were stored but Ordinary Turns used an adapter timeout of 8 seconds; ordinary REAL success did not call the existing `record_chat_success` extension. The EVM check defaulted to `LiveCheckNotAuthorized`. Description and parameter count are reference data. Freshness only changed the display verdict. Diagnostic limit truncated EVM's stored last output before display.

Now a new REAL Turn captures `profile_id`, `settings_version` and `timeout_seconds` from the EVM card. The existing adapter applies the timeout to the existing request deadline and provider call; the immutable Turn admission stores the profile snapshot. Changing timeout changes settings version and invalidates confirmation. Freshness and diagnostic display limit do not change the request version. The complete accepted answer remains in the ordinary chat RAW/Turn; EVM stores up to 8192 characters for its last diagnostic reply and clips only its displayed text to `diagnostic_limit_chars`.

Successful REAL Turns update the durable EVM confirmation using the accepted version and Turn ID. A repeated Turn ID does not refresh its time. A later FAILED/UNKNOWN REAL Turn records a failed indicator; a simulated answer never does. The server returns `evm_status_sync=UNAVAILABLE` if the separate EVM status store cannot be written, without undoing a committed Turn. The status survives F5 through the existing EVM store.

The EVM check uses an active approved personal GigaChat session and creates a visibly titled diagnostic chat, then sends exactly one fixed message with the existing `OrdinaryApplicationChatService.submit_turn`. It uses the same admission, RAW, ledger and per-grant counters as ordinary chat. The HTTP check route requires same origin and the Ultra Chat write capability; it cannot take credentials, a URL or arbitrary message from browser JSON. In TEST or without an active REAL session it remains HOLD. No real call was made by this task.

**OPEN:** EVM's own enable/disable controls still defer to Ultra Chat's existing explicit GigaChat connect/disconnect action. The temporary 12-send/30-minute/128-token grant remains because provider output caps and a safe operational spend contract have not been independently established. The historical third GigaChat-2-Pro `no_answer` cannot be attributed to a specific finish reason without its provider response; current Turn diagnostic code and usage remain visible in the chat status after reopen. New transports or guessed provider limits are not introduced.
