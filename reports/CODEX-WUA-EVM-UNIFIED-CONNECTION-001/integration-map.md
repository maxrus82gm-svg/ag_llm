# REUSE CHECK / integration map

`model_registry.py` owns the six GigaChat IDs. `ultra_connections.py` owns saved chat role selection and registration. `model_cards.py` already owns EVM profiles, settings versions and durable API status; it has no transport. `ordinary_provider.py` and `ordinary_chat_bridge.py` already carry one authorised provider session into the shared Turn, RAW and ledger. `gigachat_runtime.py` remains the only REAL sender. No manager, registry, transport, OAuth route or new Chat Core was added.

Before this change, EVM timeout/profile were stored but Ordinary Turns used an adapter timeout of 8 seconds; ordinary REAL success did not call the existing `record_chat_success` extension. The EVM check defaulted to `LiveCheckNotAuthorized`. Description and parameter count are reference data. Freshness only changed the display verdict. Diagnostic limit truncated EVM's stored last output before display.

Now a new REAL Turn captures `profile_id`, `settings_version` and `timeout_seconds` from the EVM card. The existing adapter applies the timeout to the existing request deadline and provider call; the immutable Turn admission stores the profile snapshot. Changing timeout changes settings version and invalidates confirmation. Freshness and diagnostic display limit do not change the request version. The complete accepted answer remains in the ordinary chat RAW/Turn; EVM stores up to 8192 characters for its last diagnostic reply and clips only its displayed text to `diagnostic_limit_chars`.

Successful REAL Turns update the durable EVM confirmation using the accepted version and Turn ID. The EVM checks store now retains all accounted chat Turn IDs independently of the 50-event display history: an old A replay after a newer B cannot refresh time, append history or change the red/green indicator. Cross-outcome dedup is atomic under the existing EVM store lock and survives F5. If the 2 MiB store bound is reached, status sync fails closed; the committed Turn remains readable. A later FAILED/UNKNOWN REAL Turn records a failed indicator; a simulated answer never does. The server returns `evm_status_sync=UNAVAILABLE` if the separate EVM status store cannot be written, without undoing a committed Turn.

The EVM check uses an active approved personal GigaChat session and creates a visibly titled diagnostic chat, then sends exactly one fixed message with the existing `OrdinaryApplicationChatService.submit_turn`. It uses the same admission, RAW, ledger and durable counters as ordinary chat. The HTTP check route requires same origin and the Ultra Chat write capability; it cannot take credentials, a URL or arbitrary message from browser JSON. EVM's connect/disconnect buttons use the existing local Ultra Chat capability, personal registration and live start/stop routes with the same write token. TEST cannot activate them. These controls do not send a chat Turn; the model check remains a separate explicit action. No real call was made by this task.

Operational grants are minted only by the existing local connect action and expire within 24 hours. A grant has no cumulative message or liability cutoff; every physical inference still requires a fresh user-triggered Turn, per-attempt bounds, reservation/SENT, and a no-retry transport. OAuth refresh is possible only when a later user action needs a token; catalog stays at one GET per activation. The per-chat `answer_tokens` preference now reaches the provider up to the explicit operator ceiling of 20,000. `provider_output_cap_tokens=None` remains UNKNOWN. The 512 KiB HTTP response cap, larger RAW read bounds and full-answer verification replace the trial 8192-byte/128-token path. The stored response version is pinned after first family discovery; a later different version is refused as success.

**OPEN:** A reply larger than the request/context bounds can block the next Turn; the system refuses it before POST instead of silently discarding history. The historical third GigaChat-2-Pro `no_answer` cannot be attributed to a specific finish reason without its provider response; current Turn diagnostic code and usage remain visible in the chat status after reopen. Provider output caps, exact current entitlement and balance remain UNKNOWN. New transports or guessed provider limits were not introduced.
