## 4. Что изменено

### 4.1. Общий контракт записи (`context_storage.py`)

Каждая публичная функция записи ядра (Tk и веб одинаково):

1. **Проверяет Workspace до любого создания.** `workspace.json` читается тем же ограниченным читателем без следования ссылкам, что и в этапе 1. Нет истории, повреждена, новее версии 1 — видимый отказ с кодом (`missing_history`, `invalid_metadata`, `unsupported_version`). В папке не создаётся ничего, даже файл блокировки.
2. **Берёт блокировку Workspace** `<root>/.ultra/locks/writer.lock`:
   - байтовая блокировка ОС (msvcrt на Windows, flock на POSIX); снимается системой при смерти процесса;
   - **реентерабельна в своём потоке** (вложенный вызов `create → activate` не ждёт сам себя); другой поток и другой процесс ждут;
   - заблокированный байт лежит на смещении 1 ГиБ за концом пустого файла. Байт 0, как в `store_lock`, делал файл нечитаемым и **ломал копирование Workspace во время записи** — найдено тестом, исправлено;
   - таймаут 10 с → `WorkspaceBusyError` «Workspace занят другой операцией записи»;
   - никогда не держится во время сетевого вызова или диалога пользователя: в Tk окно ввода открывается до вызова ядра.
3. **Под блокировкой ещё раз читает идентичность** (`expected_workspace_id`): папку могли подменить, пока писатель ждал.
4. **Проверяет путь записи:** каждая папка — обычная, не ссылка, её конечный путь лежит под корнем. Для нового файла дополнительно проверяется, где реально создан временный файл, **до записи байтов**. После публикации байты читаются обратно тем же ограниченным читателем и сравниваются.
5. **Проверяет владельца и версию Chat:** `chat_id` = имя папки, `workspace_id` = текущий, версия 1 (карточка без `schema_version` — старая v1, допустима; более новая — `unsupported_version`).
6. **Публикует атомарно:**
   - замена файла — `os.replace` с ограниченным повтором (≈1,6 с) при `PermissionError` (P11/P12); потом видимая ошибка, старый файл цел;
   - новый файл — временный (O_EXCL) → fsync → `os.rename` (Windows отказывает при существующем имени; POSIX — `os.link`). **Перезапись невозможна даже для писателя без блокировки**;
   - чат — staging → один `os.rename` папки, с тем же повтором.

### 4.2. Tk (`ultra_ui.py`, только writers Chat)

- «+» у Workspace → `create_chat(..., expected_workspace_id=<ID из реестра Tk>)`. Пропавший `workspace.json` больше не порождает новый Workspace.
- «Создать / подключить Workspace» → первый чат с идентичностью, только что подтверждённой.
- «✎» у чата → `rename_chat(..., expected_title=<название в окне>, expected_workspace_id=...)`. Список для окна берётся из `list_existing_chats` (без создания хранилища).
- RAW-писатели Tk (`user` перед запросом, `assistant`, терминальная ошибка) не менялись: они вызывают `append_raw_message`, который теперь идёт через общий контракт.

### 4.3. Веб (`web_alarm/ultra_chat.py`, `server.py`, `ui.py` — область Ultra Chat)

**Отдельное право записи.** `GET /ui/ultra-chat/write-capability` → `ultra_chat_write`: свой токен, свой заголовок `X-WebAlarm-Ultra-Chat-Write-Token`, только в памяти процесса.

- Токен чтения Stage1 запись **не разрешает**; токен записи историю **не читает**.
- Право есть только при loopback-привязке и включённом чтении. Выключается `--disable-ultra-chat-write` (чтение остаётся).

**Маршруты (только POST):**

| Маршрут | Тело | Ответ |
|---|---|---|
| `/ultra/chat/workspaces/<wa_id>/chats` | `{"chat_id": "chat_<32 hex>", "title"?}` | 201 создан / 200 повтор / 409 `chat_id_conflict` |
| `/ultra/chat/workspaces/<wa_id>/chats/<chat_id>/title` | `{"title", "expected_title"}` | 200 / 409 `title_changed` |

**Порядок проверок:** Host и Origin (ровно один, точный) → метод → маршрут и ID (без диска) → размер ≤ 4 КиБ (413), `Content-Type: application/json` (415) → токен записи → тело → данные.

- Workspace только из реестра Web Alarm. Нужна существующая история Ultra: иначе 409 `workspace_unavailable` с причиной. В папке ничего не создаётся.
- Ответы без путей и токенов. Сообщения ядра в браузер не уходят: только безопасный код и фиксированный текст. Непредвиденная ошибка — 500 без деталей.
- Небольшое тело читается до любого отказа, чтобы отказ доходил до клиента (иначе обрыв 10053, как F-S1).

**Страница.**

- Токен записи запрашивается **только при «Сохранить»** и уходит только с этими POST.
- ID нового чата выбирает страница при открытии формы. Повтор после потерянного ответа — тот же запрос, второго чата не будет.
- Повторное нажатие во время сохранения игнорируется.
- После любого изменения список перечитывается с сервера.
- `title_changed` → список обновляется, повторное «Сохранить» осознанно заменяет новое название.
- После перезапуска сервера страница один раз берёт новое право и повторяет запрос.
- Escape и «Отмена» закрывают форму; смена Workspace — тоже.
- Для папки без истории кнопки выключены.
- Поле ввода сообщений по-прежнему выключено.

## 5. Совместимость старого формата

- ID Workspace, Chat и Message, существующие RAW не меняются. Байтовый формат новой записи RAW совпадает со старым: поля, порядок, отступ 2, LF, `\n` в конце (тест `test_append_keeps_the_exact_stored_format`).
- Старые RAW остаются байт-в-байт; неизвестные поля карточки чата сохраняются при переименовании (`test_old_records_and_unknown_fields_survive_every_writer`).
- Карточка без `schema_version` — старая v1, остаётся доступной для записи. Неизвестная версия Workspace или Chat — видимый отказ, **без изменений на диске** (снимок байтов до и после).
- Читатели Tk (`list_existing_chats`, `load_chat_messages`, `load_chat_working_messages`) **не менялись**. Характеризационные тесты Stage1 (P1–P6) проходят без правок.
- Новое в `.ultra/`: служебная папка `locks/` с пустым `writer.lock`. Её можно удалить, когда никто не пишет. Копирование Workspace во время записи работает.

## 7. MANUAL ENGINEERING REVIEW

Самостоятельный adversarial-проход по финальному коду, не только по тестам.

**Что подтверждаю:**

- Каждая публичная функция записи ядра проходит через одну сессию: проверка → блокировка → повторная проверка → проверка пути → атомарная публикация → обратное чтение. Обходных путей записи в `context_storage.py` не осталось (ни один writer не пишет до `_existing_workspace_writer`, кроме `ensure_workspace_storage`, который создаёт под той же блокировкой).
- Отказ из-за версии, идентичности, ссылки или ввода не меняет ни байта (снимки до/после в тестах).
- Конфликт RAW никогда не перезаписывает: даже без блокировки (писатель старой версии кода) эксклюзивный `rename` не даёт заменить файл (мутант C03, тест «запись снаружи блокировки»).
- Веб не может создать или изменить ничего вне зарегистрированного Workspace с существующей историей; путь из браузера не принимается вовсе — только `wa_workspace_id`.
- Токены разделены в обе стороны; ни один ответ не несёт пути или токена.

**Что осталось и почему так:**

1. **Окно подмены папки.** Проверка временного файла закрывает подмену до записи байтов. Подмена в оставшемся окне (после проверки временного файла, до `rename`) только **обнаруживается** обратным чтением, а запись уже лежит в чужой папке. Для замены карточки (`os.replace`) проверки временного файла нет — только обратное чтение. Это защита от другой программы того же пользователя, чего контракт Stage0 §9 не обещает. Под блокировкой кооперирующие писатели папки не меняют.
2. **POSIX.** Публикация через `os.link`: читатель в долю секунды может увидеть `st_nlink == 2` и временно пометить запись `unsafe_storage_link`. Fsync каталога после rename не делается. Целевая платформа — Windows; POSIX не проверялся.
3. **Tk-читатели не менялись** (P1–P6 Stage0 остаются в Tk-пути отображения и в контексте модели). Изменение чтения Tk вне формулировки write-scope `ultra_ui.py` («только writers») и меняет закреплённое поведение; см. §11.
4. **Быстрый путь `ensure_workspace_storage`** при полном хранилище только читает и ссылки не проверяет: если `.ultra` — junction, Tk при «подключить Workspace» прочитает чужую идентичность. Любая последующая **запись** откажет (`unsafe_storage_link`). См. §11.
5. **Ожидание блокировки в главном потоке Tk** — до 10 с при чужой долгой записи (на практике миллисекунды). Видимая ошибка, не зависание навсегда.
6. **Право записи веба включено по умолчанию** (loopback, своё право, точный Origin). Обоснование: STANDARD-запускатель вне write-scope, а задача требует создание/переименование на экране. Выключается `--disable-ultra-chat-write`. Конкретного Stage1-gate, блокирующего безопасную запись, не найдено: открытые пункты Stage1 — независимые проверки чтения (§10).
7. **Создание истории Ultra в зарегистрированной папке из веба не добавлено** (Stage0 §3.1 допускает его как явное действие этапа 2, БЛОК 1 §4.4 его не требует). Веб отвечает `workspace_unavailable / missing_history`; создать историю можно в Tk.
8. **Повтор после «потерянного ответа» с изменённым названием** даёт `chat_id_conflict`; список перечитывается, и уже созданный чат виден.
