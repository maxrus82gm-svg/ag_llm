## 4. Техническая реализация

### 4.1. Один общий сервис

Использовать существующий `context_storage.py` и формат `.ultra/`.

Изучить действующие `create_chat()`, `rename_chat()`, `append_raw_message()`, функции чтения и все фактические вызовы из `ultra_ui.py`.

- Не изменять исходный текст ранее сохранённых RAW.
    
- Исключить скрытое создание другого Workspace или Chat при ошибке чтения.
    
- Для несовместимой/неизвестной версии формата — диагностируемый безопасный отказ.
    

### 4.2. Согласованная запись Tkinter и Web

Создание и переименование Chat, обновление метаданных и сохранение RAW должны проходить через общий согласованный контракт.

Проверить применимость `web_alarm/store_lock.py`. Если его область защиты недостаточна, адресно расширить механизм в разрешённых файлах.

Необходимо обеспечить:

- межпроцессную блокировку критических операций записи;
    
- защиту от потери изменений при двух одновременных писателях;
    
- атомарную публикацию файлов и корректное поведение при I/O failure;
    
- устойчивую обработку рестарта и частичных записей;
    
- отсутствие неконтролируемого выхода за Workspace root.
    

Блокировка сама по себе не заменяет проверку идентичности объекта, восстановление после сбоя и защиту от подмены пути.

### 4.3. Повторная запись RAW без дублей

Добавить внутреннюю возможность безопасно сохранить RAW с заранее определённым `message_id`.

Правила:

1. Новый ID — одна новая запись.
    
2. Существующий ID и идентичное содержимое — возврат ранее сохранённого результата, без второго RAW.
    
3. Существующий ID с отличающимся содержимым или несовместимой идентичностью — явный конфликт, без перезаписи.
    
4. Два разных ID с одинаковым текстом — две допустимые самостоятельные записи.
    

Сохранить поддержку прежнего `append_raw_message()` и совместимость его существующих вызовов.

Это **локальная идемпотентность хранения**. Полный Turn, ключ повторной отправки и управление внешними попытками — этап 3.
