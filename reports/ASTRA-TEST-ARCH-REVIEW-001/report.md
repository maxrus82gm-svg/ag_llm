## Существенные findings

### R1 / HIGH / 36.3 §4 «Минимальные реальные команды», строка 58

**Проблема.** `python -B -m unittest test_final_audit` приведён рядом с guarded S0 runner как пример целевой проверки. Однако первый запуск не является Git-free offline entrypoint: он собирает cases, сознательно выключающие Git mocks и достигающие реального subprocess. Общая оговорка «после разрешённого local preflight» не указывает эту уже существующую особенность команды. При действующем запрете локальным агентам такая команда не готова к обычному использованию.

**Доказательство по исходникам, без выполнения:**

- `test_final_audit.py:341`, `test_non_git_workspace_mutation_reaches_final_pass`: `allow_write=True`, `allow_verify=True`, запись `result.txt`, затем `run_case(..., mock_git=False)` (351). Аналогичный выбор есть в `test_precise_edit_tracks_run_and_reaches_final_audit` (375).
- `test_final_audit.py:283`: `_agent_git_status/_agent_git_diff` подменяются только при `mock_git=True`; `run_case` вызывает настоящий `server.run_agent_task` (298).
- `server.py:2934–2973`: Final Audit при разрешённом READ собирает Git observations. Непустые task-scoped пути после записи не подпадают под early return для пустого scope.
- `server.py:1598/1657`: helpers строят команды `git ... status` и `git ... diff`; `server.py:1443/1463`: `_run_verify_process` вызывает `subprocess.run`. Отсутствие `.git` в disposable workspace означает возможную ошибку Git, **не отсутствие запуска Git**.
- Guarded entrypoint `test_rt002_s0_kernel.py:464–481`, напротив, устанавливает guard до runtime imports и использует свой manifest. Полный `unittest test_final_audit` автоматически этот guard не получает.

**Почему это риск.** Будущий launcher или локальный агент может взять документированный пример как готовую offline-команду и нарушить `DOC-GIT-01@1` / `TEST-SCOPE-01@1`. Политика не отменена документом — дефект в несовместимости конкретного рецепта с политикой. Это не утверждение о фактическом нарушении в данном аудите: команда не запускалась.

**Минимальное исправление.** В 36.3 явно пометить прямой полный `unittest test_final_audit` как непригодный под default no-Git без проверенной изоляции/подмен либо отдельного разрешения. Основным доступным offline entrypoint оставить guarded S0 с его **ограниченным** manifest; не объявлять его заменой полного Final Audit suite. Для недостающих cases нужна отдельная разрешённая задача на guarded запуск. Production и существующие тесты ради исправления документа менять не требуется.

### R2 / MEDIUM / 36.2 «Raw oracle для всех критичных гонок», строки 54–66

**Проблема.** Общий алгоритм после разрешённого recovery безусловно утверждает: «новый receipt … => FAIL». Это верно для некоторых сценариев чистого replay/закрытия, но неверно как oracle **для всех** критичных гонок и recovery. Не определены baseline и разрешённая причина появления receipt.

**Контрпример по действующему контракту и коду:**

- `23_Архитектура Web Alarm Workspace.md`, CURRENT RC-6 (строки 19–25): recovery использует persisted authority; ADOPT/RETRY не запрещённые destructive dispositions.
- `test_web_alarm_mutation_executor.py:501`, `test_receipt_not_persisted_then_adopted_without_a_second_write`: physical POST уже получен, запись DONE/receipt отказала; операция остаётся STARTED, затем разрешённый ADOPT и recovery приводят к VERIFIED без второй записи.
- `web_alarm/recovery_coordinator.py:888–944`: ADOPT требует принятого resolution, актуальной revision/freshness и target locks; это отдельное разрешённое действие.
- `web_alarm/operation_store.py:767–782`: ветка ADOPT создаёт `_done_receipt(...)`, проверяет `matches_expected_post`, сохраняет receipt и VERIFIED. Появление нового receipt здесь — штатный подтверждённый переход, не само по себе дефект. В этом аудите сценарий не исполнялся; приведён статический контрпример нормативу.

**Почему это риск.** Реализация универсального oracle по буквальному правилу даст ложный FAIL законному settlement. Последующее «исправление красного теста» может либо повредить recovery-контракт, либо привести к blanket-ослаблению полезной проверки historical replay.

**Минимальное исправление.** Разделить две ветки: (1) read-only replay сохранённого результата — receipt неизменен, нового apply нет; (2) явно разрешённый recovery/ADOPT — новый receipt допустим только по независимой модели ожидаемого перехода с resolution identity, revision, подтверждёнными POST bytes и без повторного physical effect. FAIL — receipt без соответствующей authority, с неверным содержимым/identity либо изменение historical receipt там, где контракт требует неизменности. Если этот алгоритм предназначался только для F1/F3 Closeout, достаточно сузить заголовок/scope и отдельно направить F2/ADOPT к своему oracle.
