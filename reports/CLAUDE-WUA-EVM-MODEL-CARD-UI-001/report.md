## 1. Итог

Вкладка EVM показывает вместо кратких строк реестра одну общую карточку на модель. Компонент один для всех моделей и провайдеров, отдельного кода под конкретную модель нет. В карточке:

- **заголовок:** название, круглый индикатор API и рамка с числом параметров («— млрд», пока число не задано);
- **сетка назначенных ролей** 4 × 2 с подсказкой при наведении;
- **поле «Сильные стороны модели»:** фиксированная высота, прокрутка внутри, межстрочный интервал 1,15;
- **две кнопки:** «Настройки» и «Проверить чат».

Строки «В реестре», «API не проверено» и `model_id → provider_model_id` из карточки убраны. Технические идентификаторы показаны в настройках.

Сервер считает один статус API для карточки и окна диагностики. Статус хранится между запусками. Роли берутся только из реальных назначений: выбор модели веб-чата и настройки прежней Ultra (Tkinter), которые сервер только читает. Кнопка «Отправить тестовое сообщение» в этой версии ничего не отправляет: живая проверка требует отдельного USER GO. Имитированный ответ никогда не делает индикатор зелёным.

### 3.1. HTTP-маршруты

| Маршрут | Назначение |
|---|---|
| `GET /ultra/model-cards` | Всё, что показывают карточки. Ничего не создаёт и не отправляет (`network_calls: 0`). Параметры запроса отклоняются |
| `POST /ultra/model-cards/<model_id>/settings` | Данные карточки и профиль подключения одной модели, одна атомарная запись. Требуется `base_revision` — защита от потерянного обновления из другого окна (409 `settings_revision_conflict`) |
| `POST /ultra/model-cards/<model_id>/check` | Тело — только `{}`. Сейчас ответ `LIVE_CHECK_NOT_AUTHORIZED`, `network_calls: 0`, состояние не меняется |

Все три маршрута требуют локального происхождения: loopback, точный `Host`, совпадающие `Origin` и `Sec-Fetch-Site`. Для POST `Origin` обязателен. Прежние `/ultra/connections*` не менялись (предложение Stage1 P2 остаётся открытым).

### 3.2. Единый статус API

Сервер вычисляет статус при каждом чтении из `ultra/api_checks.json`. Один и тот же объект `api` отдаётся карточке и окну диагностики; на странице один компонент `apiDot`.

| Цвет | Когда |
|---|---|
| ✓ зелёный `CONFIRMED` | Подтверждённый ответ этой модели при **текущей** версии настроек, не старше срока актуальности (по умолчанию 30 суток, граница включительно) |
| ! оранжевый `STALE` | Подтверждение есть и настройки те же, но оно старше срока |
| × красный | `NEVER_CONFIRMED`, `SETTINGS_CHANGED`, `LAST_CHECK_FAILED` (отказ новее успеха), `STATE_CORRUPT`, `TIMESTAMP_INVALID` (неразборчивое время или успех в будущем больше чем на 5 минут), `ADAPTER_MISSING`, `REGISTRY_DISABLED` |

**Версия важных настроек** — SHA-256 (16 знаков) от: провайдера, адаптера, профиля, имени переменной ключа, **наличия** ключа, `credential_revision` профиля, типа доступа (`GIGACHAT_SCOPE`), адресов OAuth и API, `provider_model_id`.

В версию **не входят:** описание, число параметров, таймаут, предел диагностики, срок актуальности. Поэтому их правка статус не сбрасывает. Смена ключа, профиля, адреса или вызываемой модели — сбрасывает.

Записывается:

- успех: версия, время, источник `diagnostic`/`chat`;
- отказ: время, безопасный код и текст, версия при отказе;
- последний вывод, ограниченный пределом диагностики.

Значения вида `Basic …`/`Bearer …` в тексте заменяются на `[скрыто]`.

### 3.3. Назначенные роли: источники

| Роль в карточке | Источник | ✓ когда |
|---|---|---|
| Чат | сохранённый выбор веб-чата (`ultra/connections.json`) | Модель выбрана. **Показывается приглушённой ✓ «назначена, но роль пока не работает»:** отправки в Ultra Chat ещё нет |
| Планировщик | Tk `planner_model_id` | модель совпадает; при `planner_enabled=false` — приглушённая ✓ «роль выключена» |
| Верификатор | Tk `verifier_model_id` | модель совпадает |
| Компрессор | Tk `compressor_model_id` | модель совпадает |
| Doctor Dredd | **модель Верификатора**, отдельного назначения нет | модель Верификатора и включён Планировщик |
| Executor | Tk `main_chat_model_id` (Main) | модель совпадает |
| Final Review | **модель Верификатора** (Final Audit), отдельного назначения нет | модель Верификатора; при `final_audit_enabled=false` — приглушённая ✓ |
| Context | — | роли в runtime нет: знак «–» |

Значения Tk читаются по правилам `ui_state.load_ui_state`: проверка типов, BOM. Если сохранённая модель отсутствует в реестре или отключена, используется та же модель по умолчанию, что берёт сама Tk. Такой откат перечисляется в `roles_source.fallbacks`.

Нет файла — это значения Tk по умолчанию (`DEFAULTS`), страница так и говорит. Файл не читается (битый JSON, не объект, больше 1 МиБ, каталог) — роли Ultra показываются как «?», а не ✓.

Экземпляр сервера на собственном хранилище (тесты, TEST-запуски запускателя) настоящие настройки Tk не читает. Он читает их, только если путь передан явно. Штатный запуск (`WebAlarmApi(None)`) читает настоящий файл Tk.

### 3.4. Настройки и хранение

`ultra/model_settings.json` (атомарная запись, общая блокировка `locks/ultra/model_cards.lock`, счётчик `revision`):

- `models` — описание (до 500 символов, без управляющих символов, CRLF → LF), число параметров (`null` или (0; 100 000]), профиль модели;
- `profiles` — название, `credential_revision`, таймаут 5–120 с (по умолчанию 30, как у транспорта), предел диагностики 200–4000, срок актуальности 1–365 дней (по умолчанию 30);
- `providers` — записи справочника, добавленные вручную. Такая запись **никогда не называет адаптер** и показывается «адаптер отсутствует».

`ultra/api_checks.json` — только сведения о проверках.

Секреты не хранятся нигде. Ключ остаётся у прежнего механизма — переменная среды `GIGACHAT_CREDENTIALS`, которую читает `gigachat_transport`. Сервер проверяет только **наличие** переменной. Тесты работают с окружением, которое падает при любом чтении значения ключа; мутант M10, читающий значение, роняет 13 тестов.

Повреждённый файл (любой из двух) показывается как повреждённый и не заменяется молча. Следующая запись откладывает его рядом (`*.corrupt-<id>`) и начинает файл заново. Для настроек это требует `base_revision: null`.

Окна:

- **«Настройки»:** вкладки «Подключение» (провайдер только для чтения — его задаёт реестр; профиль; факты подключения; неактивные кнопки ключа), «Модель» (идентификаторы, число параметров, источник характеристики, описание со счётчиком), «Дополнительно» (таймаут, предел диагностики, срок актуальности);
- **«Проверка API»:** тот же индикатор, дата последнего успешного ответа, одно поле вывода, кнопки `[Закрыть] [Отправить тестовое сообщение]`. Поля ввода и истории нет.

Черновик настроек и последний ответ диагностики хранятся на странице для каждой модели. Открытие одного окна не сбрасывает состояние другого. «Закрыть» и щелчок по фону закрывают окно и возвращают фокус на кнопку карточки (тест E15). Escape тоже закрывает окно, но тестом не покрыт: в тестовом DOM нет событий клавиатуры.

## 9. Риски и вопросы координатору

1. **Замена значения ключа вне приложения не видна.** Значение не читается, видно только наличие переменной. После подмены ключа в среде статус может оставаться ✓ до первого отказа. Закрывается действиями «Заменить ключ» (повышают `credential_revision`) — нужен USER GO.
2. **Чтение `ui_state.json` во время записи Tk** на Windows может на мгновение дать ошибку совместного доступа. Роли тогда кратко покажутся «?»; ложной ✓ не будет.
3. **Защита маршрута проверки — только локальное происхождение.** Перед живыми платными запросами нужна собственная возможность (токен), как у Ultra Chat.
4. **Вопрос:** выбор модели чата временно стоит над карточками EVM. Переносить ли его к полю ввода Ultra Chat в этапе 2 (запись в экран, который сейчас только читает)?
5. **Вопрос:** нужна ли форма ручного добавления провайдеров и профилей до живого адаптера, или их добавить вместе с ним?
6. Две независимые настройки модели (Tk и веб-чат) по-прежнему существуют, как и отмечено на этапах 0–1. Карточка показывает обе честно, но не объединяет их.
