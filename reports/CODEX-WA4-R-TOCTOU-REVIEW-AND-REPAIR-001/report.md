## Прослеженная цепочка нормальной мутации

1. **CHECK / TARGET IDENTITY:** `OperationStore.begin` и `canonical_target` нормализуют цель, отвергают опасные Windows-имена, ADS, выход из root, leaf link/reparse; контракт содержит байтовое pre-state и fingerprint. Payload хранится по hash.
2. **LOCK / CLAIM:** acquire проверяет revision, владение, sufficiency и наблюдаемые bytes. `mutation_boundary` держит TASK lock → mutation lock → target lock; проверяет claim, revision, контракт, lifecycle и текущие bytes. Locks кооперативные.
3. **CAS:** несоответствие байтов до финальной проверки даёт `PRECONDITION_FAILED`, `_apply` не вызывается. Другой кооперативный владелец блокируется; существующие multiprocess-тесты подтверждают сериализацию.
4. **ACTION:** STARTED записывается до `_apply`. WRITE — temp/fsync/replace, CREATE — публикация с исключением уже занятого имени, DELETE — unlink. Эти вызовы используют путь; capability/handle каталога, удерживаемого до действия, нет.
5. **POST-PROOF / PERSISTENCE:** переход DONE повторно разрешает путь, читает bytes и проверяет ожидаемый post-state; затем сохраняет receipt/record/events. При несовпадении DONE не выдаётся, остаётся STARTED. Receipt доказывает историческое наблюдение, не вечную неизменность файла после него.
6. **RECOVERY / FINAL STATE:** DONE/VERIFIED replay возвращает сохранённую квитанцию без `_apply`; STARTED/UNKNOWN направляется в reconciliation/Resolver. Только авторитетный свежий RETRY допускает новый запуск. Crash-тесты действительно убивают дочерние процессы в контрольных окнах; ADOPT после выполненной записи не повторяет действие.

Move/rename — два отслеживаемых шага CREATE destination → DELETE source, с владением обеими целями и собственными STARTED/receipt. Прерывание между ними — явный PARTIAL, не атомарный move. Соответствующие existing tests прошли.

## F01 / F02: почему post-proof недостаточно

В F01 контролируемый конкурент меняет родительский каталог на native junction **после последнего разрешения пути**, перед реальным `_apply`. Альтернативная цель находится вне синтетического Workspace, но внутри того же TEMP fixture. Действие реально исполняется стандартным кодом. Junction затем убирается и исходный каталог возвращается перед post-proof. Альтернативные bytes уже изменены, исходная цель сохранна, результат — `POST_PROOF_FAILED`, STARTED, receipt=null. Replay даёт `FATE_UNKNOWN`, повторного `_apply` нет. Таким образом защита итогового статуса работает, но не предотвращает неправильный физический эффект. Не заявляется скрытый успешный DONE для этого сценария.

В F02 конкурентная запись после CAS заканчивается до штатного replace/unlink. Результат снова соответствует контракту, поэтому post-proof закономерно принимает его; более поздние внешние bytes теряются. Аналогичный rollback выполняет restore после собственного CAS и получает VERIFIED. Тесты не подделывают persisted operation/claim/CAS-result и не ослабляют блокировки: изменяется только принадлежащий лаборатории target в заданной точке расписания. Эти тесты доказывают возможный порядок событий, а не вероятность эксплуатации или универсальную межпроцессную атаку.

Повторная `canonical_target` или дополнительный hash перед write лишь сдвинет последнее окно и не считается полным исправлением F01/F02. Нужны отдельная модель внешних писателей и привязка OS-операции к нужному объекту/каталогу. Новый механизм владения или архитектурный контракт здесь не вводился.

## Rollback и низкоуровневый snapshot restore

Tracked RC-4: `prepare` сохраняет текущее состояние и сверяет его повторно; `apply` удерживает TASK/mutation/все target locks, проверяет basis, получает claims для всех целей, включая NOOP, делает per-target CAS → APPLYING durable → restore → receipt. При рестарте APPLYING сравнивается с expected restore/preserved; уже записанный restore не повторяется. Перед VERIFIED выполняется полный current proof, ownership освобождается после сохранения результата. Существующие crash/resume, дрейф после receipt, NOOP ownership и гонки с кооперативным писателем прошли.

Гипотеза о безусловном использовании испорченного снимка tracked rollback **опровергнута** в двух точках: изменение сразу после `restore_plan` блокируется freshness (`STALE_RESOLUTION`, запись не вызывается); изменение после последнего `_session_basis` не меняет уже удерживаемый проверенный буфер, restore пишет правильные bytes. Первый исследовательский тест ошибочно ожидал VERIFIED в первой точке; исходный FAIL сохранён, ожидание исправлено и оба порядка проверены отдельно.

F04 относится к другому, реально достижимому пути: CLI `snapshot restore` → `ManifestSnapshotStore.restore_microtask`. Он сначала вызывает verify, затем заново читает snapshot для применения без проверки этого нового буфера. Искажение после verify приводит к записи плохого содержимого, после чего выдаётся `restored hash mismatch`, статус RECOVERY_REQUIRED. Повторный вызов не восстанавливает потерянные bytes автоматически. Это не обвинение tracked RC-4: его `restore_plan` проверяет удерживаемый буфер. Патч добавляет ту же необходимую проверку в существующий low-level путь, сохраняя его API и не выдавая его за RC-4 transaction.

## Проверенное предложение исправления

`proposed-fix.patch` меняет только `web_alarm/file_state.py` и `web_alarm/manifest_store.py`. Обоснование и пределы — `repair-notes.md`. Патч не применён в общем репозитории; candidate существует только в TEMP.

F03: сравнение lstat с fstat открытого дескриптора, повторная проверка descriptor metadata/размера после streaming read и lstat имени перед возвратом. На Windows первая версия ошибочно сравнивала также ctime: lstat и fstat этой версии Python возвращали разные значения для одного стабильного файла. Этот кандидат дал **5 FAIL + 1 ERROR**, его лог сохранён. ctime исключён из cross-API signature, после чего профильная регрессия прошла. Это ограниченное обнаружение видимых замен и изменений; metadata может быть восстановлена/не обновиться своевременно. Отдельный fingerprint/CAS API и атомарный snapshot файловой системы не добавлялись.

F04: проверяются размер и SHA-256 именно `data`, который затем удерживается в `actions`. Оба вида порчи (тот же размер и другой размер) отказывают **до первой записи**. Повторный отказ проверен с count физических write=0. При неизменном снимке штатный restore продолжает работать.
