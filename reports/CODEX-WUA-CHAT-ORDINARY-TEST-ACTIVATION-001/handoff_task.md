# CODEX-WUA-CHAT-ORDINARY-TEST-ACTIVATION-001

**TASK ID:** `CODEX-WUA-CHAT-ORDINARY-TEST-ACTIVATION-001`

**Исполнитель:** Codex 007  
**Тип:** IMPLEMENTATION + FOCUSED OFFLINE TESTS  
**Приоритет:** HIGH — CHAT FIRST  
**База:** main №567, `e9f6fd2e1dfb1a00cf029f98aa1473201f27e8f6`  
**Предыдущая задача:** `H-CODEX-000027` — BOUNDED INDEPENDENT OFFLINE PASS

## 1. Цель

Подключить реализованный в предыдущей задаче `OrdinaryCoreChatService` к постоянному TEST-профилю Web Alarm Ultra.

**Итог:** пользователь запускает `Start_WebAlarm_Test.cmd` и получает веб-чат, который действительно проходит через существующее Ordinary Chat Core, а не прежний Stage5-имитатор.

Настоящий внешний провайдер пока не используется.

## 2. Обязательный вход

Прочитать актуальные №08, №000, №34, №40, №37 §3а, №20 §5а и адресный FOLLOWUP №05:

`FOLLOWUP-WUA-ORDINARY-CORE-BRIDGE-ACTIVATION-001`

Изучить результаты `H-CODEX-000027`, особенно:

- `web_alarm/ordinary_chat_bridge.py`
- `web_alarm/ultra_chat.py`
- `web_alarm/turn_service.py`
- `web_alarm/server.py`
- `web_alarm/launcher.py`
- `web_alarm/launch_test_config.json`

Сверить текущие исходники с `main`. Если появились новые изменения, сначала проверить пересечения и сообщить о конфликте.

## 3. Что реализовать

### A. Постоянный запуск

Добавить новый TEST-профиль Ordinary Core Chat и сделать его активным для `Start_WebAlarm_Test.cmd`.

Сохранить:

- существующее имя CMD;
- предупреждение о тестовом режиме;
- запуск браузера;
- изолированное временное хранилище;
- очистку тестовых данных после закрытия;
- старый Stage5-профиль как доступный вариант отката.

`Start_WebAlarm_Standard.cmd` не изменять.

### B. Работа веб-чата

Через новый TEST-профиль должны работать:

1. Создание Workspace и отдельных чатов.
2. Выбор доступной тестовой модели.
3. Отправка сообщения через Ordinary Chat Core.
4. Получение ответа через fake transport.
5. Сохранение истории и состояния Turn.
6. Восстановление после F5.
7. Изоляция контекста между двумя чатами.

Не создавать второй механизм истории, Turn или Model Registry.

### C. Минимальный учёт токенов

Если существующий интерфейс уже умеет показывать usage, связать его с результатом Ordinary Core.

Проверить корректное отображение input/output/known reasoning и UNKNOWN без двойного подсчёта.

**Не разрабатывать сейчас:** глобальные бюджеты Workspace, финансовую аналитику, полноценный Статист, большие панели настройки токенов.

Настраиваемые лимиты 250k/10k/20k остаются следующим отдельным этапом, если не поддерживаются существующим кодом.

## 4. Жёсткие ограничения

- STRICT OFFLINE: никаких GigaChat, OAuth, внешних API и платных запросов.
- STANDARD остаётся неизменным и не получает возможность физической LLM-отправки.
- S3b не обходить и не объявлять выполненным.
- Не изменять Tkinter Ultra, Blueprint, MCP, Colibri и чужие направления.
- Никаких новых общих подсистем бюджета Workspace.
- Никаких изменений Git/GitHub со стороны локального исполнителя без отдельного разрешения пользователя.

## 5. Минимальные проверки

Проверить адресно:

- Новый профиль действительно выбирается постоянным TEST-лаунчером.
- Два чата работают независимо.
- Два последовательных сообщения сохраняют правильный контекст.
- F5 не теряет историю.
- Повтор Turn не вызывает дублирования.
- Закрытие тестового запуска удаляет только временные данные.
- STANDARD не затронут.
- REAL без S3b гарантированно отклоняется.

Не запускать несвязанные большие тестовые наборы. Сохранить команды, результаты PASS/FAIL/SKIP и ограничения проверки.

## 6. Работа при заканчивающемся лимите

**Режим экономного выполнения.**

Приоритет P0 — подключить существующий мост к постоянному TEST-профилю и сохранить работоспособность старого Stage5-профиля.

Приоритет P1 — адресные регрессионные тесты, изоляция, сохранение, запрет REAL.

Приоритет P2 — минимальное отображение usage, только если хватает ресурсов и не требуется переработка UI.

После каждого законченного этапа сохранить небольшой checkpoint: сделанные изменения, выполненные тесты, оставшиеся вопросы.

Если лимит заканчивается:

- Не начинать большой дополнительный этап.
- Не заявлять незавершённое успешным.
- Сохранить промежуточный отчёт и список следующих действий.
- Не запускать автоматические длительные повторы.

Частичный результат допустим. Штатный `finish` выполнять только после подготовки достоверного отчёта, проверки сохранности результата и выполнения условий протокола сдачи; при необходимости указать PARTIAL.
