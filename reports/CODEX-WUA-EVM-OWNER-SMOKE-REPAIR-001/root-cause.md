# Root cause и ручная инженерная проверка

## F-01 — окно

H41 создаёт отдельное окно через `window.open(..., 'popup=yes,width=540,height=740,...')`; исходная DOM карточка остаётся в EVM. Внутренние `#evmPins` и Document Picture-in-Picture являются другими механизмами. В коде отсутствует перетаскивание *системного* окна за HTML-заголовок; пользователь мог перетаскивать его как внутреннюю карточку, но это **гипотеза**, а не доказанная причина. Добавлена точная подсказка о системном заголовке и Windows shortcut, без фиктивного программного перемещения. Физическая проверка не выполнена из-за остановки Computer Use на URL confidence. Статус PARTIAL.

## F-02 — check

До исправления `_OrdinaryTurnChecker.reason` направлял пользователя в Ultra Chat, а `fillCheck` оставлял кнопку отправки активной при отсутствии сессии и сообщал «в этой версии не отправляется». `ModelCards.run_check` при произвольном исключении считал его подтверждённой ошибкой и мог записать красный, хотя физический исход неизвестен. Это воспроизведено в `evidence/f02_js_red.txt`, `f02_python_red.txt`.

После исправления модальное окно EVM явно показывает отсутствие провайдера и ведёт к прежнему `evmLiveControl(true)`/`/ultra/chat/live/start`. Подключение и потенциально платная проверка подтверждаются отдельно. При активной сессии проверка идёт только через прежний `/ultra/model-cards/{id}/check` → `_OrdinaryTurnChecker` → `OrdinaryApplicationChatService.submit_turn` → TurnService/provider admission/ledger. `PreSendDenied` от `require_real` считается отказом до отправки. Непредвиденное исключение записывает UNKNOWN, не FAILED; известный Turn ID синхронизируется через прежние методы `record_chat_*` с durable dedup. Никакого второго HTTP транспорта и автоповтора нет. Повторное нажатие во время незавершённого UI запроса не создаёт второй POST. Новое действие после завершения требует нового подтверждения и может быть новым тарифицируемым запросом.

## F-03 — три состояния

H41 показывал кнопку «Отключить» как *действие* и отдельный API dot; это позволяло прочесть «включена» как «проверена». Добавлена строка с тремя подписями: `Модель`, `Провайдер`, `Работоспособность`. `enabled` остаётся разрешением модели из server store; состояние GigaChat берётся из текущей `turn_test` capability; API color/reason — из `ModelCards.api_status`. Ошибка и процесс подключения видны в текущем UI, после F5 действительное состояние снова читается сервером. Последняя подтверждённая работоспособность может оставаться зелёной у ныне отключённой модели: это отдельный исторический факт, а не разрешение отправки.

## F-04 — S2

S2 не принял изменённый в H41 `web_alarm.ordinary_provider` как точный offline admission gate, поскольку `rt002_multimodel_reconciliation.json.policy_gates` содержал прежний AST hash. Тогда статический граф видел путь к `ultra_budget_policy` через fixture-only `BudgetLedger` и сообщил 13 `PRODUCTION_REACHES_POLICY`. Импорт ledger находится внутри ветви `if initialize and fixture is not None`; стандартная реальная отправка эту ветвь не использует. После ручной проверки всего gate обновлён только его точный fingerprint. S2 снова 73/73; in-memory добавление прямого импорта policy даёт 12 нарушений. Ограничение остаётся fail closed для нерассмотренного изменения gate.

## F-05 — Tcl/Tk

Исходный H41 общий Python запуск и повтор этой задачи завершались `Tcl_AsyncDelete: async handler deleted by the wrong thread`. `-X faulthandler -v` показал, что после Tk UI теста сборка мусора уничтожала `tkinter.Variable` в HTTP worker thread во время следующего HTTP теста. Тесты создавали `UltraApp` и регистрировали `destroy`, но не принуждали сборку циклических ссылок на главном потоке. В `test_web_alarm_ultra_chat_s5.py` cleanup теперь сначала выполняет `destroy` всех Tk окон, затем `gc.collect` на test/main thread (LIFO). Повтор объединённого selector завершился 97 тестами, exit 0, без Tcl диагностики. Это исправление тестового жизненного цикла; штатный Tkinter runtime не менялся.
