## 3. Задача 3.2 — общая модель диалога

Полностью описана в `architecture-contract.md` §2–6. Основные решения:

1. **Две идентичности Workspace.** `wa_workspace_id` (регистрация Web Alarm, только этот компьютер) и `ultra_workspace_id` (`.ultra/workspace.json`, переносимая). Обе имеют вид `ws_` + 32 hex. Подтверждено: `web_alarm/models.py:72` и `context_storage.py:272`. Браузер передаёт только первую, сервер выводит вторую через `probe_existing_workspace`.
2. **Обычное сообщение не создаёт Web Alarm TASK и RUN.** `task_block_id` сохраняется лишь как техническая группировка для совместимости с отображением Tk. Run Store не принимает роль chat (`USAGE_ROLES`, `run_store.py:22`), и расширять его — решение B2.
3. **RAW записывается ровно один раз локально.** Фиксация с заранее назначенным `message_id` и эксклюзивной публикацией. Тот же ID и то же содержимое — прежний результат; другое содержимое — конфликт. Сейчас повтор `append_raw_message` создаёт второе сообщение (P7).
4. **Turn.**
   - Ключ повтора `client_request_id` и `request_hash`.
   - Снимок модели, контекста и политики при приёме и повторная проверка разрешений перед отправкой.
   - Состояния ACCEPTED / SENDING / COMPLETED / FAILED / UNKNOWN / CANCELLED; флаги `cancel_requested` и `late_result`.
   - Порядок фиксации: резервирование ключа → Turn → user RAW. «Принято» сообщается только после этого.
   - Замок попытки — признак живого исполнителя.
   - Таблица восстановления. Автоматической платной повторной отправки нет.
5. **Неизвестный исход честен.** UNKNOWN не превращается ни в успех, ни в ошибку. Однократное исполнение у провайдера не обещается.
6. **Старые записи.** Исход определяется при чтении, без переписывания: Turn → `producer.run_id` → `task_block_id` → точный маркер Tk → user без ответа (контракт §4).

## 4. Задача 3.3 — безопасное чтение истории

Контракт §7 и `stage1-handoff.md` §6. Основное:

- **Граница HTTP.** Все маршруты `/ultra/chat/*`:
  - точный `Host` (защита от DNS rebinding);
  - `Origin` и `Sec-Fetch-Site`;
  - токен возможности, в том числе для GET;
  - только GET, ошибки без путей.

  Подтверждено: общий API сейчас `Host` не проверяет (`WebAlarmApi.dispatch`), строгая проверка есть только у folder picker (`web_alarm/server.py:1125`).
- **Идентичность и границы.** Из браузера приходят только ID, проверенные регулярными выражениями. Каждая запись проверяется по всей цепочке. Звенья `.ultra` не могут быть reparse point.
- **Лимиты до чтения.** Перечень и `stat` → чтение ≤ лимитов → сортировка → страница. Лимиты:
  - 2 000 файлов и 64 МиБ на чат;
  - 4 МиБ на файл;
  - страница 50/200 сообщений;
  - ответ 8 МиБ.

  Превышение даёт видимое состояние, а не молчаливую обрезку.
- **Повреждённые, повторяющиеся и старые записи** обрабатываются без падения всей истории. Различаются состояния `complete`, `partial`, `unavailable`, `empty`.
- **Отображение и контекст модели** — разные функции. Читатель отображения не используется для запроса к модели.

## 5. Задача 3.4 — совместная работа Tkinter и Web

### 5.1. Достаточно ли существующих механизмов

| Механизм | Вывод | Доказательство |
|---|---|---|
| Атомарная запись одного файла (temp + fsync + `os.replace`) | **Достаточна** против порванных файлов; для последовательностей из нескольких файлов нужен явный порядок (контракт §6) | `context_storage.py:70`, `run_store.py:57` |
| `InterProcessLock` (msvcrt, байт 0) | **Пригоден как примитив:** исключает другой поток и другой процесс, освобождается при смерти процесса. Не реентерабелен. Ядро не может импортировать его из `web_alarm` (пакет тянет весь Web Alarm) | P10 (5/5); `web_alarm/__init__.py` |
| Защита от второго Tk (`_SingleInstanceLock`) | Защищает только Tk от Tk, веб не покрывает | `ultra_ui.py` |
| Индекс Run Store | **Недостаточен для двух писателей:** из 80 записей сохраняются 40, второй процесс падает с `KeyError` (`run_store.py:185`) | P9 (5/5) |
| Замена файла при открытом читателе | **Ограничение платформы:** замена невозможна, пока файл кем-то открыт, даже с FILE_SHARE_DELETE. В `context_storage` нет повтора (в Run Store есть). Данные не портятся, временный файл удаляется | P11, P12 (5/5) |

### 5.2. Простейший достаточный способ

Блокировка уровня Workspace в файле `.ultra/locks/writer.lock`:

- её берут **общие функции записи ядра**, а не оболочки;
- она держится только на «прочитать → проверить → записать», никогда — на время сети или ожидания пользователя;
- одновременно не больше одного Turn в `SENDING` на Workspace;
- веб-читатель закрывает файлы сразу;
- на этапе 2 запись получает ограниченный повтор замены.

На этапе 1 веб только читает, поэтому блокировка ещё не нужна. Пока индекс Run Store пишет только Tk, веб его только читает.

### 5.3. Как проверять конкурентность, перезапуск, восстановление и откат (этапы 2–3)

На синтетических Workspace в TEMP, отдельными процессами, через guarded runner:

1. **Два писателя.** Tk-путь и веб-путь — разные процессы. Они одновременно создают Chat, RAW и записи индекса. Ожидается: потерь нет, второй получает видимый отказ «занято» или проходит после первого. Тест P9 из этого пакета превращается в регрессию.
2. **Смерть процесса с блокировкой.** Процесс убивается, пока держит блокировку. Блокировка освобождается (как P10), незавершённых видимых данных нет.
3. **Сбой в каждой точке §6.2.** Процесс завершается принудительно в точках внедрения сбоя тестовой сборки. Затем выполняется восстановление по таблице §6.3 и проверяется, что не появилось второго user или assistant RAW.
4. **Открытый читатель во время записи.** Ограниченный повтор, затем видимая ошибка. Исходный файл цел.
5. **Перезапуск до и после отправки** с имитатором провайдера: UNKNOWN без автоматического повтора.
6. **Откат.** Новые операции отключаются. Записи, добавленные по новому формату, читаются прежним читателем без ошибок. Старый писатель не возвращается к несовместимому формату и не теряет принятые сообщения (№37 §2.1).

- **Число активных Turn.** Выбрана консервативная граница «один SENDING на Workspace», а не на чат.
