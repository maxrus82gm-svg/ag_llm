## 1. Топология: одно ядро, два процесса

**Решение.** На время перехода работают два процесса одного пользователя:

- процесс Tkinter Ultra (`ultra_ui.py`) — не более одного экземпляра, это уже обеспечивает `_SingleInstanceLock` (файл в `%LOCALAPPDATA%\GigaChatUltra\runtime\`);
- процесс Web Alarm (`python -m web_alarm`, `ThreadingHTTPServer`, только loopback), который импортирует те же модули ядра: `context_storage.py`, `run_store.py`, `model_registry.py`. EVM уже так использует `model_registry.py`.

Второй Python runtime, отдельный HTTP-сервис, брокер или новая база данных **не нужны**. Общая изменяемая сущность одна — файлы `.ultra` внутри папки Workspace. Для их согласования достаточно межпроцессной блокировки файла (P10: исключает другой поток и другой процесс, освобождается при смерти процесса) вместе с атомарной заменой файлов и правилами §5. Одинаковый импорт модуля сам по себе ничего не согласует: согласование возникает только тогда, когда блокировку берут **общие функции записи ядра**, а не оболочки.

Направление зависимостей: ядро не импортирует `web_alarm`. Подтверждено: `web_alarm/__init__.py` при импорте подтягивает весь Web Alarm (mutation executor, recovery, stores), поэтому ядро не может брать примитив блокировки из `web_alarm.store_lock`. Для ядра нужен свой небольшой модуль блокировки с той же семантикой (msvcrt, байт 0, освобождение при смерти процесса); `web_alarm/store_lock.py` остаётся без изменений и вне пересечения с WA4-R.

## 2. Две разные идентичности Workspace

Подтверждено:

| Идентичность | Где хранится | Кто создаёт | Переносимость |
|---|---|---|---|
| `wa_workspace_id` | регистрация Web Alarm: `web_alarm/models.py:72` `WorkspaceRegistration`, файл в локальном хранилище Web Alarm (`workspace_registry.py`) | Web Alarm при регистрации папки | только этот компьютер |
| `ultra_workspace_id` | `<папка>/.ultra/workspace.json` | `context_storage.ensure_workspace_storage` | переезжает вместе с папкой |

Обе имеют одинаковый вид `ws_` + 32 шестнадцатеричных символа (обе из `uuid4().hex`), но это **разные пространства имён**. Сравнение строк между ними — ошибка.

**Решение.**

1. В коде и HTTP эти идентификаторы всегда называются раздельно. Браузер передаёт только `wa_workspace_id`.
2. Сервер берёт корень папки из реестра Web Alarm, затем читает `ultra_workspace_id` через `probe_existing_workspace(root)`. Эта функция ничего не создаёт (P5).
3. Привязка — пара (`wa_workspace_id`, `ultra_workspace_id`). Она вычисляется при каждом запросе и в браузере не хранится как авторитетная.
4. Состояния привязки берутся из `_probe_existing_workspace_internal`: `ok`, `missing_path`, `not_directory`, `missing_metadata`, `invalid_metadata`, `id_conflict`. Состояние `missing_metadata` означает, что в папке нет истории Ultra: пользователь видит именно это, и ничего не создаётся.

## 3. Сущности

### 3.1. Workspace

- **Постоянный ID:** `ultra_workspace_id`, формат `^ws_[A-Za-z0-9_-]{16,128}$` (`context_storage.py:22`).
- **Владелец данных:** `context_storage.py` — формат `.ultra/workspace.json` и Project Context. Web Alarm владеет только своей регистрацией.
- **Чтение:** только `probe_existing_workspace` / `_require_existing_workspace`. В путях чтения запрещены `ensure_workspace_storage`, `list_chats`, `ensure_chat`, `load_project_context`: они создают `.ultra`, `chats`, `project_context.md` и `project_context_history` (P5).
- **Запись:** `ensure_workspace_storage` — только по явному действию пользователя «включить историю Ultra в этой папке» (этап 2), под блокировкой Workspace (§5).
- **Повтор:** идемпотентен, существующая metadata используется повторно.
- **Сбой:** одна атомарная запись файла (temp → fsync → `os.replace`, `context_storage.py:70`). После сбоя файла либо нет, либо он полный.
- **Старые записи:** `schema_version = 1`. Неизвестная версия — видимый отказ, без «починки».

### 3.2. Chat

- **Постоянный ID:** `chat_` + 16…128 символов `[A-Za-z0-9_-]` (`context_storage.py:23`). Новые чаты получают `chat_` + `uuid4().hex`.
- **Где:** `.ultra/chats/<chat_id>/metadata.json`, а также `messages/`, `summaries/`, `message_context/`.
- **Владелец:** `context_storage.py`.
- **Чтение — решение:**
  - каждая карточка Chat проверяется полностью: имя папки равно `chat_id`; `workspace_id` в metadata равен `ultra_workspace_id`; папка — обычный каталог, а не точка повторной обработки (reparse point).
  - Подтверждено: сейчас список чатов `workspace_id` не проверяет (P1, `context_storage.py:436`).
  - Подтверждено: сейчас список идёт по junction в чужую папку (P6).
  - Повреждённая карточка не скрывает остальные чаты: она показывается как «повреждена», без содержимого. Подтверждено: сейчас одна битая карточка обрушивает весь список (P1).
- **Запись:**
  - `create_chat` собирает чат в staging и публикует его одним `os.replace` (TASK 147A);
  - `rename_chat` атомарно заменяет metadata;
  - этап 2: обе операции идут под блокировкой Workspace и с повтором замены (§5.3).
- **Сбой:** незавершённый staging остаётся вне видимого пространства чатов.

### 3.3. RAW-сообщение

- **Постоянный ID:** `msg_` + 16…128 символов `[A-Za-z0-9_-]` (`context_storage.py:24`).
- **Файл:** `messages/<message_id>.json`.
- **Поля:** `schema_version`, `workspace_id`, `chat_id`, `message_id`, `role`, `created_at`, `original_text`, необязательные `producer` и `task_block_id`.
- **Владелец:** `context_storage.py`. RAW неизменяем (№03 §14).
- **Чтение — решение:** для каждой записи проверяется полная цепочка идентичности:
  - имя файла равно `message_id`;
  - `chat_id` совпадает с чатом;
  - `workspace_id` равен `ultra_workspace_id`;
  - `original_text` — строка;
  - роль известна;
  - `producer` и `task_block_id` корректны, если присутствуют.
- **Что подтверждено по текущему коду:**
  - Путь отображения `load_chat_messages` (`context_storage.py:626`) не сравнивает имя файла с ID (P2) и не проверяет `workspace_id` (P3).
  - Путь «по ID» `load_raw_message` (`:709`) проверяет всю цепочку.
  - Поэтому копия сообщения под другим именем попадает в рабочую историю модели **дважды** (P2: 2 записи, 1 уникальный ID, одинаковый текст).
  - Одна чужая запись обрушивает сборку рабочей истории целиком (P3).
- **Запись (этап 2):** новая функция фиксации RAW с **заранее назначенным** `message_id`.
  - Публикация эксклюзивная: временный файл → переименование, которое отказывает при существующей цели. На Windows так работает `os.rename`; для POSIX нужен вариант через `os.link`.
  - Если файл уже есть, канонические поля сравниваются: `role`, `original_text`, `producer`, `task_block_id`, `turn_id`, без `created_at`.
  - Совпали — возвращается прежний результат. Отличаются — конфликт.
  - Подтверждено: сейчас `append_raw_message` (`:572`) при каждом вызове создаёт новый UUID, и наивный повтор даёт второе сообщение (P7).
- **Сбой:** временные файлы `.<имя>.<uuid>.tmp` не совпадают с маской `*.json` и читателю не видны.
- **Старые записи:**
  - отсутствие `producer` и `task_block_id` допустимо;
  - роли `system` и `tool` в отображении сворачиваются;
  - в историю модели идут только `user` и `assistant`, как сейчас.
- **Исход:** у самого RAW исхода нет. Исход берётся из Turn (новые записи) или из классификатора старых записей (§4).

### 3.4. Turn — новая сущность (этап 3)

- **Постоянный ID:** `turn_` + `uuid4().hex`.
- **Файл:** `.ultra/chats/<chat_id>/turns/<turn_id>.json`.
- **Ключ повтора:** `client_request_id` (UUID). Оболочка создаёт его при первом нажатии «Отправить» и повторно использует при повторе того же черновика.
- **Резервирование ключа:** файл `.ultra/chats/<chat_id>/turn_keys/<sha256(client_request_id)>.json`, создаётся эксклюзивно. В нём лежат `turn_id`, `request_hash` и заранее назначенные `user_message_id` / `assistant_message_id`.
- **Поля Turn:**
  - идентификаторы: `turn_id`, `chat_id`, `ultra_workspace_id`;
  - повтор: `client_request_key_hash`, `request_hash` — SHA-256 канонического запроса (текст, выбор модели, политика);
  - сообщения: `user_message_id`, `assistant_message_id`;
  - `task_block_id` — техническая группировка для совместимости с отображением Tk, не Web Alarm TASK;
  - `snapshot`:
    - `connection_id`, `model_id`, `provider_model_id`;
    - перечень сообщений контекста (ID, представление, хеш);
    - `policy_revision`;
  - `state`;
  - `cancel_requested_at`;
  - `attempts[]`;
  - `error {code, message}` — без секретов и путей;
  - `created_at`, `updated_at`, `revision`.
- **Владелец:** общий модуль ядра (ConversationService по аналитике Астры). Оболочки только вызывают его.
- **Состояния:**

```text
ACCEPTED ──► SENDING ──► COMPLETED | FAILED | UNKNOWN
    │
    └──────► CANCELLED            (только если физическая отправка не начиналась)
флаги: cancel_requested (отмена после начала отправки), late_result (ответ пришёл после отмены)
```

- **Смысл исходов:**
  - **COMPLETED** — assistant RAW записан.
  - **FAILED** — известно, что ответа нет (ошибка провайдера, некорректный ответ, отозванное разрешение до отправки). Assistant RAW **не** записывается, ошибка хранится в Turn.
  - **UNKNOWN** — запрос мог дойти до провайдера, но исход не зафиксирован: сбой, таймаут или обрыв после отправки.
  - **CANCELLED** — отправки не было.
  - Отмена после начала отправки не означает нулевой расход и отсутствие исполнения (R2-08). Поздний ответ сохраняется как assistant RAW с флагом `late_result`. Без явного решения пользователя он в контекст модели не идёт.
- **Старые записи:** у исторических сообщений Turn нет — их обрабатывает классификатор §4.

### 3.5. RUN и попытка провайдера

- **RUN** — существующий Run Store v2: `run_id`, `.ultra/audit/index.json` (T-NNN / R-NNN), `summary.json`, потоки ролей. Он принадлежит агентскому маршруту Tk (Planner / Executor / Dredd).
  - Подтверждено: роли учёта ограничены `USAGE_ROLES = ("planner", "executor", "dredd")` (`run_store.py:22`).
  - `record_usage` и `record_provider_attempt_*` (`:495`, `:506`, `:530`) отвергают другие роли.
  - Поэтому обычный чат нельзя записать туда без изменения S1/S9 (R2-02).
- **Решение для обычного Chat:**
  - на этапах 3–5 он не создаёт ни RUN, ни Web Alarm TASK;
  - попытки провайдера фиксируются в Turn в существующем формате `provider_accounting.py`: `new_logical_call_id`, `new_provider_attempt_id`, `build_provider_attempt_started` / `build_provider_attempt_terminal`;
  - запись в Run Store / Audit как отдельная роль «chat» возможна только вместе с решением B2 по S1/S9, на этапе 6.
- **Попытка провайдера:** один Turn — от 0 до n попыток. Каждая новая попытка — явное решение пользователя или утверждённой политики. Автоматического повтора после UNKNOWN нет.
- **Три независимых состояния (R2-08):**
  - состояние Turn;
  - исход попытки: `ok` / `http_error` / `transport_error` / `timeout` / `unknown`;
  - полнота учёта: `complete` / `partial` / `unknown`.

## 4. Классификация старых записей при чтении (без переписывания истории)

Порядок признаков, от сильного к слабому:

1. **Turn** (только новые записи) — его состояние.
2. **`producer.run_id`** у assistant RAW — `index.json` → `runs[run_id].run_status`. Подтверждено:
   - recorder пишет `RUNNING` (`run_store.py:181`);
   - при ошибке — `FAILED` (`audit_storage.py:388`);
   - при завершении — статус события или `FINISHED` (`:393`);
   - Tk передаёт, например, `SUCCESS` (`ultra_ui.py:5767`).
3. **`task_block_id`** — `index.tasks[task_block_id].runs` → статусы этих RUN (P8: индекс правильно даёт `FAILED`).
4. **Точный маркер** `RUN STATUS: FAILED\n` в начале текста. Это константа `_format_terminal_worker_failure` (`ultra_ui.py:167`), Tk сохраняет такой текст как assistant RAW (TASK 147B, №03). Признак слабый и так и помечается: `legacy_failed_marker`.
5. **User RAW без ответа** в той же группе `task_block_id` → «ответ не сохранён». Это исторические блоки T-004/T-005/… из №03, TASK 147.

`RUNNING` без живого исполнителя показывается как «прервано / исход неизвестен», а не как «выполняется».

**Отображение** показывает всё с метками. **Контекст модели** (этап 4) включает только завершённые успешно пары. FAILED, UNKNOWN, «ответ не сохранён» и поздний ответ после отмены по умолчанию исключаются (№37 §2.3).

Подтверждено: сейчас текст ошибки Tk попадает в рабочую историю (P8). Поведение Tk этим контрактом не меняется до решения этапов 2 и 4. Новый маршрут Chat с первого дня строит контекст по этим правилам.

## 5. Запись двумя оболочками

### 5.1. Блокировка Workspace

**Решение.**

- Файл блокировки — `<папка>/.ultra/locks/writer.lock`, примитив той же семантики, что `InterProcessLock` (P10).
- Файл лежит **внутри** папки, потому что блокировка привязана к физическому файлу:
  - разные пути к одной папке (буква `subst`, junction, сетевой путь) блокируют один и тот же объект;
  - копии папки независимы.
- Ключ по `ultra_workspace_id` в `%LOCALAPPDATA%` хуже:
  - две копии с одинаковым ID мешали бы друг другу;
  - запись с другого компьютера по сети не была бы защищена.
- Блокировку берут только писатели (этап 2 и далее). Читатели её не берут и Tk не тормозят.

### 5.2. Что держится под блокировкой

- **Что под блокировкой.** Каждая публичная функция записи ядра держит блокировку на время «прочитать → проверить → записать», обычно миллисекунды. Это:
  - создание и переименование Chat;
  - фиксация RAW;
  - запись Turn и ключа;
  - изменения `index.json` Run Store;
  - состояние контекста сообщения;
  - `workspace.json`;
  - Project Context.
- **Чего под блокировкой нет.** Блокировка **никогда** не держится во время сетевого запроса или ожидания пользователя. Подтверждено: в Tk `_worker` есть ожидание разрешения `ready.wait()` без срока.
- **Повторный вход.** Примитив не реентерабелен: новый дескриптор в том же процессе ждёт, P10 — между потоками.
  - Поэтому блокировку берут только внешние функции.
  - Внутренние вызовы (`create_chat` → `ensure_workspace_storage` → `list_chats`) используют варианты без блокировки.
  - Отдельный тест подтверждает, что вложенный вызов не зависает.
- **Таймаут.** По истечении (по умолчанию 10 с) пользователь видит ошибку «Workspace занят другой операцией». Тихих бесконечных повторов нет.

### 5.3. Замена файла при открытом читателе (ограничение платформы)

Подтверждено на этом Windows 10 19045 (P11, P12):

- любой открытый дескриптор файла, **даже открытый с FILE_SHARE_DELETE**, делает `os.replace` на этот файл невозможным (`PermissionError`);
- `context_storage._atomic_write_text` повторной попытки не делает. Исходный файл при этом остаётся целым, временный удаляется (0 остатков);
- после закрытия читателя та же запись проходит;
- Run Store уже повторяет замену (`_replace_with_retry`) и имеет запасной путь generations (TASK 143–146, №03 §4).

Под это попадают только **заменяемые** файлы:

- `metadata.json` чата;
- `workspace.json`;
- `project_context.md`;
- `message_context/<id>/state.json`;
- `index.json` и `summary.json` аудита.

Новые RAW создаются под новыми именами, и открытые читатели других файлов им не мешают.

**Решение.**

- (а) Веб-читатель открывает файл, читает ограниченное число байт целиком и сразу закрывает. Дескрипторы не держатся между запросами и во время ожиданий.
- (б) На этапе 2 `_atomic_write_text` получает ограниченный повтор замены, как в Run Store. После исчерпания попыток — видимая ошибка без потери данных.
- (в) На этапе 1 обязателен тест: запись Tk во время чтения истории веб-сервером не теряет данные, а возможный отказ виден.
- Внешние программы (антивирус, Remote Desktop Commander из TASK 145) создают ту же ситуацию. Это ограничение платформы, а не дефект Chat.

### 5.4. Общий индекс Run Store

**Подтверждено (P9, 5 из 5 запусков).** Два процесса одновременно создают по 40 RUN в одном Workspace через `ensure_run_index_entry`:

- из 80 записей сохраняются 40;
- второй процесс падает с `KeyError` (`run_store.py:185`): задача, которую он только что записал, затёрта индексом другого процесса.

Причина — чтение, изменение и запись `index.json` без блокировки (`run_store.py:148–188`). Сегодня это скрыто тем, что пишет только один процесс Tk.

**Решение.** Пока индекс пишет только Tk, веб его только читает. До появления любого второго писателя (этап 2 или 3) все изменения индекса выполняются под блокировкой Workspace.

### 5.5. Этап 1

Веб не пишет в папку Workspace **ничего**. Блокировка этапу 1 не нужна. Нужны безопасный читатель (§7) и правило 5.3(а).

## 6. Turn: порядок фиксации и восстановление (этап 3; контракт фиксируется сейчас)

### 6.1. Повторная отправка

- **Повтор тем же ключом.** Тот же `client_request_id` с тем же `request_hash` возвращает тот же Turn (`replayed: true`). Другой `request_hash` → 409 `idempotency_conflict`. Одинаковый текст с новым ключом — новый, намеренный Turn.
- **Двойное нажатие.** В одной вкладке нажатие передаёт тот же ключ, поэтому получается один Turn. В двух вкладках или двух оболочках ключи разные, получаются два намеренных запроса.
- **Один активный Turn на Workspace.** Начальная граница: в Workspace одновременно не больше одного Turn в состоянии `SENDING` (№37 §2.3). Второй запрос получает 409 `workspace_busy` **до** приёма, его RAW не записывается. Очереди в первой версии нет — меньше состояний.
- **Снимок.** Снимок модели, контекста и политики фиксируется при приёме. Перед физической отправкой разрешения и политика проверяются заново. Если разрешение отозвано, Turn получает FAILED `policy_revoked` без отправки.

### 6.2. Порядок фиксации

1. Проверки HTTP, ID, размера и выбора модели. Ничего не пишется.
2. Под блокировкой ищется ключ. Если он есть, это повтор или конфликт (§6.1). Если в Workspace уже есть Turn в `SENDING`, ответ 409.
3. Под блокировкой: резервирование ключа (с `turn_id`, U, A и `request_hash`) → Turn в состоянии `ACCEPTED` → эксклюзивная фиксация user RAW U. Ответ «принято» отправляется **только после** этого.
4. Перед сетью (на этапе 6 здесь резерв B2 S3a и проверка S3b): под блокировкой Turn → `SENDING`, фиксируется начало попытки. Пока идёт вызов, держится «замок попытки» `turns/<turn_id>.inflight.lock`. Это признак живого исполнителя: замок освобождается, когда процесс умирает (P10).
5. Ответ провайдера: под блокировкой эксклюзивно фиксируется assistant RAW A, затем Turn → `COMPLETED` с учётом расхода. При ошибке провайдера Turn → `FAILED`, RAW A не пишется.
6. Отмена до шага 4 → `CANCELLED`. После шага 4 → флаг `cancel_requested`, итог фиксируется по факту.

### 6.3. Восстановление

| Что на диске после сбоя | Как классифицируется | Что происходит |
|---|---|---|
| Ключ есть, Turn нет | незавершённый приём | Повтор тем же ключом и текстом пересоздаёт Turn из резервирования. Без повтора ничего не видно, данных нет |
| Turn `ACCEPTED`, нет RAW U | приём не завершён | Повтор тем же ключом и текстом (хеш сверяется) дописывает U. После перезапуска без повтора: FAILED `local_commit_incomplete`. Отправки не было |
| Turn `ACCEPTED`, RAW U есть | принято, не отправлено | Автоматической платной отправки после перезапуска нет. Пользователь видит «не отправлено: отправить / отменить» |
| Turn `SENDING`, замок попытки свободен, RAW A нет | UNKNOWN | Без автоматического повтора. Новая отправка — только явным действием и с учётом прежних обязательств B2 |
| Turn `SENDING`, RAW A есть | COMPLETED | Результат уже сохранён, Turn дописывается |
| Turn `SENDING`, замок попытки занят | ещё выполняется в другом процессе | Только показ состояния |

Восстановление выполняется только под блокировкой Workspace и затрагивает только Turn, чей замок попытки удаётся взять. Ошибка обязательной фиксации всегда видна. Её нельзя оставлять только в диагностическом обработчике: подтверждено, `AuditThreadRecorder._persist_event` (`audit_storage.py:325`) кладёт ошибку сводки в поле `audit_summary_error`, а не прерывает работу.

**Не обещается:** однократное исполнение запроса провайдером. Защита от локальных дублей не доказывает внешний exactly-once (№37 этап 3).

## 7. Безопасное чтение истории (этап 1)

### 7.1. Граница HTTP

Подтверждено:

- Сервер слушает только loopback (`create_server`).
- Общий API Web Alarm (`WebAlarmApi.dispatch`) не проверяет `Host`, `Origin` и `Sec-Fetch-Site`.
- Строгая проверка есть только у folder picker (`web_alarm/server.py:1125`): точный `Host` из `127.0.0.1:<port>` / `localhost:<port>`, `Origin` и `Sec-Fetch-Site`, токен возможности в заголовке, сравнение через `compare_digest`.
- Без проверки `Host` страница чужого сайта, чьё имя переназначено на 127.0.0.1 (DNS rebinding), может читать ответы. Для приватной истории это недопустимо.

**Решение для всех маршрутов `/ultra/chat/*`:**

1. **Хост.** Ровно один заголовок `Host` из `{127.0.0.1:<port>, localhost:<port>}`; собеседник и адрес привязки — loopback.
2. **Происхождение запроса.** `Origin`, если он есть, равен `http://<Host>`. `Sec-Fetch-Site`, если он есть, — `same-origin` или `none`.
3. **Токен.** Обязательный токен возможности в заголовке, **в том числе для GET**. Токен выдаётся через тот же защищённый `/ui/capabilities`. Проверки переиспользуются: из `_folder_picker_request` выделяется общий помощник, а не пишется второй вариант.
4. **Метод и параметры.** На этапе 1 только GET, прочие методы — 405. Параметры запроса — только проверенные `before` и `limit`.
5. **Текст ошибок.** В ошибках нет путей и текста исключений. Подтверждено: исключения `context_storage` содержат абсолютные пути (например, `_read_json_object`, `context_storage.py:91`). Веб-адаптер переводит их в фиксированные коды.
6. **Ответ.** `Cache-Control: no-store` (уже есть в `_send_json`), только JSON.
7. **Модель угроз.** Другая программа того же пользователя может читать файлы `.ultra` напрямую. Она вне модели угроз, и это записывается как ограничение.

### 7.2. Идентичность и границы путей

1. **Только ID из браузера.** Из браузера приходят только `wa_workspace_id`, `chat_id` и курсор. Путей нет. Каждый ID проверяется регулярным выражением **до** соединения с путём.
2. **Корень.** Корень берётся из реестра Web Alarm. При каждом запросе он должен существовать и быть каталогом, затем выполняется `probe_existing_workspace`.
3. **Ссылки внутри `.ultra`.** `.ultra`, `.ultra/chats`, `<chat_id>` и `messages` должны быть обычными каталогами, а не reparse point (junction, symlink, точка монтирования).
   - Проверка: `os.lstat`, затем `st_file_attributes & FILE_ATTRIBUTE_REPARSE_POINT` на Windows или `S_ISLNK` на POSIX.
   - Такое звено → состояние `unsafe_storage_link`, данные не читаются.
   - Подтверждено: сейчас читатель следует по junction в чат другого Workspace (P6). Путь «по ID» останавливает это только косвенно — из-за несовпадения `workspace_id`.
   - Сама папка Workspace может быть подключена через junction или `subst` по выбору пользователя. Правило касается только звеньев внутри `.ultra`.
4. **Файл сообщения.** Это обычный файл, не reparse point. Имя соответствует `^msg_[A-Za-z0-9_-]{16,128}\.json$`, ID в содержимом равен имени.

### 7.3. Ограничения объёма

Числа — предложение, их утверждает координатор. Для сравнения: по аудиту TASK 147 (№03) во всех проверенных реальных Workspace было 158 RAW, а основной рабочий чат содержал 26 сообщений.

| Ограничение | Значение | Поведение при превышении |
|---|---|---|
| Записей каталога `chats` за запрос | 2 000 | `chats_listing_too_large`, список не выдаётся частично под видом полного |
| Чатов в ответе | 500 | то же |
| Файлов `messages/*.json` в одном чате | 2 000 | `history_too_large` с числами; без молчаливой обрезки |
| Сумма размеров файлов чата по `stat` (до чтения) | 64 МиБ | то же |
| Один файл RAW | 4 МиБ (лимит записи 2 МиБ плюс запас на экранирование JSON); читается `read(лимит + 1)` | элемент `too_large`, содержимое не выдаётся |
| Сообщений в странице ответа | по умолчанию 50, максимум 200 | курсор `before` для более ранних |
| Тело ответа | 8 МиБ | элемент `too_large_for_page` с размером; страница не режется посередине текста |

Объём чтения ограничивается **до** чтения: сначала перечень имён и `stat`, затем чтение не больше лимитов. Только после этого история сортируется по `created_at` и `message_id` и выдаётся страница. Это честно ограниченное чтение, а не «прочитать всё и обрезать» (№37 этап 1).

Если файл растёт между `stat` и чтением, его держит предел `read(лимит + 1)`. На этапе 2 для настоящего постраничного чтения без полного перечня добавляется упорядоченный индекс сообщений чата.

### 7.4. Повреждённые, повторяющиеся и старые записи

| Случай | Поведение |
|---|---|
| Повреждена metadata чата | Чат в списке как `damaged` (ID из имени папки, без названия). Остальные чаты не страдают |
| Чат другого Workspace (`workspace_id` не совпал) | `foreign_identity`, не показывается, учитывается в счётчике |
| Повреждён JSON сообщения или нет `original_text` | Не выдаётся. Счётчик `damaged` и список ID; история помечена как `partial` |
| Имя файла не равно `message_id` | Запись недействительна (`name_mismatch`). Именно это правило делает дубликаты невозможными: в одном каталоге имена уникальны |
| Чужие `chat_id` или `workspace_id` в сообщении | `foreign_identity`, исключается |
| `schema_version` новее поддерживаемой | `unsupported_version`, история `partial` |
| Нет `producer` или `task_block_id` | Допустимо (старые записи) |
| Роли `system` / `tool` | Показываются свёрнутыми или скрываются, в контекст не идут |

Ответ различает состояния истории: `complete`, `partial` (с числами по причинам), `unavailable` (с кодом причины) и `empty`. Частичная или недоступная история **видимо** отличается от пустого чата.

### 7.5. История для отображения и история для модели

- **Отображение (этап 1).** Маршрут отдаёт только RAW `original_text` с метками исхода §4. Варианты контекста и сводки он не отдаёт и для сборки запроса к модели не используется.
- **Контекст модели (этап 4).** Отдельная функция, закрытая при любой ошибке, работает по полной цепочке идентичности и с рабочим представлением (`load_chat_working_messages` или её исправленный преемник). Неуспешные исходы она исключает (§4).
- Нужен тест, что сборка запроса не вызывает читатель отображения.
- **Безопасность HTML.** Весь текст выводится только через `textContent`, `innerHTML` не используется (как в EVM). Тест проверяет текст, содержащий теги, `<script>` и обработчики событий.

## 8. Модель и выбор подключения

Этап 1 только показывает выбранную модель через существующий `GET /ultra/connections/selection?role=chat` (EVM). Новых записей нет. Повреждённый, недействительный или отсутствующий выбор показывается состояниями EVM: `CORRUPT`, `INVALID_REFERENCE`, `NOT_SELECTED`, `REGISTRY_UNAVAILABLE`. Снимок выбора в Turn — этап 3.

## 9. Чего контракт не обещает

- Однократного исполнения запроса провайдером и нулевой стоимости после отмены.
- Защиты от других программ того же пользователя, которые читают `.ultra` напрямую.
- Того, что на POSIX файлы ведут себя как на Windows. Правила 5.3 проверены только на Windows 10 19045.
- Порядка отображения по времени изменения файлов: оно ненадёжно после копирования. Порядок задают `created_at` и `message_id`.
