## Реализация

`web_alarm/turn_service.py` подключает S4A через явный Python параметр `offline_adapter`. Новый `web_alarm/ordinary_chat_test_adapter.py` содержит fixture adapter с транспортом, который возвращает данные из памяти. Третьим изменённым исходником является новый `test_web_alarm_ultra_chat_turn_s4b.py`. READ-ONLY модули, Stage 3 тесты, HTTP/Tk/UI и launcher остались по исходным SHA в проверяемом наборе. Обычный `UltraChatService` создаёт `TurnService` без адаптера.

S4B требует экземпляр конкретного fixture adapter, непустой явный allowlist потомков временной папки и `config_ref=s4b-offline:v1`. Caller задаёт синтетический контекст, его ссылку, лимиты, fake-ответ и явный `model_ref`. Адаптер является доверенным Python fixture. Тип адаптера и TEMP guard ограничивают штатный вход, а сетевую изоляцию испытаний отдельно обеспечивает ранний guard. `capability()` продолжает описывать прежний Stage 3 TEST. Для схемы 1 сохранены `REFERENCES`, `ANSWER`, producer и формат view, а для схемы 2 используются собственные проверяемые поля.

На приёме S4A `prepare_request()` разрешает registry model и валидирует контекст. Turn сохраняет в существующем summary снимок модели, контекста, лимитов и request_ref. Текущий user text хранится в user RAW. Принятые идентичности, исходный body digest и снимок связаны SHA-256. Версия Turn равна 2, схема самого Run Store и формат RAW прежние. Заново открытый READY восстанавливает принятый снимок, в том числе после смены настроек fixture. S4A перед вызовом ещё раз проверяет request binding и registry. Отзыв модели приводит к отказу без замены.

Под тем же workspace writer lock фиксируются READY RAW, ATTEMPTING и `turn_started`. Run Store синхронизирует запись и индекс, проверяет их readback. Вызов `execute_request()` с fixture transport происходит после этого и за пределами writer lock. При завершении Turn повторно проверяет RAW, RUN, принятый binding и начало попытки под lock. Единственный SERVER terminal record содержит attempt ID, request reference, accepted binding, outcome, execution и известный usage. Fake usage остаётся в событии Turn и не попадает в учёт реальных provider calls или бюджета.

Успех требует совпадения проверенного `turn_result` и неизменяемого assistant RAW. Отказ fixture до вызова и некорректный ответ дают FAILED с разными outcome/execution. Исключение и timeout после входа дают UNKNOWN. Missing, partial, invalid и явно предоставленный usage различаются. Отмена READY сохраняется без попытки. Поздний ответ после сохранённой отмены даёт discard с доступным usage. Если результат уже устойчиво записан к моменту запроса отмены, Turn сначала завершает его публикацию. Это порядок событий под существующей блокировкой.

GET только проверяет и читает. Явный повтор исходного ключа может восстановить незавершённую запись Run Store, завершить прерванное принятие user RAW или опубликовать подтверждённый ранее результат. При ATTEMPTING без владельца и результата возвращается UNKNOWN, включая случай завершения процесса внутри fake send. Новый вызов fake для такого Turn не выполняется. READY ещё не имеет начатой попытки и допускает исполнение на явном повторе. При одинаковом ключе и другом теле возвращается conflict.

## OPEN и следующий шаг

- Исторический `WorkspaceBusyError` остаётся UNKNOWN / OPEN. Его точный concurrency selector и полный Ultra suite в этой задаче **NOT RUN**. Результаты прежних диагностик сохраняются.
- S4B хранит синтетический контекст в summary только для явно разрешённой offline схемы. Для будущего пользовательского подключения нужно отдельно утвердить владельца и форму проекции контекста, перенос usage в учёт и B2. SHA binding выявляет расхождения между сохранёнными фактами. Он не служит подписью против согласованной подделки всех файлов Workspace.
- Синхронный Python вход запускает S4A через asyncio.run. Проверена текущая Windows среда. Чистый Windows перенос, другая ОС, CI, Tkinter, браузер и внешний adapter **NOT RUN**.
- NEXT — независимая приёмка S4B по HISTORY ID после одного коммита пользователя. Для Stage 4 в целом, UI/Tk подключения, STANDARD sending и real/paid provider требуется отдельное решение.
