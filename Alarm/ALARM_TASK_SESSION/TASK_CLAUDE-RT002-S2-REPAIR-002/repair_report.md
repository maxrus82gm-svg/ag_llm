## 2. F1 — повреждённый scope_id

### 2.1 Воспроизведение (исходный модуль `d08ce81d…`, scratch-скрипт, без runtime)

Базовая запись: settled executor-попытка в `run` со 200 000 известных токенов. Корректная запись → committed 200 000 → следующий executor-запрос DENY.

| `scope_id` записи | Проверяемый scope `run` | Проверяемый scope `compress-job` |
| --- | --- | --- |
| `None`, `""`, `"   "`, `[]`, `{}`, `("run",)`, `0`, `"run\ud800"`, `"x"*201` | anomalies 0, committed 0 → **ALLOW** | anomalies 0, committed 0 → **ALLOW** |

То же для контекста запроса с корректной тяжёлой историей:
- `RunContext(None | [] | "", …)` → ALLOW, committed 0;
- `final_audit_enabled = None` или `0` → ALLOW с резервом 0 (защита снята молча);
- `"false"` → резерв 48 000.

**Root cause.** В `budget_view` строка `if record.scope_id != scope_id: continue` стояла раньше `_record_problem`, а `_record_problem` scope вообще не проверял. Контекст запроса не валидировался.

### 2.2 Правило

- **Идентичность scope** — непустая строка до 200 символов, кодируемая в UTF-8. Это тот же стандарт, что у остальных идентификаторов (`_text_problem`).
- **Принадлежность решается до пропуска.** Запись с корректным чужим `scope_id` изолирована. Запись с некорректным `scope_id` может быть нашей: она попадает в аномалии **каждого** проверяемого scope с читаемым резервом, отсюда `LEDGER_ANOMALY` и NO_NEW_SENDS. Тихой потери и ALLOW нет.
- Запись с корректным `scope_id`, но повреждёнными прочими полями блокирует только **свой** scope: владелец известен.
- `_record_problem` теперь проверяет и `scope_id`.
- Некорректный запрошенный scope в `budget_view` → аномалия: иначе пустой результат выглядел бы как доступный бюджет.
- `evaluate_request`: проверка `RunContext` (тип, scope, строгий `bool` у `final_audit_enabled`) после проверки measure → DENY `INVALID_CONTEXT`. `preflight_run` при некорректном контексте возвращает `INVALID_CONTEXT`.

### 2.3 Почему так

| Вариант | Решение |
| --- | --- |
| Пропускать повреждённую запись (как было) | Отвергнут: тихая потеря обязательства и ALLOW |
| Блокировать только текущий scope | Отвергнут: принадлежность неизвестна — запись может относиться к любому scope |
| Объединить бюджеты scope | Отвергнут: ломает законную изоляцию (постановка этого не требует) |
| **Блокировать каждый scope до восстановления** | Принят: fail-closed без слияния бюджетов. Цена — запись ложно блокирует и чужие scope до восстановления. Снять блок можно только через reconciliation в S3a (USER DECISION U-2) |

## 3. F2 — численная устойчивость оценки

### 3.1 Воспроизведение (исходный модуль)

| bytes_per_token | 1 B | 4000 B | 1 GiB | evaluate_request |
| --- | --- | --- | --- | --- |
| 5e-324 (минимальный subnormal) | OverflowError | OverflowError | OverflowError | **OverflowError** |
| 2.2250738585072014e-308 (минимальный нормальный) | 308 цифр | OverflowError | OverflowError | **OverflowError** |
| 1e-300 | 300 цифр | 304 цифры | OverflowError | DENY |
| 1e-12, 0.0001 | — | — | — | DENY |
| 1.0, 64.0 | — | — | — | ALLOW |

**Соседнее:** проверено 9 делителей на диапазоне 1…400 000 B. Float-потолок занижает оценку на 1 токен уже на реальном профиле executor 4.1076 (10 269 B → 2500, точно 2501), а также на 4.1 (41 B), 3.3 (33 B), 0.7 (7 B).

**Root cause.** Оценка вычислялась как `math.ceil(wire_bytes / bpt)`: при крошечном делителе частное становится бесконечностью, а округление float-частного может уйти вниз до ближайшего целого.

### 3.2 Решение (уровень, на котором отклонять)

- **Оценка — точная.** `numerator, denominator = bpt.as_integer_ratio()`, затем `tokens = ceil(wire_bytes * denominator / numerator)` в целых числах. Результат — математический потолок для хранимого значения делителя:
  - никогда не меньше точного частного;
  - не переполняется при любом положительном делителе: для 5e-324 и 1 GiB получается число около 10^332 цифр, и это обычный DENY `REQUEST_TOKENS_EXCEEDED`.
- **Валидация не меняется:** допустимы положительные конечные значения ≤ 64. Числовой «пол» был бы новым производственным лимитом, которого пользователь не утверждал (запрет постановки). Профиль с крошечным делителем безопасен: он только переоценивает.
- **Согласованная комбинация:**
  - `preflight_run` предупреждает `PROFILE_STRICTER_THAN_HARD_BOUND`, если делитель < 1: оценка выше грубой границы «токены ≤ байты», вероятно перепутаны единицы (токен/байт);
  - сообщения сокращают астрономические числа (`~10^N`), чтобы не выводить 330 цифр;
  - профиль, собранный вручную (0, отрицательный, NaN, inf, строка, None, bool), → `PolicyInputError` (только `validate_policy` строит корректный snapshot).
- HARD_BOUND и NEEDS_CALIBRATION не изменились. Калиброванные профили работают как прежде; точная арифметика меняет их оценки не более чем на +1 токен. Точки остановки A/B/C и все наблюдения S2 совпали.

### 3.3 Исправленный оракул прежнего теста (с первым FAIL)

`test_request_byte_and_token_caps_with_exact_boundaries` (S2) вычислял границу как `floor(20000 * 4.1076)` во float = 82 152. Хранимый делитель равен 4.10759999999999969…, поэтому точная граница — **82 151**: при 82 152 точная оценка 20 001 > 20 000.

- Прежний движок на 82 152 возвращал ALLOW, и прежний тест это закреплял. Это превышение лимита на 1 токен, а не корректное поведение.
- После исправления тест упал (лог `b3cbbc66…`).
- Оракул переведён на `Fraction`, граница проверяется точно: 82 151 → ALLOW, **82 152 (+1)** → REQUEST_TOKENS_EXCEEDED. Прежний вариант проверял +5 байт; новый строже.

- **R-2.** Идентичность scope ограничена 200 символами и UTF-8. Если S3b/S3a выберут более длинные id — это решение контракта.
- **R-3.** Строгий `bool` для `final_audit_enabled` — S3b обязан передавать именно `bool`.
- **R-4.** Подкласс `str` с переопределённым `__eq__` в `scope_id` не отсекается. Это вне JSON-контракта, S3a восстанавливает обычные строки.
- **R-5.** Профили с делителем < 1 разрешены (безопасны, но бессмысленны); только предупреждение.
- **R-1 из REPAIR-001** (тот же outcome без usage после KNOWN → ANOMALY) остаётся на решение verifier.

## 7. FINDINGS / PROPOSALS

- **S3a.** Записи восстанавливаются как есть. Повреждённый `scope_id` → блок всех scope. Нужна явная reconciliation/quarantine-процедура с решением пользователя, чтобы снять блок без потери обязательства.
- **S3b.** Передавать `RunContext` со строковым scope и строгим `bool`. Использовать только снимки из `validate_policy`. `PolicyInputError` и DENY означают «не отправлять».
