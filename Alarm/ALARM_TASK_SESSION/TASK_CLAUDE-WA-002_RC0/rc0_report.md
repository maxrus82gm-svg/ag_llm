## 2. BYTE / HASH / LINE-ENDING POLICY

**Текущая реальность (read-only, `git ls-files --eol`):**
- `core.autocrlf=true` — и в системном (`C:/Program Files/Git/etc/gitconfig`), и в пользовательском `~/.gitconfig`;
- `core.eol`, `core.safecrlf`, `core.attributesFile` не заданы; `.gitattributes` и `.git/info/attributes` отсутствуют;
- **индекс:** все текстовые файлы хранятся с LF (`i/lf` — 766), CRLF в индексе нет;
- **рабочее дерево:** 711 файлов LF, **46 CRLF**, **9 смешанных**, 11 пустых, 1 бинарный.
  - CRLF среди прочих: `server.py`, `ultra_ui.py`, `Start_Ultra.cmd`, `.gitignore`, 30 файлов в `Alarm/` (manifest и снимки), 2 файла плагина в `.obsidian/`.
  - Смешанные — среди прочих: `000_Задачи Claude.md` (2026-10-03 был чистым LF; его правили инструменты с разными соглашениями), `07_Шаблоны…`, 6 тестов вне Web Alarm.
- Предупреждения `LF will be replaced by CRLF the next time Git touches it` воспроизводятся на изменённых файлах с LF при `git diff`.

**Измеренное следствие.** В ручных manifest `Alarm/ALARM_TASK_SESSION/*/manifest*.json` — **121 запись снимка**:
- 115 сходятся с байтами рабочего дерева;
- **после свежего checkout при текущей конфигурации сойдётся только 1** — у 114 SHA-256 сломается, потому что git запишет CRLF;
- **6 записей** ссылаются на уже удалённые файлы снимков.

Хранилище самого WEB-02 лежит вне git и этим не затронуто. Но целевые файлы WEB-02 находятся в репозитории, и любое `git checkout`, `pull`, `stash` или `reset` переписывает их байты.

**Код WEB-02 уже работает с байтами:** снимки и restore — `read_bytes` / `_atomic_write_bytes`, сверка — `read_bytes`, свои JSON-записи — UTF-8 с явным `\n`.

**Policy (рекомендуемая, однозначная):**
1. **Authority — только физические байты.** Доказательство состояния файла — SHA-256 (hex, нижний регистр) по точным байтам на диске плюс размер. Чтение и запись целевых файлов — только в бинарном режиме, без какой-либо трансляции переводов строк.
2. **Git — отдельный слой, не доказательство.** Blob-хеши git, содержимое индекса и нормализация (`autocrlf`, атрибуты) не используются как доказательство в решениях WEB-02. Операции git, переписывающие отслеживаемые файлы, — это **внешний писатель** (как Obsidian): после них возможен drift, автоматического ADOPT нет.
3. **Нормализованное сравнение — только диагностика.** Если байты различаются, но совпадают после приведения CRLF/LF (и снятия BOM), сверка может пометить это как отдельный диагностический признак (`EOL_ONLY_DRIFT`). Он ведёт к MANUAL_REVIEW, а не к ADOPT или RETRY. Сама эта классификация — предложение для RC-1/RC-2; контракты сейчас не меняются.
4. **Ожидаемый post-state (RC-1) — хеш ровно тех байтов, которые будут записаны;** writer обязан писать их как есть.
5. **Диагностические метаданные** (рекомендация для контракта RC-1): стиль переводов строк (`lf` / `crlf` / `mixed` / `none`) и наличие BOM для pre / post. Это не authority.
6. **Свои записи WEB-02:** UTF-8 без BOM, LF — уже так.

## 3. .GITATTRIBUTES RECOMMENDATION

**Не создан и не изменён.** Ниже — точное предложение для отдельного `DECISION / FOLLOW-UP`.

**Цель:** байты рабочего дерева не должны зависеть от `autocrlf` конкретной машины и от истории checkout, а байтовые доказательства в `Alarm/` не должны ломаться при клонировании.

```gitattributes
# Текстовые файлы: LF в индексе и в рабочем дереве на любой машине (перекрывает core.autocrlf)
* text=auto eol=lf
# Windows-скрипты требуют CRLF
*.cmd text eol=crlf
*.bat text eol=crlf
# Байтовые доказательства (snapshot/manifest с SHA-256): никакой конверсии
Alarm/** -text
# Бинарные форматы
*.png binary
*.jpg binary
*.jpeg binary
*.gif binary
*.ico binary
*.pdf binary
*.docx binary
*.xlsx binary
*.zip binary
*.bin binary
```

**Ожидаемое влияние** (оценка по `git ls-files --eol`):
- **Индекс вне `Alarm/`** уже целиком LF, поэтому `git add --renormalize .` его содержимое не меняет.
- **Индекс `Alarm/`:** при `-text` renormalize запишет в индекс байты рабочего дерева как есть. Это 30 файлов с CRLF и 1 смешанный. Среди них 2 снимка, чей SHA-256 записан по CRLF-байтам, а в индексе они сейчас нормализованы в LF — так они и починятся.
- **Рабочее дерево:** при одноразовом пересоздании (только на чистом дереве, отдельным коммитом) вне `Alarm/` **15 файлов с CRLF и 8 смешанных станут LF**. Среди них `server.py`, `ultra_ui.py`, `.gitignore`, `15_Глобальный контекст Ultra.md`, `000_Задачи Claude.md`, `07_Шаблоны…`, 7 тестов вне Web Alarm и 6 копий в `Dev-archive/snapshots/`. `Start_Ultra.cmd` останется CRLF. Файлы `Alarm/` сохранят байты.
- **Ручные manifest в `Alarm/`** перестанут ломаться при клонировании: 113 записей совпадают с LF-индексом, 2 чинятся renormalize — итого все 115 сохранившихся.
- **Вариант:** добавить `Dev-archive/** -text`. Там тоже лежат байтовые копии старого кода (`Dev-archive/snapshots/`), и при `eol=lf` их байты изменятся.
- Атрибуты **не мешают** инструментам писать CRLF в рабочее дерево (PowerShell `Set-Content`, разные редакторы). Поэтому policy п. 1–3 нужна в любом случае: атрибуты убирают только дрейф, вызванный git.

**Альтернатива минимального риска:** только `Alarm/** -text` и `*.cmd eol=crlf`. Она защищает байтовые доказательства без переписывания рабочего дерева, но оставляет зависимость остальных файлов от `autocrlf`.

**Выбор между вариантами и время применения (чистое дерево, отдельный коммит, перезапуск процессов) — решение пользователя.**

## 6. SNAPSHOT / SECRET / RETENTION CONSTRAINTS

Требования к следующим этапам; payload-хранилище RC-1 наследует их полностью.

**Текущая реальность:**
- WEB-02 хранит снимки вне репозитория: `%LOCALAPPDATA%`, папка пользователя.
- Чувствительных по имени файлов в снимках и в отслеживаемых файлах нет.
- `.gitignore` исключает `.env` и `.env.*`.
- 133 файла снимков ручных сессий `Alarm/` отслеживаются git и уходят на `origin` (GitHub).
- Лимита размера нет.
- Отдельно: локальный журнал Desktop Commander (`tool-history.jsonl`, 3,6 МБ) хранит аргументы и вывод Remote-вызовов, включая содержимое файлов. Это поверхность утечки вне контроля WEB-02.

**Ограничения:**
1. **Scope.** Снимок только для target внутри зарегистрированного workspace и объявленного scope. Список запретов по умолчанию: `.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `*credential*`, `*secret*`, `*token*`, `cookies*` и правила секретов из `.gitignore`. Совпадение → prepare fail-closed с причиной; исключение — только явным разрешением на конкретный target, записанным в контракт операции.
2. **Место.** Снимки и payload — только в машинном хранилище WEB-02 вне репозитория и vault. Новые ручные снимки непубличных файлов в `Alarm/` не создавать, потому что они уходят на GitHub. `Alarm/` считается legacy-доказательством.
3. **Размер.** Явный максимум для снимка и payload (порядка лимита сервера 1 МиБ или настраиваемый); выше лимита — fail-closed; хеш считать потоково.
4. **Retention.**
   - Restore point активных TASK и всех нерешённых операций не удаляются никогда.
   - Restore point завершённых TASK хранятся до явной очистки; в RC-фазах автоматического удаления нет.
   - Размер хранилища показывается в resume / status.
   - Перед очисткой — экспорт.
   - Сама очистка — отслеживаемая операция.
5. **Целостность.** Хеш при записи и проверка при чтении (уже есть для снимков, нужно и для payload).
6. **Логи и отчёты.** Содержимое снимков и payload никогда не пишется в events, отчёты и логи — только пути, хеши, размеры.
