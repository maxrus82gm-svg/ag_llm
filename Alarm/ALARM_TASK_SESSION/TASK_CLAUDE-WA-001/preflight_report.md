## 3. RC-1 READINESS

**Статус:** NOT READY FOR HANDOFF — ожидаемо: нужны PLAN APPROVAL, P00, RC-0. Технически задача реализуема; до выдачи нужно закрыть пробелы спецификации:

1. **Версионирование.** Глобальную `SCHEMA_VERSION` не поднимать: все v1-записи всех 8 хранилищ стали бы нечитаемыми. Нужна отдельная версия контракта операции; читатель принимает v1 (legacy) и v2.
2. **Legacy.** Существует всего 2 терминальные операции, поэтому рекомендую совместимое чтение без перезаписи: v1 помечается `contract_incomplete` и никогда не допускает RETRY. Нужны тесты на замороженных v1 JSON-фикстурах.
3. **Стабильность fingerprint.** Для v1 оставить прежний алгоритм; при изменении материала ввести версию fingerprint. Повтор legacy `operation_id` должен по-прежнему давать `RETURN_KNOWN_STATE`.
4. **Процессы разных версий.** Из-за строгого `**raw` старый код упадёт fail-closed на v2-записях. После обновления нужен перезапуск всех процессов WEB-02 — это нужно записать в критерии rollout RC-1.
5. **Каноническая идентичность target** — нужна уже в RC-1 (RC-1 её хранит, RC-3 применяет). Одна общая функция для `OperationStore`, `ManifestStore`, reconciliation и ключей `expected_post`. Требования:
   - путь относительно workspace, POSIX-разделители, `normpath`;
   - case-fold ключ для сравнения при сохранении отображаемого написания;
   - разрешённые родительские junction;
   - запрет symlink / reparse-point для самого target, ADS (`:`), конечных точек и пробелов, имён устройств.

   Живой прецедент класса — сбой PREGATE в WA-3.7.
6. **Payload.** Content-addressed неизменяемый blob в каталоге TASK, лимит размера явно (сервер сейчас принимает ≤ 1 MiB), проверка хеша при чтении (повреждение → fail-closed). Минимальный набор действий RC-1: create / write / delete; edit и move — явно в рамках или вне рамок.
7. **Зависимость от RC-0:** политика байтов / переводов строк до определения `expected_post_sha256`.
8. **Минимальная приёмка RC-1:**
   - чтение v1-фикстур;
   - round-trip v2;
   - fresh process выполняет reconcile **без** post от вызывающего;
   - legacy-операция не допускает RETRY;
   - стабильность replay;
   - эквивалентность вариантов написания target (регистр / слэш);
   - повреждённый payload → fail-closed;
   - 197 прежних тестов PASS.
9. **Границы RC-1:** не включать resolver, conflict gate, исполнитель. Блокировка — по решению D2.

## 4. BLOCKERS / DECISION REQUIRED

Процессные gate известны и не новы: PLAN APPROVAL → P00 → RC-0 до RC-1. Реальных blockers для самого preflight нет. Решения ниже нужны **до PLAN APPROVAL**; RC-1 они не блокируют, если RC-1 выполнен в описанных границах.

- **D1 — семантика RETRY в RC-2.**
  - (a) RETRY = отслеживаемый «re-arm»: операция с тем же `operation_id` снова допускается к внешнему исполнению, а результат подтверждается наблюдаемым receipt;
  - (b) RETRY откладывается до WA4-E, в RC-2 только ADOPT / ROLLBACK / ABORT.

  (a) раньше даёт пользу, но без CAS на границе записи (до WA4-E) повтор остаётся внешним. (b) проще и строже.
- **D2 — когда вводится межпроцессная сериализация.**
  - (a) глобальная блокировка хранилища + revision переносятся в RC-1 (или отдельный RC-1.5), а в RC-3 остаются conflict gate по target + CAS;
  - (b) остаётся в RC-3 с явным правилом «до RC-3 — один процесс WEB-02 на запись».

  (a) закрывает окно гонок на источнике и немного увеличивает RC-1; (b) оставляет окно и требует дисциплины.
- **D3 — обязательный состав P00.** Явное сопоставление WA-4.1–4.7 из `24` → WA4-E/A/O/R:
  - 4.1 + 4.2 → WA4-E;
  - 4.3 → ОТЛОЖИТЬ по V17, а критерий о двух сессиях переформулировать через сериализацию / CAS;
  - 4.4 + 4.5 → ограничения V13;
  - 4.6 → WA4-O;
  - 4.7 → WA4-R;

  плюс решение, остаётся ли WA-4.6 в `24` отдельным разделом или входит в WA4-O.
