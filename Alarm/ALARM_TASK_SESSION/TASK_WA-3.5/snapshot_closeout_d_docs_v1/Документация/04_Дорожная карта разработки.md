# Дорожная карта разработки GigaChat Ultra Local Agent

Этот документ фиксирует последовательность ближайших этапов развития системы. Дорожная карта разделена на конкретные TASK с критериями приёмки.

## Текущий статус

Система имеет Workspace/Chat, immutable RAW HISTORY, Project Context, активную RAW / SUMMARY Working Representation, Model Registry и назначения MAIN CHAT, COMPRESSOR, PLANNER и VERIFIER через GigaChat transport. После TASK 139 normal Planner-enabled Executor использует task-scoped seed вместо автоматической передачи всей старой Chat history. Этот механизм подтверждён live как работающий по изоляции старого Chat context и дал заметное снижение Executor prompt/token footprint, но последующие live RUN выявили несколько независимых проблем в lifecycle и observability.

На 2026-09-30 стабилизационная серия TASK 144–151 завершена и STABLE BASELINE S1 подтверждён TASK 151 / T-022/R-022. TASK 151A закрыла КТ-1 ACCOUNTING воспроизводимой статистической серией, а TASK 151B закрыла КТ-2 Evidence Freshness с live B1/B2/B3 и negative regression matrix. Текущий следующий этап программы качественного перехода — 151C Compact Final Audit Packet + Task-scoped Git Evidence. RELEVANT PRIOR FACTS и historical memory 152–154 остаются после оптимизационной базы.

### Стабилизационная программа TASK 144–151

Правило серии: **одна TASK — одна зона риска**. Если audit-задача обнаруживает новый defect, он получает отдельную следующую repair TASK; не складывать несколько исправлений в один проход.

Критерий выхода из стабилизации:

- новый Chat создаётся, переключается и переживает restart без смешивания histories;
- RAW / SUMMARY Working Representation и текущая task-scoped policy ведут себя предсказуемо;
- Planner получает только свой bounded Planning Session, Executor — только разрешённый role context;
- WRITE → READ → VERIFY → Final Audit проходит без циклов и лишних повторов;
- tool limit и API request count имеют однозначную семантику и не оставляют обязательную VERIFY за пределами budget;
- Run Store/Audit сохраняет RUN либо явно показывает диагностируемый storage failure без пустых Planner/Audit панелей и каскада UI ошибок;
- один контрольный live RUN проходит полностью на новом уникальном target;
- после этого фиксируется STABLE BASELINE S1 и начинается программа качественного перехода 151A–151J; историческая память 152–154 запускается только после закрытия оптимизационной базы.

Канонический подробный порядок программы, инварианты и контрольные точки находятся в `20_Программа качественного перехода - оптимизация runtime, контекстов и памяти.md`. История доказательств и метрик каждого рубежа ведётся в документе 21.

Краткие контрольные рубежи: КТ-0 S1 → КТ-1 Accounting → КТ-2 Freshness → КТ-3 Compact Audit → КТ-4 Direct Evidence → КТ-5 Factual Final → КТ-6 Context V2 → КТ-7 Optimized Base → КТ-8 Memory → КТ-F final reconciliation.

TASK 139/148 live-подтвердили task-scoped isolation, а T-015/R-015 дал новый post-change SUCCESS с Final Audit PASS и полным role usage. ## Этап 06: Система чатов и управление контекстом

### TASK 06.1 — Модель данных чатов и хранение на диске
**Статус: ГОТОВО**

**Критерии приёмки:**
- Каждый чат имеет собственную директорию с уникальной структурой.
- История сообщений сохраняется на диск в виде отдельных файлов.
- Метаданные чата (имя, даты, ID) хранятся в metadata.json.
- Реализован API для создания, чтения, переименования чатов.
- Проверка: после перезапуска UI отображает сохранённые чаты.

### TASK 06.2 — Навигация по чатам текущего workspace
**Статус: В РАБОТЕ**

**Критерии приёмки:**
- Sidebar или панель со списком чатов текущего workspace.
- Возможность создать новый чат.
- Возможность переключаться между чатами.
- При переключении контекст модели очищается и загружается контекст выбранного чата.
- Реализовано переименование чатов.
- Удаление Chat: НЕ РЕАЛИЗОВАНО.

### TASK 06.3 — Настоящий multi-turn context
**Статус: ГОТОВО КАК CHAT STORAGE / WORKING REPRESENTATION; EXECUTOR POLICY ИЗМЕНЕНА TASK 139**

**Критерии / текущее поведение:**
- Active Chat Context строится из истории выбранного chat_id через активные RAW / SUMMARY представления и сохраняется отдельно от RAW.
- История выбранного Chat остаётся multi-turn storage и доступна UI / compression.
- Normal Planner-enabled Executor после TASK 139 не получает всю историю автоматически: его model request task-scoped. Legacy direct caller с `planner_enabled=False` сохраняет прежний full-history compatibility path.
- Следующий этап должен возвращать нужный прошлый опыт через bounded RELEVANT PRIOR FACTS, а не через безусловную передачу всей истории.

### TASK 06.4 — Разделение raw history и active model context
**Статус: ГОТОВО**

**Результат:** immutable RAW, persistent Context Variants, активная RAW / SUMMARY Working Representation и первый role-specific Executor context compilation V1. Автоматический context-budget manager и релевантный retrieval прошлых фактов остаются отдельным будущим развитием.

### TASK 06.5 — Управляемое сжатие контекста
**Статус: В РАБОТЕ**

**Зависит от:** 06.4 + MM.4

**Реализовано:** per-message LLM compression от immutable RAW, один отдельный вызов Compressor, prompt blocks с optional Final Check внутри prompt, soft guard и не более одного corrective retry. Proposal показывается пользователю; Accept / Reject / ручная правка, RAW / SUMMARY, Original Viewer, Restore и persistence работают.

**Остаётся:** Compression Review / Discussion Chat, автоматический context-budget manager и три независимых вызова COMPRESS → VERIFY → FINALIZE. Последняя схема является целевой, а не текущим production pipeline.

## Ветка MM: Мультимодельная архитектура

Канонический документ: 11_Мультимодельная архитектура и назначение LLM. MM.0–MM.4 реализованы; MM.5+ остаются планом.

### MM.0 — Архитектурное решение мультимодельности
**Статус: ГОТОВО**

**Результат:** зафиксирована целевая цепочка `Agent Runtime → Model Assignment → Model Registry → Provider Adapter → Model`.

### MM.1 — MODEL REGISTRY
**Статус: ГОТОВО**
**Зависит от:** MM.0

Единый реестр доступных моделей и базовая расширяемая модель данных.

### MM.2 — GigaChat Multi-Model
**Статус: ГОТОВО**
**Зависит от:** MM.1

Несколько моделей доступны через работающий GigaChat transport.

### MM.3 — MAIN CHAT MODEL ASSIGNMENT
**Статус: ГОТОВО**
**Зависит от:** MM.2

Выбор модели основного Chat Agent реализован. Persistent per-Chat override остаётся MM.6.

### MM.4 — COMPRESSION MODEL ASSIGNMENT
**Статус: ГОТОВО**
**Зависит от:** MM.2

Выбор модели Context Compression через тот же MODEL REGISTRY независимо от MAIN CHAT MODEL.

### MM.5 — LOCAL PROVIDER
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.1, MM.2

Подключение локального inference backend через Provider Adapter. Ollama может быть первым практическим backend, но не является обязательной зависимостью архитектуры.

### MM.6 — PER-CHAT MODEL ASSIGNMENT
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.3

Разные Chat внутри Workspace смогут использовать разные модели без потери собственной истории и контекста.

### MM.7 — AGENT PROFILES
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.1, MM.3

Профиль объединяет `role + model_assignment + role_context + context_policy + tool_set + permission_policy + state + execution_rules`. CONTEXT POLICY остаётся частью запланированного MM.7 и не является реализованной runtime-функцией.

### MM.8 — MULTI-AGENT COORDINATION / COORDINATOR
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.7

Будущий этап координации нескольких Agent; существующим runtime не является.

## Этап 07: Переносимость между компьютерами
**Статус: ЧАСТИЧНО РЕАЛИЗОВАНА**

**Критерии приёмки:**
- Переносимое состояние отделено от локального: `.ultra`, включая Run Store v2 в `.ultra/audit`, — portable; backup и diagnostic logs вне `.ultra/audit` — локальные per-machine.
- Start_Ultra.cmd работает относительно своей директории.
- Автоматическая развёртка .venv/requirements: НЕ РЕАЛИЗОВАНА.

> **Важно:** .venv — это локальное изолированное Python-окружение, НЕ виртуальная машина.
