## 4. Фактическая схема формирования запросов

```
UI: append_raw_message(user) → run_agent_task(planner_enabled, final_audit_enabled, permissions)
 ├─ load_chat_working_messages(chat) → active_chat_messages (вся история, включая RUN STATUS и неудачные попытки)
 ├─ Planner OFF → seed = вся история        [policy "chat_working_history"]
 │   Executor DIRECT: system_core + permission_policy + global_context + project_context
 │                    + вся история + tool_schemas (9–14 по разрешениям), function_call=auto
 ├─ Planner ON  → seed = только текущая задача [policy "task_scoped_v1"]
 │   Planner INITIAL: role context + PLANNER_HARD_PROTOCOL + PLAN_FORMAT (≈ 11,1 KB)
 │                    + {raw_task, permissions, ВСЕ 14 инструментов}
 │   validate_plan(plan, raw_task)  ← разрешения RUN не участвуют
 │   Executor STAGE: те же 4 системных блока + задача + инструкция стадии + инструменты стадии
 │   Planner READINESS: та же сессия заново (stateless) + результат стадии
 └─ FINAL (Dredd ON): _collect_final_audit_evidence
      Planner ON → task_scoped_v1: git status/diff только по путям задачи (без путей — not_applicable)
      Planner OFF → legacy_workspace_compat: git status всего дерева + git diff HEAD -- <READ scope "."> (до 128 KiB каждый)
      json.dumps(indent=2) → user-сообщение verifier (system 2875 символов)
```

## 5. R-033: аномальный Final Audit (C)

**Наблюдение.** R-033 user-блок 62 913 символов / 75 207 B (Dredd 17 331 + 93 токена) против R-034 4 122 / 4 232 B (1 713 + 92). Задача, Planner OFF и разрешения одинаковые. Пакет в RAW не хранится — только хеш и размеры; `verifier_logs` тоже хранят только `verification_context_chars`.

**Первопричина.**
- `_collect_final_audit_evidence` при `task_plan_evidence=None` (Planner OFF) работает в режиме `legacy_workspace_compat`.
- При `allow_read` он выполняет `_agent_git_status(root, audit_policy)` без путей (`--untracked-files=all`) и `_agent_git_diff(root, [], …)`: при READ scope «.» это `git diff HEAD -- .`.
- Оба результата (до `MAX_VERIFY_OUTPUT_BYTES = 128 KiB` на поток) целиком попадают в `fresh_git_status` / `fresh_git_diff` пакета.
- Workspace этого чата — сам репозиторий `ag_llm`.

**Доказательство (OFFLINE, `audit_packet.py`).** Реальные `_collect_final_audit_evidence` и `_build_verifier_messages` получили реальные входы R-033/R-034 (кандидат, разрешения, `verification_state`, счётчики), а git-процесс был подменён синтетическим выводом. Сравнение «чистое дерево» против RAW:

| RUN | RAW system / user (байт) | Реконструкция при чистом дереве |
| --- | --- | --- |
| R-034 | 2875 / 4122 (4232 B) | **2875 / 4122 (4232 B) — совпадает** |
| R-033 | 2875 / 62 913 (75 207 B) | 2875 / 4122 — значит, +58 791 символ / +70 975 B — это вывод git |

Масштабирование (синтетический diff): 8 KiB → 10 030 символов; 56 KiB → 45 616; 128 KiB → 98 970 символов (138 160 B); 200 KiB → то же, diff обрезается на 128 KiB. К этому может добавиться ещё до 128 KiB `git status`. Доля кириллицы в лишних байтах (около 12 тыс. двухбайтовых символов) согласуется с diff русскоязычной документации и кода.

**Почему R-034 дёшев.** На 22:33 дерево было полностью чистым: реконструкция совпадает только при пустых status и diff. R-032 (Planner ON, 21:13) был дёшев по другой причине: режим task-scoped без путей → `not_applicable`.

**Не установлено без Git:** какие именно файлы были изменены в 21:14 (`GIT_DATA_REQUIRED`: коммиты между 2026-10-09 21:14 и 22:33 и `git status` того момента — вопрос координатору). На вывод о механизме это не влияет.

**Связь с B2.** Это ответ на исследовательский пункт **R1 / V-8** («packet delta, причина FOUND либо UNRESOLVED») — **FOUND**.

**Сопутствующие факты:**
- в пакете нет маскирования секретов (маскирование есть только в `_collect_consistency_evidence`);
- Final Audit отправляет git-evidence даже при VERIFY OFF (`audit_policy["allow_verify"] = True`, это задокументированный намеренный выбор);
- для RUN без инструментов и мутаций весь этот материал к задаче не относится.

**Обязательные evidence не удаляются.** В task-scoped режиме сервер передаёт `unattributed_git_status` — сам факт посторонних изменений, а не их содержимое. Предложение §10 сохраняет этот принцип.

## 6. Planner и цена планирования (B)

- **Приветствие при Planner ON = 4 вызова:** INITIAL (≈ 2,7 тыс.), STAGE (≈ 4,4 тыс.), READINESS (≈ 3,0 тыс.), FINAL (≈ 2,2 тыс.). Planner ≈ 5,8 тыс. — дороже самого Executor.
- **Системный промпт Planner** ≈ 11,1 KB (≈ 2,35 тыс. токенов при 4,75 B/ток.) отправляется дважды: сессия stateless, READINESS повторяет INITIAL целиком плюс ответ и результат.
- **INITIAL** обязателен по контракту Planner ON.
- **READINESS** вызывается после **каждой** стадии, кроме repair (`TaskLifecycle.readiness`). Для одностадийного `analysis`/`model_result` без артефактов и evidence он лишь подтверждает текст (`READY_TO_PERSIST` для стадии, где нечего сохранять). При Dredd ON ту же семантику проверяет Final Audit. Это **потенциально избыточно** для тривиальных стадий; при Dredd OFF READINESS остаётся единственной семантической проверкой.
- **PERMISSION и PLANNER_REVIEW** в простых RUN не вызывались. `PLANNER_REVIEW` включается только при Dredd ON после двух неудачных попыток INITIAL.
- **Уровни сложности.** Длина сообщения — плохой признак. В коде уже есть детерминированные сигналы: `_classify_mutation_intent` (сейчас UNKNOWN и для «привет», и для «напиши код» — глагол «напиши» не входит в шаблон), явные пути файлов, отсутствие файловых ссылок, `raw_task_explicitly_forbids_file_mutation`. Их можно использовать для fast-path без Planner или для пропуска READINESS — см. §10 (A3).
- **Гигиена конфигурации.** Активный вариант базового контекста Planner `custom` (`agents/ultra/contexts.json`, 2026-09-27) содержит тестовый маркер «Runtime marker: CONTEXT_RUNTIME_TEST_001»; вариант `default` содержит маркер `…PLANNER_E2E…`. Токенов ничтожно мало, но это тестовые артефакты в рабочем промпте.

## 8. R-041: блокировка C++ (E)

1. **Намерение:** «напиши мне код на C++, который будет выводить в терминале привет мир». Явного запроса файла нет; естественный ответ — код текстом. R-040 (Planner OFF) так и ответил: SUCCESS, 329 токенов completion.

Попытка 2 (3 блока: system, TASK, SERVER VALIDATION) получила указание исправить ответ, которого не было.
3. **Интерпретация Planner.**
   - План из 2 стадий: `stage_1 produce_artifact` (WRITE, `hello.cpp`, `persistence`, postcondition `equals` с кодом) и `stage_2 verification` (VERIFY).
   - Контекст Planner содержал `permissions: allow_write=false, write_scope="Документация"`, но и все 14 инструментов, включая WRITE/DELETE (`server.py:4397`, без фильтра).
   - Системный промпт: «Permissions are server-owned: requesting a capability does not grant it» и «Do not introduce file mutations for explanatory/read-only tasks». Задача «напиши код» не попала под «explanatory».
   - Канонический пример `PLAN_FORMAT` начинается со стадии `produce_artifact` с записью файла.
4. **Валидация.** `validate_plan(value, raw_task)` разрешений не получает. Офлайн (`r041_plan.py`) реальный план R-041 → **accepted**; `raw_task_explicitly_forbids_file_mutation = False`. Черновая проверка выполнимости (только предложение) находит обе проблемы: «WRITE disabled for this RUN» и «hello.cpp outside WRITE scope 'Документация'».
5. **Executor и сервер.** STAGE получил 4 инструмента и вызвал `write_file(hello.cpp)`. Порядок проверок: сначала **scope** → `permission_scope_blocked` → немедленный терминальный BLOCKED, и только потом `allow_write` с эскалацией. Запись не выполнена.
6. **Законность BLOCKED:** да. Путь вне scope — терминальный по контракту, permission-защита сработала корректно и дефектом не считается.
7. **Дефект — в согласовании плана с намерением и разрешениями.** Текстовый ответ был возможен в рамках контракта: стадия `analysis` / `model_result` без capabilities, как в R-038.
8. **Цена:** ≥ 8 227 известных токенов + 1 попытка с UNKNOWN usage, результата нет. Без Planner — 13 457 токенов и правильный ответ.

## 11. Adversarial-проверка собственных выводов

- **R-033 — может, иной блок пакета?** Реконструкция использует реальные кандидат, разрешения, `verification_state` и счётчики. Внешнее состояние в пакет вносят только `fresh_git_status` / `fresh_git_diff`. `run_owned_filesystem_evidence`, `new_file_evidence` и `tool_facts` при 0 инструментов пусты. Точное совпадение R-034 (4122 / 4232) исключает расхождение шаблона. Остаётся неизвестным только содержимое diff.
- **Может, git status в R-034 был непуст?** Тогда размер отличался бы от 4122. Совпадение возможно только при пустых status и diff (READ scope «.» ничего не отфильтровывает).
- **Дублирование истории — может, всё же программное?** Каждое сообщение имеет свой `message_id`, время и `task_block_id`; на 41 пользовательское сообщение приходится 41 блок. Байтовая реконструкция совпала. Опровергнуто.
- **«Выключенный Dredd всё-таки вызывается»:** в 8 RUN не наблюдалось. Путь через PERMISSION существует только в коде — оставлено как HYPOTHESIS риска, не как факт.
- **R-041 — может, виновата защита?** Нет: путь вне scope — терминальный по контракту. Но план можно было отклонить до Executor, а текстовый результат допустим контрактом (R-038).
- **«Planner ON дешевле DIRECT» как общий вывод — неверно.** Planner ON на приветствие ≈ 12,5 тыс. (с Dredd), DIRECT без Dredd ≈ 13,1 тыс. Цена DIRECT растёт с длиной чата (R-033 57 сообщений → R-040 71), Planner ON — нет. Выключение Planner не гарантирует экономии; это подтверждает и исходный отчёт.
- **Отношение байт/токен** различается между ролями (Executor 6,8–7,7, Planner 4,7, Dredd 4,1–4,6) — поэтому оценки даны диапазонами и помечены ESTIMATED.
