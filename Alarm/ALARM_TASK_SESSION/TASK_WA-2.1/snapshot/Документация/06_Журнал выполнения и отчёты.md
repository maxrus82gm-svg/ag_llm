## 2026-10-01 — TASK 151G-DIAG-R031: EXECUTOR CONTEXT / TOKEN EXPLOSION AUDIT — DONE, RUNTIME UNCHANGED `[ARCH: Quality Transition / Executor Context]`

T-031/R-031 (`20261001_182057_e90f93`) сохранён как новый negative/stress case для будущей TASK 151G. RUN завершился BLOCKED до Final Audit, но provider accounting полностью объясняет расход: TOTAL 668 898 tokens; Executor 665 505, Planner 3 393, Dredd 0; 15 Executor API calls и 14 physical tool calls.

Первопричина token amplification подтверждена не предположением, а request-block accounting. Executor request context начинался примерно с 27k chars. Первый полный `read_file(ultra_ui.py)` добавил serialized tool-result block ~279 325 chars, после чего request #8 вырос до ~319k chars. Второй полный read того же файла добавил ещё ~279 325 chars и request #13 вырос до ~604k chars. Оба результата затем повторно отправлялись в каждом следующем stateless provider request.

Code audit подтвердил CURRENT mechanism: `server.py` сохраняет assistant function-call + полный function result в живом `messages`; `read_file` может вернуть до 2 MiB logical text; внутри одной незавершённой stage нет compiler/compaction, а `stage_context(reset=True)` очищает transcript только при переходе stage/replan/final-repair. Stage visibility ограничена capability, но не target set, поэтому READ+WRITE stage физически может читать нерелевантные или предназначенные для будущих stages файлы в общем READ scope. Guard P1 отслеживает узкий повторный pattern и не остановил separated duplicate full reads. Tool reserve защищает число обязательных оставшихся calls, но не защищает prompt size до момента reserve activation. Audit delta в Run Store экономит storage, но не provider prompt: API остаётся stateless.

Отдельно выявлены ошибки самого контрольного задания: переиспользован dirty `B2_live_01`, где `b2_logic.py` уже имел `STATUS_PREFIX = "READY"`; RAW TASK содержал короткие пути вместо fixture-relative paths; Planner выбрал `verify_file_content(kind=equals)` для требования наличия строки, хотя файл содержит дополнительный код. Эти дефекты объясняют часть странного поведения RUN, но не объясняют 600k context: context explosion является самостоятельным runtime limitation.

Решение diagnostic TASK: runtime не менять сейчас и не перескакивать через канонический порядок 151C→151F. R-031 и прежний R-027 становятся обязательными regression inputs для 151G. Acceptance для 151G должен включать bounded in-stage working set, запрет повторной передачи full historical tool payloads, сохранение полных outputs в Run Store, явный handling больших read results, stage-relevant material selection и доказательство отсутствия loss of authoritative facts/evidence.

DOC IMPACT: YES. CURRENT STATE: YES (известное ограничение). ARCHITECTURE IMPACT: NO runtime change / YES future acceptance clarification. CONTEXT LIBRARY IMPACT: NO. REGISTRY/ROUTING IMPACT: YES (diagnostic entry only). NEW DOCUMENT: NO. Canonical owners: `03` + `13`, transition details `20/21`.

После закрытия TASK 149 и разбора T-021 принята отдельная программа оптимизации runtime, model contexts и будущей памяти.

Созданы два временных переходных документа:

- `20_Программа качественного перехода - оптимизация runtime, контекстов и памяти.md` — канонический план: порядок 150/151 → 151A–151J → 152–154, инварианты, target architecture и контрольные точки;

## 2026-09-30 — TASK 146: RUN STORE EXTERNAL-LOCK RECOVERY — DONE + LIVE VERIFIED

TASK 146 исправляет доказанный TASK 145 scenario: canonical `.ultra/audit/index.json` может быть долго открыт внешним Windows process без delete/replace sharing, поэтому обычный atomic `os.replace` и bounded retry не гарантируют сохранение нового RUN.

### Реализация

`run_store.py` теперь поддерживает revisioned workspace index:

- `index.json` получает монотонное поле `revision`; старый index без поля читается как revision 0;
- при успешном canonical replace новый state остаётся в `index.json`;
- если canonical replace после bounded retry получает persistent `PermissionError`, полный index snapshot сохраняется как уникальная immutable generation в `.ultra/audit/index_generations/index-<revision>-<uuid>.json`;
- `load_workspace_run_index()` рассматривает canonical и generation snapshots и выбирает максимальную revision; при равной revision canonical имеет приоритет;
- после появления хотя бы одной generation следующая canonical попытка выполняется без повторного полного retry-window: при продолжающемся lock сразу создаётся следующая generation;
- когда lock исчезает, следующая index mutation записывает актуальный state обратно в canonical `index.json`; generations с revision не новее canonical удаляются, недоступные для удаления snapshots не делают RUN недоступным;
- если не удаётся записать и generation storage, `PermissionError` остаётся видимым и не маскируется;
- `update_run_summary_index()` больше не переписывает workspace index при summary-only изменениях `api_requests/tool_calls/usage`; index mutation происходит только при реальном изменении `run_status` или `final_audit`.

### Статус

Проблема ОБНАРУЖЕНА.

Автоматическая защита от такого поведения пока НЕ РЕАЛИЗОВАНА.

Рабочее название возможного будущего слоя:

`TASK EXECUTION GATE / NO-TOOL STOP GUARD`

Он должен отдельно контролировать ситуацию, когда изменяющая TASK завершается без необходимых фактических tool actions.
