## 3. Root cause

- **Сеть отправок** (`scan_send_sites`) опирается на распознанного получателя. Неизвестное имя клиента для неё невидимо — так задумано, именно поэтому нужна вторая сеть.
- **Сеть эндпоинтов** (`unexplained_endpoint_reads`) в REPAIR-001:
  1. проверяла только имена, буквально равные `CHAT_URL`/`OAUTH_URL`; алиасы импорта и атрибутный доступ ей не видны;
  2. считала аргумент «объяснённым», если вызов стоит на **той же строке**, что и учтённая отправка;
  3. не проверяла строковые литералы с хостом эндпоинта и имена эндпоинтов в строках (`getattr`);
  4. знала только модули `gigachat_transport`/`server` как источники констант, поэтому реэкспорт через другой модуль терялся.

## 4. Решение (собственный выбор)

**`analyze_module(module, source)`** — одна модель за один разбор AST. `scan_send_sites` и `unexplained_endpoint_reads` стали тонкими обёртками: сопоставление по идентичности узлов внутри одного дерева.

**Поток значения эндпоинта:**
- Источники эндпоинта:
  - отличительные имена `CHAT_URL`/`OAUTH_URL` в любом модуле — покрывает и `from x import *`;
  - `from <любой модуль> import CHAT_URL [as X]` — покрывает реэкспорт;
  - атрибут `<что угодно>.CHAT_URL` / `.OAUTH_URL`.
- Алиасы — fixpoint по простым присваиваниям `Name = <эндпоинт>`, цепочки допустимы.
  - В функции: локальное связывание другим значением или параметром — затенение; одновременно эндпоинт и что-то другое (включая `+=`) — **неоднозначность**.
  - На уровне модуля: повторное связывание импортированной константы — неоднозначность.
  - Неоднозначные имена никогда не классифицируются как LLM, но их использование отслеживается.
- Классификация отправки: LLM/OAUTH — только если URL-аргумент является чистой ссылкой на эндпоинт; иначе UNKNOWN.

**Строгое правило объяснимости.** Каждая ссылка на эндпоинт должна быть **ровно тем узлом**, который служит URL-аргументом учтённой LLM/OAUTH-отправки, либо правой частью функционально-локального чистого алиаса. Всё прочее — «необъяснённое»:
- `base_url=`;
- контейнеры;
- атрибутные цели;
- распаковка кортежей;
- значения по умолчанию;
- f-строки и конкатенация;
- вызовы методов на эндпоинте;
- `httpx.Request` / `urllib.request.Request`;
- лямбды;
- аннотации;
- модульные алиасы вне `gigachat_transport.py`;
- строки `"CHAT_URL"/"OAUTH_URL"`;
- литералы с хостом `api.giga.chat`/`ngw.devices.sberbank.ru` вне канонического определения.

Сопоставление по узлу, а не по строке: несколько обращений на одной строке оцениваются независимо.

**Почему так:** правило не зависит от того, как назван или где создан клиент. Чтобы увести трафик LLM мимо инвентаря, пришлось бы получить URL без единой ссылки на константы и без литерала хоста. Production этому правилу соответствует уже сейчас: эндпоинты используются только как прямой URL-аргумент 8 учтённых отправок, литералы — только в каноническом определении.

**Production не менялся** — проблема только в тестовом анализаторе.

**Найденные и устранённые дефекты собственного черновика** (до вклейки):
1. Каноническое `CHAT_URL = "…"` в `gigachat_transport.py` считалось «другим связыванием» и сняло бы алиас: OAuth стал бы UNKNOWN.
2. Модульное переопределение импортированной константы надо считать неоднозначным, а не затенением.
3. `setdefault` не перезаписывал класс неоднозначного имени.
4. Модульный алиас разрешался как определение, а реэкспорт через другой модуль терялся. Теперь модульные алиасы вне `gigachat_transport.py` — необъяснённые; импорт `CHAT_URL` из любого модуля распознаётся; атрибут `.CHAT_URL` распознаётся у любого объекта.

**Остаточные ограничения:**
- Эндпоинт, полученный вне кода — переменная окружения, конфиг-файл, сеть, — статически не отслеживается. Его закрывают динамический guard (сеть запрещена) и маршрутные тесты с захватом транспорта.
