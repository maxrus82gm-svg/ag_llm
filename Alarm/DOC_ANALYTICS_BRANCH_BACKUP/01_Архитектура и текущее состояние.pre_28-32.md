# Архитектура и текущее состояние GigaChat Ultra Local Agent

## Статус документа

Этот документ описывает **фактическое текущее состояние** проекта `ag_llm / GigaChat Ultra Local Agent`.

Он должен отражать то, что реально существует в коде и было подтверждено тестами или живым runtime.

Будущие функции здесь явно отделяются от реализованных.

Это краткая каноническая карта работающей архитектуры: для каждой крупной подсистемы здесь фиксируются её фактическое состояние и назначение, а подробный lifecycle, компоненты, состояния, правила и ограничения описываются в профильном архитектурном документе. При наличии профильного документа раздел этой карты должен явно указывать на него, не дублируя большое техническое описание.

После значимого изменения runtime этот документ проходит Documentation Impact Check вместе с профильным документом темы: актуальный код, diff, tests/checks и доступное live evidence определяют, нужно ли обновить краткий статус и устранить противоречащие текущие формулировки. Исторические записи не переписываются; если фактического влияния нет, искусственная правка не нужна. Маршрут выбора профильного документа для каждой TASK закреплён в `08_Старт.md`.

Документационная библиотека подготовленных текстов контекста перечислена в `16_Список_контекстов.md` (включая references `14` и `15`). Она сопровождается человеком и не подключается сервером к LLM автоматически. Фактическая runtime архитектура Workspace / Chat / Context описана ниже и в `03_Чаты, проекты и контекст.md`.

# 1. Общая архитектура

Проект больше не является системой, жёстко привязанной к одной модели `GigaChat-3-Ultra`.

Текущая архитектура развивается как локальный Agent Runtime, в котором модель является заменяемым вычислительным компонентом.

Упрощённая схема:

```text
USER
↓
Ultra UI
↓
AGENT RUNTIME
↓
MODEL ASSIGNMENT
↓
MODEL REGISTRY
↓
PROVIDER
↓
SELECTED MODEL
```

При этом:

```text
MODEL ≠ AGENT
```

Модель не является владельцем:

```text
Workspace
Chat
Context
Tools
Permissions
Backup
Verification
Trace
State
Lifecycle
```

Эти сущности принадлежат runtime.

# 2. Основные компоненты

Текущий runtime состоит из нескольких основных модулей.

## server.py

Backend Agent Runtime.

File toolbox включает READ `list_dir` / `read_file` / `find_text` / `read_file_range` и MUTATION `write_file` / `replace_text` / `insert_before` / `insert_after` / `delete_file`. Precise edit проверяет `expected_content_sha256` и единственность якоря до mutation; stale или ambiguous запрос не меняет файл. Практический порядок для Executor закреплён в `09_Обязательный регламент Ultra.md`.

Отвечает за:

```text
GigaChat API
MAIN CHAT RUN
file-agent tools
permissions
backup
verification
trace
Workspace interaction
Chat context loading
selected model execution
Independent Final Audit before SUCCESS
Final Audit Evidence collection
Evidence Completeness Gate
bounded same-RUN Final Audit correction V.5
structured Server Final Verifier Feedback
```

Для MAIN CHAT runtime выбирает модель через MODEL REGISTRY и передаёт фактический `provider_model_id` в API.

## gigachat_transport.py

Небольшой shared low-level слой GigaChat auth / transport.

Он содержит общие GigaChat endpoints и получение access token, чтобы `server.py` и `verifier_runtime.py` не зависели друг от друга через transport implementation.

Фактическое направление dependency:

```text
server.py
    ↓
verifier_runtime.py
    ↓
gigachat_transport.py
```

Обратной зависимости `verifier_runtime.py → server.py` нет.

Это пока не универсальный Provider Adapter.

---

## verifier_runtime.py

Отдельная runtime role Independent Verifier.

Текущие свойства:

```text
one-shot clean call
separate Verifier Model Assignment
default = GigaChat 3 Pro (`gigachat_3_pro`)
model resolution через MODEL REGISTRY
TOOLS = NONE
persistent Verifier Chat = NONE
Workspace / Chat Storage самостоятельно не создаёт и не читает
Executor conversation/session state не наследует
```

Verifier получает только явно переданные RAW TASK и `verification_context`, возвращает typed `VerifierResult` и поддерживает semantic `PASS` / `FAIL` для `PREFLIGHT`, `MUTATION`, `FINAL`, `CONSISTENCY`, `PERMISSION`. В текущем `run_agent_task(...)` подключены `FINAL` и `PERMISSION`; остальные типы доступны в protocol, но не являются активными production gates.

`VerifierRuntimeError` и `VerifierProtocolError` остаются отдельными от semantic FAIL. Malformed response не превращается в PASS.

# 3. Workspace

Workspace является корнем конкретного проекта.

В Workspace хранится переносимое внутреннее состояние:

```text
.ultra/
```

Каждый Workspace имеет постоянный:

```text
workspace_id
```

Несколько Workspace могут быть зарегистрированы в UI.

Реализованы:

```text
создание Workspace
подключение существующего Workspace
переключение
переименование
удаление из UI registry
```

Удаление Workspace из UI registry не означает удаление самого проекта.

# 4. Portable и local state

Архитектурно разделяются:

```text
PORTABLE WORKSPACE STATE
```

и:

```text
LOCAL MACHINE STATE
```

Portable:

```text
.ultra/
```

Local:

```text
UI settings
backup paths
local diagnostic log paths вне portable `.ultra/audit`
Role Context
runtime configuration
```

Это позволяет переносить проект между компьютерами без смешивания machine-specific настроек.

# 6. RAW HISTORY

Каждое сообщение Chat сохраняется как отдельный RAW MESSAGE.

Identity:

```text
workspace_id
chat_id
message_id
```

RAW MESSAGE содержит:

```text
original_text
```

RAW является immutable source of truth.

После создания RAW не должен изменяться из-за:

```text
compression
manual summary edit
restore
model replacement
UI rerender
```

---

# 7. Assistant provenance

Для assistant messages сохраняется producer metadata.

Например:

```text
kind
role_id
run_id
model_id
model_display_name
provider
provider_model_id
```

Это позволяет после restart понимать, какой именно моделью был создан конкретный ответ.

Старые сообщения без producer metadata остаются совместимыми.

---

# 8. Project Context

Каждый Workspace имеет общий:

```text
PROJECT CONTEXT
```

Он хранится в:

```text
.ultra/project_context.md
```

Project Context:

```text
общий для Chat одного Workspace
persistent
редактируется через UI
имеет историю ревизий
загружается runtime
```

Project Context не является Chat History.

---

# 9. Role Context

MAIN CHAT и COMPRESSOR имеют отдельные Role Context.

Пример:

```text
MAIN CHAT ROLE CONTEXT
COMPRESSOR ROLE CONTEXT
```

Role Context описывает роль.

Project Context описывает проект.

Chat Context описывает конкретный разговор.

Эти сущности не должны смешиваться.

# 10. MAIN CHAT MODEL ASSIGNMENT

MAIN CHAT больше не использует только одну жёстко заданную модель.

В UI реализован выбор модели MAIN CHAT.

Runtime получает:

```text
model_id
```

и разрешает его через:

```text
MODEL REGISTRY
```

в:

```text
provider
```

# 17A. Independent Final Audit — текущая карта

Final Audit выполняется после deterministic Verification Gate и до normal SUCCESS, в том числе для no-tool RUN. Источник истины — RAW TASK и server-observed evidence; Candidate является заявлением Executor, а fresh Git state не доказывает ownership текущего RUN. Критически неполное evidence блокирует SUCCESS до Verifier call. Только valid `FINAL` PASS разрешает normal SUCCESS.

Текущий V.5 допускает до двух correction handoffs в том же RUN (`FINAL_AUDIT_CORRECTION_LIMIT = 2`) с защитой от no-progress, repeated failure и ping-pong. После исчерпания лимита следующий semantic FAIL завершает RUN с `final_audit_correction_exhausted` / `FinalAuditSemanticError`; runtime, protocol и critical evidence failures немедленно terminal. Rejected Candidate и server feedback остаются внутренними сообщениями RUN, а не persistent Chat history.

Подробные evidence fields, событийный trace, feedback, retry policy и edge cases принадлежат `13_Архитектура оперативной верификации и контроля выполнения задач.md`.

# 18. Compressor Soft Guard


# 19–35. Working Representation и Context Compression — текущая карта

`context_storage.py` хранит immutable RAW MESSAGE отдельно от MESSAGE CONTEXT STATE и Context Variants. Активное представление отдельного сообщения бывает RAW (`FULL`) либо принятая пользователем SUMMARY (`COMPRESSED`). Working Representation хранит выбранное представление в исходном порядке ролей; UI показывает активный текст (для COMPRESSED может показывать модель и фактическое сокращение), а Original Viewer открывает неизменённый RAW без переключения. Конкретный role model request получает только те Working Representations, которые включает его context policy: после TASK 139 normal Planner-enabled Executor task-scoped и не получает старые Chat messages автоматически.

Compressor создаёт Proposal от RAW. Пользователь может принять, отклонить или вручную отредактировать его; только принятое представление становится активным. Restore возвращает RAW, сохраняя прежние варианты; recompression снова начинается от RAW. Состояние и варианты переживают restart. Базовый FULL → COMPRESS → PROPOSAL → ACCEPT → COMPRESSED → ORIGINAL → RESTORE → FULL lifecycle ранее подтверждён unit tests и живым UI-тестом. Один отдельный Compressor call, soft guard и максимум один corrective retry составляют текущий base lifecycle; независимые COMPRESS → VERIFY → FINALIZE, Review Chat и автоматический context-budget manager остаются будущими.

Подробные структуры Workspace / Chat / MESSAGE CONTEXT STATE, сборка Working Chat Context, UI/trace и persistence принадлежат `03_Чаты, проекты и контекст.md`. Compression lifecycle, Proposal и будущий pipeline принадлежат `Архитектурное решение - управляемое сжатие контекста.md`. Model Assignment принадлежит `11_Мультимодельная архитектура и назначение LLM.md`.

# 51. No-tool completion и Final Audit

Базовый deterministic Verification Gate сам по себе не доказывает выполнение изменяющей TASK в сценарии:

```text
изменяющая TASK
↓
модель не вызывает tools
↓
stop
↓
пишет, что задача выполнена
```

Final Audit теперь выполняется и при `tool_call_count = 0` / `write_revision = 0`. Он может semantic FAIL заблокировать неподтверждённое заявление Executor о выполнении TASK.

При этом нулевое количество tools само по себе не является deterministic FAIL: read-only или explanatory TASK может завершиться корректно без mutations.

# 55. Главный архитектурный принцип

Система развивается не как набор отдельных чатов внутри конкретных LLM.

Источник состояния находится в runtime.

Канонически:

```text
MODEL
    = вычислительный ресурс

ROLE
    = назначение и правила

CONTEXT
    = явно собранные данные

TOOLS
    = явно разрешённый набор

STATE
    = persistent состояние runtime

PROVIDER SESSION
    ≠ источник истины
```

# 56. Канонические инварианты

1. RAW MESSAGE после создания не переписывается.

2. Compression не уничтожает RAW.

3. Context Variant хранится отдельно.

4. Proposal не активируется без решения пользователя.

5. Restore возвращает active representation к RAW.

6. Recompression выполняется от RAW.

7. Project Context не равен Chat History.

8. Role Context не равен Project Context.

9. MAIN CHAT, COMPRESSOR, PLANNER и VERIFIER имеют независимые runtime calls.

10. Tools принадлежат роли/runtime, а не модели.

11. Model selection не должен менять safety policy.

12. Provider-side hidden history не является системой памяти проекта.

13. Workspace и Chat state должны переживать restart.

14. MAIN CHAT должен получать active Working Representation.

15. Original Viewer должен всегда позволять увидеть immutable RAW.

16. Candidate Final Response не является authoritative fact до Final Verifier PASS.

17. Fresh Git state нельзя автоматически приписывать текущему RUN без подтверждения `mutation_facts`.

18. Только VALID FINAL VERIFIER PASS разрешает normal RUN SUCCESS.

19. Первый valid semantic Final Audit FAIL блокирует SUCCESS, но не завершает RUN: допускается ровно один same-RUN correction handoff.

20. Rejected Candidate и Server Final Verifier Feedback не становятся обычными persistent Chat messages.

21. Повторный semantic FAIL после использованного handoff означает `final_audit_correction_exhausted` и terminal RUN FAILED.
