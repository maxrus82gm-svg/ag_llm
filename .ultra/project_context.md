# PROJECT CONTEXT

Общий подтверждённый контекст WORKSPACE проекта:

GigaChat Ultra Local Agent / ag_llm

Этот файл является общей рабочей памятью WORKSPACE для всех его CHAT.
Он перечитывается системой перед каждым новым RUN.

PROJECT CONTEXT должен содержать только устойчивые и актуальные сведения,
которые нужны разным чатам для правильной работы с проектом.

LLM не должна молча изменять PROJECT CONTEXT.
Изменения PROJECT CONTEXT выполняются только после явного решения пользователя.


============================================================
1. НАЗНАЧЕНИЕ ПРОЕКТА
============================================================

GigaChat Ultra Local Agent — локальное приложение для работы с GigaChat Ultra
как с управляемым файловым агентом и проектным ассистентом.

Основные направления проекта:

- локальный UI;
- работа с файлами выбранного WORKSPACE;
- несколько WORKSPACE;
- несколько CHAT внутри WORKSPACE;
- persistent RAW HISTORY;
- общий PROJECT CONTEXT;
- настоящий multi-turn Active Chat Context;
- server-side безопасность;
- обязательный backup;
- наблюдаемый trace / RUN logs;
- в дальнейшем — управляемое сжатие контекста;
- в будущем — возможный web UI и другие LLM.


============================================================
2. ОСНОВНАЯ ИЕРАРХИЯ
============================================================

Основная модель:

WORKSPACE
    ├── PROJECT CONTEXT
    ├── CHAT 1
    ├── CHAT 2
    └── ...

RUN не равен CHAT.

RUN — один цикл выполнения пользовательской задачи.

CHAT — постоянная ветка разговора, которая переживает несколько RUN.

WORKSPACE — проект / рабочая папка, внутри которой существует несколько CHAT.

PROJECT CONTEXT общий для всех CHAT одного WORKSPACE.


============================================================
3. ПЕРЕНОСИМОЕ ХРАНИЛИЩЕ WORKSPACE
============================================================

Основная переносимая память WORKSPACE хранится внутри:

.ultra/

Фактическая структура включает:

.ultra/
    workspace.json
    project_context.md
    project_context_history/
    chats/
        chat_<id>/
            metadata.json
            messages/
                msg_<id>.json
            summaries/
    proposals/

Некоторые будущие каталоги могут существовать заранее,
даже если соответствующая функция ещё не реализована полностью.

.ultra является частью WORKSPACE и должна переноситься вместе с проектом.

Обычный file-agent НЕ должен напрямую изменять .ultra через write_file/delete_file.

Контекстные данные должны изменяться через контролируемый Context Storage API.


============================================================
4. ПОСТОЯННЫЕ ID
============================================================

Каждый WORKSPACE имеет постоянный:

workspace_id

формата:

ws_<uuid>

Каждый CHAT имеет постоянный:

chat_id

формата:

chat_<uuid>

Каждый RAW MESSAGE имеет постоянный:

message_id

формата:

msg_<uuid>

ID не должны зависеть от порядкового номера и не должны меняться
при переименовании сущности.


============================================================
5. RAW HISTORY
============================================================

RAW MESSAGE является неизменяемым оригиналом сообщения.

Фактический RAW MESSAGE хранится отдельным JSON-файлом и содержит основные поля:

workspace_id
chat_id
message_id
role
created_at
original_text

RAW MESSAGE не должен переписываться при будущем сжатии контекста.

Сейчас RAW HISTORY уже реализована и сохраняется на диск.

Пользовательское сообщение сохраняется до API request.

Ответ ассистента сохраняется до окончательного UI success.

История CHAT переживает restart приложения.


============================================================
6. PROJECT CONTEXT
============================================================

PROJECT CONTEXT хранится в:

.ultra/project_context.md

Он общий для всех CHAT данного WORKSPACE.

PROJECT CONTEXT перечитывается перед каждым новым RUN.

Пользователь может редактировать PROJECT CONTEXT через UI.

Предыдущие версии PROJECT CONTEXT сохраняются в history.

PROJECT CONTEXT не является полной документацией проекта.

Это компактная рабочая память, необходимая для правильной работы
разных CHAT и разных RUN.


============================================================
7. ACTIVE CHAT CONTEXT
============================================================

Настоящий multi-turn Active Chat Context уже реализован.

При RUN система получает:

SYSTEM INSTRUCTIONS
+
PROJECT CONTEXT текущего WORKSPACE
+
RAW HISTORY выбранного CHAT
+
текущий пользовательский запрос
+
служебный tool context

Выбранный chat_id реально влияет на то,
какая история передаётся основной модели.

Разные CHAT не должны смешивать собственную историю.


============================================================
8. ЧТО В СИСТЕМЕ КОНТЕКСТА ЕЩЁ НЕ РЕАЛИЗОВАНО
============================================================

Пока НЕ считать реализованными:

- MESSAGE SUMMARY;
- COMPRESSION PROPOSAL;
- COMPRESSION PROVIDER;
- WORKING REPRESENTATION сообщения;
- отдельное изменяемое состояние RAW / SUMMARY;
- кнопки сообщения:
  Сжать LLM / Редактировать / Оригинал;
- ручное переключение конкретного сообщения между RAW и SUMMARY;
- token budget Active Context;
- автоматический trimming;
- автоматические предложения обновления PROJECT CONTEXT;
- полноценный UI просмотра всех ревизий PROJECT CONTEXT.

Следующий основной функциональный рубеж:

06.4
RAW HISTORY vs WORKING / ACTIVE CONTEXT

затем:

06.5
управляемое сжатие контекста.


============================================================
9. ВАЖНОЕ АРХИТЕКТУРНОЕ ПРАВИЛО ДЛЯ SUMMARY
============================================================

RAW MESSAGE является immutable.

Следовательно изменяемое состояние вида:

active_representation = raw / summary

НЕ должно храниться внутри самого immutable RAW MESSAGE.

Будущий выбор:

RAW
или
SUMMARY

должен храниться в отдельной сущности состояния / WORKING REPRESENTATION,
связанной с message_id.

SUMMARY должна существовать отдельно от RAW MESSAGE.

============================================================
11. SERVER-SIDE SAFETY
============================================================

Физические ограничения применяет server.py.

Существуют отдельные разрешения / scopes:

READ
WRITE
DELETE
VERIFY

WRITE и DELETE требуют:

READ = ON
VERIFY = ON

WRITE scope и DELETE scope должны находиться внутри разрешённого READ scope.

Обычный текстовый приказ модели не заменяет физические server-side ограничения.


============================================================
12. VERIFICATION GATE
============================================================

Server Verification Gate физически не позволяет изменяющему RUN
завершиться SUCCESS, пока необходимые проверки после последней мутации
не выполнены.

Используются VERIFY tools:

python_compile
git_diff
git_status
ui_smoke_test

Общее правило:

- изменён существующий Python-файл → нужен python_compile;
- изменён server.py или ultra_ui.py → нужен ui_smoke_test;
- после изменения файлов → нужны актуальные git_diff и git_status.

После новой записи предыдущая проверка может стать устаревшей.

Для documentation-only TASK не нужно выполнять python_compile
или ui_smoke_test, если Python/runtime-файлы в этом RUN не изменялись.

Не тратить tool calls на проверки, которые не относятся к текущим изменениям.


============================================================
13. BACKUP
============================================================

Защищённый backup является обязательной server-side защитой.

Отключать backup через обычный RUN permissions нельзя.

Backup принадлежит WORKSPACE, а не отдельному CHAT.

По умолчанию локальное хранилище:

%LOCALAPPDATA%\GigaChatUltra\workspaces\<workspace_id>\backups

Каждый RUN получает собственный каталог:

<backup_dir>/<run_id>/

В начале RUN создаётся snapshot переносимого состояния:

context/.ultra/

manifest.json содержит в том числе:

workspace_id
chat_id
context_snapshot
changed_files
new_files
deleted_files

Обычные файлы проекта не копируются целиком заранее.

Существующий файл сохраняется непосредственно перед первой записью.

Удаляемый файл сохраняется непосредственно перед удалением.

Новый файл фиксируется в manifest как new_files.


============================================================
14. RUN LOGS
============================================================

RUN logs также принадлежат WORKSPACE.

Default:

%LOCALAPPDATA%\GigaChatUltra\workspaces\<workspace_id>\logs

Имя лога связано с run_id:

<run_id>.jsonl

Backup path и RUN log path можно локально изменить
в настройках конкретного WORKSPACE.

Эти абсолютные локальные настройки хранятся вне переносимого .ultra.

Backup/log path внутри самого WORKSPACE в текущей версии запрещён.


============================================================
15. PORTABLE И LOCAL DATA
============================================================

Portable, переносится вместе с проектом:

.ultra/
    workspace metadata
    PROJECT CONTEXT
    CHAT
    RAW HISTORY
    будущие SUMMARY / proposals

Local machine state:

%LOCALAPPDATA%\GigaChatUltra\...

В local state находятся:

- UI state;
- registry подключённых WORKSPACE;
- runtime settings;
- backup;
- RUN logs.

Потеря local UI/runtime state не должна означать потерю основной истории WORKSPACE.

============================================================
24. ЭКОНОМИЯ TOOL CALLS
============================================================

Tool limit является реальным ресурсом RUN.

При большой TASK:

- не перечитывать один и тот же файл без причины;
- не повторять одинаковые проверки;
- не запускать нерелевантные VERIFY tools;
- читать только необходимые участки больших файлов, если этого достаточно;
- оставлять запас tool calls на финальную verification.

Перед финальным SUCCESS после изменяющей TASK должны остаться возможности
выполнить обязательные:

git_diff
git_status

и другие проверки, которые действительно требуются сервером.

Если задача не помещается в лимит,
лучше завершить согласованный логический блок,
чем потратить весь лимит до Verification Gate.
