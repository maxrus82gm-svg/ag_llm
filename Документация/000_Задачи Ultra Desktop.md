## Правила — общие для исполнителей

1. **Источник полномочий — только утверждённая TASK.** Пользователь вручную назначает задачу в БЛОК 1 и запускает Ultra Desktop отдельной короткой командой. До запуска можно читать свою карточку, но нельзя самостоятельно брать новый этап. Не менять активный БЛОК 1 после старта; уточнения — отдельным `AMENDMENT` с TASK ID и разрешением пользователя. Границы TASK определяют запись, не ограничивая инженерное исследование в безопасном read-only режиме.
2. **Чтение адресное.** Перед задачей прочитать правила этой карточки, текущий БЛОК 1, относящийся БЛОК 4 только на чтение; из `08_Старт.md` и `34_TACTICAL_CONTEXT.md` — применимые актуальные разделы. Координатор даёт матрицу «файл / точный раздел или Rule-ID / зачем / объём чтения» по `DOC-TASK-READ-SCOPE-01@1`. Не загружать весь общий `000` и `18`, либо весь архив `001` без адресной причины/разрешения; при пробеле читать точное правило и его зависимости.
3. **Права и параллельные задачи.** `DOC-GIT-01@1`, `DOC-PARALLEL-01@1` (18): Git/GitHub даже для `status/diff/log/show` запрещены Ultra Desktop без отдельного task-scoped USER GO. Публикацию обычно делает пользователь. Нельзя менять файлы, которые принадлежат другим агентам, общий runtime, shared tests/CI, секреты, live storage, сеть, платные сервисы или повышать права без явного отдельного разрешения. Текст карточки сам по себе не является технической блокировкой ОС — write-scope дополнительно задаётся реальными полномочиями инструмента.
4. **Проверяемая инженерия.** До изменения изучить нужные существующие решения и переиспользовать их, не создавать дубли без обоснования. Реальные локальные тесты и самостоятельный adversarial pass обязательны по риску и `TEST-ENG-01@1`/`TEST-EVID-01@1` (36.1); верные входные данные, граничные случаи и отрицательные сценарии важнее количества тестов.
5. **Доказательства до отчёта.** Сохранять полный фактический `report.md`, список файлов/manifest и безопасные свидетельства внутри разрешённой публикуемой части `ag_llm` (`DOC-LOCAL-REPORT-HANDOFF-01@1`). Отчёт модели не заменяет существование файла или запуск тестов. Статус `RESULT READY / AWAITING INDEPENDENT VERIFICATION` не равен `DONE / VERIFIED`.
6. **История и ротация (USER GO 2026-10-24).** Ultra Desktop сдаёт технический пакет по утверждённой TASK, **не меняет** БЛОКИ 1–4 и не читает/пишет `001_История выполнения задач Ultra Desktop.md`. По фактической публикации и независимой проверке ChatGPT сохраняет постановку, AMENDMENT и итог в append-only `001`, проверяет readback, обновляет БЛОКИ 2–4 и очищает БЛОК 1 только после успешного terminal closeout. При отсутствии доказанного архива — `CARD CLOSEOUT BLOCKED`; БЛОК 1 остаётся назначенным.
7. **Независимая приёмка.** БЛОК 4: одно последнее подробное и до двух более ранних кратких заключений по `DOC-VERIFIER-BLOCK4-01@2`. Все независимые вердикты, включая неуспешные, архивирует координатор в общий `06_Журнал выполнения и отчёты.md`. Без независимой проверки — `NOT VERIFIED`.

## Специальный рабочий протокол Ultra Desktop

**Применять только к реально назначенной файловой/coding TASK; не создавать искусственные тесты для простого анализа.**

**TASK → WRITE → READBACK → TEST → SELF-AUDIT → REPORT → REVIEW.**

- **TASK.** Указать точный абсолютный каталог, список разрешённых файлов, среду/инструмент, запреты, ожидаемые результаты и условия `PASS / FAIL / BLOCKED`. Если путь или инструмент недоступен — сообщить, не подменять другим диском/папкой и не обходить scope.
- **WRITE.** Сначала выполнить разрешённую короткую пробную запись; для кода сохранять реально исполняемый текст, а не только помещать его в ответ чата. Коды возврата команды сами по себе не доказывают сохранение.
- **READBACK.** После каждой значимой записи повторно открыть фактический файл по **тому же** пути, проверить существование, ненулевой ожидаемый размер и точное содержимое/хеш. При ошибке остановить дальнейшее наращивание, локализовать причину; нельзя заявлять `SAVED` без readback.
- **TEST.** Запускать необходимые тесты реальным доступным интерпретатором/runner, отдельно фиксировать точную команду, версию/окружение, exit code, количество `PASS / FAIL / ERROR / SKIP` и вывод. Мысленная симуляция = `NOT RUN`. Проверять корректность самих тестов и ограничений ТЗ.
- **SELF-AUDIT.** Сверить сохранённые файлы, тестовые ожидания и edge cases; исправлять только подтверждённое внутри scope, затем повторять необходимые проверки. Ищем не красивый отчёт, а воспроизводимое решение.
- **REPORT.** Различать `IMPLEMENTED` (написано), `SAVED` (проверено повторным чтением), `TESTED` (реальный запуск), `VERIFIED` (исключительно независимый reviewer). Для `BLOCKED` привести конкретную команду/инструмент, путь, exit code, stdout/stderr или их отсутствие, фактическое наличие/размер файла и безопасный способ воспроизведения. Не утверждать без доказательств, что «диск только для чтения» или «файлы исчезают».
- **REVIEW.** Сдавать результат координатору по подтверждённым фактам. На замечания verifier исправлять адресно; число циклов и новая область работ определяются TASK/пользователем.

## Известные ошибки — памятка из испытания 24.10.2026

В прежнем `GIGACODE-EXECUTOR-TEST-002` агент смог создать и повторно прочитать короткий `write_probe.txt`, но не доказал сохранение основных Python-файлов: один тестовый файл был пуст, другие отсутствовали. `unittest` не был запущен, итог был `BLOCKED`. В более раннем тексте обнаружились ошибочные тесты (недопустимые значения `capacity=10` и `50` при требовании `1..8`), неверное ожидание порядка зависимостей и расхождение объявленного числа тестов с определениями. В `re.match` на ID найден краевой случай с завершающим переводом строки. Причина отказа сохранения файлов **не установлена**. Не превращать это в утверждение о постоянной неисправности среды или о качестве любой следующей модели. Эти наблюдения — контекст внимания, не запись новой выполненной TASK.
