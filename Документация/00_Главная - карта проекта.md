# GigaChat Ultra Local Agent

GigaChat Ultra Local Agent — локальная рабочая среда для работы с проектами, файлами, Workspace, Chat и долговременным контекстом.

**Текущий runtime:** `server.py` использует Model Registry и отдельные назначения моделей MAIN CHAT, COMPRESSOR и VERIFIER через GigaChat transport.

**Принятое архитектурное направление:** универсальный Agent Runtime, в котором LLM выбирается через MODEL ASSIGNMENT и MODEL REGISTRY. Мультимодельный фундамент реализован; универсальный Provider Adapter и Local Provider остаются будущими этапами.

Система развивается в сторону локального клиента уровня ChatGPT / Codex, где:

- проект и его данные остаются на диске пользователя;
- история Chat сохраняется между запусками;
- Project Context является общей памятью Workspace;
- сервер физически контролирует файловые действия модели;
- backup, trace и verification используются как независимые уровни защиты;
- RAW HISTORY сохраняется независимо от активной Working Representation и сжатия.

## Текущее состояние проекта

### Workspace

Workspace является корнем конкретного проекта.

В Workspace хранится переносимое служебное состояние:

```text
.ultra/
```

Workspace имеет постоянный `workspace_id`.

Несколько Workspace могут быть зарегистрированы в UI и переключаться пользователем.

Локальные runtime-настройки конкретного компьютера не должны смешиваться с portable Workspace state.

---

### Chat

Внутри Workspace существует несколько независимых Chat.

Для Chat реализованы:

- постоянный `chat_id`;
- создание;
- переключение;
- переименование;
- persistent history;
- восстановление истории после restart.

Удаление Chat пока НЕ РЕАЛИЗОВАНО как завершённая функция.

---

### RAW HISTORY

Каждое сообщение сохраняется отдельным RAW MESSAGE.

Используются постоянные ID:

```text
workspace_id
chat_id
message_id
```

RAW HISTORY является неизменяемым источником исходной истории разговора.

User RAW сохраняется до API request.

Assistant RAW сохраняется до успешного отображения результата в UI.

---

### Project Context

Каждый Workspace имеет общий Project Context.

Project Context:

- доступен всем Chat данного Workspace;
- хранится в `.ultra/project_context.md`;
- загружается в каждый RUN;
- редактируется через UI;
- имеет историю ревизий.

Обычные file tools не должны напрямую изменять `.ultra`.

---

### Active Chat Context

При RUN сервер загружает историю выбранного `chat_id` и собирает Main Chat context из активных RAW или SUMMARY представлений вместе с Project Context.

Это обеспечивает настоящий multi-turn context.

При этом отдельная WORKING REPRESENTATION ещё НЕ РЕАЛИЗОВАНА.

Сейчас Active Chat Context строится из Working Representation выбранного Chat: RAW для несжатых сообщений, активная SUMMARY для принятых Context Variants.

## Мультимодельная архитектура

Каноническое решение: [[11_Мультимодельная архитектура и назначение LLM]].

- архитектурное решение — **ПРИНЯТО** (`MM.0 — ГОТОВО`);
- MODEL REGISTRY, GigaChat Multi-Model и назначения MAIN CHAT, COMPRESSOR, VERIFIER — **РЕАЛИЗОВАНЫ**;
- универсальный Provider Adapter и Local Provider остаются будущими этапами;
- контекст, state, tools, permissions, safety, verification, trace и lifecycle принадлежат роли / Agent Runtime, а не физической LLM.

Рабочая цепочка с GigaChat transport; универсальный Provider Adapter — целевое расширение:

```text
AGENT RUNTIME
    ↓
MODEL ASSIGNMENT
    ↓
MODEL REGISTRY
    ↓
GigaChat transport
    ↓
MODEL
```

## Safety / Verification

Сервер использует несколько независимых уровней контроля.

### Permission scopes

Отдельно задаются:

- READ;
- WRITE;
- DELETE.

Модель не должна самостоятельно расширять разрешённый scope.

### Mandatory backup

Для RUN с изменениями используется обязательный backup.

Portable `.ultra` и локальные backup/log directories разделены.

По умолчанию локальные runtime-данные Workspace располагаются вне самого проекта в Workspace-specific namespace.

### Verification Gate

После файловых mutations сервер не разрешает завершить RUN успешным отчётом без необходимых проверок.

В зависимости от типа изменений могут требоваться:

- `git_diff`;
- `git_status`;
- `python_compile`;
- `ui_smoke_test`.

Проверки должны относиться к последней revision изменений.

## GUARD P1

GUARD P1 — первый server-side behavior / supervisor guard.

В UI существует отдельная галочка `GUARD P1`.

По умолчанию она включена.

GUARD P1 может вмешаться ДО физического выполнения подозрительного tool action и вернуть Ultra сообщение `SUPERVISOR CHECK`.

Физически подтверждены два сценария:

1. повторный успешный `read_file` одного и того же неизменённого файла;
2. попытка suspicious near-duplicate CREATE.

GUARD P1 не заменяет permission system или Verification Gate.

Это дополнительный слой коррекции поведения агента.

### Известное ограничение

Обнаружен edge case: имя файла, упомянутое в тексте TASK как пример или описание ошибки, может быть ошибочно воспринято как пользовательское разрешение на CREATE.

Эта логика требует дальнейшего усиления.

## Известный архитектурный gap

Обнаружен отдельный сценарий:

```text
изменяющая TASK
→ Ultra не вызывает tools
→ сразу stop
→ TOOLS: 0
→ текстом сообщает, что работа выполнена
```

Final Audit сравнивает заявление Executor с server-observed evidence и может отклонить ложное заявление об изменении. `TOOLS = 0` само по себе не означает ошибку. Автоматический mutation-intent / Execution Consistency gate сейчас отключён; классификация намерения остаётся диагностической.

Возможный будущий слой:

```text
TASK EXECUTION GATE
или
NO-TOOL STOP GUARD
```

Статус:

**НЕ РЕАЛИЗОВАНО.**

```text

```

## Главный принцип проекта

```text
Пользователь ставит TASK.
        ↓
Модель предлагает действия.
        ↓
Permission Gate решает, разрешены ли они.
        ↓
GUARD может вмешаться в подозрительное поведение.
        ↓
Tool выполняет разрешённое действие.
        ↓
Backup страхует изменение.
        ↓
Verification Gate требует подтверждения результата.
        ↓
Trace показывает, что реально произошло.
        ↓
Git сохраняет проверенные контрольные точки.
```

Финальный текстовый отчёт модели никогда не должен считаться более надёжным источником, чем фактический trace и состояние файлов.
