**Тип:** постоянная модельно-нейтральная необязательная оболочка, слот A. **Актуальное назначение и статус — в оперативной карточке ниже (внутри SLOT).** Отсутствие назначения не блокирует никакой RT. Имя файла не закрепляет модель, человека или тип работы.

**Навигация Obsidian:** [[33_Круглый стол - план исполнения|33 — итоговый execution plan]]. **В режиме INDEPENDENT_PLAN не переходить по ссылке и не открывать оперативную часть 33 до своей SUBMITTED-сдачи и общего разрешённого REVEAL.** Ссылка нужна для человека и Graph, но не предоставляет доступ.

## Постоянная инструкция слота

1. До начала получить **от пользователя/назначенного координатора** RT/TASK, участника, модель, режим (INDEPENDENT_PLAN или REVIEW), допустимый read/write scope, общий `input_manifest_ref`, `rule_set_ref` и known exposure. Если чего-то обязательного нет — запросить, не выдумывать задание. Режим и разрешения не появляются из наличия файла.
2. Адресно прочитать `rule-ref:DOC-GIT-01@1` и `rule-ref:DOC-CHANGE-01@1` из 18, `rule-ref:RT-INDEPENDENCE-01@1`, `RT-INPUT-01@1`, `RT-CLEANUP-01@2` из 28 и `rule-ref:PLAN-MODES-01@1`, `PLAN-SEAL-01@1`, `PLAN-RECONCILE-01@2`, `PLAN-APPROVAL-01@2` из **постоянной нормативной части 33**, вместе с зависимостями; не читать для этого полный 33 при blind-mode. При невозможности отделить правила — просить координатора о безопасной выборке.
3. Локально читать исходники напрямую; **никаких самостоятельных Git/GitHub-операций**, включая `status/diff/log`; история по запросу через пользователя/координатора. Не использовать читательский доступ для обхода запрета на чужие планы.
4. `INDEPENDENT_PLAN`: исходный собственный TASK graph, mappings, dependencies, проверки, риски и ограничения **до** чтения чужих планов/их пересказов. `REVIEW`: изучить явно указанную версию проверяемого плана и сдать findings с evidence; этот результат не объявляется слепым.
5. Редактировать **только разрешённую оперативную область собственного слота**, не трогать постоянные инструкции и другой слот. В DRAFT менять текст можно, после SUBMITTED — добавлять отдельную correction/revision; прежний seal должен восстанавливаться. Не присваивать USER APPROVAL/PLAN APPROVAL и не запускать runtime.
6. По готовности сообщить `RESULT READY / AWAITING SEAL`; координатор сверяет, сохраняет bytes/provenance/input/hash извне файла и фиксирует SUBMITTED. Получить чужие планы можно только после разрешённого группового REVEAL; сравнение — новой записью, исходный результат не переписывать. **После хотя бы одного запечатанного SUBMITTED итоговый план обязательно оформляется в отдельной постоянной оболочке `33.3_Круглый стол - итоговый план.md`, не в исходном 33**, по `RT-FINAL-01@1` из 28. Пока нет group reveal и остальных gates, 33.3 не заполнять содержательным итогом.
7. При closeout дать фактологический отчёт: изученное и реальные проверки, source refs, corrections/unresolved, DOC IMPACT, требуемое действие/владелец. `COMPARED` не означает принятия. `ARCHIVED` и очистку слота делает координатор только после retention/restore и **отдельного разрешения пользователя** по RT-CLEANUP-01.

### 6. Минимально достаточный контракт аварийного бюджета

Это уточнение T2/T3, не проект полномасштабного финансового сервиса и не раннее выполнение всей 151I.

**Единицы и authority.** На сервере одна validated policy schema: hard request bytes, attempts, RUN cap в явно выбранной единице, output allowance, verification reserve, методы token estimate и правила UNKNOWN. Bytes, chars, prompt tokens, cached tokens, total и рубли не смешиваются. Токеновый cap не доказывается делением bytes/4: это estimator, не верхняя граница. Без проверенного tokenizer/conservative model bound жёсткая гарантия ограничивается bytes/attempts и принятым консервативным allowance; финансовая гарантия остаётся неподтверждённой. Проверяются body целиком, messages, function schemas и max output, ограничения модели; token counting через платный/внешний endpoint также не должен стать обходным расходом.

**Attempt state machine:**

~~~text
PREPARED → RESERVED → SENT → KNOWN_TERMINAL
                   ↘ proven NOT_SENT
                         SENT → UNKNOWN_TERMINAL → RECONCILED
~~~

- PREPARED не вызывает provider. Permit связан с RUN/lineage, physical attempt ID, logical call ID, role/mode, immutable effective policy revision, окончательными bytes/hash и reservation. Изменение body/model/tools после permit требует нового preflight, не повторного использования разрешения.
- Атомарная операция проверяет остаток и резервирует верхнюю принятую ответственность **до отправки**. Known settled usage, active reservations, UNKNOWN liabilities и доступный verification reserve — непересекающиеся buckets. Пример баланса: available=cap−known−active−unknown−protected reserve. При settlement reservation заменяется фактом; обе величины одновременно не списываются.
- Retry/repair/replan/diagnostic — новые physical attempts в том же бюджетном lineage, даже при одном logical call. Server-dispatched physical tool сам по себе не выдумывает LLM call. Классификация роли и mode фиксирована и не меняет общий счёт.
- Timeout/cancel после потенциального send не доказывает бесплатность. UNKNOWN удерживает liability; replan/recovery не обнуляет её. Окончательное known usage может скорректировать ту же attempt append-only reconciliation record; история terminal events остаётся. Duplicate без новой информации idempotent; conflicting usage — anomaly/BLOCKED, не выбор меньшего значения.
- NOT_SENT refund допустим только при доказанном отсутствии отправки. Provider-side exactly-once не обещается: локальный ID сам по себе не предотвращает повторное выполнение удалённым сервисом. Не повторять автоматически SENT/UNKNOWN после restart.
- Validate usage: non-negative integer, не bool, missing/null отдельно от настоящего 0, проверка согласованности схемы провайдера. При actual>reservation сохранить фактический перерасход и блокировать последующее; не уменьшать measured usage до лимита ради красивого отчёта.
- При нескольких concurrent attempts — один authoritative writer/lock на ledger; два permits не используют один остаток. Для нескольких процессов право владения RUN требует lease/lock и recovery semantics. Общий account-wide cap для независимых RUN — отдельная возможная политика; один RUN cap не гарантирует общего лимита всех пользователей/окон.
- Policy snapshot неизменяем для RUN. Новый UI profile применяется к будущим RUN; emergency stop может прекратить новые sends, но не отменяет уже SENT charge. «Сбросить настройки», сменить роль или открыть новый view нельзя использовать для refund.
- До мутации отдельно проверяются существующий mandatory **tool** reserve и достаточность принятого **provider** verification reserve. Предсказать любую будущую semantic cost невозможно: reserve гарантирует лишь заявленный bounded verification scope. Если он недостаточен, сохраняются progress, pending checks и BLOCKED, а не SUCCESS без Audit.
- Минимальная recovery-запись и in-process ledger — защитный контур; GUI, summary и optional diagnostics — projections. Если restore/reservation нельзя надёжно установить, физический send=0. Повреждённый/несовместимый ledger не превращается в fresh budget. Полный raw evidence storage остаётся отдельным обязательством: при его отказе нельзя продолжать мутации, выдавать новые source refs или эвиктить единственную копию материала.

**Точки сбоя, обязательные для тестов:** до reserve; после reserve до send; после send до response; после response до durable terminal; после terminal до UI/summary; double terminal; late usage; crash/restart с active и UNKNOWN; две конкурентные попытки; corrupt policy/ledger; отключённый observer. Для каждого фиксируются send count, buckets, reason code и допустимый NEXT. Не требуется сложный распределённый протокол для одного процесса; требуется не обещать crash safety без проверенной минимальной durable границы.

### 7. Контракт bounded context и сохранения доказательств

**S6a/S6b — minimal 151G, не весь будущий контекстный стек.** Начать с устранения amplification tool results в одной stage и DIRECT, сохранив существующий SYSTEM. Modular Global Context 151F, Planner prompt projections 151H, дорогой semantic compressor и оптимизация D/E сюда не подмешиваются.

Сервер формирует manifest каждого фактического request: role/mode, run/plan/stage/generation, requirement IDs, policy/model revision, block kind/bytes/hash, source IDs, inclusion/exclusion reason, truncation/freshness и общие bytes. **RAW TASK, authoritative constraints, незакрытые obligations, отрицательные/contradictory facts не удаляются как «неполезная история».** Если защищённое ядро само не помещается, честный BLOCKED предпочтительнее красивой экономии.
