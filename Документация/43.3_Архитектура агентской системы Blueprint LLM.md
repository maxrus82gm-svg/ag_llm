## 1. Обязательное решение владельца

- Визуально собирать агентские процессы и их автоматическое продолжение **в Blueprint LLM**, а не добавлять независимую агентскую систему в обычный Chat или отдельный конструктор Workspace.
- Предусмотреть отдельную управляющую ноду ожидания/пробуждения. Владелец помещает её в граф после запуска внешней задачи или тестов, при необходимости между двумя агентскими шагами. Если тесты не запускаются, нода не обязательна; маршрут определяется графом.
- Пока проверка не завершилась, агент не обязан работать непрерывно. Нода проверяет состояние с настраиваемой периодичностью, например 10 минут. После завершения продолжает тот же процесс через подключённую следующую ноду. Проектировать пробуждение по внешнему событию также, без обязательной постоянной LLM-сессии.
- Продумать, как существующий Workspace используется в Blueprint: выбор проекта, предоставление контекста, работа с файлами, инструментами, результатами и несколькими нодами. Workspace служит средой выполнения, а схема — способом управления. Не навязывать Workspace обычному личному чату.

## 2. Предлагаемый вид узла «Ожидание / пробуждение» (Wait for Event)

Один универсальный управляющий тип, не LLM-агент. Вариант для CI — адаптер наблюдения GitHub Actions. В дальнейшем этот же тип может ждать локальный тестовый процесс, ответ инструмента, завершение другого RUN или событие с разрешённого источника. Нода запускается управляющим входом; само её размещение или открытие графа ничего не запускает.

    [Агент: изменение кода]
               |
    [Инструмент: запуск тестов] -- test/run reference -->
    [Ожидание / пробуждение] <--- событие либо проверка по интервалу
          | PASS      | FAIL       | UNKNOWN/TIMEOUT/CANCELLED
          v           v            v
    [Следующий шаг] [Агент: анализ и исправление] [Остановка/решение]
                         |
                  [Новая попытка в пределах бюджета]

Входы (предлагаемые): exec, source_ref, expected_run_ref, policy; для CI — repository, точный commit SHA, конкретные run_id/attempt и набор обязательных jobs/checks либо правило их разрешения после запуска. Никаких секретов в пинах. Настройки: интервал проверки (пример 600 секунд), timeout, число допустимых проверок, режим event/polling, условия PASS/FAIL и реакция на UNKNOWN. Таймер работает на сервере, а не в браузере; событие может разбудить раньше очередной проверки. Сигнал события сам по себе не доказывает PASS: ядро перепроверяет источник, идентичность и обязательные проверки.

Выходы (предлагаемые): отдельные управляющие пины PASS, FAIL, UNKNOWN, TIMEOUT, CANCELLED; типизированные данные status, evidence_ref, result_summary, timestamps, run_ref. Не запускать следующую LLM на каждом poll. При ожидании состояние WAITING_EVENT, при наблюдении незавершённого теста — оставаться WAITING_EVENT; статус RUN и verdict проверки различаются. Отмена/таймаут не означают успешного завершения; skipped/cancelled/missing/неопределённый результат не является PASS. FAIL ведёт на явно соединённую ветку анализа/исправления только с разрешёнными полномочиями и ограничениями повторов. PASS ведёт на явно соединённый следующий шаг; обязательные gates и решение владельца не обходятся.

## 3. Предлагаемое серверное исполнение

- Использовать существующее ядро Turn/RUN, Run Store, каталог исполнителей и политики. Не создавать второе хранилище чатов или независимого координатора в Blueprint. Снимок версии графа и политики фиксируется при запуске.
- Сохранить checkpoint перед ожиданием: run_id, invocation_id, node_id, graph_revision, workspace_ref (при наличии), reference события/теста, время последнего наблюдения, next_check_at, deadline, policy snapshot и evidence. Не держать inference, GPU-слот или контекст LLM занятым ради таймера. Затраты на наблюдение/инструменты учитываются отдельно, без ложного нулевого usage.
- Единая серверная служба планирования/доставки событий поднимает ожидающие RUN после перезапуска. Закрытие вкладки не отменяет RUN. Сбой сервера не гарантирует немедленное пробуждение: после восстановления сверить внешнее состояние, не запускать исходную операцию повторно. Повторные/запоздалые события, рестарт между событием и продолжением, конкурирующие worker — не более одного логического перехода по устойчивому ключу и под существующей блокировкой. UNKNOWN не маскируется как FAIL или PASS, не разрешает автоматически повторить внешнее действие.
- Просроченное или чужое событие, неверная ревизия результата, отменённый RUN, исчерпанный бюджет, отсутствие права на инструмент либо отозванный доступ не открывают следующий шаг. Проверять полномочия заново при пробуждении. Merge main, production, LIVE/paid и расширение scope — только по действующему регламенту и разрешению владельца. Не обещать автоматический доступ к любым сервисам.
- Интерфейс ноды/Run Inspector показывает, чего ждём, когда была проверка, когда следующая, доказательство результата, длительность ожидания, отмену/ручную повторную проверку; отдельно — время работы LLM. Не рисовать прогресс выполнения, если источник его не сообщает. Пользователь должен видеть, что задача не потеряна, а находится в ожидании.

## 4. Workspace и визуальный граф — вопросы, которые решить до первого файлового агентского RUN

Предлагаемая модель: один Workspace может хранить несколько схем и RUN, а одна переиспользуемая схема может быть запущена в разных Workspace при явно разрешённой привязке. Это проектный вариант, не утверждённая физическая схема хранения. Workspace уже является существующей сущностью Studio; не дублировать его в Blueprint.

- На запуске явно выбрать Workspace (или отсутствие Workspace для чисто аналитического RUN). Зафиксировать устойчивый workspace_ref, доступные корни/репозиторий/рабочую ветку, инструменты и разрешения. Конкретные пути разрешаются существующим реестром, не хардкодятся в переносимом графе.
- Входы/выходы нод передают ссылки на разрешённые файлы, артефакты, версии, контекст и evidence. Подключённая линия не даёт автоматически доступа ко всему проекту. Пользователь может настраивать scope нод; дочерний блок не расширяет права родительского RUN.
- Визуально различить управляющие связи (exec/event), данные (text/JSON/context/artifact) и ресурсы/Workspace references. Решить, будет ли Workspace входным пином, настройкой запуска или отдельной ресурсной нодой. Это открытый вопрос П1/П8; не плодить отдельные Workspace на каждый блок по умолчанию.
- Для нескольких агентов определить изоляцию записи, владение файлами, worktree/ветки, координацию блокировок, конфликт изменений и передачу артефактов. Первый сценарий — последовательная работа в одном разрешённом проекте; параллельная запись отдельным этапом.
- Связать результат тестов с точной версией артефакта/коммита и тем же RUN/Workspace. Сохранять lineage и переходы в существующей истории, чтобы после рестарта можно было продолжить без потери контекста и без смешения чужих задач.

| П1 | Контракт ноды, типов пинов, снимка политики, внешнего event/reference, статусов и Workspace-привязки; миграция схем. |
| П4 | Сохранение и восстановление ожидающего RUN, один владелец переходов; серверное ожидание переживает закрытие UI и рестарт. |

| П8 | Агентские среды и реальные инструменты Workspace; первый согласованный сценарий CI в графе, безопасная передача состояния между нодами. |

Сначала OFFLINE: фальшивые часы и имитатор CI (QUEUED/RUNNING → PASS или FAIL), без реальной задержки 10 минут. Проверки: один успешный переход и один цикл исправления; неверный SHA/run_id/attempt, неполный набор jobs, повторное событие, гонка event/poll, ошибка сети, таймаут, отмена, рестарт в WAITING и на границе RESUME, запрет повторного запуска теста, отозванное разрешение, чужой Workspace, независимость двух RUN, сохранение evidence и бюджета. В UI — настройка и соединение ноды, статусы, ручная отмена, восстановление. Реальный GitHub Actions и действия агента в файлах — после соответствующего допуска, отдельная TASK и проверка. На этом этапе ничего не реализовано и не принято.
