# Рабочая микро-память Ultra — концепт

**Статус:** КОНЦЕПТ / НЕ РЕАЛИЗОВАНО.

RUN MICROCONTEXT, RUN BRIEF и RUN CHECKPOINT в текущем runtime отсутствуют. Концепт возник из наблюдений за Ultra, но архитектурно RUN BRIEF / RUN CHECKPOINT / SERVER FACTS относятся к Agent Runtime и конкретному RUN, а не обязаны принадлежать одной физической модели.

Стабилизация Ultra: проблема и предлагаемая архитектура

Ultra достаточно сильна для выполнения сложных задач, но у неё наблюдается проблема не столько с интеллектом, сколько с дисциплиной исполнения и удержанием собственного рабочего состояния внутри длинного RUN.

Она может хорошо понять задачу в начале, затем выполнить несколько правильных действий, после чего постепенно потерять часть исходных ограничений или начать опираться на собственные предположения вместо уже полученных фактов. Из-за этого появляются самопротиворечия: модель может не прочитать файл, но в конце написать, что проверила его; не выполнить write_file, но описать изменения как сделанные; продолжить работу после ошибки, не переосмыслив причину; несколько раз возвращаться к неверному пути; смешивать известное из старого контекста с тем, что действительно было проверено в текущем RUN.

При этом простое добавление всё более длинных инструкций в Global Context проблему полностью не решает. Чем длиннее RUN, тем больше вероятность, что конкретная рабочая цель и детали исполнения растворятся среди истории, документации, результатов инструментов и системных сообщений.

Поэтому систему стоит строить не только как набор запретов вокруг Ultra, но и как внешнюю опору для её собственного мышления.

1. RUN Microcontext / рабочий конспект задачи

Перед началом использования инструментов Ultra должна сама сформировать короткий структурированный конспект текущего RUN.

Не сервер придумывает за неё решение — сама Ultra перечитывает пользовательскую TASK и формулирует, что она собирается делать.

Примерное содержание такого микроконтекста:

RUN GOAL
Что пользователь хочет получить.

EXPECTED RESULT
Какие реальные изменения или результат должны существовать к концу RUN.

IMPORTANT CONSTRAINTS
Что нельзя менять.
Какие файлы/области разрешены.
Какие требования пользователя нельзя потерять.

REQUIRED EVIDENCE
Что необходимо реально прочитать/проверить до выводов.

PLAN
Короткие 3–7 шагов выполнения.

COMPLETION CONDITIONS
По каким фактам задача действительно считается выполненной.

KNOWN BLOCKERS
Что сейчас мешает выполнению, если уже известно.

Этот текст не должен существовать только «в голове» модели.

Сервер сохраняет его как RUN-local state. Он относится только к конкретному run_id, не является Project Context, не становится постоянной памятью проекта и после завершения RUN больше не используется.

По сути это короткая внешняя память самой Ultra.

2. Ultra должна возвращаться к микроконтексту

Создать конспект один раз недостаточно. Его смысл именно в том, чтобы сервер мог в нужный момент снова показать его модели.

Возврат к нему особенно полезен:

после ошибки инструмента;
после GUARD intervention;
после отказа или выдачи permission;
после нескольких неудачных действий;
когда модель начинает повторяться;
перед существенной записью;
перед попыткой завершить RUN.

Тогда вместо продолжения «по инерции» Ultra получает примерно такой сигнал:

Ты столкнулась с проблемой.

Вернись к рабочему конспекту этого RUN.
Сверь:
- исходную цель;
- ограничения;
- уже подтверждённые факты;
- текущий этап плана.

После этого выбери следующий осмысленный шаг.

Это очень важно: не обязательно каждый раз заставлять её создавать новый план. Сначала она перечитывает свой первоначальный рабочий конспект.

Если ситуация действительно изменилась, она может сформировать отдельный короткий RUN CHECKPOINT или RECOVERY NOTE, не уничтожая исходную цель.

Получается две сущности:

RUN BRIEF
исходное понимание задачи — относительно стабильное

RUN CHECKPOINT
текущее состояние выполнения — может обновляться

Так модель гораздо сложнее сама себе незаметно поменяет задачу посередине RUN.

3. Сервер хранит собственные факты отдельно от мыслей Ultra

Микроконтекст Ultra — это её понимание задачи.

Но существует второй слой — Server Facts.

Это уже объективная информация:

что реально прочитано;
какие tools реально вызывались;
какие tools завершились успешно;
какие вызовы завершились ошибкой;
какие write/delete реально выполнены;
какие файлы реально изменены;
какие permissions действуют;
какие permissions были отклонены;
какие verification checks выполнены;
сколько tools осталось.

Ultra не должна иметь возможности переписывать эти факты своим текстом.

Таким образом:

RUN BRIEF
= что Ultra собирается сделать

SERVER FACTS
= что реально произошло

И именно сочетание этих двух вещей даёт нормальный контроль.

4. Final Report должен строиться поверх Server Facts

Одна из главных текущих проблем Ultra — финальный отчёт иногда отражает не реальные действия, а то, что модель считает, что она сделала.

Перед финальным ответом сервер должен дать ей короткий factual snapshot, например:

SERVER FACTS FOR FINAL REPORT

READ SUCCESS:
- server.py
- workspace_runtime_settings.py

NOT READ:
- ultra_ui.py

WRITE SUCCESS:
- Документация/08_Старт.md

DELETE SUCCESS:
- none

VERIFY:
- git_diff: success
- git_status: success

И явно сказать:

Не заявляй действие как выполненное,
если оно отсутствует среди подтверждённых Server Facts.

Тогда финальный отчёт становится интерпретацией фактов, а не источником фактов.

5. Если RUN не может завершиться — Ultra должна объяснить причину

Если сервер видит, что условия завершения не выполнены, нельзя просто бесконечно возвращать Ultra обратно в цикл.

После ограниченного числа попыток должен срабатывать controlled stop.

Но непосредственно перед окончательной блокировкой Ultra полезно заставить сформировать короткое объяснение:

На каком этапе ты остановилась?

Что реально успела выполнить?

Что осталось невыполненным?

Какой конкретный blocker помешал?

Почему следующий необходимый шаг не был выполнен?

При этом сервер снова передаёт ей реальные факты.

В результате вместо фантастического:

«STATUS OK, всё выполнено»

мы получаем:

«Документы были прочитаны, но запись не выполнялась, потому что WRITE был недоступен. Файл не изменён.»

А RUN получает состояние не SUCCESS, а, например, BLOCKED.

6. Контекстные сообщения сервера должны быть масштабируемыми

Все такие обращения сервера к модели не стоит навечно зашивать текстом в server.py.

Нужен универсальный справочник контекстных сообщений с event_id.

Например:

guard.repeat
verification.required
permission.denied
tool.error
tool_budget.low
run.blocked.explanation_required
final_report.facts
run_context.review_required

Но Python по-прежнему определяет сам факт события.

То есть код решает:

произошёл guard.repeat

а справочник определяет:

как именно объяснить Ultra,
что сейчас произошло.

Самое важное — масштабируемость.

UI не должен содержать вручную прописанный список этих событий. Он должен быть generic.

В коде появляется новый event_id — UI способен показать его автоматически. Никаких новых кнопок и if event_id == ... добавлять не требуется.

При этом пользователь может заранее создать запись для ещё не существующего события.

Тогда UI показывает два состояния:

● ACTIVE
такой event_id реально зарегистрирован текущим runtime-кодом

○ DRAFT
текст существует в справочнике, но текущий runtime такой event_id пока не использует

Когда в будущем код начинает использовать этот event_id, после запуска приложения запись автоматически становится ACTIVE.

Это позволяет нам заранее готовить тексты, не выдавая будущую функцию за уже реализованную.

7. Общая модель в итоге

Получается довольно сильная схема:

USER TASK
    ↓
ULTRA СОЗДАЁТ RUN BRIEF
    ↓
SERVER СОХРАНЯЕТ RUN MICROCONTEXT
    ↓
ULTRA РАБОТАЕТ ИНСТРУМЕНТАМИ
    ↓
SERVER ВЕДЁТ ОБЪЕКТИВНЫЙ FACT LEDGER
    ↓
ошибка / guard / blocker
    ↓
SERVER ВОЗВРАЩАЕТ ULTRA К RUN BRIEF
+ ДОБАВЛЯЕТ АКТУАЛЬНЫЕ SERVER FACTS
    ↓
ULTRA ПЕРЕОСМЫСЛЯЕТ СЛЕДУЮЩИЙ ШАГ
    ↓
перед завершением
    ↓
FINAL REPORT FACTS
    ↓
либо SUCCESS
либо BLOCKED + объяснение причины

И мне здесь особенно нравится одна вещь: мы перестаём пытаться решить проблему только способом «ещё сильнее ограничить Ultra».

У неё остаётся свобода рассуждать и выбирать способ решения. Но мы даём ей внешнюю память о её же собственном плане и внешний независимый источник правды о том, что реально произошло.

То есть условно:

не клетка для Ultra, а поручни для Ultra.

А уже вокруг этих поручней остаются наши физические заборы: permissions, scopes, backup, GUARD P1, Verification Gate, tool limit.
