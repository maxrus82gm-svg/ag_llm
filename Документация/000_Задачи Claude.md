## 6. Порядок инженерной работы

- итогового физического места записи;
    
- запусков напрямую и через `wa4a_acceptance.py`.
    

Сравнить поведение прямого локального запуска и вложенного guarded runner, насколько позволяют доступные инструменты.

Отдельно доказать, какая именно операция была разрешена и куда фактически могла записывать.

Воспроизвести проблему сначала без изменения production/harness. Сохранить RED.

### Фаза B. Минимальное исправление

После доказательства причины выбрать наименьшее безопасное изменение.

Использовать уже имеющийся механизм guard, а не создавать вторую независимую реализацию проверки путей.

Не расширять глобально разрешённую область до произвольного внешнего TEMP ради зелёных тестов.

Если тесту действительно требуются собственный внутренний корень и внешние негативные fixtures, их границы должны быть явно определены, а проверка должна реально отличать допустимую запись от запрещённой.

Сохранить запрет на:

- запись за разрешённый корень;
    
- обход через `..`, смешанные разделители и регистр;
    
- junction/reparse escapes;
    
- исходящие `replace`/`mkdir`;
    
- запрещённые `.git`-обращения;
    
- опасные пути с `\\?\` и `$Extend\$Deleted`;
    
- неразрешённые сеть, Git, процессы и системные изменения.
    

**Проверка должна выявлять реальное нарушение, а не просто возвращать ожидаемый текст.**

### Фаза C. Тесты и негативные проверки

Обязательные доказательства:

1. Сохранённый исходный RED на неисправной конфигурации.
    
2. GREEN после минимального исправления.
    
3. Изолированный прямой запуск шести guard-тестов.
    
4. Тот же модуль через настоящий guarded runner.
    
5. Все исходные восемь запретных операций реально блокируются.
    
6. Проверен сам факт отсутствия побочных записей, а не только исключение.
    
7. Положительные операции внутри своего TEMP продолжают работать.
    
8. Проверена вложенная модель TEMP, воспроизводящая CI.
    
9. Есть отрицательный контроль/мутант, доказывающий, что oracle ловит отключённую или неправильно выбранную защиту.
    

Дополнительно проверить заявленную гонку F-T1 без чрезмерных повторов; не считать случайный зелёный результат её доказанным устранением.

Если локальная среда Windows не воспроизводит CI, не подгонять тесты до искусственного PASS. Сдать доказательства и указать `ENVIRONMENT / INCONCLUSIVE / BLOCKED` либо другую подтверждённую классификацию.

### Фаза D. Регрессия

После адресных тестов выполнить необходимые проверки взаимодействующих модулей и безопасности, в том числе Archive Retry, чтобы изменение guard не нарушило предыдущую реализацию.

При доступных времени и ресурсах — один полный guarded regression Web Alarm. Если он не выполнен, явно написать `FULL NOT RUN`, причину и точный предлагаемый независимый gate.

Не запускать бессмысленные длительные серии без новой проверяемой гипотезы.

Независимый Windows GitHub Actions запуск после пользовательской публикации организует ChatGPT. Агенту не нужно и не разрешено запускать GitHub CI.

## 7. Безопасность и запреты

- Только изолированные, одноразовые тестовые каталоги.

## 10. Критерии сдачи

**BLOCKED:** нет необходимой среды, возможности безопасного воспроизведения или требуется изменение вне scope.

**FAIL:** отрицательные проверки обнаруживают неустранённую опасную ошибку.
