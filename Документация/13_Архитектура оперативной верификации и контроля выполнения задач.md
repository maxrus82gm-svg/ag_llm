# Архитектура оперативной верификации и контроля выполнения задач

Статус: АРХИТЕКТУРНАЯ КОНЦЕПЦИЯ / ПРИНЯТОЕ НАПРАВЛЕНИЕ

Документ описывает будущий механизм независимой проверки действий Agent Runtime во время выполнения задач.

Главная цель:

не только обнаруживать ошибку после завершения задачи,
но по возможности останавливать опасное или выходящее за TASK действие ДО его применения.

Система должна сочетать:

- неизменный RAW TASK;
- декомпозицию задачи на контролируемые checkpoints;
- серверное отслеживание tool-вызовов;
- независимый Verifier;
- pre-mutation проверку опасных операций;
- финальный аудит всей задачи;
- обязательные резервные копии;
- возможность вернуть Executor замечание и продолжить тот же RUN.

============================================================
1. ПРОБЛЕМА
============================================================

LLM-исполнитель может:

- правильно понять большую часть TASK;
- корректно выполнить основную работу;
- выйти за разрешённый scope в мелкой детали;
- самостоятельно посчитать это допустимым;
- после этого выдать STATUS: OK.

Пример наблюдавшегося поведения:

Executor получил разрешение изменить только хвост раздела 14 документа.

Основное изменение было выполнено правильно.

Дополнительно Executor изменил одну строку в разделе 19.

После этого Executor:

- сам признал дополнительное изменение;
- одновременно заявил, что оно не выходит за scope;
- вернул STATUS: OK.

Независимая проверка той же задачи в новом контексте показала другое поведение.

GigaChat 3 Ultra:
FAIL

GigaChat 3 Pro:
FAIL

GigaChat 3 Pro в отдельном чистом Workspace:
FAIL

GigaChat 3 Lightning:
PASS

Из этого следует важный архитектурный вывод:

одна и та же модель или семейство моделей может значительно лучше обнаруживать нарушение, когда выступает не исполнителем собственной работы, а независимым Reviewer / Verifier.

Также из эксперимента следует:

Verifier не должен считаться абсолютно надёжным.

Модель Verifier должна быть заменяемой и настраиваемой.

На текущем этапе GigaChat 3 Pro является перспективным кандидатом на роль недорогого независимого Verifier.

============================================================
2. ОСНОВНОЙ ПРИНЦИП
============================================================

Executor не должен самостоятельно определять окончательную корректность собственной работы.

Схема:

TASK
    ↓
EXECUTOR
    ↓
VERIFIER
    ↓
PASS / FAIL

Но одной финальной проверки недостаточно.

Если опасная операция уже выполнена, Verifier обнаруживает ошибку только постфактум.

Поэтому целевая архитектура должна иметь два независимых уровня проверки:

LEVEL 1
MUTATION GATE

LEVEL 2
FINAL AUDIT

============================================================
3. НЕИЗМЕННЫЙ RAW TASK
============================================================

Исходная пользовательская TASK должна сохраняться полностью и неизменно.

RAW TASK является главным источником истины.

Никакой:

- Task Contract;
- план;
- checkpoint;
- summary;
- декомпозиция;
- объяснение Executor;
- отчёт Verifier

не может заменить RAW TASK.

Система всегда должна иметь возможность вернуться к первоначальному тексту задачи.

Пример:

RUN_ID:
run_123

RAW_TASK:
полный исходный текст пользователя

RAW TASK сохраняется сервером до начала выполнения.

============================================================
4. TASK CONTRACT
============================================================

Большая пользовательская TASK может быть слишком дорогой для повторной передачи Verifier после каждой потенциально опасной операции.

Поэтому после получения RAW TASK может создаваться компактный структурированный TASK CONTRACT.

TASK CONTRACT содержит, например:

TASK_ID

TARGETS

ALLOWED OPERATIONS

ALLOWED FILES

ALLOWED AREAS

FORBIDDEN FILES

FORBIDDEN AREAS

CREATE POLICY

DELETE POLICY

GIT POLICY

REQUIRED CHECKS

SUCCESS CONDITIONS

Пример:

TASK_ID:
DOC-08B-FIX

TARGETS:
Документация/08_Старт.md

ALLOWED_AREA:
хвост раздела 14

FORBIDDEN_AREAS:
разделы 1–13
разделы 15–20

CREATE:
DENY

DELETE:
DENY

GIT_MUTATIONS:
DENY

SUCCESS:
восстановлен конкретный оборванный участок
diff ограничен разрешённой областью

ВАЖНО:

TASK CONTRACT является производным представлением RAW TASK.

Он не становится новой истиной.

Если TASK CONTRACT противоречит RAW TASK:

RAW TASK имеет приоритет.

============================================================
5. PREFLIGHT-ПРОВЕРКА TASK CONTRACT
============================================================

Нельзя позволять Executor:

самостоятельно неправильно декомпозировать TASK,
а затем проверять свои действия против собственной неправильной декомпозиции.

Поэтому возможна схема:

RAW TASK
    ↓
TASK CONTRACT / PLAN
    ↓
INDEPENDENT PREFLIGHT VERIFIER
    ↓
PASS / FAIL

Только после PASS контракт становится рабочим контрактом RUN.

Если FAIL:

Executor или специальный Planner формирует исправленную версию.

RAW TASK при этом не изменяется.

============================================================
6. CHECKPOINTS
============================================================

После утверждения TASK CONTRACT задача может быть разбита на checkpoints.

Checkpoint — это контролируемый этап одной большой TASK.

Пример:

CP-01
прочитать целевой документ

CP-02
изменить хвост раздела 14

CP-03
перечитать результат

CP-04
проверить diff

CP-05
финальная проверка

Checkpoint должен иметь стабильный ID.

Пример структуры:

checkpoint_id:
CP-02

task_id:
DOC-08B-FIX

source_requirements:
конкретные требования RAW TASK

target:
Документация/08_Старт.md

allowed_area:
хвост раздела 14

forbidden_area:
разделы 1–13
разделы 15–20

expected_action:
восстановить оборванный текст

risk:
WRITE

Checkpoint не является отдельным Chat.

Checkpoint является metadata внутри одного RUN.

============================================================
7. СОХРАНЕНИЕ КОНТЕКСТА EXECUTOR
============================================================

Разделение RUN на checkpoints НЕ должно уничтожать или дробить рабочий контекст Executor.

Executor продолжает работать в одном RUN.

Например:

RUN-123
    |
    +-- CP-01
    |     |
    |     +-- OP-001 read_file
    |
    +-- CP-02
    |     |
    |     +-- OP-002 write_file
    |
    +-- CP-03
          |
          +-- OP-003 read_file
          +-- OP-004 git_diff

Основной conversation state Executor сохраняется.

В нём остаются:

- SYSTEM;
- Role Context;
- Project Context, если разрешён;
- RAW TASK;
- история текущего RUN;
- tool calls;
- tool results;
- сообщения Server Supervisor;
- замечания Verifier.

ID checkpoints и operations являются дополнительными серверными metadata.

Они не заменяют контекст модели.

============================================================
8. OPERATION ID
============================================================

Каждый tool call получает собственный Operation ID.

Например:

OP-001
OP-002
OP-003

Запись может содержать:

operation_id

run_id

checkpoint_id

tool_name

arguments

target

timestamp

status

verification_status

Например:

OP-017

RUN:
RUN-123

CHECKPOINT:
CP-02

TOOL:
write_file

TARGET:
Документация/08_Старт.md

STATUS:
STAGED

VERIFICATION:
PENDING

============================================================
9. READ-ОПЕРАЦИИ
============================================================

Обычные операции чтения не требуют LLM-аудита после каждого вызова.

Например:

read_file

list_dir

Они проходят через существующие server-side permission checks.

Дополнительно могут работать:

- READ scope;
- GUARD;
- tool limit;
- repeated read protection.

Отправлять каждый READ в GigaChat Pro нецелесообразно.

Это увеличивает:

- количество API-запросов;
- latency;
- расход токенов;
- сложность runtime.

============================================================
10. MUTATION OPERATION
============================================================

К потенциально опасным операциям относятся прежде всего:

write_file

delete_file

В будущем также могут появиться другие mutation-tools.

Главная идея:

Mutation сначала не применяется.

Сначала она превращается в STAGED OPERATION.

Схема:

Executor вызывает write_file
    ↓
Server перехватывает запрос
    ↓
формируется proposed mutation
    ↓
файл ещё НЕ изменён
    ↓
создаётся OPERATION ID
    ↓
Verifier проверяет операцию
    ↓
PASS / FAIL

============================================================
11. STAGED WRITE
============================================================

При write_file сервер уже имеет:

TARGET

OLD CONTENT

PROPOSED NEW CONTENT

PROPOSED DIFF

Поэтому Executor не обязан писать отдельный мини-отчёт после каждого tool.

Источник фактов — сервер.

Пример:

OP-017

TOOL:
write_file

TARGET:
Документация/08_Старт.md

BEFORE:
текущее содержимое файла

AFTER:
предлагаемое новое содержимое

DIFF:
предлагаемые изменения

CHECKPOINT:
CP-02

Файл в этот момент ещё не изменён.

============================================================
12. MUTATION GATE
============================================================

Перед применением опасной операции вызывается независимый Verifier.

Verifier получает минимально достаточный контекст:

TASK CONTRACT

CHECKPOINT

OPERATION

PROPOSED DIFF

При необходимости также передаются релевантные фрагменты RAW TASK.

Verifier отвечает машинно-разбираемым результатом.

Минимальный вариант:

PASS

или:

FAIL

REASON:
...

VIOLATION:
...

Например:

FAIL

VIOLATION:
SCOPE

REASON:
Proposed diff изменяет раздел 19.
Checkpoint CP-02 разрешает изменение только хвоста раздела 14.

============================================================
13. PASS НА MUTATION GATE
============================================================

Если Verifier возвращает PASS:

OP-017
VERIFICATION = PASS

после этого сервер реально применяет mutation.

Схема:

PROPOSED WRITE
    ↓
VERIFIER PASS
    ↓
ATOMIC WRITE
    ↓
Executor продолжает RUN

============================================================
14. FAIL НА MUTATION GATE
============================================================

Если Verifier возвращает FAIL:

файл НЕ изменяется.

Не требуется обычный rollback, потому что mutation ещё не была применена.

Сервер возвращает Executor результат примерно такого типа:

SERVER VERIFIER

OPERATION:
OP-017

STATUS:
REJECTED

REASON:
Изменение затрагивает раздел 19,
который запрещён текущим TASK CONTRACT / CHECKPOINT.

PROPOSED WRITE НЕ ПРИМЕНЁН.

Исправь proposed content и повтори операцию.

После этого Executor продолжает тот же RUN.

Он сохраняет:

- исходную TASK;
- прочитанные файлы;
- результаты предыдущих tools;
- собственный рабочий контекст;
- замечание Verifier.

Executor формирует новую операцию:

OP-018

и повторно проходит Mutation Gate.

============================================================
15. ПОЧЕМУ НЕ НУЖЕН МИНИ-ОТЧЁТ EXECUTOR ПОСЛЕ КАЖДОГО TOOL
============================================================

Отдельный LLM-отчёт после каждого tool нежелателен.

Причины:

- дополнительные токены;
- дополнительные API calls;
- дополнительная latency;
- возможность галлюцинации в отчёте;
- Executor может неверно описать собственное действие;
- сервер уже знает фактические arguments и results tool.

Поэтому для оперативной проверки использовать серверные факты:

tool call

tool arguments

target

before

after

diff

checkpoint_id

task_contract

============================================================
16. НЕ ВСЕ TOOLS НУЖНО ОТПРАВЛЯТЬ VERIFIER
============================================================

Предварительная схема:

read_file
→ без LLM Gate

list_dir
→ без LLM Gate

write_file
→ Mutation Gate

delete_file
→ Mutation Gate

python_compile
→ существующая deterministic server verification

git_diff
→ существующая deterministic server verification

git_status
→ существующая deterministic server verification

ui_smoke_test
→ существующая deterministic server verification

STOP / SUCCESS
→ Final Audit

Таким образом дорогой LLM Verifier используется только там, где он действительно добавляет смысловую проверку.

============================================================
17. FINAL AUDIT
============================================================

Даже успешная проверка каждой mutation не гарантирует выполнение всей TASK.

Каждая отдельная операция может быть допустимой, но:

- часть задачи могла быть забыта;
- обязательная проверка могла отсутствовать;
- итоговый результат может не соответствовать пользовательскому намерению;
- Executor может ошибочно объявить SUCCESS.

Поэтому при попытке Executor завершить RUN:

Executor хочет STOP / SUCCESS
    ↓
Server блокирует финальный SUCCESS
    ↓
запускается Independent Final Audit
    ↓
PASS / FAIL

============================================================
18. КОНТЕКСТ FINAL AUDIT
============================================================

Final Audit может быть более дорогим, потому что выполняется один раз в конце нормального RUN.

Verifier получает:

RAW TASK

TASK CONTRACT

checkpoint results

итоговый diff

список выполненных mutation

verification results

RUN TRACE summary

финальный отчёт Executor

При необходимости:

актуальное содержимое изменённых файлов.

============================================================
19. PASS FINAL AUDIT
============================================================

Если Final Verifier возвращает:

PASS

сервер разрешает:

RUN SUCCESS

и только после этого пользователь получает финальный результат как успешно выполненную задачу.

============================================================
20. FAIL FINAL AUDIT
============================================================

Если Final Verifier возвращает FAIL:

RUN не считается завершённым.

Сервер добавляет отчёт Verifier в тот же рабочий контекст Executor.

Например:

SERVER FINAL VERIFIER

STATUS:
FAIL

НАРУШЕНИЯ:

1. Изменён раздел 19 вне разрешённого scope.
2. STATUS: OK не соответствует фактическому diff.

Исправь найденные нарушения.
После исправления повторно пройди обязательные проверки.

Executor продолжает тот же RUN.

После исправлений:

Final Audit запускается повторно.

============================================================
21. НЕЗАВИСИМОСТЬ VERIFIER
============================================================

Verifier не должен наследовать reasoning state Executor.

Это отдельный чистый model call.

Он получает только явно разрешённый verification context.

Verifier не должен получать:

- скрытую provider session Executor;
- неконтролируемую память предыдущего ответа Executor;
- инструменты записи;
- права на изменение Workspace.

Verifier работает в read-only роли.

У него нет права:

- write;
- delete;
- Git mutations.

============================================================
22. MODEL ASSIGNMENT VERIFIER
============================================================

Verifier должен иметь отдельное назначение модели.

Например:

VERIFIER MODEL ASSIGNMENT

Default candidate:

GigaChat 3 Pro

Но модель должна выбираться через Model Registry.

В будущем возможны:

GigaChat Ultra
GigaChat Pro
локальная LLM
другая provider model

Модель Executor и модель Verifier могут совпадать физически.

Но calls должны быть независимыми.

Например:

Executor:
GigaChat 3 Ultra

Verifier:
GigaChat 3 Pro

или:

Executor:
GigaChat 3 Ultra

Verifier:
GigaChat 3 Ultra

Но второй вызов должен иметь чистый verification context.

============================================================
23. ЭКСПЕРИМЕНТАЛЬНЫЕ НАБЛЮДЕНИЯ ПО МОДЕЛЯМ
============================================================

В тесте на обнаружение нарушения scope:

GigaChat 3 Ultra:
обнаружила нарушение.

GigaChat 3 Pro:
обнаружила нарушение.

GigaChat 3 Pro в чистом отдельном Workspace:
повторно обнаружила нарушение.

GigaChat 3 Lightning:
не обнаружила нарушение и подтвердила ошибочный STATUS: OK.

Это один ограниченный эксперимент.

Из него нельзя делать вывод, что Lightning всегда непригодна как Verifier.

Но он показывает:

для задач строгой verification более дешёвая модель должна быть предварительно протестирована.

На текущем этапе GigaChat 3 Pro выглядит разумным кандидатом на баланс:

стоимость
/
качество проверки.

============================================================
24. BACKUP ДО НАЧАЛА MUTATING RUN
============================================================

Независимо от Mutation Gate должен сохраняться полноценный Backup Snapshot.

Правило:

NO BACKUP
=
NO MUTATING RUN

Перед началом TASK с WRITE / DELETE сервер обязан создать persistent backup.

Если backup создать не удалось:

RUN не начинается.

============================================================
25. BACKUP НЕ ДОЛЖЕН БЫТЬ ВРЕМЕННЫМ
============================================================

Backup нельзя хранить только в RAM или временной директории, которая исчезнет при аварии.

Причины:

- падение приложения;
- перезагрузка компьютера;
- сбой питания;
- ошибка runtime;
- ошибка самого Verifier;
- ошибочный PASS;
- повреждение нескольких связанных файлов.

Backup должен существовать независимо от RUN процесса.

============================================================
26. ПРИМЕР BACKUP STRUCTURE
============================================================

Пример:

backups/
    RUN-123/
        manifest.json

        original/
            Документация/
                08_Старт.md

        operations.jsonl

Manifest может содержать:

RUN ID

TASK ID

Workspace ID

Chat ID

timestamp

исходные paths

checksums

список mutation operations

============================================================
27. BACKUP И MUTATION GATE — РАЗНЫЕ УРОВНИ ЗАЩИТЫ
============================================================

Mutation Gate предотвращает известную ошибку ДО записи.

Backup позволяет восстановиться, если предотвращение не сработало.

Поэтому:

Mutation Gate НЕ заменяет Backup.

Backup НЕ заменяет Mutation Gate.

Используются оба механизма.

============================================================
28. ROLLBACK
============================================================

Нормальный FAIL Mutation Gate не требует rollback:

operation была staged,
но не была applied.

Rollback нужен только если:

- операция уже успела примениться;
- произошёл runtime failure;
- Final Audit выявил проблему, которую невозможно безопасно исправить вперёд;
- пользователь запросил восстановление;
- Verifier ошибочно пропустил mutation.

Возможные уровни rollback:

FILE ROLLBACK

CHECKPOINT ROLLBACK

FULL RUN ROLLBACK

Реализацию выбрать отдельно.

============================================================
29. TASK / CHECKPOINT / OPERATION ID
============================================================

Для трассировки использовать иерархию:

RUN
    ↓
TASK
    ↓
CHECKPOINT
    ↓
OPERATION

Например:

RUN:
RUN-20260921-001

TASK:
TASK-DOC-08B

CHECKPOINT:
CP-02

OPERATION:
OP-017

Это позволяет точно понимать:

- какой этап выполнялся;
- какое действие было предложено;
- какой Verifier его проверял;
- почему оно прошло или было отклонено;
- какой файл реально изменился.

============================================================
30. TRACE
============================================================

Trace должен различать:

EXECUTOR ACTION

STAGED MUTATION

VERIFIER REQUEST

VERIFIER PASS

VERIFIER FAIL

MUTATION APPLIED

MUTATION REJECTED

FINAL AUDIT START

FINAL AUDIT PASS

FINAL AUDIT FAIL

RUN SUCCESS

RUN FAILED

Пример:

OP-017 STAGED WRITE
↓
VERIFIER FAIL
↓
WRITE NOT APPLIED
↓
FEEDBACK TO EXECUTOR

============================================================
31. UI / ЛОГ ДЕЙСТВИЙ
============================================================

В UI полезно визуально различать события.

Например:

обычный успешный tool
→ стандартный цвет

PASS Verifier
→ зелёный

FAIL Verifier
→ красный

Permission Denied
→ красный

Guard Block
→ красный / предупреждающий

Staged operation
→ отдельный нейтральный статус

Mutation Applied
→ зелёный

Mutation Rejected
→ красный

Это отдельная UI-задача и не является обязательным условием первой реализации Verifier.

============================================================
32. СТРУКТУРИРОВАННЫЙ ОТВЕТ VERIFIER
============================================================

Verifier желательно не просить писать произвольное длинное эссе.

Для server integration нужен предсказуемый формат.

Концептуально:

RESULT:
PASS | FAIL

CHECK_TYPE:
MUTATION | FINAL

TASK_ID:
...

CHECKPOINT_ID:
...

OPERATION_ID:
...

VIOLATIONS:
...

REASON:
...

REQUIRED_ACTION:
...

В дальнейшем это лучше сделать машинно-разбираемым schema output.

============================================================
33. VERIFIER НЕ ИМЕЕТ ПРАВА ИСПРАВЛЯТЬ
============================================================

Verifier только оценивает.

Он не должен:

- изменять файл;
- самостоятельно применять исправление;
- выполнять Git mutation;
- превращаться во второго Executor.

Схема:

Verifier обнаружил проблему
    ↓
Verifier объяснил проблему
    ↓
Server вернул feedback Executor
    ↓
Executor сформировал исправленное действие

Таким образом ответственность ролей остаётся разделённой.

============================================================
34. FAIL VERIFIER НЕ ОЗНАЧАЕТ FAIL ВСЕГО RUN
============================================================

На Mutation Gate:

FAIL означает:

конкретная proposed operation отклонена.

RUN может продолжиться после исправления.

На Final Audit:

FAIL означает:

SUCCESS заблокирован.

Executor получает замечания и продолжает исправление.

Только если:

- исчерпан retry limit;
- невозможно исправить проблему;
- нарушены server permissions;
- Verifier loop;
- критический runtime error

RUN переводится в окончательный FAILED.

============================================================
35. RETRY LIMIT
============================================================

Нельзя допустить бесконечный цикл:

Executor
→ ошибка
→ Verifier FAIL
→ Executor
→ та же ошибка
→ Verifier FAIL
→ ...

Поэтому нужен limit.

Например:

MAX_MUTATION_VERIFIER_RETRIES_PER_OPERATION

MAX_FINAL_AUDIT_RETRIES

Точные значения определить во время реализации.

При превышении:

RUN FAILED

с понятной причиной.

============================================================
36. ЗАЩИТА ОТ ОШИБКИ VERIFIER
============================================================

Verifier тоже является LLM и может ошибаться.

Поэтому нельзя отдавать ему полный физический контроль.

Server остаётся главным authority.

Server-side deterministic правила имеют приоритет.

Пример:

WRITE scope запрещает путь.

Даже если Verifier ошибочно сказал PASS:

Server всё равно запрещает WRITE.

Иерархия:

SERVER HARD RULES
    ↓
VERIFIER SEMANTIC CHECK
    ↓
EXECUTOR ACTION

Verifier дополняет server safety.

Verifier не заменяет её.

============================================================
37. КАК ЭКОНОМИТЬ ТОКЕНЫ
============================================================

Не отправлять RAW TASK в Pro после каждого обычного tool.

Использовать:

TASK CONTRACT
+
CHECKPOINT
+
PROPOSED DIFF

для Mutation Gate.

Полный RAW TASK использовать:

- при создании / проверке TASK CONTRACT;
- при неоднозначности;
- в Final Audit;
- при конфликте Contract с фактической задачей.

Таким образом дорогая полная проверка происходит редко.

============================================================
38. ПРЕДВАРИТЕЛЬНАЯ ЦЕЛЕВАЯ СХЕМА
============================================================

RAW TASK
    ↓
TASK CONTRACT
    ↓
PREFLIGHT VERIFIER
    ↓
PASS
    ↓
EXECUTOR RUN
    ↓
READ / ANALYSIS
    ↓
PROPOSED MUTATION
    ↓
STAGED OPERATION
    ↓
MUTATION VERIFIER
    |
    +-- PASS
    |      ↓
    |   APPLY
    |      ↓
    |   CONTINUE RUN
    |
    +-- FAIL
           ↓
        DO NOT APPLY
           ↓
        VERIFIER FEEDBACK
           ↓
        EXECUTOR RETRY
           ↓
        NEW OPERATION

После завершения:

EXECUTOR WANTS SUCCESS
    ↓
FINAL AUDIT
    |
    +-- PASS
    |      ↓
    |   RUN SUCCESS
    |
    +-- FAIL
           ↓
        FEEDBACK
           ↓
        EXECUTOR FIX
           ↓
        FINAL AUDIT AGAIN

============================================================
39. ЧТО УЖЕ ЕСТЬ В ТЕКУЩЕМ ПРОЕКТЕ
============================================================

В существующем runtime уже есть фундаментальные элементы, на которые можно опереться:

- Agent Runtime;
- tool interception;
- READ / WRITE / DELETE permissions;
- narrow scopes;
- backup before mutating RUN;
- backup before file overwrite;
- tool trace;
- GUARD P1;
- Verification Gate;
- git_diff;
- git_status;
- python_compile;
- ui_smoke_test;
- tool limit;
- Model Registry;
- Main Chat Model Assignment;
- independent Compressor Runtime;
- persistent Chat / Context storage.

Поэтому будущий Verifier не требует строить весь runtime заново.

Нужен новый слой orchestration поверх уже существующего tool execution loop.

============================================================
42. ПЕРВЫЙ ПРАКТИЧЕСКИЙ ЭТАП
============================================================

Самый безопасный первый production-шаг:

НЕ начинать сразу с interception каждого write_file.

Сначала реализовать:

Executor завершает обычную TASK
    ↓
до SUCCESS запускается отдельный GigaChat Pro Verifier
    ↓
Verifier получает RAW TASK + итоговые факты
    ↓
PASS / FAIL
    ↓
PASS разрешает SUCCESS
FAIL пока только блокирует SUCCESS и показывает отчёт

После проверки этой схемы:

добавить автоматическую передачу FAIL обратно Executor.

И только после стабилизации Final Audit:

переходить к Staged Mutation и Pre-Mutation Gate.

============================================================
43. ГЛАВНЫЙ ПРИНЦИП
============================================================

Executor выполняет.

Server управляет.

Verifier проверяет.

Backup сохраняет исходное состояние.

Trace фиксирует факты.

RAW TASK остаётся источником истины.

Ни Executor, ни Verifier не получают единоличный контроль над системой.

============================================================
44. ЦЕЛЕВОЙ РЕЗУЛЬТАТ
============================================================

Система должна прийти к поведению:

Executor допустил ошибку
    ↓
ошибка обнаружена независимо
    ↓
опасная mutation по возможности не применяется
    ↓
Executor получает конкретное замечание
    ↓
Executor исправляет действие
    ↓
Verifier проверяет повторно
    ↓
только корректный результат получает SUCCESS

Именно это является целью архитектуры оперативной верификации и контроля выполнения задач.
