# Архитектура оперативной верификации и контроля выполнения задач

Статус: ЦЕЛЕВАЯ АРХИТЕКТУРА / V.0–V.4 РЕАЛИЗОВАНЫ

Документ описывает целевую архитектуру независимой проверки действий Agent Runtime и фиксирует фактически реализованный production-слой: Verifier Model Assignment, one-shot clean Verifier Runtime, Independent Final Audit перед SUCCESS и one-shot Final Audit Correction Handoff.

Главная цель:

не только обнаруживать ошибку после завершения задачи,
но по возможности останавливать опасное или выходящее за TASK действие ДО его применения.

Система должна сочетать:

- неизменный RAW TASK;
- декомпозицию задачи на контролируемые checkpoints;
- серверное отслеживание tool-вызовов;
- независимый Verifier;
- pre-mutation проверку опасных операций;
- финальный аудит всей задачи;
- обязательные резервные копии;
- возможность вернуть Executor замечание и продолжить тот же RUN.

============================================================
1. ПРОБЛЕМА
============================================================

LLM-исполнитель может:

- правильно понять большую часть TASK;
- корректно выполнить основную работу;
- выйти за разрешённый scope в мелкой детали;
- самостоятельно посчитать это допустимым;
- после этого выдать STATUS: OK.

Пример наблюдавшегося поведения:

Executor получил разрешение изменить только хвост раздела 14 документа.

Основное изменение было выполнено правильно.

Дополнительно Executor изменил одну строку в разделе 19.

После этого Executor:

- сам признал дополнительное изменение;
- одновременно заявил, что оно не выходит за scope;
- вернул STATUS: OK.

Независимая проверка той же задачи в новом контексте показала другое поведение.

GigaChat 3 Ultra:
FAIL

GigaChat 3 Pro:
FAIL

GigaChat 3 Pro в отдельном чистом Workspace:
FAIL

GigaChat 3 Lightning:
PASS

Из этого следует важный архитектурный вывод:

одна и та же модель или семейство моделей может значительно лучше обнаруживать нарушение, когда выступает не исполнителем собственной работы, а независимым Reviewer / Verifier.

Также из эксперимента следует:

Verifier не должен считаться абсолютно надёжным.

Модель Verifier должна быть заменяемой и настраиваемой.

На текущем этапе GigaChat 3 Pro является перспективным кандидатом на роль недорогого независимого Verifier.

============================================================
2. ОСНОВНОЙ ПРИНЦИП
============================================================

Executor не должен самостоятельно определять окончательную корректность собственной работы.

Схема:

TASK
    ↓
EXECUTOR
    ↓
VERIFIER
    ↓
PASS / FAIL

Но одной финальной проверки недостаточно.

Если опасная операция уже выполнена, Verifier обнаруживает ошибку только постфактум.

Поэтому целевая архитектура должна иметь два независимых уровня проверки:

LEVEL 1
MUTATION GATE

LEVEL 2
FINAL AUDIT

============================================================
3. НЕИЗМЕННЫЙ RAW TASK
============================================================

Исходная пользовательская TASK должна сохраняться полностью и неизменно.

RAW TASK является главным источником истины.

Никакой:

- Task Contract;
- план;
- checkpoint;
- summary;
- декомпозиция;
- объяснение Executor;
- отчёт Verifier

не может заменить RAW TASK.

Система всегда должна иметь возможность вернуться к первоначальному тексту задачи.

Пример:

RUN_ID:
run_123

RAW_TASK:
полный исходный текст пользователя

RAW TASK сохраняется сервером до начала выполнения.

============================================================
4. TASK CONTRACT
============================================================

Большая пользовательская TASK может быть слишком дорогой для повторной передачи Verifier после каждой потенциально опасной операции.

Поэтому после получения RAW TASK может создаваться компактный структурированный TASK CONTRACT.

TASK CONTRACT содержит, например:

TASK_ID

TARGETS

ALLOWED OPERATIONS

ALLOWED FILES

ALLOWED AREAS

FORBIDDEN FILES

FORBIDDEN AREAS

CREATE POLICY

DELETE POLICY

GIT POLICY

REQUIRED CHECKS

SUCCESS CONDITIONS

Пример:

TASK_ID:
DOC-08B-FIX

TARGETS:
Документация/08_Старт.md

ALLOWED_AREA:
хвост раздела 14

FORBIDDEN_AREAS:
разделы 1–13
разделы 15–20

CREATE:
DENY

DELETE:
DENY

GIT_MUTATIONS:
DENY

SUCCESS:
восстановлен конкретный оборванный участок
diff ограничен разрешённой областью

ВАЖНО:

TASK CONTRACT является производным представлением RAW TASK.

Он не становится новой истиной.

Если TASK CONTRACT противоречит RAW TASK:

RAW TASK имеет приоритет.

============================================================
5. PREFLIGHT-ПРОВЕРКА TASK CONTRACT
============================================================

Нельзя позволять Executor:

самостоятельно неправильно декомпозировать TASK,
а затем проверять свои действия против собственной неправильной декомпозиции.

Поэтому возможна схема:

RAW TASK
    ↓
TASK CONTRACT / PLAN
    ↓
INDEPENDENT PREFLIGHT VERIFIER
    ↓
PASS / FAIL

Только после PASS контракт становится рабочим контрактом RUN.

Если FAIL:

Executor или специальный Planner формирует исправленную версию.

RAW TASK при этом не изменяется.

============================================================
6. CHECKPOINTS
============================================================

После утверждения TASK CONTRACT задача может быть разбита на checkpoints.

Checkpoint — это контролируемый этап одной большой TASK.

Пример:

CP-01
прочитать целевой документ

CP-02
изменить хвост раздела 14

CP-03
перечитать результат

CP-04
проверить diff

CP-05
финальная проверка

Checkpoint должен иметь стабильный ID.

Пример структуры:

checkpoint_id:
CP-02

task_id:
DOC-08B-FIX

source_requirements:
конкретные требования RAW TASK

target:
Документация/08_Старт.md

allowed_area:
хвост раздела 14

forbidden_area:
разделы 1–13
разделы 15–20

expected_action:
восстановить оборванный текст

risk:
WRITE

Checkpoint не является отдельным Chat.

Checkpoint является metadata внутри одного RUN.

============================================================
7. СОХРАНЕНИЕ КОНТЕКСТА EXECUTOR
============================================================

Разделение RUN на checkpoints НЕ должно уничтожать или дробить рабочий контекст Executor.

Executor продолжает работать в одном RUN.

Например:

RUN-123
    |
    +-- CP-01
    |     |
    |     +-- OP-001 read_file
    |
    +-- CP-02
    |     |
    |     +-- OP-002 write_file
    |
    +-- CP-03
          |
          +-- OP-003 read_file
          +-- OP-004 git_diff

Основной conversation state Executor сохраняется.

В нём остаются:

- SYSTEM;
- Role Context;
- Project Context, если разрешён;
- RAW TASK;
- история текущего RUN;
- tool calls;
- tool results;
- сообщения Server Supervisor;
- замечания Verifier.

ID checkpoints и operations являются дополнительными серверными metadata.

Они не заменяют контекст модели.

============================================================
8. OPERATION ID
============================================================

Каждый tool call получает собственный Operation ID.

Например:

OP-001
OP-002
OP-003

Запись может содержать:

operation_id

run_id

checkpoint_id

tool_name

arguments

target

timestamp

status

verification_status

Например:

OP-017

RUN:
RUN-123

CHECKPOINT:
CP-02

TOOL:
write_file

TARGET:
Документация/08_Старт.md

STATUS:
STAGED

VERIFICATION:
PENDING

============================================================
9. READ-ОПЕРАЦИИ
============================================================

Обычные операции чтения не требуют LLM-аудита после каждого вызова.

Например:

read_file

list_dir

Они проходят через существующие server-side permission checks.

Дополнительно могут работать:

- READ scope;
- GUARD;
- tool limit;
- repeated read protection.

Отправлять каждый READ в GigaChat Pro нецелесообразно.

Это увеличивает:

- количество API-запросов;
- latency;
- расход токенов;
- сложность runtime.

============================================================
10. MUTATION OPERATION
============================================================

К потенциально опасным операциям относятся прежде всего:

write_file

delete_file

В будущем также могут появиться другие mutation-tools.

Главная идея:

Mutation сначала не применяется.

Сначала она превращается в STAGED OPERATION.

Схема:

Executor вызывает write_file
    ↓
Server перехватывает запрос
    ↓
формируется proposed mutation
    ↓
файл ещё НЕ изменён
    ↓
создаётся OPERATION ID
    ↓
Verifier проверяет операцию
    ↓
PASS / FAIL

============================================================
11. STAGED WRITE
============================================================

При write_file сервер уже имеет:

TARGET

OLD CONTENT

PROPOSED NEW CONTENT

PROPOSED DIFF

Поэтому Executor не обязан писать отдельный мини-отчёт после каждого tool.

Источник фактов — сервер.

Пример:

OP-017

TOOL:
write_file

TARGET:
Документация/08_Старт.md

BEFORE:
текущее содержимое файла

AFTER:
предлагаемое новое содержимое

DIFF:
предлагаемые изменения

CHECKPOINT:
CP-02

Файл в этот момент ещё не изменён.

============================================================
12. MUTATION GATE
============================================================

Перед применением опасной операции вызывается независимый Verifier.

Verifier получает минимально достаточный контекст:

TASK CONTRACT

CHECKPOINT

OPERATION

PROPOSED DIFF

При необходимости также передаются релевантные фрагменты RAW TASK.

Verifier отвечает машинно-разбираемым результатом.

Минимальный вариант:

PASS

или:

FAIL

REASON:
...

VIOLATION:
...

Например:

FAIL

VIOLATION:
SCOPE

REASON:
Proposed diff изменяет раздел 19.
Checkpoint CP-02 разрешает изменение только хвоста раздела 14.

============================================================
13. PASS НА MUTATION GATE
============================================================

Если Verifier возвращает PASS:

OP-017
VERIFICATION = PASS

после этого сервер реально применяет mutation.

Схема:

PROPOSED WRITE
    ↓
VERIFIER PASS
    ↓
ATOMIC WRITE
    ↓
Executor продолжает RUN

============================================================
14. FAIL НА MUTATION GATE
============================================================

Если Verifier возвращает FAIL:

файл НЕ изменяется.

Не требуется обычный rollback, потому что mutation ещё не была применена.

Сервер возвращает Executor результат примерно такого типа:

SERVER VERIFIER

OPERATION:
OP-017

STATUS:
REJECTED

REASON:
Изменение затрагивает раздел 19,
который запрещён текущим TASK CONTRACT / CHECKPOINT.

PROPOSED WRITE НЕ ПРИМЕНЁН.

Исправь proposed content и повтори операцию.

После этого Executor продолжает тот же RUN.

Он сохраняет:

- исходную TASK;
- прочитанные файлы;
- результаты предыдущих tools;
- собственный рабочий контекст;
- замечание Verifier.

Executor формирует новую операцию:

OP-018

и повторно проходит Mutation Gate.

============================================================
15. ПОЧЕМУ НЕ НУЖЕН МИНИ-ОТЧЁТ EXECUTOR ПОСЛЕ КАЖДОГО TOOL
============================================================

Отдельный LLM-отчёт после каждого tool нежелателен.

Причины:

- дополнительные токены;
- дополнительные API calls;
- дополнительная latency;
- возможность галлюцинации в отчёте;
- Executor может неверно описать собственное действие;
- сервер уже знает фактические arguments и results tool.

Поэтому для оперативной проверки использовать серверные факты:

tool call

tool arguments

target

before

after

diff

checkpoint_id

task_contract

============================================================
16. НЕ ВСЕ TOOLS НУЖНО ОТПРАВЛЯТЬ VERIFIER
============================================================

Предварительная схема:

read_file
→ без LLM Gate

list_dir
→ без LLM Gate

write_file
→ Mutation Gate

delete_file
→ Mutation Gate

python_compile
→ существующая deterministic server verification

git_diff
→ существующая deterministic server verification

git_status
→ существующая deterministic server verification

ui_smoke_test
→ существующая deterministic server verification

STOP / SUCCESS
→ Final Audit

Таким образом дорогой LLM Verifier используется только там, где он действительно добавляет смысловую проверку.

============================================================
17. FINAL AUDIT
============================================================

Даже успешная проверка каждой mutation не гарантирует выполнение всей TASK.

Каждая отдельная операция может быть допустимой, но:

- часть задачи могла быть забыта;
- обязательная проверка могла отсутствовать;
- итоговый результат может не соответствовать пользовательскому намерению;
- Executor может ошибочно объявить SUCCESS.

Первая практическая стадия этого механизма уже реализована в `run_agent_task(...)`.

Текущий lifecycle normal completion:

Executor normal STOP / EOS
    ↓
Deterministic Verification Gate
    ↓
Candidate Final Response validation
    ↓
Server собирает Final Audit Evidence
    ↓
Evidence Completeness Gate
    ↓
Independent Final Verifier
    |
    +-- VALID PASS
    |      ↓
    |   run_finished SUCCESS
    |      ↓
    |   return content
    |
    +-- FIRST VALID semantic FAIL
           ↓
        SUCCESS BLOCKED
           ↓
        Server Feedback
           ↓
        same RUN / one correction cycle
           ↓
        Deterministic Verification Gate
           ↓
        new clean Final Audit

Final Audit выполняется перед каждым normal SUCCESS, в том числе при:

write_revision = 0

и:

tool_call_count = 0

Нулевое число tools или mutations само по себе не является deterministic FAIL: это может быть корректно для read-only или explanatory TASK.

До VALID PASS финальный текст Executor является Candidate Final Response, а не подтверждённым SUCCESS.

============================================================
18. КОНТЕКСТ FINAL AUDIT
============================================================

Каждый Final Audit выполняется отдельным clean one-shot call. После единственного V.4 correction handoff следующий аудит является новым независимым вызовом без наследования Verifier history.

RAW TASK передаётся отдельно как source of truth. В текущей реализации это исходный аргумент `task` данного RUN, а не вся Chat History и не отдельный ALLOWED RUN CONTEXT для зависимых multi-turn задач.

Server самостоятельно собирает `verification_context`, включающий:

- Candidate Final Response;
- run facts: `run_id`, API/tool counters и `write_revision`;
- `changed_python_paths` и `deleted_python_paths`;
- permission policy и scopes;
- deterministic verification state и missing requirements;
- `mutation_facts` текущего RUN;
- fresh Git status и fresh Git diff;
- evidence для новых файлов;
- completeness / truncation metadata.

Evidence semantics различаются явно:

RAW TASK
= source of truth

Candidate Final Response
= claim Executor, не authoritative fact

Mutation Facts
= server-observed mutations текущего RUN

Fresh Git State
= workspace-wide observation, которое может включать pre-existing и external changes

Git change нельзя автоматически приписывать текущему RUN без подтверждения `mutation_facts`. Например, внешнее изменение `.obsidian/workspace.json` само по себе не доказывает нарушение TASK текущим Executor.

Обычный `git diff HEAD` не показывает содержимое обычного untracked-файла. Поэтому для нового файла текущего RUN Server отдельно включает его актуальное содержимое, если это разрешено READ scope и safety limits.

Перед LLM call действует Evidence Completeness Gate. Обычная incompleteness и `critical_for_success` не равнозначны. Критическими для SUCCESS являются, в частности:

- truncated Candidate Final Response;
- критически неполный или недоступный Git evidence для mutating RUN;
- truncated или недоступный new-file evidence;
- превышение hard limit всего Final Audit context.

При `critical_for_success = true` Verifier не вызывается, возникает `final_audit_evidence_incomplete`, а SUCCESS блокируется server-side.

============================================================
19. PASS FINAL AUDIT
============================================================

Если Final Verifier возвращает:

PASS

сервер разрешает:

RUN SUCCESS

и только после этого пользователь получает финальный результат как успешно выполненную задачу.

============================================================
20. FAIL FINAL AUDIT
============================================================

Текущая V.4 различает три класса исходов:

VALID PASS
→ `final_audit_passed`
→ RUN SUCCESS

VALID semantic FAIL
→ `final_audit_failed`
→ SUCCESS BLOCKED
→ при первом FAIL structured feedback передаётся Executor
→ тот же RUN получает один correction cycle

evidence / runtime / protocol problem
→ `final_audit_error`
→ SUCCESS BLOCKED

Semantic FAIL не объединяется с `VerifierRuntimeError`, `VerifierProtocolError` или Critical Evidence Error.

V.4 работает fail-closed: единственным исходом, разрешающим normal RUN SUCCESS, является VALID FINAL VERIFIER PASS.

На первом valid semantic FAIL Server напрямую строит feedback из полей `VerifierResult`: `verdict`, `reason`, `violations`, `required_action`, `verifier_run_id`, `check_type`. Вторая нейросеть для перефразирования feedback не используется. Server добавляет отклонённый Candidate Final Response как `assistant` и Server Final Verifier Feedback как `user` только во внутренний `messages`, после чего продолжает тот же `run_agent_task(...)`. Сохраняются исходный RAW TASK, `run_id`, Executor context, tool budget, backup session и `verification_state`.

Один correction cycle означает один разрешённый handoff `Final Audit FAIL → Executor`, а не один model API call или один tool call. Внутри correction cycle Executor может выполнять обычные model/tool итерации и обязан снова пройти deterministic Verification Gate перед следующим Final Audit.

Если повторный clean Final Audit снова возвращает semantic FAIL, новый handoff не создаётся: возникает terminal `FinalAuditSemanticError`, а `run_failed.reason` равен `final_audit_correction_exhausted`.

Runtime, protocol и critical evidence errors остаются немедленно terminal fail-closed и не передаются Executor как correction request.

============================================================
21. НЕЗАВИСИМОСТЬ VERIFIER
============================================================

Реализованный Verifier не наследует reasoning state Executor.

Это отдельный чистый model call.

Он получает только явно разрешённый verification context.

Verifier не должен получать:

- скрытую provider session Executor;
- неконтролируемую память предыдущего ответа Executor;
- инструменты записи;
- права на изменение Workspace.

Verifier работает без file tools.

У него нет права:

- write;
- delete;
- Git mutations.

Verifier Runtime не является обычным persistent Chat.

Каждая проверка выполняется как отдельный одноразовый чистый model call.

Например:

verify_mutation(...)

verify_final_result(...)

Рабочий контекст конкретного Verifier call существует только на время одной проверки.

После получения:

PASS

или:

FAIL

временное conversation state Verifier больше не требуется.

Verifier НЕ должен автоматически создавать:

- пользовательский Chat;
- persistent Chat History;
- отдельный Workspace;
- накопительную память между verification calls;
- provider session, общую с Executor.

Каждый новый verification call получает заново только явно собранный Server Runtime verification context.

Это необходимо для:

- независимости проверки;
- отсутствия скрытого влияния предыдущих решений;
- предотвращения context leakage;
- отсутствия бесконтрольного накопления Verifier history.

Если результат проверки необходимо сохранить, сохраняется не Chat Verifier, а:

- structured verification result;
- VERIFIER REQUEST metadata;
- VERIFIER PASS / FAIL;
- причина решения;
- соответствующая запись Trace.

Таким образом Verifier является временным вычислительным вызовом, а не ещё одним постоянным участником Chat Storage.

============================================================
22. MODEL ASSIGNMENT VERIFIER
============================================================

Verifier имеет отдельное назначение модели, независимое от MAIN CHAT и COMPRESSOR.

Например:

VERIFIER MODEL ASSIGNMENT

Текущий default (`verifier_model_id = gigachat_3_pro`):

GigaChat 3 Pro

Модель выбирается через Model Registry и передаётся явно как `verifier_model_id`.

В будущем возможны:

GigaChat Ultra
GigaChat Pro
локальная LLM
другая provider model

Модель Executor и модель Verifier могут совпадать физически.

Но calls должны быть независимыми.

Например:

Executor:
GigaChat 3 Ultra

Verifier:
GigaChat 3 Pro

или:

Executor:
GigaChat 3 Ultra

Verifier:
GigaChat 3 Ultra

Но второй вызов должен иметь чистый verification context.

25. BACKUP НЕ ДОЛЖЕН БЫТЬ ВРЕМЕННЫМ
============================================================

Backup нельзя хранить только в RAM или временной директории, которая исчезнет при аварии.

Причины:

- падение приложения;
- перезагрузка компьютера;
- сбой питания;
- ошибка runtime;
- ошибка самого Verifier;
- ошибочный PASS;
- повреждение нескольких связанных файлов.

Backup должен существовать независимо от RUN процесса.

============================================================
26.1. BACKUP COVERAGE INVARIANT
============================================================

Фундаментальное правило:

НИ ОДНА mutation существующего файла не может быть применена,
пока исходное состояние этого файла физически не сохранено
в persistent backup текущего RUN.

Если TARGET известен заранее из TASK CONTRACT:

Server может включить его в первоначальный Backup Snapshot
до начала Executor RUN.

Если TARGET становится известен только во время выполнения:

перед первой фактической mutation Server обязан:

1. определить текущее состояние TARGET;
2. проверить, был ли TARGET уже сохранён в backup текущего RUN;
3. если нет — сохранить исходную версию TARGET;
4. обновить backup manifest;
5. убедиться, что backup физически записан;
6. только после этого разрешить Mutation Gate / APPLY.

Если backup исходного состояния создать не удалось:

mutation запрещается.

Для существующего файла backup хранит состояние файла ДО первой mutation этого RUN.

Последующие изменения того же файла не должны перезаписывать исходный snapshot.

То есть backup текущего RUN сохраняет именно состояние:

BEFORE RUN MUTATION

а не:

BEFORE LAST MUTATION.

Для нового файла физической исходной версии не существует.

В таком случае backup manifest обязан сохранить:

existed_before = false

и path нового файла.

Это необходимо для корректного FULL RUN ROLLBACK.

Если RUN создал новый файл:

rollback к исходному состоянию должен удалить этот файл.

Таким образом Backup Snapshot описывает не только содержимое существующих файлов,
но и состояние filesystem до mutations.

============================================================
26.2. STAGING И BACKUP — РАЗНЫЕ МЕХАНИЗМЫ
============================================================

STAGED OPERATION и BACKUP нельзя смешивать.

STAGING — краткоживущий transactional layer.

Он описывает:

что Executor ХОЧЕТ изменить.

Например:

TARGET

OLD CONTENT

PROPOSED NEW CONTENT

PROPOSED DIFF

OPERATION ID

CHECKPOINT ID

Staging существует до принятия решения:

PASS

или:

FAIL.

Если Mutation Verifier возвращает FAIL:

proposed mutation НЕ применяется.

После фиксации необходимых данных в Trace
staging representation может быть уничтожена.

Если Mutation Verifier возвращает PASS:

Server выполняет обязательные hard checks,
применяет mutation,
после чего staging representation также больше не требуется.

BACKUP — persistent safety layer.

Он описывает:

что физически существовало ДО mutation.

То есть:

STAGING
=
что Executor предлагает сделать

BACKUP
=
что было до того, как Executor начал менять состояние

Staging нужен, чтобы неправильное изменение по возможности вообще не попало на диск.

Backup нужен, чтобы иметь возможность восстановиться,
если ошибка всё-таки была применена,
пропущена Verifier,
обнаружена позднее
или произошёл runtime failure.

Mutation Gate НЕ заменяет Backup.

Backup НЕ заменяет Mutation Gate.

============================================================
26.3. BACKUP RETENTION
============================================================

Успешный PASS задачи НЕ должен немедленно удалять Backup Snapshot текущего RUN.

Backup остаётся доступным после завершения RUN.

Предварительная политика хранения:

BACKUP RETENTION DEFAULT = 10

То есть Server хранит последние 10 persistent backup snapshots mutating RUN.

Backup History должна переживать:

- завершение RUN;
- закрытие приложения;
- повторный запуск приложения;
- перезагрузку компьютера.

Backup может храниться для RUN со статусом:

SUCCESS

FAILED

INTERRUPTED

ROLLED_BACK

если его состояние полезно для восстановления или анализа.

Активный RUN и его Backup Snapshot никогда не должны удаляться retention-механизмом во время выполнения.

После завершения RUN:

RUN завершён
    ↓
backup manifest получает final run status
    ↓
snapshot закрывается как завершённый
    ↓
Server проверяет retention limit
    ↓
если допустимых snapshots больше лимита
    ↓
удаляется самый старый snapshot,
который разрешено удалить

Первоначальный default:

10

В дальнейшем параметр должен быть настраиваемым.

Например:

3
5
10
20
unlimited

Backup History в будущем должна позволять:

- восстановить файл до конкретного RUN;
- восстановить несколько файлов конкретного RUN;
- выполнить FULL RUN ROLLBACK;
- посмотреть исходное состояние файла;
- сравнить backup с текущей версией;
- развернуть snapshot в отдельную директорию;
- провести forensic analysis ошибочного RUN;
- вручную выбрать состояние для Restore;
- позволить Agent Runtime выполнить Restore,
  только если такая операция явно разрешена пользователем / policy.

28. ROLLBACK
============================================================

Нормальный FAIL Mutation Gate не требует rollback:

operation была staged,
но не была applied.

- операция уже успела примениться;
- произошёл runtime failure;
- Final Audit выявил проблему, которую невозможно безопасно исправить вперёд;
- пользователь запросил восстановление;
- Verifier ошибочно пропустил mutation.

Возможные уровни rollback:

FILE ROLLBACK

CHECKPOINT ROLLBACK

FULL RUN ROLLBACK

Реализацию выбрать отдельно.

============================================================
34. SEMANTIC FAIL: CURRENT V.4 BEHAVIOR
============================================================

На Mutation Gate:

FAIL означает:

конкретная proposed operation отклонена.

RUN может продолжиться после исправления.

На текущем Final Audit V.4 первый semantic FAIL означает:

SUCCESS заблокирован,

`final_audit_failed` фиксирует результат конкретного audit, но не является terminal `run_failed`,

отклонённый Candidate Final Response добавляется как `assistant` только во внутренний `messages`,

structured `SERVER FINAL VERIFIER FEEDBACK` добавляется как server-authored `user` message,

тот же RUN получает один correction cycle и затем проходит новый clean Final Audit.

`final_audit.feedback` разрешается через `server_context_messages`: human-readable template редактируем, но authoritative `SERVER FACTS — NOT TEMPLATE CONTROLLED` добавляются Server отдельно. Editable template не может изменить эти факты:

- `event_id`;
- `message_kind = SERVER_FINAL_VERIFIER_FEEDBACK`;
- `is_new_user_task = false`;
- `raw_task_authority = SOURCE_OF_TRUTH`;
- `decision = SUCCESS_BLOCKED_CORRECTION_REQUESTED`;
- `run_id`, `verifier_run_id`, `check_type`, `verdict`;
- `reason`, `violations`, `required_action`;
- `correction_cycle`, `correction_limit`.

Отклонённый Candidate и feedback не записываются как обычные persistent Chat RAW messages. После успешной коррекции UI сохраняет только реально возвращённый Candidate B.

Второй semantic FAIL после использованного handoff означает `final_audit_correction_exhausted` и terminal RUN FAILED. Infrastructure / protocol / evidence errors завершают RUN сразу, без correction handoff.

============================================================
35. RETRY LIMIT
============================================================

Нельзя допустить бесконечный цикл:

Executor
→ ошибка
→ Verifier FAIL
→ Executor
→ та же ошибка
→ Verifier FAIL
→ ...

Текущий V.4 limit реализован отдельно:

`FINAL_AUDIT_CORRECTION_LIMIT = 1`

и учитывается через `final_audit_feedback_count` текущего RUN.

Этот limit ограничивает количество handoff `semantic FAIL → Executor`. Он не связан с `tool_limit`: один correction cycle может содержать несколько model API calls и несколько разрешённых tool executions.

После исчерпания единственного handoff повторный semantic FAIL завершает RUN с `final_audit_correction_exhausted`.

Полноценный generalized bounded retry manager относится к V.5. Он должен добавить `MAX_FINAL_AUDIT_RETRIES`, несколько correction attempts, repeated-failure signature, same-reason / ping-pong / loop detection, API-only loop protection, terminal retry policy и понятный retry trace.

============================================================

Поэтому нельзя отдавать ему полный физический контроль.

Server остаётся главным authority.

Server-side deterministic правила имеют приоритет.

    ↓

    ↓

Verifier дополняет server safety.

Verifier не заменяет её.
