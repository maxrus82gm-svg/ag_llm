#### 3. Оценка по компонентам

##### Planner

- [Ф] Ограничен со всех сторон:
  - не больше 32 сообщений и 128 КБ на сессию, 8 stages (planner_runtime.py:23–26, 538, 570–575);
  - READINESS CONTINUE ≤2, REPLAN ≤2;
  - lifecycle: ≤64 calls, ≤1800 s (task_planner.py:14–18, 249–252).
- [Ф] На простом сообщении запускается потому, что так выставлен переключатель UI (`planner_enabled`, ultra_ui.py:5825–5838). Отдельной ветки для разговорных сообщений нет. Расход на приветствие — около 5,8k токенов, без опасности.
- [Г] Косвенный вклад в R-027:
  - stage reset удаляет прочитанный материал;
  - READINESS отвечает CONTINUE («Требуется перечитать ultra_ui.py»);
  - большой файл читается заново.
  Это вклад через разбиение на stages, а не через собственные токены Planner.

##### Executor

- [Ф] Главный усилитель расхода, см. D-1…D-5.
- Фиксированная надбавка каждого call — 37–41 КБ (≈4,4–5,4k реальных токенов): global context, permission, project, schemas.
- [О] На 15 calls только эта надбавка даёт ~70–80k токенов.

##### Context / history

- [Ф] В DIRECT-режиме в каждый RUN передаётся вся user/assistant-история чата без ограничений (server.py:3562–3570, 3759–3807; context_storage.py:989–1011). В R-033 это 57 сообщений.
- [Ф] Tool outputs не переходят между RUN: в историю попадают только финальные тексты. История растёт линейно, её вклад — тысячи токенов, а не сотни тысяч.

##### Accounting

- [Ф] Учёт корректен по attempt_id, двойного учёта нет:
  - dedup duplicate / orphan (run_store.py:456–507; audit_storage.py:381–395);
  - сумма terminals = summary для R-024…R-033.
- [Ф] `precached_prompt_tokens` сохраняются в raw, но не агрегируются (gigachat_transport.py:17–28; run_store.py:206–219, 433–442).
- [Ф] В ответе GigaChat `prompt_tokens` не включает cached часть: например, prompt 400 + precached 73 920 при запросе 318 тыс. символов.
- [Ф] Оценка bytes/4 только диагностическая и в итоги не входит.
- [Ф] Поле UI «API: N» считает только executor-запросы (audit_storage.py:358–361; событие api_request — server.py:4590). У R-032 «API: 1» при 4 provider calls.

#### 8. Риски

- **Correctness:** тихое усечение больших файлов может привести к правкам по частичным данным. Поэтому только явный отказ с sha; read_file_range остаётся.
- **Fail-closed:** если потолок сработает после записи, файл изменён без верификации. RUN должен стать BLOCKED с mutation facts, backup уже есть — но не SUCCESS.
- **Freshness:** кэш и дедупликация чтений должны учитывать sha и write_revision (151B), иначе в контекст попадёт устаревший материал.
- **Run Store:** новые поля summary нужно добавить обратно совместимо; в старых summary cached нет — помечать UNKNOWN, а не 0.
- **UX:** чаще будут BLOCKED у больших задач — нужны понятная причина и настройка потолка на RUN. Метка «API» вводит в заблуждение. D-9 уже испортил ответ пользователю.
