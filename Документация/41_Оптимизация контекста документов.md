## 1. Рекомендация и измеримый результат будущего изменения

Рекомендую сочетать компактный рабочий №34, стабильный стартовый №08 и двухступенчатую текстовую навигацию №05. История остаётся у существующих владельцев. Новый чат получает достаточную текущую картину и точный маршрут к доказательствам; полный архив не становится обязательной платой за вход.

Основная причина расхода контекста — накопительное добавление новых состояний перед старыми и повторение норм в нескольких местах. Поэтому одного сокращения текста недостаточно. Нужны один владелец каждого вида факта, различение текущего состояния и исторического события, проверка сохранности до вытеснения и контроль размера при закрытии TASK.

## 2. Фактический аудит локального снимка

### 2.1. Метод и пределы

Размеры посчитаны по UTF-8-файлам: байты — исходный файл, символы — декодированный Unicode-текст с исходными окончаниями строк, строки — `splitlines`. SHA-256 фиксирует точную локальную версию. Каталог размеров охватывает 70 Markdown-документов. Базовая проверка неизменности охватывает 326 существующих файлов: документацию, Obsidian, корневые файлы, `web_alarm`, `integrations`, `.github`; `.git` не открывался.

Содержательно изучены собственные Правила/БЛОК 1/БЛОК 4, стартовые и нормативные разделы, структура №08/34/05, актуальная координация №40, адресные сведения профильных владельцев. Для №05 использованы оглавление, выбранные записи и машинная проверка текстовых указателей; реестр не загружался целиком как контекст. №06/25 и персональные №001 учитывались по назначению, размерам и контрольным суммам, без загрузки исторических тел в контекст и без ретроспективного поиска TASK. Машинные контрольные суммы/инвентаризация синтаксиса не являются содержательной проверкой архивов.

В ходе первичного обследования был запрошен полный вывод собственного файла карточки и №08/34; часть вывода оказалась усечённой. Эти вызовы не считаются доказательством полного прочтения. Затем использованы адресные диапазоны и структурная инвентаризация. Это также демонстрирует риск неограниченного чтения больших документов. Никакой слепой процедуры `INDEPENDENT_PLAN` текущая TASK не назначает: независимость здесь архитектурная, а не утверждение о BLIND-START.

Локальные цитируемые статусы рассматриваются как документные утверждения на снимке, не как заново проверенные source/CI/runtime результаты. История публикаций и актуальный GitHub HEAD не проверялись. Полная семантическая сохранность будущей миграции ещё не доказана: такой миграции не было.

### 4.2. Включение, вытеснение и текущие решения

Включать сведения, если они изменяют ближайшее разрешённое действие, объясняют действующую архитектурную границу, сохраняют открытый gate или нужны для безопасного запуска после смены чата. Существенный старый риск не вытесняется из-за возраста. Постоянные ограничения не входят в лимит последних завершённых TASK.

Последние результаты выбираются по времени принятого существенного события, а не по времени любого редактирования файла. Несколько repair/amendment одной TASK сворачиваются в одну короткую запись с сохранением полного маршрута к версиям. Запись не считается завершённой только потому, что исполнитель сдал отчёт.

Для двух текущих направлений держать 3–5 результатов каждого, максимум 10 в суммарной рабочей выборке. Если направлений станет больше и правило окажется несовместимым с бюджетом, явно определить рабочие направления данного handoff; остальные сохранить в строках состояния и открытых gate, а их истории читать по №05. Не скрывать активные задачи или блокеры ради лимита. Изменение самого правила выборки требует решения координатора/пользователя, не молчаливой потери фактов.

Вытеснение допускается только после проверки: существует каноническая запись → совпадают факт, дата, TASK, результат, оговорки и provenance → проверен точный locator → адрес доступен читателю в его правах. Если владелец/адрес не найден, пометка `PRESERVATION UNRESOLVED`; исходный фрагмент остаётся. В этой TASK ни одного фрагмента не вытеснено.

## 7. Протокол выборочного чтения

Текстовый указатель имеет форму `имя документа → точный заголовок → TASK ID / раздел / источник`. Для надёжности добавляются версия источника и хеш фрагмента; номера строк — только ускоритель для закреплённого снимка. Ни Wiki-ссылки, ни внутренние Markdown-ссылки, ни embeds, ни новые aliases/теги не требуются.

Предлагаемый алгоритм ручного или будущего read-only извлечения:

1. Проверить роль, mode, разрешённые файлы/разделы и цель чтения. Для истории требуется адресное разрешение; достижимость файла не даёт права читать его.
2. Получить актуальность источника разрешённым способом. Codex использует локальный SHA-256, не Git; координатор получает опубликованную версию в своих правах. Локальный digest не доказывает GitHub publication.
3. В обычном реестре прочитать только заголовки/индекс нужной темы. В архиве не строить общий рекурсивный индекс: использовать переданный точный locator. При неизвестном locator запросить минимальную выдержку у координатора.
4. Разрешить locator однозначно: полный путь + заголовок + родитель/номер вхождения при повторе + TASK ID. Нулевое или несколько совпадений — `LOCATOR UNRESOLVED`, не произвольный первый match.
5. Извлечь раздел до следующего заголовка того же или более высокого уровня. Для таблицы — её шапку, выбранную строку, применимые общие оговорки; длинную ячейку не обрезать посередине. Заголовки внутри fenced code не считать границами.
6. Для нормы включить полный нормативный блок, `rule-meta`, исключения, overrides и транзитивные `requires`. Контролировать посещённые Rule-ID, циклы и недоступные версии. Для истории переход по одному указателю не даёт разрешения автоматически раскрыть следующий архив.
7. Предлагаемый размер обычной выдачи 2–8 тысяч символов; полный нормативный контракт может превысить бюджет. При превышении выдавать именованные части с `CONTINUATION REQUIRED`; не объявлять чтение завершённым после первой части. Ограничение контекста не отменяет безопасность.
8. Записать read receipt: запрос/цель, разрешение, путь, локатор, версия, диапазон, полнота, прочитанные зависимости. При изменении хеша повторно разрешить адрес, а не использовать устаревшие строки.

Такой extractor/resolver пока только проект. В этой TASK создан лишь скрипт анализа размеров и неизменности; он не является производственным resolver и не доказывает все особенности Markdown. До отдельно проверенной реализации достаточно адресного чтения и ручной проверки границ. Не нужен векторный поиск или LLM-сжатие всего архива для нахождения известного TASK ID.

Недоступность исторического адреса, конфликт версии или графа оставляет `DOC CLOSEOUT BLOCKED`; нельзя сначала очистить БЛОК 1, а затем пытаться восстановить постановку. Обычная запись №05 о результате обновляется после принятия, а незавершённость исполнения остаётся видимой в карточке/координации. Отдельно разрешённый terminal PARTIAL/BLOCKED возможен без VERIFIED, с явным решением пользователя.

Состояния не сводятся к одной зелёной метке: `execution`, `publication`, `independent_review`, `user_plan_approval`, `runtime/rollout_gates` независимы. Подтверждённая архитектура не означает реализованный код; код/evidence accepted не означает Windows/visual accepted; ACK доставки не означает review. Историческое CURRENT маркируется датой и замещающим событием, а в оперативном представлении остаётся только актуальный вариант в его области.

Ключ повторной доставки: `TASK ID + digest/version отчёта`. Повторная доставка того же пакета не создаёт новую TASK, новую запись истории или второй самостоятельный verdict. Новый digest требует новой проверки изменённой версии. При смене чата восстанавливаются TASK ID, read/write-scope, текущие gates и точный пакет; старый чат не является скрытым единственным источником.

## 9. Защита от повторного роста

При каждом documentation closeout измерять №34/08 до и после, фиксировать delta и заполнение бюджета; проверять окна последних результатов, текущие источники и отсутствие повторных глав handoff. Контроль событийный — при закрытии TASK, существенном решении и перед передачей новому чату. Фоновой автоматизации не создано.

№34 выше 25 тысяч требует обоснования временного расширения, владельца и ближайшего события возврата. Выше 50 тысяч кандидат не принимается. Нельзя выполнять механический truncate. Если открытые важные сведения не помещаются, сначала удостоверить каноническое хранение и улучшить адреса; при невозможности — остановить миграцию и сохранить старый текст.

Новая TASK обычно заменяет устаревшую строку рабочей картины и один элемент окна результатов. Нулевая delta размера не обязательна: важная новая действующая граница может законно увеличить документ. Контролируется отсутствие необоснованного накопления, а не косметическая фиксированная длина.

Для №08 триггер обновления — изменение ролей, стартового маршрута, обязательной безопасности или владельца информации. Очередной CI PASS, repair и смена текущего исполнителя не повод дописывать историю в №08. Для №05 контролируется доступность индекса и сохранность всего содержимого, не запрет роста исторических данных.

Проверка актуальности: каждое CURRENT имеет область, дату сверки и источник; смена статуса требует явного supersedes; ссылки на недоступные архивы не принимаются за loss-check. Запрет/OPEN pin не удаляется до явного resolution. В №40 смена направления или пересечение scope обновляется адресно и последовательно двумя координаторами.

Для измерения будущей пользы: размер стартовой выборки, число прочитанных фрагментов до ответа на контрольные вопросы, ошибки выбора CURRENT, доля разрешённых locators, доля норм с полными requires, число дубликатов статуса. Цель — все обязательные вопросы отвечаются без полного №05/06/001 и без потери ограничений. Время/токены сейчас не измерялись.

Машинный `migration_inventory.json` дополнительно покрывает каждый фрагмент №08/34 исходным диапазоном и хешем; все future preservation gates до отдельной проверки остаются OPEN.

LOSS CHECK проводится не только сравнением количества символов. Для каждого фрагмента нужны факты, отрицательные ограничения, числовые границы, даты, provenance, исключения и будущий адрес. Совпадение темы у документа-владельца не доказывает сохранение смысла. Минимум один независимый reviewer проверяет семантическое покрытие; автоматические проверки гарантируют лишь структурные условия. Неразрешённые позиции не превращаются в «потерь нет».

## 11. Obsidian Graph: неизменность связей как жёсткий gate

Текстовая навигация не является графом. В №41 и новом техническом отчёте нет новых Wiki-ссылок, внутренних Markdown-ссылок/embeds, YAML aliases/tags или отдельных тегов. Имена документов и стрелка в обычном тексте используются как адреса для чтения. Исходные документы и `.obsidian` не редактировались.

Важное различие: пользователь явно поручил создать новый Markdown №41. При нынешних `search = path:/^Документация\//` и `showOrphans = true` он может отображаться в Obsidian как новый изолированный документ. Это не новое ребро, однако нельзя обещать буквальную идентичность множества видимых узлов после создания файла. Настройки графа ради сокрытия №41 не меняются. В этой работе сохраняются все существующие связи; визуальная сцена Obsidian не проверялась. Если требование трактуется также как запрет появления разрешённого нового узла, это несовместимо с размещением №41 в этой папке и требует отдельного решения пользователя; самовольного обхода фильтрами нет.

Перед будущей реализацией нужен реальный снимок разрешённых графовых отношений: направленный мультимножество `source file → resolved target file + heading/block anchor`, тип связи, исходное написание и число вхождений; отдельно unresolved targets, aliases, embeds и все reference-style Markdown links. Нельзя ограничиться числом рёбер: удаление одного и добавление другого даст прежнее число. Сравнивать состав, направления, кратность и разрешение target/anchor; учитывать входящие связи из остальных файлов vault.

Нельзя переносить существующую ссылку из №34 в архив: это изменит source ребра. Нельзя переименовать заголовок, на который ссылается другой документ, даже если имя файла сохранено. Если сокращаемый фрагмент содержит такую конструкцию, она и нужный target остаются на прежнем источнике; сжимается только безопасное окружение. Если это мешает бюджету, статус `GRAPH CONSTRAINT BLOCKED`, а не автоматическая перестройка графа. Новые связи допускаются лишь отдельным решением пользователя, не в рамках этой оптимизации.

Текущие доказательства ограничены байтовым сравнением существующих файлов и консервативной инвентаризацией синтаксиса. Они сильны для доказательства отсутствия наших правок существующих связей, но не заменяют разрешённый read-only export Obsidian resolved graph при реальной миграции. В инвентаре 70 исходных документов не найдены графовые конструкции с названием нового №41 или префиксом `41_`; это ограниченная проверка ранее dangling ссылок, не полный анализ всех файлов vault. Если полноценный экспорт недоступен, нельзя выдавать regex-скан за полную графовую приёмку; будущую миграцию оставить заблокированной до достаточного доказательства.

Первая сверка обнаружила изменение `.obsidian/workspace.json` относительно baseline во время выполнения TASK. Агент этот файл не записывал; происхождение изменения не установлено. Он не восстановлен и не переопределён. Все 70 исходных Markdown-документов и `.obsidian/graph.json` остались с прежними hashes. Поэтому нельзя заявлять полную байтовую неизменность всей папки Obsidian: в отчёте отдельно сохранено это наблюдаемое расхождение. Оно не является доказательством изменения графовых рёбер.

Если ещё нет чужих изменений, восстановить точные исходные байты только файлов миграции и сверить граф/размеры/хеши. Новые архивные factual записи не уничтожать ради отката стартового представления; отметить отмену миграции отдельно. Runtime rollback здесь не нужен, потому что документационная TASK не меняет runtime. Git rollback локальному агенту не разрешается автоматически.

Главные риски: непроверенный исторический locator; случайная подмена source PASS полным VERIFIED; регресс запрещающих правил; старая CURRENT-копия; скрытое увеличение №40/000; устаревший индекс; повреждение anchor/alias графа; слишком агрессивное ограничение объёма; путаница локальной версии и опубликованного результата. Принимать следует архитектуру доступа и процесс сохранности, а затем отдельный проверяемый миграционный пакет. Текущая работа предоставляет предложение и воспроизводимые локальные замеры. Она не утверждает, что архивы уже сверены, что все указатели разрешены, что Obsidian visual проверен или что оптимизация внедрена.
