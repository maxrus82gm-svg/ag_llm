# 1. Главная иерархия

Базовая структура системы:

```text
WORKSPACE
│
├── PROJECT CONTEXT
│
└── CHAT
    │
    ├── RAW HISTORY
    │   └── RAW MESSAGE
    │
    └── MESSAGE CONTEXT
        ├── STATE
        └── CONTEXT VARIANTS
```

Главный принцип:

```text
WORKSPACE
≠
CHAT
≠
RAW HISTORY
≠
WORKING CONTEXT
≠
PROJECT CONTEXT
```

Это разные сущности с разным назначением.

# 2. Workspace

Workspace — корневая директория конкретного проекта.

Он определяет:

```text
область файлов проекта
PROJECT CONTEXT
набор Chat
переносимое внутреннее состояние
```

Каждый Workspace имеет постоянный:

```text
workspace_id
```

Внутреннее переносимое состояние хранится в:

```text
.ultra/
```

---

# 3. Несколько Workspace

UI поддерживает работу с несколькими Workspace.

Реализованы:

```text
создание Workspace
подключение существующего Workspace
переключение Workspace
переименование Workspace
удаление Workspace из локального registry
```

Удаление Workspace из registry не означает физическое удаление проекта с диска.

# 4. Portable Workspace State

Переносимое состояние проекта находится внутри:

```text
.ultra/
```

Оно должно перемещаться вместе с проектом между компьютерами.

К нему относятся:

```text
workspace identity
Project Context
Chat metadata
RAW HISTORY
MESSAGE CONTEXT STATE
Context Variants
Run Store v2 index, summaries, role streams и record indexes
```

Текущий portable Audit storage:

```text
.ultra/audit/index.json
.ultra/audit/index_generations/index-<revision>-<uuid>.json   # fallback only
.ultra/audit/<chat_id>/<run_id>/summary.json
.ultra/audit/<chat_id>/<run_id>/task.json
.ultra/audit/<chat_id>/<run_id>/executor_base.json
.ultra/audit/<chat_id>/<run_id>/{executor,planner,server,dredd}.jsonl
.ultra/audit/<chat_id>/<run_id>/records.idx.jsonl
```

Legacy `<run_id>.json` читается только по явному выбору, не мигрируется массово при startup и не удаляется автоматически. Новые RUN не создают один большой monolithic RUN JSON.

## CURRENT — TASK BLOCK / RUN STORE IDENTITY

Canonical runtime identity сохраняют:

```text
workspace_id
chat_id
message_id
task_block_id
run_id
verifier_run_id
```

Persistent display aliases `T-001`, `T-002`, … и `R-001`, `R-002`, … scoped к Workspace, растут монотонно и не переиспользуются. Они предназначены для UI и человека и не заменяют canonical IDs.

```text
CHAT
↓
TASK BLOCK
↓
RUN
↓
ROLE STREAMS / SUMMARY / RECORD INDEX
```

Один logical Task Block связывает user TASK, assistant result, относящиеся к ней RUN и Audit / Planner observability. `records.idx.jsonl` хранит metadata и UTF-8 byte offset/length; выбранная запись читается точным seek/read/decode. Audit UI сначала использует index/summary, затем отдельно загружает selected record и Planner stream. Первый Executor context хранится в `executor_base.json`, следующие диагностические contexts — как deterministic deltas; provider API при этом остаётся stateless и получает собранный runtime context, а не только delta.

TASK 143 усилила Windows-устойчивость Run Store bounded retry для кратковременного `PermissionError`, но live RUN доказал persistent external lock на `index.json`. TASK 145 установила root cause: файл удерживал Remote Desktop Commander `node.exe` без совместимого delete/replace sharing.

TASK 146 убирает `index.json` как single point of failure при таком lock. Workspace index имеет монотонную `revision`. Если canonical `index.json` не удаётся заменить после bounded retry, Run Store сохраняет полный immutable snapshot в `.ultra/audit/index_generations/`. Все readers выбирают индекс с максимальной revision, поэтому Task/Run aliases и discovery продолжают работать без потери RUN. Пока generation fallback активен, последующие canonical attempts не ждут полный retry-window. Когда external lock исчезает, очередная index mutation записывает актуальную revision обратно в `index.json` и удаляет устаревшие generation snapshots, которые можно удалить. Summary-only updates (`api_requests`, `tool_calls`, token usage) больше не переписывают workspace index, если `run_status/final_audit` не менялись.

Generation fallback относится именно к workspace `index.json`; generic lock любого произвольного JSON-файла не объявляется решённым без отдельного evidence. Если Audit recorder всё же не может создать ни canonical, ни generation storage, ошибка остаётся видимой и не маскируется.

Audit events не являются Working Chat Context. Planner/Dredd diagnostics не должны автоматически попадать в Main Chat context. Аналогично, полный persistent Chat history не является обязательным Executor prompt: role-specific context compilation может использовать только текущую TASK и необходимые authoritative facts.

# 6. Project Context

Один Workspace имеет общий:

```text
PROJECT CONTEXT
```

Он хранится в:

```text
.ultra/project_context.md
```

Project Context является общей проектной памятью для всех Chat данного Workspace.

Он может содержать:

```text
назначение проекта
устойчивые факты
архитектурные решения
термины
ограничения
важное текущее состояние
```

Project Context не является полной историей разговоров.

# 7. Project Context и Chat

Все Chat одного Workspace используют один общий Project Context.

Схема:

```text
WORKSPACE
│
├── PROJECT CONTEXT
│
├── CHAT A
├── CHAT B
└── CHAT C
```

Переключение Chat:

```text
НЕ меняет Workspace
НЕ меняет Project Context

```

# 8. Project Context revisions

Project Context редактируется через контролируемый Context Storage API.

Реализована история предыдущих версий.

Таким образом изменение Project Context не должно уничтожать предыдущую версию без возможности восстановления через storage history.

Обычные file-agent tools не должны напрямую переписывать внутреннее `.ultra` storage.

# 14. RAW MESSAGE

RAW MESSAGE содержит первоначальный текст сообщения.

Основное поле:

```text
original_text
```

```text
immutable source of truth
```

После создания RAW не должен переписываться из-за:

```text
сжатия

Restore

перезапуска приложения
```

---

# 15. Когда сохраняется RAW

User RAW сохраняется до основного API request.

Assistant RAW сохраняется как persistent message при успешном завершении соответствующего процесса.

История поэтому существует независимо от памяти внешнего LLM provider.

```text
model_display_name
```

Это позволяет после restart сохранять provenance конкретного ответа.

# 18. Multi-turn Chat storage и Executor Task-Scoped Context

Persistent multi-turn Chat и Working Representation реализованы: runtime загружает историю выбранного Chat, сохраняет RAW / SUMMARY representations и не смешивает сообщения другого Chat.

После TASK 139 storage и рабочая история Chat больше не означают автоматическую передачу всей истории в normal Planner-enabled Executor. Для такого RUN Server компилирует task-scoped Executor seed:

```text
SYSTEM / permissions
+ GLOBAL ULTRA CONTEXT
+ PROJECT CONTEXT
+ CURRENT RAW TASK
+ CURRENT STAGE / SERVER FACTS
+ bounded completed stage results
```

Старые user/assistant сообщения выбранного Chat остаются в persistent history и доступны UI / Working Representation / compression, но не копируются целиком в Executor prompt без отдельной policy. Это устраняет прямое загрязнение новой TASK предыдущими TASK и не удаляет историю.

Legacy direct callers с `planner_enabled=False` сохраняют прежний путь через полный active Working Chat Context для compatibility.

Runtime event `executor_context_compiled` фиксирует выбранную policy, число и объём включённых и исключённых chat messages.

## 18.1 TASK 148 — Context boundary audit

На R-015/T-015 подтверждена фактическая граница между persistent Chat и model context.

```text
Chat Working Representation:
25 messages / 16 801 chars

normal Planner-enabled Executor seed:
1 message / 293 chars = CURRENT RAW TASK

excluded from Executor:
24 messages / 16 508 chars
```

Server при этом **локально всё ещё загружает** полный Working Chat через `load_chat_working_messages()` для проверки identity/метрик и затем отбрасывает старые сообщения policy `task_scoped_v1`. Это локальный disk/CPU cost, а не model-token cost. По мере роста Chat TASK 154 должен убрать необходимость полного linear scan из hot RUN path либо заменить его индексированным retrieval.

R-015 Executor base:

```text
SYSTEM                         21 219 chars
CURRENT RAW TASK                  293 chars
SERVER STAGE CONTEXT            1 241 chars
----------------------------------------
base message chars             22 753 chars
first request + tool schemas   25 968 chars
provider prompt tokens          5 015
```

Точный полный RAW TASK присутствовал в Executor base **ровно один раз**. Stage context не дублировал RAW TASK целиком, но закономерно повторял отдельные task-derived значения внутри server-owned persistence contract, например exact artifact postcondition.

SYSTEM decomposition R-015:

```text
Global Ultra Context          ~16 151 chars
Project Context               ~ 2 038 chars
permissions/system wrappers   ~ 3 030 chars
SYSTEM total                   21 219 chars
```

Следовательно после удаления full Chat history главным постоянным Executor budget hotspot стал Global/System layer, а не Chat.

### Planner boundary

Planner работает в отдельной `PlannerSession`:

- RAW TASK входит один раз в INITIAL turn;
- INITIAL context содержит только server-owned permissions + tools;
- Project Context и Working Chat Planner не получает;
- READINESS/REPLAN получают bounded server lifecycle facts, а не повторный полный Chat;
- локальная Planning Session сохраняет собственный transcript между Planner turns;
- fail-closed bounds: максимум 32 messages и 128 KiB serialized planning context;
- Planner Dredd review при protocol error получает RAW TASK + Planner transcript + validation error, но не Executor/Chat history.

Live R-015:

```text
INITIAL:   system 7 521 chars + user payload 1 272 chars
           provider prompt 1 988 tokens

READINESS: same bounded system + session history
           provider prompt 2 803 tokens
```

### Final Verifier / Dredd boundary

Final Verifier является one-shot ролью и получает только:

```text
RAW TASK
+
SERVER-GENERATED VERIFICATION CONTEXT
```

Он прямо инструктирован не предполагать Chat history, tools/files или external facts вне переданного evidence.

R-015 выявил отдельный budget hotspot:

```text
Final Audit attempt #1:
verification context = 104 614 chars
prompt tokens         = 28 779

Final Audit attempt #2:
verification context = 104 181 chars
prompt tokens         = 28 718
```

Большой объём создаётся server evidence: mutation facts, verification state, run-owned filesystem evidence, fresh Git status/diff и new-file evidence. Это **не Chat history** и не должно подвергаться lossy Chat compression: authority evidence требует отдельной optimization policy.

### Stage-local growth

Stage reset работает: новый stage возвращает Executor к task-scoped base + новый SERVER STAGE CONTEXT. Но внутри одного stage tool/function history накапливается.

R-015:

```text
stage_1: 1 Executor call,   5 100 total tokens
stage_2: 10 calls,        57 090 total tokens
stage_3: 10 calls,        61 935 total tokens
```

Request size stage_2 вырос примерно с 24.8k до 39.2k chars до reset. Это относится к TASK 149 (лишние READ/VERIFY loops), а не к historical Chat memory.

## 18.2 Будущий server-owned CHAT MICRO HISTORY

TASK 148 фиксирует задел под TASK 152–154. Нельзя возвращать full Chat в Executor prompt и нельзя разрешать LLM-компрессору переписывать authoritative context.

Разделение доверия:

```text
A. AUTHORITATIVE — НЕ LLM-COMPRESS
   system/runtime rules
   permissions
   CURRENT RAW TASK
   task plan / server facts / receipts
   deterministic verification / Final Audit evidence

B. HUMAN-APPROVED DURABLE MEMORY
   PROJECT CONTEXT
   Compressor может предложить изменение, но не должен молча переписывать его

C. DERIVED HISTORICAL MEMORY — МОЖНО СЖИМАТЬ
   completed Task Digests
   chronological task ledger
   rolling archive summaries
   relevant prior facts
```

Новый механизм должен работать **не как compression каждого сообщения**, а как server-owned derived memory завершённого Task Block.

```text
terminal RUN
  ↓
SERVER STRUCTURED TASK DIGEST
  RAW TASK/source refs
  task_block_id / run_id / terminal status
  accepted contract
  receipts / artifacts
  verification / Final Audit refs
  unresolved / OPEN facts
  ↓
optional COMPRESSOR NARRATIVE
  не меняет authoritative fields
  ↓
CHAT MICRO HISTORY
  ├─ RECENT STRUCTURED DIGESTS
  ├─ COMPACT CHRONOLOGICAL LEDGER
  ├─ PINNED OPEN ITEMS
  └─ ARCHIVED ROLLING SUMMARY
  ↓
Relevant Prior Facts
  извлекаются из structured digests/source records
  ↓
Context Compiler V2
  PROJECT CONTEXT
  + bounded MICRO HISTORY
  + RELEVANT PRIOR FACTS
  + CURRENT RAW TASK
  + CURRENT SERVER FACTS
```

Server, а не Compressor, обязан владеть identity/status/source refs и budget. LLM может создать optional narrative summary, но не имеет authority менять `task_block_id`, `run_id`, terminal status, artifact facts, permissions или verification result.

Structured Task Digest должен хранить source references/hashes, чтобы derived memory можно было проверить против RAW Chat/Run Store. Narrative и rolling summary не становятся единственным источником исторического факта.

### Rolling compaction

Чтобы микроистория сама не превратилась во второй огромный Chat:

- recent completed tasks хранятся подробнее;
- каждая задача оставляет хотя бы очень короткую chronological запись;
- unresolved / OPEN items pin и не исчезают при compaction;
- старые Task Digests сворачиваются в archive summary с диапазоном source task IDs;
- Context Compiler выбирает richer `RELEVANT PRIOR FACTS` только для текущей задачи;
- budget задаётся Server в tokens/bytes, а не пожеланием модели «сжать на 90%».

Текущий manual Message Compressor остаётся отдельной функцией RAW→Context Variant: он работает по одному message, default reduction 50% и не является server-owned Task Digest pipeline.

Реализация памяти отложена не только до завершения стабилизации, но и до закрытия оптимизационной базы программы 20:

```text
TASK 150–151 — stabilisation close / STABLE BASELINE S1
TASK 151A–151J — accounting, freshness, compact audit, direct evidence, context optimization
TASK 152 — Server Structured Task Digest
TASK 153 — Rolling Chat Micro History
TASK 154 — Relevant Prior Facts / Context Compiler V2
```

Канонический порядок и контрольные точки временно принадлежат `20_Программа качественного перехода - оптимизация runtime, контекстов и памяти.md`; доказательная история перехода — `21_Журнал качественного перехода - решения, метрики и аудит.md`. После финального reconciliation эти переходные документы удаляются, а подтверждённая архитектура остаётся здесь и в других профильных документах.

# 19. RAW HISTORY и Active Context — не одно и то же

Раньше фактический Active Chat Context практически совпадал с RAW HISTORY.

Теперь между ними существует отдельный слой:

```text
WORKING REPRESENTATION
```

Поэтому:

```text
RAW HISTORY
≠
ACTIVE CHAT CONTEXT
```

RAW HISTORY хранит оригиналы.

Active Chat Context содержит выбранные RAW / SUMMARY representations текущего Chat. Он является доступным источником контекста, но после TASK 139 не обязан целиком входить в каждый Planner-enabled Executor request: конкретная role context policy определяет, какие части storage реально компилируются в model call.

Поэтому:

```text
STORAGE CONTEXT
≠
ROLE WORKING CONTEXT
≠
MODEL REQUEST
```

```text
RAW
```


```text
active_representation = raw
```

состояние UI называется:

```text
FULL
```

В этом состоянии:

```text
CHAT показывает RAW

```

---

# 23. COMPRESSED

Когда активно:

```text
active_representation = summary
```

состояние UI называется:

```text
COMPRESSED
```

В этом состоянии:

```text
CHAT показывает active Context Variant
Working Representation = active Context Variant
```

Конкретный model call получает эту representation только если его role context policy включает соответствующее Chat message. После TASK 139 normal Planner-enabled Executor не получает старые Chat messages автоматически; SUMMARY продолжает существовать в storage и может использоваться UI / compression / будущим relevant-facts layer. RAW при этом продолжает существовать отдельно и не изменяется.

---

# 25. Старые варианты не уничтожаются

Создание новой рабочей версии не должно автоматически уничтожать предыдущие Context Variants.

Активным является только один вариант.

Остальные могут сохраняться как история предыдущих representations.

Это отдельно от immutable RAW.

---

# 26. Working Representation

Для каждого user/assistant message runtime может получить:

```text
WORKING REPRESENTATION
```

Она разрешается так:

```text
если state = RAW
→ original_text

если state = SUMMARY
→ active Context Variant
```

Именно Working Representation используется при построении Chat Context для MAIN CHAT.

---

# 27. Сборка Working Chat Context

Server использует рабочие representations сообщений текущего Chat.

Логически:

```text
CHAT HISTORY
↓
для каждого message_id
↓
resolve MESSAGE CONTEXT STATE
↓
RAW или active SUMMARY
↓
сохранить исходный role и порядок
↓
ACTIVE CHAT CONTEXT
```

Текущая реализация использует:

```text
load_chat_working_messages()
```

---

# 28. Порядок сообщений

Context Compression не меняет хронологию Chat.

Например:

```text
USER RAW
ASSISTANT SUMMARY
USER RAW
ASSISTANT RAW
```

по-прежнему передаются модели в исходном порядке ролей.

Меняется только текстовое representation отдельного сообщения.

---

# 29. Отображение Chat

Текущий UI показывает пользователю активную Working Representation.

Поэтому:

```text
FULL
→ пользователь видит RAW

COMPRESSED
→ пользователь видит SUMMARY
```

Это сделано намеренно.

Видимое сообщение соответствует тому тексту, который MAIN CHAT использует как active representation.

---

# 30. Просмотр RAW

Для доступа к неизменяемому оригиналу существует действие:

```text
Оригинал
```

Оно открывает отдельный read-only viewer.

Viewer всегда получает:

```text
original_text
```

а не active summary.

---

# 31. Просмотр оригинала не меняет Context

Само открытие:

```text
Оригинал
```

ничего не переключает.

Если пользователь просто открыл и закрыл окно:

```text
MESSAGE CONTEXT STATE
не изменяется
```

---

# 32. Restore

Если сообщение находится в состоянии COMPRESSED, Original Viewer позволяет выполнить:

```text
Восстановить в контекст
```

После Restore:

```text
active_representation = raw
active_variant_id = None
```

После этого:

```text
CHAT снова показывает RAW
MAIN CHAT снова получает RAW
```

Существовавшая summary не обязана удаляться.

---

# 33. Управляемое сжатие сообщения

Для сообщения доступна операция:

```text
Сжать
```

Базовый lifecycle уже реализован:

```text
FULL
↓
СЖАТЬ
↓
COMPRESSION PROPOSAL
↓
USER DECISION
↓
COMPRESSED
```

---

# 34. COMPRESSION PROPOSAL

LLM Compressor сначала создаёт только предложение.

Proposal содержит новую возможную Working Representation.

До пользовательского подтверждения:

```text
RAW не меняется
active representation не меняется
persistent summary не активируется
```

---

# 35. Решение пользователя

Пользователь может:

```text
Принять
```

или:

```text
отредактировать Proposal
и Принять
```

или:

```text
Отклонить
```

LLM не должна самостоятельно решать, что новая summary становится active.

---

# 36. Accept

После Accept:

```text
создаётся Context Variant
↓
variant сохраняется
↓
state переключается на SUMMARY
↓
UI rerender
↓
CHAT показывает summary
```

MAIN CHAT после этого также получает summary.

---

# 37. Manual Edit

Рабочее representation можно редактировать вручную.

Если сообщение уже COMPRESSED:

```text
редактируется active working version
```

и создаётся новый Context Variant.

Если сообщение FULL, система также может создать manual working variant без изменения RAW.

---

# 38. Recompression

LLM recompression не должна выполняться от предыдущей summary.

Канонический workflow:

```text
RAW
↓
COMPRESS
↓
SUMMARY
↓
RESTORE
↓
RAW
↓
COMPRESS AGAIN
```

Новый Compressor RUN получает исходный immutable RAW.

Это предотвращает деградацию:

```text
SUMMARY
→ ещё более сжатая SUMMARY
→ ещё более сжатая SUMMARY
```

---

# 39. Persistence после restart

MESSAGE CONTEXT хранится на диске.

Поэтому если до закрытия приложения сообщение было:

```text
COMPRESSED
```

после restart оно снова разрешается как:

```text
COMPRESSED
```

и UI отображает active summary.

То же относится к Restore:

если состояние переключено обратно на RAW, после restart активным остаётся RAW.

---

# 40. Live verification

Базовый lifecycle был проверен не только тестами, но и вручную в реальном UI.

Подтверждена последовательность:

```text
FULL
↓
видимый RAW
↓
СЖАТЬ
↓
реальный Compressor RUN
↓
Proposal
↓
Принять
↓
COMPRESSED
↓
в основном Chat видна summary
↓
Оригинал
↓
виден полный RAW
↓
Восстановить в контекст
↓
FULL
↓
в основном Chat снова виден RAW
```

---

# 41. Trace Active Context

При загрузке Chat Context runtime может фиксировать:

```text
messages
raw_messages
compressed_messages
chars
```

Таким образом можно различать:

```text
сколько сообщений используется как RAW
```

и:

```text
сколько сообщений используется как SUMMARY
```

---

# 42. Project Context и Compressor

Context Compressor может получать Project Context как справочную информацию.

Но действует правило:

```text
RAW SOURCE = источник истины

PROJECT CONTEXT = справка
```

Факт не должен попадать в summary только потому, что он присутствует в Project Context, если его нет в исходном RAW MESSAGE.

---

# 43. Role Context

Project Context не нужно путать с Role Context.

Сейчас существуют отдельные app-level контексты ролей.

Например:

```text
MAIN CHAT ROLE CONTEXT

COMPRESSOR ROLE CONTEXT
```

Они хранят инструкции роли, а не память конкретного Workspace.

Поэтому:

```text
ROLE CONTEXT
≠
PROJECT CONTEXT
≠
CHAT HISTORY
```

---

# 44. Контекст не должен наследоваться скрытно

Физическая LLM не является владельцем постоянного состояния разговора.

Каждый runtime call должен получать нужный контекст явно.

Архитектурная формула:

```text
ROLE CONTEXT
+
ALLOWED SHARED CONTEXT
+
RUN CONTEXT
+
EXPLICIT TOOL SET
```

Полный универсальный CONTEXT POLICY framework пока ещё не реализован как общий Agent Profile mechanism.

---

# 45. Смена модели

MAIN CHAT MODEL можно менять независимо от хранения Chat.

Смена модели не меняет:

```text
Workspace
chat_id
message_id
RAW HISTORY
Project Context
Context Variants
active Working Representation
```

Assistant provenance позволяет при этом сохранять информацию о том, какая модель создала старый ответ.

---

# 46. Per-Chat Model Assignment

Полноценная схема:

```text
Workspace default model
↓
optional Chat-specific override
```

пока не реализована.

Текущий model selector уже позволяет выбирать MAIN CHAT MODEL, но отдельное persistent назначение модели каждому Chat является будущим слоем.

---

# 47. Context Policy

Архитектурно принято, что разные роли могут иметь разные разрешённые источники контекста.

Например:

```text
MAIN CHAT
→ Role Context
→ Project Context
→ Working Chat Context
→ tools

COMPRESSOR
→ Compressor Role Context
→ разрешённый Project Context
→ RAW SOURCE
→ compression templates
→ tools none
```

Универсальный Context Policy пока не оформлен как отдельный общий runtime abstraction.

---

# 48. Будущий Review / Discussion Chat

Следующим планируемым развитием Compression Proposal является message-scoped Review Chat.

Он должен работать только вокруг конкретного:

```text
message_id
```

и иметь доступ к:

```text
RAW SOURCE
CURRENT PROPOSAL
REVIEW DIALOGUE
```

Его задача — позволить пользователю обсудить с Compressor качество конкретной summary.

---

# 49. Review не должен сам менять Proposal

Обычное сообщение пользователя в Review Chat должно означать:

```text
обсуждение
```

а не:

```text
автоматическую замену summary
```

Для создания новой версии планируется отдельное действие:

```text
Сформировать новую версию
```

---

# 50. Будущий независимый Verifier для Compressor

Independent Execution Verifier с Final Audit уже реализован и описан в `13_Архитектура оперативной верификации и контроля выполнения задач.md`. Здесь речь только о будущем отдельном semantic check для Compressor pipeline.

Он должен быть отдельным runtime call/role.

Задача:

```text
RAW
+
CANDIDATE SUMMARY
↓
проверка смысловых потерь и искажений
```

Текущий optional Final Check Compressor не считается отдельным независимым Verifier.

---

# 51. Automatic Context Management

Автоматическое сжатие истории при приближении к context limit пока не реализовано.

Текущая модель управления:

```text
пользователь выбирает сообщение
↓
явно запускает compression
↓
проверяет Proposal
↓
решает, активировать ли summary
```

Это сохраняет полный пользовательский контроль.

---

# 52. Token / Context Budget

Полноценный автоматический token-budget manager пока отсутствует.

Сейчас runtime может учитывать объём Working Context по символам и состояниям сообщений. Отдельно Run Store v2 сохраняет фактический provider usage для Planner / Executor / Dredd и агрегирует его в summary; если usage отсутствует, token count не угадывается, а char metrics не называются токенами. Полноценное автоматическое управление context budget остаётся будущей задачей.

# 55. Что в TASK 06.5 ещё осталось

Не реализованы:

```text
Review / Discussion Chat
Independent Compressor Verifier
автоматический context-budget manager
automatic compression near model limit
полноценная semantic verification pipeline
```

Эти функции являются дальнейшим развитием уже существующего механизма, а не заменой нынешней архитектуры.

`task_block_id` связывает одну логическую пользовательскую TASK с её user message, assistant result при успешном возврате worker и server-owned Audit Thread. `message_id` идентифицирует persistent Chat message; `run_id` идентифицирует Main RUN; `verifier_run_id` относится к отдельной проверке. Один SEND создаёт один Task Block, а audit events не включаются в обычный LLM Chat context. Подробности Final Audit, permission и observability принадлежат `13_Архитектура оперативной верификации и контроля выполнения задач.md`.

## TASK 147 — live/storage audit Chat identity и Working Representation

На 2026-09-30 повторно проверена фактическая Chat storage цепочка после TASK 139–146.

Подтверждено:

- все 158 существующих RAW MESSAGE имеют согласованные `workspace_id/chat_id/message_id`; duplicate `message_id` и cross-chat identity mismatch не обнаружены;
- `load_chat_working_messages()` успешно собрал каждый видимый Chat fail-closed без foreign message ids;
- существующие active SUMMARY сохранились и принадлежат своим RAW MESSAGE: 9 summary representations в `Документация_Закрыто` и 3 в `Документы_2`; текущий `Чат 7` использует 26/26 RAW representations;
- controlled two-Chat test подтвердил: SUMMARY в Chat A не меняет Working Representation Chat B; lookup RAW MESSAGE по чужому `chat_id` блокируется;
- отдельный второй Python process после создания temporary Workspace подтвердил restart persistence RAW/SUMMARY state;
- реальный `UltraApp` восстановил из `%LOCALAPPDATA%/GigaChatUltra/ui_state.json` правильный Workspace и `last_chat_id=chat_b36a4eba7fdf47f98b1d71507bc2938d`; controlled UI switch `Чат 7 → Чат 5 → Чат 7` перестроил message/task-block binding 26 → 2 → 26 без leakage;
- Run Store v2 содержит 15 Task/15 RUN; для каждого indexed Task найден RAW USER в том же Chat, RUN↔Task↔Chat identity mismatch не обнаружен. Старые raw task blocks, созданные до Run Store v2, намеренно не мигрировались массово.

Аудит выявил два durability gap, которые не считаются cross-chat leakage:

1. **RESOLVED в TASK 147A:** `create_chat()` больше не публикует частично созданную directory внутри `.ultra/chats`. Новый Chat полностью собирается в `.ultra/chat_staging/<chat_id>.<uuid>.tmp` (`messages/`, `summaries/`, `metadata.json`) и только после успешной сборки публикуется одним `os.replace(staging_dir, chat_dir)`. При обычном exception staging удаляется; при hard crash незавершённая staging directory остаётся вне visible Chat namespace и не может попасть в `list_existing_chats()`/Working Context. Старый пустой `chat_2224a4cf0fca4a72ab61cb383f8053a1` после audit-evidence удалён.
2. **RESOLVED в TASK 147B:** exception path `ultra_ui._worker()` теперь формирует persistent terminal ASSISTANT RAW вида `RUN STATUS: FAILED\n<ExceptionType>: <message>` с тем же `task_block_id`. Если `run_started` уже дал валидный producer snapshot, он сохраняется вместе с terminal message; если failure произошёл до `run_started`, producer не выдумывается и сохраняется provenance warning. Если сама terminal persistence падает, ошибка storage остаётся видимой в UI payload и не маскируется.

После TASK 147A/147B Chat creation и terminal history стали crash/exception durable в проверенных сценариях. Исторические USER-only blocks T-004/T-005/T-008/T-010/T-013/T-014 не переписывались задним числом.

# 56. Основные инварианты

```text
Workspace имеет постоянный workspace_id.

Chat имеет постоянный chat_id.

Message имеет постоянный message_id.

RAW MESSAGE после создания не переписывается.

RAW HISTORY переживает restart.

Project Context общий для Chat одного Workspace.

Project Context не равен Chat History.

Role Context не равен Project Context.

Working Representation существует отдельно от RAW.

SUMMARY не уничтожает RAW.

LLM не активирует Proposal без пользователя.

Original Viewer всегда показывает RAW.

Просмотр Original не означает Restore.

Restore явно переключает Working Representation на RAW.

Recompression выполняется от RAW.

MAIN CHAT получает active Working Representation.

Видимый Chat показывает active Working Representation.

Смена MODEL не уничтожает память Chat.

Provider-side session не является источником истины.
```

# Главная идея

Контекст в `ag_llm` является управляемой частью runtime и Workspace, а не скрытой памятью конкретной LLM.

Пользователь может:

```text
сохранить полный RAW
↓
сжать конкретное сообщение
↓
проверить Proposal
↓
принять или отклонить
↓
редактировать Working Representation
↓
посмотреть оригинал
↓
восстановить RAW
↓
повторно сжать исходный RAW
```

При этом полная исходная история не уничтожается.

Такой подход позволяет постепенно уменьшать Active Chat Context без потери исходных данных и без привязки памяти проекта к конкретной модели.
