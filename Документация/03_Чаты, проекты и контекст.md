# Чаты, проекты и контекст в GigaChat Ultra Local Agent

Этот документ описывает фактическую модель организации Workspace, Chat, истории сообщений и управляемого контекста в текущем `ag_llm`.

Основная карта проекта:

[[00_Главная - карта проекта]]

---

# 1. Главная иерархия

Базовая структура системы:

```text
WORKSPACE
│
├── PROJECT CONTEXT
│
└── CHAT
    │
    ├── RAW HISTORY
    │   └── RAW MESSAGE
    │
    └── MESSAGE CONTEXT
        ├── STATE
        └── CONTEXT VARIANTS
```

Главный принцип:

```text
WORKSPACE
≠
CHAT
≠
RAW HISTORY
≠
WORKING CONTEXT
≠
PROJECT CONTEXT
```

Это разные сущности с разным назначением.

---

# 2. Workspace

Workspace — корневая директория конкретного проекта.

Он определяет:

```text
область файлов проекта
PROJECT CONTEXT
набор Chat
переносимое внутреннее состояние
```

Каждый Workspace имеет постоянный:

```text
workspace_id
```

Внутреннее переносимое состояние хранится в:

```text
.ultra/
```

---

# 3. Несколько Workspace

UI поддерживает работу с несколькими Workspace.

Реализованы:

```text
создание Workspace
подключение существующего Workspace
переключение Workspace
переименование Workspace
удаление Workspace из локального registry
```

Удаление Workspace из registry не означает физическое удаление проекта с диска.

---

# 4. Portable Workspace State

Переносимое состояние проекта находится внутри:

```text
.ultra/
```

Оно должно перемещаться вместе с проектом между компьютерами.

К нему относятся:

```text
workspace identity
Project Context
Chat metadata
RAW HISTORY
MESSAGE CONTEXT STATE
Context Variants
```

---

# 5. Local Machine State

От portable Workspace state отделяется состояние конкретного компьютера.

Например:

```text
UI settings
Workspace registry
backup paths
run log paths
Role Context
локальные runtime settings
```

Эти данные не должны без необходимости становиться частью переносимого проекта.

---

# 6. Project Context

Один Workspace имеет общий:

```text
PROJECT CONTEXT
```

Он хранится в:

```text
.ultra/project_context.md
```

Project Context является общей проектной памятью для всех Chat данного Workspace.

Он может содержать:

```text
назначение проекта
устойчивые факты
архитектурные решения
термины
ограничения
важное текущее состояние
```

Project Context не является полной историей разговоров.

---

# 7. Project Context и Chat

Все Chat одного Workspace используют один общий Project Context.

Схема:

```text
WORKSPACE
│
├── PROJECT CONTEXT
│
├── CHAT A
├── CHAT B
└── CHAT C
```

Переключение Chat:

```text
НЕ меняет Workspace
НЕ меняет Project Context
меняет текущую историю разговора
меняет Working Chat Context
```

---

# 8. Project Context revisions

Project Context редактируется через контролируемый Context Storage API.

Реализована история предыдущих версий.

Таким образом изменение Project Context не должно уничтожать предыдущую версию без возможности восстановления через storage history.

Обычные file-agent tools не должны напрямую переписывать внутреннее `.ultra` storage.

---

# 9. Chat

Chat — отдельная ветка разговора внутри Workspace.

Каждый Chat имеет постоянный:

```text
chat_id
```

и собственные:

```text
metadata
RAW HISTORY
MESSAGE CONTEXT STATE
Working Chat Context
```

Один Workspace может содержать несколько независимых Chat.

---

# 10. Chat metadata

Метаданные Chat хранятся отдельно.

Пример логической структуры:

```text
.ultra/
└── chats/
    └── <chat_id>/
        └── metadata.json
```

Chat metadata содержит необходимые данные самого Chat, включая его identity и информацию, используемую UI/storage.

---

# 11. Навигация по Chat

Реализованы:

```text
создание Chat
переключение Chat
переименование Chat
persistent сохранение
восстановление после restart
```

Удаление Chat пока не является завершённой production-функцией.

Поэтому TASK 06.2 остаётся формально:

```text
В РАБОТЕ
```

несмотря на то, что основная навигация уже функционирует.

---

# 12. RAW HISTORY

Каждый Chat имеет собственную RAW HISTORY.

Каждое сообщение сохраняется отдельным RAW MESSAGE.

Пример структуры:

```text
.ultra/
└── chats/
    └── <chat_id>/
        └── messages/
            ├── <message_id>.json
            ├── <message_id>.json
            └── ...
```

---

# 13. Identity сообщений

Основная цепочка identity:

```text
workspace_id
↓
chat_id
↓
message_id
```

Каждое сообщение имеет постоянный:

```text
message_id
```

Это позволяет привязывать к одному конкретному сообщению:

```text
RAW
Context State
Context Variants
Compression metadata
действия UI
```

---

# 14. RAW MESSAGE

RAW MESSAGE содержит первоначальный текст сообщения.

Основное поле:

```text
original_text
```

RAW является:

```text
immutable source of truth
```

После создания RAW не должен переписываться из-за:

```text
сжатия
ручного редактирования summary
смены модели
Restore
повторного сжатия
перезапуска приложения
```

---

# 15. Когда сохраняется RAW

User RAW сохраняется до основного API request.

Assistant RAW сохраняется как persistent message при успешном завершении соответствующего процесса.

История поэтому существует независимо от памяти внешнего LLM provider.

---

# 16. Producer metadata

Для новых assistant messages может сохраняться информация о модели, которая создала ответ.

Например:

```text
kind
role_id
run_id
model_id
model_display_name
provider
provider_model_id
```

Это позволяет после restart сохранять provenance конкретного ответа.

Смена текущей MAIN CHAT MODEL не переписывает provenance старых сообщений.

---

# 17. История не принадлежит LLM

Chat History принадлежит runtime/storage.

Она не является provider-side conversation session.

Принцип:

```text
LLM
можно заменить

CHAT HISTORY
остаётся
```

Смена модели не должна уничтожать:

```text
chat_id
message_id
RAW HISTORY
Project Context
MESSAGE CONTEXT STATE
Context Variants
```

---

# 18. Multi-turn Context

Настоящий multi-turn Chat уже реализован.

При новом MAIN CHAT RUN runtime загружает историю выбранного Chat и формирует сообщения для модели.

История другого Chat автоматически не смешивается с текущим.

Таким образом:

```text
CHAT A
→ свой conversation context

CHAT B
→ свой conversation context
```

при общем Project Context одного Workspace.

---

# 19. RAW HISTORY и Active Context — не одно и то же

Раньше фактический Active Chat Context практически совпадал с RAW HISTORY.

Теперь между ними существует отдельный слой:

```text
WORKING REPRESENTATION
```

Поэтому:

```text
RAW HISTORY
≠
ACTIVE CHAT CONTEXT
```

RAW HISTORY хранит оригиналы.

Active Chat Context содержит версии сообщений, которые runtime реально выбрал для передачи MAIN CHAT MODEL.

---

# 20. MESSAGE CONTEXT

Для user и assistant messages реализовано отдельное состояние контекста.

Пример структуры:

```text
.ultra/
└── chats/
    └── <chat_id>/
        └── message_context/
            └── <message_id>/
                ├── state.json
                └── variants/
                    ├── ctxv_<uuid>.json
                    └── ...
```

RAW MESSAGE при этом остаётся отдельно в:

```text
messages/
```

---

# 21. MESSAGE CONTEXT STATE

`state.json` определяет, какое представление конкретного сообщения сейчас активно.

Основные состояния:

```text
RAW
```

и:

```text
SUMMARY
```

Фактически:

```text
active_representation = raw
```

или:

```text
active_representation = summary
```

---

# 22. FULL

Когда активно:

```text
active_representation = raw
```

состояние UI называется:

```text
FULL
```

В этом состоянии:

```text
CHAT показывает RAW
MAIN CHAT получает RAW
```

---

# 23. COMPRESSED

Когда активно:

```text
active_representation = summary
```

состояние UI называется:

```text
COMPRESSED
```

В этом состоянии:

```text
CHAT показывает active Context Variant
MAIN CHAT получает active Context Variant
```

RAW при этом продолжает существовать отдельно и не изменяется.

---

# 24. Context Variant

Context Variant — отдельная рабочая версия сообщения.

Он может быть создан:

```text
LLM compression
manual edit
```

Variant имеет собственный:

```text
context_variant_id
```

и может содержать:

```text
text
source
parent_variant_id
manually_edited
compression metadata
```

---

# 25. Старые варианты не уничтожаются

Создание новой рабочей версии не должно автоматически уничтожать предыдущие Context Variants.

Активным является только один вариант.

Остальные могут сохраняться как история предыдущих representations.

Это отдельно от immutable RAW.

---

# 26. Working Representation

Для каждого user/assistant message runtime может получить:

```text
WORKING REPRESENTATION
```

Она разрешается так:

```text
если state = RAW
→ original_text

если state = SUMMARY
→ active Context Variant
```

Именно Working Representation используется при построении Chat Context для MAIN CHAT.

---

# 27. Сборка Working Chat Context

Server использует рабочие representations сообщений текущего Chat.

Логически:

```text
CHAT HISTORY
↓
для каждого message_id
↓
resolve MESSAGE CONTEXT STATE
↓
RAW или active SUMMARY
↓
сохранить исходный role и порядок
↓
ACTIVE CHAT CONTEXT
```

Текущая реализация использует:

```text
load_chat_working_messages()
```

---

# 28. Порядок сообщений

Context Compression не меняет хронологию Chat.

Например:

```text
USER RAW
ASSISTANT SUMMARY
USER RAW
ASSISTANT RAW
```

по-прежнему передаются модели в исходном порядке ролей.

Меняется только текстовое representation отдельного сообщения.

---

# 29. Отображение Chat

Текущий UI показывает пользователю активную Working Representation.

Поэтому:

```text
FULL
→ пользователь видит RAW

COMPRESSED
→ пользователь видит SUMMARY
```

Это сделано намеренно.

Видимое сообщение соответствует тому тексту, который MAIN CHAT использует как active representation.

---

# 30. Просмотр RAW

Для доступа к неизменяемому оригиналу существует действие:

```text
Оригинал
```

Оно открывает отдельный read-only viewer.

Viewer всегда получает:

```text
original_text
```

а не active summary.

---

# 31. Просмотр оригинала не меняет Context

Само открытие:

```text
Оригинал
```

ничего не переключает.

Если пользователь просто открыл и закрыл окно:

```text
MESSAGE CONTEXT STATE
не изменяется
```

---

# 32. Restore

Если сообщение находится в состоянии COMPRESSED, Original Viewer позволяет выполнить:

```text
Восстановить в контекст
```

После Restore:

```text
active_representation = raw
active_variant_id = None
```

После этого:

```text
CHAT снова показывает RAW
MAIN CHAT снова получает RAW
```

Существовавшая summary не обязана удаляться.

---

# 33. Управляемое сжатие сообщения

Для сообщения доступна операция:

```text
Сжать
```

Базовый lifecycle уже реализован:

```text
FULL
↓
СЖАТЬ
↓
COMPRESSION PROPOSAL
↓
USER DECISION
↓
COMPRESSED
```

---

# 34. COMPRESSION PROPOSAL

LLM Compressor сначала создаёт только предложение.

Proposal содержит новую возможную Working Representation.

До пользовательского подтверждения:

```text
RAW не меняется
active representation не меняется
persistent summary не активируется
```

---

# 35. Решение пользователя

Пользователь может:

```text
Принять
```

или:

```text
отредактировать Proposal
и Принять
```

или:

```text
Отклонить
```

LLM не должна самостоятельно решать, что новая summary становится active.

---

# 36. Accept

После Accept:

```text
создаётся Context Variant
↓
variant сохраняется
↓
state переключается на SUMMARY
↓
UI rerender
↓
CHAT показывает summary
```

MAIN CHAT после этого также получает summary.

---

# 37. Manual Edit

Рабочее representation можно редактировать вручную.

Если сообщение уже COMPRESSED:

```text
редактируется active working version
```

и создаётся новый Context Variant.

Если сообщение FULL, система также может создать manual working variant без изменения RAW.

---

# 38. Recompression

LLM recompression не должна выполняться от предыдущей summary.

Канонический workflow:

```text
RAW
↓
COMPRESS
↓
SUMMARY
↓
RESTORE
↓
RAW
↓
COMPRESS AGAIN
```

Новый Compressor RUN получает исходный immutable RAW.

Это предотвращает деградацию:

```text
SUMMARY
→ ещё более сжатая SUMMARY
→ ещё более сжатая SUMMARY
```

---

# 39. Persistence после restart

MESSAGE CONTEXT хранится на диске.

Поэтому если до закрытия приложения сообщение было:

```text
COMPRESSED
```

после restart оно снова разрешается как:

```text
COMPRESSED
```

и UI отображает active summary.

То же относится к Restore:

если состояние переключено обратно на RAW, после restart активным остаётся RAW.

---

# 40. Live verification

Базовый lifecycle был проверен не только тестами, но и вручную в реальном UI.

Подтверждена последовательность:

```text
FULL
↓
видимый RAW
↓
СЖАТЬ
↓
реальный Compressor RUN
↓
Proposal
↓
Принять
↓
COMPRESSED
↓
в основном Chat видна summary
↓
Оригинал
↓
виден полный RAW
↓
Восстановить в контекст
↓
FULL
↓
в основном Chat снова виден RAW
```

---

# 41. Trace Active Context

При загрузке Chat Context runtime может фиксировать:

```text
messages
raw_messages
compressed_messages
chars
```

Таким образом можно различать:

```text
сколько сообщений используется как RAW
```

и:

```text
сколько сообщений используется как SUMMARY
```

---

# 42. Project Context и Compressor

Context Compressor может получать Project Context как справочную информацию.

Но действует правило:

```text
RAW SOURCE = источник истины

PROJECT CONTEXT = справка
```

Факт не должен попадать в summary только потому, что он присутствует в Project Context, если его нет в исходном RAW MESSAGE.

---

# 43. Role Context

Project Context не нужно путать с Role Context.

Сейчас существуют отдельные app-level контексты ролей.

Например:

```text
MAIN CHAT ROLE CONTEXT

COMPRESSOR ROLE CONTEXT
```

Они хранят инструкции роли, а не память конкретного Workspace.

Поэтому:

```text
ROLE CONTEXT
≠
PROJECT CONTEXT
≠
CHAT HISTORY
```

---

# 44. Контекст не должен наследоваться скрытно

Физическая LLM не является владельцем постоянного состояния разговора.

Каждый runtime call должен получать нужный контекст явно.

Архитектурная формула:

```text
ROLE CONTEXT
+
ALLOWED SHARED CONTEXT
+
RUN CONTEXT
+
EXPLICIT TOOL SET
```

Полный универсальный CONTEXT POLICY framework пока ещё не реализован как общий Agent Profile mechanism.

---

# 45. Смена модели

MAIN CHAT MODEL можно менять независимо от хранения Chat.

Смена модели не меняет:

```text
Workspace
chat_id
message_id
RAW HISTORY
Project Context
Context Variants
active Working Representation
```

Assistant provenance позволяет при этом сохранять информацию о том, какая модель создала старый ответ.

---

# 46. Per-Chat Model Assignment

Полноценная схема:

```text
Workspace default model
↓
optional Chat-specific override
```

пока не реализована.

Текущий model selector уже позволяет выбирать MAIN CHAT MODEL, но отдельное persistent назначение модели каждому Chat является будущим слоем.

---

# 47. Context Policy

Архитектурно принято, что разные роли могут иметь разные разрешённые источники контекста.

Например:

```text
MAIN CHAT
→ Role Context
→ Project Context
→ Working Chat Context
→ tools

COMPRESSOR
→ Compressor Role Context
→ разрешённый Project Context
→ RAW SOURCE
→ compression templates
→ tools none
```

Универсальный Context Policy пока не оформлен как отдельный общий runtime abstraction.

---

# 48. Будущий Review / Discussion Chat

Следующим планируемым развитием Compression Proposal является message-scoped Review Chat.

Он должен работать только вокруг конкретного:

```text
message_id
```

и иметь доступ к:

```text
RAW SOURCE
CURRENT PROPOSAL
REVIEW DIALOGUE
```

Его задача — позволить пользователю обсудить с Compressor качество конкретной summary.

---

# 49. Review не должен сам менять Proposal

Обычное сообщение пользователя в Review Chat должно означать:

```text
обсуждение
```

а не:

```text
автоматическую замену summary
```

Для создания новой версии планируется отдельное действие:

```text
Сформировать новую версию
```

---

# 50. Будущий независимый Verifier для Compressor

Independent Execution Verifier с Final Audit уже реализован и описан в `13_Архитектура оперативной верификации и контроля выполнения задач.md`. Здесь речь только о будущем отдельном semantic check для Compressor pipeline.

Он должен быть отдельным runtime call/role.

Задача:

```text
RAW
+
CANDIDATE SUMMARY
↓
проверка смысловых потерь и искажений
```

Текущий optional Final Check Compressor не считается отдельным независимым Verifier.

---

# 51. Automatic Context Management

Автоматическое сжатие истории при приближении к context limit пока не реализовано.

Текущая модель управления:

```text
пользователь выбирает сообщение
↓
явно запускает compression
↓
проверяет Proposal
↓
решает, активировать ли summary
```

Это сохраняет полный пользовательский контроль.

---

# 52. Token / Context Budget

Полноценный автоматический token-budget manager пока отсутствует.

Сейчас runtime может учитывать объём Working Context по символам и состояниям сообщений, но полноценное управление token budget является будущей задачей.

```text
Review / Discussion Chat
Independent Compressor Verifier
автоматический context-budget manager
automatic compression near model limit
полноценная semantic verification pipeline
```

Эти функции являются дальнейшим развитием уже существующего механизма, а не заменой нынешней архитектуры.

`task_block_id` связывает одну логическую пользовательскую TASK с её user message, successful assistant message и server-owned Audit Thread. `message_id` идентифицирует persistent Chat message; `run_id` идентифицирует Main RUN; `verifier_run_id` относится к отдельной проверке. Один SEND создаёт один Task Block, а audit events не включаются в обычный LLM Chat context. Подробности Final Audit, permission и observability принадлежат `13_Архитектура оперативной верификации и контроля выполнения задач.md`.

# 56. Основные инварианты

```text
Workspace имеет постоянный workspace_id.

Chat имеет постоянный chat_id.

Message имеет постоянный message_id.

RAW MESSAGE после создания не переписывается.

RAW HISTORY переживает restart.

Project Context общий для Chat одного Workspace.

Project Context не равен Chat History.

Role Context не равен Project Context.

Working Representation существует отдельно от RAW.

SUMMARY не уничтожает RAW.

LLM не активирует Proposal без пользователя.

Original Viewer всегда показывает RAW.

Просмотр Original не означает Restore.

Restore явно переключает Working Representation на RAW.

Recompression выполняется от RAW.

MAIN CHAT получает active Working Representation.

Видимый Chat показывает active Working Representation.

Смена MODEL не уничтожает память Chat.

Provider-side session не является источником истины.
```

# Главная идея

Контекст в `ag_llm` является управляемой частью runtime и Workspace, а не скрытой памятью конкретной LLM.

Пользователь может:

```text
сохранить полный RAW
↓
сжать конкретное сообщение
↓
проверить Proposal
↓
принять или отклонить
↓
редактировать Working Representation
↓
посмотреть оригинал
↓
восстановить RAW
↓
повторно сжать исходный RAW
```

При этом полная исходная история не уничтожается.

Такой подход позволяет постепенно уменьшать Active Chat Context без потери исходных данных и без привязки памяти проекта к конкретной модели.
