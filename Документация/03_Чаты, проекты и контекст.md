# GigaChat Ultra Local Agent

GigaChat Ultra Local Agent — локальная агентская среда для работы с проектами, файлами, Workspace, Chat, долговременным контекстом и подключаемыми LLM.

Проект уже вышел за рамки схемы:

```text
одна программа
↓
одна жёстко заданная модель
```

и фактически развивается как:

```text
LOCAL AGENT RUNTIME
        ↓
MODEL REGISTRY
        ↓
MODEL ASSIGNMENT
        ↓
специализированные роли
        ↓
Workspace / Chat / Context / Tools
```

Основной принцип проекта:

> LLM является сменным вычислительным компонентом.  
> Контекст, память, Workspace, инструменты, permissions, backup, verification и lifecycle принадлежат runtime, а не самой модели.

# 1. Текущее состояние проекта

Система уже имеет работающий локальный runtime, persistent Workspace/Chat storage, мультимодельный GigaChat foundation и управляемый per-message Context Compression.

Текущая рабочая схема в упрощённом виде:

```text
USER
↓
Ultra UI
↓
Agent Runtime
↓
MAIN CHAT MODEL ASSIGNMENT
↓
MODEL REGISTRY
↓
GigaChat provider
↓
выбранная GigaChat model
```

Для сжатия контекста существует отдельный путь:

```text
RAW MESSAGE
↓
COMPRESSOR ROLE
↓
COMPRESSION MODEL ASSIGNMENT
↓
MODEL REGISTRY
↓
выбранная GigaChat model
↓
COMPRESSION PROPOSAL
↓
USER ACCEPT / EDIT / REJECT
↓
ACTIVE WORKING REPRESENTATION
```

# 3. Workspace

Workspace является корнем конкретного проекта.

Переносимое внутреннее состояние хранится в:

```text
.ultra/
```

Workspace имеет постоянный:

```text
workspace_id
```

В одном UI может быть зарегистрировано несколько Workspace.

Пользователь может:

```text
создавать Workspace
подключать Workspace
переключаться между Workspace
переименовывать Workspace
удалять Workspace из локального UI registry
```

Удаление из UI registry не означает удаление самого проекта с диска.

---

# 4. Portable state и local runtime state

Переносимое состояние проекта:

```text
.ultra/
```

должно перемещаться вместе с Workspace.

Локальное состояние конкретного компьютера хранится отдельно.

К нему относятся, например:

```text
backup directories
run log directories
UI state
локальные runtime-настройки
agent-level context
```

Portable project state и machine-local runtime state не должны смешиваться.

---

# 5. Chat

Один Workspace может иметь несколько независимых Chat.

Каждый Chat имеет постоянный:

```text
chat_id
```

Реализованы:

```text
создание Chat
переключение Chat
переименование Chat
persistent history
восстановление истории после restart
изоляция истории разных Chat
```

Удаление Chat пока не является завершённой production-функцией.

---

# 6. RAW HISTORY

Каждое сообщение Chat сохраняется как отдельный RAW MESSAGE.

Используются постоянные identity:

```text
workspace_id
chat_id
message_id
```

RAW MESSAGE содержит исходный текст:

```text
original_text
```

RAW является immutable source of truth.

Сжатие, ручное редактирование рабочей версии или восстановление контекста не должны переписывать RAW MESSAGE.

---

# 7. Project Context

Каждый Workspace имеет общий:

```text
PROJECT CONTEXT
```

Он доступен всем Chat данного Workspace.

Хранится в:

```text
.ultra/project_context.md
```

Project Context:

```text
загружается перед RUN
редактируется через UI
имеет историю ревизий
переносится вместе с Workspace
```

Обычные file-agent tools не должны напрямую переписывать внутренний `.ultra` storage.

Работа с внутренним состоянием выполняется через контролируемый storage API.

---

# 8. Global / Role Context

Помимо Project Context существует app-level контекст роли.

Например:

```text
MAIN CHAT ROLE CONTEXT
COMPRESSOR ROLE CONTEXT
```

Эти контексты хранятся локально вне Workspace.

Они описывают поведение конкретной роли, а не состояние конкретного проекта.

Это позволяет разделять:

```text
ROLE CONTEXT
PROJECT CONTEXT
CHAT CONTEXT
```

---

# 9. Model Registry

MODEL REGISTRY уже реализован как отдельный слой.

Он описывает доступные модели независимо от того, где именно они используются.

В текущем registry присутствуют несколько GigaChat-моделей.

Среди них:

```text
GigaChat 2
GigaChat 2 Max
GigaChat 2 Pro
GigaChat 3 Lightning
GigaChat 3 Pro
GigaChat 3 Ultra
```

MODEL REGISTRY не должен хранить смысл конкретной роли.

Он является справочником доступных моделей.

---

# 10. MAIN CHAT MODEL ASSIGNMENT

Основная модель Chat больше не обязана быть жёстко заданной как одна GigaChat Ultra.

В UI реализован выбор MAIN CHAT MODEL.

Выбранная модель используется для конкретного MAIN CHAT RUN.

Runtime фиксирует её metadata:

```text
model_id
model_display_name
provider
provider_model_id
```

Assistant message сохраняет producer metadata.

Благодаря этому история Chat после restart продолжает показывать, какой моделью был создан конкретный ответ.

---

# 11. GigaChat Multi-Model

Практически подтверждена работа нескольких моделей через существующий GigaChat backend.

То есть мультимодельность уже не является только архитектурным планом.

Рабочая схема:

```text
MODEL ASSIGNMENT
↓
MODEL REGISTRY
↓
GigaChat provider
↓
конкретная GigaChat model
```

Обобщённый Provider Adapter для произвольных внешних и локальных backend ещё не является завершённой production-системой.

---

# 12. Context Compressor

Реализована отдельная роль:

```text
COMPRESSOR
```

Она имеет собственный:

```text
role context
model assignment
prompt configuration
runtime
```

COMPRESSOR работает независимо от MAIN CHAT MODEL.

Например:

```text
MAIN CHAT MODEL
    GigaChat 3 Ultra

COMPRESSOR MODEL
    GigaChat 3 Pro
```

---

# 13. Изоляция Compressor

COMPRESSOR не является обычным Chat Agent.

Ему не предоставляются file-agent tools.

Базовый принцип:

```text
COMPRESSOR TOOLS = NONE
```

Каждый запрос Compressor создаётся server/runtime отдельно.

Модель не должна автоматически наследовать скрытый provider-side Chat history.

Контекст операции собирается явно.

---

# 14. Контекст Compressor

Текущий Compressor может получать:

```text
ROLE CONTEXT
PROJECT CONTEXT
MESSAGE COMPRESSION TEMPLATE
RUNTIME TARGET
RAW SOURCE
optional FINAL CHECK
```

При этом:

```text
RAW SOURCE = source of truth
PROJECT CONTEXT = reference only
```

COMPRESSOR не должен добавлять в summary факты только потому, что они присутствуют в Project Context.

---

# 15. Настройки сжатия

В UI доступны:

```text
Compressor Model
Reduction Percent
Role Context
Message Compression Template
Additional Final Check
Final Check Template
```

Поддерживаются runtime placeholders:

```text
{{REDUCTION_PERCENT}}
{{REMAINING_PERCENT}}
```

Целевой процент является ориентиром.

Сохранение смысла важнее точного попадания в математический процент.

---

# 16. Compressor Guard

После получения результата runtime выполняет soft guard.

Он отклоняет, например:

```text
пустой результат
результат, равный RAW
результат длиннее RAW
практически отсутствующее сокращение
```

При необходимости возможен один corrective retry.

Guard не является полноценным независимым Verifier.

---

# 17. Per-message Working Representation

Для user/assistant messages реализован отдельный MESSAGE CONTEXT STATE.

Сообщение может находиться в состоянии:

```text
FULL
```

или:

```text
COMPRESSED
```

В storage это соответствует:

```text
active_representation = raw
```

или:

```text
active_representation = summary
```

---

# 18. MESSAGE CONTEXT storage

Для каждого сообщения может существовать отдельный context state и набор вариантов.

Схема:

```text
.ultra/
└── chats/
    └── <chat_id>/
        ├── messages/
        │   └── <message_id>.json
        │
        └── message_context/
            └── <message_id>/
                ├── state.json
                └── variants/
                    └── ctxv_<id>.json
```

RAW MESSAGE хранится отдельно.

Context Variant никогда не заменяет исходный RAW-файл.

---

# 19. Context Variant

Context Variant является альтернативным рабочим представлением сообщения.

Он может быть создан:

```text
LLM compression
manual edit
```

Variant имеет собственный:

```text
context_variant_id
```

Старые варианты сохраняются.

Активация нового варианта меняет только MESSAGE CONTEXT STATE.

---

# 20. Управляемое сжатие сообщения

Реализован рабочий lifecycle:

```text
RAW
↓
СЖАТЬ
↓
COMPRESSION PROPOSAL
↓
Принять / изменить / отклонить
↓
COMPRESSED
```

Proposal не становится активным автоматически.

Только явное действие пользователя активирует Context Variant.

---

# 21. COMPRESSION PROPOSAL

Окно Proposal показывает:

```text
RAW SOURCE
предлагаемую рабочую версию
model
target reduction
actual reduction
character counts
```

Пользователь может:

```text
Принять
изменить текст перед принятием
Отклонить
```

До принятия persistent context сообщения не изменяется.

---

# 22. Отображение CHAT

Текущий CHAT показывает активную WORKING REPRESENTATION.

То есть:

```text
FULL
→ CHAT показывает RAW
```

```text
COMPRESSED
→ CHAT показывает active summary
```

Это не означает изменение RAW HISTORY.

RAW остаётся отдельным immutable источником.

---

# 23. Original Viewer

Возле сообщения существует действие:

```text
Оригинал
```

Оно открывает immutable RAW MESSAGE.

Если сейчас активна summary, пользователь видит:

```text
Сейчас в контексте используется сжатая версия.
```

и может выполнить:

```text
Восстановить в контекст
```

Простое открытие или закрытие Original Viewer не изменяет состояние.

---

# 24. Restore RAW

При:

```text
Восстановить в контекст
```

MESSAGE CONTEXT переключается обратно на:

```text
active_representation = raw
active_variant_id = None
```

После этого:

```text
CHAT снова показывает RAW
MAIN CHAT снова получает RAW
```

Существовавшие Context Variant при этом не удаляются.

---

# 25. Повторное сжатие

После Restore пользователь может снова выполнить:

```text
Сжать
```

Новый Compressor RUN всегда должен брать:

```text
immutable RAW original_text
```

а не предыдущую summary.

Это защищает систему от последовательной деградации:

```text
summary
→ summary
→ summary
```

Канонический источник для нового LLM compression всегда RAW.

---

# 26. Manual Edit

Рабочую версию сообщения можно редактировать вручную.

Если активна summary:

```text
редактируется active working representation
```

RAW при этом не меняется.

Новая ручная версия создаётся как новый Context Variant.

---

# 27. Active Chat Context

MAIN CHAT больше не обязан получать полную RAW HISTORY буквально.

Server собирает Chat history через:

```text
load_chat_working_messages()
```

Для каждого сообщения используется его текущая working representation:

```text
FULL
→ RAW

COMPRESSED
→ active summary
```

Порядок сообщений и роли сохраняются.

---

# 28. Active Context и RAW History — разные сущности

Необходимо строго различать:

```text
RAW HISTORY
```

и:

```text
ACTIVE / WORKING CONTEXT
```

RAW HISTORY хранит исходную историю.

ACTIVE CONTEXT содержит то представление, которое реально передаётся модели при конкретном RUN.

---

# 29. Trace Context Counters

Server trace фиксирует состояние загруженного Chat context.

В частности:

```text
messages
raw_messages
compressed_messages
chars
```

Это позволяет видеть, сколько active context реально построено из RAW и сколько из compressed representations.

Полный базовый lifecycle был проверен не только unit tests, но и вручную через реальный UI:

```text
FULL RAW
↓
COMPRESS
↓
реальный GigaChat Compressor
↓
PROPOSAL
↓
ACCEPT
↓
```

Таким образом базовая цепочка управляемого per-message compression реально работает.

# 32. Что в Context Compression ещё НЕ реализовано

Пока отсутствует полноценный независимый:

```text
VERIFIER
```

Также ещё не реализован:

```text
Review / Discussion Chat
```

для обсуждения конкретного Compression Proposal с Compressor.

Планируемая будущая схема:

```text
RAW SOURCE
+
CURRENT PROPOSAL
+
message-scoped Review Chat
```

с возможностью:

```text
сравнить RAW и Proposal
обсудить потери
уточнить требования
сформировать новую версию
```

Этот Review Chat должен быть временным и привязанным к конкретному message_id.

---

# 33. Будущий Verifier

Полноценный Verifier должен быть отдельной ролью.

Его задача:

```text
RAW
+
CANDIDATE SUMMARY
↓
проверка потерь / искажений
```

Verifier не должен автоматически приниматься за реализованный только потому, что Compressor имеет дополнительный Final Check prompt.

Текущий Final Check и будущий независимый Verifier — разные механизмы.

---

# 34. MAIN CHAT и Compressor — независимые роли

Система уже фактически движется к архитектуре:

```text
MAIN CHAT
    own model
    own role context
    own runtime behavior
    tools allowed by policy

COMPRESSOR
    own model
    own role context
    own runtime
    tools none

future VERIFIER
    own model
    own role context

    tools none
```

# 35. Context Policy

Архитектурно принято, что каждая роль должна получать только явно разрешённый контекст.

Общая идея:

```text
ROLE CONTEXT
+
ALLOWED SHARED CONTEXT
+
RUN CONTEXT
+
EXPLICIT TOOL SET
```

Полноценный универсальный CONTEXT POLICY / Agent Profile framework пока не реализован.

Сейчас необходимые правила частично закреплены непосредственно в runtime конкретных ролей.

---

# 36. Agent Profile — будущее развитие

Целевой Agent Profile должен объединять:

```text
role
model_assignment
role_context
context_policy
tool_set
permission_policy
state
execution_rules
```

Это будущий архитектурный слой.

MAIN CHAT и COMPRESSOR уже дают практическое основание для такого обобщения, но универсального Agent Profile runtime пока нет.

---

# 37. Local Provider

Полноценный Local Provider для Chat/Agent моделей пока не является production-функцией.

Архитектура должна позволять в будущем подключать:

```text
Ollama
другой local inference runtime
другой внешний API
```

без переноса Workspace/Context ownership внутрь provider.

---

# 38. Per-Chat Model Assignment

Пока модель MAIN CHAT выбирается на уровне текущего UI/runtime assignment.

Полноценная схема:

```text
Workspace default model
↓
optional Chat override
```

пока не является завершённой функцией.

---

# 39. Multi-Agent Coordinator

Автоматическая коммуникация нескольких Agent через центральный Coordinator пока не реализована.

Целевая схема:

```text
Agent A
↓
Coordinator / Runtime
↓
selected result/context
↓
Agent B
```

Агенты не должны скрытно наследовать внутренние provider sessions друг друга.

---

# 40. Safety / Permissions

Server/runtime физически контролирует действия модели.

Раздельно существуют permission scopes:

```text
READ
WRITE
DELETE
VERIFY
```

Модель не имеет права самостоятельно расширять разрешённый scope.

---

# 41. Backup

Перед изменяющими RUN используется backup.

Portable `.ultra` state и local backup storage разделены.

Для обычных изменяемых файлов может использоваться lazy backup непосредственно перед mutation.

---

# 42. Verification Gate

После файловых mutations модель не должна завершать RUN успешным отчётом без требуемых проверок.

В зависимости от ситуации используются:

```text
git_diff
git_status
python_compile
ui_smoke_test
другие verification tools
```

Verification должен соответствовать последней revision изменений.

---

# 43. VERIFY toggle

Runtime поддерживает включение и отключение verification tooling.

При:

```text
VERIFY = ON
```

доступны соответствующие проверочные tools.

При:

```text
VERIFY = OFF
```

они не должны оставаться доступными модели.

---

# 44. GUARD P1

Существует server-side GUARD P1.

Он может вмешиваться до выполнения подозрительного tool action.

GUARD является дополнительным behavior/safety layer.

Он не заменяет:

```text
permissions
backup
verification
```

---

# 45. Известный safety gap

По-прежнему существует важный архитектурный сценарий:

```text
пользователь дал изменяющую задачу
↓
модель не вызвала tools
↓
сразу написала, что задача выполнена
```

Если физическая mutation не произошла, обычный Verification Gate не всегда может определить, что модель просто не выполнила работу.

Будущий возможный слой:

```text
TASK EXECUTION GATE
```

или:

```text
NO-TOOL STOP GUARD
```

Полноценное решение пока не реализовано.

```text
             │             │             │
             ↓             ↓             ↓
        MAIN CHAT      COMPRESSOR     future VERIFIER
             │             │             │
             ↓             ↓             ↓
        MODEL         MODEL          MODEL
      ASSIGNMENT    ASSIGNMENT     ASSIGNMENT
             │             │             │
             └─────── MODEL REGISTRY ────┘
                           │
                           ↓
                       PROVIDERS
                           │
              ┌────────────┴────────────┐
              ↓                         ↓
          GigaChat                  future Local

                           │

             ┌─────────────┼──────────────┐
```

Модель является заменяемым исполнителем.

Память и состояние принадлежат системе.

# 54. Канонические инварианты

```text
RAW MESSAGE никогда не уничтожается сжатием.

RAW MESSAGE не переписывается при изменении summary.

Context Variant хранится отдельно от RAW.

LLM не активирует proposal без решения пользователя.

Restore переключает active representation обратно на RAW.

Повторное LLM compression выполняется от RAW.

Project Context не является RAW MESSAGE.

Role Context не является Project Context.

MAIN CHAT и COMPRESSOR имеют независимые runtime context.

Tools принадлежат роли/runtime, а не модели.

Смена модели не должна уничтожать Workspace или Chat state.

Provider не является владельцем Chat memory.

UI должен показывать фактическую active working representation.

Original Viewer всегда должен позволять увидеть immutable RAW.
```
