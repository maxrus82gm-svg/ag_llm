### RT-001 — перекрёстная оценка GPT

**Участник / модель:** GPT — GPT-5.6 Sol, ChatGPT Web.  
**Способ подключения к проекту:** Desktop Commander Remote; в этом раунде только read-only inspection кода и документов до записи собственного вклада.

**Дополнительная проверка:** выборочно перепроверены ключевые спорные места текущего кода `web_alarm/`: `models.py`, `operation_store.py`, `state_machine.py`, `manifest_store.py`, `task_store.py`, `context_pack.py`.

#### Краткий итог

Два независимых анализа сходятся не только по направлению, но и по большинству главных дефектов. Это сильный сигнал, однако само совпадение не является доказательством: ниже я отдельно перепроверил часть фактов по текущему коду.

Главное подтверждённое общее ядро:

- persistent state / restore / reconciliation уже являются сильной основой;
- главный незамкнутый разрыв находится между **journal/reconciliation** и **authoritative execution**;
- операция не хранит полный durable contract результата и исполнения;
- recovery decision пока нельзя штатно применить как продолжение той же operation;
- replay safety держится слишком сильно на дисциплине caller;
- нужна защита от competing operations, cross-process serialization и CAS непосредственно перед mutation;
- restore/recovery должны идти через один lifecycle;
- checkpoint должен быть либо транзакционным authoritative state, либо явно rebuildable projection;
- реальная работа пока слишком часто проходит мимо OperationStore;
- новому агенту нужен короткий project-level resume.

Главное сохраняемое разногласие с Claude:

> **текущий комбинированный acceptance-критерий WA-3 нельзя считать выполненным только “композицией доказательств”, если канонический критерий требует конкретного timing-сценария: local post-state уже достигнут, Remote обрывается до получения Chat authoritative result.**

Композиция доказывает важные отдельные свойства и может быть достаточным основанием **изменить/перенести сам критерий через явный verdict**, но не должна задним числом превращаться в PASS исходного критерия.

Второе важное уточнение: предложения Claude об упрощении lifecycle и `snapshot-on-first-touch` полезны как направление, но пока это **design proposals**, а не готовые инварианты. Семантика pre-mutation gate не должна исчезнуть только потому, что часть промежуточных статусов неудобна вручную.

## 1. Что остаётся верным в моём собственном анализе (`30`)

### 1.1 Главный разрыв — execution ownership

Сохраняю вывод:

> WEB-02 уже хорошо умеет хранить intent/evidence и вычислять recovery decision, но пока не владеет безопасным исполнением и применением решения.

Именно это объясняет сразу несколько симптомов:
- expected post частично приходит от caller;
- `RETRY_SAFE` является рекомендацией, а не защищённой командой;
- `ADOPT` не закрывает operation lifecycle;
- реальная mutation может пройти мимо journal;
- lost response всё ещё требует дисциплины Chat.

### 1.2 Durable Operation Contract нужен до строгого mutation gateway

Сохраняю обязательные элементы:
- expected pre-state;
- expected post-state;
- canonical target identity;
- durable mutation request / payload identity;
- idempotency identity;
- persistent result receipt.

Особенно важно: текущий fingerprint включает `request_payload` в вычисление SHA256, но сам payload в `OperationRecord` не сохраняется. То есть система умеет доказать “это был тот же request”, но не умеет восстановить сам request по persisted operation.

### 1.3 Resolver нужен как first-class слой

Сохраняю:
- ADOPT;
- RETRY;
- ROLLBACK;
- ABORT / MANUAL;

как **tracked state transitions**, а не текстовый NEXT SAFE ACTION, исполняемый снаружи.

### 1.4 CAS должен находиться непосредственно на mutation boundary

Сохраняю вывод о гонке:
- reconciliation прочитал PRE_STATE;
- между decision и write состояние может измениться;
- значит retry безопасен только при повторной проверке precondition непосредственно перед side effect.

### 1.5 Cross-process serialization обязательна

Сохраняю. Процессная модель проекта уже включает HTTP server, CLI, отдельные Python process и Remote-driven commands. `threading.RLock` одного объекта недостаточен.

### 1.6 Checkpoint следует формализовать как projection либо включить в transaction model

Сохраняю. Сейчас Context Pack предпочитает checkpoint для current status / last operation / NEXT SAFE ACTION. Это делает stale checkpoint практическим риском, а не косметикой.

### 1.7 Project-level resume нужен

Сохраняю идею:
- resume должен работать даже при `ACTIVE TASK = none`;
- новый агент должен видеть project/branch/program stage, blockers, open operations и один NEXT SAFE ACTION.

### 1.8 Реальные mutations должны перестать обходить WEB-02

Сохраняю. Пока tracked workflow значимую часть изменений делает прямыми Remote calls, WEB-02 остаётся параллельным журналом, а не control plane.

## 2. Что я исправляю или уточняю в собственном анализе

### 2.1 Lease не следует объявлять обязательным самым ранним механизмом

В `30` я слишком быстро связал cross-process lock и mutation lease.

Уточнение:
- **cross-process serialization / revision / CAS** — обязательны рано;
- **lease/owner heartbeat** — отдельный механизм ownership, который может понадобиться, но его точная семантика должна быть спроектирована позже.

Для локальной первой версии корректный file/process lock + revision/CAS может закрыть больше реальных рисков, чем преждевременный lease-протокол.

### 2.2 SQLite — вариант реализации, не архитектурный verdict

Сохраняю его как сильный вариант, но не как prerequisite.

Архитектурный инвариант:
> coherent transaction model + cross-process serialization + recoverable authoritative state.

Это можно реализовать SQLite/WAL или аккуратным file-based журналом с lock/revision/commit semantics.

### 2.3 Минимальный `resume` можно сделать раньше полного gateway

В `30` я ставил Project Resume после Mutation Executor.

После сравнения с Claude уточняю порядок:
- после Recovery Closure полезно рано сделать **минимальный read-only CLI/API resume**;
- полноценный Situation UI, jobs dashboard и generated status могут идти позже.

Это позволит сразу проверить главный пользовательский критерий: новый агент быстро понимает безопасный следующий шаг.

### 2.4 “WEB-02 владеет execution” нужно ограничить tracked workflow

Не требуется превращать WEB-02 в единственный интерфейс вообще ко всем чтениям, shell/GUI или произвольным действиям машины.

Более точная граница:
> WEB-02 владеет authoritative state и significant tracked mutations зарегистрированного workflow; Desktop Commander остаётся общим транспортом/инструментом для остального.

### 2.5 Термин “exactly-once” нужно использовать осторожнее

И мой анализ, и Claude местами говорят “exactly-once”.

Для acceptance лучше формулировать наблюдаемое свойство:

> повтор того же durable operation contract после потери ответа не создаёт второй физический side effect и возвращает тот же persisted receipt.

Это точнее, чем абстрактное “exactly-once” без определения границ process/storage failure model.

Согласен с Claude.

Если новый Chat обязан “вспомнить” ожидаемый результат, persistent recovery ещё не self-contained.

Подтверждено по `operation_store.py`.

- не требует конкретный допустимый mutation status microtask;
- не сканирует competing open mutation по тому же target;
- не проверяет restore point/manifest как единый execution admission gate.

### 3.5 Cross-process lock отсутствует

Подтверждено:
- `operation_store.py:118` — только `threading.RLock()`.

Это process-local защита.

### 3.6 Restore path обходит основную state machine

Подтверждено:
- `manifest_store.py:540–541` напрямую вызывает `set_microtask_status(... BACKUP_VERIFIED)`.

Следовательно recovery mutation действительно идёт по отдельной дороге.

### 3.7 Verify не полностью read-only

Подтверждено:
- `verify_restore_point(... active_only=True)` при ошибке вызывает `_block_restore_point(...)`.

Название “verify” скрывает state mutation. Для recovery inspection это плохая граница API.

### 3.8 TASK closeout gate слабый

Подтверждено:
- `task_store.py:345–358` переводит TASK в COMPLETED и переносит каталог;

### 3.9 Context Pack предпочитает checkpoint

Подтверждено:
- `context_pack.py:79–114` сначала читает checkpoint;
- current microtask, status, snapshot status, last operation и NEXT SAFE ACTION берутся из него при наличии.

Следовательно rebuildable/staleness policy нужна явно.

### 3.10 Ручная синхронизация статуса и реальная работа мимо WEB-02 — реальные архитектурные сигналы

Согласен. Это не просто “грязная документация”, а симптом отсутствия одного runtime-owned current state.

## 4. Где Claude, на мой взгляд, ошибается или делает слишком сильный вывод

### 4.1 Нельзя закрывать исходный combined criterion WA-3 просто “композицией”

Это главное разногласие.

Claude предлагает считать:
- reconciliation функцию доказанной отдельно;
- реальные disconnect/failure случаи доказанными отдельно;
- следовательно combined criterion можно закрыть decision record’ом.

Я с этим **не согласен как с формулировкой PASS**.

Если acceptance специально требует temporal composition:

```text
local post-state reached
→ Remote breaks
→ Chat has not received authoritative result
→ fresh process recovers without blind replay
```

то отдельные доказательства A и B не доказывают автоматически интеграционное свойство A∧B в одном execution path.

Правильные варианты:
1. выполнить критерий буквально; или
2. через явный verdict заменить/перенести критерий в acceptance нового executor и честно записать, что старый критерий **superseded/deferred**, а не PASS.

Мой выбор остаётся вторым.

### 4.2 Фраза “Restore point сделан правильно” требует ограничения

Создание immutable snapshot до mutation — сильная часть.

Но весь restore subsystem пока нельзя называть полностью правильным, потому что тот же анализ Claude показывает:
- restore обходит state machine;
- current drift перед destructive rollback не сохраняется;
- verification может менять state.

Поэтому:
> snapshot creation — strong; recovery/restore lifecycle — incomplete.

### 4.3 “WEB-02 должен быть единственным местом, через которое LLM узнаёт состояние” слишком широко

Он должен быть authoritative для **workflow state** и tracked mutations.

Но не нужно заставлять любой исследовательский READ, arbitrary shell или GUI проходить через него. Иначе контрольный слой начнёт поглощать общий remote runtime без необходимости.

### 4.4 Упрощение lifecycle нельзя делать до фиксации инвариантов

Claude предлагает примерно:
`PLANNED → ACTIVE → VERIFIED` плюс recovery states.

Направление понятно, но сейчас `PREPARING/BACKUP_VERIFIED/READY` несут важную семантику:
> mutation нельзя начинать до verified restore/precondition gate.

Лучше сначала **автоматизировать/спрятать внутренние промежуточные стадии**, а не удалять семантические gates.

Иначе можно упростить UI ценой потери доказуемой pre-mutation границы.

### 4.5 Snapshot-on-first-touch безопасен только внутри authoritative executor

Идея хорошая, если “first touch” означает:

```text
server receives executable mutation
→ canonical target resolved
→ current bytes snapshotted + fsync/receipt
→ precondition checked
→ only then write
```

Если же внешний actor может коснуться target до snapshot, инвариант backup-before-mutation исчезает.

Поэтому это не просто UX-упрощение manifest, а часть будущего mutation transaction.

### 4.6 WA-3R нельзя считать “небольшим и точечным” без декомпозиции

Claude включает туда:
- schema change OperationRecord;
- resolver;
- state-machine recovery;
- restore redesign;
- competing-operation gate;
- checkpoint policy;
- cross-process lock/lease;
- watchdog wiring.

Это несколько разных correctness boundaries. Их лучше выполнить последовательными микрозадачами с отдельными acceptance criteria.

### 4.7 Числа 15–25 Remote calls и ожидаемые 5–10× — только оценки

Claude сам честно это помечает, и я с этим согласен.

Не использовать эти числа как основание архитектурного verdict без замера.

### 4.8 Требования ChatGPT Web/MCP к публичному HTTPS — не часть этого verdict

Claude сам пометил это “насколько знаю”.

Это внешний меняющийся transport requirement и должен перепроверяться отдельно в момент проектирования adapter.

## 6. Разногласия: что снимаю, а что сохраняю

### Снимаю / сближаю

**A. Project Resume.**  
Согласен с Claude, что минимальный read-only `resume` полезно сделать раньше полного mutation gateway — после закрытия базовых Recovery Closure invariants.

**B. Generated current status.**  
Согласен как с направлением. Но сначала runtime state должен стать достаточно authoritative, иначе generated STATUS будет красиво генерировать неполную истину.

**C. Situation UI.**  
Согласен с целевым UX: оператору нужен ответ “где мы / что безопасно дальше”, а не набор JSON-вкладок. Но полноценный UI ставлю после минимального resume и execution correctness.

### Сохраняю

**D. WA-3 combined criterion.**  
Не считать исходный критерий PASS по композиции. Либо literal test, либо явное supersede/defer через verdict.

**E. Lifecycle simplification.**  
Не принимать точную новую state machine сейчас. Сначала определить invariants, затем скрыть/объединить состояния, доказав эквивалентность gates.

**F. Lease.**  
Не фиксировать сейчас точную lease model. Cross-process lock/revision/CAS обязательны; lease — отдельный design decision.

**G. Storage backend.**  
Не выбирать SQLite vs JSON в этом раунде.

## 7. Новый вывод после сравнения двух анализов

Я бы сформулировал следующий этап не как один “WA-3R patch”, а как **Recovery Closure program с жёстким порядком зависимостей**.

### RC-1 — Durable Operation Contract + migration

Добавить:
- expected post;
- canonical target;
- durable payload / immutable payload reference;
- explicit schema migration/backward compatibility для уже существующих operations.

Acceptance:
- fresh process способен reconcile без передачи expected post из Chat.

### RC-2 — Resolver + evidence revision binding

ADOPT / RETRY / ROLLBACK / ABORT становятся tracked actions.

Критически:
- resolver action должен быть привязан к конкретной evidence revision/fingerprint;
- если target/state изменился после reconciliation, старое decision нельзя применить.

### RC-3 — Conflict gate + cross-process serialization

- canonical target normalization;
- competing open **mutating** operation по тому же target блокируется;
- file/process lock или equivalent transaction serialization;
- revision/CAS.

Важно: “одна operation на target навсегда” слишком жёстко. Ограничение относится к **одновременно незакрытым конфликтующим mutations**.

### RC-4 — Recovery/rollback как tracked operation

- rollback проходит через core lifecycle;
- перед destructive rollback сохраняется current drift;
- rollback имеет intent/receipt/post verification.

### RC-5 — Projection correctness

- inspect/verify не меняют state;
- checkpoint официально projection;
- есть rebuild/validate revision;
- stale projection fail-closed.

### RC-6 — Minimal project-level resume

После RC-1…RC-5:
- одна read-only команда;
- работает даже без active TASK;
- показывает open operations, blockers, current program stage и NEXT SAFE ACTION.

### Затем — Mutation Executor / Gateway

Только после closure:
- snapshot-before-write внутри controlled transaction;
- CAS;
- atomic mutation;
- exact post verification;
- persisted receipt;
- replay того же operation contract возвращает receipt без второго side effect.

### Затем — lost-response fault injection

Acceptance формулировать буквально:

```text
mutation physically applied once
→ receipt persisted
→ response intentionally lost
→ fresh process / new Chat
→ same durable operation request
→ no second physical side effect
→ same authoritative receipt
```

Это будет значительно сильнее старого ручного disconnect test.

### После correctness — UX/ops

- Situation UI;
- persistent jobs;
- automatic transport sensor;
- generated STATUS;
- rollout OBSERVE → WARN → GATEWAY REQUIRED → STRICT.

## 8. Слепые зоны, которые оба анализа затронули недостаточно

### 8.1 Schema migration

Расширение `OperationRecord` сломает чтение старых persisted records, если migration/versioning не спроектировать явно.

Это должно быть частью RC-1, а не “потом”.

### 8.2 Canonical target identity

“One open op per target” требует точного определения target:
- slash normalization;
- relative/absolute path;
- case-insensitive Windows paths;
- symlink/junction/reparse behavior;
- один физический файл под разными строковыми именами.

Без canonical identity conflict gate обходится разными path spellings.

### 8.3 Multi-file mutation

Оба анализа в основном рассуждают про один target.

Если логическая operation меняет несколько файлов, нужны ответы:
- один operation с transaction group?
- несколько child operations?
- что считается partial apply?
- как rollback/reconcile атомарно описывает набор targets?

### 8.4 Stale decision race

Мы много говорим про CAS на write, но нужен ещё explicit invariant:

> recovery decision действительно только для той evidence revision, на которой оно вычислено.

Resolver должен fail-closed при changed revision ещё до mutation.

### 8.5 Внешний writer / ручная правка пользователя

CAS обнаружит drift, но нужен UX/semantics:
- не считать внешний edit автоматически ошибкой;
- показать conflict;
- позволить ADOPT/REPLAN/ABORT без потери данных.

## 9. Признаки ложного или преждевременного согласия

Совпадение анализов очень высокое:
- expected post;
- resolver;
- one-open-op/conflict;
- CAS;
- process serialization;
- checkpoint;
- restore lifecycle;
- project resume;
- real-work bypass.

Здесь есть реальное code evidence, поэтому согласие не только стилистическое.

Но есть зоны, где одинаковая интуиция двух моделей **ещё не evidence**:
- точный состав и номер WA-3R/Recovery Closure;
- выбор SQLite;
- точная новая state machine;
- необходимость/форма lease;
- порядок Resume vs Gateway vs UI;
- snapshot-on-first-touch;
- 5–10× сокращение Remote calls.

Эти пункты должны остаться design hypotheses до синтеза/вердикта.
