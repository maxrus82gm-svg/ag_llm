# 17_Архитектура межчатового контекста и Cross-Chat Context Broker

**Статус:** FUTURE / NOT IMPLEMENTED

## 1. Проблема

В проекте `ag_llm` разные специализированные Chat могут работать над разными ветками одной задачи. Полезная информация при этом оказывается распределена:

- один Chat может содержать важное архитектурное решение;
- другой Chat — детали реализации;
- третий — результаты экспериментов.

Простое объединение историй Chat недопустимо:

- это приводит к загрязнению контекста;
- вызывает конфликты инструкций;
- резко увеличивает context budget;
- разрушает изоляцию веток.

Требуется механизм строго контролируемого обмена только необходимой информацией между Chat.

## 2. Базовый принцип

Фиксируем разделение источников контекста:

- **RAW HISTORY** — исходный источник фактов конкретного Chat. Не подлежит автоматическому изменению извне.
- **Working Representation** — активное RAW / SUMMARY представление, с которым работает модель в рамках Chat.
- **Project Context / Role Context** — отдельные управляемые источники общих и ролевых фактов.
- **Shared Context** — компактный подготовленный слой для обмена полезной информацией между ветками. Не является source of truth и не заменяет RAW HISTORY.

## 3. Specialized Chats / Branch Context

Каждый Chat:

- сохраняет собственную историю;
- имеет собственное рабочее представление;
- отражает контекст конкретной ветки работы (Branch Context).

Чаты не должны автоматически получать полную историю друг друга. Доступ к чужому контексту должен быть явным и обоснованным.

## 4. Shared Project Context

Shared Project Context — это компактный набор общих устойчивых фактов:

- содержит только то, что действительно должно быть доступно нескольким Chat;
- не копирует всю историю;
- не заменяет исходные данные;
- имеет понятное происхождение (какой Chat/ветка, какой материал, какой тип представления).

Shared Context может использоваться как дополнительный слой, но не отменяет обращение к RAW при необходимости.

## 5. Cross-Chat Context Broker

**Cross-Chat Context Broker — FUTURE / NOT IMPLEMENTED**

Предполагаемая роль Broker — быть центральным компонентом межчатового обмена контекстом.

Примерный lifecycle:

1. В Chat A возникает конкретный информационный вопрос.
2. Chat A отправляет запрос Cross-Chat Context Broker.
3. Broker определяет подходящие источники (какие Chat/ветки могут содержать ответ).
4. Broker запрашивает минимально необходимый контекст.
5. Broker возвращает bounded result (компактный, по возможности с указанием происхождения).
6. Chat A использует этот результат как дополнительный контекст, не сливаясь с исходным Chat.

Broker не является владельцем исходных данных и не должен автоматически объединять Chat.

## 6. Question-oriented retrieval

Retrieval должен строиться вокруг конкретного вопроса, а не принципа «дай мне всё из другого Chat».

Примеры:

- «Какое архитектурное решение было принято по модулю X?»
- «Какие ограничения по производительности были зафиксированы в эксперименте Y?»

Это существенно снижает шум и риск загрязнения контекста.

## 7. Staged retrieval

Возможная ступенчатая схема получения контекста:

1. Метаданные / компактный summary.
2. Более подробный prepared context (подготовленный фрагмент).
3. Фрагменты исходного материала.
4. RAW — только при реальной необходимости и явном обосновании.

Чем глубже уровень, тем более явной должна быть причина обращения к нему.

## 8. Provenance / Evidence

Любой полученный межчатовый контекст должен сохранять происхождение:

- source Chat;
- source message / context item (если доступно);
- тип представления (RAW / SUMMARY / prepared context);
- время / revision (если применимо).

Модель должна отличать:

- исходный факт;
- summary;
- вывод другой модели.

Без сохранения provenance межчатовый контекст быстро теряет доверие.

## 9. Read-only и безопасность

По умолчанию Cross-Chat retrieval должен быть read-only:

- получение контекста из другого Chat не даёт права менять его RAW HISTORY;
- не даёт права менять его Working Representation;
- не даёт права автоматически публиковать туда результаты текущего Chat.

Default deny для любого лишнего доступа. Любое расширение прав — явное и обоснованное.

## 10. Context contamination protection

Необходимо защититься от:

- смешивания противоречащих инструкций из разных Chat;
- переноса чужих временных задач и предположений;
- использования assistant reasoning другого Chat как authoritative fact;
- бесконтрольного разрастания контекста;
- циклического retrieval (Chat A → Chat B → Chat A);
- использования устаревшего summary как текущего факта.

## 11. Связь с Compression

Cross-Chat Context должен учитывать существующую архитектуру RAW / SUMMARY:

- summary может помогать при retrieval;
- но не должен уничтожать возможность дойти до исходного материала;
- Compression и Cross-Chat retrieval — разные механизмы с разными целями.

## 12. Context presets / будущие роли

В будущем могут появиться:

- context presets для разных ролей;
- политики, определяющие, какие типы контекста разрешены конкретному Chat или роли.

На момент создания документа универсальный Context Policy не считается реализованным.

## 13. Инварианты

Минимальный набор инвариантов:

- RAW остаётся источником истины.
- Chat сохраняют изоляцию.
- Shared Context не заменяет RAW.
- Broker не является владельцем исходных данных.
- Retrieval минимален и question-oriented.
- Provenance не теряется.
- Cross-Chat доступ по умолчанию read-only.
- Модель не решает самостоятельно, какие физические права ей выдавать.

## 14. CURRENT / CONCEPT / FUTURE

- **CURRENT:** существующие механизмы изоляции Chat, RAW HISTORY, Working Representation, сжатие контекста внутри Chat.
- **CONCEPT:** архитектурные идеи, описанные в этом документе.
- **FUTURE / NOT IMPLEMENTED:** Cross-Chat Context Broker, универсальная межчатовая retrieval-система, общий Context Registry и связанные механизмы.
