# AG LLM Connect

## Концепция внешних интеграций, Living World и Unreal-интеграции

_Опорный документ / отправная точка_

**Связи концепции:** [[00_Главная - карта проекта]] · [[AG LLM Unreal]] · [[AG LLM Godot]] · [[AG LLM Blender]]

---

> **Статус документа**
> 
> Фиксирует решения, сформулированные к 27 сентября 2026 года. Это не финальная спецификация API и не техническое ТЗ на Unreal-плагин; это единая архитектурная точка, от которой можно дальше проектировать продукт.

AG LLM остаётся самостоятельным Python-ядром. Unreal — внешний визуальный клиент, а не место, где живёт интеллект.

## 1. Коротко: что мы строим

AG LLM развивается из локального LLM-агента в универсальный Agent Runtime: самостоятельное ядро, которое умеет планировать задачи, вызывать реальные инструменты, проверять результат, управлять контекстами, правами и моделями, а также обслуживать внешние сущности.

Первым крупным внешним клиентом предполагается Unreal Engine. В нём может жить трёхмерный персонаж и целое «жизненное пространство» пользователя: комната, телевизор, книжные полки, рабочее место, уведомления и другие объекты. 3D-слой показывает состояние и предоставляет естественный интерфейс, а вся агентная логика остаётся в AG LLM.

> **Главная идея**
> 
> Не делать «нейросеть внутри игры». Сделать игру одним из клиентов AG LLM. Игра регистрирует сущности и события; AG LLM выбирает модель, собирает контекст, подключает память и инструменты, проверяет права и возвращает решение или действие.

## 2. Зафиксированные решения

- Python-ядро AG LLM сохраняется и продолжает развиваться независимо от визуального клиента.
- Текущий Tkinter-интерфейс — рабочая техническая панель, но не конечный пользовательский UI.
- Unreal Engine рассматривается как основной 3D-клиент и база для Living World.
- AG LLM должен устанавливаться и работать без Unreal.
- Living World устанавливается как дополнительный модуль поверх того же ядра.
- Связь Unreal ↔ AG LLM должна быть тонкой и формальной: команды, запросы, события и данные.
- Внешняя 3D-сущность регистрируется в AG LLM и получает собственный профиль: контексты, память, доступные действия, события и политику выбора модели.
- Unreal отвечает за физический мир, анимацию, навигацию и визуальное исполнение. AG LLM отвечает за смысл, выбор действия и агентную логику.
- Реальные права и ограничения всегда проверяет ядро AG LLM, а не Blueprint.
- Простые фоновые проверки выполняют дешёвые watcher-скрипты; LLM подключается только когда нужна интерпретация или решение.
- Архитектура должна позволять в будущем подключать не только Unreal, но и Blender, веб-клиенты, другие игры и приложения.

## 3. Что такое AG LLM как продукт

AG LLM — это не один чат и не один NPC. Это сервисный слой между приложением и набором нейросетей. Он скрывает от клиента детали провайдера модели, структуру промптов, сборку контекста, права, память, инструменты и проверку результата.

```
Клиент / игра / приложение
          │
          ▼
      AG LLM API
          │
          ├── Entity Registry
          ├── Context Registry
          ├── Model Router
          ├── Memory / State
          ├── Planner / Executor
          ├── Tools / Permissions
          └── Verification / Audit
          │
          ▼
      LLM / провайдеры
```

## 4. Варианты поставки

|Вариант|Состав|Назначение|
|---|---|---|
|AG LLM|Core + обычный desktop UI|Полноценный локальный агент без 3D.|
|AG LLM + Living World|Core + desktop UI + Unreal Client|Живой 3D-помощник и визуальный мир.|
|AG LLM Core / Headless|Core без пользовательского UI|Будущий серверный или встраиваемый режим.|

Ключевое требование к установке: пользователь не должен вручную ставить Python, создавать venv, запускать Git Bash или собирать зависимости. Установщик должен привозить рабочий runtime и заводские контексты, а при первом запуске запрашивать только пользовательские параметры: модель/авторизацию, рабочие каталоги и базовые настройки.

## 5. Living World: пользовательский слой

Living World — это не замена AG LLM, а понятный человеку пространственный интерфейс. Персонаж живёт в небольшой 3D-комнате и может оставаться открытым на рабочем столе постоянно или скрываться по желанию пользователя.

|Объект|Смысл|
|---|---|
|Персонаж|Главный голосовой и визуальный представитель AG LLM; разговаривает, реагирует на события и запускает задачи.|
|Книжная полка|Workspace, проекты, watchers, справочники и постоянные задачи в форме книг.|
|Телевизор|Информационный поток: новости, изменения на сайтах, видео, контекст и выбранные источники.|
|Рабочий стол / компьютер|Текущая активная работа агента и состояние RUN.|
|Доска / план|Визуализация Planner и этапов выполнения.|
|Архив|История задач, результаты, логи и сохранённые материалы.|
|Радио / уведомления|Фоновый канал событий, который можно отключить обычной командой.|

## 6. Событийная модель и «жизнь» персонажа

Персонаж не должен постоянно спрашивать LLM, что ему делать. Большая часть мира работает на обычных событиях. Системные службы или Unreal фиксируют факт, затем AG LLM при необходимости интерпретирует его и выбирает реакцию.

```
GPU_TEMP_HIGH
NEW_VERSION_FOUND
TASK_STARTED
TASK_COMPLETED
TASK_FAILED
VERIFY_FAILED
WORKSPACE_CREATED
CONTEXT_CHANGED
WATCHER_TRIGGERED
DOWNLOAD_COMPLETED
```

Одно и то же событие не задаёт жёсткую реплику. Контекст сущности определяет характер реакции: спокойную, шутливую, деловую или эмоциональную.

> **Пример**
> 
> Температура GPU повысилась → мониторинг создаёт GPU_TEMP_HIGH → персонаж получает событие → выбирает подходящую реакцию → Unreal проигрывает анимацию «подойти к окну / открыть окно» → персонаж произносит реплику. Простая проверка температуры не расходует LLM-вызовы.

## 7. Watchers: фоновые наблюдатели

Watchers — отдельный слой лёгких постоянных задач. Их цель — отслеживать внешние источники без постоянного участия LLM. Если сайт предоставляет API, RSS или структурированный источник, используется он. Если структура нестабильна, watcher обнаруживает изменение и передаёт материал в AG LLM для интерпретации.

- Проверка выхода новой версии Blender.
- Отслеживание интересующего сайта или страницы.
- Наблюдение за обновлениями документации, проекта или репозитория.
- Формирование персонального информационного потока для телевизора.
- Правила пользователя: «только сообщать», «спрашивать перед скачиванием», «скачивать автоматически».

## 8. Unreal ↔ AG LLM: принцип связи

Unreal не хранит внутри себя агентную систему. Он подключается к локальному AG LLM через формальный API. Связь можно строить поверх локального HTTP/WebSocket или другого транспорта, но смысл интерфейса должен оставаться стабильным.

```
Unreal Client
   │
   ├── Commands  →  запусти задачу / останови / открой workspace
   ├── Queries   →  состояние сущности / состояние RUN
   ├── Events    ←  TASK_DONE / NEWS_FOUND / VERIFY_FAILED
   └── Data      ↔  профили сущностей / настройки / контексты
   │
   ▼
AG LLM Core
```

## 9. External Entity Registry

Главный масштабируемый механизм — реестр внешних сущностей. Любой объект клиента может зарегистрироваться в AG LLM как отдельная сущность. Это может быть кот, торговец, преподаватель, телевизор, робот, Blender-плагин или другой внешний клиент.

```
{
  "entity_id": "cat_01",
  "entity_type": "companion",
  "name": "Кот",
  "model_policy": "light_fast",
  "contexts": [
    "cat.personality",
    "cat.world_rules",
    "cat.user_relation"
  ],
  "tools": [
    "speak",
    "look_at",
    "move_to",
    "use_tv"
  ],
  "subscriptions": [
    "user_message",
    "task_finished",
    "news_found"
  ]
}
```

AG LLM создаёт runtime-профиль сущности и дальше принимает запросы по entity_id. Вместо создания отдельного процесса для каждого персонажа один AG LLM обслуживает множество профилей.

## 10. Model Router

Сущность не должна знать конкретное название модели. В её профиле лучше хранить политику выбора модели, а соответствие реальным провайдерам задаётся в AG LLM.

```
light_fast       → быстрая дешёвая модель
reasoning        → сильная reasoning-модель
vision           → модель с изображениями
cheap_background → фоновые решения
high_quality     → максимальное качество
```

Это позволяет заменить провайдера или модель без обновления Unreal-проекта. Один и тот же NPC может использовать разные модели для разных задач, а fallback-политика может переключить запрос при ошибке основной модели.

## 11. Контекст сущности

Контекст не должен быть одним огромным системным промптом. Он собирается из независимых слоёв:

- System Core — общие правила платформы.
- Entity Type — правила класса сущности.
- Personality — характер и стиль общения.
- World State — текущее состояние мира и объекта.
- Relationship / Memory — релевантная долговременная память.
- Current Event — событие, которое нужно обработать сейчас.
- Available Actions — реальные действия, доступные конкретной сущности.  
    Благодаря этому коту не требуется загружать инструкции по git_diff или Python Compile, а рабочему агенту не нужен полный контекст анимационного поведения кота.

## 12. Разделение ответственности

|AG LLM|Unreal Engine|
|---|---|
|Смысл и выбор действия|Actor и физический мир|
|Выбор LLM / fallback|Навигация и перемещение|
|Сборка контекста|Анимации|
|Память и состояние сущности|Материалы / освещение|
|Права и ограничения|UI и взаимодействия|
|Planner / Executor|Blueprint / C++-логика|
|Tool orchestration|Проигрывание действий|
|Verification / Audit|Отчёт о результате действия|

Пример: AG LLM возвращает действие move_to(window). Unreal решает, существует ли окно, можно ли к нему пройти, какую анимацию включить и как выполнить взаимодействие. После выполнения Unreal возвращает результат. LLM не управляет Transform напрямую.

## 13. Права и безопасность

Настройки в Unreal описывают желаемые возможности объекта, но не являются источником истины для прав. Любое действие, затрагивающее файлы, внешние системы, загрузки или критические операции, повторно проверяется ядром AG LLM.

- Blueprint может запросить capability, но не может сам себе выдать право.
- Сущность получает только релевантный набор tools.
- Scope файлов и ресурсов хранится и проверяется в Core.
- Критические действия могут требовать подтверждения пользователя.
- Audit фиксирует фактические действия, а не только текстовые утверждения модели.

## 14. Продуктовая форма для разработчиков игр

Если архитектура стабилизируется, AG LLM можно распространять не только как конечного помощника, но и как middleware / AI Runtime для игр и приложений.

- AG LLM Runtime — универсальное ядро.
- AG LLM Unreal Plugin — компонент регистрации сущностей, события, API и Blueprint-узлы.
- Living World — демонстрационное и одновременно пользовательское приложение.
- В дальнейшем возможны другие клиенты: Blender, Unity, веб, собственные приложения.  
    Ценность для разработчика: не строить заново провайдеры LLM, память, контексты, model routing, инструменты, права и аудит. Разработчик описывает сущность и игровые действия, а агентная инфраструктура остаётся в AG LLM.

## 15. Инсталляция и модульность

Целевой пользовательский сценарий — обычный установщик. AG LLM должен разворачиваться на чистом компьютере без ручной подготовки окружения.

```
AG LLM
│
├── Core                (обязательно)
├── Desktop UI          (обычный интерфейс)
├── Living World 3D     (опционально)
├── Models / Providers  (настраиваемо)
├── Tools               (модули)
└── Watchers            (модули)
```

Living World можно докачать позднее. Удаление или обновление Unreal-клиента не должно повреждать данные и контексты Core.

## 16. Производительность Living World

Unreal-клиент следует проектировать с постоянным desktop-режимом как отдельным профилем производительности. Графическую оптимизацию можно обеспечить контентом, но код также должен быть событийным: минимум постоянных Tick, отключение ненужной физики, редкие фоновые обновления и ограниченная частота визуального обновления там, где это допустимо.

- Desktop Mode — лёгкий, постоянно работающий режим.
- Full Mode — развёрнутая комната / будущая игровая форма с более высоким качеством.
- AG LLM Core продолжает работать независимо от того, открыт ли 3D-клиент.

## 17. Этапы развития

A. Стабильное ядро — Довести текущий AG LLM до устойчивой архитектуры и закрыть накопленные технические хвосты.

B. Installable Runtime — Собрать AG LLM как устанавливаемое приложение на чистом компьютере.

C. External Entity Runtime — Entity Registry, Model Router, API, события, состояния и capability-профили.

D. Unreal Plugin — Минимальный плагин: connect/register/send event/request action/receive result.

E. Living World Prototype — Одна комната, один персонаж, телевизор, книги, несколько реальных событий.

F. Product SDK — Документация, примеры, шаблоны сущностей, marketplace/distribution-пакет.

## 20. Граница концепции

Этот документ фиксирует направление, но намеренно не определяет конкретный сетевой протокол, формат каждого API-метода, схему хранения entity memory и коммерческую модель. Эти решения должны появиться после стабилизации Core и небольшого proof-of-concept внешней сущности.

> **Опорная формула**
> 
> AG LLM = самостоятельный Agent Runtime. Living World = один из клиентов. Unreal Plugin = мост. External Entity Registry = масштабирование. Model Router = независимость от конкретной нейросети.
