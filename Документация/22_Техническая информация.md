# 22. Техническая информация

Краткий технический справочник проекта `ag_llm`: команды, локальные настройки, подключение инструментов и плагинов, служебные приёмы и другие вещи, которые полезно быстро восстановить без чтения архитектурной документации.

Родительская карта: [[00_Главная - карта проекта]]

## Правила ведения

- Одна техническая тема — один небольшой блок.
- Пояснение пишется по-русски простыми словами.
- Команды, пути и параметры сохраняются дословно в кодовых блоках.
- Если инструкция зависит от версии, окружения или конкретного ПК — это указывается рядом.
- Пароли, токены, ключи и другие секреты сюда не записываются.
- Архитектурные решения и история TASK сюда не переносятся: для них остаются профильные документы и журналы.
- Если короткая заметка перерастает в полноценный регламент, здесь остаётся только ссылка на него.

## Быстрые технические записи

### Windows 11 — AI Proxy KillSwitch (ChatGPT / Codex / Claude), 2026-10-15

**Для чего:** гарантированно **стремиться** направлять сетевую работу настольных ChatGPT, Codex и Claude через локальный V2Ray/sing-box, не допуская незаметного прямого выхода при изменении путей после обновления. Реализованные меры — **многоуровневая защита**, но полная fail-closed гарантия для всех самостоятельных компонентов Codex, DNS/UDP и первого запуска ещё **не подтверждена**. Не путать наблюдение за TCP с формальной гарантией сетевой изоляции.

**Область применения:** конкретный ПК с Windows 11, V2RayN / sing-box, Windows Defender Firewall, установленными пакетами `OpenAI.Codex` и `AnthropicPBC.Claude`. Работа выполнена через Desktop Commander Remote в повышенном сеансе 2026-10-15. Это **внешняя инфраструктура разработки**, а не компонент `ag_llm`; размещено здесь для сохранения контекста. В GitHub **нет копии локальных скриптов и состояния брандмауэра**: ниже описано, где искать оригиналы на ПК.

**Жёсткое требование:** ChatGPT Desktop, Codex и Claude должны пользоваться V2Ray; **не переключать** V2Ray в TUN/Global без отдельной задачи, не останавливать sing-box и не трогать маршрутизацию остальных приложений. В наблюдениях ChatGPT/Codex использовали `127.0.0.1:10808` (локальный прокси sing-box). `TUN OFF / Global OFF` — рабочее состояние на момент диагностики; Chrome/SwitchyOmega имеет отдельные правила и не определяет маршрутизацию Desktop-приложений.

**Локальные файлы** (на соответствующем ПК под текущим пользователем):

```text
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\Refresh.ps1      — актуальная логика синхронизации firewall
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\Refresh-v2.ps1   — копия новой реализации
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\Watcher.ps1      — событийный наблюдатель
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\Install.ps1      — исторический установщик
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\Remove.ps1       — историческое удаление (не запускать вслепую)
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\killswitch.log   — журнал обновления правил
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\watcher.log      — журнал наблюдателя
%USERPROFILE%\Desktop\AI_Proxy_KillSwitch\backup_20261015_220822\
```

**Что реально сделано и проверено 15.10.2026:**

- Предыдущий `AI Proxy KillSwitch Refresh` **уже существовал** в планировщике Windows с повышенными правами. Его старая реализация удаляла старые правила **до** создания новых; отслеживала основной Claude, но не `cowork-svc.exe`; запускалась при входе в систему.
- Создана резервная копия старого `Refresh.ps1`, `Install.ps1`, экспорт задачи `task.xml` и снимок действовавших правил `firewall_rules.json`. Перед изменением было 12 правил группы `AI Proxy KillSwitch`.
- `Refresh.ps1` заменён проверенной новой версией: выявляет актуальные пути файлов, **сначала создаёт и сверяет** новые блокирующие правила `Outbound / Block / RemoteAddress Internet`, **только затем** удаляет устаревшие; при неудачном обнаружении обязательных пакетов сохраняет существующие правила. Отдельно учитывает Claude `Claude.exe` и `cowork-svc.exe`, ChatGPT, службу песочницы Codex, `codex.exe`, `codex-code-mode-host.exe`, `node.exe`, `node_repl.exe`, `codex-computer-use-swift.exe` под корнями Codex.
- Проверен запуск `-DryRun`, затем применение: **14 активных правил** `AI Proxy KillSwitch`; 12 устаревших удалены после верификации. Последующий запуск через планировщик завершился **кодом 0**, при отсутствии изменений `stale_removed=0`.
- Добавлены отдельно от группы обновления два постоянных правила `AI Proxy PackageGuard ChatGPT` и `AI Proxy PackageGuard Claude` (группа `AI Proxy PackageGuard`, `Outbound / Block / RemoteAddress Internet`) по **Package SID**, считанным из уже существующих разрешающих правил Windows. Не зависят от имени версионной папки пакета. Package Family Names: `OpenAI.Codex_2p2nqsd0c76g0` и `AnthropicPBC.Claude_fnn82j28hfe8t`. **Полное покрытие отдельных дочерних процессов пакетом не доказано**; вспомогательные `.exe` защищаются также отдельными правилами.
- Создан `Watcher.ps1`: `FileSystemWatcher` для `C:\Program Files\WindowsApps` (наблюдение **не рекурсивное**, за появлением/переименованием/удалением элементов верхнего уровня), а также `%LOCALAPPDATA%\OpenAI\Codex\bin` и `%LOCALAPPDATA%\OpenAI\Codex\runtimes` (рекурсивно, включая изменения). После серии событий с задержкой примерно 5 с запрашивает запуск существующей задачи `AI Proxy KillSwitch Refresh`. Наблюдатель работает по событиям, а **не делает полный опрос каждую секунду**.
- В планировщике создано отдельное повышенное задание `AI Proxy KillSwitch Watcher`, запускающее наблюдатель **при входе пользователя в Windows**; основная задача `AI Proxy KillSwitch Refresh` теперь выполняется при входе и резервно **каждые 15 минут**. Тестовое создание временного файла в Codex `bin` породило событие, наблюдатель запустил проверку, в логе `Refresh complete: protected=14 stale_removed=0`; наблюдатель остался запущен.
- После добавления правил контрольный срез `Get-NetTCPConnection` по основным процессам ChatGPT / Codex / Claude показал соединения только с `127.0.0.1:10808`; **это не доказывает отсутствие всех попыток прямого соединения**.

**Короткая диагностика** (PowerShell **от администратора**; команды только читают):

```powershell
Get-ScheduledTask -TaskName 'AI Proxy KillSwitch Refresh','AI Proxy KillSwitch Watcher' |
  Select-Object TaskName,State
Get-ScheduledTaskInfo -TaskName 'AI Proxy KillSwitch Refresh' |
  Select-Object LastRunTime,LastTaskResult,NextRunTime
Get-NetFirewallRule -Group 'AI Proxy KillSwitch' |
  Select-Object DisplayName,Enabled,Action
Get-NetFirewallRule -Group 'AI Proxy PackageGuard' |
  Select-Object DisplayName,Enabled,Action
Get-Content "$env:USERPROFILE\Desktop\AI_Proxy_KillSwitch\killswitch.log" -Tail 15
Get-Content "$env:USERPROFILE\Desktop\AI_Proxy_KillSwitch\watcher.log" -Tail 15
Get-NetTCPConnection -State Listen -LocalPort 10808 -ErrorAction SilentlyContinue
```

**Ограничения / нерешённая задача:**

- **Главная открытая уязвимость:** новый самостоятельный `codex.exe` (или новый тип исполняемого файла Codex) может успеть установить прямое соединение **до** события и применения правила. Ни `FileSystemWatcher`, ни повторная проверка через 15 минут не являются гарантией `fail-closed`. Нужна предварительная изоляция на уровне ОС/сетевого контейнера/строгой политики по приложению; подход выбрать и испытать отдельно с безопасным откатом. Не объявлять задачу полностью закрытой.
- Проверки DNS, UDP, IPv6, реальной блокировки при выключении прокси, поведения при установке новых версий и охвата неучтённых дочерних процессов ещё **не завершены**. `RemoteAddress Internet` и package SID не заменяют комплексного аудита фильтрации.
- FileSystemWatcher может пропускать события и выдавать дубликаты; резервная периодическая сверка остаётся обязательной. Наблюдатель стартует **при входе пользователя**, не является системной boot-службой; во время отсутствия входа мгновенной реакции нет.
- **Не останавливать и не убивать автоматически Codex/Claude при каждом файловом событии:** возможны ложные срабатывания и потеря выполняемой агентом работы. Не выключать общий V2Ray ради обновления правил. Не использовать `Remove.ps1` как простой аварийный откат: он также удаляет задачу и связан с Tripo HOSTS-настройками.
- При добавлении новых типов процессов или изменении расположения `Codex` необходимо пересмотреть перечень `.exe` в `Refresh.ps1`. Старый пакетный SID может измениться при переходе на приложение другого издателя/с другой идентичностью.
- Не публиковать в этом документе токены, конфигурации выходного узла, адреса внешнего прокси, приватные ключи и другие секреты.

**При следующем обращении:** проверить актуальность двух заданий, журналов и обеих групп правил; затем отдельно спроектировать действительно `fail-closed` изоляцию для самостоятельных компонентов Codex, DNS/UDP и тест отключения V2Ray **без затрагивания остальных программ**. Все сетевые изменения проводить постепенно, с подтверждением работоспособности и проверенным откатом.

### Desktop Commander Remote 0.2.52 — false-online / зависший local MCP child

**Подробный журнал наблюдений и recovery evidence:** [[26_Журнал наблюдений Remote - обрывы, transport и recovery evidence]]

**Для чего:** быстро распознать ситуацию, когда Remote формально остаётся `online`, но реальные file/process tools перестают выполняться.

**Когда использовать:** `list_devices`/remote-канал выглядят живыми, однако `read_file`, `get_config`, `start_process` или другие execution-tools зависают/таймаутятся.

**Проверка:**

```text
Не считать ping/online достаточной проверкой.
Проверять data plane безопасным execution-вызовом, например get_config.
```

**Важно:** для установленной версии `@wonderwhy-er/desktop-commander 0.2.52` подтверждено: remote-parent и local MCP child могут оставаться живыми по PID, а local child — перестать отвечать. MCP SDK ограничивает request примерно 60 секундами; текущий `callClientTool()` после такого отказа логирует/rethrow, но не обязан инвалидировать `isReady` и пересоздать зависший child. Поэтому обычный heartbeat/`online` может давать false healthy. Не отправлять случайный Enter как keep-alive и не патчить живой Remote-пакет во время удалённой сессии без возможности локального восстановления. Внешний watchdog/recovery для hung-but-alive child требуется рассмотреть отдельно.

### DesktopCommander_Watchdog V1 — монитор Remote-связи

**Для чего:** внешний наблюдатель за Desktop Commander Remote, чтобы видеть реальные переходы `ONLINE/OFFLINE` и не полагаться только на страницу Devices.

**Где лежит:** `DesktopCommander_Watchdog/` (`Start_Watchdog.cmd`, `watchdog.ps1`, `config.json`, `logs/watchdog.log`).

**Запуск:** открыть `Start_Watchdog.cmd`. Скрипт опрашивает состояние каждые 3 секунды.

**Логика V1:** ищется процесс Desktop Commander Remote; `ONLINE` считается при наличии установленного TLS-соединения процесса на remote port 443. Если процесса или TLS-канала нет — `OFFLINE`. Смена статуса записывается в `logs/watchdog.log`.

**Важно:** V1 только наблюдает. Она не перезапускает Remote, не отправляет Enter и не выполняет автолечение. Один экземпляр watchdog достаточно.

**Перенос:** скопировать папку `DesktopCommander_Watchdog` целиком и заменить в `config.json` `expectedDeviceId`, `expectedDeviceName`; `pollSeconds` задаёт интервал. Секреты в папке не хранятся.

**Текущая конфигурация:** `DESKTOP-SC96D3U`, Desktop Commander Remote 0.2.52, `pollSeconds=3`.

**Подтверждённая рабочая версия:** `@wonderwhy-er/desktop-commander@0.2.52`. На 2026-10-01 это также текущий официальный релиз. Для воспроизводимой установки лучше пиновать именно `0.2.52`, а не использовать `@latest`, потому что будущий latest может измениться.

	https://mcp.desktopcommander.app/
