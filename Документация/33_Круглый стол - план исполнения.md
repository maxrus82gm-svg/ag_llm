# Круглый стол — план исполнения

**Статус документа:** постоянный post-verdict bridge между утверждённым решением Круглого стола и каноническим планом реализации профильной подсистемы.

Документ **не является архитектурным source of truth и не является каноническим implementation plan**. Он временно хранит подробный план исполнения уже утверждённого verdict до его проверки пользователем и переноса в профильный план реализации.

## 1. Зачем существует документ 33

Круглый стол заканчивает decision authority в документе `32`: сформирован verdict, получен USER APPROVAL, записан Decision Record.

После этого ещё нельзя сразу начинать код, если утверждённое решение состоит из нескольких зависимых работ. Нужен отдельный planning bridge:

```text
32 — approved verdict / Decision Record
↓
33 — execution plan draft
↓
USER PLAN REVIEW
↓
PLAN APPROVAL
↓
перенос в канонический профильный implementation plan
↓
создание и запуск отдельных TASK
↓
verification / профильный журнал
```

`33` отвечает только на вопрос **«как разложить уже принятое решение на исполнимые TASK»**. Он не имеет права заново решать вопрос Круглого стола.

## 2. Универсальные входы

Для каждого плана обязательны:

- RT-ID и approved verdict из `32`;
- версия/hash утверждённого verdict;
- Decision Record;
- актуальное состояние затронутой подсистемы;
- профильные архитектурные документы;
- существующий профильный implementation plan, если он уже есть;
- зависимости, ограничения и deferred-пункты verdict;
- текущий git/dirty state перед фактическим handoff.

Если между verdict и planning обнаружен drift, меняющий предпосылки решения, `33` не адаптирует verdict молча: затронутый пункт возвращается на **ПЕРЕРАБОТАТЬ** новым `RT-xxx`.

## 3. Обязательный выход

Execution plan должен содержать:

1. цель исполнения;
2. целевой канонический plan/document destination;
3. ordered TASK graph;
4. зависимости и блокировки;
5. scope каждой TASK;
6. что TASK сознательно не делает;
7. acceptance/verification каждой TASK;
8. proposed executor, если это полезно;
9. concurrency/ownership rules;
10. mapping пунктов verdict → TASK;
11. условия передачи плана в канонический профильный документ;
12. PLAN APPROVAL пользователя.

План не должен превращаться в огромную единую TASK. Correctness boundaries должны быть отдельными проверяемыми задачами.

## 4. Правила планирования

1. **Verdict immutable для Planner.** `33` может декомпозировать, упорядочивать и назначать исполнителей, но не менять утверждённое содержание.
2. **Decision ≠ plan ≠ execution.** `32` отвечает «что принято», `33` — «как исполнять», профильный implementation plan — «какой план теперь канонический», TASK — «что выполняем прямо сейчас».
3. **USER PLAN REVIEW обязателен.** До подтверждения пользователя план из `33` не переносится в профильные документы и TASK не запускаются.
4. После PLAN APPROVAL содержимое переносится/встраивается в профильный implementation plan. С этого момента именно профильный документ становится каноническим владельцем плана.
5. После проверенного handoff `33` перестаёт быть источником рабочего плана. Его оперативная часть может быть очищена после git-печати/commit, а постоянная инструкция остаётся.
6. При нескольких профильных подсистемах один execution plan может иметь несколько destination, но каждый фрагмент должен получить одного канонического владельца.
7. До появления технического ownership/locking разные агенты **не изменяют параллельно пересекающийся scope**.
8. Proposed executor не является жёсткой привязкой к физической модели. Role ≠ Model ≠ Connection Adapter.
9. Отложенные/отклонённые пункты verdict не превращаются в TASK скрытно.
10. Никакой runtime-код не меняется самим фактом заполнения `33`.

## 5. Lifecycle документа 33

```text
EMPTY
↓ approved RT verdict
DRAFT
↓ план сформирован
AWAITING PLAN REVIEW
↓ USER PLAN APPROVAL
APPROVED FOR HANDOFF
↓ профильный plan обновлён и проверен
HANDED OFF
↓ отдельные TASK создаются из канонического профильного plan
↓ после git-печати оперативная часть очищается
EMPTY
```

`ROUND TABLE CLOSED` остаётся состоянием Круглого стола уже после `32`. Документ `33` — **post-round execution planning**, а не дополнительная decision-stage.

## 6. FUTURE Ultra

В будущей Ultra функции этого документа выполняет Execution Planner / Coordinator:

```text
Approved Verdict
→ Execution Plan
→ Task graph
→ Role/Agent assignment
→ dependency / ownership control
→ execution TASKs
→ verification
→ reconciliation
```

Ручной `33` — прототип этого слоя. После автоматизации формат может стать runtime-entity, но инвариант остаётся: Execution Planner не меняет утверждённый verdict.

## 7. Правила очистки

Оперативная часть находится между маркерами `RT-EXEC:BEGIN` / `RT-EXEC:END`.

Очищать её разрешено только когда одновременно выполнено:

- PLAN APPROVAL записан;
- профильный канонический implementation plan обновлён;
- mapping verdict → canonical plan проверен;
- создана/зарегистрирована первая исполнительная TASK либо явно записан следующий execution action;
- состояние запечатано git commit или пользователь явно разрешил сброс без commit.

### 4. Детализация TASK и границы

#### P00 — Canonical Plan Handoff

Сделать только документационный перенос утверждённого решения:

- `23`: новые архитектурные инварианты и authority boundary;
- `24`: заменить старый маршрут WA-3→WA-4 на WA-3 closeout → RC-0…RC-6 → WA-4;
- `25`: append-only запись о decision/plan transition;
- исправить устаревшие CURRENT/status формулировки, не переписывая историю;
- явно сопоставить старые WA-4.1–WA-4.7 из `24` с новым маршрутом: WA-4.1/4.2 → `WA4-E` (с предварительными RC-boundaries), WA-4.3 lease → **DEFERRED по V17** после базовой serialization/CAS, WA-4.4 retention и WA-4.5 security → сохранить как cross-cutting constraints, WA-4.6 Task Progress UI → `WA4-O`, WA-4.7 Rollout → `WA4-R`;
- зафиксировать старый combined criterion WA-3 как SUPERSEDED / DEFERRED, **не PASS**.

**Не делать:** runtime, refactor, RC-0 code.

#### RC-0 — Baseline

До изменения storage/recovery contracts зафиксировать:

1. полный regression baseline;
2. Remote calls per logical mutation;
3. Actions to safe resume;
4. Untracked mutation ratio;
5. Manual status sync count;
6. byte/hash/line-ending policy;
7. policy для `.gitattributes`;
8. snapshot secret/scope/retention constraints как требования следующих этапов.

Числа из аналитики не считать baseline без измерения.

#### RC-1 — Durable Operation Contract

Минимальный контракт операции должен переживать новый process/Chat без внешней памяти:

```text
operation identity
canonical target identity
action
expected pre-state
expected post-state
durable mutation payload / immutable payload reference
request fingerprint / idempotency identity
agent identity / provenance
schema version
result receipt
timestamps / revision
```

Обязательна migration/backward-compatibility стратегия существующего persistent storage.

**Первый рекомендуемый substantive code handoff:** Claude Opus 5.5 после PASS P00 и RC-0.

#### RC-2 — Resolver

Reconciliation перестаёт быть только советом.

Resolver применяет только decision, привязанное к текущей evidence revision. При изменившемся target/revision — fail-closed и новая reconciliation.

`RETRY` на этом этапе означает только **persistent re-arm / tracked request на повтор** с тем же `operation_id` и новым разрешённым переходом состояния. RC-2 не выполняет физическую mutation: фактическое повторное исполнение появляется только в authoritative executor `WA4-E`.

#### RC-3 — Conflict / serialization / CAS

RC-1 уже защищает целостность записи persistent Operation Store/revision между процессами. RC-3 добавляет более высокий уровень: conflict gate по canonical physical target, mutation-boundary CAS и ownership reservation для конфликтующих mutations.

Canonical target обязан учитывать Windows path normalization/case и не позволять обойти conflict gate другим spelling.

До PASS RC-3 не запускать несколько mutating агентов параллельно по пересекающемуся scope.

После RC-3 параллельность разрешается только для явно независимых scopes и с ownership reservation.

#### RC-4 — Rollback

Rollback не должен уничтожать неизвестный current drift.

Перед destructive restore сохраняется recoverable current state. Сам rollback получает tracked identity, event/receipt и verification.

#### RC-5 — Projection correctness

Checkpoint становится projection, а не самостоятельной истиной:

- rebuild from authoritative state;
- revision validation;
- stale projection fail-closed;
- read/inspect methods не меняют state;
- closeout gate не завершает TASK при open/unresolved operations.

Обязательны реальные multiprocess race tests, а не только однопроцессный regression.

#### RC-6 — Project-level Recovery Closure / bounded resume coordinator

Изначальная цель пользователя сохраняется:

```text
новый агент
→ одна команда recover/resume
→ authoritative project position
→ один NEXT SAFE ACTION
```

Утверждённая Chat TASK `CHATGPT-WA-008` расширяет старый read-only RC-6: одна canonical команда может bounded выполнять только уже разрешённые safe recovery / administrative steps поверх RC-5 Projection + RC-2 Resolver + RC-3 ownership + RC-4 rollback, пока TASK не достигнет `READY_FOR_EXECUTION`, human-decision boundary или fail-closed blocker.

Ключевая граница остаётся прежней: RC-6 **не выполняет normal physical mutation** следующей operation. Fresh accepted `RETRY` только подготавливается и возвращается как NEXT для будущего authoritative Executor `WA4-E`. ADOPT / ABORT получают durable lifecycle semantics; ROLLBACK использует существующий RC-4, а не второй restore engine.

Coordinator не создаёт новую competing truth: после каждого recovery mutation перечитывается fresh RC-5 Projection, и именно она задаёт final state/NEXT. Обязательны bounded loop, restart/replay safety и multiprocess races `recover vs recover / Resolver / new operation`.

Полноценный UI ещё не требуется.

#### WA4-E — Executor

Mutation transaction должна механически владеть цепочкой:

```text
intent
→ canonical target
→ snapshot current bytes/state
→ CAS/precondition
→ physical mutation
→ exact post verification
→ persisted receipt
→ return result
```

Повтор того же durable contract после потерянного ответа возвращает persisted receipt и не создаёт второй side effect.

#### WA4-A — Fault injection

Приёмка не зависит от ручного попадания в момент disconnect:

```text
mutation physically applied once
→ receipt persisted
→ response intentionally suppressed/lost
→ fresh process / new Chat
→ same durable operation request
→ same authoritative receipt
→ no second physical side effect
```

Именно здесь живёт смысл бывшего stricter combined criterion WA-3.

#### WA4-O — UX / Ops

После correctness:

- Situation UI;
- persistent jobs;
- automatic transport sensor;
- generated current status;
- минимизация ручной status synchronization.

#### WA4-R — Rollout

```text
OBSERVE
→ WARN
→ GATEWAY REQUIRED
→ STRICT
```

Strict нельзя включать раньше полного regression и подтверждения, что bypass tracked mutations обнаруживается/блокируется по принятой политике.
