## 1. Зачем существует документ 33

Круглый стол заканчивает decision authority в документе `32`: сформирован verdict, получен USER APPROVAL, записан Decision Record.

После этого ещё нельзя сразу начинать код, если утверждённое решение состоит из нескольких зависимых работ. Нужен отдельный planning bridge:

```text
32 — approved verdict / Decision Record
↓
33 — исходный execution plan draft
↓
по RT-FINAL-01: 33 без альтернатив / 33.3 при запечатанных альтернативах
↓
USER PLAN REVIEW
↓
PLAN APPROVAL
↓
перенос в канонический профильный implementation plan
↓
создание и запуск отдельных TASK
↓
verification / профильный журнал
```

`33` отвечает на вопрос **«как разложить уже принятое решение на исполнимые TASK»** и сохраняет первоначальный план. Если задействованы сданные альтернативы, окончательную согласованную редакцию и approval получает только документ 33.3; если альтернатив не было — 33. Он не имеет права заново решать вопрос Круглого стола.

**Временный генератор плана:** после PLAN APPROVAL и проверенного переноса план, статусы и дальнейшая работа ведутся в канонической профильной документации соответствующей подсистемы. Документ `33` не становится постоянным местом разработки или сопровождения плана.

## 2. Универсальные входы

Для каждого плана обязательны:

- RT-ID и approved verdict из `32`;
- версия/hash утверждённого verdict;
- Decision Record;
- актуальное состояние затронутой подсистемы;
- профильные архитектурные документы;
- существующий профильный implementation plan, если он уже есть;
- зависимости, ограничения и deferred-пункты verdict;
- точная версия исходников/тестов и рабочее состояние перед handoff, полученные от пользователя/уполномоченного координатора; локальный агент не вызывает Git по `DOC-GIT-01@1`.

**До составления плана обязательна проверка актуальных источников:** изучить текущий исходный код затронутых компонентов, архитектуру, профильную программу/план реализации и существующие тесты. По результатам сверки зафиксировать в плане реальное состояние реализации, зависимости, риски и критерии приёмки. Старые отчёты не могут быть единственным основанием плана; непроверенные предположения не выдаются за факты.

Если между verdict и planning обнаружен drift, меняющий предпосылки решения, `33` не адаптирует verdict молча: затронутый пункт возвращается на **ПЕРЕРАБОТАТЬ** новым `RT-xxx`.

## 3. Обязательный выход

Execution plan должен содержать:

1. цель исполнения;
2. целевой канонический plan/document destination;
3. ordered TASK graph;
4. зависимости, блокировки и риски;
5. scope каждой TASK;
6. что TASK сознательно не делает;
7. acceptance/verification каждой TASK;
8. proposed executor, если это полезно;
9. concurrency/ownership rules;
10. mapping пунктов verdict → TASK;
11. условия передачи плана в канонический профильный документ;
12. PLAN APPROVAL пользователя.

План не должен превращаться в огромную единую TASK. Correctness boundaries должны быть отдельными проверяемыми задачами.

## 4. Правила планирования

1. **Verdict immutable для Planner.** `33` может декомпозировать, упорядочивать и назначать исполнителей, но не менять утверждённое содержание.
2. **Decision ≠ plan ≠ execution.** `32` отвечает «что принято», `33` — «как исполнять», профильный implementation plan — «какой план теперь канонический», TASK — «что выполняем прямо сейчас».
3. **USER PLAN REVIEW обязателен.** До подтверждения пользователя выбранный итоговый план из `33` либо `33.3` не переносится в профильные документы и TASK не запускаются.
3а. **Два постоянных необязательных слота `[[33.1_Круглый стол - альтернативное планирование A]]` и `[[33.2_Круглый стол - альтернативное планирование B]]`.** По поручению пользователя слоту назначается INDEPENDENT_PLAN или REVIEW. Слоты остаются NOT_REQUESTED без поручения и не запускают анализ; самостоятельный исходный план слепого участника скрыт до SUBMITTED. Полный контракт — PLAN-MODES-01/PLAN-SEAL-01 выше.
3б. **Обязательный выбор финала (`rule-ref:RT-FINAL-01@1`):** если 33.1/33.2 не дали ни одного SUBMITTED, утверждаемый документ — 33; если хотя бы один запечатанный вклад существует и группа раскрыта, заполняется **только 33.3**, даже при полном совпадении с исходным 33. Пока раскрытие или сдача не завершены, итоговый approval блокируется.
4. После PLAN APPROVAL содержимое выбранного финала переносится/встраивается в профильный implementation plan. С этого момента именно профильный документ становится каноническим владельцем плана.
5. После проверенного handoff выбранный итоговый документ `33`/`33.3` перестаёт быть источником рабочего плана. Его оперативная часть может быть очищена **только после** полного внешнего seal/retention и отдельного разрешения пользователя по RT-CLEANUP-01, а постоянная инструкция остаётся.
6. При нескольких профильных подсистемах один execution plan может иметь несколько destination, но каждый фрагмент должен получить одного канонического владельца.
7. До появления технического ownership/locking разные агенты **не изменяют параллельно пересекающийся scope**.
8. Proposed executor не является жёсткой привязкой к физической модели. Role ≠ Model ≠ Connection Adapter.
9. Отложенные/отклонённые пункты verdict не превращаются в TASK скрытно.
10. Никакой runtime-код не меняется самим фактом заполнения `33`.

## 5. Lifecycle документа 33

```text
EMPTY
↓ approved RT verdict / Decision Record
DRAFT
↓ план сформирован
AWAITING PLAN REVIEW
↓ если включён SUBMITTED альтернативный вклад: после разрешённого reveal итог заполняется в 33.3; 33 сохраняет исходник
↓ иначе финальным кандидатом остаётся 33
↓ USER PLAN APPROVAL только выбранного документа
APPROVED FOR HANDOFF
↓ профильный plan обновлён и проверен
HANDED OFF
↓ отдельные TASK создаются из канонического профильного plan
↓ после архивирования, проверки восстановления и отдельного разрешения пользователя оперативная часть может быть очищена
EMPTY
```

`ROUND TABLE CLOSED` остаётся состоянием Круглого стола уже после `32`. Документ `33` — **post-round execution planning**, а не дополнительная decision-stage.

## 6. FUTURE Ultra

В будущей Ultra функции этого документа выполняет Execution Planner / Coordinator:

```text
Approved Verdict
→ Execution Plan
→ Task graph
→ Role/Agent assignment
→ dependency / ownership control
→ execution TASKs
→ verification
→ reconciliation
```

Ручная пара `33` (исходник) / условный `33.3` (итог при альтернативном участии) — прототип этого слоя. После автоматизации формат может стать runtime-entity, но инвариант остаётся: Execution Planner не меняет утверждённый verdict.

## 7. Правила очистки

Оперативная часть находится между маркерами `RT-EXEC:BEGIN` / `RT-EXEC:END`.

Очищать её разрешено только когда одновременно выполнено:

- PLAN APPROVAL записан;
- профильный канонический implementation plan обновлён;
- mapping verdict → canonical plan проверен;
- создана/зарегистрирована первая исполнительная TASK либо явно записан следующий execution action;
- исходный и итоговый план, SUBMITTED альтернативы, comparison, approvals, essential raw evidence и внешние locators сохранены и проверены на восстановимость;
- пользователь **отдельно** разрешил очистку (commit/handoff сами по себе её не разрешают).

**Главный принцип:** защита реально выполняется в Server *до* каждого внешнего HTTP-вызова; UI — интерфейс управления и наблюдения, но не охранный механизм. Закрытие UI / неисправность Audit / переключение ролей не отключают защиту. Доступные значения задаются пользователем; защищённый минимальный policy layer и валидация остаются в коде. Если UI отключает лимит или значение выходит за безопасную границу, явное подтверждение/отказ по политике, без скрытого обхода safety.

## B. Как будет выглядеть это для пользователя

Предложена группа настроек **«Контроль расходов и контекста»** в существующем `ultra_ui.py` (не отдельное чужое приложение). Окончательную компоновку проверить на рабочем окне Tkinter, без перегрузки интерфейса.

| Блок UI | Настраивается пользователем | Что видно сразу | Зачем это по-человечески |
| --- | --- | --- | --- |
| **Лимиты** | предельный размер полного `read_file`; общий предельный объём/оценка входа запроса; бюджет одного HTTP-attempt; лимит запросов/попыток и всего RUN; запас на обязательную проверку | значения, единицы (bytes/tokens/attempts), профиль, индикатор остатка и причина BLOCKED | Ultra не сможет незаметно потратить огромный контекст |
| **Роли** | отдельно Planner, Executor, Final Audit/Dredd; независимая история/context policy; отдельно enable/disable Planner и Audit по действующим правилам | активные настройки каждой роли | одна галочка не меняет тайком три разные политики |
| **Контекст** | безопасные варианты для больших файлов и поведение при превышении; режим stage compiler по фазе rollout | что вошло/не вошло в следующий запрос, объём до/после, ссылки на полный материал в Run Store | видно, куда делись токены; ничего важного не исчезает бесследно |
| **Расход / Журнал** | отображение, фильтр по RUN/роли; экспорт диагностического отчёта без секретов | provider-reported, cached, processed estimate, attempts, UNKNOWN, предсказанное vs фактическое, причины отказов | можно самому проверить эффект, не читая сырые JSON |
| **Режим проверки** | локальный демонстрационный сценарий/mock, позднее отдельно live с подтверждением | ожидаемо/фактически, PASS/FAIL/BLOCKED, расход *реальных* токенов = 0 для offline | каждое улучшение можно пощупать безопасно |

**UX-договор:** обычные значения и понятные подсказки; расширенные настройки можно сворачивать. В каждом новом управлении: текущее значение, безопасное значение по умолчанию, допустимый диапазон, единицы, объяснение рисков, «Применить», явный признак сохранения, «Сбросить» и объяснение, распространяется ли изменение на будущие RUN или уже запущенный. **Никакого изменения активного бюджета во время RUN, которое молча обнуляет расход**. Негативный статус сообщает: что ограничено, каким действием, как исправить настройку без отключения safeguards. Конкретные числовые defaults не назначать наугад: утвердить после offline-benchmark и проверки модели.

## C. Полная последовательность TASK и проверяемые контрольные точки

**Не запускать всё одной огромной задачей.** Ниже — предлагаемый исполнимый граф после PLAN APPROVAL, а не разрешение на выполнение. Каждый этап завершает offline unit/integration, GUI smoke (если есть UI), визуальное наблюдение и запись в 21. Открытые defects не прятать статусом SUCCESS.

### Фаза 0 — очистить доказательства и зафиксировать эталон

**T0 — Приёмка 151C / КТ-3** *(V-8, dependency)*. Независимый проверяющий перепроверяет Codex recovery по source IDs, обязательным evidence, свежести, literal paths, truncated output и git dirty; PASS или мотивированный FINDINGS, без ложного DONE.
- **Увидишь:** «151C принят / не принят, почему» и компактный пример Audit Packet.
- **Сам проверишь:** открыть в UI выбранный offline RUN и убедиться, что обязательные отрицательные факты и источник материала видны, а слепой PASS невозможен. Тесты — mock, не live.
- **Gate:** до принятия 151C не объявлять КТ-3 и не развивать зависящие от него 151D/151G.

**T1 — Нулевой benchmark и карта маршрутов API** *(V-1, V-2, V-7, V-9)*. Зафиксировать R-031/R-027, R-026/R-033 и clean/dirty контрольные образцы; провести inventory всех выходов к provider (Executor, Planner INITIAL/READINESS/REPLAN, Final Audit/Dredd, repair, direct, diagnostic, Compressor/Chat если эти пути попадают в согласованный scope). Отдельно описать границу RUN vs обычный чат. Offline-сравнение размеров запросов, количества попыток, расхода по ролям; не повторять дорогой R-031.
- **Увидишь:** таблицу «до», причину перерасхода и наглядную схему маршрутов.
- **Сам проверишь:** открыть отчёт на R-031 и увидеть рост двух повторных больших read, без нового вызова API.
- **Gate:** перечень маршрутов не имеет необъяснённых дыр; фиксированы исходные метрики и применимость лимитов.

### Фаза 1 — предохранители раньше оптимизации контекста

**T2 — Единая спецификация budget policy и UI preview** *(V-3, V-4; обязательный вход для реализации)*. Формально определить единицы и семантику: logical file bytes, serialized request bytes, приблизительная preflight оценка токенов, provider final usage, попытки/повторы, общий RUN cap, роли, резерв Audit/verification, UNKNOWN. Ограничения отдельно на большой full `read_file` **и** на весь запрос; apply precedence и перезапуск. Предусмотреть policy migration, validation, профили и флаг safe rollback, отличать soft warning от hard stop. Макет панели обсудить до реализации.
- **Увидишь:** таблицу полей UI и ожидаемых действий; что произойдёт при каждом превышении.
- **Сам проверишь:** на макете/офлайн contract-test пройти примеры «маленький файл», «слишком большой», «исчерпан RUN», «unknown usage».
- **Gate:** никакой цифры лимита без единиц, строгой семантики и fallback; UI и Server используют одну валидированную схему.

**T3 — Budget Server / pre-HTTP fail-closed** *(V-3; P0 ДО 151G)*. Ввести authoritative in-process RUN-budget ledger и атомарный preflight на всех релевантных provider paths: оценка до HTTP, reservation, attempt identity, terminal reconciliation, idempotency при повторах, recovery/replan без reset, persistent diagnostic events + durable snapshot для восстановления (не считать runtime callbacks авторитетом). Лимит не должен обнуляться от ошибки Audit, GUI, смены stage; UNKNOWN не считать нулём, прежде чем разрешить следующую попытку. Сохранить обязательный verification reserve; не обещать точный billing до получения provider usage.
- **Увидишь:** остаток бюджета RUN, количество попыток, причину отказа, предупреждение об оценке.
- **Сам проверишь:** offline fake-provider: пакет больше лимита ⇒ **0 HTTP**, BLOCKED, сервер сообщает причину; recovery ⇒ прежний расход; двойной terminal ⇒ без двойного списания; отказ Run Store ⇒ fail-closed.
- **Gate:** обязательная matrix каждой роли и маршрута, включая diagnostic, direct и repair; нет тихого обхода и отрицательного остатка.

**T4 — Честное чтение больших файлов** *(V-4)*. Подключить настраиваемый separate limit для полного `read_file`; при превышении выдавать детерминированное `LARGE_FILE` / путь `find_text` или `read_file_range`. Проверить взаимодействие с уже имеющимся 2 MiB file bound и общим request gate. Никакого молчаливого partial content, masking или бесконечного повторного чтения.
- **Увидишь:** «Файл слишком большой для полного чтения; выбери диапазон» и фактические размеры.
- **Сам проверишь:** выбрать тестовый большой текст: полный READ отклонён, SEARCH и RANGE работают; успешная маленькая выборка не списывает бюджет как большой полный файл.
- **Gate:** отказ не делает будущую VERIFY ложноположительной; все ошибки обратимы через UI/корректный workflow.

**T5 — Панель «Лимиты и бюджет» в Tkinter** *(сквозное пользовательское требование)*. Реализовать редактирование/сохранение/валидацию T2–T4 через UI с нейтральными defaults и безопасным fallback; текущий RUN получает immutable effective policy snapshot, будущие RUN — новую. Сохранение настройками workspace/профиля без смешения with `ui_state.py` presentation и `workspace_runtime_settings.py` paths; формат выбрать при реализации после ревью владельца данных.
- **Увидишь:** живую панель, редактируемые пределы, предупреждения и историю BLOCKED.
- **Сам проверишь:** изменить предел → перезапустить Ultra → значение осталось; создать mock RUN → увидеть реально применённый effective cap и невозможность обхода через старый snapshot.
- **Gate:** значения UI фактически доходят до Server, проверка не декоративная; тесты на коррумпированные настройки и миграции.

### Фаза 2 — прозрачный и экономный контекст, без потери доказательств

**T6 — Stage Context Compiler 151G, minimal functional slice** *(V-2, V-5)*. Собирать для каждого Executor API только current-stage facts/relevant material + RAW TASK + authoritative plan/stage + failures/freshness. Сохранять все полные tool outputs в Run Store, но заменять старые повторные большие payloads на bounded references/summaries; explicit re-access для нужного evidence. Отличать fresh/stale и запретить тихую потерю actual material; исправить separated large reads, а не только соседние повторения.
- **Увидишь:** «контекст до/после» по роли/stage, список сохранённых/исключённых блоков с причиной, ссылки на full audit record.
- **Сам проверишь:** offline воспроизвести R-031-подобную цепочку «большой файл → действия → повторный read»: запрос не растёт ступенчато, нужный негативный факт остаётся виден.

**T7 — UI «Что видела модель» и Context Inspector** *(V-5, пользовательский UX)*. Обновить уже существующие панели диагностики: отдельный режим краткого набора blocks, размер, роль, stage, source IDs, truncation, freshness и почему блок включён/исключён. Полный Audit по требованию, не засорять основной экран.

- **Сам проверишь:** открыть offline RUN и сверить содержимое последнего запроса с Inspector; сохранённый полный файл доступен для Audit.
- **Gate:** UI отображает именно фактический отправленный request, а не гипотетическую «экономию».

**T8 — Корректность Final Audit и Task Stage** *(V-6)*. Исправить `task.stage` и typed границу internal protocol vs пользовательский ответ: `{"candidates":[]}` не является корректным человеческим ответом и не может пройти Final Audit PASS как результат обычного приветствия. Проверить семантический fallback, отсутствие ошибочной подстановки.
- **Увидишь:** человеку понятный результат или BLOCKED с объяснением; сырой протокол остаётся только в диагностике.
- **Сам проверишь:** offline scripted «приветствие → ошибочный protocol JSON» получает FAIL, а нормальный ответ — корректный verdict.

- **Gate:** невозможно случайно отключить обязательную проверку обходным флагом; изменения условий пользователь видит явно.

**T11 — Пути, `contains`/`equals` и проверка dirty tree** *(V-8, V-12)*. - **Сам проверишь:** офлайн относительный путь однозначно разрешён, `contains` проходит при включении строки, не подменяется `equals`; если причины dirty discrepancy не найдены — остаётся UNRESOLVED, а не фиктивный PASS.

## E. Что запрещено и как ограничиваем цену тестов

1. **Offline-first без внешних LLM:** unittest/pytest с mock HTTP/recorded fixture, статический анализ, scripted adapter fake, GUI smoke в тестовом Workspace. Отдельные runner флаги: `OFFLINE_ONLY=true`, запрет настоящих sockets в тестах, fake credentials, temp appdata/workspace, отдельный profile.
2. Любой тест, который может привести к платному вызову, отмечать **LIVE / COST RISK**: не запускать автоматически; нужна отдельная команда пользователя, test-specific hard cap, прогноз верхнего расхода и Stop/Abort на первом отклонении. Сценарии вроде R-031 **не повторять live**. «Ноль платных токенов» обещаем только для реально полностью изолированного mock-пути.
3. Сначала показывать каждый небольшого шага через UI/скрин или лог с человеческой легендой; не требовать от пользователя читать тысячи строк, чтобы убедиться в работе. Для чисто серверных инвариантов — доступный из UI статус + протокол offline проверок.
4. Не отключать mandatory evidence/Final Audit незаметно ради меньшего расхода; снижение цены не считается успехом при ложном PASS, потерянном материале или частичной записи.
5. Изменение safety policy требует validation, migration и rollback к совместимым исходным настройкам; не убирает факт уже потраченных токенов. В процессе активного RUN нельзя повысить лимит с пересчётом расхода в ноль.
6. Пользователь лично проверяет incremental demo: пока текущая контрольная точка не принята, зависимые TASK не стартуют. Отсутствие GUI для backend-only требования допускается лишь с объяснением, как убедиться через audit/тест.
7. Не делать запросов к платным LLM на этапе написания/утверждения самого плана. Отказ/ошибка обязаны дать понятную причину и NEXT, а не молчание.
