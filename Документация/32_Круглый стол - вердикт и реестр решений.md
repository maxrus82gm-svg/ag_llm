# Круглый стол — вердикт и реестр решений

**Назначение:** короткий decision-ready вердикт по текущему вопросу Круглого стола для человека, фиксация USER APPROVAL и постоянный реестр закрытых решений. Протокол и карточка вопроса — `28_Круглый стол - протокол и текущий вопрос`.

## Постоянная инструкция

**Входы:** [[31_Круглый стол - синтез и разногласия]] с пройденным representation check; карточка вопроса в `28`.

**Выход:** вердикт по пунктам → USER APPROVAL → Decision Record в реестре ниже.

**Состояния пункта решения:**
- **ВНЕСТИ** — решение утверждено для переноса в соответствующие документы и/или код;
- **НЕ ВНОСИТЬ** — решение отклонено;
- **ОТЛОЖИТЬ** — решение пока не готово к переносу;
- **ПЕРЕРАБОТАТЬ** — требуется новый цикл анализа: новый `RT-xxx` со ссылкой на родительский.

**Критическое правило:** если для пункта нет утверждённого пользователем состояния ВНЕСТИ, **никакие изменения канонической документации или runtime на его основании не выполняются**. Сам факт появления аналитики, синтеза или проекта вердикта не меняет `01` и профильные документы.

**После утверждения:** approved verdict передаётся в [[33_Круглый стол - план исполнения]]. Там формируется post-round execution plan с TASK graph, зависимостями, scope и acceptance. До отдельного USER PLAN REVIEW / PLAN APPROVAL этот план не переносится в профильные документы и execution не начинается. После PLAN APPROVAL план передаётся в канонический профильный implementation plan, и только затем создаются отдельные исполнительные TASK.

**Закрытие:** Круглый стол закрыт после USER APPROVAL и записи Decision Record. Planning в `33` и последующие исполнительные TASK живут дальше независимо и не переоткрывают Круглый стол.

**Разрешено:**
- формулировать вердикт строго на основе `31`;
- держать оперативный вердикт коротким — на одну-две страницы.

**Запрещено:**
- добавлять пункты, которых нет в `31`, без явной пометки;
- объединять разные решения в один пункт;
- фиксировать USER APPROVAL от имени пользователя;
- удалять или переписывать строки реестра.

**Шаблон вердикта:**

```text

Предпосылки для проверки дрейфа исполнительной TASK:

USER APPROVAL

Execution plan / package:
```

**Правила очистки:** оперативная часть между `RT:BEGIN` и `RT:END` очищается только после записи Decision Record. Реестр решений — постоянный, append-only, вне маркеров; при сбросе не меняется.

### RT-001 — вердикт

**Финализатор:** GPT-5.6 Sol.
**Основание:** `31_Круглый стол - синтез и разногласия.md`, 2026-10-03; representation check A = DONE, B = DONE.
**Версия основания:** HEAD `dc246b9` + текущий representation check B; SHA-256 файла `31` = `e478de1bfebfd0c13c2cb741cc23019f867fe23671641fd6cabf4480717f12db`.

### Итоговое решение

WEB-02 сохраняет выбранное направление, но следующий шаг меняется: **не начинать WA-4 напрямую и не добивать старый WA-3 ещё одним ручным disconnect-тестом. Сначала провести отдельную Recovery Closure program, которая замыкает durable operation contract, recovery lifecycle, serialization/CAS и authoritative resume; затем строить mutation executor/gateway и уже на нём проводить детерминированный lost-response fault injection.**

WA-3 считать завершённой только через явное решение: строгий старый combined criterion **SUPERSEDED / DEFERRED, НЕ PASS**. Его смысл переносится в более сильный acceptance нового executor.

### Не принято

- Старый combined criterion WA-3 **не получает PASS задним числом**.
- Числовые оценки Remote-call savings не становятся обещаниями/критериями без измерений.
- Новый lifecycle, storage backend, lease protocol и MCP topology не фиксируются этим раундом.

### Не определено / unresolved

Это не блокирует V1–V14, но должно быть разрешено внутри соответствующих RC-задач либо отдельным анализом:

- точная модель multi-file operation / transaction group;
- точный migration format для существующих persisted operation records;
- конечная hash/line-ending policy;
- модель non-file operations (`git`, process, network);
- lease semantics, если после serialization/CAS она действительно потребуется;
- выбор SQLite vs file/event storage.

Перед любым переносом этого решения в канонические документы/runtime исполнитель обязан:
