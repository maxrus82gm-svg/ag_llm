### Быстрый вход для сменяемого агента — обязательный порядок

Если пользователь в любом чате поручил «Приступай к оформлению документа 32 Круглого стола» (с указанием RT-ID или с однозначно активным RT-ID из 28), это **явное назначение адресата автором проекта вердикта 32**, а не разрешение утверждать решение, запускать 33 или менять код. Модель не закреплена за документом: ChatGPT, Claude, Codex, Astra или другой агент действуют по одинаковым правилам. Если конкретное поручение противоречит более новому назначению в 28, сначала согласовать назначение; не присваивать роль самовольно.

1. **Точка входа — сам документ 32.** Прочитать его постоянную инструкцию и актуальный оперативный RT; затем открыть **28** (активная карточка, стадия, назначение, NEXT ACTION), **31** (основной финальный синтез) и **31.1 / 31.2** (последние личные проверки каждого участника). В новом чате без восстановленного проектного контекста использовать общий маршрут 08 → 000 → 34; это не заменяет чтение 28/31/31.1/31.2.
2. **Проверить gate по содержимому, а не по памяти чата.** Вычислить полный SHA-256 **текущего файла 31**. Найти в 31.1 и 31.2 **последнее относящееся именно к этому SHA-256 датированное заключение** каждого назначенного участника. Требуются два личных, явных статуса **PASS**, тот же полный SHA-256, аттестация проверки и отсутствие незакрытых замечаний к точности представления позиций. Старый PASS другого SHA, условное «буду согласен», прошлые FINDINGS, молчание или оценка координатора PASS не заменяют. Не требовать исчезновения законных содержательных UNRESOLVED из самого синтеза — они переходят в проект вердикта.
3. **Сверить запись координатора в 28.** Representation gate должен быть явно зафиксирован для того же SHA-256. Если в 28 остался устаревший статус при реально полученных обоих PASS, назначенный координатор сначала документирует сверку и закрытие gate в 28, не изменяя 31 и не подписывая PASS за участников. Если назначение/версия/подлинность проверок не установлены — остановка.
4. **Решение о входе:** при выполнении всех условий — `READY FOR VERDICT`: создать **проект**, опираясь прежде всего на 31; 31.1/31.2 использовать для подтверждения точности. Исторические 29/29.1/30/30.1 читать адресно лишь для проверки ссылок или доказательств, без нового R1/R2. При отсутствии любого обязательного подтверждения — `BLOCKED / REPRESENTATION GATE`: **не оформлять вердикт, обязательно выпустить короткий диагностический отчёт по шаблону ниже**, указать конкретное препятствие и действие для разблокировки. Молчаливый отказ или одно слово `BLOCKED` недопустимы.
5. **Остановиться на границе полномочий:** проект 32 содержит отдельные предложения с источниками, вариантами состояний и нерешёнными вопросами; `USER APPROVAL: NOT REQUESTED / PENDING` до реального ответа пользователя. Ни агент, ни два PASS не утверждают предложения автоматически. Только после личного USER APPROVAL и записи Decision Record открывается отдельная стадия планирования 33.

### Обязательный мини-отчёт при отказе в старте (preflight BLOCKED)

Если вход в стадию 32 запрещён, агент **обязательно**:
- сообщает пользователю конкретную причину, найденные доказательства и точный NEXT ACTION; не пишет просто «остановился»;
- сохраняет краткую запись **`PREFLIGHT BLOCKED`** в оперативной части этого 32 (между `RT:BEGIN`/`RT:END`), если файл доступен для разрешённой записи; это **диагностика допуска, а не проект вердикта и не Decision Record**; существующий вердикт/историю не стирать;
- если запись невозможна, возвращает тот же полный мини-отчёт в чат с пометкой `NOT PERSISTED`, не утверждая, что журнал обновлён; чужие проверки 31.1/31.2 и синтез 31 не исправлять;
- при нескольких препятствиях перечисляет все обнаруженные, не придумывая статусы для непроверенных источников. После отчёта дальнейшая работа на стадии 32 запрещена до устранения блокировки и новой проверки.

**Компактный формат (человекочитаемый и пригодный для события Ultra `STAGE_BLOCKED`):**

```text
RT-ID / stage: RT-xxx / VERDICT_32
Status: BLOCKED
Reason code: MISSING_PASS | FINDINGS_OPEN | HASH_MISMATCH | GATE_NOT_CLOSED | ROLE_MISMATCH | SOURCE_UNAVAILABLE | OTHER
Checked at / agent:
31 SHA-256: <фактический либо UNAVAILABLE>
31.1: <PASS/FINDINGS/BLOCKED/MISSING/UNVERIFIED; версия/hash; ссылка на запись>
31.2: <PASS/FINDINGS/BLOCKED/MISSING/UNVERIFIED; версия/hash; ссылка на запись>
28 gate: <PASS/CLOSED или PENDING/UNVERIFIED; ссылка>
Why blocked: <1–3 конкретные фразы без догадок>
NEXT ACTION / responsible: <что требуется сделать и кому>
32 verdict: NOT STARTED; USER APPROVAL: NOT REQUESTED
Report persistence: RECORDED_IN_32 | NOT_PERSISTED
```

Для будущей Ultra эти же поля сохраняются как структурированное диагностическое событие; остановка стадии и запись причины — **единое обязательное действие**, а не тихий сбой. Отсутствие PASS не подменяется автоматическим согласием или автоповтором платного вызова.

**Входы:** документ 31 с учтёнными результатами отдельных проверок 31.1 / 31.2; карточка вопроса в `28`. Здесь номера упоминаются обычным текстом: граф должен вести от 31 к 32 через два проверочных документа, без прямого ребра.

**Representation gate:** координатор сверяет 31.1/31.2 с **полным SHA-256 текущего итогового содержания 31**. После **любого изменения** синтеза прежние PASS остаются историей, но не означают PASS новой версии: каждый участник должен **лично** дать новый explicit PASS, допустима короткая адресная проверка diff. Условное согласие и оценка самого координатора не заменяют ответ агента. Gate закрыт только если все участники проверили одну и ту же текущую версию и не оставили претензий к точности передачи их позиций. Содержательные нерешённые вопросы сохраняются честно для вердикта. Без gate к подготовке проекта решения в 32 не переходить.

**Выход:** вердикт по пунктам → USER APPROVAL → Decision Record в реестре ниже.

**Состояния пункта решения:**
- **ВНЕСТИ** — решение утверждено для переноса в соответствующие документы и/или код;
- **НЕ ВНОСИТЬ** — решение отклонено;
- **ОТЛОЖИТЬ** — решение пока не готово к переносу;
- **ПЕРЕРАБОТАТЬ** — требуется новый цикл анализа: новый `RT-xxx` со ссылкой на родительский.

**Критическое правило:** если для пункта нет утверждённого пользователем состояния ВНЕСТИ, **никакие изменения канонической документации или runtime на его основании не выполняются**. Сам факт появления аналитики, синтеза или проекта вердикта не меняет `01` и профильные документы.

**После утверждения:** approved verdict передаётся в [[33_Круглый стол - план исполнения]]. Там формируется post-round execution plan с TASK graph, зависимостями, scope и acceptance. До отдельного USER PLAN REVIEW / PLAN APPROVAL этот план не переносится в профильные документы и execution не начинается. После PLAN APPROVAL план передаётся в канонический профильный implementation plan, и только затем создаются отдельные исполнительные TASK.

**Закрытие:** Круглый стол закрыт после USER APPROVAL и записи Decision Record. Planning в `33` и последующие исполнительные TASK живут дальше независимо и не переоткрывают Круглый стол.

**Разрешено:**
- формулировать вердикт строго на основе `31` и двух результатов representation check;
- держать оперативный вердикт коротким — на одну-две страницы.

**Запрещено:**
- добавлять пункты, которых нет в `31`, без явной пометки;
- объединять разные решения в один пункт;
- фиксировать USER APPROVAL от имени пользователя;
- удалять записи постоянного архива 35 и очищать текущий RT до handoff.

**Шаблон вердикта:**

```text
### RT-xxx — вердикт
Основание: 31 (дата / commit)

Пункты решения:
№ | Что предлагается | Куда внести | Критерий приёмки | Предлагаемое состояние

Не принято:
Не определено (unresolved):
Предпосылки для проверки дрейфа исполнительной TASK:

USER APPROVAL
Дата:
Утверждённые пункты и итоговые состояния:
Версия / hash вердикта:
Execution plan / package:
```

**Правила очистки:** оперативная часть между `RT:BEGIN` и `RT:END` очищается только после записи Decision Record. Реестр текущего RT можно очистить после USER APPROVAL, проверенного handoff и записи краткого итога в постоянный архив 35.
