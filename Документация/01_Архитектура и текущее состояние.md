# Архитектура и текущее состояние GigaChat Ultra Local Agent

## Статус документа

Этот документ описывает **фактическое текущее состояние** проекта `ag_llm / GigaChat Ultra Local Agent`.

Он должен отражать то, что реально существует в коде и было подтверждено тестами или живым runtime.

Будущие функции здесь явно отделяются от реализованных.

# 1. Общая архитектура

Проект больше не является системой, жёстко привязанной к одной модели `GigaChat-3-Ultra`.

Текущая архитектура развивается как локальный Agent Runtime, в котором модель является заменяемым вычислительным компонентом.

Упрощённая схема:

```text
USER
↓
Ultra UI
↓
AGENT RUNTIME
↓
MODEL ASSIGNMENT
↓
MODEL REGISTRY
↓
PROVIDER
↓
SELECTED MODEL
```

При этом:

```text
MODEL ≠ AGENT
```

Модель не является владельцем:

```text
Workspace
Chat
Context
Tools
Permissions
Backup
Verification
Trace
State
Lifecycle
```

Эти сущности принадлежат runtime.

---

# 2. Основные компоненты

Текущий runtime состоит из нескольких основных модулей.

## server.py

Backend Agent Runtime.

Отвечает за:

```text
GigaChat API
MAIN CHAT RUN
file-agent tools
permissions
backup
verification
trace
Workspace interaction
Chat context loading
selected model execution
```

Для MAIN CHAT runtime выбирает модель через MODEL REGISTRY и передаёт фактический `provider_model_id` в API.

---

## ultra_ui.py

Основной пользовательский интерфейс.

Текущий UI реализован на:

```text
Tkinter
```

UI включает:

```text
trace / log
CHAT
message input
Workspace sidebar
Chat sidebar
MAIN CHAT model selector
Compressor panel
Project Context editor
Role Context editors
message context actions
Compression Proposal UI
Original Viewer
```

---

## context_storage.py

Центральный storage API для Workspace и Chat.

Отвечает за:

```text
workspace identity
chat identity
message identity
RAW HISTORY
Project Context
Project Context revisions
MESSAGE CONTEXT STATE
Context Variants
active Working Representation
atomic storage operations
```

Обычные file-agent tools не должны напрямую изменять внутреннее `.ultra` storage.

---

## model_registry.py

Единый MODEL REGISTRY.

Он хранит описание доступных моделей независимо от конкретной роли.

Текущий ModelSpec включает:

```text
model_id
display_name
provider
provider_model_id
enabled
is_local
```

Текущий GigaChat registry содержит несколько моделей:

```text
GigaChat 2
GigaChat 2 Max
GigaChat 2 Pro
GigaChat 3 Lightning
GigaChat 3 Pro
GigaChat 3 Ultra
```

---

## compressor_runtime.py

Отдельный runtime Context Compressor.

Он не является частью обычного MAIN CHAT RUN.

Compressor имеет собственную:

```text
роль
модель
контекст роли
prompt configuration
runtime target
soft guard
```

Compressor не получает file-agent tools.

---

## compressor_settings.py

Persistent настройки prompt-слоя Compressor.

Используются:

```text
Message Compression Template
Final Check Template
```

Поддерживаются placeholders:

```text
{{REDUCTION_PERCENT}}
{{REMAINING_PERCENT}}
```

---

## agent_global_context.py

Хранилище локального app-level Role Context.

Поддерживает отдельные agent/role IDs.

Например:

```text
ultra
compressor
```

Role Context хранится вне Workspace.

---

## workspace_runtime_settings.py

Хранит machine-local runtime-настройки Workspace.

Например:

```text
backup directory
run log directory
```

Эти настройки не должны смешиваться с portable `.ultra` state.

---

## ui_state.py

Persistent UI state.

Хранит:

```text
geometry
layout
theme
colors
Workspace registry
selected MAIN CHAT model
другие локальные UI settings
```

---

## server_context_messages.py

Отдельная подсистема server/runtime context messages.

Она не является заменой:

```text
Project Context
Role Context
Chat history
MESSAGE CONTEXT
```

Это отдельный служебный механизм.

# 3. Workspace

Workspace является корнем конкретного проекта.

В Workspace хранится переносимое внутреннее состояние:

```text
.ultra/
```

Каждый Workspace имеет постоянный:

```text
workspace_id
```

Несколько Workspace могут быть зарегистрированы в UI.

Реализованы:

```text
создание Workspace
подключение существующего Workspace
переключение
переименование
удаление из UI registry
```

Удаление Workspace из UI registry не означает удаление самого проекта.

---

# 4. Portable и local state

Архитектурно разделяются:

```text
PORTABLE WORKSPACE STATE
```

и:

```text
LOCAL MACHINE STATE
```

Portable:

```text
.ultra/
```

Local:

```text
UI settings
backup paths
run log paths
Role Context
runtime configuration
```

Это позволяет переносить проект между компьютерами без смешивания machine-specific настроек.

---

# 5. Chat

Один Workspace может содержать несколько независимых Chat.

Каждый Chat имеет:

```text
chat_id
```

Реализованы:

```text
создание
переключение
переименование
persistent history
restart recovery
изоляция Chat history
```

Удаление Chat пока не является законченной production-функцией.

---

# 6. RAW HISTORY

Каждое сообщение Chat сохраняется как отдельный RAW MESSAGE.

Identity:

```text
workspace_id
chat_id
message_id
```

RAW MESSAGE содержит:

```text
original_text
```

RAW является immutable source of truth.

После создания RAW не должен изменяться из-за:

```text
compression
manual summary edit
restore
model replacement
UI rerender
```

---

# 7. Assistant provenance

Для assistant messages сохраняется producer metadata.

Например:

```text
kind
role_id
run_id
model_id
model_display_name
provider
provider_model_id
```

Это позволяет после restart понимать, какой именно моделью был создан конкретный ответ.

Старые сообщения без producer metadata остаются совместимыми.

---

# 8. Project Context

Каждый Workspace имеет общий:

```text
PROJECT CONTEXT
```

Он хранится в:

```text
.ultra/project_context.md
```

Project Context:

```text
общий для Chat одного Workspace
persistent
редактируется через UI
имеет историю ревизий
загружается runtime
```

Project Context не является Chat History.

---

# 9. Role Context

MAIN CHAT и COMPRESSOR имеют отдельные Role Context.

Пример:

```text
MAIN CHAT ROLE CONTEXT
COMPRESSOR ROLE CONTEXT
```

Role Context описывает роль.

Project Context описывает проект.

Chat Context описывает конкретный разговор.

Эти сущности не должны смешиваться.

---

# 10. MAIN CHAT MODEL ASSIGNMENT

MAIN CHAT больше не использует только одну жёстко заданную модель.

В UI реализован выбор модели MAIN CHAT.

Runtime получает:

```text
model_id
```

и разрешает его через:

```text
MODEL REGISTRY
```

в:

```text
provider
provider_model_id
```

Фактическая модель конкретного RUN фиксируется в trace.

---

# 11. GigaChat Multi-Model

Работа нескольких GigaChat-моделей через существующий backend подтверждена практически.

То есть этап:

```text
MODEL REGISTRY
+
GigaChat Multi-Model
+
MAIN CHAT Model Assignment
```

уже реализован.

Архитектура больше не зависит от одной `GigaChat-3-Ultra`.

---

# 12. Compressor Model Assignment

COMPRESSOR имеет отдельный выбор модели.

Например:

```text
MAIN CHAT
    GigaChat 3 Ultra

COMPRESSOR
    GigaChat 3 Pro
```

Модель Compressor выбирается независимо от MAIN CHAT.

Оба selector используют общий MODEL REGISTRY.

---

# 13. Изоляция ролей

MAIN CHAT и COMPRESSOR являются разными runtime roles.

Их вызовы не должны автоматически наследовать скрытую provider-side историю друг друга.

Каждый вызов получает явно собранный context.

Основной принцип:

```text
ROLE CONTEXT
+
ALLOWED SHARED CONTEXT
+
RUN CONTEXT
+
EXPLICIT TOOL SET
```

Полный универсальный CONTEXT POLICY framework пока не реализован, но этот принцип уже используется архитектурно.

---

# 14. Compressor Tools

Для Context Compressor действует:

```text
TOOLS = NONE
```

Compressor не должен:

```text
читать файлы через agent tools
изменять Workspace
запускать команды
управлять Git
менять Context Storage напрямую
```

Его задача:

```text
TEXT → COMPRESSED TEXT
```

---

# 15. Compressor Context

Текущий Compressor runtime может собирать:

```text
ROLE CONTEXT
PROJECT CONTEXT
MESSAGE COMPRESSION TEMPLATE
RUNTIME TARGET
SOURCE TEXT
optional FINAL CHECK
```

При этом действует фундаментальное правило:

```text
RAW SOURCE = SOURCE OF TRUTH
PROJECT CONTEXT = REFERENCE ONLY
```

Compressor не должен переносить в summary сведения, существующие только в Project Context.

---

# 16. Reduction Target

Compressor поддерживает пользовательский процент сокращения.

Например:

```text
50%
```

Поддерживаются placeholders:

```text
{{REDUCTION_PERCENT}}
{{REMAINING_PERCENT}}
```

Target является ориентиром.

Сохранение смысла, ограничений, чисел, имён и причинно-следственных связей важнее точного попадания в процент.

---

# 17. Final Check

В Compressor UI существует optional:

```text
Дополнительная проверка
```

Она подключает отдельный Final Check prompt block.

Это пока НЕ является независимым Verifier Agent.

Текущий Final Check:

```text
часть одного Compressor request
```

Будущий Verifier:

```text
отдельная роль
отдельный clean call
```

---

# 18. Compressor Soft Guard

После получения результата runtime измеряет фактическое сокращение.

Soft Guard отклоняет:

```text
empty result
unchanged result
result >= RAW length
слишком слабое сокращение
```

При неудаче возможен один corrective retry.

Guard проверяет форму результата, но не является полноценной semantic verification model.

---

# 19. Per-message Working Representation

Для user/assistant messages реализована отдельная рабочая representation.

Каждое сообщение может использовать:

```text
RAW
```

или:

```text
SUMMARY
```

Storage state:

```text
active_representation = raw
```

или:

```text
active_representation = summary
```

---

# 20. MESSAGE CONTEXT STATE

Per-message state хранится отдельно от RAW MESSAGE.

Пример структуры:

```text
.ultra/
└── chats/
    └── <chat_id>/
        ├── messages/
        │   └── <message_id>.json
        │
        └── message_context/
            └── <message_id>/
                ├── state.json
                └── variants/
                    └── ctxv_<uuid>.json
```

`state.json` определяет active working representation.

---

# 21. Context Variant

Context Variant является отдельной версией рабочего текста сообщения.

Variant содержит:

```text
context_variant_id
text
source
parent_variant_id
manually_edited
compression metadata
```

Источники:

```text
llm_compression
manual_edit
```

Создание нового Variant не уничтожает предыдущие.

---

# 22. FULL state

Если:

```text
active_representation = raw
```

то:

```text
CHAT показывает RAW
MAIN CHAT получает RAW
```

Статус UI:

```text
FULL
```

---

# 23. COMPRESSED state

Если:

```text
active_representation = summary
```

то:

```text
CHAT показывает active Context Variant
MAIN CHAT получает active Context Variant
```

Статус UI:

```text
COMPRESSED
```

с возможным отображением:

```text
model
actual reduction
```

---

# 24. Compression Proposal

При нажатии:

```text
Сжать
```

Compressor получает RAW MESSAGE по `message_id`.

Результат сначала является:

```text
COMPRESSION PROPOSAL
```

Proposal не активируется автоматически.

Пользователь может:

```text
Принять
изменить перед принятием
Отклонить
```

---

# 25. Accept

После:

```text
Принять
```

создаётся новый Context Variant.

State переключается:

```text
raw
→
summary
```

После UI rerender основное тело сообщения показывает уже активную summary.

---

# 26. Reject

При:

```text
Отклонить
```

proposal не становится persistent active representation.

Сообщение остаётся в прежнем состоянии.

---

# 27. Manual Edit

Пользователь может вручную редактировать Working Representation.

Если сообщение FULL:

```text
можно создать manual working variant на основе RAW
```

Если сообщение COMPRESSED:

```text
редактируется текущая active working version
```

RAW MESSAGE при этом не изменяется.

---

# 28. Original Viewer

Кнопка:

```text
Оригинал
```

открывает immutable RAW MESSAGE.

Если active representation = summary, UI явно сообщает:

```text
Сейчас в контексте используется сжатая версия.
```

Просмотр оригинала сам по себе ничего не меняет.

---

# 29. Restore RAW

Пользователь может выполнить:

```text
Восстановить в контекст
```

После этого:

```text
active_representation = raw
active_variant_id = None
```

CHAT снова отображает RAW.

MAIN CHAT снова получает RAW.

Старые variants сохраняются.

---

# 30. Recompression

После Restore можно снова выполнить Compression.

Новый LLM Compressor RUN всегда должен брать:

```text
immutable RAW original_text
```

а не предыдущую summary.

Это защищает систему от degradation chain:

```text
SUMMARY
↓
SUMMARY
↓
SUMMARY
```

Канонический источник повторного сжатия:

```text
RAW
```

---

# 31. Active Chat Context

MAIN CHAT собирает history через Working Representation.

Runtime использует:

```text
load_chat_working_messages()
```

Для каждого сообщения:

```text
FULL
→ RAW

COMPRESSED
→ SUMMARY
```

Роли и порядок сообщений сохраняются.

---

# 32. UI history и Active Context

В текущей архитектуре видимое тело Chat соответствует active working representation.

То есть пользователь непосредственно видит то представление сообщения, которое используется MAIN CHAT.

Для просмотра immutable исходника существует отдельный:

```text
Original Viewer
```

---

# 33. Trace Active Context

При RUN runtime фиксирует:

```text
messages
raw_messages
compressed_messages
chars
```

Это позволяет видеть фактический состав Working Chat Context.

# 34. Persistent restart behavior

MESSAGE CONTEXT STATE и Context Variants хранятся на диске.

После restart:

```text
active summary остаётся active
```

и UI снова показывает её.

Restore также сохраняется persistent.

# 38. Compression Review / Discussion — следующий слой

Для COMPRESSION PROPOSAL запланирован message-scoped review mechanism.

Предварительная структура:

```text
RAW SOURCE
+
CURRENT PROPOSAL
+
REVIEW CHAT
```

При открытии Review система должна уметь сравнить:

```text
что было
```

с:

```text
что получилось
```

и выявлять:

```text
потерянные факты
потерянные числа
потерянные условия
ослабленные запреты
изменение смысла
добавленные факты
неоднозначности
```

После этого пользователь сможет обсуждать proposal с Compressor.

---

# 39. Review Chat lifecycle

Review Chat должен быть временным и привязанным к:

```text
message_id
```

Обычное сообщение в Review Chat:

```text
не должно автоматически менять Proposal
```

Отдельное действие:

```text
Сформировать новую версию
```

должно создавать новый Proposal на основе:

```text
RAW
+
CURRENT PROPOSAL
+
REVIEW DIALOGUE
```

RAW остаётся source of truth.

---

# 40. Independent Verifier

После Review-механики может быть реализован настоящий независимый Verifier.

Его задача:

```text
RAW
+
CANDIDATE
↓
SEMANTIC CHECK
```

Verifier должен быть отдельной runtime role.

Он может использовать:

```text
ту же модель
или
другую модель
```

но всегда через отдельный explicit call.

---

# 41. Agent Profiles

Будущий Agent Profile должен объединять:

```text
role
model_assignment
role_context
context_policy
tool_set
permission_policy
state
execution_rules
```

MAIN CHAT и COMPRESSOR уже частично демонстрируют эту структуру, но универсальный Agent Profile runtime пока не реализован.

---

# 42. Provider architecture

Текущий production provider:

```text
GigaChat API
```

Полный универсальный Provider Adapter abstraction ещё не завершён.

Будущий runtime должен позволять:

```text
GigaChat
Local Provider
другой внешний API
```

при сохранении одного общего Agent Runtime.

---

# 43. Local Provider

Local Provider пока не является production-функцией.

В будущем возможно подключение:

```text
Ollama
другого local inference runtime
```

Локальная модель не должна становиться владельцем Context или State.

---

# 44. Per-Chat Model Assignment

Полноценная схема:

```text
Workspace default model
↓
optional Chat override
```

пока не реализована.

Текущий MAIN CHAT selector уже создаёт базу для дальнейшего развития этого направления.

---

# 45. Coordinator

Multi-Agent Coordinator пока не реализован.

Целевая логика:

```text
Agent A
↓
Runtime / Coordinator
↓
selected result
↓
Agent B
```

Передача контекста между Agent должна быть explicit.

---

# 46. Safety scopes

Runtime контролирует permission scopes.

Основные категории:

```text
READ
WRITE
DELETE
VERIFY
```

Модель не может сама расширять разрешённый scope.

---

# 47. Backup

Для изменяющих RUN используется backup.

Portable state:

```text
.ultra
```

и machine-local backup storage разделены.

Перед физической mutation обычного файла может выполняться lazy protected backup.

---

# 48. Verification Gate

После mutation runtime требует проверку результата.

В зависимости от задачи могут использоваться:

```text
git_diff
git_status
python_compile
ui_smoke_test
другие verification tools
```

SUCCESS не должен считаться подтверждённым только потому, что модель написала текстовый отчёт.

---

# 49. VERIFY

Verification tools могут включаться и выключаться через runtime policy.

При:

```text
VERIFY = OFF
```

проверочные tools не должны оставаться доступными.

При:

```text
VERIFY = ON
```

runtime может требовать соответствующие checks.

# 50. GUARD P1

GUARD P1 является отдельным server-side behavior layer.

Он может остановить подозрительное действие до физического tool execution.

GUARD не заменяет:

```text
Permissions
Backup
Verification
```

# 51. Известный execution gap

Сохраняется отдельный архитектурный риск:

```text
изменяющая TASK
↓
модель не вызывает tools
↓
stop
↓
пишет, что задача выполнена
```

Если mutation физически не произошла, Verification Gate не всегда способен определить, что задача не была выполнена.

Будущий возможный слой:

```text
TASK EXECUTION GATE
```

или:

```text
NO-TOOL STOP GUARD
```

Статус:

```text
НЕ РЕАЛИЗОВАНО
```

# 55. Главный архитектурный принцип

Система развивается не как набор отдельных чатов внутри конкретных LLM.

Источник состояния находится в runtime.

Канонически:

```text
MODEL
    = вычислительный ресурс

ROLE
    = назначение и правила

CONTEXT
    = явно собранные данные

TOOLS
    = явно разрешённый набор

STATE
    = persistent состояние runtime

PROVIDER SESSION
    ≠ источник истины
```

---

# 56. Канонические инварианты

1. RAW MESSAGE после создания не переписывается.

2. Compression не уничтожает RAW.

3. Context Variant хранится отдельно.

4. Proposal не активируется без решения пользователя.

5. Restore возвращает active representation к RAW.

6. Recompression выполняется от RAW.

7. Project Context не равен Chat History.

8. Role Context не равен Project Context.

9. MAIN CHAT и COMPRESSOR имеют независимые runtime calls.

10. Tools принадлежат роли/runtime, а не модели.

11. Model selection не должен менять safety policy.

12. Provider-side hidden history не является системой памяти проекта.

13. Workspace и Chat state должны переживать restart.

14. MAIN CHAT должен получать active Working Representation.

15. Original Viewer должен всегда позволять увидеть immutable RAW.
