Этот документ описывает **фактическое текущее состояние** проекта `ag_llm / GigaChat Ultra Local Agent`.

Он должен отражать то, что реально существует в коде и было подтверждено тестами или живым runtime.

# 1. Общая архитектура

Проект больше не является системой, жёстко привязанной к одной модели `GigaChat-3-Ultra`.

Текущая архитектура развивается как локальный Agent Runtime, в котором модель является заменяемым вычислительным компонентом.

Упрощённая схема:

```text
USER
↓
Ultra UI
↓
AGENT RUNTIME
↓
MODEL ASSIGNMENT
↓
MODEL REGISTRY
↓
PROVIDER
↓
SELECTED MODEL
```

При этом:

```text
MODEL ≠ AGENT
```

Модель не является владельцем:

```text
Workspace
Chat
Context
Tools
Permissions
Backup
Verification
Trace
State
Lifecycle
```

Эти сущности принадлежат runtime.

## verifier_runtime.py

Отдельная runtime role Independent Verifier.

Текущие свойства:

```text
one-shot clean call
separate Verifier Model Assignment
default = GigaChat 3 Pro (`gigachat_3_pro`)
model resolution через MODEL REGISTRY
TOOLS = NONE
persistent Verifier Chat = NONE
Workspace / Chat Storage самостоятельно не создаёт и не читает
Executor conversation/session state не наследует
```

Verifier получает только явно переданные RAW TASK и `verification_context`, возвращает typed `VerifierResult` и поддерживает semantic `PASS` / `FAIL` для `PREFLIGHT`, `MUTATION`, `FINAL`.

`VerifierRuntimeError` и `VerifierProtocolError` остаются отдельными от semantic FAIL. Malformed response не превращается в PASS.

# 17A. Independent Final Audit

Independent Final Audit встроен в `run_agent_task(...)` после deterministic Verification Gate и проверки Candidate Final Response, но до `run_finished SUCCESS` и `return content`.

Текущий lifecycle:

```text
Executor STOP / EOS
↓
Deterministic Verification Gate
↓
Candidate Final Response
↓
Server Final Audit Evidence
↓
Evidence Completeness Gate
↓
Independent Final Verifier
|
+-- VALID PASS → RUN SUCCESS
|
+-- FIRST VALID semantic FAIL
       ↓
    Server Final Verifier Feedback
       ↓
    same RUN / one correction cycle
       ↓
    Deterministic Verification Gate
       ↓
    new clean Final Audit
```

Final Audit выполняется перед каждым normal SUCCESS, включая no-tool и `write_revision = 0` сценарии.

RAW TASK текущего RUN является source of truth. Candidate Final Response является claim Executor, а не authoritative fact. `mutation_facts` описывают server-observed mutations текущего RUN. Fresh Git status / diff являются workspace-wide observations и могут включать pre-existing или external changes; без подтверждения `mutation_facts` их нельзя приписывать текущему RUN.

Server evidence также включает run / permission / deterministic facts, new-file content и completeness metadata. Это важно для обычных untracked-файлов, содержимое которых не показывает `git diff HEAD`.

Если evidence имеет `critical_for_success = true`, LLM Verifier не вызывается и SUCCESS блокируется. Критическими являются, в частности, truncated Candidate Final Response, неполный Git / new-file evidence mutating RUN и превышение hard context limit.

Исходы разделены:

```text
final_audit_passed = valid semantic PASS
final_audit_failed = valid semantic FAIL
final_audit_error = evidence / runtime / protocol problem
```

Только valid PASS разрешает SUCCESS. FAIL и ошибки работают fail-closed.

V.4 добавляет один разрешённый correction handoff. На первом valid semantic FAIL Server напрямую строит feedback из `VerifierResult`, добавляет rejected Candidate как внутреннее `assistant` message, затем `final_audit.feedback` как server-authored `user` message и продолжает тот же `run_agent_task(...)`.

Это continuation одного RUN: сохраняются `run_id`, исходный RAW TASK, локальный `messages`, предыдущая Executor conversation, API/tool counters и tool budget, `backup_session`, `verification_state`, workspace, Chat и model assignments.

`FINAL_AUDIT_CORRECTION_LIMIT = 1` и `final_audit_feedback_count` ограничивают именно число handoff `semantic FAIL → Executor`. Correction cycle может включать несколько API calls и tool executions; отдельный `tool_limit` продолжает действовать независимо. Любая новая mutation обновляет обычный `verification_state`, поэтому перед следующим Final Audit снова обязателен deterministic Verification Gate.

Human-readable feedback template редактируем, но Server отдельно добавляет authoritative facts: `event_id`, `message_kind`, `is_new_user_task = false`, `raw_task_authority = SOURCE_OF_TRUTH`, decision, run / verifier metadata, reason, violations, required action и correction counters.

Correction lifecycle виден в отдельных runtime events: `final_audit_feedback_created`, `final_audit_feedback_delivered`, `final_audit_correction_started`.

Rejected Candidate и feedback существуют только во внутреннем `messages`; UI сохраняет assistant Chat message только после успешного возврата `run_agent_task(...)`. Первый `final_audit_failed` поэтому не является terminal `run_failed`.

Если второй clean Final Audit снова возвращает semantic FAIL, новый handoff не создаётся: RUN завершается с `final_audit_correction_exhausted` и `FinalAuditSemanticError`. Runtime / protocol / critical evidence failures остаются немедленно terminal и не получают correction handoff.

# 18. Compressor Soft Guard

После получения результата runtime измеряет фактическое сокращение.

Soft Guard отклоняет:

```text
empty result
unchanged result
result >= RAW length
слишком слабое сокращение
```

При неудаче возможен один corrective retry.

Guard проверяет форму результата, но не является полноценной semantic verification model.

# 30. Recompression

После Restore можно снова выполнить Compression.

Новый LLM Compressor RUN всегда должен брать:

```text

```

а не предыдущую summary.

Это защищает систему от degradation chain:

```text
SUMMARY
↓
SUMMARY
↓
SUMMARY
```

Канонический источник повторного сжатия:

```text
RAW
```

# 40. Independent Verifier

Independent Execution Verifier уже реализован как отдельная runtime role и не зависит от будущего Compressor Review-механизма.

Его задача:

```text
RAW TASK
+
SERVER-PREPARED EVIDENCE
↓
SEMANTIC CHECK
```

Текущая модель назначается отдельно от MAIN CHAT и COMPRESSOR через общий Model Registry. Default — GigaChat 3 Pro.

Каждая проверка является отдельным one-shot clean call без file tools и persistent Chat.

Фактически реализованы:

```text
V.1 Verifier Model Assignment
V.2 One-shot Clean Verifier Runtime
V.3 Independent Final Audit before SUCCESS
V.4 One-shot Final Audit Correction Handoff
```

V.4 разрешает ровно один structured feedback handoff в тот же Executor RUN. Каждый audit остаётся отдельным clean one-shot Verifier call с исходной RAW TASK; Verifier history между вызовами не переносится.

Следующий этап V.5 — generalized bounded Final Audit retry engine: несколько correction attempts, `MAX_FINAL_AUDIT_RETRIES`, repeated-failure signatures, same-reason / ping-pong / loop detection, API-only loop protection и terminal retry policy.

# 48. Verification Gate


# 49. VERIFY

Verification tools могут включаться и выключаться через runtime policy.

При:


При:


# 51. No-tool completion и Final Audit

Базовый deterministic Verification Gate сам по себе не доказывает выполнение изменяющей TASK в сценарии:

```text
изменяющая TASK
↓
модель не вызывает tools
↓
stop
↓
пишет, что задача выполнена
```

Final Audit теперь выполняется и при `tool_call_count = 0` / `write_revision = 0`. Он может semantic FAIL заблокировать неподтверждённое заявление Executor о выполнении TASK.

При этом нулевое количество tools само по себе не является deterministic FAIL: read-only или explanatory TASK может завершиться корректно без mutations.

# 55. Главный архитектурный принцип

Система развивается не как набор отдельных чатов внутри конкретных LLM.

Источник состояния находится в runtime.

Канонически:

```text
MODEL
    = вычислительный ресурс

ROLE
    = назначение и правила

CONTEXT
    = явно собранные данные

TOOLS
    = явно разрешённый набор

STATE
    = persistent состояние runtime

PROVIDER SESSION
    ≠ источник истины
```

---

# 56. Канонические инварианты

1. RAW MESSAGE после создания не переписывается.

2. Compression не уничтожает RAW.

3. Context Variant хранится отдельно.

4. Proposal не активируется без решения пользователя.

5. Restore возвращает active representation к RAW.

6. Recompression выполняется от RAW.

7. Project Context не равен Chat History.

8. Role Context не равен Project Context.

9. MAIN CHAT, COMPRESSOR и VERIFIER имеют независимые runtime calls.

10. Tools принадлежат роли/runtime, а не модели.

11. Model selection не должен менять safety policy.

12. Provider-side hidden history не является системой памяти проекта.

13. Workspace и Chat state должны переживать restart.

14. MAIN CHAT должен получать active Working Representation.

15. Original Viewer должен всегда позволять увидеть immutable RAW.

16. Candidate Final Response не является authoritative fact до Final Verifier PASS.

17. Fresh Git state нельзя автоматически приписывать текущему RUN без подтверждения `mutation_facts`.

18. Только VALID FINAL VERIFIER PASS разрешает normal RUN SUCCESS.

19. Первый valid semantic Final Audit FAIL блокирует SUCCESS, но не завершает RUN: допускается ровно один same-RUN correction handoff.

20. Rejected Candidate и Server Final Verifier Feedback не становятся обычными persistent Chat messages.

21. Повторный semantic FAIL после использованного handoff означает `final_audit_correction_exhausted` и terminal RUN FAILED.
