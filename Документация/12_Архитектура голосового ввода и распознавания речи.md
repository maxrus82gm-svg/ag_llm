# Архитектура голосового ввода и распознавания речи

## Статус

**АРХИТЕКТУРНЫЙ КОНЦЕПТ / БУДУЩАЯ ВЕТКА РАЗРАБОТКИ**

Голосовой ввод в текущем runtime `ag_llm` пока не реализован.

Этот документ фиксирует саму идею, место голосовой подсистемы в общей архитектуре и требования, которые важно не потерять до начала реализации.

Точные зависимости, способ установки моделей, хранение весов, использование CPU/GPU, параметры inference и конкретный runtime пока не фиксируются. Это будет определено позже после практического исследования выбранных моделей.

---

# 1. Назначение

В `ag_llm` планируется добавить локальную подсистему распознавания речи.

Её основная задача:

```text
ГОЛОС ПОЛЬЗОВАТЕЛЯ
        ↓
МОДЕЛЬ РАСПОЗНАВАНИЯ РЕЧИ
        ↓
ТЕКСТ
        ↓
ПОЛЕ ВВОДА НУЖНОГО CHAT
        ↓
обычная работа существующей системы
```

То есть голосовая модель не является основным Chat Agent и не заменяет существующие LLM.

Она выполняет специализированную функцию:

```text
AUDIO → TEXT
```

После распознавания полученный текст должен использоваться системой так же, как если бы пользователь ввёл его с клавиатуры.

---

# 2. Место голосовой подсистемы

Голосовая подсистема располагается перед обычным Chat.

Предварительная логическая схема:

```text
ПОЛЬЗОВАТЕЛЬ
    ↓
VOICE INPUT
    ↓
ASR MODULE
    ↓
SELECTED ASR MODEL
    ↓
TEXT
    ↓
INPUT НУЖНОГО CHAT
    ↓
SEND
    ↓
RAW MESSAGE
    ↓
существующий Agent Runtime
```

Таким образом голосовой ввод не создаёт вторую параллельную систему Chat.

Он является ещё одним способом создать текст для уже существующего Chat.

---

# 3. Универсальный блок распознавания

Подсистема не должна быть жёстко построена вокруг одной конкретной нейронной сети.

Нужен универсальный программный блок, через который система сможет работать с разными моделями распознавания речи.

Пример:

```text
VOICE INPUT
        ↓
ASR MODEL ASSIGNMENT
        ↓
ASR ADAPTER / RUNTIME
        ↓
SELECTED ASR MODEL
```

Система должна разделять две вещи:

```text
ОПЕРАЦИЯ
speech_to_text
```

и:

```text
ИСПОЛНИТЕЛЬ
GigaAM v3
Whisper
другая будущая ASR-модель
```

Замена модели не должна требовать переделки Chat, Context Storage или основного Agent Runtime.

---

# 4. Первые кандидаты

Первой выбранной моделью для исследования является:

```text
GigaAM v3
```

Предполагается, что она будет работать локально.

Также рассматривается возможность в будущем подключить:

```text
Whisper
```

или другие модели распознавания речи.

На текущем этапе не утверждается, какая из моделей в итоге станет основной.

Сначала необходимо практически проверить их работу, требования и качество.

---

# 5. ASR MODEL ASSIGNMENT

Для голосовой подсистемы логично предусмотреть отдельное назначение модели:

```text
ASR MODEL
```

или эквивалентное внутреннее название:

```text
SPEECH-TO-TEXT MODEL
```

Пример будущей конфигурации:

```text
MAIN CHAT MODEL
    GigaChat 3 Ultra

COMPRESSION MODEL
    GigaChat 3 Pro

ASR MODEL
    GigaAM v3
```

Позже ASR MODEL может быть переключена, например:

```text
ASR MODEL
    Whisper
```

Таким образом выбор модели распознавания не зависит от выбора основной Chat-модели.

---

# 6. ASR Adapter / Runtime

Для подключения конкретных моделей понадобится программная «оснастка» между системой и моделью.

Её задача — предоставить системе единый интерфейс.

Условно:

```text
ag_llm
    ↓
ASR Adapter
    ↓
конкретный runtime модели
    ↓
GigaAM v3 / Whisper / другая модель
```

Основной системе не должно быть важно:

- как именно загружаются веса конкретной модели;
- какие библиотеки она использует;
- какой формат аудио ей требуется;
- работает она на CPU или GPU;
- какие внутренние параметры нужны для inference.

Для системы операция должна выглядеть примерно одинаково:

```text
transcribe(audio)
        ↓
text
```

Конкретная реализация Adapter будет определена после изучения выбранных моделей.

---

# 7. Связь с Model Registry

Текущий MODEL REGISTRY проекта в первую очередь развивается для LLM.

Не требуется прямо сейчас переделывать его ради ASR.

На первом этапе голосовая подсистема может иметь собственное небольшое описание доступных моделей.

В будущем общий Model Registry может быть расширен понятием типа модели или capability.

Например:

```text
MODEL
    id
    runtime/provider
    capabilities
```

Возможные capabilities:

```text
chat
compression
verification
speech_to_text
```

Тогда:

```text
GigaChat 3 Ultra
    capability: chat

GigaChat 3 Pro
    capability: compression

GigaAM v3
    capability: speech_to_text

Whisper
    capability: speech_to_text
```

Но это пока только направление дальнейшего обобщения архитектуры.

Первая реализация ASR не должна требовать большого рефакторинга существующей мультимодельной системы.

---

# 8. Контекст и Chat

Голосовая подсистема должна понимать, **куда именно отправляется распознанный текст**.

Она должна работать в рамках выбранного пользователем Chat.

Пример:

```text
WORKSPACE A
    ↓
CHAT 3 выбран пользователем
    ↓
пользователь включает голосовой ввод
    ↓
ASR получает речь
    ↓
получает текст
    ↓
текст появляется во вводе CHAT 3
```

ASR не получает автоматически полный контекст Chat только потому, что используется внутри этого Chat.

Её базовая задача остаётся простой:

```text
AUDIO → TEXT
```

Контекст Chat нужен системе прежде всего для определения места, куда попадёт результат.

Если позже какой-либо ASR или дополнительная модель потребует специальный текстовый контекст для повышения качества распознавания, это должно быть отдельным явно управляемым механизмом.

---

# 9. Текст после распознавания

Базовая схема должна быть максимально простой:

```text
пользователь говорит
↓
ASR распознаёт
↓
текст появляется в обычном поле ввода
↓
пользователь может его проверить или исправить
↓
пользователь нажимает SEND
↓
создаётся обычный RAW MESSAGE
```

До отправки распознанный текст является просто содержимым input-поля.

После SEND он становится обычным сообщением существующего Chat.

Дальше к нему применяются все уже существующие механизмы:

```text
RAW MESSAGE
WORKING REPRESENTATION
SUMMARY
Context Compression
MAIN CHAT MODEL
```

Для дальнейшей системы нет принципиальной разницы, был ли текст:

```text
напечатан клавиатурой
```

или:

```text
получен из голоса
```

# 10. Что ещё предстоит исследовать

Перед реализацией необходимо отдельно разобраться с GigaAM v3.

В частности:

```text
где и как распространяется модель;
какие веса нужны;
как они загружаются;
какие зависимости требуются;
какой Python/runtime используется;
работа на CPU;
работа на GPU;
требования RAM;
требования VRAM;
скорость загрузки;
скорость распознавания;
поддерживаемые форматы аудио;
качество русского языка;
возможность держать модель загруженной;
возможность выгружать модель из памяти.
```

После этого можно будет решить, как именно модель должна «жить» внутри системы.

Возможные варианты:

```text
модель загружается вместе с программой
```

или:

```text
модель загружается при первом голосовом запросе
```

или:

```text
работает отдельный локальный ASR runtime/service
```

Пока ни один вариант не закрепляется.

# 11. Отдельная документация конкретных моделей

Архитектура голосового ввода должна оставаться общей.

Инструкции по конкретной модели лучше хранить отдельно.

Например:

```text
12_Архитектура голосового ввода и распознавания речи.md

13_GigaAM v3 - установка и настройка.md

14_Whisper - установка и настройка.md
```

Если Whisper в итоге не понадобится, отдельный документ для него создавать не требуется.

Так архитектурный документ не будет превращаться в инструкцию по установке одной конкретной нейронки.

# 12. Что пока НЕ фиксируется

На текущем этапе намеренно не закрепляются:

```text
конкретная библиотека записи с микрофона;
формат временных аудиофайлов;
точная структура UI;
точные кнопки;
точный механизм загрузки модели;
точные пути хранения весов;
CPU/GPU configuration;
keep-alive модели;
streaming transcription;
автоматическая отправка текста;
Voice Activity Detection;
Text-to-Speech;
wake word;
постобработка текста отдельной LLM.
```

Эти решения будут приниматься постепенно после реальных тестов.

---

# 13. Главный архитектурный принцип

Голосовая подсистема является самостоятельным специализированным блоком:

```text
VOICE / AUDIO
        ↓
ASR MODEL
        ↓
TEXT
```

После получения текста управление возвращается обычной системе `ag_llm`.

ASR не должна:

```text
становиться владельцем Chat;
заменять MAIN CHAT MODEL;
управлять Workspace;
самостоятельно менять Context Storage;
самостоятельно выполнять задачи основного Agent;
быть жёстко привязанной только к одной модели.
```


# Итог

В `ag_llm` планируется отдельный универсальный блок голосового ввода.

Его задача:

```text
ГОЛОС
↓
ВЫБРАННАЯ ASR-МОДЕЛЬ
↓
ТЕКСТ
↓
ВЫБРАННЫЙ CHAT
```

Первой моделью для практического исследования выбрана:

```text
GigaAM v3
```

В будущем должна существовать возможность подключения других моделей, например Whisper.

Конкретную техническую реализацию пока не фиксируем.

Следующий реальный шаг этой ветки — отдельно исследовать GigaAM v3, понять способ её установки и запуска, проверить локальное распознавание и только после этого проектировать production-интеграцию.
