# 🔴 Итоговый круглый стол (33.3)

**Назначение:** универсальная постоянная оболочка для **одного итогового согласованного плана** после фактического участия хотя бы одного альтернативного планировщика или рецензента в 33.1/33.2. Не новая стадия вердикта и не разрешение выполнять код. **CURRENT: см. оперативный SLOT ниже.** Для RT-002 Codex 33.1 уже SUBMITTED/SEALED; пользователь выбрал вариант B как основу проекта B2 (ревизия уточняет обязательный release gate), USER PLAN APPROVAL пока PENDING.

**Навигация Obsidian:** [[33_Круглый стол - план исполнения|33 — исходный план]]. Правила, источники альтернатив 33.1/33.2 и архивные locators здесь указаны текстом (без дополнительных Graph-связей).

## Постоянная инструкция — выбрать один-единственный источник финального плана

1. **Нет фактического альтернативного участия.** Если обе оболочки 33.1 и 33.2 `NOT_REQUESTED` либо их назначения закончились `CANCELLED` без сданных результатов (при этом пользователь явно закрыл группу), **33 остаётся единственным итоговым планом**. 33.3 остаётся `NOT_REQUIRED / EMPTY`; не копировать сюда 33, не заполнять таблицы «для порядка» и не утверждать 33.3.
2. **Альтернатива назначена, ещё не сдана.** Пока хотя бы один включённый участник находится в `ASSIGNED`/`DRAFT`/`BLOCKED`, выбор итогового плана ожидает его `SUBMITTED` либо отдельного решения пользователя об отмене/изменении группы. 33.3 остаётся `WAITING_INPUT`, **без содержательного итогового плана**.
3. **Альтернативное участие подтверждено.** Как только хотя бы один назначенный вариант/REVIEW в 33.1 или 33.2 **сдан и запечатан** (`SUBMITTED`) и пользователь/координатор по установленным правилам разрешил раскрытие и сравнение, **итог оформляется исключительно в 33.3**, даже если альтернатива только одна, даже если её предложения все отклонены и итог совпал с базовым 33. В этом случае 33 **не** превращается в финальный и сохраняет первоначальную независимую редакцию.
4. Результат `COMPARED` и решение об учёте альтернатив не означают автоматического USER PLAN APPROVAL. При наличии альтернатив запрещено утверждать/передавать 33 как финальный вместо 33.3. Если gate отсутствует, файл не заполнять содержательной финальной редакцией: показать `BLOCKED` и точное условие возобновления.
5. **План только по отдельному поручению редактору итогового документа.** Наличие файла, альтернативы или submission само по себе не назначает редактора и не даёт ему write permissions. Координатор фиксирует состав источников и разрешённую стадию; редактор заполняет только оперативную часть ниже.
6. По `rule-ref:RT-FINAL-01@1` из 28 и `rule-ref:PLAN-RECONCILE-01@2`, `PLAN-APPROVAL-01@2` из 33 извлечь действующие нормативные определения с зависимостями; применить `DOC-GIT-01@1`, `DOC-VERSION-01@1`, `DOC-CHANGE-01@1` из 18. Точный `rule_set_ref` и допустимый доказательный input сохраняются в записи подготовки.
7. **Печать и внешние approvals:** до пользовательского PLAN APPROVAL сохранить точные bytes итогового 33.3, SHA-256 и immutable locator вне запечатанного текста (в оперативном реестре 28; затем locator в архиве 35). Любая новая редакция требует нового подтверждения. Только после личного PLAN APPROVAL и verified handoff в профильный план можно создавать отдельные implementation TASK. Архивирование и очистка только по `RT-CLEANUP-01@2` и отдельному разрешению пользователя.

- **RT / assignment:** RT-ID, назначенный составитель, решение о ветке (альтернативы включены), статус, scope и дата.
- **Frozen inputs:** approved Decision Record 32, SHA-256 синтеза 31, версия общего Planning Input Manifest 28, версия исходного 33 (с original seal), exact `SUBMITTED` refs альтернатив/REVIEW 33.1/33.2, known exposure и применимые версии правил.
- **Таблица сверки:** `source + exact revision → предложение/findings → принято/модифицировано/отклонено/отложено → evidence/rationale → пункт итогового плана`. Существенное отклонение имеет объяснение. Согласие моделей не подменяет проверку.
- **Один итоговый план:** TASK graph, verdict V→TASK, зависимости, boundaries, исполнители как предложения, scope и exclusions, offline/visual/user acceptance, порядок согласованного handoff. Все неразрешённые противоречия, изменившиеся предпосылки и риск неправильного утверждения отмечаются как BLOCKED/OPEN.
- **Gate:** завершённый reveal всей выбранной группы, архивируемые исходные редакции, consistency check с вердиктом, внешняя печать итогового файла, затем **отдельный USER PLAN APPROVAL конкретной версии**. Нельзя молча «улучшить» verdict.
- **Проверка перед очисткой:** 33/33.1/33.2/33.3, reasons, approvals, существенное raw evidence и архивные locators должны быть восстановимы до разрешённого сброса.

### 4. Safety budget: минимальный обязательный контракт ДО HTTP

**Всегда проверять final serialized request**, включая system/history/RAW TASK/tool schemas/output allowance и весь optional context, а не уже урезанный UI preview. S1 подтверждает физические LLM endpoints и mode-caller coverage (в Codex AST-инвентаризации их 7, OAuth не считать LLM bill). Если standalone Chat/Compressor не защищены общим ledger, назначить отдельную scoped защиту либо явный BLOCKED/coverage incomplete; нельзя выдать V-3 PASS с тихим дорогим обходом.

**Единицы:** hard serialized bytes, hard full-read bytes, physical attempt count, RUN/lineage cap в точно принятой единице, conservative model-specific estimate, output allowance, protected verification reserve, provider-known usage и UNKNOWN. Bytes/4 — только приближение, не token bound и не рублёвый ceiling. Provider-reported total, cached, processed estimate и денежная стоимость — разные поля; отсутствие cached не означает ноль. Без проверенного tokenizer/rate нельзя обещать точный денежный предел. UI значения editable с safety validation/defaults после offline calibration, а не хардкод без права пользователя их менять.

**Authoritative transitions:** PREPARED → RESERVED → SENT → KNOWN_TERMINAL либо SENT → UNKNOWN_TERMINAL → RECONCILED. Только доказанный NOT_SENT разрешает вернуть reserve. Reserve привязан к immutable RUN/lineage, physical attempt ID, logical call, role/mode, policy revision и body hash; после изменения body новая проверка. Known settled, active reservations, UNKNOWN liabilities и protected reserve считаются без двойного списания. Retries/replan/repair/diagnostics — новые physical attempts того же ledger; смена UI/profile/stage не создаёт бесплатного RUN. Timeout/cancel после потенциальной отправки = UNKNOWN, duplicate terminal идемпотентен, late known корректирует ту же attempt, conflicting usage = anomaly/BLOCKED. Usage валидируется (non-negative integer, bool/null/missing отдельно от настоящего нуля).

**Durability/concurrency/fail-closed:** один authoritative writer на budget, reserve-before-send; два конкурентных permits не могут использовать один остаток. Crash после reserve/send, restore, corrupt schema/state, second process/ownership ambiguity, disabled diagnostic observer проверяются offline. При невозможности восстановить liability ⇒ **0 новых physical sends / BLOCKED + понятный NEXT**. Observability callbacks/GUI не являются enforcement. Отдельно сохраняется обязательный полный raw evidence: потеря единственной копии запрещает eviction/source refs и дальнейшую критичную mutation. Перед mutation сохранять существующий mandatory tool reserve **и** bounded provider verification reserve; невыполнимый Audit не заменять SUCCESS.

**Rollback:** компилятор может откатиться только к старому builder **под тем же жёстким budget guard**; UI Reset не освобождает pending/unknown debt. Migration/rollback incompatible ledger — stop/reconcile, а не unlimited defaults. Global account-wide cap вне текущего guaranteed per-RUN scope, если не утверждён отдельной политикой.

### 5. Два ограничения READ/context и сохранение действительных доказательств

1. **Полный read_file cap отдельно от full request cap.** Большой full READ отклоняется объяснимо и без молчаливого partial. Range/find доступны лишь в физически поддерживаемых границах: текущий общий reader bound порядка 2 MiB может запрещать и range/find. Не обещать fallback для >physical bound; потоковый reader — отдельная утверждаемая будущая задача. Проверить cap±1, физический bound±1, long lines, UTF-8/UTF-16, truncation, rejected-read→VERIFY.
2. **Durable before compact:** сначала сохранить полные tool outputs и source IDs, только потом исключать повторную большую отправку из model body. Кеш по content hash не делает два разных targets/generations одним доказательством. Каждый observation имеет task/run/plan/stage/generation/target/args/source/status/negative/freshness.
3. **Context manifest реально отправленного запроса:** role/mode, policy revision, requirement IDs, included/excluded blocks, bytes, source refs, reason, truncation/staleness; различать sent, planned, blocked и UI preview. RAW TASK, обязательные constraints, negative/contradictory facts, unfinished obligations сохраняют authoritative presence.
4. **Permission-aware expansion:** reference/hash/summary не заменяет actual required READ. Разрешать чтение только доступных source/range в scope и current generation; чужая TASK/secret/stale/missing source ⇒ blocked, а не PASS. Provider function call/result grammar не нарушать (никаких orphan сообщений), исходный файл — недоверенный data, не instruction.
5. **DIRECT/repair/audit:** DIRECT получает bounded working set без искусственной stage, разрешённая dependent history не исчезает; repair и diagnostic обязаны проходить тот же budget/ACL/lineage; freshness recheck после packet collection и после Dredd до SUCCESS. Exact predicate contains/equals и source requirements не подменяются SHA другой операции.
6. **Критерий 151G:** repeated large reads внутри одной stage и DIRECT уменьшают фактически переданные bytes на recorded fixture, но required material остаётся доступен, negative evidence и correctness сохранены, положительные задачи завершаются. Блокировка всех сложных файлов не считается оптимизацией.
