# 37. Старт перехода к Web Alarm Ultra

**Статус:** `USER-DIRECTED START CONCEPT / INITIAL ROADMAP / IMPLEMENTATION NOT ASSIGNED`.
**Дата:** 2026-10-15. **Архитектурный класс:** Web Alarm Ultra / новый веб-контур чата и подключений моделей.
**Источник:** последовательное обсуждение пользователя о новой вкладке Ultra, GigaChat, Codex, workspace и Blueprint LLM. **Документ подготовлен ChatGPT как начальная рамка**, а не как утверждённая спецификация реализации.

> **Первый достижимый результат:** в существующем Web Alarm есть отдельная вкладка **Ultra**, в которой пользователь выбирает сохранённое подключение GigaChat и доступную модель, ведёт обычный диалог и получает реальный ответ через сервер. До реального сетевого прогона — офлайн-имитация. Это новая веб-функция, не миграция всего старого `server.py`.

## 1. Зафиксированное направление пользователя

1. Создать **отдельную вкладку Ultra со своим интерфейсом** внутри Web Alarm; прежняя Ultra/Tkinter остаётся нетронутой и используется как проверенный источник примеров и контрактов.
2. **Сначала способы подключения моделей**: сохранить отдельные профили провайдера/модели и их настройки; в чате и в LLM-блоке выбирать уже созданное подключение по ссылке, не дублировать API/auth в каждом блоке.
3. **Первый provider — GigaChat** с выбором поддерживаемых профилей (в исходном `model_registry.py` представлены GigaChat 2, 2 Max/Pro, 3 Lightning/Pro/Ultra). Показ в UI не доказывает доступность модели: обнаружение, тест и ошибки должны быть реальными.
4. **После рабочего GigaChat — Codex** как самостоятельный агент в отдельной сессии/рабочей среде; транспорт исследовать адресно: App Server / CLI / другие реально поддерживаемые варианты. MCP может давать инструменты, но не автоматически полноценное управление жизненным циклом Codex.
5. Далее расширять каталог подключений (например, локальные модели через Ollama и иные совместимые интерфейсы), позже Claude и варианты работы с ChatGPT; не обещать единый протокол там, где агентский lifecycle принципиально отличается от обычного LLM API.
6. **Blueprint LLM учитывать с первого этапа проектирования**: профили отдельно, переиспользуемый блок запроса к LLM, типизированные входы/выходы и ссылки на контексты. Полный визуальный редактор, оркестрация сложных графов, Dredd и «Круглый стол» не являются условием самого первого ответа GigaChat.
7. Claude и Codex — **самостоятельные инженеры**. Разрешены самостоятельное исследование, альтернативы, критика и выбор технологии; ограничения касаются физического write-scope, безопасности, user gates и параллельных ресурсов, а не свободы мышления.

## 2. Не путать три уровня

| Уровень | Назначение | Что не смешивать |
| --- | --- | --- |
| **Подключения / Connection Registry** | Сохраняет `connection_id`, тип адаптера, модель/способ её выбора, capabilities, статус проверки, ссылку на защищённый credential; пользователь выбирает один готовый профиль | Не хранить секреты в узле, в документации и в git; наличие профиля не означает успешной авторизации |
| **Чат / Chat Runtime** | Workspace/chat/turn, история, формирование запроса, отправка через адаптер, ответ, ошибки, отмена и метрики | Не использовать свой Chat ID как Web Alarm TASK ID; не создавать второго независимого владельца workflow/mutation state |
| **Blueprint / LLM Node** | Ссылается на connection profile; получает Role, Input и 0..N разрешённых Context, выдаёт Response, status/metadata | Не дублировать провайдерную авторизацию; не обходить разрешения, обязательную проверку или budget guard |

**Разные подключения:** обычная модель с типовым chat-completions API может использовать общий adapter; нетиповой локальный агент с длительными сессиями, tools/approval/cancel/recovery требует отдельного agent adapter. Единый registry/capability contract не означает одинаковую реализацию всех провайдеров.

## 3. Минимальная схема первой функции

```text
Пользователь / Ultra Tab
       ↓
Workspace → Chat → Turn / Input
       ↓
LLM Node: provider_connection_ref → GigaChat model
       ↑            ↑
Role preset       Context refs (global / workspace / chat / task)
       ↓
Provider Adapter → GigaChat API → Response + status/usage
       ↓
История Ultra Chat → ответ в Ultra Tab
```

**Role** определяет поведение исполнителя; **Input** — конкретный запрос/сообщение; **Context** — разрешённые источники знаний. «Глобальный» — именованный источник с отдельной областью и правами, а не автоматическое право прочитать всё. Контекстов может быть несколько; объединение/порядок, дедупликация, источник и версия должны быть наблюдаемыми.

**Первый контракт узла (предложение, не окончательная схема):** `node_id`, `kind=llm_request`, `connection_ref`, `model_ref` (если профиль поддерживает выбор), `role_ref`, список `context_refs`, вход `input`, выходы `response`, `status/error`, `metadata/usage`. UI-настройка и сохранение графа не должны сами выдавать разрешения или запускать LLM.

## 4. Короткая последовательность работ (кандидаты будущих TASK)

| Этап | Минимальная сдача | Приёмочное доказательство |
| --- | --- | --- |
| **WUA-0 — Feasibility / границы** | Исследовать действующий Web Alarm HTTP/UI, GigaChat registry/transport, storage, контракты permissions, границу TASK authority и варианты modular service vs отдельный процесс. Определить самый маленький безопасный путь. | Карта компонентов и владельцев, 2–3 варианта с trade-offs, exact read/write scope, независимый source review. **Никаких runtime изменений.** |
| **WUA-1 — Connections** | Реестр сохранённых подключений и модельных профилей с безопасным тестом доступности, статусами configured/authenticated/ready/error и UI настроек. Первый адаптер — GigaChat, сначала fake provider. | Offline adapter/secret/error/timeout tests; ключи не уходят в UI responses, логи, Git или граф. Реальный доступ отдельно разрешается. |
| **WUA-2 — Ultra Tab / Chat** | Отдельная вкладка, чат с простым composer, выбором готового GigaChat-профиля/модели, ответом, ошибками и сохранением переписки; начальный Workspace может переиспользовать существующий Registry через контракт. | UI smoke + HTTP tests; два чата не смешивают историю; перезапуск сохраняет данные; отмена/сбой показываются честно; Web Alarm regression без деградации. |
| **WUA-3 — First Blueprint Node** | Минимальная сериализуемая схема `Chat Input → LLM Node → Chat Output`; готовый профиль LLM, роль, несколько context refs и реальные вход/выход. Возможность двигать и соединять блоки — отдельный узкий UI-итератор после подтверждения базового выполнения. | Исполнение той же схемы без браузера; versioned schema, типы портов, отклонение неправильного соединения; нет скрытого обхода server-owned gates. |
| **WUA-4 — Codex Adapter** | Отдельная сессия Codex с bounded input/result, events, cancel/timeout, approvals, provenance; исследовать App Server/CLI на установленной версии до выбора конкретного транспорта. | Offline mock lifecycle + ограниченный local smoke после USER GO; независимость чатов/рабочих областей; никаких неразрешённых Git операций. |
| **Позже** | Подключение других LLM/локальных моделей, два независимых агента, «Круглый стол», Dredd/Planner, Inspector, перенос пригодных сервисов Ultra. | Отдельные TASK/решения. Не выдавать будущие возможности за уже реализованные. |

**Точный первый инженерный handoff — WUA-0 (исследование/варианты), не WUA-1..WUA-4 сразу.** После анализа пользователь выбирает порядок и даёт отдельный GO. Пользователь сейчас **не назначал** Claude/Codex исполнительный БЛОК 1.

## 5. Архитектурные границы / что ещё не решено

- **Один процесс или sidecar?** Открыто. На старте не требовать отдельного сервера и не смешивать код в монолит. API-first модуль должен допускать будущий отдельный процесс, но окончательный выбор — после WUA-0.
- Web Alarm остаётся **authoritative control plane** для его TASK, жизненного цикла и управляемых файловых мутаций. У Ultra Chat может быть собственная Chat/Turn history, но нет второй конкурирующей mutation authority для тех же файлов.
- Для свободного обычного чата **не нужен Planner/Dredd на каждый текстовый ответ**. Но отсутствие агента-проверяющего не отменяет аутентификацию, ограничение размера запроса, сетевой timeout, cancellation, изоляцию Workspace/Chat, защиту секретов и explicit permission при будущих tool/write действиях.
- Код Tkinter/старого `server.py` не копировать автоматически в Web Alarm. Переносить только проверенные reusable компоненты или заново оформить короткие адаптеры; оригинальная Ultra остаётся доступным reference/fallback.
- **Параллельность:** существующий WEB_08 / WA4-R и его код, tests, CI, отчёты и тактический документ не являются write-scope этой концепции. Первые инженерные этапы нельзя выдавать как разрешённый concurrent edit тех же `web_alarm/server.py`, `web_alarm/ui.py` или shared settings без отдельного согласования.
- **Подключение Claude/Codex/GigaChat:** реальный транспорт, user auth, лимиты, стоимость и сетевой маршрут подтверждаются фактическим supported capability test. Браузерный доступ/подписка не равны автоматически разрешённому API; локальный CLI не наследует браузерный proxy.
- **Расширяемость Blueprint:** готовые connection profiles, context refs и typed ports пригодны для будущих nested graphs. Не делать сейчас общий оркестратор циклов/параллельных writes до state/permission design.

## 6. Минимальные UX-требования первой вкладки

**Навигация:** Web Alarm | Ultra; отдельный UI раздела Ultra. Рядом/в настройках Ultra — **Подключения**, модель, статус доступности и проверка подключения. Чат: выбор Workspace (если включён), список диалогов, выбор модели, история, поле отправки, состояния отправляется/ошибка/отменено и читаемый ответ. В первой версии можно ограничиться одним провайдером и одним активным запросом на чат; возможность расширения не требует запуска двух агентов прямо сейчас.

**Не выдавать тестовый результат за настоящий:** mocked adapter отмечается TEST; реально подтверждённый профиль — только после разрешённого сетевого health/smoke. Пустой UI без server round-trip не закрывает WUA-2.

## 7. Контракт приёмки и документации

- Каждая инженерная TASK: pinned source SHA, точный scope, unit/HTTP/UI tests, negative cases, mock-first, документированный guard от сетевых/платных/деструктивных операций, raw evidence, независимая проверка ChatGPT, решение пользователя.
- В UI и в описании считать `configured` / `reachable` / `authenticated` / `capability-confirmed` разными состояниями; не выдавать наличие записи за реальную доступность. У каждого провайдера свои ограничения.
- Данные Workspace/Chat и роли/контексты сохранять с explicit identity/revision и источником. Отсутствие контекста или ошибки провайдера не скрывать за успешным пустым ответом.
- Без отдельного разрешения: никаких live платных запусков, постоянных изменений системной сети/прокси, новых сторонних integrations, git операций локальных агентов, rollout режимов WA4-R, переписывания B2, удаления Tkinter.
- При документальном closeout: `23` владеет архитектурой Web Alarm, `24` — его текущим исполнением, `19` — внешними AI adapters, `11` — ролями/моделями, `Blueprint LLM.md` — авторской целью, `Blueprint LLM - тактический контекст.md` — журналом эволюции идей. **Этот документ 37 владеет только началом перехода/дорожной картой будущей Ultra Tab**, пока следующая программа не утверждена; исторические факты не переписывает.

## 8. Решения и открытые вопросы перед реализацией

**USER DIRECTION / CONFIRMED:** новая вкладка Ultra; сначала реальный простой чат GigaChat с выбором модели; независимые профили подключения и контексты; единый механизм ссылки на модель для блока; Blueprint-фундамент с самого начала; затем Codex; старая Ultra остаётся нетронутой; пока без круглого стола.

**НЕ ОДОБРЕНО АВТОМАТИЧЕСКИ:** конкретный стек UI/процессная топология, кодовое исполнение WUA-1+, точная структура storage/credential manager, реальные provider/API платежи, выполнение параллельных агентских TASK, полный визуальный редактор, изменение исходного утверждённого RT-002/B2 и текущего WA4-R rollout.

**Ближайшее управленческое действие:** согласовать исследовательскую TASK WUA-0 после разведения ресурсов с WEB_08; её инженер получает свободу предложить более простой или надёжный маршрут. Круглый стол — по желанию позже, сейчас не назначен.

## 9. ChatGPT Desktop ↔ Web Alarm Ultra: локальный MCP и вызов по событию (2026-10-16)

**Решение пользователя / приоритет исследования:** после завершения действующего WEB_08 по ранее утверждённым gates первым предметно разобрать, как подключить **обычный ChatGPT Desktop на Windows к локальному Web Alarm / будущей Web Alarm Ultra через свой ограниченный MCP-мост**, по аналогии с инструментальным доступом Desktop Commander. Это **архитектурное направление и feasibility-кандидат для WUA-0**, а не запуск реализации или переназначение активных задач. Старая Tkinter Ultra остаётся источником проверенных решений; целевой сервер — Web Alarm Ultra. Сохранить план будущей Ultra Tab и профилей GigaChat/Codex, уточнив последовательность исследований по отдельному GO.

**Два независимых механизма одного возможного контура:**

1. **Инструментальный доступ:** ChatGPT Desktop → разрешённый локальный MCP plugin/tool → узкий Web Alarm Ultra adapter → server-owned READ/STATUS/REPORT/context/evidence → ChatGPT. Первое испытание — read-only `ping` и чтение синтетического контекста из обычного Desktop Chat на компьютере пользователя. Никакой обязательной публикации исходников в GitHub и отдельного OpenAI model API для этого направления. Доступность в конкретной Windows/Plus-конфигурации, permissions, маршрут транспорта, продолжение после внешнего сообщения — **UNVERIFIED**. Не путать с отдельным направлением Ultra → GPT как вызываемый model provider (там иной контракт и обычно отдельный API).
2. **Инициирование обращения в чат:** эксперимент **AG LLM → Codex → существующий чат «Сервер WEB_08»** 2026-10-16 завершился **SUCCESS (BOUNDED)**: по поручению пользователя в чат действительно поступило сообщение агента, ChatGPT ответил; следующее сообщение инициировало адресное обновление `34_TACTICAL_CONTEXT.md` через подключённый GitHub (запись отражена в №34). Следовательно, уже продемонстрирована **возможность агента отправить сообщение в существующий чат и вызвать обработку поручения**, а не только пассивное хранение отчёта. Рассматривать Codex как **возможный канал доставки вызова Planner/Reviewer** после завершения задачи Web Alarm. Цель будущего сценария: Web Alarm хранит TASK/результат, Codex отправляет короткий `TASK ID + event`, ChatGPT при доступном MCP читает локальный контекст и возвращает решение; Web Alarm применяет его по своим gates. GitHub/общая папка/локальное хранилище могут служить транспортом данных, но не должны быть обязательны для самого сигнала.

**Границы подтверждения:** пока доказан **один ограниченный message/documentation smoke**, НЕ доказаны автоматический триггер именно из Web Alarm при task completion, точная оснастка/транспорт Codex, достоверная идентичность отправителя, получение Codex ответа, стабильный unattended двусторонний цикл, гарантированное «пробуждение» закрытого/спящего чата или доступность MCP после такого обращения. Нельзя приписывать OpenAI конкретное назначение интеграции или гарантировать сохранность этого механизма в будущих версиях. Канал Codex — **replaceable optional relay**, не единая точка отказа; при недоступности события сохраняются сервером до ручного или иного разрешённого возобновления.

**Будущий минимальный план проверки (не TASK / NO IMPLEMENTATION GO):** подтвердить создание/доступность локального MCP-плагина в обычном ChatGPT Desktop Chat; безопасно вызвать `ping` и `read_context` с проверкой источника; отдельно повторить доставку Codex-сообщения с `request_id/TASK ID`, затем проверить чтение локального статуса после обращения и независимый readback ответа. Предусмотреть проверку отправителя/полномочий, идемпотентность, ограниченные попытки/таймауты, аудит, ручные/автоматические gates и STOP. **Web Alarm остаётся единственным owner TASK, approvals и mutations**; само сообщение не разрешает write/execute/Git. Никаких изменений production, сети, тарифов или пользовательских прав без нового явного GO. Документ №34 содержит тактический статус и доказательства начального smoke.
