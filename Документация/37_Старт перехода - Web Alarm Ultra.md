## 2. Не путать три уровня

| Уровень | Назначение | Что не смешивать |
| --- | --- | --- |
| **Подключения / Connection Registry** | Сохраняет `connection_id`, тип адаптера, модель/способ её выбора, capabilities, статус проверки, ссылку на защищённый credential; пользователь выбирает один готовый профиль | Не хранить секреты в узле, в документации и в git; наличие профиля не означает успешной авторизации |
| **Чат / Chat Runtime** | Workspace/chat/turn, история, формирование запроса, отправка через адаптер, ответ, ошибки, отмена и метрики | Не использовать свой Chat ID как Web Alarm TASK ID; не создавать второго независимого владельца workflow/mutation state |
| **Blueprint / LLM Node** | Ссылается на connection profile; получает Role, Input и 0..N разрешённых Context, выдаёт Response, status/metadata | Не дублировать провайдерную авторизацию; не обходить разрешения, обязательную проверку или budget guard |

**Разные подключения:** обычная модель с типовым chat-completions API может использовать общий adapter; нетиповой локальный агент с длительными сессиями, tools/approval/cancel/recovery требует отдельного agent adapter. Единый registry/capability contract не означает одинаковую реализацию всех провайдеров.

## 3. Минимальная схема первой функции

```text
Пользователь / Ultra Tab
       ↓
Workspace → Chat → Turn / Input
       ↓
LLM Node: provider_connection_ref → GigaChat model
       ↑            ↑
Role preset       Context refs (global / workspace / chat / task)
       ↓
Provider Adapter → GigaChat API → Response + status/usage
       ↓
История Ultra Chat → ответ в Ultra Tab
```

**Role** определяет поведение исполнителя; **Input** — конкретный запрос/сообщение; **Context** — разрешённые источники знаний. «Глобальный» — именованный источник с отдельной областью и правами, а не автоматическое право прочитать всё. Контекстов может быть несколько; объединение/порядок, дедупликация, источник и версия должны быть наблюдаемыми.

**Первый контракт узла (предложение, не окончательная схема):** `node_id`, `kind=llm_request`, `connection_ref`, `model_ref` (если профиль поддерживает выбор), `role_ref`, список `context_refs`, вход `input`, выходы `response`, `status/error`, `metadata/usage`. UI-настройка и сохранение графа не должны сами выдавать разрешения или запускать LLM.

## 5. Архитектурные границы / что ещё не решено

- **Один процесс или sidecar?** Открыто. На старте не требовать отдельного сервера и не смешивать код в монолит. API-first модуль должен допускать будущий отдельный процесс, но окончательный выбор — после WUA-0.
- Web Alarm остаётся **authoritative control plane** для его TASK, жизненного цикла и управляемых файловых мутаций. У Ultra Chat может быть собственная Chat/Turn history, но нет второй конкурирующей mutation authority для тех же файлов.
- Для свободного обычного чата **не нужен Planner/Dredd на каждый текстовый ответ**. Но отсутствие агента-проверяющего не отменяет аутентификацию, ограничение размера запроса, сетевой timeout, cancellation, изоляцию Workspace/Chat, защиту секретов и explicit permission при будущих tool/write действиях.
- Код Tkinter/старого `server.py` не копировать автоматически в Web Alarm. Переносить только проверенные reusable компоненты или заново оформить короткие адаптеры; оригинальная Ultra остаётся доступным reference/fallback.
- **Параллельность:** существующий WEB_08 / WA4-R и его код, tests, CI, отчёты и тактический документ не являются write-scope этой концепции. Первые инженерные этапы нельзя выдавать как разрешённый concurrent edit тех же `web_alarm/server.py`, `web_alarm/ui.py` или shared settings без отдельного согласования.
- **Подключение Claude/Codex/GigaChat:** реальный транспорт, user auth, лимиты, стоимость и сетевой маршрут подтверждаются фактическим supported capability test. Браузерный доступ/подписка не равны автоматически разрешённому API; локальный CLI не наследует браузерный proxy.
- **Расширяемость Blueprint:** готовые connection profiles, context refs и typed ports пригодны для будущих nested graphs. Не делать сейчас общий оркестратор циклов/параллельных writes до state/permission design.

## 6. Минимальные UX-требования первой вкладки

## 9. ChatGPT Desktop ↔ Web Alarm Ultra: локальный MCP и вызов по событию (2026-10-16)

**Решение пользователя / приоритет исследования:** после завершения действующего WEB_08 по ранее утверждённым gates первым предметно разобрать, как подключить **обычный ChatGPT Desktop на Windows к локальному Web Alarm / будущей Web Alarm Ultra через свой ограниченный MCP-мост**, по аналогии с инструментальным доступом Desktop Commander. Это **архитектурное направление и feasibility-кандидат для WUA-0**, а не запуск реализации или переназначение активных задач. Старая Tkinter Ultra остаётся источником проверенных решений; целевой сервер — Web Alarm Ultra. Сохранить план будущей Ultra Tab и профилей GigaChat/Codex, уточнив последовательность исследований по отдельному GO.

**Два независимых механизма одного возможного контура:**

1. **Инструментальный доступ:** ChatGPT Desktop → разрешённый локальный MCP plugin/tool → узкий Web Alarm Ultra adapter → server-owned READ/STATUS/REPORT/context/evidence → ChatGPT. Первое испытание — read-only `ping` и чтение синтетического контекста из обычного Desktop Chat на компьютере пользователя. Никакой обязательной публикации исходников в GitHub и отдельного OpenAI model API для этого направления. Доступность в конкретной Windows/Plus-конфигурации, permissions, маршрут транспорта, продолжение после внешнего сообщения — **UNVERIFIED**. Не путать с отдельным направлением Ultra → GPT как вызываемый model provider (там иной контракт и обычно отдельный API).

## 10. Центр тестирования Web Alarm Ultra: ранняя концепция (2026-10-24)

**USER IDEA / PROPOSAL — NO IMPLEMENTATION GO.** Отдельная панель/блок «Тесты» по Workspace должна показывать, что реально происходит с проверками, без ожидания сообщений Claude/Codex и без ложного «задача завершена». Кандидат на раннюю оснастку Web Alarm Ultra, в том числе до полнофункционального чата и редактора Blueprint; очередность относительно GigaChat/WUA-0 решит пользователь.

**Интерфейс:** Workspace → TASK → TestPlan → TestRun; видимый индикатор `N/M` (только для достоверно измеренного прогресса), `QUEUED / RUNNING / PAUSED / PASS / FAIL / BLOCKED / CANCELLED / UNKNOWN`, название активной проверки, время последнего достоверного события, heartbeat/последний event, уровень связи агента, длительность, тестовые результаты (FAIL/ERROR/SKIP/изоляция), report/manifest/evidence/source SHA, кто и когда проверил. Незавершённые тесты выделять предупреждением `🔴 ТЕСТЫ НЕ ЗАВЕРШЕНЫ`. Пропажа связи = `STALE / UNKNOWN`, не автоматический PASS/FAIL.

**Действия по отдельным правам:** «Обновить состояние», «Запустить утверждённую проверку», «Отменить/остановить» при безопасном механизме, «Запросить независимую проверку». Разрешения `view/run/cancel/verify` различны; изменение производственного кода, Git-публикация, запуски сетевых/платных действий и окончательная приёмка — отдельные gates, не побочный эффект клика.

**Сущности не смешивать:** `AgentConnection` (действительно проверенная доступность MCP/Claude/Codex/ChatGPT), `TestPlan` (версионированный whitelist тестов и expected gates), `TestRun` (настоящий процесс/CI job, run_id, источник данных, revision, progress, exit code, artifact refs) и `Verification` (независимое `NOT VERIFIED / PASS / REVISE / BLOCKED`). Python может работать локально, когда чат агента уже завершён. Живой тест не означает, что LLM сейчас вычисляет, а online-плагин не доказывает способность автоматически пробудить чат.

**Server-owned execution:** Web Alarm сохраняет единственный authority по TASK, lock, scope, approvals и transitions. Status-сервис читает реальные события локального runner/OS/GitHub Actions через read-only adapter, с `event_seq`, heartbeat, persisted results и recovery/reconcile после перезапуска. Не разрешать произвольные команды shell из браузера; только предопределённые test recipes в disposable TEMP с workspace isolation, сроком исполнения, лимитами CPU/токенов, журналом действий и идемпотентностью повторных запусков. Смена owner или запись в живой storage без GO запрещена.

**Ранние этапы для обсуждения, не назначенные задачи:** `WUA-T0` — source/architecture review действующего test runner и согласование протокола статуса; `WUA-T1` — read-only мониторинг существующих локальных/CI тестов с минимальным интерфейсом; `WUA-T2` — контролируемый запуск allowlisted checks с остановкой/reconcile; `WUA-T3` — проверенные MCP/agent adapters, назначение Claude/Codex/ChatGPT и независимая проверка. Начинать с настоящего runner signal, не с имитации бегающего progress bar. MCP нужен для агентских инструментов, но не обязан быть условием read-only MVP; доступность вызовов и unattended lifecycle доказать E2E отдельно. Контракт `DOC-TEST-LIFECYCLE-01@1` остаётся текущим временным решением.
