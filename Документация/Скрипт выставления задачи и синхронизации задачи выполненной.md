# Скрипт выставления задачи и синхронизации задачи выполненной

Дата: 2026-11-04. Статус: предложение пользователя для будущей универсализации. Этот документ описывает проект, а не подтверждённую реализацию универсального инструмента и не новую TASK агенту.

Документ самостоятельный: не добавлять ссылки на него в карты проекта, карточки, реестры и другие документы без отдельного поручения пользователя.

## Назначение

Одно окно должно позволять пользователю назначать и сдавать задачи в разных проектах без постоянного открытия MD-карточек в Obsidian. Пользователь выбирает заранее подготовленный документ и профиль его структуры; инструмент показывает фактический статус, принимает Markdown новой задачи и выполняет безопасный перенос законченной задачи. Для каждого проекта меняются настройки, а не исходники программы.

## Что уже есть и что предлагается

Сейчас в ag_llm есть tools/task_slot_rotate.py и tools/task_slot_monitor.py: проверка карточки, назначение в ожидающий БЛОК 1, завершение через finish, окно статусов и локальная история. Они используют существующие фиксированные маркеры и правила карточек проекта. Папка итогового пакета задаётся по умолчанию как reports/<TASK-ID>, а для finish может быть указана отдельно. Это ещё не универсальный редактор произвольных Markdown-документов.

Предлагается добавить настройки профилей: явный выбор MD-карточки, схемы блоков и каталогов хранения. Существующие алгоритмы проверки, блокировки, атомарной записи и readback следует переиспользовать. Работающая конфигурация ag_llm должна стать одним из профилей без потери истории.

## Схема готового MD-документа

До подключения карточка уже должна содержать согласованный каркас. Программа проверяет его; не угадывает разделы по похожим словам и не вставляет маркеры молча.

| Область | Содержимое | Допустимое действие |
| --- | --- | --- |
| Правила и заголовки | Постоянный каркас карточки | Сохранять |
| Текущая задача | Точная строка ожидания или одна полная постановка с TASK ID | Назначать только в ожидание; освобождать при сдаче |
| Последняя сданная задача | Полная предыдущая постановка и служебные ссылки на её снимок | Менять только через проверенный процесс завершения |
| Остальная история и разделы | Архивные итоги, независимые проверки, другие блоки | Не изменять в ходе назначения и ротации |

Для каждой изменяемой области нужны однозначные начало и конец. В профиле указываются версия схемы, точная строка ожидания и способ распознавания TASK ID. Нулевое, повторное или противоречивое совпадение — отказ без записи. Неподдерживаемая версия — отказ, а не автоматическое преобразование.

## Настройки профиля

В окне «Настройки» пользователь должен видеть и выбирать:

| Настройка | Для чего нужна |
| --- | --- |
| Имя профиля и проекта | Понимать, с какой карточкой работает окно |
| Корень проекта | Разрешать относительные пути и переносить комплект на другой компьютер |
| Подготовленный MD-документ | Единственная карточка, в которую разрешена запись для этого профиля |
| Схема и её версия | Находить области документа и проверять готовность каркаса |
| Каталог постоянных пакетов задач | Хранить отчёты, evidence и manifest по TASK ID |
| Правило пути полного снимка задачи | Находить и сохранять исходную постановку, например `<TASK-ID>/handoff_task.md` |
| Исторический документ, если нужен | Только адресный и проверяемый источник по правилам схемы; без общего сканирования |
| Каталог локального состояния окна | Хранить настройки размера, диагностику, ограниченную историю запусков и черновики |
| Параметры отображения | Тёмная тема, размер шрифта, период обновления, автозакрытие, показ отладочного окна |
| Ограничения ввода и хранения | Минимальная длина постановки, максимальный размер, число записей локальной истории |

Относительные пути разрешаются от выбранного корня проекта; перед сохранением показываются фактические абсолютные пути. Нельзя незаметно подставлять каталоги другого профиля. Конфигурация должна быть версионируемой, понятной человеку и валидируемой до применения. Смена профиля не должна подменять открытый черновик или незавершённую операцию.

## Куда что сохраняется

Нужно явно разделить постоянную историю задач и состояние графического окна.

1. Новая задача записывается только в область текущей задачи выбранного MD-документа. Предыдущая сданная задача и остальные разделы не меняются.
2. Полная постановка и принятые отдельные поправки сохраняются в постоянный снимок внутри настроенного каталога задач. Перед вытеснением предыдущей постановки проверяется её точная сохранённая копия. Совпавшая копия переиспользуется, конфликт не перезаписывается.
3. Финальный report, evidence, manifest и протокол сдачи находятся в постоянном пакете конкретной задачи по правилам профиля. Это не TEMP-кэш окна.
4. Геометрия окна, последний выбранный профиль, краткая история операций и диагностические данные находятся в отдельном локальном каталоге состояния. Их можно ограничивать по объёму. Они не заменяют архив полных постановок.
5. Неотправленный текст не должен исчезать при ошибке или смене профиля. Для будущей версии нужно отдельно определить восстановление черновика и подтверждение его удаления; автосохранение черновика не означает назначения задачи.

Пользователь должен видеть путь сохранения и итог операции. Слово «синхронизация» здесь означает согласование карточки с её снимками и историей, а не автоматическую загрузку на GitHub или сетевую синхронизацию.

## Пользовательский процесс

Первый запуск: открыть настройки → выбрать корень проекта и подготовленную MD-карточку → выбрать схему → указать папки хранения → выполнить проверку без записи → сохранить профиль.

Назначение: выбрать профиль → увидеть «Ожидает новую задачу» → открыть «Новая задача» → вставить Markdown → проверить распознанный TASK ID и назначение → нажать «Отправить». Одна вставка не должна автоматически менять карточку. После записи окно перечитывает документ и показывает назначенную задачу. Запуск агента и отправка сообщения в его чат являются отдельными действиями.

Завершение: итоговый пакет готов → пользователь или уполномоченный исполнитель запускает единый процесс завершения → программа проверяет прежнюю историю и снимки, сохраняет постановку и поправки, переносит задачу в последний сданный слот и устанавливает ожидание → выполняет readback → сохраняет протокол и показывает результат. Ручное переписывание блоков моделью не требуется.

При изменении карточки другим процессом операция останавливается. Текст в форме сохраняется; пользователь обновляет проверку и видит фактическое состояние. Завершение исполнительского слота не означает независимой приёмки результата.

## Требования к окну

Кнопки действий и сообщения о результате имеют приоритет при уменьшении окна. Сначала сжимается поле текста или журнал, вплоть до одной строки с прокруткой. Нельзя прятать «Отправить» и «Закрыть» из-за большого запрошенного размера редактора. Минимальный размер окна учитывает фактический шрифт и масштаб Windows.

Видны выбранные профиль, карточка, текущая задача и состояние последней сданной. Окно можно двигать и менять его размер. Повторное открытие того же профиля восстанавливает существующее окно; другая карточка не получает его состояние по ошибке. Обновление перечитывает локальные файлы, но не запускает новую задачу и не повторяет последнюю запись автоматически.

## Проверки сохранности

- Писать только в выбранную карточку и разрешённые каталоги профиля. Не исполнять команды, ссылки или код из Markdown.
- Перед записью сверять версию/хеш показанной карточки и брать общую блокировку для назначения и завершения.
- Сохранять всё вне разрешённой области без изменений; после атомарной записи проверять содержимое повторно. При ошибке не выдавать успех.
- Не назначать задачу поверх занятого или повреждённого слота. Не переносить строку ожидания в историю.
- Не затирать отличающийся снимок, не терять отдельные поправки и не выдавать локальное сохранение за публикацию.
- Повторы завершения должны подтверждать уже сделанную работу без дублей. Повторная отправка назначения не должна перезаписывать текущую задачу.
- Не начинать Git/GitHub, сетевые операции, запуск агента или изменение других профилей по факту открытия окна.

## Будущая реализация и приёмка

До разработки согласовать минимальную версию схемы и формат настроек. Первый этап — профиль существующей карточки ag_llm и ещё одна синтетическая карточка с другими именами и путями. Затем проверить сохранение/переключение настроек, перенос комплекта в другую папку, совпадающие/разные TASK ID, конкурентные изменения, ошибку записи, восстановление черновика и повторный запуск.

Отдельно проверить настоящую геометрию окон при разных размерах и шрифтах: все кнопки остаются доступны, поле текста сжимается первым. CLI должен работать без GUI там, где есть разрешённый Python runtime; наличие доступа к файлам через веб-интерфейс само по себе не доказывает возможность исполнения.

Готовность универсального варианта подтверждается на двух независимых профилях без изменения исходников и без потери посторонних частей документов. До такой проверки этот документ остаётся проектным предложением. Само его создание не разрешает расширение текущей разработки, изменение чужих карточек или публикацию.
