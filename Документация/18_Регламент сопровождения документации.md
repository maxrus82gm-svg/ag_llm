### DOC-TEST-START-01@1 — обязательное чтение тестовой архитектуры при каждом новом входе (2026-10-13)

**Для нового обычного чата ChatGPT-координатора** сохраняется полный маршрут `08 → 000_Задачи для агента → 34 → 18 → 01/профиль → 36 → 36.1 → 36.2/36.3` по актуальному GitHub и проверенным ревизиям. **Для локального исполнителя Claude/Codex** маршрут задаётся персональной карточкой и адресной матрицей БЛОКА 1 по `DOC-TASK-READ-SCOPE-01@1`: обязательный контекст `08` (актуальные применимые разделы), `34` (текущий и профильный контекст), `01/профиль` и `36/36.1/36.2/36.3` (релевантные тестовые контракты) сохраняется; полный глобальный `000` и весь `18` механически не навязываются, если применимые нормативные правила уже точно переданы. Координатор обязан извлечь нужные определения и зависимости из `18`, а исполнитель — перечитать адресно указанные правила при пробеле, конфликте или специальном документном/Git scope. Ни одно сокращение чтения не меняет запреты, права, требования evidence, CI и независимой приёмки. Фиксировать, что реально прочитано, не выдавать память прежнего чата за проверенный источник. Для `INDEPENDENT_PLAN` действует прежний BLIND-START с разрешёнными выдержками; документационная TASK не требует бессмысленного CI.

После получения отчёта агента координатор **без повторного разрешения пользователя** начинает независимую проверку исходников, актуальности тестов, oracle, CI и evidence в уже разрешённом scope. При доступном GitHub может организовать отдельный диагностический CI без production/merge/rollout; обязан проверить source revision, exact collection, counts, isolation, первоначальные FAIL и NOT RUN. Дополнительные production-изменения, расширение полномочий, merge и rollout остаются под отдельным user GO. Этот процесс дополняет, а не заменяет TEST-* правила 36.1 и DOC-GIT-01@1.

При каждом новом входе проверить реальные tools/permissions, revision и CI triggers, а не выводить возможности из текста старого чата. Подробности — 36. ## DOC-TEST-LIFECYCLE-01 — Длительные тесты, видимый статус и финальная сдача

```rule-meta
contract: 1
status: ACTIVE
requires: [DOC-TASK-BLOCK1-01@1, DOC-LOCAL-REPORT-HANDOFF-01@1, DOC-AGENT-REPORT-TRIGGER-01@2]
```

**USER DIRECTION 2026-10-24.** Любой исполнитель (Claude 008, Codex 007, другие) обязан различать черновик, продолжающийся тест и конечный handoff. Созданный файл `report.md`, отправленный копируемый текст или кнопка «Копировать» в чате не доказывают завершения тестов. Нельзя объявлять `RESULT READY` или очищать БЛОК 1, пока не известны результаты всех обязательных проверок и не выполнена безопасная передача материалов. Не изменять замороженный БЛОК 1 ради этого правила; уточнения активной TASK идут через отдельный CHAT-ONLY AMENDMENT с TASK ID.

1. **Видимость незавершённости.** Когда агент возвращает управление пользователю, а обязательные тесты продолжаются либо их исход неизвестен, первым видимым заголовком сообщить: `# 🔴 ТЕСТЫ НЕ ЗАВЕРШЕНЫ — ЗАДАЧА В РАБОТЕ — ОТЧЁТ ПРЕДВАРИТЕЛЬНЫЙ`. Указать фактический `RUNNING / QUEUED / PAUSED / UNKNOWN / BLOCKED`, TASK ID, какой прогон завершён, какой ещё идёт, текущий проверенный run/process identifier (если доступен) и источник наблюдения. Не выдавать предполагаемый процент за измеренный и `UNKNOWN` за PASS.
2. **Возобновление.** Если инструмент поддерживает ожидание завершения тестового процесса в текущем цикле, можно дождаться его exit code и итогового файла, не расходуя контекст на постоянное чтение длинных логов. Если ответ заканчивается, пока процесс продолжает работать отдельно, прямо предупредить: **автоматическое возобновление чата не гарантировано**. Дать пользователю одну короткую точную инструкцию продолжения, например: «Продолжи TASK <ID>: проверь существующий тестовый процесс и доведи сдачу». Перед возобновлением проверить реальный процесс, файл результатов и exit code, не стартовать дублирующую регрессию по догадке. Не обещать собственное пробуждение без проверенного канала событий.
3. **Черновик и финал.** Черновой `report.md` может создаваться параллельно с тестами только с явным `DRAFT / TESTS RUNNING / NOT FINAL`, не должен выглядеть как финальная сдача. `RESULT READY / AWAITING INDEPENDENT VERIFICATION`, окончательный копируемый блок, manifest и ротация допускаются **после** подтверждённых results/counts, FAIL/ERROR/SKIP/NOT RUN, exit code, isolation, evidence и engineering review. При FAIL/ERROR сначала корректировать в утверждённом scope и повторять нужную проверку; если невозможно — честный `PARTIAL / BLOCKED / FAIL`, факты и NEXT, без фиктивного зелёного итога. БЛОК 1 не очищать до полной архивной ротации в соответствии с регламентом.
4. **Независимая приёмка.** Исполнитель отвечает за локальный тестовый цикл, но не ставит себе независимый PASS. ChatGPT проверяет опубликованный GitHub commit/source, report/manifest/evidence, исходные RED и независимый CI; наличие предварительного отчёта не является триггером успешной приёмки. Git-права локальных исполнителей, пользовательский push, branch boundary и запрет конфликтующих записей остаются прежними.
5. **Ultra-design bridge.** Будущий Workspace Test Control Center — только архитектурное предложение из документа 37, требующее отдельного USER GO. Статус тестового процесса, присутствие MCP/agent adapter и активность LLM — разные независимые состояния; доступный плагин не доказывает автоматического пробуждения агента.

Повтор того же TASK+revision/evidence без новой самостоятельной проверки — не новая итерация; более позднюю проверку явно помечать новой датой/верификатором. `34_TACTICAL_CONTEXT.md` — краткий current handoff, не замена 06.

**Совместимость:** не переписывать активный БЛОК 1, существующие БЛОКИ 2–3, task reports или исторические записи. Не менять Git/CI/production-права и правила BLIND-START для INDEPENDENT_PLAN. Если безопасно ротировать невозможно — оставить карточку нетронутой и сообщить о блокере.

## DOC-TASK-READ-SCOPE-01 — Адресная матрица чтения при передаче TASK исполнителю

```rule-meta
contract: 1
status: ACTIVE
requires: [DOC-READ-01@1, DOC-TASK-BLOCK1-01@1, DOC-GIT-01@1]
```

**Решение пользователя 2026-10-22.** Это правило для ChatGPT-координатора, который составляет БЛОК 1 любому локальному агенту (Claude, Codex и последующим). Координатор сам читает полный применимый маршрут проекта, сверяет реальные версии, личную карточку агента, существующие правила, активные TASK и `requires`. Исполнитель не должен повторно прочитывать весь общий маршрутизатор `000_Задачи для агента.md` или весь регламент `18` только потому, что их прочитал координатор: персональная карточка — его операционный вход. **Одинаковыми должны быть обязательные контракты, а не весь текст/история персональных и общего документов.**

**Каждая новая постановка содержит адресную «МАТРИЦУ ЧТЕНИЯ»:** `файл → точный устойчивый раздел/Rule-ID → зачем нужен → обязательно / при условии / полностью`. Давать не просто перечень названий. Для большой области выбрать нужный заголовок/Rule-ID и его вложенные подпункты; для действительно необходимого полного контекста прямо написать «прочитать полностью» и причину. Ссылки на нормативные правила не заменяют текст требования в TASK: ключевые запреты, write-scope, тесты, evidence и границы полномочий должны быть самодостаточны. Не копировать многократно одинаковые регламенты в каждую персональную карточку; исправить обнаруженное противоречие в единственном нормативном владельце и привести короткие персональные правила в соответствие.

**Маршрут локального исполнителя по умолчанию:** (1) собственная персональная карточка — **Правила**, активный **БЛОК 1**, а также **БЛОК 4** для понимания предыдущих замечаний, если относится к TASK (БЛОК 4 только читать); (2) `08_Старт.md` — актуальный стартовый раздел и указанные связанные правила, без обязательного чтения всех исторических датированных блоков; (3) `34_TACTICAL_CONTEXT.md` — свежий общий/current и соответствующий подсистеме тактический контекст, а при необходимости полный относящийся к задаче фрагмент; (4) архитектура `01` и профиль ветки — релевантные разделы; (5) `36`, `36.1` и проектный `36.2` (Web Alarm) / `36.3` (Ultra) — актуальные применимые контракты и профиль тестирования, при coding TASK всегда включая необходимый объём `TEST-COLLAB/ENG/AREA/COV/EXEC/QA/EVID/SCOPE`; (6) `18` — **точные определения `## DOC-...` с `rule-meta/requires`**, если они не покрыты карточкой/TASK, расходятся с ними или нужны по заданию. Для документной/Git/security TASK объём может быть шире и должен быть назван явно; локальному агенту не передаются Git-права простым упоминанием раздела.

Пользователь обычно выполняет commit/push; другой исполнитель может сделать это только в рамках отдельного явного user GO для той же TASK.
4. **ChatGPT и обратный маршрут.** Координатор при получении сообщения о результате **сначала проверяет актуальный GitHub**: точный commit/ветку, отчёт, код, проверки и доказательства. Не заявлять «GitHub не содержит отчёта» до адресной проверки и не считать слова агента самостоятельной верификацией. 5. **Нет постоянного доступа к ChatGPT.** Исторический успешный bounded smoke Codex → существующий чат ChatGPT и гипотеза Codex Relay **не означают**, что у Codex/Claude есть общий канал доставки, разрешение обращаться к ChatGPT или unattended review. Автоматические проверки без LLM предпочтительны, но **неподключённый валидатор не выдаётся за PASS**.

**Практическая памятка для исполнительной записи:**

| Событие | Действие и получатель |
| --- | --- |
| Новый анализ | Только в свой разрешённый DRAFT: факт/гипотеза/вывод, source + версия, границы, unresolved |
| Ошибка собственного незапечатанного DRAFT | Адресно исправить; при смысловом пересмотре кратко сохранить прежний вывод → новый → причину |
| Ошибка уже SUBMITTED | Сохранить точный исходник; новая correction с target revision, evidence и влиянием, не подмена старого |
| Замечание чужому плану | Только после разрешённого раскрытия; finding/comparison в собственном слоте, без чужой записи |
| Изменение общего CURRENT или Rule-ID | Только его назначенный редактор; остальные передают SHARED DOC DELTA с проверенными основаниями |
| Смена после PASS/approval | Новая revision и повторный нужный gate, старое решение не наследуется |
| Архив/новый RT | `RT-CLEANUP-01@2`, проверка восстановления, условного финала 33/33.3 и user authorization; исторический archive остаётся доступным |

**Кто меняет состояния и почему:** `NOT_REQUESTED → ASSIGNED` — координатор по поручению человека; `ASSIGNED → DRAFT` — участник при начале; `DRAFT → SUBMITTED` — вклад подан, координатор зафиксировал snapshot, hash, автора и входы, иначе `RESULT READY / AWAITING SEAL`; `SUBMITTED → COMPARED` — после раскрытия и регистрации сравнения; `BLOCKED` — указана причина и область остановки; `CANCELLED` — только решение пользователя; `ARCHIVED` и очистка — после retention, восстановления и отдельного разрешения человека. `USER APPROVAL / PLAN APPROVAL` даёт только пользователь. `DONE / VERIFIED` — только предусмотренная независимая проверка. `COMPARED` не означает «принято».

**Форма factual closeout в существующем слоте/отчёте:** `RT/TASK, assignment, mode, write-scope, record-kind (fact/hypothesis/proposal/correction/comparison), source revision/selector, содержание и границы, previous→new при пересмотре, checks performed/not performed, DOC IMPACT, result state, NEXT/receiver`. Новый файл на каждую опечатку не создавать. Отдельное поле `SHARED DOC DELTA` содержит точную дельту, а не фиктивное «обновлено».

## DOC-GITHUB-HANDOFF-01 — Обязательное заметное уведомление о принятии изменений

**Приоритет / 2026-10-24:** для новых публикаций ChatGPT в `GPT` действуют уточнения `DOC-GPT-BRANCH-01@1`: в финальном handoff просить пользовательский review/merge PR, не утверждать, что обновлён `main`.

## DOC-COMMIT-01 — Один нумерованный коммит на логическую задачу

**Уточнение пользователя 2026-10-13 — COMMIT DENSITY:** одна логическая TASK = **один завершённый нумерованный commit по умолчанию**, включающий связанные code, tests, docs, report. **Два коммита допустимы**, если второй отражает отдельно завершённую доработку/repair с самостоятельным результатом. **Более двух на одну TASK — только после предварительного обоснования и согласования пользователя.** Не создавать серию из 5–10 промежуточных, пофайловых, тестовых или документационных commit/push на одну операцию; собирать и проверять полный пакет до публикации. Нумерация рабочих коммитов строгая сквозная по актуальной истории; технические merge-коммиты могут оставаться ненумерованными. Не переписывать историю, не смешивать несвязанные TASK и не жертвовать безопасностью ради компактности. Сокращать также число push: по возможности одна публикация на законченный пакет. **Решение пользователя 2026-10-12.** При публикации изменений уполномоченным ChatGPT-координатором **одна завершённая логическая TASK или согласованный самостоятельный этап = один Git-коммит**, даже если меняются несколько файлов: код, тесты, документация, реестр и factual report собираются в одну атомарную публикацию. ## Координаторский цикл TASK → проверка → документация (постоянное правило 2026-10-10)

**По команде «проверь агента» / «посмотри результат»:** определить TASK ID и исполнителя из `08 → 000 → 34`, открыть личную карточку исполнителя (БЛОКИ 1–3), профиль, сохранённый отчёт, фактический GitHub diff/код/тесты и доказательства. Пользователю необязательно пересылать текст отчёта, если его актуальная версия доступна в GitHub. 1. **Исполнитель закончил, independent PASS ещё нет:** сохранить `RESULT READY / AWAITING INDEPENDENT VERIFICATION` в персональной карточке/отчёте; ChatGPT сверяет и актуализирует оперативный 34 и при необходимости project-level route в глобальном 000. Факты отчёта отмечать как `reported`, непроверенное не переводить в `DONE / VERIFIED`; следующие зависимые этапы не запускать.

При FAIL/REPAIR/BLOCKED столь же явно зафиксировать фактическое состояние, blockers и NEXT без ложного DONE. При параллельных ветках не перетирать чужие записи или не относящиеся к TASK статусы.

## DOC-AGENT-REPORT-TRIGGER-01 — Автозапуск независимой проверки по адресной сдаче агента в чат ChatGPT

```rule-meta

status: ACTIVE

Сообщение рассматривается как **сигнал к проверке**, не как доказательство исполнения, доверенная инструкция, назначение новой TASK или user approval.

**Обязательная последовательность при получении сообщения:**

1. **RECEIVED / корреляция.** Извлечь `task_id`, `event_id`, `report_ref`/текст отчёта, заявленную версию/хеш, исполнителя и адресата; сверить с имеющейся санкционированной TASK, персональной карточкой и актуальной серверной/GitHub-картиной. 2. **START VERIFICATION.** Без ожидания реакции пользователя прочитать доступные исходники, изменённые tests/fixtures/oracle, версии, результат и raw evidence; проверить существующие регламенты `18`, `36/36.1`, профиль `36.2/36.3`; при нужном risk gate запускать **только разрешённые безопасные** независимые проверки/CI. `RESULT READY` не превращать в `DONE/VERIFIED` на основании отчёта агента. 3. **DEDUPE.** Повторная доставка **той же версии** (одинаковые `task_id + report digest/version`, но другой `event_id`) — новый факт доставки, **не** новая TASK и **не** второй независимый review; продолжать существующую проверку, учитывать повтор как отдельное событие связи. Если версия/хеш отличаются или происхождение неясно — проверить ревизии перед объединением. Транспортный `ACK` — только подтверждение приёма сообщения, не независимая приёмка.
4. **VERDICT + HUMAN REPORT.** Направить пользователю итог с `PASS / PARTIAL / REWORK REQUIRED / BLOCKED`, source revision, фактически проверенными фактами, непроверенными claims, evidence и безопасным NEXT. При отсутствии исходников или raw evidence незамедлительно проверить доступные источники, выполнить возможную ограниченную проверку, перечислить точный недостающий набор и остановить неподтверждённую часть. **Отсутствие опубликованных локальных файлов не отменяет старт проверки, но исключает ложный независимый PASS.**
5. **RETURN TO EXECUTOR (по доступному разрешённому каналу).** Если нужен repair, ChatGPT готовит конкретный findings/AMENDMENT по действующему `DOC-TASK-BLOCK1-01@1` и `DOC-ENGINEERING-ROLES-01@2`. При реально доступном и отдельно подтверждённом инструменте адресной отправки Codex/Claude можно передать сообщение/отчёт с `TASK ID`, без повышения полномочий; если такого инструмента нет — **не утверждать, что агенту отправлено**, выдать пользователю готовый текст/ссылку для передачи. Уже активный/замороженный БЛОК 1 **не перезаписывать автоматически**; новую TASK/расширение scope назначает пользователь. После исправления — новая независимая проверка новой ревизии.
6. **DOCUMENTATION DELTA.** Фактический статус и вердикт, если обоснованы, централизованно разнести в `34` и профильные владельцы `000/05/06/19/23/24/25` по Documentation Closeout, не смешивая архитектурную идею с implemented runtime. **Сессионность и гарантии:** правило действует **при фактическом поступлении сообщения и доступном исполнении ChatGPT** — не обещает самостоятельного периодического опроса сервера, вечного активного контекста, гарантированного wake-up закрытого чата или delivery/readback внешнего `ACK`. ## Локальные исполнители Claude / Codex — без Remote-continuity overhead (решение пользователя 2026-10-08)

**Режим определяется способом исполнения, а не названием модели.** Claude Desktop/Code и Codex CLI, которые выполняют TASK локально с доступом к рабочей копии, используют штатный локальный контекст своего клиента и прямое чтение файлов без обращения к Git/GitHub по умолчанию (см. DOC-GIT-01). В отличие от удалённого ChatGPT через Desktop Commander Remote, они **не обязаны** вести аварийный per-action журнал и дублирующие восстановительные документы в `Alarm/ALARM_TASK_SESSION`.

Нельзя подменять Git-историей реальные резервные копии таких данных. Штатные snapshots, rollback и receipts самого Web Alarm runtime не относятся к этим лишним агентским логам — их гарантии сохраняются.
- Существующие task-session файлы и историю не удалять задним числом без отдельной авторизации и проверки потерь. Изолированный worktree — опциональная мера для задач, которым требуется чистый Git baseline, а не обязательное условие параллельной работы.

**Contract 1 / ACTIVE / решение пользователя 2026-10-10.** Для задач, которые ChatGPT готовит для локальных Claude/Codex или другого агента, используется **два копируемых сообщения**: (1) **полная утверждённая постановка** для персонального **БЛОКА 1**, (2) **короткая стартовая команда для чата исполнителя**, с TASK ID и ссылкой на БЛОК 1. Пользователь **лично вставляет/заменяет БЛОК 1, подтверждает назначение и запускает агента**. ChatGPT не пишет в персональный БЛОК 1, не заменяет полный task-текст и не начинает следующую задачу вместо пользователя без нового прямого поручения; может готовить содержимое в чате, читать карточку и обновлять **только общие** документы в пределах разрешённой работы.

**Freeze активной задачи:** как только пользователь поставил БЛОК 1 и запустил исполнителя, **большую исходную постановку не переписывать до фактической сдачи/иного прямого решения пользователя**. При небольшом дополнении, замеченном уже во время исполнения, координатор даёт **короткий адресный AMENDMENT в том же чате агента**, с TASK ID и точным смыслом изменений, не перегенерируя полную карточку. Исполнитель фиксирует такие уточнения в собственном factual report / amendment trace; они не отменяют исходный scope и не дают прав на посторонние файлы. Если дополнение меняет authority, запрещённые действия, существенный scope, безопасность или приоритет — **отдельное явное решение пользователя**; не маскировать новую задачу под мелкую правку и не переписывать историю.

**Write-scope для безопасной ротации (уточнение 2026-10-18):** при первичной выдаче TASK координатор обязан **явно включать персональную карточку назначенного исполнителя в адресный write_scope только для собственной ротации БЛОКОВ 1–3 и минимального собственного handoff**. После завершения разрешённого объёма работы, когда factual report, manifest и evidence уже сохранены (включая итог PARTIAL/BLOCKED с готовым отчётом), исполнитель самостоятельно сохраняет всю исходную постановку и принятые AMENDMENT в БЛОКЕ 2, factual result/блокировки — в БЛОКЕ 3, доказывает сохранность прежней истории и **только потом** очищает БЛОК 1 до `ОЖИДАНИЕ НОВОЙ ЗАДАЧИ`. Незавершённую, продолжающуюся или лишь временно приостановленную TASK **не ротировать**; внешний gate BLOCKED не превращается в VERIFIED. При конфликте scope, обнаруженном drift, сбое readback или отсутствии полноценного отчёта — `CARD ROTATION BLOCKED`, без слепой очистки; о причине сообщить пользователю. Право на ротацию не расширяет полномочий на другие документы/карточки/Git/сеть. Историческая TASK `CODEX-WUA-0-OFFLINE-VM-PREFLIGHT-001` независимо подтверждает пример успешной ротации без потери старых БЛОКОВ 2–3.

**После фактической сдачи:** исполнитель сохраняет полную постановку/AMENDMENT и factual result согласно актуальной личной карточке (Codex — append-only в 001 с точечным readback; Claude — действующий личный формат), затем ротирует собственные БЛОКИ 2–3 (Codex — последние пять кратких задач/итогов) и лишь после подтверждённого сохранения переводит свой БЛОК 1 в \`ОЖИДАНИЕ НОВОЙ ЗАДАЧИ\`. Это разрешённая safe rotation **исполнителя**, не право ChatGPT менять пользовательский активный слот. При сбое/неполном отчёте — не очищать БЛОК 1 вслепую, сначала reconciliation. Верификатор отмечает \`RESULT READY\` отдельно от собственного \`DONE / VERIFIED\`, обновляет общий 000/05/06/34 и профильные документы, но не вставляет следующую TASK в личную карточку.

**Назначение для Ultra:** позднее эту дисциплину можно автоматизировать в TASK-router/Coordinator: source task immutable, follow-up amendment append-only, отдельные авторизация/запуск/результат/verification. **CONCEPT ONLY / NOT IMPLEMENTED**; текущее правило организационное и не меняет runtime.

## Per-model task routing

Каждая внешняя/вспомогательная LLM получает задачу **в своём собственном task-контуре**. Нельзя считать запись только в общем `000_Задачи для агента.md` достаточной постановкой для конкретной модели.

Правило маршрутизации:
- общий `000_Задачи для агента.md` хранит канонический проектный NEXT, назначенного исполнителя и ссылку на его персональную карточку;
- конкретный исполнитель получает отдельную карточку в своём task-файле с собственным ID, scope, запретами, критериями приёмки, verification и форматом отчёта;
- отчёт/closeout модели ведётся в её собственном контуре; при устойчивой серии задач для модели допускается отдельная append-only история;
- Claude, GPT/ChatGPT, Codex и другие исполнители не наследуют молча карточки и отчёты друг друга;
- если исполнитель меняется, задача должна быть явно перемаршрутизирована: новый исполнитель получает свою карточку до начала работы, а общий `000` обновляет назначение;
- персональные файлы/истории не создавать заранее без реальной необходимости: сначала использовать существующий контур, а новый документ заводить только при устойчивой серии задач и регистрировать по обычным правилам документации.

Для Claude текущий персональный контур: `000_Задачи Claude.md` + `001_История выполненных задач Claude.md`. Его оперативный handoff использует три блока: БЛОК 1 — текущая утверждённая постановка, БЛОК 2 — полная копия последней фактически выполненной постановки, БЛОК 3 — краткий factual result. После фактического завершения исполнения Claude **сам** выполняет атомарную по смыслу ротацию: сначала копирует полную постановку из БЛОКА 1 в БЛОК 2, затем записывает factual closeout в БЛОК 3 со статусом `RESULT READY / AWAITING INDEPENDENT VERIFICATION`, и только после успешной записи обоих блоков очищает БЛОК 1 до короткого состояния `ОЖИДАНИЕ НОВОЙ ЗАДАЧИ`. Отдельная команда пользователя на очистку БЛОКА 1 не требуется. Если ротация оборвалась или сохранность БЛОКОВ 2–3 не доказана, БЛОК 1 не очищается вслепую: сначала reconciliation фактического файла. После PASS независимый verifier/ChatGPT синхронизирует `001`, `06`, профильный журнал/реестр и другие реально затронутые канонические документы и только тогда фиксирует `DONE / VERIFIED`.

Персональные карточки ChatGPT и Codex уже существуют как отдельные TASK-контуры (см. реестр `08`); для новых агентов отдельный контур и TASK ID заводятся только при реальной необходимости. Claude и Codex равноправны; роли назначаются для конкретной задачи, без постоянного старшинства.

## Самостоятельность сильного агента и adversarial review

Scope, запреты `НЕ ДЕЛАТЬ`, границы этапа и запрет перехода к следующей TASK ограничивают **самовольные изменения кода, архитектуры и project state**, но не глубину анализа. Для значимой технической TASK исполнитель обязан работать не только как механический исполнитель чек-листа, но и как самостоятельный инженерный агент.

Правило:
- перечисленные tests / acceptance cases — **обязательный минимум, а не потолок проверки**;
- до `RESULT READY` исполнитель делает отдельный adversarial pass: пытается опровергнуть собственное решение и ищет race, interruption/restart, stale/replay, persistence/reopen, ownership/authority, finalization-boundary, backward-compatibility и соседние-инварианты, если они релевантны TASK;
- безопасные isolated probes, дополнительные тесты, чтение соседнего кода и формирование гипотез разрешены, даже если конкретный сценарий не перечислен в TASK;
- если найденная проблема находится внутри утверждённого scope, исполнитель исправляет её и добавляет regression test без ожидания отдельной подсказки;
- если проблема реальна, но исправление требует выхода за scope, смены этапа, нового архитектурного решения или затрагивает отложенную подсистему, исполнитель **не расширяет mutation-scope самовольно**: фиксирует evidence, reproduction/root cause, влияние и конкретное предложение в отчёте как `FINDING / PROPOSAL / BLOCKER`, затем останавливается в рамках текущей TASK;
- предложения не считаются автоматически утверждённым NEXT и не дают authority менять план. Решение об их принятии остаётся за verifier/координатором/пользователем.

Короткий принцип: **широкая свобода анализа, ограниченная свобода изменений**. Цель исполнителя перед передачей результата — не только показать, что обязательные тесты зелёные, но и самостоятельно попытаться доказать, что его решение неверно.

## Cold start и профиль активной ветки

Маршрут: `08_Старт.md` → обязательный `000_Задачи для агента.md` → этот регламент → `01_Архитектура и текущее состояние.md` → профильный документ текущей архитектурной ветки. `08` всегда остаётся первой точкой входа нового Chat/Agent; уже внутри Start-маршрута `000` используется как оперативный handoff и показывает текущую задачу, последнюю завершённую точку и ближайший NEXT. Он не заменяет канонические реестры, историю или архитектурные документы. После чтения `000` определить и сверить конкретную TASK; не читать все профильные документы подряд. Технические CURRENT-факты при необходимости сверять с кодом, runtime, тестами, live evidence и Git.

Для TASK по конкретной архитектуре её профиль обязателен к чтению **в любом Chat**:

| Тема | Профильный владелец |
| --- | --- |
| Workspace / Chat / runtime Context | `03_Чаты, проекты и контекст.md` |
| Multi-model / роли | `11_Мультимодельная архитектура и назначение LLM.md` |
| External AI integration / Codex CLI / ChatGPT plugin-MCP | `19_Архитектура внешних AI-интеграций - Codex CLI и ChatGPT MCP.md` |
| Voice / ASR | `12_Архитектура голосового ввода и распознавания речи.md` |
| Verifier / Final Audit / Permissions | `13_Архитектура оперативной верификации и контроля выполнения задач.md` |
| Web Alarm Workspace / Remote continuity / snapshots / recovery | архитектура — `23_Архитектура Web Alarm Workspace.md`; план/статус реализации — `24_План реализации Web Alarm Workspace.md`; подтверждённая профильная история — `25_Журнал Web Alarm Workspace - выполненные задачи и аудит.md` |
| Compression | `Архитектурное решение - управляемое сжатие контекста.md` |

Предпочтительно удерживать один основной архитектурный профиль в Chat. Для задачи на пересечении веток указать `PRIMARY PROFILE` и при необходимости `SECONDARY PROFILE`; каждый дополнительный профиль читать только по реальной теме TASK. Выбор пересматривается для каждой новой TASK и не наследуется от предыдущей темы Chat.

## Context reading policy

Знать о существовании библиотеки подготовленных контекстов обязательно; читать её перед каждой TASK не нужно. `14_Контекст проекта.md`, `15_Глобальный контекст Ultra.md` и `16_Список_контекстов.md` читаются, когда TASK непосредственно работает с контекстом, проблема предположительно вызвана контекстом, меняется постоянное содержание Global / Project Context или архитектура контекстов / presets либо пользователь прямо просит проверку. При `CONTEXT LIBRARY IMPACT: YES` читать и синхронизировать после фактического результата только затронутые документы. Документальная библиотека не является автоматически подключаемым runtime context.

## Documentation Block и Impact Check

Для значимой технической TASK отдельный Documentation Block планируется одновременно с технической постановкой; исполняется после фактического результата. Documentation-only TASK не требует рекурсивного блока. Маршрут и единственный полный реестр ответственности Markdown-документов находятся в `08_Старт.md`.

После значимого изменения заполнить:

```text
DOC IMPACT: YES / NO
CURRENT STATE IMPACT: YES / NO
ARCHITECTURE IMPACT: YES / NO
CONTEXT LIBRARY IMPACT: YES / NO
REGISTRY / ROUTING IMPACT: YES / NO
NEW DOCUMENT REQUIRED: YES / NO
CANONICAL OWNER: <документ>
AFFECTED DOCUMENTS: <только реально затронутые>
CONTRADICTION CHECK: REQUIRED / NOT REQUIRED
LOSS CHECK: PASS / NOT APPLICABLE / FAILED
```

При `NO` для документального влияния не делать искусственных правок. При `YES` сверить фактический результат, затем обновить владельца и необходимые краткие карты. Исторический журнал `06` не переписывать задним числом.

## Трёхуровневая фиксация работы

Для крупной TASK или архитектурной ветки документация ведётся в трёх уровнях, чтобы не смешивать статус, общую историю и подробный технический разбор:

1. `05_Реестр задач.md` — короткий оперативный статус TASK: что сделано, текущий статус, ключевой подтверждённый результат, что остаётся до закрытия. Без длинной хронологии.
2. `06_Журнал выполнения и отчёты.md` — общая история проекта: значимые milestones, найденные дефекты, repair, live-подтверждение и итог этапа. Запись должна позволять восстановить последовательность событий без чтения профильного журнала.
3. Профильный журнал активной архитектурной программы — подробные решения, метрики, контрольные точки, negative/positive evidence, rollback и rationale. Для текущей программы качественного перехода таким журналом является `21_Журнал качественного перехода - решения, метрики и аудит.md`, работающий вместе с планом `20_Программа качественного перехода - оптимизация runtime, контекстов и памяти.md`.

Если начинается новая крупная ветка, например Voice/ASR, межчатовый контекст или другая самостоятельная архитектура, сначала определить её профильного владельца. Если существующего профильного документа достаточно — вести подробности там или рядом в специализированном журнале. Новый журнал создавать только при устойчивой серии TASK, где общей истории `06` уже недостаточно для точного аудита решений. Такой журнал обязан иметь однозначную ответственность и routing в `08_Старт.md`.

`22_Техническая информация.md` — не журнал решений: туда идут компактные технические справки, version-specific notes, команды и эксплуатационные детали, которые полезно быстро находить отдельно от истории TASK.

Для ветки Web Alarm Workspace архитектурный источник истины — `23_Архитектура Web Alarm Workspace.md`, порядок и статус внедрения — `24_План реализации Web Alarm Workspace.md`, а append-only профильная история подтверждённых больших задач/микрозадач — `25_Журнал Web Alarm Workspace - выполненные задачи и аудит.md`. При изменении фактической архитектуры, протокола или state model проверять `23`; при изменении очередности, состава, критериев приёмки или статуса этапов — `24`; после фактического выполнения и verification добавлять запись в `25`. Не переносить подробности этой ветки в общие карты: `00`, `01`, `04` и `08` должны содержать только краткий статус, routing и ответственность.

До начала каждой значимой TASK общий `000_Задачи для агента.md` должен показывать короткий project-level NEXT, назначенного исполнителя и route на его персональную карточку. Полная постановка хранится в БЛОКЕ 1 персонального task-файла исполнителя. Персональная карточка работает как входной слот: после фактического завершения исполнитель сам делает безопасную ротацию `БЛОК 1 → БЛОК 2 + БЛОК 3 → ОЖИДАНИЕ НОВОЙ ЗАДАЧИ`, причём очищать БЛОК 1 разрешено только после сохранения полной постановки в БЛОКЕ 2 и factual closeout в БЛОКЕ 3. Незавершённая/приостановленная TASK не маскируется под выполненную и не очищается по этому правилу. После независимого PASS verifier переносит подтверждённый итог в permanent history. **Глобальный** `000_Задачи для агента.md` — отдельный project-level router: исполнитель не очищает его БЛОК 1 как свою персональную карточку; project-level NEXT и последняя подтверждённая точка обновляются verifier/координатором после проверки. Оперативные `000`-файлы не являются долговременной историей.

Для каждой значимой завершённой или изменившей статус TASK выполнять сверку минимум по `05` и `06`; если TASK относится к активной профильной программе — дополнительно сверять её профильный журнал. Это правило применяется и при remote-работе через `Alarm/ALARM_TASK_SESSION`: аварийные `context.md/history.md/session.jsonl` сохраняют continuity, но не заменяют `000`, канонические `05/06` и профильный журнал.

## Противоречия, дубли и новые документы

При противоречии сначала установить актуальный факт по коду, runtime, тестам и доступному live evidence; затем обновить канонического владельца и исправить остальные CURRENT-копии. Не превращать план или protocol capability в работающий production lifecycle без подтверждения.

Перед удалением дубля: определить владельца → проверить полноту и актуальность его версии → при необходимости дополнить → сохранить смысл, ограничения, статус CURRENT/FUTURE и edge cases → только затем удалить копию и выполнить `LOSS CHECK`. Если сохранность нельзя доказать, текст не удалять.

Новый Markdown создавать только тогда, когда существующий документ не владеет темой. Назначить уникальную ответственность и routing, проверить смысловые дубли, зарегистрировать документ в `08` и при необходимости в HUB `00`. Для нового подготовленного context document дополнительно обновить человеческий каталог `16`; это не создаёт runtime registry.

## Правило Obsidian: номера Repair не являются тегами

Обозначения TASK/Repair (например, `Repair #2A`, `#4A`, `#4B`) — **текстовые номера исправлений**, а не теги, Wiki-ссылки или отдельные документы. В обычном Markdown-тексте экранировать решётку: `Repair \#2A` (в предпросмотре выглядит как обычный номер исправления, не создавая тег), либо целиком заключать обозначение в inline-code. В заголовках применять экранирование; в fenced code, дословных постановках и технических примерах исходный текст не переписывать ради графа.

Не отключать все теги и не применять `-tag:`-фильтры ради отдельных номеров: фильтры могут скрыть настоящие заметки. Перед приёмкой документации проверить, что случайные номера Repair не создают узлов-тегов в графе Obsidian, а файлы, Wiki-ссылки, история TASK и иные настоящие теги сохранены. Новых документов для каждого Repair без архитектурной необходимости не создавать.

## Documentation health review

Отдельно пересматривать документационную архитектуру после серии крупных архитектурных изменений, перед новым крупным этапом или контрольной точкой, при нескольких противоречиях, при трудном cold start нового Chat либо когда `00`, `08` или `01` снова начинают дублировать профильные документы. Такой review выбирает реально затронутых владельцев и выполняет contradiction / loss checks.

## Obsidian — контроль случайных связей и тегов

При записи Markdown агент проверяет, не порождают ли текстовые примеры новых узлов/рёбер графа. `[[Wiki-ссылки]]` допускаются только по утверждённой карте связей; прочие имена документов оформляются обычным текстом либо inline-code. Обозначения вида `#k` / `#tag` вне кода Obsidian распознаёт как теги: писать их внутри inline-code или использовать нейтральное обозначение, например `№k`. Создание новых файлов, YAML-тегов, Wiki-ссылок и графовых связей — только по явному заданию и после проверки назначения. Для Круглого стола топология определяется документом 28.
