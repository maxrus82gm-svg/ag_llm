6. PERSISTENT WORKSPACE STATE
======================================================================

Основное переносимое состояние WORKSPACE хранится в:

.ultra/

К нему относятся, в частности:

- metadata WORKSPACE;
- Project Context;
- история Project Context;
- CHAT;
- RAW messages;
- Working Representation;
- Context Variants;
- данные compression;
- Audit Thread и связанные persistent данные.

.ultra является служебным persistent storage.

Обычные file-editing tools
не должны напрямую использовать .ultra
как обычную рабочую папку.

Изменение внутреннего состояния должно идти
через предназначенные runtime / storage mechanisms.


======================================================================
7. RAW HISTORY И WORKING REPRESENTATION
======================================================================

RAW MESSAGE является неизменяемым оригиналом сообщения.

RAW нельзя переписывать
при редактировании или сжатии рабочей версии.

Отдельно существует Working Representation сообщения.

Рабочая версия может использовать:

- RAW;
- compressed representation;
- вручную изменённую рабочую representation;
- другую допустимую Context Variant.

Выбор рабочей representation
не изменяет RAW MESSAGE.

RAW остаётся источником истины разговора.


======================================================================
8. ACTIVE CHAT CONTEXT
======================================================================

Active Chat Context относится
к конкретному выбранному CHAT.

Разные CHAT не должны смешивать свою историю.

При формировании рабочего контекста
модель может получать сочетание:

- глобальных system instructions;
- Project Context текущего WORKSPACE;
- активной Working Representation истории выбранного CHAT;
- текущего пользовательского сообщения;
- server/tool context.

Если у сообщения активна compressed
или edited Working Representation,
в рабочий контекст может идти именно она,
а RAW остаётся сохранённым оригиналом.

======================================================================
11. FILE EDITING TOOLBOX
======================================================================

Для работы с файлами используются
read и precise-edit tools.

READ:

- list_dir;
- read_file;
- find_text;
- read_file_range.

Основные precise mutation tools:

- replace_text;
- insert_before;
- insert_after;
- write_file;
- delete_file.

Для небольшого изменения существующего файла
предпочтителен цикл:

FIND
→ READ LOCAL RANGE
→ PRECISE EDIT
→ LOCAL READBACK

Полный write_file
не должен быть первым выбором
для маленькой правки большого существующего файла.

Точный инструмент предпочтительнее
грубого инструмента,
если он решает ту же TASK безопаснее
и с меньшим объёмом изменений.


======================================================================
12. PERMISSIONS И SCOPES
======================================================================

Физические ограничения применяет Server.

Основные capability:

- READ;
- WRITE;
- DELETE;
- VERIFY.

Scope определяет,
где capability физически разрешена.

WRITE permission не означает,
что можно менять всё подряд.

DELETE является отдельным capability.

Текст TASK
не может расширить физический scope.


======================================================================
13. WRITE / DELETE PERMISSION ESCALATION
======================================================================

Реализован runtime lifecycle
для попыток WRITE / DELETE,
когда capability выключена.

Основные правила:

- mutation tools могут быть видимы модели как tool schemas;
- видимость tool НЕ означает permission на выполнение;
- физическое действие всегда проходит server-side проверку;
- запрещённый вызов НЕ выполняется;
- первый denied вызов даёт Executor server feedback;
- повторная попытка той же capability
  приводит к отдельному permission review;
- capability анализируется по классу действия,
  а не только по точному имени tool;
- WRITE capability включает,
  в частности:
  write_file,
  replace_text,
  insert_before,
  insert_after;
- DELETE относится к delete_file.

Расширить capability может только пользователь.

Server,
Executor
или Verifier
не могут самостоятельно выдать WRITE / DELETE.


======================================================================
14. TEMPORARY PERMISSION GRANT
======================================================================

Если пользователь разрешил capability
после permission review:

- разрешение действует только в текущем RUN;
- исходное состояние UI checkbox не меняется;
- следующий RUN снова использует обычные настройки;
- run_id сохраняется;
- Executor context сохраняется;
- tool budget сохраняется;
- backup state сохраняется;
- verification state сохраняется;
- предыдущий denied tool call
  НЕ исполняется автоматически.

После grant Executor должен
сам заново запросить нужное действие.

Scope при этом
не расширяется автоматически.


======================================================================
15. PERMISSION DENY / BLOCKED
======================================================================

Если пользователь не выдаёт требуемое разрешение,
RUN может завершиться состоянием:

BLOCKED

а не притворным SUCCESS.

Отсутствие permission callback
не должно приводить к автоматическому grant.

Server работает fail-closed.

Если permission review показывает,
что capability для TASK не нужна,
права не расширяются.

Нельзя превращать permission review
в бесконечный цикл.


======================================================================
16. MUTATION INTENT
======================================================================

Текстовый анализ Mutation Intent
может использоваться только
как диагностический сигнал.

LIKELY_MUTATION
не является доказательством,
что TASK действительно требует mutation.

Mutation Intent:

- не выдаёт WRITE;
- не выдаёт DELETE;
- не расширяет scope;
- не должен сам по себе запускать retry;
- не должен сам по себе запускать CONSISTENCY lifecycle;
- не должен сам по себе блокировать SUCCESS.

Физические факты runtime
имеют приоритет над текстовой эвристикой.


======================================================================
17. VERIFICATION
======================================================================

Verification должна соответствовать
реально изменённым файлам.

После новой mutation
старая verification может стать неактуальной.

Для Python-кода
может требоваться:

python_compile

Для соответствующего UI/runtime
может требоваться:

ui_smoke_test

Git diagnostics
не являются универсальным обязательным Verification Gate.

git_diff / git_status
используются как read-only diagnostics,
когда это действительно необходимо.


======================================================================
18. INDEPENDENT FINAL AUDIT
======================================================================

После выполнения TASK
существует отдельный независимый Final Audit.

Verifier
не является Executor.

Executor не должен знать
внутреннюю архитектуру независимого evaluator,
его внутренние роли,
имена,
сценарии correction
или правила принятия решения.

Исполнитель знает правила выполнения работы.

Server знает правила контроля.

Server может передавать Executor
конкретные замечания,
которые нужно исправить,
не раскрывая внутреннюю архитектуру evaluator.


======================================================================
19. FINAL AUDIT И CORRECTION
======================================================================

Final Audit работает bounded.

Correction не должна превращаться
в бесконечный цикл.

Существуют server-side механизмы
ограничения повторов
и обнаружения отсутствия прогресса.

При повторяющихся неудачных correction
RUN должен завершаться явным состоянием,
а не бесконечно продолжаться.


======================================================================
20. EXECUTION CONSISTENCY
======================================================================

Execution Consistency является отдельным
server/verifier механизмом анализа
фактического выполнения.

Но текстовый Mutation Intent
не должен управлять этим lifecycle.

Consistency должна опираться
на реальные server facts,
trace,
tool calls
и фактическое состояние результата.

21. TASK BLOCK / MESSAGE / RUN
======================================================================

Различать:

task_block_id
— логический блок пользовательской задачи;

message_id
— конкретное сообщение;

run_id
— основной RUN;

verifier_run_id
— отдельный verifier call.

Одна пользовательская задача
может быть связана

служебными этапами контроля.

Не смешивать эти идентификаторы.


======================================================================
22. AUDIT THREAD
======================================================================

Audit Thread хранит наблюдаемый lifecycle выполнения.

В нём могут отображаться:

- RUN events;
- tool activity;
- permission events;
- server blockers;
- permission review;
- Final Audit;
- correction;
- outcome.

Audit является не только выводом Verifier.

Server также является источником Audit events.


======================================================================
23. BACKUP
======================================================================

Backup является server-side safety mechanism.

Backup не является разрешением
на более широкий scope.

Backup не означает,
что рискованное действие можно выполнять
без TASK.

Обычный агент
не должен вручную изменять backup storage.


======================================================================
24. TRACE
======================================================================

Trace является наблюдаемой
фактической историей RUN.

Trace важнее текстового REPORT модели
при вопросе:

что реально было выполнено?

Нельзя утверждать,
что tool использовался,
если trace этого не подтверждает.


======================================================================
25. TOOL BUDGET
======================================================================

Tool limit является реальным ресурсом RUN.

Executor должен экономить tools
на:

- чтение;
- mutation;
- readback;
- verification.

Не тратить budget
на бессмысленные повторы.

Correction внутри того же RUN
не означает новый независимый
бесконечный tool budget.

32. НЕДАВНО ПРИНЯТЫЕ РЕШЕНИЯ
======================================================================

- textual LIKELY_MUTATION не управляет lifecycle;

  на фактических denied tool attempts;

  только внутри текущего RUN;

  не меняется;

- denied tool call
  не воспроизводится автоматически после grant;
- Executor не должен знать

- server-owned permission events
  должны быть видимы в Audit Thread.

33. СЛЕДУЮЩИЙ ШАГ
======================================================================

1. запустить приложение
   с актуальным runtime;

2. выполнить live permission test:

   что исходный UI checkbox
   не изменился;

6. проверить,
   что после grant

   при необходимости
