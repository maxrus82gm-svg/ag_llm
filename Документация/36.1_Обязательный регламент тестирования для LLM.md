# 36.1 — Обязательный регламент тестирования для LLM

**Назначение:** единый исполнительный контракт для ChatGPT, Codex, Claude, Ultra и будущих LLM-агентов **при разработке любого программного проекта**. **Исходные контракты:** версия 1 (2026-10-12); **TEST-COLLAB-01@2** по решению 2026-10-22. Вступает в обязательный маршрут агента после публикации этого комплекта и обновления 08. Не заменяет permission gates, `09`, `18` или профильную архитектуру.

**Scope:** каждый change, способный затронуть выполняемый код, API, хранилище, schema, CLI/UI, конфигурацию runtime, тестовый runner, CI или механизм безопасности. Документационная/изобразительная TASK без кода — проверить ссылки/согласованность, **не** запускать бессмысленный full suite.

**Тестовые платформы / пояснение 2026-10-21, без изменения контрактов:** GitHub Actions утверждён как основная независимая CI-лаборатория; существующий Web Alarm workflow работает на Windows; Ubuntu/Linux CI — запланирован, НЕ внедрён. Тесты и CI YAML изменяют назначенные Claude/Codex в отдельном scope; ChatGPT проверяет их с доступом к GitHub, может запускать безопасную доступную проверку, но сам исходники, тесты, runner и workflow не правит. Local-first разработчика остаётся, первый красный результат/негативные oracle сохраняются; CI-результат требует точных SHA, OS, run ID и evidence. Повтор старой job не является независимым новым прогоном HEAD; при любом новом чате применять маршрут 08/18/36 и исключение BLIND-START.

## TEST-COLLAB-01 — Общая накопительная база и двухэтапная независимая проверка

```rule-meta
contract: 2
status: ACTIVE
requires: [TEST-DEV-01, TEST-COV-01, TEST-EXEC-01, TEST-QA-01, TEST-EVID-01, TEST-SCOPE-01, TEST-ENG-01]
```

1. **Исполнитель владеет локальным циклом своей TASK.** Codex/Claude/Ultra/другой назначенный агент читает актуальные tests/profile, выявляет `change → risk → existing selector → gap`, по разрешённому scope дополняет/улучшает **общую базу** тестов, запускает локально подходящие target/integration/regression/negative gates, исправляет найденное, повторяет проверки и передаёт `RESULT READY / AWAITING INDEPENDENT VERIFICATION` с командами, revision, collection, counts, diff и raw evidence. Если локальный запуск невозможен, честно `NOT RUN / BLOCKED`; CI не выдавать за local run.
2. **Независимый ChatGPT-verifier** начинает review в утверждённом scope без нового GO: проверяет source/diff, тесты, oracle, negative controls и raw evidence. Сам может создавать/запускать безопасные временные синтетические тесты в изолированном scratch и доступные безопасные GitHub CI с точным SHA/run/OS/evidence. Tracked исходники/тесты/runner/workflow меняет **только по прямому USER GO** на конкретную инженерную работу (`DOC-ENGINEERING-ROLES-01@2` в 18); иначе поручает Claude/Codex. Не выдаёт свою авторскую проверку за независимую приёмку собственного fix. Запрещено расширять scope через скрипты/CI.
3. **Единый тестовый фонд:** подтверждённые новые и улучшенные тесты сохраняются в существующем проектном наборе и каталоге/профиле, без отдельных несовместимых коллекций по имени агента. Не добавлять бессмысленные дубли; устаревший selector менять только после проверки актуального контракта и сохранения первоначального FAIL. Каждый новый сложный тест проверять на реальный trigger/oracle и negative control пропорционально риску.
4. **Local-first, CI-confirmed when risk requires.** Быстрый цикл исполнителя — локально; независимый verifier выбирает повторные target/integration/quality checks и при необходимости чистый Windows/platform CI, full regression, bounded race/stress по риску и среде. Для F1–F3 и других исторических flaky failures сохранять первый FAIL, source/environment/seed/raw state; поздний PASS не стирает его. Считать `NOT RUN` любые пропущенные после падения шаги.
5. **Acceptance** только после отдельного вердикта verifier с source pin, exact test IDs/collection, PASS/FAIL/ERROR/SKIP, isolation, negative controls, evidence, gaps и NEXT SAFE ACTION. Production merge/rollout, destructive fault injection и расширение scope не разрешаются этим правилом.

## TEST-FULL-CYCLE-01 — Универсальный регламент инженерной, CI и пользовательской проверки (USER GO 14.11.2026)

```rule-meta
contract: 1
status: ACTIVE
requires: [TEST-COLLAB-01, TEST-ENG-01, TEST-QA-01, TEST-EVID-01, TEST-SCOPE-01, TEST-HUMAN-UX-01]
```

**Назначение.** Единый переносимый порядок проверки **любого программного продукта**: веб-приложения, настольной программы, сервера, API, менеджера, плагина, игры, инструмента или их интеграции. Не зависит от конкретного репозитория, языка, поставщика API, интерфейса и названия агента. В проекте могут быть дополнительные обязательные правила безопасности, CI, публикации и прав доступа — этот регламент их не отменяет.

**Ключевое разделение ответственности:** агент-разработчик отвечает за свою реализацию и авторские тесты; независимый проверяющий отвечает за попытку обнаружить скрытые ошибки, повторные технические проверки и обоснованный вердикт; **человек — владелец или назначенный пользователь — оценивает реальный продукт, его удобство, необходимость функций и новые идеи**. Ни одна из этих проверок не подменяет остальные. Человек не обязан вручную выполнять то, что можно проверить автоматически.

### 1. Начало проверки и фиксация исходной версии

1. Получить постановку, границы разрешённых действий, критерии результата, перечень изменённых компонентов и опубликованные исходники. Зафиксировать точную версию: commit SHA, ветку, manifest/hash файлов или идентификатор сборки. Не основывать вердикт только на сообщении автора «всё работает».
2. Прочитать diff, фактический код, используемые контракты, настройки, точки входа, связанные хранилища и соседние зависимости. Проверить, не изменены ли чужие компоненты, файлы конфигурации или данные без назначения.
3. Составить матрицу `изменение → риск → уже существующий тест → пробел → дополнительная проверка`. Разделить фактически проверенные сценарии, открытые риски и `NOT RUN`.
4. Авторский `PASS` означает лишь, что проверку выполнил автор. Независимый проверяющий изучает исходники и доказательства сам; он не копирует авторский итог в свой вердикт.

### 2. Обязательная самостоятельная инженерная проверка

Проверяющий **не ограничивается запуском тестов**. Он ищет неправильные решения под капотом: избыточную или бессмысленную функциональность, неверные допущения, архитектурные обходы, скрытые зависимости, непроверенные переходы состояния, утечки ресурсов, ошибки расчётов и учёта, безопасность, гонки, повторные действия, восстановление, совместимость и потерю данных. Прослеживает путь от пользовательского действия до конечного эффекта, включая ошибки и частичные сбои.

Проверяются не только ветви, которые тесты уже достигают. Для каждого серьёзного риска нужен независимый оракул: ожидаемый файл/байты/состояние/событие/ответ, а не только результат того же самого метода. Особое внимание — границам доверия, retry, cancel, timeout, restart, stale state, неправильному порядку операций, сохранению истории и откату.

**Если найден дефект:** зафиксировать воспроизведение, причину или честную гипотезу, последствия и границу исправления. Не ослаблять тест ради зелёного результата. Исправление выполняет уполномоченный исполнитель; независимый проверяющий не объявляет собственное исправление независимо принятым.

### 3. Право инициировать и создавать дополнительные тесты

Независимый проверяющий **сам выбирает и инициирует необходимые технические проверки**, не ожидая, пока разработчик перечислит все тесты. Он вправе повторять существующие suites, писать новые диагностические и регрессионные тесты, создавать негативные сценарии, проверять fault/recovery и запускать их в доступной изолированной среде **в пределах выданных прав и scope**.

- Временные диагностические тесты допускаются в разрешённом scratch/CI-окружении без изменения боевых исходников. Сохранение новых тестов, runner или workflow в Git требует соответствующих прав на запись и разрешения, установленного в проекте. Если таких прав нет — подготовить точный патч/поручение уполномоченному агенту; не выдавать подготовку за публикацию.
- Полезный тест должен попасть в общую поддерживаемую базу после проверки качества, а не остаться одноразовым доказательством. Не дублировать без причины существующие тесты.
- Для опасных изменений предусматривать negative controls: намеренно нарушенный инвариант **должен вызвать ожидаемый RED**. Отдельно фиксировать ожидаемый RED и неожиданный FAIL. Тест на пустой collection, любое исключение или один лишь exit code 0 не доказывает успех.
- Не писать тесты, которые обходят права через скрытую сеть, реальные учётные данные, production-хранилища или чужие процессы.

### 4. Независимая проверка на GitHub Actions и Windows

Если проект доступен через GitHub, **GitHub Actions — штатная независимая техническая лаборатория**. Для Windows-программы по умолчанию используется GitHub-hosted `windows-latest`; для других целевых платформ выбирается соответствующая ОС. Это отдельный компьютер для воспроизводимых тестов, **не эквивалент физическому компьютеру пользователя и полной GUI-приёмке**.

Порядок работы независимого проверяющего:

1. Привязать CI к точному проверяемому SHA. Проверить существующие workflows, команды запуска и зависимости. Если покрытия недостаточно — подготовить новый адресный workflow в `.github/workflows/` либо расширить разрешённый существующий; не создавать конфликтующие или бесконтрольно дублирующиеся pipelines.
2. Настроить `runs-on: windows-latest` для Windows, конечный `timeout-minutes`, минимальные `permissions` (обычно `contents: read`), checkout без сохранения credentials (`persist-credentials: false`), фиксированные версии интерпретаторов и разумно закреплённые зависимости. Для больших репозиториев использовать полный проверенный dependency graph и при необходимости sparse checkout/короткие временные пути.
3. Запускать настоящие штатные тесты проекта: syntax/static, unit, integration, API/transport, безопасность, негативные сценарии, restart/recovery, затронутую регрессию, UI/JS automation и сборку/упаковку — **по риску и применимости**, а не для красивого числа PASS. Каждый runner должен завершаться с проверенным exit code и непустым ожидаемым collection.
4. Изолировать данные и процессы, ставить guard до опасных импортов, не передавать secrets в непроверенный код. Для setup может понадобиться установка пакетов из сети; это **не разрешение** тестируемому приложению обращаться к внешним API. Внешние запросы, платные сервисы и реальные пользовательские данные разрешаются только отдельным установленным порядком.
5. Запустить workflow через доступный `workflow_dispatch` или через разрешённый `push`/PR-trigger. Если подключённый инструмент не поддерживает запуск workflow, использовать разрешённый GitHub-механизм либо честно сообщить `CI NOT RUN / BLOCKED` и конкретную причину. **Написанный YAML или старый успешный run не считаются новым тестированием.**
6. Получить конкретные run ID, SHA, ОС, версии инструментов, названия реально выполненных suites, PASS/FAIL/ERROR/SKIP, отрицательные контроли, stdout/stderr и загруженные artifacts. При провале исследовать первичный лог и причину; пропущенные последующие шаги считать `NOT RUN`. Не стирать первый FAIL успешным повтором.
7. Если workflow на проверочной ветке содержит только изменения CI/документации сверх исходного кода, сверить, что проверяемые production-файлы действительно совпадают с зафиксированным источником. Не объявлять непроверенный источник проверенным после изменений.

**Управление Git:** создавать и менять tracked workflow/test files, коммитить и двигать ветки можно только в согласованной роли и с разрешённым write-scope. Соблюдать правила проекта об атомарности коммитов, ветках и независимой приёмке; не подменять недостаток разрешений импровизированным обходом. Для обычного CI владельца не привлекать к ручному запуску тестов, если технический проверяющий может выполнить их сам.

### 5. Настоящее приложение — следующий обязательный уровень

Синтетический `PASS` доказывает только заявленные свойства тестовой среды. Как только реализация безопасно готова, проверять **штатную сборку настоящего приложения**: реальный запуск, установку/EXE или веб-точку входа, сохранение, настройку, работу основного инструмента, переключение режимов, остановку, повторный запуск, ошибки, обновление и возврат к прежнему состоянию. Для интеграций оценивать не только формальный ответ, но и фактическую задержку первого отклика, поток, полноту результата и работоспособность пользовательского маршрута.

Не создавать параллельную игрушечную оболочку как замену проверки готового продукта. Если мост, backend или интеграция пока не работают — инженерная отладка остаётся обязанностью команды, а реальное приложение получает честный статус `REAL APPLICATION NOT RUN` либо `FAIL`. **Чем раньше появляется работающий пользовательский вертикальный сценарий, тем раньше его нужно показать человеку.**

Реальные внешние API, оплачиваемые вызовы, production-изменения и разрушительные fault tests требуют отдельного согласования, технических ворот, ограничений расходов и плана остановки/отката. Наличие GitHub не заменяет резервную копию и восстановление пользовательских данных.

### 6. Регулярная пользовательская приёмка и совместное проектирование

Человек лично проверяет каждое **значимое изменение взаимодействия**: новый экран, расположение, размеры и необходимость кнопок, подписи, шрифты, горизонтальное растяжение, выбор режима/модели/инструмента, настройки, последовательность действий и понятность обратной связи. Даже идеально работающая кнопка может оказаться ненужной. Его задача — оценить, **как продукт ощущается и зачем в нём существует каждая функция**, а не заменить автоматические проверки.

Владелец должен регулярно видеть **продукт целиком**, а не только скриншот отдельной новой функции. Показывать рабочий сценарий после заметного изменения, при готовности новой интеграции и на промежуточных точках крупных этапов; не откладывать всё до релиза. Во время использования возникают новые идеи, обнаруживаются давние нелогичные решения, неудобные переходы и запросы на изменение масштаба или поведения.

Обратная связь человека — самостоятельный инженерный вход: `BUG`, `USER OBSERVATION`, `UX/PRODUCT FOLLOWUP`, `NEW IDEA`. Фиксировать конкретный шаг, наблюдение, желаемое поведение и решение о приоритете. Не отвергать идею потому, что существующий CI зелёный, и не вносить её незаметно в уже утверждённую задачу без согласования.

### 7. Короткая передача человеку на проверку

После подтверждения технической готовности координатор **сам инициирует** человеческий осмотр и сообщает без длинной инструкции:

- точную сборку, режим, ожидаемую среду и безопасный способ запуска;
- что изменилось по сравнению с предыдущим вариантом;
- **2–6 конкретных действий** для проверки настоящего пользовательского пути;
- что оценить визуально и по ощущениям, какие риски или `NOT RUN` ещё открыты;
- как остановить приложение и откатить изменение при проблеме.

Рекомендуемая фраза: **«Техническая проверка [объём] завершена. Теперь нужна твоя пользовательская проверка [сборка/сценарий]. Посмотри не только, работает ли функция, но и насколько понятно, удобно и нужно ли это вообще. По твоему отзыву отдельно зафиксируем ошибки и идеи».**

Не говорить «осталось только проверить у тебя», пока действительно не закрыты остальные обязательные технические проверки. Не требовать повторять уже принятые пользовательские проверки без причины.

### 8. Проверка развёртывания на других компьютерах

Для устанавливаемого или переносимого продукта отдельно планировать проверку на иных целевых машинах: чистая Windows, EXE/ярлык/инсталлятор, отсутствие нужных runtime-зависимостей, нестандартные пути, права обычного пользователя без администратора, ограничения на запись, антивирус/политики, локальная сеть, порты, CPU/GPU, память и доступность обновления/отката. Проверять **по мере готовности эксплуатационного этапа**, не объявлять выполненным заранее. GitHub-hosted Windows не воспроизводит автоматически все эти условия; при необходимости применяются отдельные стенды и пользовательские наблюдения.

### 9. Статусы: не смешивать разные доказательства

- `AUTHOR TESTED` — проверки исполнителя, независимость не подтверждена.
- `TECHNICAL PASS / FAIL / PARTIAL / NOT RUN` — самостоятельный source review и технические проверки; рядом перечислены границы.
- `CI WINDOWS PASS / FAIL / NOT RUN` — только фактически выполненный Windows run с SHA и ссылкой на evidence.
- `REAL APPLICATION PASS / FAIL / NOT RUN` — запуск настоящего продукта и его пользовательского сценария, с указанием среды и проверяющего.
- `USER UX ACCEPTED / ISSUE / CHANGE REQUEST / PENDING` — личный человеческий отзыв; автоматический тест не вправе выставить `USER UX ACCEPTED`.
- `RELEASE READY / HOLD` — отдельное итоговое решение с учётом применимых технических, реальных и пользовательских ворот. Частичный PASS не превращать в полный релизный PASS.

Для чисто внутренней задачи допускается завершить **технический scope** без немедленного осмотра владельца, если внешний сценарий не изменён. Но новый или изменённый пользовательский маршрут не считать полностью принятым без требуемой человеческой проверки.

### 10. Минимальный итог независимого проверяющего

После каждой значимой сдачи представить один связанный результат:

```text
TASK / CHANGE / проверенная версия (SHA, ветка, сборка):
Инженерный review: что прочитано, какие ошибки/риски обнаружены:
```

## TEST-HUMAN-UX-01 — Регулярная проверка настоящего продукта человеком (USER GO 14.11.2026)

```rule-meta
contract: 1
status: ACTIVE
requires: [TEST-COLLAB-01, TEST-ENG-01]
```

**Главный принцип:** успешные unit/integration/CI-тесты и безошибочная работа синтетических fixtures **не доказывают**, что реальная программа понятна, удобна, нужна пользователю и исправно работает в его сценарии. Владелец продукта — не замена автоматическим тестам, а **отдельный участник проектирования и качественной приёмки**. Его непосредственный опыт работы с целым приложением выявляет проблемы и идеи, которые недоступны при чтении кода. Этот цикл обязателен для Web Alarm Ultra и применяется к другим продуктам при их профильной адаптации.

1. **Инженерная ответственность остаётся за агентами и независимым координатором.** Исполнитель проверяет реализацию и собственные тесты. ChatGPT независимо анализирует архитектуру, причинные и логические ошибки, смысл существования функций, побочные эффекты, безопасность, гонки, восстановление, учёт, реальные переходы состояний и отрицательные сценарии; воспроизводимые Python/JS/HTTP/регрессионные проверки выполняет преимущественно на GitHub Actions Windows. Не требовать от владельца ручного тестирования вместо доступных инженерных проверок. Зелёный CI не отменяет инженерного source review.
2. **Реальное приложение — обязательная следующая ступень, а не необязательная демонстрация.** Как только изменённая функция технически пригодна для безопасного запуска, проверить штатный продукт, его настоящие точки входа, существующие настройки, данные и привычные пользовательские сценарии в разрешённой среде. Не ограничиваться MockTransport, тестовыми фрагментами или отдельной демонстрационной оболочкой. Если изменился только backend и пользовательский путь пока не готов, честно отметить `REAL APPLICATION NOT RUN`, а не объявить проверку приложения успешной.
3. **Владелец лично оценивает значимые UX/GUI-изменения.** После изменения компоновки, размеров, расположения или назначения элементов, подписей и шрифтов, выбора модели, настроек, сценария запуска, навигации, обратной связи и взаимодействия с инструментом координатор **сам предлагает своевременный пользовательский осмотр**, не дожидаясь финала большого этапа. Проверка включает не только «работает ли кнопка», но и «зачем она вообще нужна», что мешает, что лишнее, что надо увеличить или уменьшить, нет ли ненужного растяжения по горизонтали, понятен ли порядок действий и ощущается ли программа удобной. Не считать корректность внутренней реализации доказательством полезности элемента.
4. **Показывать продукт регулярно и целиком.** После значимого изменения пользовательского пути, после готовности нового моста/подключения и периодически по мере накопления функциональности предоставлять владельцу возможность открыть актуальную сборку и самостоятельно пройти реальную последовательность действий. Не откладывать первый осмотр на момент, когда дорого менять архитектуру или UI. Мелкие внутренние изменения без пользовательского эффекта не требуют отдельного ручного прогона после каждого коммита; триггер — значимое воздействие на продукт либо полезная контрольная точка.
5. **Проверка владельца — также источник новых требований.** Он может выявить не только баг, но и бессмысленную функцию, неподходящий способ управления, несоответствие продуктовой цели или новую идею при работе с приложением. Фиксировать `USER OBSERVATION` и `UX/PRODUCT FOLLOWUP` отдельно от `BUG`, с конкретным сценарием, ожидаемым поведением и приоритетом; обсуждать решение до реализации. Не отбрасывать замечание только потому, что существующий автоматический тест стабильно PASS. Не внедрять новую идею исподтишка в текущую замороженную TASK без разрешения.
6. **Перед пользовательской проверкой — короткий воспроизводимый handoff.** Координатор сообщает: какая сборка/версия и режим проверяются; что реально изменилось; как открыть штатную программу; какие 2–6 действий выполнить; на что смотреть; какие ограничения или `NOT RUN` остаются; как безопасно остановиться и вернуться к прежнему состоянию. Не выдавать неподготовленный мост или ещё не работающую функцию пользователю для инженерной отладки. После отчёта владельца фиксировать `PASS / ISSUE / CHANGE REQUEST / NOT RUN` с наблюдением и дальнейшим действием.
7. **Раздельные статусы приёмки.** `TECHNICAL PASS` — независимо проверены назначенные внутренние контракты; `REAL APPLICATION PASS` — проверен настоящий пользовательский путь в штатном приложении (с указанием кем, где и с какими ограничениями); `USER UX ACCEPTED` — владелец лично оценил значимые визуальные и поведенческие изменения. Эти статусы не подменяют друг друга; без требуемого пользовательского осмотра писать `USER UX PENDING`, не полный пользовательский PASS. Для чисто внутренней задачи можно закрыть подтверждённый технический scope, сохраняя отдельную пользовательскую проверку до принятия затронутого сценария.
8. **Реальные провайдеры, данные и устройства — отдельные ворота безопасности.** Стремиться как можно раньше проверять штатное приложение и настоящий отклик (в том числе время первого видимого ответа, поток, выбор модели, перезапуск), а не бесконечно накапливать синтетические PASS. Но настоящий OAuth/API, оплачиваемые запросы, работа с production-данными или разрушительные испытания требуют соответствующих принятых технических ворот и **отдельного явного USER GO**. GitHub откатывает код, но не гарантирует восстановление уже изменённых пользовательских данных: предусматривать backup/recovery. Проверка установки EXE/Manager на других Windows-машинах, включая ограниченные права пользователей, — отдельный эксплуатационный этап, когда он станет актуален, а не скрыто выполненный тест.

**Обязательная формулировка передачи:** «Техническая проверка [объём] завершена. Теперь нужна твоя пользовательская проверка: [сборка/режим], [конкретные действия]. Обрати внимание не только на ошибки, но и на удобство, размеры, расположение и необходимость элементов. После твоего отзыва отдельно зафиксируем замечания и предложения». Пока владелец не подтвердил результат, не объявлять `USER UX ACCEPTED`.

## TEST-EVID-ARCHIVE-01 — Адресные диагностические доказательства и раздельный архив

```rule-meta

status: ACTIVE
requires: [TEST-EVID-01, TEST-SCOPE-01]
```

**Решение пользователя 2026-10-13 / общий протокол Web Alarm + Ultra.** При ошибке агенту/координатору передаётся **короткая проверяемая диагностическая выписка**, а не весь массив тестов по умолчанию. Исполнитель самостоятельно расследует исходники, последствия и альтернативные причины; выдержка указывает точку сбоя, **не ограничивая** исследование. После локального FAIL исполнитель в пределах своей TASK и filesystem scope сам готовит evidence, без ожидания ручного копирования пользователем. При GitHub CI координатор получает source artifact и готовит аналогичную выписку. Первичный FAIL и исходный источник никогда не перезаписываются повторным PASS.

**Два слоя хранения, разделённые по архитектуре (целевая схема; автоматизация НЕ РЕАЛИЗОВАНА):**

- **Локальный объёмный архив:** `logs/test-evidence/web_alarm/<TASK-ID>/<attempt>/` и `logs/test-evidence/ultra/<TASK-ID>/<attempt>/` — исходные `results.json`, ZIP, журналы и необходимые raw-state снимки; `logs/` уже исключён в `.gitignore`, поэтому GitHub **не получит** эти данные автоматически. Предлагаемая будущая ротация: четыре обычных поколения **независимо для каждой подсистемы и набора прогонов**, с новыми каталогами для каждого attempt; до внедрения проверенного механизма ничего автоматически не удалять. Первичные красные прогоны, открытые инциденты и evidence незавершённой приёмки помечаются pinned и исключаются из ротации.
- **Компактный GitHub-доступный handoff:** `reports/test-evidence/web_alarm/<TASK-ID>/` либо `reports/test-evidence/ultra/<TASK-ID>/`, содержащий по необходимости `diagnostic.json` и короткий `manifest.json`/отчёт. Эти файлы находятся **вне `logs/`** и после явной проверки содержимого могут быть включены пользователем или уполномоченным ChatGPT в обычный GitHub-коммит. В них не включать секреты, приватные live-данные, избыточные дампы или огромные ZIP. Гарантии исходного полного evidence: сохранённый оригинал либо ссылка/ID/дата истечения CI-artifact плюс закреплённая минимальная независимая выписка; временная ссылка на CI сама по себе не означает долговременное сохранение.

**Минимальная адресная выписка:** `TASK-ID`, `profile`, `source commit/hash`, `CI run/artifact ID` либо local attempt, точный selector/round/phase, `expected vs observed`, полный релевантный error chain/frames, terminal raw-state/oracle, состояние других участвовавших workers (если нужно), исходный FAIL, команды/платформа, контрольные суммы и пути к оригиналам, известные пробелы. Указывать provenance каждого факта; не превращать рабочую гипотезу в подтверждённую root cause. Проверять существование и читаемость передаваемых путей. Если выдержки недостаточно для независимого oracle — передавать **ровно нужную** дополнительную часть оригинала, вплоть до полного артефакта.

**Синхронизация и полномочия:** локальные Codex/Claude могут записывать разрешённые evidence-файлы, но по `DOC-GIT-01@1` **не** выполняют `git status/diff/add/commit/push` и GitHub-операции без отдельного GO. Пользователь штатно синхронизирует проверенные материалы через GitHub Desktop; ChatGPT читает **фактически опубликованные** файлы и независимо проверяет их. Пока commit/push не подтверждены, ставить `LOCAL ONLY / NOT SYNCED`, а не утверждать доступность ChatGPT; отсутствие файла в GitHub не доказывает отсутствие локального результата. Remote/Desktop Commander не требуется по умолчанию. Различать подготовку evidence, публикацию, самостоятельное расследование и финальную независимую приёмку.

**Статус реализации:** правило передачи и классификации обязательно с момента публикации; единый сборщик, загрузчик CI artifact, index, перенос из TEMP и ротация четырёх поколений — **FUTURE / NOT IMPLEMENTED**, требуют самостоятельной ограниченной TASK, проверки `.gitignore`, retention, permissions и безопасного удаления. Это правило не расширяет scope текущих TASK и не меняет замороженные БЛОКИ 1; необходимые уточнения для активного агента — через короткий `TASK-ID AMENDMENT`.

## Рекомендуемый короткий сценарий любой coding TASK

```text
READ current code + relevant project profile
 → RISK/TEST IMPACT (what breaks / what proves)
 → BASELINE or failing reproducer (if useful)
 → CODE CHANGE + DIFF REVIEW
 → TARGET/INTEGRATION TESTS
 → NEGATIVE / crash / race as needed
 → FULL or platform CI by bounded risk decision
 → EVIDENCE + remaining gaps → INDEPENDENT REVIEW
```

### Практическая стоимость

Чтобы экономить токены, сначала запускать готовый target selector без LLM анализа каждого шага; при FAIL читать его traceback + relevant code/data, затем узко повторять. Массовую FULL не делать после каждой запятой. Для безопасности, durability и core contracts экономия **никогда** не оправдывает пропуск обязательного gate.

### Проверка качества системы тестирования

`ASTRA-WEB02-TEST-ARCH-001` показала два недостатка текущего Web Alarm runner: пустой TestCase может дать exit=0 при 0 collected; несколько failed subtests могут привести к отрицательному `passed` counter. Это **открытые инфраструктурные дефекты**, а не основание автоматически отрицать все отдельные test cases. До исправления consumer обязан независимо проверять counts, IDs и artifacts. Планируется отдельная согласованная TASK для общего validator.

### Как подключить агента, а не только написать документ

`08_Старт.md` объявляет обязательное адресное чтение определения `TEST-DEV-01@1` и применимых `TEST-COV-01@1`, `TEST-EXEC-01@1`, `TEST-QA-01@1`, `TEST-FLAKY-01@1`, `TEST-EVID-01@1`, `TEST-SCOPE-01@1` при кодовой TASK. Все агенты следуют маршруту 08 → 000 → 34 → 18 → 01 → профиль, затем применяют этот testing contract. Для независимого слепого `INDEPENDENT_PLAN` действуют его специальные ограничения на чтение чужого контекста; coordinator доставляет адресный норматив без раскрытия forbidden plans.

**Для самой Ultra:** текстовый документ в GitHub не загружается автоматически внутрь каждого RUN; требование закрепляется в существующем регламенте `09` только как text-level правило для тех агентов, которым он реально предоставлен. Автоматический enforcement сервером и отдельный универсальный тестовый UI требуют последующей реализации и собственного evidence.
