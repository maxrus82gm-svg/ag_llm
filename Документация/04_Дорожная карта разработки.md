# Дорожная карта разработки GigaChat Ultra Local Agent

Этот документ фиксирует последовательность ближайших этапов развития системы. Дорожная карта разделена на конкретные TASK с критериями приёмки.

## Текущий статус

Система уже имеет устойчивую базу: Workspace/Chat, persistent RAW HISTORY, Project Context и настоящий Active Chat Context. Runtime пока использует `MODEL = "GigaChat-3-Ultra"`; мультимодельность не реализована.

Ближайший архитектурный рубеж объединяет завершение 06.4 и мультимодельный фундамент MM.1–MM.4 перед production Context Compressor:

```text
06.4
↓
MM.1
↓
MM.2
↓
MM.3 + MM.4
↓
06.5
```

## Этап 06: Система чатов и управление контекстом

### TASK 06.1 — Модель данных чатов и хранение на диске
**Статус: ГОТОВО**

**Критерии приёмки:**
- Каждый чат имеет собственную директорию с уникальной структурой.
- История сообщений сохраняется на диск в виде отдельных файлов.
- Метаданные чата (имя, даты, ID) хранятся в metadata.json.
- Реализован API для создания, чтения, переименования чатов.
- Проверка: после перезапуска UI отображает сохранённые чаты.

### TASK 06.2 — Навигация по чатам текущего workspace
**Статус: В РАБОТЕ**

**Критерии приёмки:**
- Sidebar или панель со списком чатов текущего workspace.
- Возможность создать новый чат.
- Возможность переключаться между чатами.
- При переключении контекст модели очищается и загружается контекст выбранного чата.
- Реализовано переименование чатов.
- Удаление Chat: НЕ РЕАЛИЗОВАНО.

### TASK 06.3 — Настоящий multi-turn context
**Статус: ГОТОВО**

**Критерии приёмки:**
- Active context строится из полной истории выбранного chat_id.
- Модель получает несколько RAW user/assistant сообщений, а не только последнее.
- Проверка: trace CHAT CONTEXT подтверждает загрузку нескольких сообщений; история включается в запрос модели.

### TASK 06.4 — Разделение raw history и active model context
**Статус: В РАБОТЕ**

**Критерии приёмки:**
- Raw history всегда полная и неизменная.
- Active context строится из RAW history выбранного Chat.
- WORKING REPRESENTATION / SUMMARY: НЕ РЕАЛИЗОВАНО.
- Механизм trimming и предупреждение: НЕ РЕАЛИЗОВАНО.

### TASK 06.5 — Управляемое сжатие контекста
**Статус: ЗАПЛАНИРОВАНО**

**Зависит от:** 06.4 + MM.4

**Критерии приёмки:**
- Пользователь может выбрать фрагмент истории для сжатия.
- Создаётся summary с сохранением критической информации.
- Оригинал остаётся на диске.
- В active context помещается summary.
- Интерфейс для действий: Сжать, Развернуть, Показать оригинал, Пересжать.
- Summary доступен для ручного редактирования.
- Production pipeline управляется server/runtime и выполняется как три отдельных чистых вызова: COMPRESS → VERIFY → FINALIZE.
- VERIFY отдельно сравнивает ORIGINAL и DRAFT; FINALIZE отдельно создаёт FINAL с учётом VERIFICATION.
- RAW остаётся неизменяемым, а FINAL не активируется без предусмотренного пользовательского подтверждения.
- Модель сжатия выбирается через COMPRESSION MODEL ASSIGNMENT.

## Ветка MM: Мультимодельная архитектура

Канонический документ: [[11_Мультимодельная архитектура и назначение LLM]]. Архитектурное решение принято, но runtime-реализация ветки MM ещё не начата.

### MM.0 — Архитектурное решение мультимодельности
**Статус: ГОТОВО**

**Результат:** зафиксирована целевая цепочка `Agent Runtime → Model Assignment → Model Registry → Provider Adapter → Model`.

### MM.1 — MODEL REGISTRY
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.0

Единый реестр доступных моделей и базовая расширяемая модель данных.

### MM.2 — GigaChat Multi-Model
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.1

Проверить несколько моделей через уже работающий GigaChat backend, не подключая новый Provider раньше необходимости.

### MM.3 — MAIN CHAT MODEL ASSIGNMENT
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.2

Выбор модели основного Chat Agent. Первый этап может быть глобальным; архитектура должна допускать `Workspace default → Chat override`.

### MM.4 — COMPRESSION MODEL ASSIGNMENT
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.2

Выбор модели Context Compression через тот же MODEL REGISTRY независимо от MAIN CHAT MODEL.

### MM.5 — LOCAL PROVIDER
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.1, MM.2

Подключение локального inference backend через Provider Adapter. Ollama может быть первым практическим backend, но не является обязательной зависимостью архитектуры.

### MM.6 — PER-CHAT MODEL ASSIGNMENT
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.3

Разные Chat внутри Workspace смогут использовать разные модели без потери собственной истории и контекста.

### MM.7 — AGENT PROFILES
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.1, MM.3

Профиль объединяет role, model assignment, role context, tools, permissions, state и execution rules.

### MM.8 — MULTI-AGENT COORDINATION / COORDINATOR
**Статус: ЗАПЛАНИРОВАНО**
**Зависит от:** MM.7

Будущий этап координации нескольких Agent; существующим runtime не является.

## Этап 07: Переносимость между компьютерами
**Статус: ЧАСТИЧНО РЕАЛИЗОВАНА**

**Критерии приёмки:**
- Переносимое состояние отделено от локального: .ultra — portable; backup/log — локальные per-machine.
- Start_Ultra.cmd работает относительно своей директории.
- Автоматическая развёртка .venv/requirements: НЕ РЕАЛИЗОВАНА.

> **Важно:** .venv — это локальное изолированное Python-окружение, НЕ виртуальная машина.

## Этап 08: Переход на web UI
**Статус: ЗАПЛАНИРОВАНО**

**Критерии приёмки:**
- Сохранена вся бизнес-логика server.py.
- UI переписан на HTML/CSS/JS (или легковесный фреймворк).
- Сохранена функциональность file-agent, trace, логирования.
- Приложение доступно по localhost:port.
- Поддержка нескольких одновременных сессий (опционально на этом этапе).

## Этап 09+: Дальнейшее развитие

После завершения этапов 06–08 система станет полноценной рабочей средой. Дальнейшие направления:
- Коллаборативная работа (несколько пользователей).
- Интеграция с внешними инструментами.
- Расширенные возможности управления контекстом.

Поддержка нескольких моделей и Provider больше не относится только к этому отдалённому разделу: она вынесена в текущую ветку MM.
