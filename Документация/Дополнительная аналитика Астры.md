## 1. Краткий вывод

Рекомендуется **переносить пользовательские сценарии вертикальными срезами через общее Python-ядро**, сохраняя действующие model_registry, OAuth, RAW/Working storage и проверенные механизмы ролей. Ultra Chat становится главным экраном. Первый небольшой инкремент — безопасное чтение существующих диалогов; **первый рабочий Chat MVP — уже создание/открытие чата, обычная отправка в GigaChat, ответ, ошибка, отмена и восстановление истории**. Просмотр истории не подменяет эту цель. Агентский режим переносится отдельно: Web Alarm остаётся единственным владельцем его TASK, разрешений и физических мутаций файлов проекта.

Общее ядро означает единые реализации и явных владельцев состояния, а не обязательный единый процесс, новый универсальный framework или предварительный перенос всей старой Ultra. Нужны несколько небольших швов в существующем коде: проверенное чтение, согласованная запись, общий completion-вызов, долговечный Turn и поддержка ordinary Chat в учёте. Библиотечный вариант выбран с условиями по конкурентности; sidecar остаётся возможной топологией того же ядра.

Существенные результаты сопоставления:

1. **Общий фундамент уже есть:** model_registry.py, gigachat_transport.py, context_storage.py, context_registry.py, Planner/Verifier, Run Store. Эти модули не требуют копирования Tkinter. Но отправка, сохранение сообщений, снимки назначения модели, обработка ошибки и permission dialog частично организованы внутри UltraApp; готового общего ConversationService пока нет.
2. **Старая кнопка «отправить» запускает file-agent**, а не дешёвый обычный разговор: ultra_ui.py::UltraApp._send → _worker → server.py::run_agent_task. Выключение Planner само по себе не выключает агентский цикл и Final Audit. Существующий ask_gigachat — односообщенческий путь с глобальной моделью, без истории и полноценного accounting; непосредственно назначать его новым Chat Runtime нельзя.
3. **EVM реализована как правильный тонкий слой ссылок на общий реестр**, но не является действующим Chat API или доказательством доступности GigaChat. Все пять её файлов совпали с локальным манифестом сдачи Claude. По входной постановке первичный source/publication review проведён, окончательные Windows CI и визуальная приёмка ещё открыты.
4. **Подключённый accounting ≠ внедрённый budget guard.** provider_accounting.py вызывается из production; ultra_budget_policy.py не импортируется production-модулями. Durable ledger S3a, pre-HTTP S3b и mutation reserve S3c отсутствуют. Обещание готового ограничения стоимости сейчас было бы ошибкой.
5. **Два интерфейса не должны стать двумя писателями одного состояния.** Одни и те же imports не создают общего singleton между процессами. Перед веб-записью нужны согласованные владельцы затрагиваемых данных и покрытие всех путей записи именно в эти данные, включая Tkinter. Это не требование сначала переписать все UI-настройки и все роли.
6. **Ultra TaskLifecycle и Web Alarm ServerStateMachine сейчас независимы.** Нельзя связать их только одинаковым TASK ID и разрешить обоим завершать/откатывать одну операцию. Старый file-agent не вызывается из веб-HTTP до отдельной интеграции gateway.
7. **Около 13 000 токенов не подтверждено как benchmark полного RUN.** Найденные измерения приведены в §9 с идентификаторами и границами. Storage delta не уменьшает повторно отправленный prompt.

Это предложение не заменяет №37, не меняет RT-002/B2 и не закрывает WA4-R. Замороженный ChatGPT Desktop MCP/Tunnel/V2Ray не является зависимостью Ultra Chat.

## 3. AS-IS старая Ultra

### 3.1. Фактические слои и направление вызовов

```text
UltraApp / Tkinter
  _send: UI policy + model snapshot + user RAW
  _worker: asyncio.run(run_agent_task) + callbacks + assistant RAW
      → root server.py: agent runtime, tools, permissions, evidence, finalization
          → model_registry: immutable ModelSpec
          → gigachat_transport: OAuth cache, endpoints, usage parsing
          → planner_runtime + task_planner: plan/session/stage lifecycle
          → verifier_runtime: tool-free Dredd calls
          → context_storage + context_registry: RAW/working/context templates
          → audit_storage + run_store: durable role streams and read models
```

**Tkinter-зависимость направлена преимущественно наружу:** ultra_ui.py импортирует server и storage; корневой server.py не импортирует UltraApp/Tk. Поэтому выделение сервисов возможно без переписывания Planner/Verifier. Однако server.py импортирует MCPServer и при импорте создаёт mcp = MCPServer(...), содержит совместимые глобальные MODEL/MAX_TOKENS и собственные tool функции. Это не чистый transport library, и его целиком не следует делать обязательным импортом HTTP-слоя.

model_registry.py::ModelSpec — frozen dataclass; MODEL_REGISTRY — MappingProxyType. Реестр содержит шесть ID и provider_model_id, не credentials, capabilities proof или per-chat assignments. get_model_spec проверяет unknown/disabled, list_model_specs перечисляет общий каталог.

gigachat_transport.py **не содержит универсальной функции chat(messages, model)**. В нём OAuth get_access_token, CHAT_URL/OAUTH_URL и extract_usage; HTTP completion POST выполняются в других модулях. Поэтому обещание «подключить существующий transport одной строкой» скрывает недостающий общий request-контракт.

### 3.2. Workspace, чат и сохранение

context_storage.py::ensure_workspace_storage создаёт .ultra/workspace.json, project context и служебные каталоги; workspace_id генерируется как ws_<uuid>. create_chat публикует staging-directory через rename; append_raw_message сохраняет отдельный immutable JSON с msg_<uuid>, role/original_text и необязательными producer/task_block_id. load_chat_messages проверяет записи, сортирует created_at/message_id. get_message_working_representation/load_chat_working_messages разрешают RAW либо активный context variant.

**Читающий веб-экран не должен вызывать ensure_*:** это создание состояния при GET. Для первого этапа использовать probe_existing_workspace, list_existing_chats, load_existing_project_context и чтение существующей истории; отсутствие данных отображать явно.

RAW/working механизм уже UI-independent. Но транзакция «принять отправку → сохранить user → выполнить request → сохранить assistant/error» распределена между UltraApp._send и _worker. Идемпотентного TurnStore, отмены Turn и причинно связанной пары сообщений в текущем storage нет. task_block_id группирует агентскую задачу, а не универсальный turn обычного чата.

**Граница переиспользования чтения:** context_storage.py::_list_existing_chats_from_root (:436) проверяет chat_id против имени папки, но не workspace_id каждого Chat. load_chat_messages (:626) проверяет chat_id внутри сообщения, но не загружает и не сверяет workspace_id Chat/RAW с ожидаемым Workspace. load_raw_message (:709) вместе с _require_chat (:675) делает более сильную проверку этой цепочки. _chat_root (:411) проверяет формат chat_id, затем строит путь; это не защита от подмены внутреннего каталога ссылкой/junction. Поэтому existing/read-only не означает готовый HTTP security contract. Новому общему query helper нужны проверка root → workspace → chat → message, безопасная политика внутренних reparse points и ограничения объёма; не копия parser в JavaScript. Разовая Path.resolve()/проверка строкового префикса не доказывает защиту от последующей подмены: конкретную политику открытия файлов и reparse/TOCTOU-предел нужно принять и испытать в этой узкой read-границе, не объявляя завершённой параллельную WA4-R. Это source finding и требование будущей проверки, не доказанный exploit.

load_chat_messages перечисляет и разбирает все *.json, затем сортирует. Лимит 2 MiB действует при append, но не ограничивает внешний повреждённый JSON при чтении и суммарную историю. Срез списка после полного load не является bounded I/O. Для раннего viewer допустим ограниченный объём с явным «история превышает лимит»; затем paging/read model. Частичное чтение нельзя показывать как полную историю.

### 3.3. Роли, исполнение, evidence

run_agent_task нормализует permissions и фиксирует выбранный ModelSpec в RUN. Planner-enabled seed берёт текущую RAW TASK вместо полной истории. Далее TaskLifecycle управляет планом/стадиями, server-owned tool dispatch проверяет scope, backups, обязательную верификацию и fresh evidence. Dredd возвращает заключение, но не исполняет инструмент и не выдаёт WRITE permission.

UltraApp._worker содержит Tk-specific permission_request_callback с threading.Event.ready.wait() без deadline; результат отображается через queues и Tk pollers. Такой callback нельзя переносить в HTTP request thread: потребуется отдельный ожидающий server-owned approval со сроком действия и явным продолжением.

AuditThreadRecorder.observe → _persist_event → run_store.append_run_record хранит role streams, records.idx.jsonl, hash/offset/length и ack. Summary и UI projection могут ошибаться независимо. Root server._emit делает обязательными отдельные tool/final/terminal доказательства, а часть диагностических/accounting events остаётся best-effort. Provisional SUCCESS callback не равен гарантированно возвращённому SUCCESS: после callback идут проверки сохранности evidence.

**Дополнительные ограничения Run Store для Chat:** run_store.py:16–22 фиксирует четыре streams SERVER/EXECUTOR/PLANNER/DREDD и usage roles planner/executor/dredd. record_usage (:495), record_provider_attempt_started (:506), record_provider_attempt_terminal (:530) отвергают другую роль. AuditThreadRecorder._source_for_event (:289) отправит неизвестную accounting role в SERVER; _persist_event (:324) поймает ошибку _update_summary и добавит audit_summary_error. Поэтому сохранённый event ещё не доказывает корректный total для нового chat. test_provider_attempt_integration.py::test_audit_routes_attempts_to_role_streams_and_aggregates_once проверяет три текущие роли; coverage chat там нет. Compressor имеет отдельный accounting путь вне этого Run Store. Веб-сервис не должен маскировать chat как executor ради прохождения этих проверок.

Кроме того, AuditThreadRecorder.__init__ (:240) уже умеет получить task_block_id=None: он создаёт внутренний детерминированный tb_ для индекса и оставляет None в публичном payload. Это существующий совместимый механизм для direct RUN, а не готовая семантика обычного Chat. Вывод редакции 1 «обычному чату обязательно генерировать пользовательский task block» был излишне жёстким; точный additive контракт выбирается с учётом этого пути.

### 3.4. Настройки и ограничения многопроцессности

ui_state.py хранит геометрию, локальный workspace browser и role assignments в LOCALAPPDATA/GigaChatUltra/ui_state.json. workspace_runtime_settings.py отдельно хранит внешние backup/log dirs. Global/context variants и шаблоны имеют ещё собственные app-level stores. Их нельзя целиком скопировать в Web Alarm settings и оставить синхронизацию «по последнему записавшему».

Single-instance lock в ultra_ui.py защищает экземпляр Tkinter, **не** Web Alarm и все общие writers. В context_storage атомарная замена отдельного файла не даёт serializable транзакцию из нескольких записей. В run_store._next_sequence/append_run_record нет общей межпроцессной critical section на вычисление sequence и append потока/индекса. Риск столкновения при новых параллельных writers выведен из исходников; аварийный race здесь не воспроизводился.

## 4. AS-IS Web Alarm и готовая EVM

WebAlarmApi.__init__ связывает WorkspaceRegistry, TaskStore, state/recovery/operation/projection/closeout services и UltraConnections. create_server создаёт ThreadingHTTPServer: один API instance обслуживает несколько request threads. Это уже конкурентный контур, даже при одном окне браузера.

WorkspaceRegistry хранит регистрации внешних проектных папок в LOCALAPPDATA/WebAlarmWorkspace/workspaces, нормализует roots и не использует автоматически Ultra workspace.json. TASK/microtask/operation IDs, approvals, snapshots, rollback, reconciliation и closeout принадлежат Web Alarm. web_alarm/mutation_executor.py::MutationExecutor.execute — физический gateway; ServerStateMachine и CloseoutService владеют своими переходами. Наличие этих механизмов не означает завершённого STRICT rollout.

**EVM call graph:**

```text
web_alarm/ui.py: loadEvm / selectEvm
   → GET /ultra/connections
   → GET|POST /ultra/connections/selection
      → WebAlarmApi.dispatch
         → UltraConnections.catalog / selection / select
            → root model_registry, без GigaChat network import
            → <Web Alarm storage>/ultra/connections.json, только сохранённая ссылка
```

connection_id = api:<provider>:<model_id>; в текущем каталоге — api:gigachat:gigachat_ultra и остальные пять моделей общего реестра. ROLES = ("chat",); отдельные назначения Planner/Verifier/Compressor через EVM ещё не реализованы. Профиль по chat сейчас общий для веб-интерфейса, не per Workspace/per Chat.

Запись выбора защищена InterProcessLock и temp/fsync/replace; CORRUPT сохраняется отдельно только при явном новом выборе. Каталог показывает REGISTERED/DISABLED, verification всегда UNVERIFIED; MCP/local колонки пустые. EVM не читает Tkinter ui_state и не синхронизирует его assignment. Это два **разных UI-scoped назначения**, а не два каталога моделей; будущий общий assignment scope должен быть назван явно.

В UI текущий default — operator, EVM загружается по открытию; test_web_alarm_evm_ui.js E1 закрепляет это. Требование нового Ultra Chat как default — **будущее намеренное изменение контракта**, с адаптацией теста, возвратом в operator и сохранением прямых входов в TASK.

**Статус тестов EVM:** авторский report сообщает Python full 1004 = 1002 PASS + 2 symlink SKIP, JS 9/9 + 77/77, 16/16 mutants. Это отчёт Claude, не новые тесты Astra и не финальная независимая Windows/visual acceptance. Частично открытая приёмка не превращается в VERIFIED от нашего source анализа.

**Security gap для нового Chat:** _JsonHandler._folder_picker_request проверяет loopback peer/bind, точный Host, Origin/Sec-Fetch-Site и capability token для специальных /ui маршрутов. Общий _run ведёт остальные API в dispatch без такого общего gate. Наличие application/json и loopback bind само по себе не устанавливает авторизацию платного send. Здесь установлен разрыв защиты по коду, **не продемонстрирован exploit**. Новые chat/read-context/write endpoints требуют transport gate до открытия приватной истории и запуска API. Изменение EVM selection тоже управляет будущей платной отправкой: защищать этот POST тем же подходящим browser gate и проверять явный expected connection/revision при send, с согласованной совместимостью всего Ultra API. Не считать Origin идентификацией пользователя/правом на Workspace; loopback contract защищает от чужого browser origin, но не заявляет защиту от любого процесса под тем же OS account.

## 6. Рекомендуемая архитектура общего ядра

### 6.1. Сравнение вариантов

| Критерий | 1. Общие модули + сервисные фасады | 2. Отдельный core service / sidecar | 3. Временно вызывать старый server.py как есть |
| --- | --- | --- | --- |
| Новые механизмы | несколько узких контрактов, общий writer coordinator | те же контракты + IPC, version/auth, supervisor и lifecycle | мало внешне, но скрытая адаптация агентского режима |
| Дублирование | минимально при совместимых Tk wrappers; imports не заменяют ownership | низкое при обязательном едином сервере | высок риск параллельных TASK authority/политик |
| Serialization | DTO на HTTP boundary; Python внутри без копирования всей state | каждый IPC event/result, reconnect/versioning | string result и callbacks не дают полного Chat/Turn DTO |
| Concurrency | явные locks/revisions для обеих оболочек; один writer на ресурс | проще один physical writer, но недопустим второй standalone owner | старый UI lock не защищает WA threads |
| Ошибки/cancel/recovery | общий Turn state и управляемый async worker нужны в любом случае | дополнительно sidecar death и orphan requests | ожидание Tk permission callback и нет общего Turn resume |
| Security | HTTP gate + narrow service capabilities | дополнительно IPC identity и endpoint ACL | импорт file-agent открывает слишком широкий путь |
| Testing/compatibility | перенос по функции, старые API остаются wrappers | Tk обязан стать client; большой migration seam | трудно доказать отсутствие дорогих/побочных вызовов |
| Сопровождение/вывод Tk | UI-local код уходит постепенно, core остаётся | возможно позже без смены DTO | долг закрепляет Tk orchestration внутри нового продукта |

**Выбор: вариант 1.** В пользу него работают уже независимые ModelSpec, context storage, Planner/Verifier и Run Store; EVM показывает, что web adapter может обходиться без root server import. Отдельный процесс сейчас не нужен для read-only Chat и shared library refactor. Вариант 3 отклонён: даже planner_enabled=False не образует требуемый обычный разговор.

**Критически важное условие выбора:** общий логический owner — модуль/сервис с едиными правилами; число процессов само по себе его не определяет. Однако отдельные Tk/web процессы могут одновременно менять одни и те же файлы. До доказанного координирования этого доступа веб читает историю. Первый write-режим целесообразно ограничить одним активным mutating owner на Workspace: второй интерфейс читает и получает явный BUSY при попытке записи. Покрыть нужно writers общей .ultra/chat/context и workspace-wide Run index, а не предварительно переносить все UI preference stores и все роли. Нельзя считать отдельные Chat независимыми writers: их Run index общий. Старый необновлённый writer, не соблюдающий контракт, не может безопасно работать одновременно на том же Workspace; совместимость означает сохранение функций Tk через совместимый фасад, а не допуск обходящей gate старой сборки.

Sidecar становится оправдан, если потребуется одновременное управление одной TASK двумя UI, длительный owner после закрытия интерфейса, общий loop/token/ledger, либо межпроцессные writers не удаётся надёжно оградить. Тогда переносится **тот же** сервисный фасад; второй runtime/каталог/ledger не пишется.

### 6.2. Предлагаемые контракты и владельцы

Все названия новых сервисов/DTO здесь — **PROPOSAL**, не существующие классы.

| Контракт | Используемый исходник | Единственная ответственность |
| --- | --- | --- |
| WorkspaceBindingService | WA WorkspaceRegistry + context_storage.probe | разрешить wa_workspace_id в проверенный root и existing ultra_workspace_id; никаких произвольных путей из browser |
| ConversationService | context_storage + вынесенные _send/_worker части | create/open chat, принять Turn, сохранить RAW/terminal, вернуть read model |
| ContextAssemblyService | working-message resolution + context_registry | mode-specific список реально включённых context refs/revisions и messages; не второй memory store |
| GigaChatRequestPort | выделение общего completion POST из существующих callers; gigachat_transport reuse | единый request/response/error/usage DTO, OAuth и модель из общего core |
| RunQueryService | run_store/audit_storage | read-only index/summary/selected record, без второго журнала фактов |
| AgentExecutionPort | root runtime + WA gateway adapter | предложение/исполнение tools с единственным WA mutation authority; отдельно от ordinary Chat |
| BudgetPort | утверждённый B2 S2→S3a/b/c | authoritative reservation/settlement physical attempts, не web-local счётчик |
| Mutation/Approval authority | действующие WA services | scope, CAS, approval revision, physical operation, recovery и final closeout |

Предлагаемые границы не требуют восьми новых подсистем или framework. ConversationService можно начать одним UI-independent модулем, а query/request/worker оставить малыми функциями и объектами. Условные пути ultra_core/conversation.py и web_alarm/ultra_chat.py обозначают ответственность, не обязательную новую структуру каталогов. Существующие context_storage.py/run_store.py/gigachat_transport.py остаются владельцами своей логики; тонкий HTTP adapter не владеет второй её копией. Старые публичные функции сохраняются совместимыми wrappers. Ни экран, ни новый service не импортируют весь server.py ради одной отправки.

**Направление зависимостей:** Tk/HTTP adapters → common conversation/request/storage contracts → существующие provider/storage modules. WA WorkspaceRegistry и EVM передаются как разрешённые идентификаторы/snapshots либо через узкие ports; общий Chat не должен импортировать WebAlarmApi. В агентском режиме root runtime получает ToolExecutionPort, реализация которого принадлежит WA. Так направление вызова инструмента меняется без переноса authority в модель. Для будущего Blueprint достаточно этих типизированных запросов, результатов, context refs и handles; графовый orchestrator сейчас не нужен.

### 6.3. Владение, конкурентность и effective snapshot

- Первый уровень — короткая защита read-check-write общих metadata/index и один lifecycle owner активного Turn. Уже есть web_alarm/store_lock.py::InterProcessLock; оценить его повторное использование/выделение в нейтральный модуль. Он не обеспечивает сам по себе fencing, recovery, same-process thread serialization или физическую безопасность целевого файла. Не писать второй lock framework без выявленной необходимости.
- Идентичность ресурса — проверенный root и его данные, не только строка workspace_id. Windows case/alias/reparse не должны дать две независимые блокировки одного storage. При неизвестной/изменившейся identity запись отказывается.
- После crash OS-lock может освободиться, но неизвестный исход paid attempt остаётся durable. До нового send выполняется reconciliation; timeout не доказывает отсутствие вызова. Для первого режима можно блокировать unresolved Turn без автоматического takeover. Leases/fencing с возобновлением второго owner — отдельное усложнение, не обязательная первая реализация.
- Метаданные Chat пишет ConversationService через общий storage contract; произвольные файлы проекта меняет только будущий WA gateway. Эти разные права не превращают каждое сохранение реплики в Web Alarm TASK.
- Read API не вызывает ensure/migration/repair. Во время активной записи он возвращает подтверждённую revision или обозначенную неполную/занятую проекцию, а не «согласованный snapshot» из независимо прочитанных файлов без такого контракта.
- Для первого веб-send достаточно одного управляемого worker в процессе WA, bounded queue и polling; отдельный демон и SSE не обязательны. HTTP принимает/читает/отменяет Turn через handle, а не держит handler до ответа модели. Tk может сохранить свой поток/asyncio.run через совместимый adapter: обязательна общая семантика, не немедленная унификация всех event loops.
- OAuth cache сейчас process-local. Два cache одной реализации не равны двум credential stores; общий межпроцессный token broker не является доказанной необходимостью MVP. При последовательных запросах нового owner достаточно reuse get_access_token и понятного refresh/error contract; при реальной concurrency отдельно проверить refresh stampede и привязку async locks к loop. Токены не записываются в Workspace/Turn/Blueprint.
- Модель, mode, context snapshot и policy фиксируются до dispatch; изменение EVM влияет на следующую отправку. Authoritative permissions/доступность модели проверяются повторно перед физическим send; их отзыв не обходится старым snapshot. Неизменность snapshot не даёт право продолжать отозванную операцию.
- Координация расхода в будущем принадлежит B2 ledger. Если нужен лимит между несколькими Workspace/UI, scope должен охватывать их общий ресурс; локальный cap одного Turn не доказывает общий cap аккаунта. Это отдельное решение policy, без создания web-local ledger.

### 6.4. Что значит сохранение Tkinter

На первом этапе Tkinter продолжает работать без изменений, веб только читает. При выделении сервисов его старые entry points становятся совместимыми wrappers, с той же RAW/evidence semantics и regression coverage. Одновременное редактирование одного Workspace допускается только в объёме доказанного coordination gate; до него второй writer серверно отказывается.

Откат веба скрывает новый экран/dispatch; не переписывает .ultra обратно, не удаляет новые сообщения и не возвращает старый writer в обход общего safety gate. Полный вывод Tk — отдельное пользовательское решение после feature parity, data recovery и UI acceptance.

## 7. Дизайн Ultra Chat и структура Workspace/Chat

### 7.1. Главный экран

Сверху — **Ultra Chat | Операторская панель | EVM / Подключения Ultra**. Ultra Chat открывается по умолчанию; явная ссылка на конкретную TASK открывает её в operator, не теряется при смене default. Навигация не инициирует provider requests.

Слева: существующие WA Workspace, внутри — чаты выбранного проекта, создание/открытие после соответствующего этапа. В центре: переписка с отделёнными user/assistant/error состояниями, метаданные автора/модели и composer. Справа: модель из EVM, подключённые context refs, разрешённые действия, usage и переход к RUN/verdict. Редкие diagnostics и агентские permissions — в раскрываемой панели/операторской области; обычный разговор не перегружается стадиями file-agent.

В узком окне боковые панели становятся drawers; доступ к composer, отмене и ошибке не исчезает. Assistant content — безопасный текст либо проверенный sanitizer; не выполнять HTML/скрипты из истории/provider.

Первый экран до write/network этапов честно показывает «просмотр истории; отправка ещё не подключена». Не создавать fake assistant и не показывать REGISTERED как authenticated.

### 7.2. Канонические сущности и схема хранения

| Сущность | Канонический ID / ссылка | Owner и хранение | Связь/миграционная политика |
| --- | --- | --- | --- |
| WA Workspace | wa_workspace_id (нынешнее поле workspace_id WA) | WorkspaceRegistry, machine-local registration | canonical root для navigation/authority; ID не выводится из имени папки |
| Ultra Workspace | ultra_workspace_id из .ultra/workspace.json | существующий portable context_storage | отдельный namespace, сохранить даже если оба имеют префикс ws_ |
| Workspace binding | wa_workspace_id + ultra_workspace_id + root identity + revision | предложенная запись интеграции в WA storage | не переписывать один ID другим; unknown/corrupt/mismatch → отказ/явное связывание |
| Chat | существующий chat_<uuid>, scoped Ultra Workspace | .ultra/chats/<chat_id> | прежняя история без массового копирования; активный UI chat — preference |
| Message | существующий msg_<uuid> | те же RAW JSON | неизменяемый original_text; context variant отдельно |
| Turn | предлагаемый turn_<uuid> + client_request_id | общий core, версионированная additive запись рядом с Chat | user_message_id, assistant_message_id, model/policy/context snapshots, status; старые сообщения остаются readable |
| TASK | существующий task_id Web Alarm | TaskStore/ServerStateMachine | создаётся только при явном «создать агентскую задачу» |
| Ultra task block | tb_<uuid> | Run Store/RAW refs | связь с WA TASK, не её замена и не второй closeout |
| RUN | существующий run_id + workspace/chat | Run Store | один запуск исполнения; физические provider attempts отдельны; пользовательский повтор после terminal Turn получает новую явно связанную операцию |
| Context | context_id/variant_id/source hash/revision/scope | context_registry и existing message variants/project context | refs разрешаются сервером; «global» не означает read-all |
| Model Assignment | EVM connection_ref + resolved model snapshot + scope | существующий EVM default; future Chat override в core | EVM остаётся каталогом/источником выбора; override не второй список ModelSpec |

Все новые запросы содержат wa_workspace_id/chat_id/turn_id, но **не принимают произвольный workspace_root/path** как authority. Binding проверяет реальный root и метаданные существующего Ultra. Для переноса проекта на другую машину сохраняется portable ultra_workspace_id; локальный WA ID может измениться, создаётся новый проверенный binding. При клонировании папки с тем же Ultra ID конфликт показывается явно — автоматического merge/history overwrite нет.

**Предпочтительный шов совместимости:** сохранить run_id для LLM provenance: context_storage._validate_producer требует его у kind=llm. Использовать общий Run Store с явно новым mode=chat, без TaskLifecycle и без WA TASK. Внутренняя техническая tb_ группировка, необходимая текущему индексу, не показывается как управляемая агентская TASK; учесть уже существующий nullable task_block_id adapter AuditThreadRecorder (§3.3).

Одного mode поля недостаточно. До первой Chat-записи нужны согласованные: role=chat в producer/accounting, допустимый stream для этих events (возможен SERVER без нового полного лога), aggregation/total и legacy readers, terminal outcome, Final Audit NOT_APPLICABLE либо другое явно принятое значение вместо PENDING/PASS. Не подменять роль на executor и не обходить producer validation фиктивным kind. На этапе schema-проверки решить, какие additive поля читают прежние версии; неизвестная schema не должна незаметно терять данные.

Разделение владельцев: RAW файлы — содержание сообщений; Turn — идемпотентное принятие, связь request → message IDs → RUN, порядок и пользовательский outcome; Run Store — attempts/evidence/usage; будущий B2 ledger — обязательства по расходу; WA TaskStore — только агентская TASK. Остальные представления являются проекциями этих владельцев. Это не пять журналов одного и того же факта. Дублирование terminal статуса в summary допустимо лишь как восстанавливаемая проекция с явно заданным источником истины.

Первое MVP «создать Workspace» означает зарегистрировать/открыть существующую папку через имеющийся WA registration flow, затем явно инициализировать Ultra state, если его нет. Физическое создание/перемещение папок — отдельная возможность с отдельными правами, не скрытый побочный эффект чата.

**Данные сначала не мигрируются:** читается существующий .ultra. Новые metadata — additive/versioned; legacy readers проверяются на неизвестные поля/файлы. При несовместимости — explicit export/import preview с mapping, backup и отказом от destructive in-place rewrite. Новая server-private Turn metadata не должна стать произвольным write endpoint в project files; право на историю чата отделяется от file-agent WRITE.

### 7.3. Жизненный цикл обычного Turn

Предлагаемый пользовательский ход: ACCEPTED → RUNNING → COMPLETED | FAILED | CANCELLED | UNKNOWN; при отмене допустим CANCEL_REQUESTED. Это не WA TASK verification. Отдельно хранятся phase/outcome provider attempt и usage completeness: Turn CANCELLED может иметь UNKNOWN usage, а локальная ошибка публикации ответа — уже известный расход.

**Приём и восстановление — обязательный bounded контракт:**

1. Проверить Workspace/Chat identity, права, EVM selection, лимиты очереди/ввода и version запроса. Idempotency key scoped Workspace+Chat; сервер хранит fingerprint принятого содержимого. Повтор того же ключа/содержимого возвращает прежний Turn; тот же ключ с иным содержимым — conflict. Два намеренно одинаковых сообщения с разными ключами остаются двумя сообщениями.
2. До сети долговечно закрепить Turn, заранее назначенный user_message_id, выбранную модель, mode и context snapshot; опубликовать user RAW восстановимо. Не считать отдельные atomic replace общей транзакцией. Нынешний append_raw_message каждый раз создаёт новый msg UUID — простой повтор вызова после сбоя создаёт дубль. Нужен общий узкий commit/recovery helper либо совместимое расширение функции с фиксированным ID и проверкой already-committed bytes; старую сигнатуру оставить рабочей.
3. Зафиксировать точное содержимое body и references/revisions/hashes реально использованных контекстов. Перед физической отправкой заново проверить право выполнения и общий budget guard. Смена разрешений/модели/источника не должна тихо менять уже принятый body. Если snapshot больше нельзя использовать, вернуть явный отказ/новое решение.
4. Связать RUN, logical_call_id и provider_attempt_id; до возможного send сохранить соответствующую phase/reservation. Потеря процесса между записью «начинаем отправлять» и реальным HTTP принципиально оставляет неопределённость. Пока не доказана provider idempotency, нельзя гарантировать exactly-once на стороне GigaChat. Достижимы локальная дедупликация и отсутствие автоматической повторной отправки неопределённого attempt.
5. Полученный ответ сначала сохранить восстановимо с назначенным assistant_message_id, затем завершить публикацию RAW/Turn. Если ответ сохранён, но сообщение ещё не опубликовано, recovery заканчивает локальную публикацию под тем же ID без нового API. Если ответ утрачен после возможной отправки, outcome UNKNOWN требует явного решения; новый сетевой вызов не является storage recovery.
6. Ошибка/отмена — отдельный terminal result, не успешное assistant-знание. Usage сохраняется и при отвергнутом/обрезанном ответе, если оно получено. Освобождение UI от ожидания не освобождает автоматически budget liability.

**Отмена:** AbortController закрывает браузерное ожидание; backend cancel обязан адресовать конкретный Turn/attempt. Поздний успех после cancel обрабатывается единственным durable transition: модель могла ответить и потратить токены, но второй assistant или скрытое возобновление отменённого Turn недопустимы. Если response уже committed до cancel, отмена возвращает фактический completed state. После terminal пользовательский «повторить» — новая явно связанная попытка/Turn с отдельным ключом, не незаметный resend старой операции. В первом MVP автоматические LLM retries отключены; 401-refresh, 429 и timeout требуют отдельного проверенного решения о числе физических sends.

Нужны connect/read/total deadlines, bounded queue, пределы history/input/output и concurrent requests. Для первого MVP один web worker/один active Turn на Chat и polling по revision достаточны. Состояние очереди восстанавливается из durable записей; «у нас был Python future» не является сохранённым исходом операции.

### 7.4. История и контекст — разные продукты одного storage

Новые ordinary Chat по умолчанию используют chat mode; старые чаты открываются для чтения без миграции. Историческое отсутствие mode означает legacy/unknown, а не автоматически chat. Для продолжения существующего диалога пользователь явно выбирает обычный разговор и видит, какая история/контексты будут включены; новый пустой Chat остаётся простым безопасным вариантом. Старые RAW не переклассифицируются и не переписываются массово.

Причина: UltraApp._worker сохраняет terminal failure в assistant RAW, а load_chat_working_messages выбирает роли user/assistant без анализа исхода RUN. Старые ответы могут включать агентские отчёты, ошибки, утверждения о выполненных действиях. Их можно показать в history; включение в новый prompt — отдельная context policy. Для новых Turn ошибки исключаются по структурированному outcome. Для legacy нельзя надёжно восстановить тип результата эвристикой по тексту: использовать доступный provenance/RUN либо показывать неопределённость и требовать явного выбора.

Порядок существующих RAW — created_at/message_id; он сохраняется как legacy display order, но не доказывает причинный порядок конкурентных Turn. Для новых сообщений порядок задаёт common Turn owner (sequence/revision и явные message IDs). Текущий user включается в prompt по ID ровно один раз; сравнение последней строки с task в server.py:4032 — историческая эвристика агентского entry point, не новый контракт дедупликации.

Первый MVP не обязан давать редактор context variants. Он обязан использовать существующий resolver для выбранных представлений, не включать автоматически весь Project/Global context, показывать состав контекста и честно отказывать при превышении лимита. Нельзя выдавать «все сообщения видны слева» за обещание «все они были отправлены модели».

## 8. Перенос ролей, проверок и агентских функций

### 8.1. Развести три действия пользователя

**«Отправить сообщение»** вызывает tool-free ordinary Chat: один completion attempt, без Planner/Executor tools/Dredd/Final Audit и без автоматического чтения файлов проекта. История — только выбранного Chat и явно разрешённые contexts. Это самостоятельный режим общего ядра, не второй Ultra runtime.

**«Проверить результат»** — отдельное действие/право. Сначала показывается существующая проверка из Run Store; новый verifier call требует выбранного check_type, bound evidence, модели и отдельного расхода. PASS Dredd означает verdict по предъявленным фактам, а не разрешение записи и не независимую приёмку разработческого изменения ChatGPT.

**«Создать/продолжить агентскую TASK»** — отдельный workflow: WA TASK, план/approval, effective permissions, budget и gateway. Обычный chat_id или task_block_id не подставляется вместо TASK authorization.

### 8.2. Что переиспользовать

planner_runtime.PlannerSession обслуживает INITIAL/READINESS/REPLAN и свою историю. TaskLifecycle проверяет планы, stages, obligations и evidence. verifier_runtime.run_verifier_check покрывает FINAL/PERMISSION/CONSISTENCY; run_planner_dredd_review помогает исправить Planner, но сам план не устанавливает. Root server формирует verification context и принимает terminal решения после deterministic checks.

Будущий веб-адаптер передаёт запрос в эти же функции, получает typed events и читает те же Run Store records. На вкладке видны QUEUED/RUNNING/BLOCKED/FAILED, текущий stage, длительность, последний event/heartbeat, usage completeness и evidence refs. Разрыв связи → STALE/UNKNOWN, не PASS и не автоматическое повторение инструмента.

В операторской панели остаются: scope/approval, mutation manifests, backups/snapshots, operation recovery/rollback, CAS conflicts, unresolved outcomes, завершение TASK и подробные forensic diagnostics. Ultra Chat показывает понятный статус и переход к ним.

### 8.3. Главная интеграционная граница

Сейчас root server._agent_write_file/_agent_precise_edit/_agent_delete_file выполняют собственные filesystem operations и backup logic. Они не маршрутизированы через WA MutationExecutor. Совместный UI не делает их автоматически gateway-compliant.

Предлагаемый путь: ToolExecutionPort возвращает в агентский runtime нормализованный tool result/evidence, но физическая запись и её operation_id/expected revision принадлежат WA. Ultra TaskLifecycle остаётся внутренним планом исполнения роли, подчинённым WA lifecycle; не может самостоятельно ACTIVE/VERIFIED/COMPLETE Web Alarm. Не выполнять double backup/rollback или повторную write после lost response; использовать существующий WA operation contract/replay result. Точное mapping plan_version/stage_id ↔ microtask_id требует отдельного design gate и negative tests.

Final Audit Ultra проверяет результат RUN; Final Audit/STRICT rollout Web Alarm — **другие gates**. Совпадение названия не даёт права включить новый режим или закрыть WA4-R.

### 8.4. Внешний проверяющий

Будущий ReviewPort получает immutable request_id, TASK/RUN/evidence hash и возвращает verdict с provenance. Поздний ответ к старой revision не применяется. Authentication, дедупликация, timeout, права и независимость проверяющего доказываются отдельной интеграцией. Сейчас достаточно ручного handoff ChatGPT; frozen Desktop MCP/Tunnel/V2Ray остаётся PAUSED и не включается для Chat MVP.

## 9. Контексты, оптимизация токенов и бюджеты

### 9.1. Реальная сборка prompt

В root server._run_agent_task_impl:

1. load_chat_working_messages разрешает RAW/summary; server.py:4032 не добавляет task повторно, только если последняя role=user и её content в точности равен task. Это условная эвристика, не дедупликация по message_id и не гарантия для изменённого working variant/конкурентного writer.
2. _select_executor_seed_messages при planner_enabled=True берёт только current task. При False оставляет multi-turn working history.
3. Executor получает system core + permission text + Global Ultra Context + Project Context + seed; stage_context добавляет authoritative stage facts.
4. Tool results добавляются в messages. reset=True очищает накопление на определённых stage/replan/repair boundaries; **внутри долгой stage bounded compiler нет**.
5. HTTP получает полный body.messages. AuditThreadRecorder._context_delta экономит запись diagnostics в storage, не bytes отправленного запроса.

Planner получает собственный role/session контекст, RAW task и server facts без общей Chat/Project history. Его stateless вызовы повторяют накопленную локальную PlannerSession. Verifier получает one-shot RAW TASK + verification context; «one-shot» не гарантирует малого размера evidence. Audit diagnostic может ещё раз отправить большой Executor context, хотя max output ограничен 160.

Для ordinary Chat нельзя без разбора перенести Executor system/permissions, Global Ultra и весь audit log. Нужна короткая chat role policy + выбранная working history + explicit allowed context refs. Existing variant resolution обязательно reuse; новая policy не должна выдавать выбор по последним N сообщениям за безусловно безопасное сохранение смысла. Если контекст не помещается — объяснимый отказ/предложение summary, а RAW остаётся целым.

### 9.4. Что сохранять по режимам

| Режим | Обязательный reuse / действующая экономия | Следующий безопасный шаг и предел |
| --- | --- | --- |
| Chat | ModelSpec/EVM, RAW-working variants, явная история выбранного Chat, extract_usage | tool-free body, нет pipeline tax; history policy и request/output limits с объяснимым отказом |
| Planner | изоляция от Chat/Project, RAW task once в session, server facts | измерять повтор session transcript; не урезать protocol/evidence ради числа |
| Executor | task-scoped seed, stage facts, capability visibility, резерв слотов tool calls, freshness | не вернуть full Chat при веб-переносе; bounded in-stage compiler только по B2 gates |
| Verifier/Dredd | отдельный tool-free one-shot, typed JSON verdict, actual evidence snapshot | не заменять material ссылкой, которую verifier не читает; budget отдельно |
| Final Audit | plan/evidence/source/generation binding, mandatory terminal checks | сохранять protected verification reserve; выключение Audit — явная mode policy, не экономия по умолчанию |
| Память/история | RAW immutable, variants, source hashes, user accept/restore | manual compression может стоить отдельного call/final check; не включать автоматически |
| Tools/повторная передача | полномочия, exact args, source/freshness/negative facts | storage delta не сеть; dedupe/ref только при доступности реального материала; no lossy success |

Резерв оставшихся tool calls в server.py:4687–4736 ограничивает число инструментальных шагов; он не является резервом provider tokens для Final Audit. Эти две единицы нельзя смешивать.

provider_accounting.py считает canonical JSON snapshot и приблизительную оценку utf8_bytes/4. Физический httpx json=body может сериализовать иначе. Ни canonical hash, ни число байтов не являются доказанным wire hash/token cap. Usage missing/timeout/cancel не приравнивается к нулю; цены и валюту без тарифного источника не вычислять.

**Новая route требует явного B2-контракта.** ultra_budget_policy.py::ROUTES (:57) содержит executor, audit_diagnostic, planner_session/direct, verifier_final/permission, planner_review, compressor, mcp_chat, oauth. Обычного web Chat там нет. mcp_chat — legacy MCP_SESSION, не разрешение возобновить frozen интеграцию и не подходящая метка нового Chat. Перевод старого POST в общий primitive может сохранить число физических sites, но добавит reachable logical caller; «осталось семь POST» не доказывает полноту guard.

Поэтому перед live требуются: обновлённая S1 route map; согласованное дополнение S2 route/scope/profile и mode policy; accepted S3a/S3b coverage точного нового send и UNKNOWN/recovery; нужный общий accounting contract. Route ID задаёт backend, не browser. Для ordinary Chat без tools/автопроверок не требуется выдуманный обязательный Final Audit; отсутствие этого расхода задаётся отдельной принятой mode policy, а не выключением protection у агентских RUN. Утверждённую B2 программу и числовые defaults меняет только её назначенный owner по отдельному GO.

**Развязка программ:** read-only UI, shared-library refactor и mocked Chat round-trip можно подготовить без S6b/полного Inspector/agent gateway. Безопасный paid-send является отдельным пересечением WUA и B2; его нельзя объявить готовым только по pure S2 или best-effort accounting. В предлагаемом штатном маршруте live gate обязателен, а не «предпочтителен». Ранний эксперимент до него — возможное отдельное решение пользователя о специальной TASK и остаточном риске, но не запасной разрешённый маршрут этого плана. S13a/S6a → S6b остаётся обязательной последовательностью для bounded stage compiler; данная аналитика её не переопределяет.

### 9.5. Как доказать экономию при переносе

Первое ожидаемое сокращение затрат ordinary Chat — отсутствие Planner/Executor tool loop/Dredd. Это структурное свойство маршрута, не измеренный коэффициент экономии и не результат внедрённого Stage Compiler.

Сначала на одинаковом фиксированном input/history/context snapshot проверить mock-протокол: один logical chat call, один physical LLM send при обычном успешном ходе, ноль planner/verifier/tool calls; model ID из EVM; body hash/bytes; output cap; current message exactly once. Время очереди, model latency, число попыток, prompt/completion/total, usage completeness и результат публикации считать раздельно. Пары ошибок/отмен не исключать из accounting.

Затем только по отдельному live GO — небольшой сопоставимый сценарий с указанными source revision, provider model, режимом, policy revision, входными hashes, RUN/attempt IDs и фактическим usage. Сравнение обычного Chat с прежней агентской TASK показывает цену разных режимов; оно само по себе не доказывает улучшение того же agent runtime. Для агентской оптимизации сохраняется B2 baseline/factor matrix, включая отрицательные примеры R-031. При отсутствии этих данных записывать «экономия не измерена», а не «достигнуто 13k».

## 11. Предлагаемые этапы миграции

**Ни один ID ниже не назначен этой аналитикой.** Это последовательность проверяемых результатов, а не обязательные организационные паузы между каждой функцией. Размер каждой implementation TASK уточняется по preflight и file ownership; общей «переписать core» TASK нет. Все этапы: user TASK → local guarded checks → independent ChatGPT review/нужный exact-source Windows CI → user acceptance. Базовый rollback: выключить новый entry point, сохранить данные/evidence, вернуться к старому совместимому фасаду без bypass общих guards. Полная регрессия выбирается по №36.2/36.3, не складывается из пересекающихся suites.

Зависимости WUA и B2 соединяются в одной точке paid-send, а не блокируют всякую работу по Chat:

```text
принятая EVM + согласованный source/file ownership
    → A: главный экран + безопасное чтение
    → B: совместимый store/Turn/ownership ─┐
       C: общий completion + mock ────────┤
                                         → D: сквозной offline Chat
B2: S1/S2 дополнение → S3a/S3b coverage ─┤
отдельный live GO + security acceptance ─┘→ E: рабочий GigaChat MVP
после этого: F (расширение UI) / G (отдельный agent gateway) / H (parity)
```

C не обязан ждать окончания B: ему нужны согласованные request/model/context DTO и отдельное владение файлами. Подготовка может быть разнесена по независимым TASK; граф не разрешает запуск нескольких агентов или конкурентные записи. Полная унификация всех семи legacy send-sites — последующие небольшие refactor-задачи, не prerequisite первого tool-free Chat; новый route при этом обязательно проходит общий guard.

### Этап A — WUA-2A-CHAT-READONLY-001: главный экран и чтение существующего Chat

- **Пользователь получает:** Ultra Chat по умолчанию; Workspace/чаты/сохранённая RAW переписка; EVM model badge; явное read-only состояние.
- **Зависимости:** принятая EVM, подтверждённая база, отсутствие конфликтующего owner server.py/ui.py; общий gate приватного чтения.
- **Предполагаемые файлы:** web_alarm/ui.py, web_alarm/server.py; новый web_alarm/ultra_chat.py как read adapter; узкий общий query helper в context_storage.py либо отдельном общем модуле для identity/containment/объёма; test_web_alarm_ultra_chat.py/js и адресные storage tests; адаптация test_web_alarm_evm_ui.js E1 и затронутых operator tests.
- **Границы:** только зарегистрированные roots и existing data; никаких ensure_*, созданий Chat, ввода credentials, send buttons с fake success, agent imports/network.
- **Acceptance:** HTTP round-trip на disposable existing fixture; read-only byte-tree equality, включая empty/missing/corrupt storage; mismatch workspace/chat/message, duplicate IDs и internal junction/symlink negative по принятой платформенной политике; большие/повреждённые файлы и лимит совокупной истории; XSS text, denied Host/Origin, default/navigation/deep link; EVM/operator regression; Windows visual check. Если реальная проверка reparse недоступна, не заявлять её PASS.
- **Откат:** убрать маршрут/экран, вернуть operator default; storage не менялся.
- **Далее:** общий write service B; при выявленном unsafe read path — сначала узкий transport gate repair.

### Этап B — WUA-2B-COMMON-CONVERSATION-STORE-001: общая запись Chat без сети

- **Пользователь получает:** регистрация/открытие существующей папки, явная инициализация Ultra state, создание/открытие Chat, совместимое хранение. Backend Turn/commit/recovery проверяется на fixtures. Composer не принимает в пользовательскую историю «отправленный Turn» до подключения исполняемой цепочки D/E; при необходимости draft хранится как draft, не RAW отправка.
- **Зависимости:** A, одобренный binding/ownership/Turn schema. Preflight всех Tk writers, которые затрагивают те же файлы.
- **Файлы:** context_storage.py, run_store.py/audit_storage.py для узкой chat-compatible schema/projection, общий ConversationService и ownership helper (условно ultra_core/conversation.py); совместимые вызовы ultra_ui.py и другие writers затрагиваемого storage по точному inventory; reuse/выделение store_lock.py; web adapter; tests context/create/ownership/Turn/Run Store. Переименование Chat может остаться последующим малым UI шагом.
- **Границы:** не дублировать .ultra и registry; отдельные UI preferences; без root file tools, сети и массового migration. Если полный writer coverage не входит в bounded TASK, сузить веб до отдельных безопасных данных либо оставить write disabled и вынести остаток отдельной подзадачей.
- **Acceptance:** заранее назначенные message IDs, crash до/после RAW/Turn commit и восстановление без нового append-дубля; duplicate key/same payload и conflict key/different payload; intentional equal messages/different IDs; два Chat с общим Run index; concurrent Tk/web отказ второму writer; legacy nullable tb/mode/summary readers и chat usage totals; moved/duplicate workspace, unknown metadata, staging failures; owner death → explicit reconcile.

- **Далее:** интеграция D с результатом C; нельзя объявлять atomic replace доказательством общей transaction safety.

### Этап C — WUA-2C-SHARED-GIGACHAT-REQUEST-001: общий request-контракт, mock-only

- **Пользователь получает:** проверяемую цепочку выбора EVM → model snapshot → ContextAssembly → response/error DTO в тестовом режиме; общие старые transport entry points сохраняются.
- **Зависимости:** одобренные ordinary Chat context/request contracts, EVM/source acceptance и inventory семи send-sites/всех logical callers + OAuth. Завершённая B не является техническим predecessor для pure/mock request refactor.
- **Файлы:** gigachat_transport.py либо один общий request module; server.py::ask_gigachat как совместимый wrapper над извлечённым primitive; provider_accounting.py по необходимости; mock tests. ## 12. NEXT TASK — первая рекомендованная задача для реализации

**PROPOSED / NOT ASSIGNED: WUA-2A-CHAT-READONLY-001 — «Ultra Chat: главный экран с существующими Workspace и перепиской».**

Начать **после независимой приёмки EVM**, утверждения настоящего направления и разведения write ownership с LLM15. Это одна небольшая задача с наблюдаемой пользой: пользователь открывает Web Alarm Ultra сразу в знакомых диалогах; может переключить Workspace/Chat, читать RAW history и увидеть выбранную EVM модель.

**Минимальный контракт сдачи:**

1. Ultra Chat default, рабочие переходы в operator/EVM; прямой TASK link не сломан.
2. Workspace берутся из существующего WA registry; existing Ultra identity и Chat читаются через probe/list/load без ensure/создания файлов.
3. Один read adapter поверх общего bounded query contract (§3.2): identity всего пути и containment, лимит размера отдельной записи/общего ответа. Не выдавать load_chat_messages(...)[-N:] за bounded чтение. UI не содержит списка моделей и не читает filesystem напрямую.
4. Общий transport privacy gate для новых private history endpoints, same-origin session capability, отказ чужим Host/Origin и произвольному root/chat.
5. Missing/corrupt/empty workspace и отсутствующий EVM выбор отображаются раздельно. История не попадает автоматически в LLM; credential/transport не импортируются ради страницы.
6. Targeted HTTP/JS/offline fixture checks, отсутствие storage writes/network, operator/EVM regression, source manifest и independent Windows/visual verification. Изменение default явно отражено в бывшем E1.
7. Откат — вернуть operator default и скрыть read-only adapter; existing .ultra и settings сохранены.

Если потребуется значительное общее security изменение server.py вне согласованного scope, выделить его в отдельную короткую prerequisite TASK с тем же результатом gate; **не расширять молча** WUA-2A. Модель передачи/хранения history приватна уже при чтении, поэтому security нельзя откладывать до платной отправки.

**Граница результата:** WUA-2A — полезный первый инкремент, не завершённый MVP. После него целевой ближайший milestone — D: полный offline round-trip на общем core; E включает настоящий provider после budget/live gates. Подготовку C можно вести отдельной TASK без ожидания полного B. Не открывать пользователю мнимую отправку между B и D/E и не превращать A в замену поставленной цели.
