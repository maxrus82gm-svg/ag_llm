## DOC-GITHUB-HANDOFF-01 — Обязательное заметное уведомление о принятии изменений

**Приоритет / 2026-10-24:** для новых публикаций ChatGPT в `GPT` действуют уточнения `DOC-GPT-BRANCH-01@1`: в финальном handoff просить пользовательский review/merge PR, не утверждать, что обновлён `main`.

**Обязательный финальный сигнал — уточнение пользователя 2026-10-13:** после **каждой завершённой серии успешных прямых GitHub-публикаций ChatGPT** в том же пользовательском ответе, после проверки опубликованного `main/HEAD`, отдельным заметным заголовком вывести **«🟢 ПРИМИ МОИ ИЗМЕНЕНИЯ ИЗ GITHUB»** (крупно, зелёным при поддержке интерфейса; иначе заголовок + зелёный символ). Нельзя заменять его мелкой сноской «синхронизируйте репозиторий», ссылкой на коммит или упоминанием, что локальная копия не проверена. Обязательно указать `branch`, полный `HEAD SHA`, краткий список изменённых документов и `GitHub Desktop → Fetch origin → Pull origin`; при нескольких коммитах подряд один финальный сигнал с итоговым HEAD. Это двусторонняя дисциплина актуальности: пользователь передаёт изменения ChatGPT через GitHub, а ChatGPT после своих публикаций явно требует обновления локальной копии пользователя. До подтверждения Pull не объявлять локальную копию актуальной. Если работа только READ-ONLY или публикация не состоялась, не выводить ложный призыв. При локальных несохранённых изменениях сначала согласовать безопасную синхронизацию, без force/reset.

**Железное правило пользовательского handoff.** Когда ChatGPT/внешний координатор по утверждённой TASK **успешно опубликовал изменения прямо в GitHub** и для продолжения работы, просмотра в Obsidian или использования новой редакции пользователю нужно получить их в локальную рабочую копию, в финальном видимом сообщении **обязательно** дать отдельный яркий и максимально заметный призыв:

**🟢 ПРИМИ МОИ ИЗМЕНЕНИЯ ИЗ GITHUB**

Ниже коротко: `GitHub Desktop → Fetch origin → Pull origin`, указать `branch`, актуальный полный `HEAD SHA`, изменённые файлы или ссылку на сравнение, чтобы пользователь мог проверить корректность синхронизации. Для серии адресных GitHub-коммитов объединять уведомление **в один итоговый сигнал**, не повторять шумное сообщение на каждую промежуточную запись. Если интерфейс допускает зелёную текстовую метку/цвет — использовать, иначе явно выделить текст крупно/жирно; обычный незаметный абзац недостаточен.

**Не утверждать, что пользователь уже выполнил Pull, пока он сам это не подтвердил.** До подтверждения различать `PUBLISHED ON GITHUB` и `ACCEPTED/SYNCED LOCALLY`. Если есть незакоммиченные пользовательские изменения, конфликт или синхронизация сомнительна, **не советовать слепой Pull, перезапись или reset**: сначала предупредить о сохранении изменений и предложить безопасно разобраться.

Это правило относится к **прямым GitHub-записям уполномоченного ChatGPT**, а не выдаёт Claude/Codex новых Git-прав; при отсутствии опубликованных изменений не показывать сигнал. Сохранять это требование при переходе между чатами через 08 → 000 → 34 → 18. Оно определяет только формат завершения работы, а не принятие TASK или независимую верификацию.
