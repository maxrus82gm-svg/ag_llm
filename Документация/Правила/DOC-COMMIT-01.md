## DOC-COMMIT-01 — Один нумерованный коммит на логическую задачу

**Строгая сквозная нумерация: задача, микрозадача, проверка, доработка, закрытие — один атомарный нумерованный коммит.**

**Уточнение пользователя 2026-10-13 — COMMIT DENSITY:** одна логическая TASK = **один завершённый нумерованный commit по умолчанию**, включающий связанные code, tests, docs, report. **Два коммита допустимы**, если второй отражает отдельно завершённую доработку/repair с самостоятельным результатом. **Более двух на одну TASK — только после предварительного обоснования и согласования пользователя.** Не создавать серию из 5–10 промежуточных, пофайловых, тестовых или документационных commit/push на одну операцию; собирать и проверять полный пакет до публикации. Нумерация рабочих коммитов строгая сквозная по актуальной истории; технические merge-коммиты могут оставаться ненумерованными. Не переписывать историю, не смешивать несвязанные TASK и не жертвовать безопасностью ради компактности. Сокращать также число push: по возможности одна публикация на законченный пакет. Не расширяет Git-права локальных агентов.

```rule-meta
contract: 1
status: ACTIVE
requires:
  - DOC-GIT-01@1
  - DOC-GITHUB-HANDOFF-01@1
```

**Решение пользователя 2026-10-12.** При публикации изменений уполномоченным ChatGPT-координатором **одна завершённая логическая TASK или согласованный самостоятельный этап = один Git-коммит**, даже если меняются несколько файлов: код, тесты, документация, реестр и factual report собираются в одну атомарную публикацию. Не создавать коммит на каждую запись файла или сообщение; перед публикацией подготовить полный согласованный набор, проверить scope/содержимое/Documentation Impact и только затем записывать commit. Для многофайловых изменений использовать атомарную GitHub tree/commit операцию или эквивалент вместо отдельных коммитов через пофайловый Contents API. Не включать несвязанные задачи ради уменьшения количества коммитов.

**Сквозная человеческая нумерация:** в начале commit message ставить очередное `301`, `302`, ... и короткий смысл. Подтверждённая пользователем точка отсчёта — последний пронумерованный `300` (`9bf9759f`), следующий координаторский коммит — `301`. Перед каждым новым коммитом проверять актуальный `main` и последние пронумерованные записи, не повторять использованный номер, не переписывать уже опубликованную историю ради исправления пропусков или переименования старых коммитов. Служебные merge-коммиты, созданные платформой, отличать от нумерованных рабочих TASK; отсутствие номера у старых записей не повод их пересоздавать.

Если объём требует нескольких коммитов, сперва **явно выделить независимые по смыслу этапы** с отдельным завершённым результатом и собственной нумерацией; не разбивать один документационный closeout на шесть технических коммитов. При конфликте версии/HEAD или неполном составе обязательных файлов остановить публикацию и согласовать, не подменять атомарность частично опубликованной задачей. Правило не даёт новых Git-прав локальным Claude/Codex, не разрешает самовольный merge, изменение чужих веток или bypass `DOC-GIT-01@1`. После успешной записи обязателен handoff `DOC-GITHUB-HANDOFF-01@1`.
