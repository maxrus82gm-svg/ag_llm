## DOC-COMMIT-01 — Один нумерованный коммит на логическую задачу

## USER GO 12.11.2026 — ОБЯЗАТЕЛЬНЫЙ ЦИКЛ ПРИЁМКИ → ДОКУМЕНТАЦИИ → КОММИТА

**ЖЁСТКО ДЛЯ КАЖДОГО НОВОГО ЧАТА ag_llm:** одна сдача TASK/HISTORY ID → открыть опубликованные исходники, отчёт и точный SHA → независимо выполнить проверки (по умолчанию GitHub Actions Windows в OFFLINE с сохранёнными run ID/logs; Desktop Commander только для незаменимых локальных/GUI проверок) → установить подтверждённый результат и границы NOT RUN → **только после независимого успешного PASS** оформить единый полный closeout: свой review, существующий task_record, №001, №05 и FOLLOWUP, №06, №34, №40 при влиянии, БЛОК 4 карточки и прочие затронутые документы → сверить ID, SHA, ссылки, исходные источники, OPEN и неизменность БЛОКОВ 1/1.1 → **один атомарный нумерованный Git-коммит только в ветке GPT** → readback и ссылка пользователю для его самостоятельного merge в main.

**Нет успешной независимой проверки — нет заявления PASS и успешного документационного закрытия.** FAIL/PARTIAL/NOT RUN фиксировать честно как диагностику/OPEN и не маскировать отчётом о сдаче. Авторские тесты не заменяют independent. Никаких промежуточных/пофайловых коммитов одного закрытия; если проверка или согласованный пакет неполны — STOP, не публиковать частичный closeout. GitHub-коммит не является пользовательским merge, синхронизацией локальной папки или очисткой TEMP backup.


**USER GO 06.11.2026 — СТРОГИЙ COMMIT-GATE (ПРИОРИТЕТ НАД ПРЕЖНИМИ ИСКЛЮЧЕНИЯМИ):** сквозная нумерация рабочих Git-коммитов без повторов и пропусков; перед каждой публикацией проверять свежие `main` и `GPT`, последний номер и HEAD. Последний подтверждённый рабочий №519, следующий — №520; далее номер вычисляется заново, а не берётся из памяти. **Одна завершённая логическая задача/сдача = один атомарный commit = одно нумерованное commit message.** Код, тесты, CI, отчёты, evidence, реестры и документацию одного результата собирать в одну запись. Отдельные промежуточные, пофайловые, тестовые и документационные коммиты в рамках одной сдачи ЗАПРЕЩЕНЫ, включая действия ChatGPT. Сообщение коммита начинается со следующего числа (может содержать краткий смысл). Если объём невозможно завершить атомарно, остановиться и согласовать новый самостоятельный этап, а не дробить текущий. Нельзя самостоятельно создавать merge/rebase/force-push, переписывать историю или пропускать номер; технические GitHub merge-коммиты пользователя не занимают рабочий номер. ChatGPT пишет только в `GPT`, пользователь принимает в `main`. Это не новые Git-права для локальных исполнителей. Старое разрешение на два коммита одной задачи ОТМЕНЕНО.

**Строгая сквозная нумерация: задача, микрозадача, проверка, доработка, закрытие — один атомарный нумерованный коммит.**

**Уточнение пользователя 2026-10-13 — COMMIT DENSITY:** одна логическая TASK = **один завершённый нумерованный commit по умолчанию**, включающий связанные code, tests, docs, report. **Два и более коммитов на одну TASK запрещены**. Для действительно самостоятельной новой работы пользователь назначает новую сдачу с отдельным следующим номером. Не создавать серию из 5–10 промежуточных, пофайловых, тестовых или документационных commit/push на одну операцию; собирать и проверять полный пакет до публикации. Нумерация рабочих коммитов строгая сквозная по актуальной истории; технические merge-коммиты могут оставаться ненумерованными. Не переписывать историю, не смешивать несвязанные TASK и не жертвовать безопасностью ради компактности. Сокращать также число push: по возможности одна публикация на законченный пакет. Не расширяет Git-права локальных агентов.

**Решение пользователя 2026-10-12.** При публикации изменений уполномоченным ChatGPT-координатором **одна завершённая логическая TASK или согласованный самостоятельный этап = один Git-коммит**, даже если меняются несколько файлов: код, тесты, документация, реестр и factual report собираются в одну атомарную публикацию. Не создавать коммит на каждую запись файла или сообщение; перед публикацией подготовить полный согласованный набор, проверить scope/содержимое/Documentation Impact и только затем записывать commit. Для многофайловых изменений использовать атомарную GitHub tree/commit операцию или эквивалент вместо отдельных коммитов через пофайловый Contents API. Не включать несвязанные задачи ради уменьшения количества коммитов.

**Сквозная человеческая нумерация:** в начале commit message ставить очередное `301`, `302`, ... и короткий смысл. Подтверждённая пользователем точка отсчёта — последний пронумерованный `300` (`9bf9759f`), следующий координаторский коммит — `301`. Перед каждым новым коммитом проверять актуальный `main` и последние пронумерованные записи, не повторять использованный номер, не переписывать уже опубликованную историю ради исправления пропусков или переименования старых коммитов. Служебные merge-коммиты, созданные платформой, отличать от нумерованных рабочих TASK; отсутствие номера у старых записей не повод их пересоздавать.

Если объём не помещается в один атомарный commit, **остановить публикацию** и согласовать отдельный логический этап, не разбивать один closeout на несколько коммитов. При конфликте версии/HEAD или неполном составе обязательных файлов остановить публикацию и согласовать, не подменять атомарность частично опубликованной задачей. Правило не даёт новых Git-прав локальным Claude/Codex, не разрешает самовольный merge, изменение чужих веток или bypass `DOC-GIT-01@1`. После успешной записи обязателен handoff `DOC-GITHUB-HANDOFF-01@1`.
