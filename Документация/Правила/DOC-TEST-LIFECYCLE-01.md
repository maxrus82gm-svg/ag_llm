## DOC-TEST-LIFECYCLE-01 — Длительные тесты, видимый статус и финальная сдача

```rule-meta
contract: 1
status: ACTIVE
requires: [DOC-TASK-BLOCK1-01@1, DOC-LOCAL-REPORT-HANDOFF-01@1, DOC-AGENT-REPORT-TRIGGER-01@2]
```

**USER DIRECTION 2026-10-24.** Любой исполнитель (Claude 008, Codex 007, другие) обязан различать черновик, продолжающийся тест и конечный handoff. Созданный файл `report.md`, отправленный копируемый текст или кнопка «Копировать» в чате не доказывают завершения тестов. Нельзя объявлять `RESULT READY`, пока не известны результаты всех обязательных проверок и не сохранён технический пакет; **после готовности финального пакета допускается узкий локальный перенос БЛОК 1 → 1.1 по `DOC-BLOCK1-SLOT-01@1`, до независимой приёмки; прочие карточки/архивы ротирует только координатор**. Не изменять замороженный БЛОК 1 ради этого правила; уточнения активной TASK идут через отдельный CHAT-ONLY AMENDMENT с TASK ID.

1. **Видимость незавершённости.** Когда агент возвращает управление пользователю, а обязательные тесты продолжаются либо их исход неизвестен, первым видимым заголовком сообщить: `# 🔴 ТЕСТЫ НЕ ЗАВЕРШЕНЫ — ЗАДАЧА В РАБОТЕ — ОТЧЁТ ПРЕДВАРИТЕЛЬНЫЙ`. Указать фактический `RUNNING / QUEUED / PAUSED / UNKNOWN / BLOCKED`, TASK ID, какой прогон завершён, какой ещё идёт, текущий проверенный run/process identifier (если доступен) и источник наблюдения. Не выдавать предполагаемый процент за измеренный и `UNKNOWN` за PASS.
2. **Возобновление.** Если инструмент поддерживает ожидание завершения тестового процесса в текущем цикле, можно дождаться его exit code и итогового файла, не расходуя контекст на постоянное чтение длинных логов. Если ответ заканчивается, пока процесс продолжает работать отдельно, прямо предупредить: **автоматическое возобновление чата не гарантировано**. Дать пользователю одну короткую точную инструкцию продолжения, например: «Продолжи TASK <ID>: проверь существующий тестовый процесс и доведи сдачу». Перед возобновлением проверить реальный процесс, файл результатов и exit code, не стартовать дублирующую регрессию по догадке. Не обещать собственное пробуждение без проверенного канала событий.
3. **Черновик и финал.** Черновой `report.md` может создаваться параллельно с тестами только с явным `DRAFT / TESTS RUNNING / NOT FINAL`, не должен выглядеть как финальная сдача. `RESULT READY / AWAITING INDEPENDENT VERIFICATION`, окончательный копируемый отчёт и manifest исполнителя допускаются **после** подтверждённых results/counts, FAIL/ERROR/SKIP/NOT RUN, exit code, isolation, evidence и engineering review; **ротация карточки только после независимого closeout координатора**. При FAIL/ERROR сначала корректировать в утверждённом scope и повторять нужную проверку; если невозможно — честный `PARTIAL / BLOCKED / FAIL`, факты и NEXT, без фиктивного зелёного итога. Исполнитель **не очищает** БЛОК 1 ни при каком исходе; координатор применяет `DOC-TASK-CLOSEOUT-OWNER-01@1` и архивный gate.
4. **Независимая приёмка.** Исполнитель отвечает за локальный тестовый цикл, но не ставит себе независимый PASS. ChatGPT проверяет опубликованный GitHub commit/source, report/manifest/evidence, исходные RED и независимый CI; наличие предварительного отчёта не является триггером успешной приёмки. Git-права локальных исполнителей, пользовательский push, branch boundary и запрет конфликтующих записей остаются прежними.
5. **Ultra-design bridge.** Будущий Workspace Test Control Center — только архитектурное предложение из документа 37, требующее отдельного USER GO. Статус тестового процесса, присутствие MCP/agent adapter и активность LLM — разные независимые состояния; доступный плагин не доказывает автоматического пробуждения агента.
