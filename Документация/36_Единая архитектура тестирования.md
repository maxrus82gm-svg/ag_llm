# 36 — Единая архитектура тестирования

**ARCH CLASS:** Cross-project / Testing & Quality Assurance. **Статус:** нормативная архитектура, подготовленная к внедрению; работает как правило процесса разработки после публикации/синхронизации утверждённого документа. **Это не новый runtime, runner или CI.**

**Владелец:** этот документ — принципы и границы тестирования для всех проектов/LLM. Источник обязательных действий — дочерний регламент 36.1. Конкретные инварианты/команды — проектные профили 36.2 (Web Alarm) и 36.3 (Ultra). Технические протоколы Web Alarm остаются в 23/24/25, механика Ultra — в 01/09/13. Ни один универсальный тест не подменяет проектный oracle.

## ChatGPT ↔ GitHub Actions: обязательный маршрут и проверка полномочий (2026-10-13)

**При каждом новом входе ChatGPT-чата в проект:** открыть этот раздел из актуального GitHub `36` (не по памяти), затем `36.1` и профиль `36.2` (Web Alarm) или `36.3` (Ultra). До решений о тестах явно подтвердить в ответе: **«Прочитал 36 и профильные правила. Понимаю, что могу самостоятельно создавать, изменять и проверять тесты и документы в назначенном write-scope, публиковать разрешённые изменения через GitHub и инициировать CI доступными механизмами; фактические права и ревизию проверяю перед действиями».** Это подтверждение чтения и понимания, **не** автоматическое разрешение менять любые файлы, обходить scope или делать merge.

**Подтверждённые возможности подключённого GitHub для ChatGPT:** чтение репозитория/веток/коммитов/PR, чтение GitHub Actions runs/jobs/logs, создание и обновление файлов (в т.ч. тестов и документов), создание веток, коммитов и PR, повторный запуск существующих jobs. 13.10.2026 вызов `rerun_workflow_job` для job `115236349866` вернул `success=true`; run `38379575748` стал attempt 2 (`in_progress` при проверке). **Rerun = проверка старого SHA**, не нового кода. Доступность операций определяет текущий набор инструментов и права, а не воспоминание агента.

**Новый CI без отдельного ручного `workflow_dispatch` (проверочный PR):**
1. Прочитать `08`, `18` (`DOC-PARALLEL-01`), `36.1` и профиль; зафиксировать `source_sha`, `ARCH CLASS`, read/write scope, CI paths/trigger, runner, TEMP, пересечение с другими агентами. Проверить, нет ли уже подходящего свежего run для точно этого SHA.
2. Создать **отдельную** `review/...` ветку от целевой ревизии. Не изменять `main` и чужую ветку. Если нужна диагностика, внести реальный ограниченный тест/проверку и отдельный коммит, без пустых коммитов ради запуска. Для строгой приёмки сопоставить тестируемый head SHA с исходным target SHA и явно описать диагностическую разницу.
3. Создать PR в `main`, **только если** workflow действительно слушает `pull_request` и фильтры `paths` охватывают изменения. Например, `.github/workflows/web-alarm-tests.yml` слушает PR в `main` для `web_alarm/**`, `test_web_alarm_*.py`, `test_web_alarm_*.js`, `wa4a_acceptance.py` и собственного YAML. Не считать, что пустой PR или документационный diff запустит CI.
4. Получить новый `run_id`, проверить `event`, `head_sha`, нужную Windows matrix/jobs и шаги; прочитать FAIL и сохранённые evidence. PASS на диагностическом SHA не равен автоматически PASS исходного SHA. Исторический пример: PR #15 → run `38379575748` → `37123b176097c15c8d21e0040bdf7d7f3e8072a3`, с FAIL в некоторых jobs.
5. Записать итог и ссылки в TASK/отчёт; сохранить исходные FAIL. **Не** сливать PR, не проводить rollout и не объявлять независимую приёмку без необходимых проверок. Публикацию и локальную синхронизацию выполнять по `18`.

**Ограничение:** отдельная команда создания `workflow_dispatch` в доступном GitHub-коннекторе не обнаружена. Если нужен запуск **точно** текущего HEAD без диагностического коммита, выбрать реально доступный авторизованный manual/API/CLI способ; не выдавать PR с другим SHA или rerun старого SHA за такую проверку. GitHub CLI — один из способов, **не** обязательная предпосылка доступа к GitHub.

## Разделение тестовых областей (решение 2026-10-13)

Web Alarm и Ultra сохраняют **раздельные** тестовые профили, наборы selectors, fixtures, временные каталоги и evidence. Универсальные методики могут переиспользоваться, но исполняемый тест работает как **проектная копия** в собственной области с самостоятельным oracle; тесты одной подсистемы нельзя автоматически считать тестами другой.

**CURRENT:** WA-тесты `test_web_alarm_*` и runner `wa4a_acceptance.py` находятся в корне репозитория; Ultra-тесты также в корне. Раздельные физические каталоги и запуск из них — **целевое требование, НЕ реализовано**. Перенос только отдельной TASK с проверкой import/discovery, Windows CI, всех ожидаемых selectors и сохранением прежнего evidence. До переноса действуют точные file scopes из профилей 36.2/36.3; детали обязательного порядка — `TEST-AREA-01@1` в 36.1.

## Общий цикл: исполнитель → независимый verifier → накопленная база (2026-10-13)

**Local-first / independent-review / risk-based CI.** Исполнитель (Codex, Claude, Ultra или другой назначенный агент) читает существующий каталог тестов и профиль, определяет risk/test impact, **самостоятельно запускает доступные разрешённые локальные target/integration/regression tests**, исправляет обнаруженное, повторяет проверки и передаёт исходники, diff, точные команды, результаты, версии и raw evidence. Локальный PASS исполнителя — это `RESULT READY`, а не независимая приёмка.

**И исполнитель, и ChatGPT-verifier вправе в пределах назначенной TASK и разрешений дополнять одну общую накопительную базу тестов:** создавать regression/reproducer, усиливать oracle/assertions, актуализировать устаревшие selectors, добавлять negative controls и фиксировать покрытие/каталог. Не создавать параллельные частные «тесты агента» вместо общей базы. Не дублировать проверки без полезного отличия. Каждый новый/изменённый тест сам проходит review и quality/trigger checks; нельзя скрывать исходный FAIL, ослаблять oracle, silently skip/XFAIL или объявлять PASS без исполнения.

**Самостоятельная инженерная работа необходима помимо тестов:** агент до изменения читает код и формирует причинные гипотезы, после — выполняет ручной source/adversarial walkthrough алгоритмов, неблагоприятных последовательностей и краевых состояний, сравнивает raw state с контрактами и документирует выводы. Отдельный `MANUAL ENGINEERING REVIEW` обязателен перед `RESULT READY` для значимых кодовых TASK; зелёная регрессия без этого анализа недостаточна. Канон: `TEST-ENG-01@1` (36.1).

После отчёта исполнителя **ChatGPT без повторного GO начинает независимую проверку** source/diff, тестов, рисков и evidence. Если найдена ошибка, verifier может исправить код/тесты **только в пределах уже разрешённого write-scope**, сохранить отдельный след изменения и повторно выполнить затронутые проверки; за пределами scope — оформить repair TASK/запросить GO, а не менять самовольно. По результатам risk matrix назначается дополнительный platform/CI/stress gate; GitHub CI — независимое подтверждение по необходимости, **не замена локального цикла** и не обязательный полный прогон для каждой мелочи. Для Windows races, recovery, safety и исторических красных CI сохранять платформенные проверки и первый FAIL с provenance. Если локальные tools недоступны, отметить `NOT RUN / BLOCKED` и использовать разрешённую альтернативу, не выдумывая local PASS.

Итог независимой приёмки привязывать к конкретному source revision, фактической collection, PASS/FAIL/ERROR/SKIP, isolation, доказательствам и открытым рискам. Общее тестовое наследие должно оставаться пригодным для следующего чата и агента. Нормативный исполнительный контракт: `36.1`, правило `TEST-COLLAB-01@1`.

## 2. Зачем и что переиспользуем

Цель — **не заставлять LLM многократно пересматривать всю кодовую базу**, а сохранять проверяемое знание о поведении кода в накопительных автоматических тестах. После каждой существенной правки агент сначала понимает изменение и его риски, затем дополняет проверяемые инварианты, запускает нужные тесты, анализирует diff и конкретные падения, а не выдаёт зелёный результат за гарантию отсутствия ошибок.

Это **потенциальная**, а не гарантированная экономия токенов и времени: быстрые детерминированные проверки дают агенту локализованную ошибку; тяжёлые интеграционные и стресс-прогоны могут быть дороже ручного разбора и требуют бюджета.

Переносимо между проектами: владение fixtures, воспроизводимость, наблюдение raw bytes/JSON, модель ожидаемого результата независимо от production-кода, fault injection, фазовые барьеры, процессный restart, отрицательные controls, учёт source revision и формирование evidence.

**Не переносимо без нового профиля:** TASK/state-machine и closeout Web Alarm, статусы и NEXT Ultra, схемы operation/receipt, конкретные файловые пути, права, rollback, cache/project context. Три теста Астры P1–P3 написаны **для Web Alarm**, а не являются готовой библиотекой для Ultra.

## 3. Обязательная обратная связь разработки

```text
Новая TASK / изменение требования
  → читать текущий код, контракт и профильный инвариант
  → определить impact и baseline проверок
  → выбрать/add test, если поведение или риск не покрыт
  → изменить код и просмотреть diff
  → выполнить адресные unit/contract/regression tests
  → проверить failed/success evidence, независимость oracle
  → при нужном риске: integration/full/Windows/stress отдельно
  → handoff: что изменилось, что проверено, что НЕ проверено
  → сохранить тесты и их историю вместе с исходниками
```

Порядок гибкий: для исправления ошибки обычно сначала создают **падающий reproducer**, затем чинят; для изучения неизвестной системы сначала read + baseline. В обоих случаях просмотр изменённого кода обязателен. PASS тестов никогда не отменяет code review, security review, boundary checks и проверку архитектуры.

Агент, который меняет код, обычно пишет/обновляет ближайшие тесты. Независимый verifier вправе **предложить** дополнительные тесты и, при разрешённом write-scope, добавить их; сам себе финальный независимый PASS исполнитель не выставляет.

## 4. Классы тестов, не фиксированные партии «по 200»

| Класс | Смысл | Когда |
| --- | --- | --- |
| SMOKE | быстрый сигнал, что критичные пути живы | перед/после малой правки, на commit |
| UNIT / CONTRACT | конкретное поведение, негативный вход, совместимость | у изменённой функции/контракта |
| INTEGRATION | взаимодействие компонентов, хранилищ, сети | при изменении границ и протоколов |
| REGRESSION | накопленные tests, особенно прошлые ошибки | после каждой значимой правки в затронутой зоне; полный набор по бюджету |
| FAULT / RESTART | частичная запись, crash, replay, recovery | для durable/critical state |
| CONCURRENCY | реальные interleavings, lock, CAS, race | для совместного доступа и асинхронности |
| STRESS / PLATFORM | длинные прогоны, конкретная Windows/Linux специфика | по отдельному бюджету/разрешению |

Группировать **по компонентам, рискам, времени, platform и зависимости**, а не по произвольному числу тестов. Один длинный тест может содержать десятки шагов и несколько процессов; значение `Ran 600` говорит о собранных test cases, а не о 600 независимых гарантиях.

Тесты должны быть изолированы: собственный временный root и cleanup, отсутствие зависимости от порядка, запрет на live-данные, bounded timeouts, детерминированные fixtures. Если flaky case падает только в полном suite, проверять order dependence, lock/filesystem sharing, clock, orphan workers и неверные предпосылки; сохранять исходный FAIL, не удалять тест и не заменять его blanket skip.

## 5. Тесты как живой продукт

**Код теста — источник точных assertions** и должен храниться с кодом проекта (локальный checkout и GitHub после публикации). Небольшой самоочевидный тест не получает отдельную Markdown-страницу. Для важных сценариев достаточно компактной записи в проектном профиле:

```text
TEST / selector:
INVARIANT / risk:
PRECONDITION + fixture:
ACTION / fault / crash phase:
INDEPENDENT ORACLE:
EXPECTED / forbidden outcome:
RUN: exact command and platform
EVIDENCE: versioned report / CI run / source digest
STATUS: PASS / FAIL / FLAKY / SKIP / NOT RUN / INCONCLUSIVE
OWNER / next review:
```

История жизненного цикла теста: **ADDED → VERIFIED ON REVISION → MAINTAINED/REPLACED**; при rename/обновлении фиксировать изменённое требование, почему старый oracle устарел, на какую regression заменили. Не переписывать старые FAIL задним числом. Каталог простых тестов желательно строить автоматически из selectors/annotations; **общего такого генератора пока нет**.

## 6. Нельзя выдавать за доказательство

- Зеленый тест с пустой collection; неверный счётчик (например, отрицательный PASS при нескольких failing subtests); тест, который не выполняет нужную fault phase; тест с expected, полученным из того же production oracle.
- После нового изменения исходников нельзя повторно использовать PASS прежнего source revision.
- Одна воспроизведённая безопасная Windows ошибка не доказывает, что все возможные `CloseoutError` безопасны.
- Recovery-safe и fail-closed — разные выводы: безопасность промежуточного состояния ещё не означает подтверждённого восстановления.
- Injected fault != natural Windows incident != power loss. Повторный зелёный прогон не стирает первичное красное evidence.
- Синтаксическая компиляция и UI smoke полезны, но не равны интеграционному доказательству поведения.

## 7. Безопасность, стоимость, пределы

Тесты запускаются без платных LLM, когда они уже написаны; пользователь сможет позже запускать стандартные команды/кнопку локально, а GitHub Actions — автоматически. **Кнопка, универсальная CLI оболочка, граф покрытия и единый runner для всех подсистем ещё не реализованы**: это future infrastructure tasks, не результат описания архитектуры.

Локальный агент следует его собственным правам. Запрет `DOC-GIT-01@1` на Git/GitHub для локальных Codex/Claude не отменяется тем, что тесты живут в GitHub. Только пользователь/уполномоченный ChatGPT-координатор публикует/проверяет remote CI в разрешённом scope. Внешний Desktop Commander — транспорт, не источник истинности; важные факты и immutable evidence надо сохранять в надёжном репозитории.
