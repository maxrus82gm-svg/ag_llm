# 36 — Единая архитектура тестирования

**ARCH CLASS:** Cross-project / Testing & Quality Assurance. **Статус:** нормативная архитектура, подготовленная к внедрению; работает как правило процесса разработки после публикации/синхронизации утверждённого документа. **Это не новый runtime, runner или CI.**

**Владелец:** этот документ — принципы и границы тестирования для всех проектов/LLM. Источник обязательных действий — дочерний регламент 36.1. Конкретные инварианты/команды — проектные профили 36.2 (Web Alarm) и 36.3 (Ultra). Технические протоколы Web Alarm остаются в 23/24/25, механика Ultra — в 01/09/13. Ни один универсальный тест не подменяет проектный oracle.

## 2. Зачем и что переиспользуем

Цель — **не заставлять LLM многократно пересматривать всю кодовую базу**, а сохранять проверяемое знание о поведении кода в накопительных автоматических тестах. После каждой существенной правки агент сначала понимает изменение и его риски, затем дополняет проверяемые инварианты, запускает нужные тесты, анализирует diff и конкретные падения, а не выдаёт зелёный результат за гарантию отсутствия ошибок.

Это **потенциальная**, а не гарантированная экономия токенов и времени: быстрые детерминированные проверки дают агенту локализованную ошибку; тяжёлые интеграционные и стресс-прогоны могут быть дороже ручного разбора и требуют бюджета.

Переносимо между проектами: владение fixtures, воспроизводимость, наблюдение raw bytes/JSON, модель ожидаемого результата независимо от production-кода, fault injection, фазовые барьеры, процессный restart, отрицательные controls, учёт source revision и формирование evidence.

**Не переносимо без нового профиля:** TASK/state-machine и closeout Web Alarm, статусы и NEXT Ultra, схемы operation/receipt, конкретные файловые пути, права, rollback, cache/project context. Три теста Астры P1–P3 написаны **для Web Alarm**, а не являются готовой библиотекой для Ultra.

## 3. Обязательная обратная связь разработки

```text
Новая TASK / изменение требования
  → читать текущий код, контракт и профильный инвариант
  → определить impact и baseline проверок
  → выбрать/add test, если поведение или риск не покрыт
  → изменить код и просмотреть diff
  → выполнить адресные unit/contract/regression tests
  → проверить failed/success evidence, независимость oracle
  → при нужном риске: integration/full/Windows/stress отдельно
  → handoff: что изменилось, что проверено, что НЕ проверено
  → сохранить тесты и их историю вместе с исходниками
```

Порядок гибкий: для исправления ошибки обычно сначала создают **падающий reproducer**, затем чинят; для изучения неизвестной системы сначала read + baseline. В обоих случаях просмотр изменённого кода обязателен. PASS тестов никогда не отменяет code review, security review, boundary checks и проверку архитектуры.

Агент, который меняет код, обычно пишет/обновляет ближайшие тесты. Независимый verifier вправе **предложить** дополнительные тесты и, при разрешённом write-scope, добавить их; сам себе финальный независимый PASS исполнитель не выставляет.

## 4. Классы тестов, не фиксированные партии «по 200»

| Класс | Смысл | Когда |
| --- | --- | --- |
| SMOKE | быстрый сигнал, что критичные пути живы | перед/после малой правки, на commit |
| UNIT / CONTRACT | конкретное поведение, негативный вход, совместимость | у изменённой функции/контракта |
| INTEGRATION | взаимодействие компонентов, хранилищ, сети | при изменении границ и протоколов |
| REGRESSION | накопленные tests, особенно прошлые ошибки | после каждой значимой правки в затронутой зоне; полный набор по бюджету |
| FAULT / RESTART | частичная запись, crash, replay, recovery | для durable/critical state |
| CONCURRENCY | реальные interleavings, lock, CAS, race | для совместного доступа и асинхронности |
| STRESS / PLATFORM | длинные прогоны, конкретная Windows/Linux специфика | по отдельному бюджету/разрешению |

Группировать **по компонентам, рискам, времени, platform и зависимости**, а не по произвольному числу тестов. Один длинный тест может содержать десятки шагов и несколько процессов; значение `Ran 600` говорит о собранных test cases, а не о 600 независимых гарантиях.

Тесты должны быть изолированы: собственный временный root и cleanup, отсутствие зависимости от порядка, запрет на live-данные, bounded timeouts, детерминированные fixtures. Если flaky case падает только в полном suite, проверять order dependence, lock/filesystem sharing, clock, orphan workers и неверные предпосылки; сохранять исходный FAIL, не удалять тест и не заменять его blanket skip.

## 5. Тесты как живой продукт

**Код теста — источник точных assertions** и должен храниться с кодом проекта (локальный checkout и GitHub после публикации). Небольшой самоочевидный тест не получает отдельную Markdown-страницу. Для важных сценариев достаточно компактной записи в проектном профиле:

```text
TEST / selector:
INVARIANT / risk:
PRECONDITION + fixture:
ACTION / fault / crash phase:
INDEPENDENT ORACLE:
EXPECTED / forbidden outcome:
RUN: exact command and platform
EVIDENCE: versioned report / CI run / source digest
STATUS: PASS / FAIL / FLAKY / SKIP / NOT RUN / INCONCLUSIVE
OWNER / next review:
```

История жизненного цикла теста: **ADDED → VERIFIED ON REVISION → MAINTAINED/REPLACED**; при rename/обновлении фиксировать изменённое требование, почему старый oracle устарел, на какую regression заменили. Не переписывать старые FAIL задним числом. Каталог простых тестов желательно строить автоматически из selectors/annotations; **общего такого генератора пока нет**.

## 6. Нельзя выдавать за доказательство

- Зеленый тест с пустой collection; неверный счётчик (например, отрицательный PASS при нескольких failing subtests); тест, который не выполняет нужную fault phase; тест с expected, полученным из того же production oracle.
- После нового изменения исходников нельзя повторно использовать PASS прежнего source revision.
- Одна воспроизведённая безопасная Windows ошибка не доказывает, что все возможные `CloseoutError` безопасны.
- Recovery-safe и fail-closed — разные выводы: безопасность промежуточного состояния ещё не означает подтверждённого восстановления.
- Injected fault != natural Windows incident != power loss. Повторный зелёный прогон не стирает первичное красное evidence.
- Синтаксическая компиляция и UI smoke полезны, но не равны интеграционному доказательству поведения.

## 7. Безопасность, стоимость, пределы

Тесты запускаются без платных LLM, когда они уже написаны; пользователь сможет позже запускать стандартные команды/кнопку локально, а GitHub Actions — автоматически. **Кнопка, универсальная CLI оболочка, граф покрытия и единый runner для всех подсистем ещё не реализованы**: это future infrastructure tasks, не результат описания архитектуры.

Локальный агент следует его собственным правам. Запрет `DOC-GIT-01@1` на Git/GitHub для локальных Codex/Claude не отменяется тем, что тесты живут в GitHub. Только пользователь/уполномоченный ChatGPT-координатор публикует/проверяет remote CI в разрешённом scope. Внешний Desktop Commander — транспорт, не источник истинности; важные факты и immutable evidence надо сохранять в надёжном репозитории.
