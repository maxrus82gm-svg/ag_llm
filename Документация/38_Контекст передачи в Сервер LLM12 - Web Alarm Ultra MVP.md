## 1. Текущее распределение задач — ПРИОРИТЕТНОЕ РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ

- **«Сервер LLM 12» — основной Web Alarm.** Продолжать действующий первоначальный план Web Alarm с фактической точки готовности, закрывать оставшиеся этапы и аудит надёжности WA4-R, организовать независимую проверку опубликованной работы Claude, вести инженерные решения и постепенный безопасный перенос *отдельных пригодных возможностей* старой Ultra в Web Alarm после согласования. **Не начинать сейчас разработку отдельной Ultra Tab / нового Ultra MVP.**
- **«Сервер WEB_10» (преемник WEB_09) — MCP и безопасное подключение ChatGPT к Web Alarm.** WUA Desktop Read-only MCP, возможности обычного ChatGPT Desktop, Secure MCP Tunnel, V2Ray/fail-closed и связанные исследования. WEB_10 не берёт себе приёмку Claude WA4-R как основной рабочий поток после передачи. При пересечении общих файлов/контрактов координировать изменения и исключать параллельные записи.
- **Claude 008** — локальный исполнитель Web Alarm Reliability по отдельной назначенной пользователем TASK; **Codex 007** — локальная исследовательская ветка MCP по отдельной TASK. Это роли агентов, а не дополнительные чаты с правом самостоятельно менять общую архитектуру.
- **ChatGPT** координирует архитектуру, документацию, source/evidence review и GitHub. Пользователь обычно вручную выдаёт агентам задания и делает их локальные commit/push.

**Ранее написанное о том, что LLM12 занимается WUA-0/новым GigaChat MVP, а WEB_10 принимает WA4-R, — историческая, теперь заменённая схема. Не применять её.**

- Основные механизмы Web Alarm Workspace созданы: TASK/микрозадачи, состояния и переходы, журнал событий, recovery/closeout, permissions и проверочные процедуры. Не начинать систему заново и не объявлять весь план полностью завершённым по одному зелёному набору тестов.
- Предыдущие этапы WA и их критерии сверять по первичным документам `23`, `24`, `25`, журналам `05/06`, тестовому профилю `36.2` и актуальным source/evidence. Перед новым GO составить *проверенный перечень* CLOSED / PARTIAL / OPEN: конкретные названия, gates, SHA, документы. Не выводить закрытость только из общего handoff.
- **WA4-R остаётся PARTIAL.** Базовый OBSERVE и ограниченные результаты можно учитывать лишь в подтверждённом объёме. **WARN, GATEWAY REQUIRED, STRICT и Final Audit не разрешены.** Нужны независимая проверка, решения по остаточным finding, чистый CI (W1) и отдельно согласованный read-only live-storage preflight (W3).

## 4. MCP, V2Ray и интеграция ChatGPT — ТОЛЬКО КОНТЕКСТ ДЛЯ LLM12

## 5. Ultra / дальнейший постепенный перенос — НЕ ТЕКУЩИЙ MVP

- `37_Старт перехода - Web Alarm Ultra.md` остаётся **долгосрочной концепцией**: Connection Registry → Chat Runtime/Ultra Tab → Blueprint LLM Node → возможный Codex adapter. Шаги `WUA-0…WUA-4` сейчас **не назначены**; **не начинать WUA-0 как автоматически следующий шаг**.
- Старая Ultra (Tkinter, RT-002/B2) остаётся работоспособным независимым reference/fallback. Не переносить её целиком, не подменять её status matrix и не ломать `server.py`/`ultra_ui.py`.
- Постепенный перенос в Web Alarm обсуждать после стабилизации текущей базы: инвентаризировать переиспользуемые сервисы и контракты, согласовать приоритеты, изоляцию данных и точный write-scope. Новые реализации и real GigaChat calls требуют отдельного пользовательского GO; будущий Blueprint LLM не выдавать за текущую работающую подсистему.

## 6. Роли, локальные артефакты и публикация

- Codex/Claude/Astra **не используют Git/GitHub по умолчанию, даже read-only**, не делают commit/push и не обращаются к ChatGPT сами. Исключения — только явно согласованное пользователем разрешение для конкретной задачи.
- Все полные отчёты и необходимые безопасные evidence хранятся **внутри `ag_llm`** по проектным путям, пригодным для публикации; существенные артефакты не должны скрываться `.gitignore`. Секреты и небезопасные сырые логи нельзя добавлять в Git; вместо них — безопасные публикационные копии и manifest.
- ChatGPT ведёт общую документацию и независимую проверку источников; пользователь обычно выполняет локальные commit/push. Не редактировать персональные БЛОКИ 1–3 агентов за них.
- Перед каждой TASK: точные pinned SHA, границы read/write, негативные тесты, rollback/evidence, запрет на неподтверждённый rollout, user gates и совместимость с параллельным MCP.
