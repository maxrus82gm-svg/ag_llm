# Правила разработки и работы с GigaChat Ultra Local Agent

Этот документ фиксирует практический регламент внесения изменений и эксплуатации системы. Он основан на реальном опыте разработки и направлен на предотвращение типичных ошибок.

## Основные принципы

1. **Читать реальные файлы перед изменениями**
   Перед модификацией любого файла необходимо прочитать его актуальное содержимое. Не полагаться на память или устаревшие представления.

2. **Не придумывать несуществующую архитектуру**
   Документировать только то, что реально существует в коде. Чётко разделять: ГОТОВО, В РАЗРАБОТКЕ, ЗАПЛАНИРОВАНО, АРХИТЕКТУРНОЕ РЕШЕНИЕ.

3. **Выполнять задачу, а не только писать план**
   Каждая TASK должна завершаться реальными изменениями в файлах и проверкой результата.

4. **Дробить большие задачи на маленькие этапы**
   Сложные изменения разбивать на последовательные, проверяемые шаги.

5. **Контролировать MAX_AGENT_TOOL_ITERATIONS**
   Не увеличивать лимит итераций без веской причины. Если задача требует много шагов — дробить её.

6. **Правило повторяющихся ошибок**
   При повторяющейся одинаковой ошибке не долбиться бесконечно. После 2–3 одинаковых неудачных попыток остановиться, дать диагностику и пересмотреть подход.

7. **Runtime-изменения требуют restart**
   После изменения runtime-файлов (server.py, ultra_ui.py и др.) требуется полный перезапуск приложения. Учитывать runtime warning.

8. **Использовать trace**
   Все значимые действия должны фиксироваться в trace/event subsystem для последующей диагностики.

9. **Не выдавать chain-of-thought**
   В финальных ответах не показывать внутренние рассуждения, только результат и обоснование.

10. **Логировать только наблюдаемые действия**
    В отчётах фиксировать только то, что реально выполнено и проверено.

11. **write_file не раскрывает полный контент в trace**
    При записи файлов в trace фиксируется факт операции, а не полное содержимое.

12. **Сохранять обратную совместимость**
    Если задача явно не требует breaking changes, сохранять совместимость с существующим поведением.

## Правила подготовки задач (TASK)

Каждая TASK должна быть самодостаточной, поскольку контекст между отдельными запусками агента может отсутствовать.

**Принцип «БОЛЬШОЙ БЛОК + МАЛЫЙ БЛОК»:**
- Задача формулируется целиком, с полным контекстом.
- Внутри задачи — небольшие, последовательные шаги.
- Задача должна быть пригодна для копирования и запуска как единое целое.

## Работа с документацией

- Все архитектурные решения фиксируются в отдельных документах в папке «Документация».
- Реестр задач (05_Реестр задач.md) поддерживается в актуальном состоянии.
- Журнал выполнения (06_Журнал выполнения и отчётов.md) пополняется после каждого значимого изменения.
- Использовать Obsidian-ссылки в двойных квадратных скобках для связей между документами.

## Приоритеты

1. Стабильность существующего функционала.
2. Завершение TASK 06.4: WORKING REPRESENTATION / RAW vs SUMMARY.
3. Мультимодельный фундамент MM.1–MM.4: MODEL REGISTRY, GigaChat Multi-Model, MAIN CHAT MODEL и COMPRESSION MODEL.
4. TASK 06.5: управляемое сжатие через COMPRESS → VERIFY → FINALIZE.
5. MM.5 и дальнейшая мультимодельность.
6. Переносимость и Web UI по Roadmap.

Смена или назначение модели не должна обходить server-side safety, permissions, backup, GUARD, Verification Gate и trace. Эти механизмы принадлежат Agent Runtime и действуют независимо от выбранной LLM.

Канонические детали мультимодельной архитектуры находятся в [[11_Мультимодельная архитектура и назначение LLM]]; этот практический регламент их не дублирует.

## Чего избегать

- Создавать TASK без чётких критериев приёмки.
- Объявлять реализованным то, что не проверено.
- Игнорировать runtime warning.
- Вносить изменения без фиксации в журнале.
- Повторять одни и те же ошибочные действия.

## Глобальный контекст Ultra

Глобальный контекст Ultra хранится локально вне Workspace, редактируется через UI «Глобальный контекст Ultra» и загружается server.py перед каждым RUN.
