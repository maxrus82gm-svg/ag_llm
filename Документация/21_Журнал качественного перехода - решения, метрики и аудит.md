Этот документ является историей исполнения программы:
`20_Программа качественного перехода - оптимизация runtime, контекстов и памяти.md`.

## 1. Назначение журнала

Для каждой задачи перехода здесь фиксируются:

- цель и baseline;
- configuration/models/permissions/budgets;
- конкретно изменённая зона;
- сохранённые invariants;
- targeted/integration/full tests;
- positive и negative live RUN;
- token/call/tool/latency metrics;
- regressions и неожиданные finding;
- rollback path;
- решение по контрольной точке;
- Documentation Impact.

Журнал не заменяет общий `06_Журнал выполнения и отчёты.md`: 06 остаётся общей историей проекта, а 21 — специализированной трассой программы 20.

## 2. Правило записи

Каждая запись получает:

```text
DATE / TASK / SUBTASK
BASELINE / CONFIGURATION
GOAL
CHANGE
PRESERVED INVARIANTS
TESTS
LIVE POSITIVE
LIVE NEGATIVE
METRICS BEFORE
METRICS AFTER
FINDINGS
KNOWN LIMITATIONS
ROLLBACK
CONTROL POINT DECISION
DOCUMENTATION IMPACT
NEXT
```

Если этап diagnostic-only, поле CHANGE явно говорит `runtime unchanged`.
Если live отсутствует, нельзя писать LIVE VERIFIED.
UNKNOWN usage не превращается в ноль.

Любой новый defect получает отдельную repair task/subtask, если его исправление меняет другую зону риска.

## 5. Принятое архитектурное решение

### 2026-09-30 — переход к программе 20

Решение принято после внутреннего разбора TASK 148/149 и независимого архитектурного ревью.

Главный вывод:

> архитектуру authoritative Server + Planner + Executor + independent Dredd сохраняем; оптимизируем объём и маршрутизацию информации и убираем model decisions там, где Server уже имеет exact contract.

Приоритет первой волны:

1. измерить всё;
2. доказать freshness;
3. уменьшить Final Audit packet;
4. убрать Executor из exact READ/VERIFY;
5. убрать Executor из factual final маленьких deterministic tasks;
6. затем оптимизировать постоянные prompts/context;
7. только потом подключать historical memory.
