Архитектурное решение — управляемый контекст проекта и сжатие истории чатов


ТЕРМИНЫ СИСТЕМЫ КОНТЕКСТА

WORKSPACE
Рабочее пространство / проект, привязанный к конкретной папке.

PROJECT CONTEXT
Общий постоянный контекст Workspace.
Доступен всем чатам данного Workspace.

CHAT
Отдельная ветка разговора внутри Workspace.

RAW MESSAGE
Неизменяемый оригинал сообщения.

WORKING REPRESENTATION
Текст сообщения, реально используемый при сборке активного контекста.
Может быть RAW или SUMMARY.

MESSAGE SUMMARY
Сжатая редактируемая версия конкретного RAW MESSAGE.

ACTIVE CONTEXT
Итоговый набор данных, реально отправляемый модели при конкретном запросе.

COMPRESSION PROPOSAL
Черновая версия сжатия, созданная LLM и ожидающая подтверждения пользователя.



ЦЕЛЬ

Контекст модели не должен быть непрозрачным, бесконтрольно разрастаться
или автоматически схлопываться так, чтобы пользователь терял важные данные.

Система должна одновременно обеспечивать:

- полное сохранение исходной истории;
- возможность уменьшать активный контекст;
- ручной контроль пользователя над сжатием;
- возможность исправлять ошибки LLM в созданной выжимке;
- общий постоянный контекст проекта для всех чатов;
- прозрачность: всегда должно быть понятно, какой именно текст сейчас
  используется моделью как контекст.


============================================================
1. ТРИ УРОВНЯ КОНТЕКСТА
============================================================

Система использует три различных слоя.


1. RAW HISTORY — исходная история

Каждое сообщение пользователя, модели, системное сообщение и другой
значимый фрагмент разговора сохраняется на диске в исходном виде.

RAW HISTORY:

- никогда автоматически не переписывается;
- никогда не удаляется при сжатии;
- является источником истины;
- всегда может быть открыт пользователем;
- позволяет восстановить первоначальную формулировку сообщения;
- позволяет повторно создать другую сжатую версию.

Сжатие изменяет не RAW HISTORY, а только представление сообщения,
используемое в активном контексте модели.


2. CHAT WORKING CONTEXT — рабочий контекст конкретного чата

Для старых, больших или малозначимых сообщений может создаваться
сжатая версия.

В активный контекст модели вместо полного исходного сообщения может
попадать его сжатая версия.

Сжатая версия является редактируемой.

Пользователь может:

- создать её вручную;
- попросить LLM автоматически сжать сообщение;
- отредактировать результат LLM;
- сделать выжимку подробнее;
- сделать её короче;
- временно вернуть оригинал в активный контекст;
- полностью отказаться от текущей сжатой версии и создать новую.

Оригинал при этом всегда сохраняется отдельно.


3. PROJECT CONTEXT — постоянный контекст проекта

Каждая рабочая папка / проект имеет отдельный небольшой файл
контекста проекта.

Этот контекст общий для ВСЕХ чатов, созданных внутри данного проекта.

PROJECT CONTEXT содержит только наиболее важную информацию:

- что представляет собой проект;
- текущую архитектуру;
- важные принятые решения;
- существующие функции и возможности;
- ключевые ограничения;
- важные пути и файлы;
- договорённости пользователя и агента;
- текущие цели;
- отменённые или заменённые решения, если это необходимо для понимания;
- другие факты, потеря которых может привести к неправильным действиям.

Это не полная документация проекта.

Это небольшая рабочая выжимка, необходимая LLM для понимания текущего
состояния проекта.


============================================================
2. PROJECT CONTEXT ОБЯЗАТЕЛЕН ДЛЯ ВСЕХ ЧАТОВ ПРОЕКТА
============================================================

Перед каждым новым пользовательским запросом / RUN система должна
загружать актуальную версию PROJECT CONTEXT с диска.

Таким образом любой новый чат в папке проекта сразу знает основные
решения и текущее состояние проекта.

Нельзя полагаться только на то, что модель когда-то уже прочитала этот
контекст.

Файл PROJECT CONTEXT должен перечитываться при каждом новом RUN, чтобы:

- пользователь мог исправить его вручную;
- другой чат мог внести утверждённое изменение;
- изменения сразу становились доступны всем чатам проекта;
- модель не продолжала работать со старой копией контекста.


============================================================
3. PROJECT CONTEXT НЕ ДОЛЖЕН АВТОМАТИЧЕСКИ ПЕРЕПИСЫВАТЬСЯ LLM
============================================================

LLM может обнаружить, что PROJECT CONTEXT устарел или требует дополнения.

Например:

- появилось новое важное решение;
- старая архитектура была заменена;
- изменился путь;
- добавлена новая фундаментальная функция;
- найден конфликт между текущей работой и PROJECT CONTEXT;
- содержащаяся в контексте информация больше не соответствует реальности.

В этом случае LLM НЕ должна молча переписывать PROJECT CONTEXT.

Она должна создать ПРЕДЛОЖЕНИЕ ОБНОВЛЕНИЯ КОНТЕКСТА.

Предложение должно содержать:

- что предлагается добавить;
- что предлагается изменить;
- что предлагается удалить как устаревшее;
- почему агент считает изменение необходимым.

Пользователь получает три варианта:

- ПРИНЯТЬ;
- ОТРЕДАКТИРОВАТЬ И ПРИНЯТЬ;
- ОТКЛОНИТЬ.

Только после подтверждения пользователя изменение становится частью
PROJECT CONTEXT.

Это принципиальное правило.

PROJECT CONTEXT является совместно поддерживаемой памятью пользователя
и LLM, но окончательный контроль принадлежит пользователю.


============================================================
4. КОНТРОЛЬ АКТУАЛЬНОСТИ PROJECT CONTEXT
============================================================

В системной инструкции агента должно быть закреплено:

"При работе постоянно сопоставляй текущую задачу с PROJECT CONTEXT.

Если обнаружено новое фундаментальное решение, изменение существующего
решения, устаревшая информация или конфликт с PROJECT CONTEXT —
не изменяй контекст самостоятельно.

Сообщи пользователю и предложи конкретное обновление."

Таким образом обязанность следить за контекстом лежит не только на
пользователе.

LLM также участвует в поддержании его актуальности.


============================================================
5. ID ЧАТОВ И СООБЩЕНИЙ
============================================================

Каждый чат получает уникальный постоянный ID.

Например:

chat_0001
chat_0002
chat_0003

Каждое сообщение внутри чата получает собственный последовательный ID.

Например:

msg_000001
msg_000002
msg_000003

Полный идентификатор сообщения:

chat_0001:msg_000001
chat_0001:msg_000002
chat_0002:msg_000001

ID никогда не меняется после создания сообщения.

Это позволяет независимо хранить:

- оригинал сообщения;
- его текущую сжатую версию;
- предыдущие версии сжатия;
- метаданные;
- состояние использования сообщения в активном контексте.


============================================================
6. СТРУКТУРА ХРАНЕНИЯ
============================================================

Пример структуры проекта:

project/

    context/
        project_context.md
        metadata.json
        history/

    chats/

        chat_0001/
            metadata.json

            messages/
                msg_000001.json
                msg_000002.json
                msg_000003.json

            summaries/
                msg_000001.md
                msg_000002.md

        chat_0002/
            metadata.json
            messages/
            summaries/


messages/msg_000001.json хранит исходное сообщение.

Например:

{
    "id": "chat_0001:msg_000001",
    "chat_id": "chat_0001",
    "message_id": "msg_000001",
    "role": "user",
    "created_at": "...",
    "original_text": "...",
    "active_representation": "raw"
}


Если для сообщения создана сжатая версия:

summaries/msg_000001.md

Она содержит только рабочую выжимку.

RAW-оригинал при этом остаётся неизменным.


============================================================
7. ДЕЙСТВИЯ НАД СООБЩЕНИЕМ В ИНТЕРФЕЙСЕ
============================================================

Возле сообщения желательно предусмотреть действия:

- Редактировать рабочую версию;
- Сжать при помощи LLM;
- Сжать ещё сильнее;
- Сделать подробнее;
- Показать оригинал;
- Использовать оригинал в контексте;
- Использовать сжатую версию в контексте;
- Создать новую выжимку из оригинала.

Особенно важно различать:

ОРИГИНАЛ
и
РАБОЧЕЕ ПРЕДСТАВЛЕНИЕ.

Редактирование текста, отображаемого в рабочем контексте, не должно
изменять исходное сообщение.


============================================================
8. РУЧНОЕ РЕДАКТИРОВАНИЕ СЖАТОЙ ВЕРСИИ
============================================================

LLM может ошибиться при сжатии.

Поэтому пользователь имеет право открыть созданную выжимку и вручную
изменить её.

Например:

LLM создала:

"Обсуждалось изменение интерфейса."

Пользователь может исправить на:

"Принято решение перенести настройки цветов в верхний блок ИНТЕРФЕЙС.
Лог действий — зелёный, пользователь — белый, ответ Ultra —
светло-синий. Синий разделитель RUN не менять."

Именно исправленная версия после этого используется как активный
контекст.

Оригинальный разговор остаётся нетронутым.


============================================================
9. АКТИВНЫЙ КОНТЕКСТ МОДЕЛИ
============================================================

ACTIVE CONTEXT не является простым копированием всей истории чата.

Он собирается системой перед запросом.

Пример:

ACTIVE CONTEXT =

SYSTEM INSTRUCTIONS
+
PROJECT CONTEXT
+
сжатые старые сообщения
+
при необходимости развёрнутые старые оригиналы
+
свежие несжатые сообщения
+
текущий запрос пользователя
+
служебный контекст tools


Таким образом:

RAW HISTORY ≠ ACTIVE CONTEXT

и

PROJECT CONTEXT ≠ CHAT HISTORY


Это три разные сущности.


============================================================
10. СВЕЖИЕ СООБЩЕНИЯ
============================================================

Новые сообщения некоторое время желательно оставлять в полном виде.

Не имеет смысла сразу после каждого ответа автоматически сжимать всё.

Пользователь должен видеть нормальный живой разговор.

Сжатие прежде всего предназначено для старых или слишком больших
фрагментов.


============================================================
11. АВТОМАТИЧЕСКОЕ СЖАТИЕ НЕ ДОЛЖНО УНИЧТОЖАТЬ КОНТРОЛЬ
============================================================

В будущем система может предлагать автоматическое сжатие при приближении
к лимиту контекста.

Однако автоматическое сжатие не означает автоматическую потерю данных.

Даже если система сама создала summary:

- оригинал сохраняется;
- summary можно открыть;
- summary можно исправить;
- summary можно заменить;
- оригинал можно вернуть в активный контекст.


============================================================
12. ВЕРСИОНИРОВАНИЕ ВЫЖИМОК
============================================================

Желательно сохранять предыдущие версии PROJECT CONTEXT и важных summary.

Например:

context/history/project_context_0001.md
context/history/project_context_0002.md

Это позволит восстановиться после неудачной ручной или LLM-правки.

Для message summary позднее можно использовать тот же принцип.


============================================================
13. UI PROJECT CONTEXT
============================================================

В интерфейсе должен существовать отдельный способ открыть PROJECT CONTEXT.

Пользователь должен иметь возможность:

- посмотреть его;
- редактировать;
- сохранить;
- увидеть его размер;
- увидеть последнюю ревизию;
- увидеть предложения LLM по обновлению.

Если агент считает PROJECT CONTEXT устаревшим, интерфейс должен заметно
сообщить об этом пользователю.

Например:

КОНТЕКСТ ПРОЕКТА ТРЕБУЕТ ВНИМАНИЯ

Предлагается изменить:
...

[Принять]
[Редактировать]
[Отклонить]

Для таких уведомлений можно использовать отдельное заметное оформление,
например красный или другой специальный цвет.


============================================================
14. ГЛАВНЫЕ ПРИНЦИПЫ
============================================================

15. Оригинал сообщения никогда не уничтожается сжатием.

16. Каждое сообщение имеет постоянный ID.

17. Каждый чат имеет постоянный ID.

18. Сжатая версия сообщения является отдельной сущностью.

19. Сжатая версия редактируется пользователем независимо от оригинала.

20. PROJECT CONTEXT общий для всех чатов одного проекта.

21. PROJECT CONTEXT перечитывается перед каждым новым пользовательским RUN.

22. LLM обязана следить за актуальностью PROJECT CONTEXT.

23. LLM не изменяет PROJECT CONTEXT без подтверждения пользователя.

24. Пользователь может принять, исправить или отклонить предложение LLM.

25. Активный контекст модели собирается из нескольких источников,
    а не равен полной истории чата.

26. RAW HISTORY всегда остаётся источником истины.

27. Пользователь должен видеть и понимать, что сейчас находится
    в активном контексте.


============================================================
ГЛАВНАЯ ИДЕЯ
============================================================

Контекст должен быть не скрытой внутренней памятью LLM, а управляемой
частью проекта.

Пользователь и агент совместно поддерживают небольшую актуальную память
проекта.

При этом полная исходная история сохраняется отдельно и никогда
не уничтожается.
