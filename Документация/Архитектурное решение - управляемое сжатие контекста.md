
============================================================
ТЕРМИНЫ СИСТЕМЫ КОНТЕКСТА
============================================================

WORKSPACE

Рабочее пространство / проект, привязанный к конкретной папке.

Один WORKSPACE может содержать множество CHAT.

WORKSPACE является верхним уровнем принадлежности:

- PROJECT CONTEXT;
- чатов;
- сообщений;
- summaries;
- предложений обновления контекста;
- других данных системы контекста.


PROJECT CONTEXT

Общий постоянный контекст WORKSPACE.

Доступен всем чатам данного WORKSPACE.

Содержит небольшую, актуальную, контролируемую пользователем
выжимку наиболее важных сведений о проекте.


CHAT

Отдельная ветка разговора внутри WORKSPACE.

Каждый CHAT имеет собственную историю сообщений и собственный
рабочий контекст разговора, но одновременно получает общий
PROJECT CONTEXT своего WORKSPACE.


RAW MESSAGE

Неизменяемый оригинал сообщения.

Это исходный текст, который реально написал пользователь,
LLM или система.

RAW MESSAGE является источником истины и никогда не уничтожается
при сжатии.


WORKING REPRESENTATION

Текст сообщения, реально используемый при сборке ACTIVE CONTEXT.

WORKING REPRESENTATION может быть:

- RAW;
- SUMMARY.


MESSAGE SUMMARY

Сжатая редактируемая версия конкретного RAW MESSAGE.

MESSAGE SUMMARY существует отдельно от оригинала.

Изменение MESSAGE SUMMARY никогда не изменяет RAW MESSAGE.


ACTIVE CONTEXT

Итоговый набор данных, реально отправляемый модели
при конкретном запросе / RUN.

ACTIVE CONTEXT не равен полной истории чата.


COMPRESSION PROPOSAL

Черновая версия сжатия, созданная LLM.

COMPRESSION PROPOSAL ещё не является активной сжатой версией.

Она должна быть:

- принята пользователем;
- отредактирована и принята;
- либо отклонена.


COMPRESSION PROVIDER

LLM или другой сервис, используемый специально для создания
COMPRESSION PROPOSAL.

COMPRESSION PROVIDER не обязан совпадать с основной моделью,
которая выполняет пользовательскую задачу.


PERSISTENT STORAGE

Постоянное хранилище контекста, которое переживает закрытие
и повторный запуск программы.

Основная переносимая часть persistent storage принадлежит WORKSPACE
и должна иметь возможность перемещаться между компьютерами
вместе с проектом.


============================================================
ЦЕЛЬ
============================================================

Контекст модели не должен быть непрозрачным, бесконтрольно разрастаться
или автоматически схлопываться так, чтобы пользователь терял важные данные.

Система должна одновременно обеспечивать:

- полное сохранение исходной истории;
- возможность уменьшать ACTIVE CONTEXT;
- ручной контроль пользователя над сжатием;
- возможность исправлять ошибки LLM в созданной выжимке;
- общий постоянный PROJECT CONTEXT для всех чатов WORKSPACE;
- переносимость истории и контекста между компьютерами;
- возможность использовать разные LLM для разных операций;
- прозрачность: пользователь должен понимать, какой текст
  сейчас реально используется моделью как контекст.


============================================================
1. ТРИ ОСНОВНЫХ УРОВНЯ КОНТЕКСТА
============================================================

Система использует три основных слоя.


------------------------------------------------------------
1.1. RAW HISTORY — исходная история
------------------------------------------------------------

Каждое сообщение пользователя, модели, системное сообщение
и другой значимый фрагмент разговора сохраняется
в исходном виде.

RAW HISTORY:

- никогда автоматически не переписывается;
- никогда не удаляется при сжатии;
- является источником истины;
- всегда может быть открыт пользователем;
- позволяет восстановить первоначальную формулировку сообщения;
- позволяет повторно создать другую сжатую версию;
- должна сохраняться сразу после появления сообщения,
  а не только при закрытии приложения.

Сжатие изменяет не RAW HISTORY, а только WORKING REPRESENTATION,
используемое при сборке ACTIVE CONTEXT.


------------------------------------------------------------
1.2. CHAT WORKING CONTEXT — рабочий контекст конкретного чата
------------------------------------------------------------

Для большого или малозначимого сообщения может создаваться
MESSAGE SUMMARY.

В ACTIVE CONTEXT вместо полного RAW MESSAGE может попадать
его MESSAGE SUMMARY.

Сжатая версия является редактируемой.

Пользователь может:

- создать summary при помощи LLM;
- создать рабочую версию вручную;
- отредактировать результат LLM;
- пересжать сообщение;
- сделать выжимку подробнее;
- сделать выжимку короче;
- открыть оригинал;
- снова переключить сообщение на RAW;
- сохранить старый summary для возможного дальнейшего использования.

Оригинал при этом всегда сохраняется.


------------------------------------------------------------
1.3. PROJECT CONTEXT — постоянный контекст WORKSPACE
------------------------------------------------------------

Каждый WORKSPACE имеет отдельный PROJECT CONTEXT.

PROJECT CONTEXT общий для ВСЕХ CHAT данного WORKSPACE.

Он содержит только наиболее важную информацию:

- что представляет собой проект;
- текущую архитектуру;
- важные принятые решения;
- существующие функции и возможности;
- ключевые ограничения;
- важные пути и файлы;
- договорённости пользователя и агента;
- текущие цели;
- текущий этап работы;
- отменённые или заменённые решения,
  если это необходимо для правильного понимания;
- другие факты, потеря которых может привести
  к неправильным действиям.

PROJECT CONTEXT — не полная документация проекта.

Это небольшая рабочая память проекта,
которую должны понимать одновременно:

- пользователь;
- основная LLM;
- другие LLM, работающие внутри данного WORKSPACE.


============================================================
2. PROJECT CONTEXT ОБЯЗАТЕЛЕН ДЛЯ ВСЕХ ЧАТОВ WORKSPACE
============================================================

Перед каждым новым пользовательским запросом / RUN
система должна загружать актуальную версию PROJECT CONTEXT.

Таким образом новый CHAT внутри WORKSPACE сразу получает
основные сведения о проекте, даже если этот CHAT был создан только что.

Нельзя полагаться только на то, что модель когда-то уже видела
PROJECT CONTEXT.

PROJECT CONTEXT должен перечитываться перед каждым новым RUN.

Это необходимо, чтобы:

- пользователь мог изменить его вручную;
- другой CHAT мог инициировать утверждённое изменение;
- изменения сразу становились доступны остальным CHAT;
- модель не продолжала работать со старой копией контекста;
- новый CHAT сразу понимал текущее состояние проекта.


============================================================
3. PROJECT CONTEXT НЕ ПЕРЕПИСЫВАЕТСЯ LLM САМОСТОЯТЕЛЬНО
============================================================

LLM обязана следить за актуальностью PROJECT CONTEXT.

Например, она может обнаружить:

- новое фундаментальное решение;
- изменение старой архитектуры;
- новый важный путь;
- новую функцию;
- отмену ранее принятого решения;
- конфликт между текущей работой и PROJECT CONTEXT;
- устаревшую информацию.

Однако LLM НЕ должна молча изменять PROJECT CONTEXT.

Вместо этого она создаёт предложение обновления.

Предложение должно содержать:

ДОБАВИТЬ:
...

ИЗМЕНИТЬ:
...

УДАЛИТЬ КАК УСТАРЕВШЕЕ:
...

ПРИЧИНА:
...


Пользователь получает варианты:

[Принять]

[Редактировать и принять]

[Отклонить]


Только после явного подтверждения пользователя изменение
становится частью PROJECT CONTEXT.

PROJECT CONTEXT является совместно поддерживаемой памятью
пользователя и LLM.

Окончательный контроль принадлежит пользователю.


============================================================
4. КОНТРОЛЬ АКТУАЛЬНОСТИ PROJECT CONTEXT
============================================================

В системной инструкции агента должно быть закреплено примерно следующее:

"При работе постоянно сопоставляй текущую задачу с PROJECT CONTEXT.

Если обнаружено новое фундаментальное решение,
изменение существующего решения,
устаревшая информация
или конфликт с PROJECT CONTEXT —
не изменяй PROJECT CONTEXT самостоятельно.

Сообщи пользователю и предложи конкретное обновление."


Таким образом обязанность следить за PROJECT CONTEXT
лежит не только на пользователе.

LLM также обязана участвовать в поддержании его актуальности.


============================================================
5. WORKSPACE, CHAT И ID
============================================================

Каждый WORKSPACE получает постоянный внутренний ID.

Например:

workspace_id:
ws_<unique_id>


Каждый CHAT получает постоянный внутренний ID.

Например:

chat_<unique_id>


Каждое сообщение получает постоянный ID.

Например:

msg_<unique_id>


Полный логический адрес сообщения связывает:

workspace_id
+
chat_id
+
message_id


Например:

WORKSPACE:
ws_A

CHAT:
chat_B

MESSAGE:
msg_C


Внутренние ID не должны зависеть только от последовательной нумерации.

Причина:

один и тот же WORKSPACE в будущем может использоваться
на нескольких компьютерах.

Если два компьютера независимо создадут:

msg_000001

возникнет конфликт.

Поэтому внутренний постоянный ID должен быть глобально уникальным.

Допустимые варианты реализации:

- UUID;
- UUIDv7;
- ULID;
- другой механизм уникальных ID.

Отдельно UI при желании может показывать человеку удобные номера:

Чат 1
Сообщение 35

но это не должно быть настоящим первичным ID.


ID никогда не изменяется после создания сущности.


============================================================
6. ПЕРЕНОСИМОЕ ХРАНИЛИЩЕ WORKSPACE
============================================================

Контекст проекта должен иметь возможность перемещаться
между компьютерами вместе с WORKSPACE.

Поэтому основное переносимое хранилище не должно существовать
только в AppData конкретного компьютера.

Внутри WORKSPACE должна существовать специальная
служебная директория системы.

Предварительное имя:

.ultra/


Пример:

project/

    .ultra/

        workspace.json

        project_context.md

        project_context_history/

        chats/

            chat_<id>/

                metadata.json

                messages/

                    msg_<id>.json
                    msg_<id>.json

                summaries/

                    msg_<id>/

                        revision_0001.json
                        revision_0002.json

        proposals/

        metadata/


Точное внутреннее устройство может быть уточнено
во время реализации.

Главный принцип:

данные должны быть:

- структурированными;
- переносимыми;
- адресуемыми по постоянным ID;
- восстанавливаемыми;
- пригодными для Git.


============================================================
7. RAW MESSAGE ХРАНИТСЯ ОТДЕЛЬНО И НЕИЗМЕНЯЕМО
============================================================

RAW MESSAGE сохраняется сразу после создания.

Пример логического содержимого:

{
    "workspace_id": "...",
    "chat_id": "...",
    "message_id": "...",
    "role": "user",
    "created_at": "...",
    "original_text": "...",
    "active_representation": "raw"
}


Если пользователь позже создаёт MESSAGE SUMMARY,
original_text не изменяется.

Система создаёт связанную отдельную сущность SUMMARY.

После принятия summary состояние может измениться:

active_representation = "summary"


Если пользователь восстанавливает оригинал:

active_representation = "raw"


При этом сам summary не обязан удаляться.

Он может остаться в persistent storage.


============================================================
8. НИКАКОГО "СОХРАНИМ ВСЁ ПРИ ЗАКРЫТИИ"
============================================================

Система не должна рассчитывать на штатное закрытие окна.

Важные данные должны сохраняться сразу после события.

Например:

пришло сообщение пользователя
→ сразу сохранить RAW MESSAGE

пришёл ответ LLM
→ сразу сохранить RAW MESSAGE

пользователь принял summary
→ сразу сохранить новую ревизию summary
→ сразу изменить active_representation

пользователь изменил PROJECT CONTEXT
→ сразу сохранить новую утверждённую версию

создан CHAT
→ сразу сохранить его metadata

переименован CHAT
→ сразу сохранить изменение


Если приложение аварийно завершится через секунду после операции,
уже подтверждённые данные не должны потеряться.


============================================================
9. JSON / MARKDOWN И SQLITE
============================================================

Переносимые данные WORKSPACE являются источником истины.

Для машинных сущностей предпочтительно использовать
структурированный формат JSON.

Например:

- metadata;
- CHAT;
- RAW MESSAGE;
- SUMMARY metadata;
- состояния;
- ID;
- ревизии;
- предложения.


Для PROJECT CONTEXT желательно использовать человекочитаемый Markdown:

.ultra/project_context.md


Это позволит:

- читать PROJECT CONTEXT вручную;
- редактировать его при необходимости;
- просматривать изменения через Git;
- переносить его между компьютерами.


SQLite при этом может использоваться дополнительно.

Например:

%LOCALAPPDATA%\GigaChatUltra\data\...


Назначение SQLite:

- быстрый локальный индекс;
- быстрый поиск;
- ускорение загрузки;
- кэш метаданных;
- построение связей;
- служебные запросы.


SQLite НЕ должна быть единственным источником истины.

Если локальная SQLite:

- отсутствует;
- устарела;
- удалена;
- находится на другом компьютере;

приложение должно иметь возможность восстановить локальное состояние
из переносимых данных `.ultra/` текущего WORKSPACE.


============================================================
10. РАБОТА НА ДРУГОМ КОМПЬЮТЕРЕ
============================================================

Предполагаемый сценарий:

1. Пользователь работает с WORKSPACE на компьютере A.

2. Контекст, CHAT, RAW MESSAGE и SUMMARY сразу сохраняются
   внутри переносимого слоя `.ultra/`.

3. Пользователь синхронизирует репозиторий привычным способом.

4. На компьютере B он получает актуальную версию WORKSPACE.

5. GigaChat Ultra Local Agent открывает WORKSPACE.

6. Система обнаруживает `.ultra/`.

7. Читает workspace metadata.

8. Читает PROJECT CONTEXT.

9. Восстанавливает список CHAT.

10. При необходимости создаёт или обновляет локальный SQLite-кэш.

11. Работа продолжается с того же состояния.


Таким образом новый компьютер не должен зависеть
от старой AppData другого компьютера.


============================================================
11. РАБОТА НА НЕСКОЛЬКИХ КОМПЬЮТЕРАХ И КОНФЛИКТЫ
============================================================

До появления центрального сервера пользователь должен сам
синхронизировать состояние проекта между компьютерами.

Если пользователь независимо продолжил работу
на двух компьютерах без синхронизации,
могут появиться две ветки истории.

Это нормальная проблема распределённой работы,
а не специфическая проблема LLM.

Для уменьшения конфликтов:

- RAW MESSAGE должны иметь глобально уникальные ID;
- желательно хранить сообщения отдельными объектами / файлами;
- существующий RAW MESSAGE не должен переписываться;
- новые сообщения в основном добавляются;
- PROJECT CONTEXT и другие редактируемые общие документы
  требуют более внимательного разрешения конфликтов.


В будущем эта проблема может быть устранена
центральным серверным хранилищем.

Например:

пользователь авторизуется
→ клиент синхронизируется с сервером
→ любой компьютер получает единое актуальное состояние

Но серверная синхронизация является отдельным будущим этапом.


============================================================
12. СЛУЖЕБНАЯ ПАПКА КОНТЕКСТА ДОЛЖНА БЫТЬ ЗАЩИЩЕНА
============================================================

Несмотря на то, что `.ultra/` находится внутри WORKSPACE,
обычный file-agent не должен иметь право бесконтрольно
изменять системную память проекта.

Работа с контекстом должна идти через отдельный
контролируемый программный слой.

Например:

Context Storage API


Обычный инструмент:

write_file

не должен использоваться LLM для самостоятельной
перезаписи RAW HISTORY или PROJECT CONTEXT.


Для контекста должны существовать специальные операции,
которые соблюдают правила:

- RAW MESSAGE неизменяем;
- PROJECT CONTEXT требует подтверждения пользователя;
- summary требует подтверждения пользователя;
- ревизии не теряются;
- изменение логируется.


============================================================
13. ДЕЙСТВИЯ НАД СООБЩЕНИЕМ В UI
============================================================

Возле сообщения должны существовать три основные операции:

[Сжать LLM]

[Редактировать]

[Оригинал]


------------------------------------------------------------
13.1. Сжать LLM
------------------------------------------------------------

Система получает RAW MESSAGE по его постоянному ID.

RAW MESSAGE передаётся настроенному COMPRESSION PROVIDER.

LLM создаёт COMPRESSION PROPOSAL.

Результат НЕ заменяет текущее сообщение автоматически.

Пользователь получает окно:

Предлагаемая сжатая версия:

...

[Принять]

[Редактировать и принять]

[Отклонить]


Только после явного подтверждения summary становится
WORKING REPRESENTATION.


------------------------------------------------------------
13.2. Редактировать
------------------------------------------------------------

Пользователь может вручную изменить рабочую версию сообщения.

Если существует MESSAGE SUMMARY,
редактируется именно summary.

RAW MESSAGE никогда не изменяется.


Если summary ещё нет, UI может предложить создать
ручную рабочую версию на основе оригинала.


------------------------------------------------------------
13.3. Оригинал
------------------------------------------------------------

Кнопка:

[Оригинал]

не должна сразу восстанавливать RAW.

Сначала она открывает окно просмотра.


Пример:

--------------------------------------------------

Исходное сообщение

ID:
...

Полный первоначальный текст:

...

[Восстановить в контекст]

[Закрыть]

--------------------------------------------------


Если пользователь нажимает:

[Закрыть]

ничего не меняется.

Если пользователь нажимает:

[Восстановить в контекст]

active_representation переключается на RAW.


MESSAGE SUMMARY при этом может сохраниться
для будущего повторного использования.


============================================================
14. ДОПОЛНИТЕЛЬНЫЕ ОПЕРАЦИИ С SUMMARY
============================================================

Дополнительные действия могут существовать
внутри интерфейса сжатия:

- пересжать подробнее;
- пересжать короче;
- создать новую версию;
- сравнить с оригиналом;
- сравнить с предыдущей summary;
- отменить последнее изменение.

Эти функции не обязательно должны занимать отдельные
постоянные кнопки возле каждого сообщения.


============================================================
15. COMPRESSION PROVIDER
============================================================

Сжатие сообщений не должно быть жёстко привязано
к основной LLM.

Для операции сжатия вводится абстракция:

COMPRESSION PROVIDER


Основная LLM может выполнять сложную пользовательскую задачу,
а другая, более дешёвая модель — создавать summaries.


Первоначальный вариант:

GigaChat Lite


Например:

Основная работа:
GigaChat Ultra

Сжатие сообщения:
GigaChat Lite


Это позволяет расходовать дорогую модель только там,
где действительно требуется её уровень рассуждения.


Однако архитектура не должна быть привязана только к GigaChat.

В будущем COMPRESSION PROVIDER может быть:

- GigaChat Lite;
- GigaChat Pro;
- другая облачная LLM;
- локальная LLM;
- специализированная модель сжатия.


Кнопка:

[Сжать LLM]

обращается не к конкретному названию модели,
а к выбранному COMPRESSION PROVIDER.


============================================================
16. LLM НЕ ИМЕЕТ ПРАВА САМА ПРИНИМАТЬ SUMMARY
============================================================

Независимо от выбранного COMPRESSION PROVIDER
действует одно фундаментальное правило:

LLM создаёт только предложение.

COMPRESSION PROPOSAL
↓
Пользователь проверяет
↓
Пользователь принимает / редактирует / отклоняет
↓
Только после этого появляется утверждённый MESSAGE SUMMARY


LLM не должна самостоятельно:

- уничтожать RAW MESSAGE;
- заменять RAW на summary;
- делать summary активным;
- изменять утверждённый PROJECT CONTEXT.


============================================================
17. РУЧНОЕ РЕДАКТИРОВАНИЕ SUMMARY
============================================================

LLM может ошибиться при сжатии.

Например она может создать:

"Обсуждалось изменение интерфейса."


Пользователь имеет право исправить это на:

"Принято решение перенести настройки цветов
в верхний блок ИНТЕРФЕЙС.
Лог действий — зелёный,
пользователь — белый,
ответ Ultra — светло-синий.
Синий разделитель RUN не менять."


Именно исправленная версия после подтверждения
становится WORKING REPRESENTATION.

RAW MESSAGE остаётся нетронутым.


============================================================
18. ВЕРСИОНИРОВАНИЕ SUMMARY
============================================================

MESSAGE SUMMARY желательно хранить по ревизиям.

Например:

revision 1
revision 2
revision 3


Каждая ревизия может содержать:

- message_id;
- номер ревизии;
- текст;
- дату создания;
- источник;
- модель, создавшую proposal;
- признак ручного редактирования;
- статус.


Это позволит:

- восстановить старую summary;
- сравнить версии;
- исправить ошибочное сжатие;
- увидеть, что именно изменилось.


RAW MESSAGE версионировать не требуется,
так как он является неизменяемым источником истины.


============================================================
19. ВЕРСИОНИРОВАНИЕ PROJECT CONTEXT
============================================================

PROJECT CONTEXT также желательно хранить по ревизиям.

Каждое утверждённое изменение создаёт новую ревизию.

Например:

revision 12
revision 13
revision 14


Это позволит восстановить PROJECT CONTEXT
после ошибочного изменения.

Для ревизии желательно хранить:

- workspace_id;
- revision;
- текст;
- время;
- источник;
- описание причины изменения;
- при необходимости ID предложения LLM.


============================================================
20. UI PROJECT CONTEXT
============================================================

PROJECT CONTEXT должен быть явно доступен
из интерфейса WORKSPACE.

Рядом с выбранным Workspace должна находиться
отдельная кнопка.

Например:

[Контекст проекта]


При её нажатии открывается окно PROJECT CONTEXT.


Пользователь должен иметь возможность:

- прочитать PROJECT CONTEXT;
- вручную его отредактировать;
- сохранить утверждённые изменения;
- увидеть размер;
- увидеть номер последней ревизии;
- увидеть предложения LLM;
- при необходимости посмотреть предыдущие ревизии.


PROJECT CONTEXT общий для всех CHAT данного WORKSPACE.


============================================================
21. ПРЕДЛОЖЕНИЯ LLM ПО PROJECT CONTEXT
============================================================

Если агент считает PROJECT CONTEXT устаревшим,
интерфейс должен заметно сообщить об этом пользователю.

Например:

КОНТЕКСТ ПРОЕКТА ТРЕБУЕТ ВНИМАНИЯ


ДОБАВИТЬ:
...


ИЗМЕНИТЬ:
...


УДАЛИТЬ КАК УСТАРЕВШЕЕ:
...


ПРИЧИНА:
...


[Принять]

[Редактировать]

[Отклонить]


Для таких уведомлений может использоваться
отдельное заметное визуальное оформление.


============================================================
22. ACTIVE CONTEXT
============================================================

ACTIVE CONTEXT не является полной историей чата.

Он собирается системой перед конкретным запросом.


Предварительная структура:

SYSTEM INSTRUCTIONS
+
PROJECT CONTEXT
+
WORKING REPRESENTATION предыдущих сообщений текущего CHAT
+
при необходимости специально развёрнутые RAW MESSAGE
+
свежие несжатые сообщения
+
текущий пользовательский запрос
+
служебный контекст tools


Таким образом:

RAW HISTORY ≠ ACTIVE CONTEXT

PROJECT CONTEXT ≠ CHAT HISTORY

MESSAGE SUMMARY ≠ RAW MESSAGE


Это разные сущности.


============================================================
23. СВЕЖИЕ СООБЩЕНИЯ
============================================================

Не имеет смысла автоматически сжимать каждое сообщение
сразу после появления.

По умолчанию новые сообщения сохраняются как RAW.

Сжатие выполняется по явному действию пользователя:

[Сжать LLM]


В будущем система может предлагать сжатие
при росте ACTIVE CONTEXT.

Однако предложение не должно автоматически
заменять оригинал.


============================================================
24. АВТОМАТИЧЕСКОЕ СЖАТИЕ В БУДУЩЕМ
============================================================

В будущем может появиться режим:

"Контекст приближается к лимиту.
Предлагается сжать следующие сообщения."


Но даже в таком режиме:

- RAW сохраняется;
- LLM создаёт proposal;
- пользователь может проверить summary;
- summary можно отредактировать;
- summary можно отклонить;
- оригинал всегда доступен.


То есть автоматизация не должна уничтожать
ручной контроль пользователя.


============================================================
25. CHAT
============================================================

Один WORKSPACE может иметь множество CHAT.

Каждый CHAT имеет:

- постоянный chat_id;
- название;
- дату создания;
- дату последнего изменения;
- историю RAW MESSAGE;
- MESSAGE SUMMARY;
- рабочие состояния сообщений;
- метаданные.


Переключение между CHAT:

- не меняет WORKSPACE;
- не меняет PROJECT CONTEXT;
- меняет текущую историю разговора;
- меняет CHAT WORKING CONTEXT.


Новый CHAT:

- получает новый chat_id;
- начинает новую историю;
- получает общий PROJECT CONTEXT текущего WORKSPACE.


============================================================
26. ОТОБРАЖЕНИЕ ЧАТА И РЕАЛЬНЫЙ ACTIVE CONTEXT — НЕ ОДНО И ТО ЖЕ
============================================================

UI может показывать пользователю полную историю разговора.

При этом модель может получать только:

- SUMMARY некоторых сообщений;
- RAW других сообщений;
- PROJECT CONTEXT;
- текущий запрос.


Поэтому необходимо явно различать:

ИСТОРИЮ ДЛЯ ПОЛЬЗОВАТЕЛЯ

и

ACTIVE CONTEXT ДЛЯ МОДЕЛИ


Пользователь должен иметь возможность понять,
какое представление сообщения сейчас активно:

RAW

или

SUMMARY.


============================================================
27. ПРОЗРАЧНОСТЬ ACTIVE CONTEXT
============================================================

В будущем интерфейс должен показывать
состояние ACTIVE CONTEXT.

Например:

- размер;
- количество сообщений;
- сколько RAW;
- сколько SUMMARY;
- размер PROJECT CONTEXT;
- приблизительный или точный token usage.


Конкретная схема token budget будет определена
отдельным архитектурным решением.

На данном этапе точные лимиты токенов
не закрепляются.


============================================================
28. РАЗНЫЕ LLM ДЛЯ РАЗНЫХ ОПЕРАЦИЙ
============================================================

Архитектура должна допускать,
что разные операции выполняют разные модели.

Например:

основная сложная задача
→ Ultra

сжатие сообщения
→ Lite

простая классификация
→ дешёвая модель

локальная служебная операция
→ Local LLM


На данном этапе подробно проектируется
только COMPRESSION PROVIDER.

Полная система маршрутизации разных операций
между моделями будет рассмотрена отдельно.


============================================================
29. БУДУЩИЙ ЦЕНТРАЛЬНЫЙ СЕРВЕР
============================================================

Текущая архитектура должна работать полностью локально.

Однако в будущем может появиться серверная синхронизация.

Тогда:

пользователь авторизуется
↓
WORKSPACE связывается с серверным аккаунтом
↓
контекст и история синхронизируются
↓
любой компьютер получает актуальное состояние


При появлении сервера переносимый локальный слой
может остаться:

- локальным кэшем;
- offline storage;
- резервной копией;
- экспортируемым представлением проекта.


Серверная синхронизация является отдельным
будущим этапом разработки.


============================================================
30. ОСНОВНЫЕ ПРИНЦИПЫ
============================================================

31. RAW MESSAGE никогда не уничтожается сжатием.

32. RAW MESSAGE после создания не переписывается.

33. Каждое сообщение имеет постоянный глобально уникальный ID.

34. Каждый CHAT имеет постоянный уникальный ID.

35. Каждый WORKSPACE имеет постоянный ID.

36. MESSAGE SUMMARY является отдельной сущностью.

37. MESSAGE SUMMARY можно редактировать независимо от RAW MESSAGE.

38. PROJECT CONTEXT общий для всех CHAT одного WORKSPACE.

39. PROJECT CONTEXT перечитывается перед каждым новым RUN.

40. LLM обязана следить за актуальностью PROJECT CONTEXT.

41. LLM не изменяет PROJECT CONTEXT без подтверждения пользователя.

42. Пользователь может принять, исправить или отклонить предложение LLM.

43. LLM не активирует MESSAGE SUMMARY без подтверждения пользователя.

44. COMPRESSION PROVIDER отделён от основной LLM.

45. Основная переносимая история принадлежит WORKSPACE.

46. Контекст должен переноситься между компьютерами вместе с проектом.

47. Важные данные сохраняются сразу после события,
    а не только при закрытии приложения.

48. Локальная SQLite при её использовании является индексом / кэшем,
    а не единственным источником истины.

49. Потеря локальной SQLite не должна означать потерю истории.

50. Обычный file-agent не должен напрямую переписывать
    внутреннее хранилище контекста.

51. Работа с памятью выполняется через контролируемый Context Storage API.

52. ACTIVE CONTEXT собирается из нескольких источников
    и не равен полной истории CHAT.

53. Пользователь должен видеть и понимать,
    что сейчас находится в ACTIVE CONTEXT.

54. Просмотр RAW MESSAGE не должен автоматически
    восстанавливать его в ACTIVE CONTEXT.

55. Восстановление RAW выполняется только
    явным действием пользователя.

56. Архитектура должна быть готова к будущему использованию
    разных LLM для разных операций.

57. Архитектура должна допускать будущую серверную синхронизацию,
    но не зависеть от неё для локальной работы.


============================================================
ГЛАВНАЯ ИДЕЯ
============================================================

Контекст не должен быть скрытой внутренней памятью LLM.

Контекст является управляемой частью WORKSPACE.


Пользователь и агент совместно поддерживают:

PROJECT CONTEXT

и

CHAT WORKING CONTEXT.


При этом RAW HISTORY всегда остаётся отдельно
и никогда не уничтожается.


Пользователь должен иметь возможность:

увидеть оригинал
↓
увидеть summary
↓
исправить summary
↓
принять или отклонить предложение LLM
↓
вернуть оригинал
↓
понять, что именно сейчас читает модель


WORKSPACE должен сохранять эту память
и иметь возможность переносить её между компьютерами.
