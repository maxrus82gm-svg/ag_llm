## 1. Краткое заключение Астры

**Программу следует оптимизировать, сохранив её архитектурное основание.** Одно ядро Ultra, общие данные, отдельный Ordinary Chat, устойчивый Turn, долговечные обязательства и защита перед физической отправкой — правильные решения. Их замена новым сервером, бюджетным сервисом или хранилищем увеличит путь до результата.

Основная проблема §3а — смешение трёх вещей: пользовательских возможностей, инженерных пакетов и независимых ворот допуска. Двенадцать RM37 — не двенадцать обязательных последовательных задач. Их безопасное укрупнение возможно внутри одного уровня зависимостей; независимую приёмку S2 → S3a → S3b → S3c и общий S13a объединением названий устранить нельзя. Кроме того, S4/C1/C2 сейчас спрятаны в оговорках RM37-07, хотя могут задержать весь выпуск.

Рекомендую совместно проектировать политику, модельные ограничения и формат usage; отдельно принять расширение ledger; затем реализовать защиту всех физических отправок. Учёт, настройки, ограничения чтения и протокольные проверки готовить по собственным зависимостям, с одним владельцем каждого общего файла. После независимого S13a и завершения применимых требований этапов 5–6 — отдельный ограниченный GigaChat-сценарий. Сжатие и память развивать поверх тех же контрактов после MVP. Полноценный Статист не должен блокировать управляемую память.

Это сокращает повторное согласование интерфейсов и ненужное ожидание между независимыми ветками. Число фактических TASK и выигрыш по времени — **UNKNOWN / NEEDS VERIFICATION**: они зависят от объёма устранения FOLLOWUP и приёмки, а не от числа строк roadmap.

Продолжения и прикладные ограничения | S3c после C/S0; S4 проектируется после A, применяется после C; S5 подготовлен после A, runtime после C/S4; S9 после S1/B; C1/C2 после S0 | Перед каждым инструментом/LLM проверяются права и бюджет; Final Audit защищён; read/request caps; сохранение настроек; известные/неизвестные расходы; протокольные негативы. Каждому узлу своё evidence |
| E. Независимый выпуск OFFLINE | Приняты S3c/S4/S5/C1/C2/S9; применимые Stage5 остатки и Windows/изоляция | **S13a независимо ACCEPTED**, общий negative/crash/restart/rollback/UI набор на фиксированной ревизии; применимость A1–A8 прослеживается до канона №20, полный B2 не объявляется завершённым |
| F. Первый live | Приняты этапы 5–6 в требуемом scope, E и точное разрешение пользователя | Один обычный текстовый диалог через принятый transport, сохранённый Turn/RAW/usage и обязательства, reopen/restart без повторного оплаченного запроса |
| G. Развитие | Отдельные назначения после MVP | 09→10, Статист, управляемая Memory; Codex adapter в сохранённом пользовательском приоритете; Blueprint по №43 |

Критический путь на уровне ворот: **свежие S0/S1 → расширенный S2 → расширенный S3a → S3b → S3c → S13a → Stage7**. В точку S13a входят также **S4, S5, C1, C2, S9**; без любого из них путь не открыт. Точный календарный критический путь зависит от длительности боковых веток и пока неизвестен.

S6a может готовиться только после собственных S0/S3b/S3c/S4. **S6b начинается лишь после независимо принятого S13a + S6a** и остальных условий №20. Простому текстовому MVP не следует навязывать завершение всего будущего компилятора S6b/S7/S10/S13b, если используется уже принятый ограниченный сборщик и не затрагивается compiler scope. Это предложение границы Stage7 для явной сверки с владельцем B2; оно не отменяет ни один обязательный predecessor и не позволяет назвать весь B2 завершённым. Если выбранный сценарий требует нового Stage Compiler, его путь добавляется полностью.

## 6. Техническое заключение по токенам и расходам

### 6.1. Пять независимых величин

| Величина | Назначение | Правило |
| --- | --- | --- |
| Контекстное окно модели | Вместимость одного запроса и генерации по семантике конкретного API | Привязано к endpoint/model/revision/template; UNKNOWN не повышается настройкой UI |
| Порог сжатия Chat | Когда предложить управляемое сокращение активного представления | Пользовательский default **250 000**, изменяемый. Не квота расходов, не обещание окна |
| Максимум ответа | Запрошенный пользователем предел | Default **10 000**, расширенный **20 000**; effective value зависит от модели. Несовместимость показать до отправки, не молча обещать недоступное |
| Reasoning / вся генерация | Дополнительная или вложенная часть вывода | Отдельный параметр только при реальной поддержке. Если общий cap включает reasoning, доступный ответ может быть меньше; UI обязан это объяснить |
| Накопительные обязательства | Уже понесённый и ещё возможный расход Workspace | Durable aggregate для всех маршрутов. Нет сброса при новом Chat, смене модели, restart, compression или переносе |

Для text-only профиля с общей вместимостью: `input_upper + generated_upper + safety_margin <= context_limit`. Input включает разрешённую историю, активную Workspace Memory, system, шаблоны и tool schemas. Если у API раздельные input/output/reasoning limits, проверять их по паспортному контракту, не подставлять в универсальную формулу. JSON-байты нужны для ограничения передачи и фиксации тела, но не равны токенам модельного контекста.

Рабочий порог действия — меньший из пользовательского порога и доказанной доступной вместимости после резервов. Сохранять requested 250k и показывать effective threshold отдельно. Если даже обязательные правила и резерв не помещаются, безопасный отказ; не удалять инструкции ради успешного send. Пока сжатие не реализовано, UI предлагает явное уменьшение разрешённого контекста или другую модель, без скрытой отправки компрессору.

Официальная карточка GigaChat 2 Lite указывает окно **128 000** токенов (E2). Это конкретный пример, почему 250 000 нельзя принять за универсальную вместимость. Проверка доступности именно этой модели в аккаунте и её runtime-пределов не выполнялась.

### 6.2. Один агрегат, несколько представлений

Рекомендация — расширить существующие S2/S3a. Каждая физическая попытка хранится один раз и имеет `workspace_id`, необязательные `chat_id/turn_id/run_id/node_call_id`, logical_call_id, provider_attempt_id, route, model/endpoint profile и policy revision. Chat/RUN/компрессор — атрибуция и подлимиты внутри общего контура, не новые кошельки. Бюджет Ordinary-сессии может ссылаться на тот же envelope, если это следует CHAT-A01; не заводить два равных независимых остатка.

Под общей writer-транзакцией проверять:

`settled_usage + unresolved_liabilities + new_attempt_reserve + unspent_protected_reserve <= approved_workspace_limit`.

Та же попытка входит в Workspace и в отчёт Chat, но эти отчёты не складываются друг с другом. Применимые RUN/route/session ceilings проверяются в той же транзакции. Protected reserve не начисляется дважды, когда обязательная проверка уже получила собственную reservation. Числовой Workspace limit, срок действия grants и пополнение остаются решениями пользователя; срок или новая revision не стирают старые расходы.

Сложность по сравнению с текущим S2: дополнительная проекция агрегата и версия политики Workspace, независимая от immutable RUN/Turn snapshot. Уменьшение текущего лимита ниже обязательств запрещает следующие действия; старый принятый Turn не обходит отзыв прав. Повышение лимита — явное изменение политики, не reset. Самый простой безопасный старт сохраняет сериализацию изменяющих операций Workspace; HTTP ждать под файловой блокировкой нельзя.

Чисто локальный ledger не контролирует чужие приложения с тем же API-аккаунтом. Если нужен общий account-wide потолок между Workspace, это отдельное будущее решение, которое нельзя выдать за уже утверждённую квоту CHAT-A01.

### 6.3. Долговечный допуск и неопределённые исходы

Предлагаемая последовательность: авторизовать источники → собрать окончательное тело → определить верхние оценки → под блокировкой проверить все обязательства и сохранить RESERVED → повторно проверить актуальные запреты → долговечно отметить потребление единственного разрешения на попытку → отправить те же bytes → сохранить terminal/usage → отдельно зафиксировать ответ Turn/RAW.

Состояние непосредственно перед I/O означает «могло быть отправлено», а не доказанное получение провайдером. Падение между ним и фактическим send оставляет консервативное обязательство. Receipt с `replayed=true` не даёт второй send. Hash связывает байты, но не является ни полномочием, ни гарантией exactly-once у провайдера; permit должен также связывать route, endpoint/account reference, идентичность и revision. Секретные заголовки в ledger не сохраняются.

Новый retry — новый provider_attempt_id и новый резерв в той же цепочке. Двойной клик/F5 с тем же idempotency key возвращает прежний Turn. После timeout/cancel/обрыва UNKNOWN не освобождается по таймеру; поздний достоверный usage уточняет ту же запись. Отмена UI не доказывает остановку удалённого вычисления. Автоматические retry SDK, redirects, middleware и fallback модели входят в inventory; скрытый resend запрещён. NOT_SENT допускается лишь при доказанной границе до физического начала. При превышении фактического usage над резервом сохранить реальный расход, отметить breach и запретить следующие отправки до разбора профиля, а не обрезать счётчик.

Сбой до reserve — отказ без send; после send при ошибке записи terminal — остаются прежние обязательства, успех не выдаётся. В B предусмотреть запас места для SENT/terminal/reconciliation уже принятых попыток: текущий общий предел 4096 событий иначе может блокировать завершение вместе с новыми резервами. Компактация позднее сохраняет итоги, unresolved записи, dedup identities и версии; нельзя просто обрезать журнал.

### 6.4. Usage без двойного счёта

Нормализованный факт содержит значения и признаки `known/unknown/not_applicable`, источник и версию семантики. Полезные поля: input_total, input_cached, input_uncached, output_total, reasoning, answer, provider_reported_total, billed_tokens, money/валюта/версия тарифа. Не все поля обязаны быть известны. Raw usage не показывать автоматически целиком; сохранить разрешённые числовые поля и provenance.

Если cached входит в input_total, а reasoning входит в output_total, общий объём равен `input_total + output_total`; cached и reasoning показываются как вложенные. Ответ можно вычислять как разность только при документированной семантике, что прочих категорий нет. У другого API cached может быть отдельным слагаемым — адаптер явно сообщает этот вариант. Отсутствующее поле не превращается в ноль; противоречивые или отрицательные значения дают anomaly и fail-closed учёт.

**Конкретно GigaChat:** официальное руководство E1 описывает prompt_tokens после исключения precached, completion и тарифицируемый total. Поэтому для этой схемы вход с кэшем — `prompt + precached`, а тарифицируемые токены — `prompt + completion`; это разные метрики. Текущий S2 учитывает такое различие в `_input_of()`. Этот алгоритм нельзя без адаптации переносить на API, где cached уже вложен в prompt. При отсутствующем precached текущий S2 оставляет консервативную оценку входа; это обязательство, его нельзя подписывать «точно измеренные входные токены».

Стоимость считать только по верифицированному тарифу нужного аккаунта, модели, даты и единиц; на mixed-model Workspace суммируются денежные обязательства общей валюты, а токеновые категории остаются видимы по модели. До подтверждения — `UNKNOWN`, не «0 ₽». При reserve не рассчитывать на cache hit; подтверждённая экономия учитывается при reconciliation. Бюджет внешнего платного инструмента — отдельная размерность той же системы обязательств, не выдуманные LLM-токены.

### 6.5. Начальный допуск, калибровка и provider cap

Профиль возможностей — расширение существующего каталога/подключения с versioned evidence, не второй список моделей. Ключ включает provider, endpoint/API version, model/revision, tokenizer/template; для локального backend — также параметры экземпляра. ModelSpec `enabled` и EVM configured не равны доказанному cap.

E3/OpenAPI описывает `max_tokens` как ограничитель генерации, однако прочитанная схема не доказывает отдельно reasoning, максимальную допустимую величину каждого endpoint и поведение при отмене. **Provider cap enforcement: UNKNOWN / NEEDS VERIFICATION.** Синтетический transport проверяет передачу параметра, но не исполнение удалённой моделью.

Разделить два доказательства. До первого live нужен обоснованный верхний резерв: достоверный tokenizer/template либо документированный и независимо оценённый консервативный envelope конкретного профиля с ограниченным размером запроса. Историческая средняя bytes/token или запас 20% не дают математического верхнего предела; bytes/4 особенно нельзя объявлять гарантией. Разрешение такого начального профиля требует адресного решения и проверки S2, не ослабляет missing_profile=DENY. Если верхнюю границу всей оплачиваемой генерации установить нельзя — live остаётся HOLD; можно выбрать другую доказанно ограниченную модель. Заявлять «сначала бесплатно проверим cap реальным запросом» нельзя.

После safety-gates короткая разрешённая серия Stage7 уточняет usage и соответствие документации. Она не является стресс-тестом максимального окна. Позднее Статист калибрует estimates на репрезентативных данных: язык, код/JSON, tool schemas, размеры, модель/revision; смена template/revision инвалидирует неподходящий профиль. Статист не может сам повысить hard limits. Так устраняется логический круг калибровки без пробного обхода защиты.

### 6.6. Циклы, инструменты и видимость

Перед каждым следующим LLM-вызовом и каждым инструментом проверять актуальные права, живой owner/Turn/RUN, отмену, остаток Workspace и обязательный verification reserve. Локальный бесплатный tool тоже потребляет ограничение шагов/времени и может увеличить будущий контекст. До мутации резервировать обязательную последующую проверку, как требует S3c; недостаток — остановка до действия.

Нужны пределы физических попыток цепочки, retries, tool steps, глубины вложенных вызовов и повторения одинакового действия без нового результата; общее число сообщений обычного чата не ограничивать произвольной постоянной. Детектор повторов — дополнительная защита, он не заменяет durable счётчик. Rate/concurrency limits ограничивают нагрузку отдельно от расходного лимита.

UI показывает контекст по составляющим; requested/effective output; известный input/output/reasoning; settled, reserved и UNKNOWN отдельно; расход Chat как часть Workspace; остаток с указанием единиц и достоверности. DENY содержит код и понятное действие: меньше контекста, подходящая модель, проверка неизвестной попытки, явное изменение бюджета. Кнопка «повторить» не должна скрыто создавать новый оплачиваемый запрос.

## 7. Альтернативы хранения, privacy и диагностика

| Вариант | Выгода | Недостаток / решение |
| --- | --- | --- |
| Расширить существующие S2/S3a и Run Store | Сохраняет текущие locks, recovery, данные и доказательства | Рекомендуется. До live нужны aggregate, миграция, privacy и тесты ёмкости |
| Отдельный ledger для web/компрессора/Blueprint | Простое локальное подключение | Отвергнуть: несколько авторитетных остатков и обход CHAT-A01 |
| Новый общий SQLite ledger | Может упростить транзакции/запросы при росте | Сейчас не обоснован измерениями; новая миграция и owner. Рассматривать только как замену внутреннего storage, с отдельным решением, не как второй параллельный бюджет |
| Внешний broker/распределённые leases | Может обеспечить один owner между хостами | Новая служба и отказоустойчивость; не обязательный старт для одного хоста. Нельзя обещать clone fencing без такого механизма либо доказанного ограниченного rollout |
| Только provider cap и postfactum счётчик | Мало кода | Отвергнуть: не защищает накопительный расход, retries, UNKNOWN и tools |

**RAW wire в ledger.** Рекомендуемый будущий формат хранит минимальный неизменяемый факт reserve: измеренные bytes/hash, верхние обязательства, binding, policy/profile версии и transition evidence. Replay восстанавливает уже принятые обязательства, не переоценивает старые запросы новым mutable estimator. Тело держится в памяти до send; восстановление не пересылает его автоматически. Разрешённый исходный контекст восстанавливается по существующим RAW/variant IDs, без копии в каждой ledger generation. Это требует новой версии S3a, проверки provenance и миграции старого формата; простое удаление `wire_utf8` сломает сегодняшний replay. Если точное тело всё же нужно сохранять, его retention/доступ согласовать отдельно; hash не даёт права раскрывать RAW.

**U5.** Существующий `server.py` уже направляет runtime-логи в локальные пути и проверяет невложенность в Workspace; compressor использует APP_DATA_ROOT. Это полезная база, не полный доказанный privacy gate для каждого источника событий. Проверять конечный разрешённый путь, смену root, links/reparse, fallback и все sinks, включая исключения, stderr, trace, browser errors и support export. Одного `.gitignore` недостаточно. Авторитетные минимальные бюджетные факты в существующем Workspace storage отличаются от технических журналов: их нельзя удалить или вынести без согласованного механизма восстановления переносимого учёта.

Маскирование выполняется **до записи и экспорта**, только для чувствительных фрагментов строки. Оставлять полезный остаток, стабильный случайный event_id, line/fragment ordinal и тип маски. ID не вычислять из секрета: обычный хеш короткого секрета допускает перебор. При повторном отображении тот же event сохраняет ID. Экранировать управляющие символы, чтобы payload не создавал ложные строки журнала. Нужны тесты split/multiline/encoded secrets, bearer/ключей/URL, вложенного исключения и сохранности соседнего текста; неизвестный формат — безопасное сообщение с ID, без raw echo. Сейчас compressor формирует исключения с полным ответом провайдера: `_request_gigachat()` — адрес для будущего устранения утечки, не подтверждение фактической публикации секрета.

**Отдельный шифрованный архив секретных строк не включать.** Если пользователь позднее увидит необходимость: отдельное opt-in решение с минимальным scope, OS-защищённым ключом вне Workspace, шифрованием с проверкой целостности, аудитом доступа без секретов, явным сроком хранения, удалением вместе с резервными копиями и процедурой восстановления ключей. Автоматически писать туда оригинал при redaction сейчас нельзя. Политика RAW пользовательского чата решается отдельно от диагностики.

## 8. Минимальный безопасный маршрут до GigaChat

1. Выбрать **один** существующий GigaChat profile/endpoint и text-only ordinary сценарий; подтвердить доступный протокол и безопасный верхний резерв. Все остальные reachable sends всё равно включить в S3b: принятый общий guard либо доказанный серверный DENY. Отключённая кнопка не доказывает недостижимость.
2. Принять A/B/C/D/E по разделу 5. Сохранить отдельность independent acceptance и USER GO. Закрыть применимые Stage5 cancel/retry/isolation/Windows требования; clean-Windows FOLLOWUP нельзя молча снять ради скорости.
3. Рассмотреть **свежий специально выделенный Workspace** для первого ограниченного live только по явному rollout-решению пользователя. Это позволяет не писать импорт старых audit как условие именно первой пробы, если принятое ограничение допуска это разрешает. Existing Workspace остаётся закрыт до adoption; нельзя переименовать/клонировать старый Workspace или переносить запросы между новыми ради сброса долга. Если пользователь выбирает текущий Workspace, миграция обязательна до live.
4. Утвердить точные endpoint/model/account scope, разрешённые данные, числовой совокупный и разовый предел, число физических попыток, retry policy и stop criteria. Значения в этой рецензии не назначаются. «Привет», «Как дела?», «Пока» — короткие примеры из U6, не три уже разрешённых запроса.
5. Выполнить разрешённый диалог через тот же production guard, сохранить результат и usage, сверить ledger и reopen. При UNKNOWN, cap breach, ошибке фиксации либо исчерпании лимита остановиться без автоматического повторения. Live-проверка не запускает tools, Codex, Colibri или Blueprint.

Сжатие длинного чата, автоматическая Workspace Memory, все доступные модели и полный аналитический Статист не нужны короткому первому диалогу. Однако модельный admission, privacy, счётчики, накопительные обязательства и обязательные B2-гейты нужны с первого запроса. Свежий Workspace — предложение уменьшения объёма rollout, а не основание обойти действующее условие приёмки.

## 9. Сжатие, память и Blueprint после MVP

**Сообщение.** Повторно использовать RAW/message_id, Context Variants и restore из `context_storage.py`; вынести зависимость компрессора от `server` к общему транспортному контракту. Вызов компрессора, корректирующий retry и отдельная проверка качества, если включена, получают физические attempt IDs и оплачиваются из того же Workspace. Сохранить настройку модели и степени сжатия. Старые `MAX_COMPRESSOR_ATTEMPTS=2` и процент сокращения не заменяют модельный и расходный admission.

Текущий guard измеряет символы; меньшая строка может иметь больше токенов другого tokenizer. Приёмка должна сравнивать токены нужной модели и сохранность смысла. Утверждённые правила пользователя и важные решения выделить как защищённые источники: summary не может редактировать их authority. Проверять обязательные числа, имена, paths, ограничения и связь с RAW; семантическая LLM-проверка — дополнительное evidence, не математическая гарантия отсутствия потерь. При несогласии/неизвестности остаётся прежнее активное представление.

**Целый чат.** Сначала закрепить неизменяемый snapshot: ordered message IDs, hashes, роли, состояния Turn, граница истории и версия активного контекста. Архивировать его проверяемым manifest существующих источников; физическая резервная копия нужна там, где иначе не обеспечено сохранение, но не как второе редактируемое дерево переписки. Делить историю по смыслу, удерживая пары tool-call/result и завершённые turn; слишком большой одиночный материал обрабатывать адресно, не silently truncate.

Для каждой части сохранить промежуточную summary, исходные ID, версию модели/промпта, оценку потерь, attempt и checkpoint. Затем выполнить ограниченное число reduce-ступеней, пока результат укладывается в целевой бюджет. При росте вместо сокращения, превышении depth/attempt/budget или потере защищённого материала — STOP. Каждая ступень резервируется отдельно, а верхняя оценка работы показывается до старта; compression не должна запускать саму себя без предела.

Применение новой сводки — отдельная атомарная смена активного представления после проверки и явного разрешения. Пока идёт вычисление, новые сообщения остаются отдельным хвостом; при смене исходной revision merge допустим лишь по проверенному контракту, иначе конфликт. Crash/restart не повторяет неизвестный вызов; можно продолжить с подтверждённых checkpoint. Restore возвращает RAW по ID, не создаёт повторные сообщения и не обнуляет расход. Оригиналы имеют независимый retention, не удаляются потому, что summary успешна.

**Workspace Memory.** Начать с ручного создания/редактирования и явной команды «сохранить в память». Предложение модели и commit — разные операции. Запись: стабильный ID, категория/authority, version, источник Chat/message/RAW, автор, права, статус и supersedes. Конфликтующие решения показать пользователю; LLM-summary не становится системным правилом. Использовать один существующий слой Context/Project Context с совместимым расширением; не назначать заранее новый второй registry или базу. Точный schema требует отдельного анализа совместимости.

Активная память — ограниченная выборка, архив не ограничивается её окном. Выборка и разрешённый получатель фиксируются в снимке запроса; обновление памяти не меняет уже принятый Turn. Новый Chat получает только разрешённую память своего Workspace; чтение чужих чатов не следует из общей принадлежности. Введение ручной памяти не зависит от законченного Статиста или многошагового compressor. LLM-assisted extraction требует общих защиты, прав и отдельного назначения.

**Статист.** До первого live подготовить пассивные поля из RM37-06: profile revision, known/estimated tokens, monotonic queue/start/first-content/end times, outcome, нагрузка при наличии измерения. Для нынешнего non-stream ответа first-content time не выдавать за настоящий TTFT генерации. После MVP строить зависимости latency/error от контекста, показывать размер выборки и неопределённость; не заявлять скорость/окно по одному «Привет». LLM-интерпретатор расходует тот же бюджет и не меняет safety-политику. Активные benchmarks требуют отдельного лимита и GO.

**Blueprint.** В №43 передать один contract Context Source: источник/version/разрешённый fragment, recipient/ACL, byte/token estimate, provenance и expiry/freshness. Блок получает ссылку на существующего исполнителя (`executor_ref`) и snapshot, а не свою авторизацию/transport/ledger. Context Source, Compress, Memory Propose/Commit и Metrics используют общие сервисы; плановые имена узлов не объявляются утверждённой схемой. П0/П1/П3/П4 и последующие П5–П8 сохраняются. RUN/node-call/provider-attempt — различные идентичности. Параллельность и циклы Blueprint появляются только в предусмотренных этапах с общим admission. Приоритет пользователя «после рабочего GigaChat — Codex adapter» остаётся; эта рецензия его не переставляет.

**Что подготовить до live:** контракты источников и usage, version/provenance, возможность восстановления по ID, пассивную телеметрию, offline-негативы и admission для будущего compressor. **Что отложить:** реальные компрессии длинных переписок, многошаговый UI, автоматические кандидаты Memory, полный dashboard и активные benchmarks, LLM-Статист, исполнение Blueprint и распределённый model manager. Подготовка контрактов не означает запуск этих направлений.

## 10. Открытые решения, проверка и итоговая рекомендация

Уже утверждены: U1–U6, defaults 250k/10k/20k с модельными ограничениями, CHAT-A01, одно ядро, сохранение Tkinter, приватность логов, future-направления сжатия/Статиста/памяти и канон №43. Повторного выбора этих требований не предлагается.

**Для отдельного решения остаются:**

- Накопительные числовые потолки/единицы Workspace и стартового live, правила grant/population/reset без потери истории; смешанные модели и платные tools.
- Точный начальный endpoint/model и достаточное evidence для cap, tokenizer/верхней оценки; поведение requested/effective 10k/20k при несовместимости.
- Принятие предложенной группировки и полноты Stage6/S13a; rollout в свежий Workspace или предварительная миграция старого; матрица Stage5/clean-Windows/legacy OPEN.
- Формат ledger v2 без RAW duplication, engine migration, capacity/terminal headroom, срок хранения и ownership при переносе; active-active остаётся отдельно неподдержанным до доказательства.
- Момент применения compression, защищённые материалы, критерии потерь и rollback; формат/размер активной Memory, explicit commit и разрешения получателя.
- Порядок после MVP в пределах сохранённого пользовательского приоритета; шифрованный секретный архив — только как отдельное будущее решение при реальной необходимости.

Новые проверки должны быть направлены на риск: агрегатная гонка двух Chat/RUN/компрессора; смена revision и endpoint между reserve/send; replay permit; crash до/после I/O и RAW commit; usage с вложенным reasoning/cached, missing/null/malformed/late; исчерпание ёмкости перед terminal; no-network denial всех маршрутов; отмена и отозванные права; privacy до любого sink; compression loss/restore/stale snapshot; Memory ACL/conflicts и Blueprint recipient. Мутационные негативы должны показывать отказ слабой реализации; зелёные mocked happy paths недостаточны.

**Ограничения этой рецензии:** выполнены source/document review, read-only проверка опубликованных heads и механическая проверка собственного пакета. Новые runtime/pytest/CI, GUI/Obsidian UI, чистая Windows, hardware power-loss, действующие provider caps, тариф аккаунта, реальные LLM/OAuth, стоимость и нагрузка **NOT RUN / UNKNOWN**. Сохранённые чужие PASS приведены с границами; они не являются новым исполнением Астры. Полная инвентаризация динамических сторонних transport не выполнена в аналитическом scope. Проверка графовой связи выполнена по синтаксису и единственному точному имени целевого файла; фактическая перерисовка Obsidian не проверялась.

Внешние первичные источники проверены 09.11.2026 чтением публичной документации, без inference и credentials. Они используются только в указанных утверждениях; полный текст не копировался:

Сохранить последовательные safety-gates, общие RAW/Turn/Run/Model Registry, ограниченный live после этапа 6, восстанавливаемое сжатие, полномочия Web Alarm, fallback Tkinter и №43. Экономить на повторной разработке и ожидании независимых работ; обязательные доказательства сохранять. Этот документ остаётся предложением до решения пользователя.
