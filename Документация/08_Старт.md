# Старт

Стартовый документ проекта `ag_llm / GigaChat Ultra Local Agent`.
Этот файл нужен как **точка входа в проект для нового чата или нового агента**.
Если пользователь пишет **«Старт»**, сначала использовать этот документ как краткую карту проекта, а затем читать только те документы, которые действительно нужны для текущей задачи.

> Важно: этот файл адаптирован под проект `ag_llm`. Он не является копией шаблона из другого проекта и не должен навязывать чужую структуру задач, отчётов или папок.

## COLD START / FAST ROUTE

Для крупной LLM: прочитать этот `08` → обязательный `18_Регламент сопровождения документации.md` → краткую карту `01_Архитектура и текущее состояние.md` → определить текущую TASK и по реестру раздела 3 прочитать **профиль активной архитектурной ветки**. Профиль обязателен независимо от того, в каком Chat возникла TASK: Workspace / Chat / Context → `03`; Multi-model → `11`; Voice / ASR → `12`; Verifier / Final Audit / Permissions → `13`; Compression → профильное архитектурное решение о сжатии. При пересечении веток выбрать primary и только нужный secondary profile. Технические CURRENT-факты сверять с кодом, runtime и доступным evidence.

Не читать всю документацию подряд. О существовании библиотеки контекстов `14`–`16` нужно знать, но читать её только по Context Reading Policy в `18`, когда тема TASK этого требует. Она не является автоматически подключаемым runtime context.

## 2. Назначение проекта

Проект создаёт локальную агентскую среду для работы с проектами, файлами, Workspace, Chat и управляемым контекстом.

Мультимодельный фундамент уже реализован.

Текущая схема MAIN CHAT:

    Ultra UI
        ↓
    Agent Runtime
        ↓
    MAIN CHAT MODEL ASSIGNMENT
        ↓
    MODEL REGISTRY
        ↓
    GigaChat provider
        ↓
    selected GigaChat model

Отдельно существует Context Compressor:

    RAW MESSAGE
        ↓
    COMPRESSOR RUNTIME
        ↓
    COMPRESSION MODEL ASSIGNMENT
        ↓
    MODEL REGISTRY
        ↓
    selected GigaChat model
        ↓
    COMPRESSION PROPOSAL

Фундаментальный принцип:

    MODEL ≠ AGENT

Контекст, Workspace, Chat, tools, permissions, state, backup,
verification и trace принадлежат Agent Runtime, а не физической LLM.

Runtime явно собирает необходимые источники контекста для
конкретной роли и конкретного RUN.

One MODEL может использоваться разными Role с разными
Role Context, Context Policy и Tool Set.

Основные файлы runtime:

    server.py
    ultra_ui.py
    context_storage.py
    model_registry.py
    compressor_runtime.py
    compressor_settings.py
    workspace_runtime_settings.py
    ui_state.py
    Start_Ultra.cmd
    agent_global_context.py

Полный список существующих Markdown и их ответственность зафиксированы в единственном каноническом реестре раздела 3. Список не дублируется здесь.

Не добавлять новые [[Wiki Links]].

### Маршрут новой TASK

После команды пользователя **«Старт»** или при переходе к новой значимой технической TASK:

1. Прочитать этот файл и реестр ответственности выше, затем обязательный meta-document `18_Регламент сопровождения документации.md`.
2. Прочитать `01_Архитектура и текущее состояние.md` как карту фактически работающей системы и определить текущую TASK.
3. По теме TASK выбрать и прочитать профиль активной архитектурной ветки; дополнительные профили — только при реальном пересечении тем. Сверить необходимые CURRENT-факты с актуальным кодом.
4. Одновременно с технической постановкой сформировать отдельный Documentation Block по правилам `18` и ниже.

`Документация/00_Главная - карта проекта.md` помогает с общей навигацией; остальные документы читать **по теме и необходимости**. Не нужно автоматически перечитывать всю папку документации перед каждой небольшой задачей.

Профильные документы не наследуются от предыдущей TASK, темы или Chat и не выбираются только по памяти: в одном Chat TASK A может относиться к `13`, следующая TASK B — к `11`, затем TASK C — к `12`. Если изменение действительно пересекает подсистемы, Documentation Scope может включать несколько профильных документов (например, `03` и `11` для изменения Context и Model Assignment). Выбор должен быть минимальным и обоснованным; пересечение тем не означает обновление всей документации.

### Обязательный Documentation Workflow

Значимая техническая / runtime / architectural TASK **не считается полностью сформированной, пока для неё одновременно с технической постановкой не подготовлен отдельный Documentation Block**. При схеме «БЛОК 1 — техническая TASK» сразу готовится «БЛОК 2 — DOCUMENTATION». При схеме «Большой блок + Малый блок» сразу готовится следующий «DOCUMENTATION BLOCK». Число технических блоков может отличаться; документационный блок остаётся отдельным. Documentation-only TASK не требует рекурсивно создавать ещё один блок о собственном изменении документации.

Минимальный каркас блока:

```text
DOCUMENTATION BLOCK
TASK TOPIC: <тема / подсистема>
PROFILE DOCUMENTS: <один или несколько профильных документов из реестра>
CHECK 01: YES / NO + причина
OTHER AFFECTED DOCUMENTS: <только реально возможные>
AFTER TECHNICAL RESULT:
- сверить code / diff / tests / live evidence;
- обновить только подтверждённые факты;
- убрать ставшие ложными CURRENT STATUS;
- проверить ссылки и роли документов;
- не переписывать исторический журнал задним числом.
REGISTRY IMPACT: YES / NO
CONTEXT LIBRARY IMPACT: YES / NO
CONTEXT DOCUMENTS: <14 / 15 / 16 / другой профильный документ при YES; иначе —>
```

`REGISTRY IMPACT` обычно `NO`, если новый файл не создаётся и роль существующих документов не меняется.

`CONTEXT LIBRARY IMPACT` определяется заново для каждой значимой TASK, которая касается контекста, независимо от Chat или предыдущей TASK. `YES` означает возможное постоянное изменение содержания, назначения либо состава подготовленных контекстов: Global / Project Context, устойчивое правило, новый или изменённый вариант, отдельная роль / LLM либо будущая preset-логика. Указать конкретные `CONTEXT DOCUMENTS`, а после фактического результата проверить и обновить только затронутые `14`, `15`, `16` или будущий профильный документ. Изменение runtime context не обновляет документальную копию автоматически; изменение Markdown не меняет runtime context. Для не связанных с контекстами TASK не нужно читать всю библиотеку.

**Формирование не означает исполнение.** Documentation Block исполняется только после фактического результата технической работы. Он не должен заранее объявлять план реализованным. Источники истины в порядке проверки: актуальный код, реальный diff, выполненные tests/checks, доступное live runtime evidence и лишь затем существующая документация.

После значимой технической TASK обязателен **Documentation Impact Check**:

1. Изменились ли фактическая архитектура, lifecycle подсистемы или production-механизмы?
2. Изменился ли статус прежде запланированной функции?
3. Какой профильный документ отвечает за тему и какие общие документы реально затронуты?
4. Есть ли в затронутых документах старые утверждения, ставшие ложными из-за изменения?

Проверяются `01`, профильный документ текущей TASK и действительно затронутые документы; всю папку перечитывать не требуется. Противоречащий **текущий статус** нужно заменить или переработать, а исторические записи журнала не переписывать задним числом. Если фактического влияния нет, искусственных правок документации не делать.

Для контекстной TASK в этом Check отдельно подтвердить `CONTEXT LIBRARY IMPACT: YES / NO`. При `YES` сверить указанные библиотечные документы с принятым постоянным изменением; при `NO` не править их искусственно.

`01_Архитектура и текущее состояние.md` — главный краткий источник о фактически работающей архитектуре. После значимого изменения проверить необходимость его обновления: зафиксировать краткий факт, назначение и явную отсылку на профильный документ. Подробные lifecycle, компоненты, состояния, правила, ограничения и edge cases принадлежат профильному документу. Если он уже существует, не создавать новый архитектурный Markdown для той же темы и не копировать большие разделы в `08` или `01`.

Подробное каноническое описание каждого факта имеет одного понятного владельца. Краткое упоминание и отсылка допустимы для навигации: `01` даёт факт и профильную отсылку, `13` владеет подробной verification architecture, `08` — только routing и ownership. Если два профильных документа претендуют на одни подробности, сначала явно разделить их ответственность, а не вести параллельные копии.

Если TASK действительно создаёт новый Markdown, она **не завершена**, пока в той же документационной работе не проверено покрытие существующими документами, не определена уникальная роль нового файла, он не внесён в этот реестр с правилом чтения / обновления и при необходимости не обновлена общая навигация проекта. При дублировании по умолчанию расширять существующий профильный документ либо явно разрешать конфликт ответственности, а не создавать новый. При изменении роли уже существующего документа обновлять его запись в реестре в той же TASK.

Если новый Markdown хранит самостоятельный подготовленный контекст или вариант, дополнительно проверить отсутствие смыслового дубля и зарегистрировать его в `16_Список_контекстов.md`; определить уникальное назначение, внести в общий реестр выше и при необходимости обновить HUB `00`. Это правило относится к документальной библиотеке, не создаёт runtime registry и не подключает файл к LLM.

## 4. Текущее состояние runtime — короткий ориентир

Рабочий UI — Tkinter. Main Chat использует Model Registry и назначенную GigaChat модель; Compressor и Verifier имеют отдельные назначения. Immutable RAW / SUMMARY Working Representation и базовое управляемое сжатие реализованы. Normal SUCCESS требует valid Final Audit PASS; текущий V.5 допускает не более двух correction handoffs в том же RUN. Permission escalation реализована в коде и покрыта tests, без подтверждённого live пользовательского RUN. Mutation intent trace — diagnostic-only; автоматический Execution Consistency gate отключён.

Подробный CURRENT STATUS — в `01_Архитектура и текущее состояние.md`. Model Registry и роли — `11`; Final Audit, permission и evidence — `13`; Workspace / Chat — `03`; compression — профильное архитектурное решение о сжатии. Local Provider, per-Chat assignment, универсальные Agent Profiles / Context Policy, Coordinator, Voice / ASR и Web UI остаются будущими.

Следующие эксплуатационные заметки читать только по теме TASK; они не входят в обязательный cold-start маршрут.

## 5. SAFE Mode — текущее проверенное состояние

SAFE Mode v1 уже реализован и проверен.

Есть отдельные настройки:

```
Разрешить чтение
Чтение только в: <scope>

Разрешить запись
Запись только в: <scope>

Разрешить удаление
Удаление только в: <scope>

VERIFY
GUARD P1
```

Пример безопасной настройки для документации:

```
READ = ON
READ SCOPE = .

WRITE = ON
WRITE SCOPE = Документация

DELETE = OFF

VERIFY = ON
GUARD P1 = ON
```

В таком режиме Ultra физически не может читать или писать за пределами разрешённой области.

Mutation schemas могут быть видны модели и при выключенной записи; server execution gate отказывает в действии по текущим разрешениям.

Сервер проверяет путь до выполнения операции.

Пример уже проверенного поведения:

```
WRITE SCOPE = Документация
```

Попытка записи:

```
SAFE_DENY_TEST.md
```

в корень workspace была остановлена сервером через `PermissionError`.

Запись:

```
Документация/SAFE_ALLOW_TEST.md
```

успешно прошла.

## 6. Автобэкап

Бэкап создаётся **до первого API-вызова назначенной основной модели**, а не по таймеру.

Порядок:

```
Пользователь нажал Отправить
    ↓
сервер создаёт backup
    ↓
backup успешно завершён
    ↓
только после этого запускается Ultra
```

Защищённая папка бэкапов:

```
%LOCALAPPDATA%\GigaChatUltra\workspaces\<workspace_id>\backups
```

Эта папка находится вне workspace и не должна быть доступна агенту.

## 8. Важный принцип работы с Ultra

Ultra не всегда надёжно удерживает границы задачи только по текстовой инструкции.

Поэтому для серьёзных изменений использовать схему:

```
PLAN
    ↓
APPROVAL
    ↓
EXECUTE
    ↓
VERIFY
```

Для рискованных задач сначала предпочтителен read-only запуск.

После согласования:

- включить запись;
- задать узкий write scope;
- учитывать, что обязательный server-side backup выполняется автоматически;
- дать точную исполнительную TASK.

Не полагаться только на обещание Ultra «ничего не менять».

## 9. Логи важнее отчёта Ultra

Финальный текстовый отчёт Ultra может не полностью совпадать с реальными действиями.

Источник истины:

```
ЛОГ ДЕЙСТВИЙ
%LOCALAPPDATA%\GigaChatUltra\workspaces\<workspace_id>\logs\<run_id>.jsonl
```

Если Ultra пишет:

```
«Файл не изменялся»
```

но trace показывает:

```
write_file(...)
```

считать фактом именно запись в trace.

При review сначала смотреть:

```
tool calls
permission_denied
write_file
run_finished / run_failed
backup events
```

## 14. Управляемое сжатие контекста — маршрут

Базовый per-message lifecycle уже работает: immutable RAW, активная RAW / SUMMARY Working Representation, Compressor Proposal и решение пользователя. Три независимых вызова COMPRESS → VERIFY → FINALIZE, Review Chat и автоматическое управление бюджетом контекста остаются будущими. Базовый lifecycle покрыт существующими tests; новая live-проверка в этой документационной TASK не выполнялась.

Подробности и ограничения принадлежат `Архитектурное решение - управляемое сжатие контекста.md`; назначения моделей — `11_Мультимодельная архитектура и назначение LLM.md`, общие Workspace / Chat структуры — `03_Чаты, проекты и контекст.md`.
