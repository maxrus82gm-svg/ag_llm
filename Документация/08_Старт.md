## 2. Назначение проекта

Проект создаёт локальную агентскую среду для работы с проектами, файлами, Workspace, Chat и управляемым контекстом.

Мультимодельный фундамент уже реализован.

Текущая схема MAIN CHAT:

    Ultra UI
        ↓
    Agent Runtime
        ↓
    MAIN CHAT MODEL ASSIGNMENT
        ↓
    MODEL REGISTRY
        ↓
    GigaChat provider
        ↓
    selected GigaChat model

Отдельно существует Context Compressor:

    RAW MESSAGE
        ↓
    COMPRESSOR RUNTIME
        ↓
    COMPRESSION MODEL ASSIGNMENT
        ↓
    MODEL REGISTRY
        ↓
    selected GigaChat model
        ↓
    COMPRESSION PROPOSAL

Фундаментальный принцип:

    MODEL ≠ AGENT

Контекст, Workspace, Chat, tools, permissions, state, backup,
verification и trace принадлежат Agent Runtime, а не физической LLM.

Runtime явно собирает необходимые источники контекста для
конкретной роли и конкретного RUN.

One MODEL может использоваться разными Role с разными
Role Context, Context Policy и Tool Set.

## 4. Текущее состояние runtime

Рабочий интерфейс — Tkinter UI.

Фактический путь MAIN CHAT:

    UI
        ↓
    MAIN CHAT MODEL ASSIGNMENT
        ↓
    MODEL REGISTRY
        ↓
    GigaChat provider
        ↓
    selected model

Уже реализованы:

    MODEL REGISTRY
    GigaChat Multi-Model
    MAIN CHAT MODEL selection
    assistant model provenance
    independent Compressor runtime
    Compressor model selection
    Verifier Model Assignment
    one-shot clean Verifier Runtime
    Independent Final Audit before SUCCESS
    Final Audit Evidence Completeness Gate
    per-message Working Representation
    RAW / SUMMARY switching
    Compression Proposal
    Original Viewer
    Restore RAW
    persistent Working Context

Пока НЕ реализованы как законченные production-механизмы:

    Local Provider
    per-Chat persistent model assignment
    universal Agent Profiles
    universal Context Policy framework
    Compression Review / Discussion Chat
    Multi-Agent Coordinator
    Voice / ASR
    Web UI

SAFE Mode управляется из интерфейса, но реальные ограничения
применяет server.py.

### Independent Verifier / Final Audit

Execution Verifier уже является отдельной runtime role:

```text
VERIFIER MODEL ASSIGNMENT
default = GigaChat 3 Pro (`gigachat_3_pro`)
MODEL REGISTRY
one-shot clean call
typed PASS / FAIL
runtime / protocol errors отдельно
TOOLS = NONE
persistent Verifier Chat = NONE
```

В `run_agent_task(...)` реализован Independent Final Audit перед normal SUCCESS. Server передаёт Verifier исходный RAW TASK текущего RUN и самостоятельно собирает evidence: Candidate Final Response, run / permission / deterministic facts, mutation facts текущего RUN, fresh Git state, а для новых файлов — их актуальное содержимое в разрешённых границах.

Fresh Git state является workspace-wide observation и может содержать pre-existing или external changes. Такие изменения нельзя автоматически приписывать текущему RUN без подтверждения `mutation_facts`.

До model call действует Evidence Completeness Gate. Критически неполное evidence блокирует SUCCESS без вызова Verifier. Semantic FAIL, runtime/protocol error и evidence error также работают fail-closed.

```text
VALID FINAL VERIFIER PASS
= обязательное условие normal RUN SUCCESS
```

Final Audit выполняется и для no-tool / non-mutating normal completion. При этом `TOOLS = 0` само по себе не означает FAIL.

V.4 — следующий этап: semantic FAIL → structured feedback в тот же Executor RUN. Automatic retry пока не реализован.

## 5. SAFE Mode — текущее проверенное состояние

SAFE Mode v1 уже реализован и проверен.

Есть отдельные настройки:

```
Разрешить чтение
Чтение только в: <scope>

Разрешить запись
Запись только в: <scope>

Разрешить удаление
Удаление только в: <scope>

VERIFY
GUARD P1
```

Пример безопасной настройки для документации:

```
READ = ON
READ SCOPE = .

WRITE = ON
WRITE SCOPE = Документация

DELETE = OFF

VERIFY = ON
GUARD P1 = ON
```

В таком режиме Ultra физически не может читать или писать за пределами разрешённой области.

Если запись выключена, `write_file` не должен быть доступен модели как рабочий инструмент.

Сервер проверяет путь до выполнения операции.

Пример уже проверенного поведения:

```
WRITE SCOPE = Документация
```

Попытка записи:

```
SAFE_DENY_TEST.md
```

в корень workspace была остановлена сервером через `PermissionError`.

Запись:

```
Документация/SAFE_ALLOW_TEST.md
```

успешно прошла.

## 6. Автобэкап

Бэкап создаётся **до первого API-вызова основной модели; в текущем runtime — GigaChat Ultra**, а не по таймеру.

Порядок:

```
Пользователь нажал Отправить
    ↓
сервер создаёт backup
    ↓
backup успешно завершён
    ↓
только после этого запускается Ultra
```

Защищённая папка бэкапов:

```
%LOCALAPPDATA%\GigaChatUltra\workspaces\<workspace_id>\backups
```

Эта папка находится вне workspace и не должна быть доступна агенту.

В стартовый backup входят критичные файлы:
```

server.py  
context_storage.py  
workspace_runtime_settings.py  
ui_state.py  
ultra_ui.py  
Start_Ultra.cmd  
.gitignore  
agent_global_context.py
server_context_messages.py
```

Дополнительно перед первой записью в существующий файл сервер сохраняет его старую версию в backup текущего run.

Это проверено на файле:

```
Документация/SAFE_ALLOW_TEST.md
```

Старая версия `TEST` была сохранена до перезаписи на `TEST_2`.

## 7. Tool limit

В `server.py` установлены следующие константы:

```
MAX_AGENT_TOOL_ITERATIONS = 20
MAX_CONFIGURABLE_TOOL_ITERATIONS = 200
```

Это предохранитель от бесконечных циклов и неконтролируемого блуждания агента.

Важно:

- 20 — серверный default.
- UI позволяет задавать tool limit в диапазоне 1..200.
- значение отображается в UI рядом с SAFE Mode / автобэкапом.
- крупные задачи лучше дробить на небольшие контролируемые этапы.

## 8. Важный принцип работы с Ultra

Ultra не всегда надёжно удерживает границы задачи только по текстовой инструкции.

Поэтому для серьёзных изменений использовать схему:

```
PLAN
    ↓
APPROVAL
    ↓
EXECUTE
    ↓
VERIFY
```

Для рискованных задач сначала предпочтителен read-only запуск.

После согласования:

- включить запись;
- задать узкий write scope;
- учитывать, что обязательный server-side backup выполняется автоматически;
- дать точную исполнительную TASK.

Не полагаться только на обещание Ultra «ничего не менять».

## 14. Управляемое сжатие контекста

Базовый механизм управляемого Context Compression уже реализован.

Подробная архитектура зафиксирована в:

Документация/Архитектурное решение - управляемое сжатие контекста.md
Документация/11_Мультимодельная архитектура и назначение LLM.md

Главный принцип:

RAW HISTORY
хранится полностью и неизменно

WORKING REPRESENTATION
определяет текст, реально используемый MAIN CHAT

Сообщение может находиться в состоянии:

FULL
→ используется RAW

или:

COMPRESSED
→ используется active Context Variant / SUMMARY

Текущий рабочий lifecycle:

RAW
    ↓
Сжать
    ↓
Compressor RUN
    ↓
COMPRESSION PROPOSAL
    ↓
пользователь принимает / редактирует / отклоняет
    ↓
active SUMMARY

RAW MESSAGE при этом не изменяется.

Через Original Viewer пользователь может открыть immutable RAW и выполнить:

Восстановить в контекст

После Restore:

active representation = RAW

Старые Context Variants сохраняются.

Повторное LLM compression выполняется от immutable RAW, а не от предыдущей summary.

Базовый lifecycle подтверждён тестами и вручную через реальный UI:

FULL
    ↓
COMPRESS
    ↓
PROPOSAL
    ↓
ACCEPT
    ↓
COMPRESSED
    ↓
ORIGINAL
    ↓
RESTORE
    ↓
FULL

Текущий production foundation использует:

один independent Compressor call
+
soft server guard
+
при необходимости corrective retry
+
user-controlled Proposal

ВАЖНО:

Полноценный независимый Compressor pipeline:

COMPRESS → VERIFY → FINALIZE

пока НЕ реализован как три отдельные production-роли / независимые вызовы.

Independent Execution Verifier при этом уже реализован отдельно и выполняет Final Audit normal Agent RUN. Он не является стадией текущего Compressor pipeline.

Также пока НЕ реализованы:

Compression Review / Discussion Chat
automatic context-budget manager
automatic compression near context limit

Текущий optional Final Check Compressor НЕ является отдельным Independent Verifier.

## 20. Главный принцип

```
Модель предлагает действие.
Сервер решает, разрешено ли его выполнить.
Backup страхует изменение.
Trace показывает, что реально произошло.
Git сохраняет проверенные контрольные точки.
```

Это базовая модель безопасности проекта `ag_llm`.
